<Tldr>
A composite index on `(status, created_at)` is **one** B-tree whose entries are sorted by `status` first and, among equal statuses, by `created_at`: all `cancelled` orders by date, then all `delivered` by date, and so on. A query can use it efficiently only for conditions that select **one contiguous stretch** of that order: `status = 'shipped'`, or `status = 'shipped' AND created_at` in June. `created_at` in June alone is spread over five separate stretches (one per status), so PostgreSQL 17 ignored the index for it and scanned the table. Everything in this session follows from this one sort order.
</Tldr>

## The phone-book order

| Position in the index | `status` | `created_at` |
|---|---|---|
| first entries | cancelled | 2025-01-01 00:00:32 |
| … | cancelled | … rising … |
| ≈ 50,000th | cancelled | 2025-12-31 23:59:… |
| next | delivered | 2025-01-01 00:01:03 |
| … | delivered | … rising … |
| … | paid, pending, shipped | each by date |

The entries are in exactly the order of `ORDER BY status, created_at`. Each entry also carries the row pointer: a ctid in PostgreSQL, the primary key in InnoDB (so the InnoDB entry is really `(status, created_at, id)`), a RecordId in MongoDB.

| Condition | Stretches of the index | Efficient? |
|---|---|---|
| `status = 'shipped'` | 1 | ✓ |
| `status = 'shipped' AND created_at` in June | 1 (narrower) | ✓ |
| `status IN ('paid', 'shipped')` | 2 | ✓ (two descents) |
| `created_at` in June | 5 (June inside each status) | ✗ in general |
| `ORDER BY status, created_at` | the whole index, in order | ✓ |
| `ORDER BY created_at` | — the index is not in this order | ✗ |

## Size: one index, two columns

| PostgreSQL index | Leaves | Note |
|---|---|---|
| `(status)` | 848 | Deduplicated: 5 distinct keys |
| `(created_at)` | 2,733 | |
| `(status, created_at)` | 4,270 | Almost every pair is distinct, so no deduplication; wider entries |
| `(customer_id, created_at)` | 3,832 | |

A composite index is bigger than either single-column index, but it can replace the single-column index on its **first** column (Concept 2).

## PostgreSQL: walking (status, created_at)

| Term | Meaning |
|---|---|
| Contiguous stretch | A run of adjacent index entries; reached with one descent and a walk along the leaves |
| Index Cond | Conditions used to position and stop the walk |
| **✓ One stretch** | The condition fixes the leading column(s), so matches are adjacent |
| **✗ Many stretches** | Matches are scattered through the index |

## MySQL InnoDB: the primary key is the last column

| Term | Meaning |
|---|---|
| Secondary entry | `(status, created_at, id)`: the indexed columns plus the primary key, always |
| `key_len` (EXPLAIN) | How many bytes of the key the access uses: shows how many leading columns were used |
| **✓ Prefix of the key / ✗ Not a prefix** | Same stretch rule as PostgreSQL |

## MongoDB: compound indexes and direction

| Term | Meaning |
|---|---|
| Compound index | `{ status: 1, created_at: -1 }`: field order and a direction (1 ascending, −1 descending) per field |
| Direction | Matters only when sorting on several fields in mixed directions (Concept 4) |
| `indexBounds` | Shows the stretch: `status: ["paid", "paid"], created_at: [MaxKey, MinKey]` |
| **✓ Prefix fixed / ✗ Prefix missing** | Same rule; MongoDB has no skip scan |

<Pitfall>
"An index on (a, b) is an index on a and an index on b" is half true: it serves `a` (it starts with `a`) but not `b` on its own. Column order is a design decision, not a detail.
</Pitfall>

## Real-world scenario: one index per screen

An admin app has screens "orders of a merchant", "orders of a merchant by date" and "a merchant's pending orders, newest first". The team has three single-column indexes: `merchant_id`, `created_at`, `status`.

| Screen query | Best single index | One composite `(merchant_id, status, created_at)` |
|---|---|---|
| `WHERE merchant_id = ?` | `merchant_id` | ✓ prefix (merchant_id) |
| `WHERE merchant_id = ? ORDER BY created_at DESC` | `merchant_id`, then sort | ✗ status sits between them; needs `(merchant_id, created_at)` |
| `WHERE merchant_id = ? AND status = 'pending' ORDER BY created_at DESC LIMIT 50` | BitmapAnd + sort | ✓ one stretch, already ordered, stops after 50 |

Two composites, `(merchant_id, created_at)` and `(merchant_id, status, created_at)`, replace the three single-column indexes and serve every screen without a sort. Concepts 2–4 explain each ✓ and ✗.

## Key takeaways

1. A composite index is one B-tree sorted by its columns left to right, like a phone book.
2. Efficient conditions select one contiguous stretch: equality on the leading column(s), optionally a range on the next.
3. A condition on a later column alone is spread across one stretch per leading value.
4. InnoDB secondary entries end with the primary key, which is part of the sort order.
5. MongoDB compound indexes have a direction per field; it matters for mixed-direction sorts.
6. A composite index is bigger than a single-column one but can replace the index on its first column.
