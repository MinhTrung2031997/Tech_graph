<Tldr>
An index on `(a, b, c)` can seek with conditions on its **leftmost prefixes**: `a`, `a + b`, `a + b + c`. Without a condition on `a` it has no starting point. In the lab, with only `(status, created_at)`, PostgreSQL 17 answered `created_at` in one day with a **Seq Scan**, and MongoDB with a COLLSCAN. MySQL 8.0.13+ can **skip scan**: one small seek per distinct `status` (5 of them), 2 ms instead of 86 ms, but only when the index covers the query. PostgreSQL 18 adds skip scan too. The practical rule: put the column every query filters on first, and do not count on skip scan for anything but few-valued leading columns.
</Tldr>

## What each prefix can do

For an index on `(status, created_at)`; the same pattern holds for any number of columns.

| Conditions in the query | Prefix used for seeking | Result |
|---|---|---|
| `status = ?` | `status` | ✓ one stretch |
| `status = ? AND created_at …` | `status, created_at` | ✓ one narrower stretch |
| `created_at …` | none | ✗ no seek: full index scan, skip scan, or a different plan |
| For `(a, b, c)`: `a = ? AND c = ?` | `a` | ✓ seek on `a`; `c` is checked on each entry in that stretch (still no table visit for the check) |

The rule is about **seeking**, not about which columns can be read: a column after a gap can still filter entries inside the stretch.

| Term | Meaning |
|---|---|
| Leftmost prefix | The first k columns of the index, for any k |
| Skip scan | For a missing leading column with few distinct values, seek once per value: (cancelled, June) … (delivered, June) … |
| **✓ Prefix present** | A starting key exists: descend and walk |
| **✗ Prefix missing** | No starting key; skip scan if supported and cheap, otherwise another plan |

## Redundant indexes

Because an index on `(a, b)` serves every query an index on `(a)` serves, the single-column index on the leading column is usually redundant:

| Indexes | Verdict |
|---|---|
| `(status)` and `(status, created_at)` | `(status)` is redundant (unless it is much smaller and very hot) |
| `(created_at)` and `(status, created_at)` | Not redundant: different leading column |
| `(a, b)` and `(a, b, c)` | `(a, b)` is redundant for queries; keep it only if it enforces uniqueness |
| `(a, b)` and `(b, a)` | Not redundant: each serves different prefixes |

<Pitfall>
Skip scan is not a reason to ignore column order. It helps only when the missing leading column has **few** distinct values (one seek each) and, in MySQL, only for covering queries. With `customer_id` (100,000 values) first, a skip scan would be 100,000 seeks.
</Pitfall>

## Real-world scenario: the tenant column

A multi-tenant SaaS table has `(tenant_id, created_at)` as its main index. Every application query has `tenant_id = ?`. An internal report "orders created today across all tenants" is slow.

| Query | With `(tenant_id, created_at)` |
|---|---|
| App: `tenant_id = ? AND created_at > ?` | ✓ one stretch per request |
| Report: `created_at > today` | ✗ no prefix; skip scan would mean one seek per tenant (thousands) |

**Fix:** a separate index on `(created_at)` for the report, or run the report on a replica or warehouse. Do not reorder the main index to `(created_at, tenant_id)`: every application query would get worse (Concept 3).

## Key takeaways

1. A composite index seeks only with its leftmost prefixes: `a`, `a+b`, `a+b+c`.
2. Without the leading column there is no starting key; PostgreSQL 17 and MongoDB then use another plan.
3. Columns after a gap can still filter entries inside the stretch, without seeking.
4. MySQL 8.0.13+ skip scan seeks once per leading value, only for covering queries; PostgreSQL 18 adds skip scan.
5. Skip scan only pays off when the leading column has few distinct values.
6. An index on `(a)` is redundant next to `(a, b)`; `(b)` is not.
