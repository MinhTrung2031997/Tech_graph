<Tldr>
For `status = 'shipped' AND created_at` in June, an index on **`(status, created_at)`** seeks straight to "shipped, 1 June" and reads exactly the 4,110 matching entries: **19 index pages**. An index on **`(created_at, status)`** can only seek on the June range, then must step through every June entry of every status, checking `status` on each: **355 index pages**. Once a column is used as a **range**, the columns after it can no longer narrow the seek. So: equality columns first, the range column last. MySQL showed the same (30 vs 257 page requests); MongoDB can seek past non-matching keys after a range, which narrows but does not remove the gap.
</Tldr>

## Why the order matters

With `(status, created_at)`, all matches are **adjacent**: inside the shipped section, June is one run. With `(created_at, status)`, June is one run, but inside it shipped entries alternate with paid, delivered, pending and cancelled ones:

| `(created_at, status)` entries in June | Matches `status = 'shipped'`? |
|---|---|
| 2025-06-01 00:00:… delivered | ✗ |
| 2025-06-01 00:00:… paid | ✗ |
| 2025-06-01 00:01:… shipped | ✓ |
| 2025-06-01 00:01:… pending | ✗ |
| … 82,000 entries in June … | ≈ 1 in 20 |

| Term | Meaning |
|---|---|
| Seek condition | Positions the start and end of the walk (`Index Cond` used as bounds) |
| Index filter | Checked on each entry inside the walk, without narrowing it |
| **✓ Equality first** | All conditions are seek conditions: the walk covers only matches |
| **✗ Range first** | Conditions after the range are only filters: the walk covers the whole range |

## MongoDB: seeking inside the range

MongoDB's index scan can use bounds on fields **after** a range: when it meets a key outside the later field's bounds, it seeks ahead to the next key that could match instead of reading every key. That narrows the gap but does not close it.

| Term | Meaning |
|---|---|
| Bounds per field | `indexBounds` lists a range for every field, including those after a range |
| Seek ahead | On a non-matching key, jump to the next possible match (like a tiny skip scan inside the range) |
| **✓ Equality first / ✗ Range first** | As in the SQL engines |

## Several equalities, one range

The rule extends to any number of columns: **all equality columns first (in any order among themselves), then one range column.** Only one range can narrow the seek; a second range column is a filter.

| Query | Good index | Why |
|---|---|---|
| `merchant_id = ? AND status = ? AND created_at > ?` | `(merchant_id, status, created_at)` or `(status, merchant_id, created_at)` | Two equalities, then the range |
| `merchant_id = ? AND created_at > ? AND amount > ?` | `(merchant_id, created_at, amount)` | One range seeks (`created_at`); `amount` is filtered inside the index |
| `status IN ('paid', 'pending') AND created_at > ?` | `(status, created_at)` | An `IN` behaves like several equalities: one stretch per value |

Among the equality columns, order matters little for filtering; it matters for **other** queries that use a prefix (Concept 2) and for sorting (Concept 4).

<Pitfall>
"Put the most selective column first" is a common rule of thumb, and it is wrong when that column is used with a range. `created_at` is far more selective than `status`, but as a range it must go last. Order by **how** each column is compared (equality before range) first, and use selectivity only to break ties.
</Pitfall>

## Real-world scenario: the dashboard filter

A dashboard counts a merchant's orders by status for a date range: `WHERE merchant_id = ? AND status = ? AND created_at BETWEEN ? AND ?`. The existing index is `(created_at, merchant_id, status)`, created "because date filters are the most common".

| Index | What a one-year query walks |
|---|---|
| `(created_at, merchant_id, status)` | Every order of every merchant for the year, checking merchant and status on each |
| `(merchant_id, status, created_at)` | Only this merchant's orders with this status, for the year |

With 10,000 merchants, the second walk is roughly 10,000 × 5 times shorter.

## Key takeaways

1. In a composite index, columns compared with `=` (or `IN`) go before the column compared with a range.
2. After a range column, later columns can only filter entries, not narrow the seek.
3. Measured: 19 vs 355 index pages in PostgreSQL, 30 vs 257 page requests in MySQL, for the same 4,110 rows.
4. MongoDB seeks ahead inside a range using later bounds, so the penalty is smaller (76,499 vs 70,000 keys) but still real, and the sort order is lost.
5. Only one range column can narrow the seek; put the most important range last among the leading columns.
6. Order by comparison type first, selectivity second.
