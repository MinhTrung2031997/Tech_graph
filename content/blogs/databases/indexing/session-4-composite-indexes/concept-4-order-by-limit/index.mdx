<Tldr>
"The newest 20 paid orders" can cost **4 pages** or a **full scan plus a sort of 350,000 rows**. With an index on `(status, created_at)`, the paid entries are already in `created_at` order, so the database walks the stretch backwards from the newest, takes 20 and stops: PostgreSQL 0.04 ms, MySQL 0.35 ms, MongoDB 20 keys. Without it: 62 ms, 135 ms. The rule: the **equality columns** of the filter, then the **ORDER BY columns in order**, all in one index. An `IN` list breaks it in PostgreSQL and MySQL (each value is a separate sorted stretch), but MongoDB merges the stretches (SORT_MERGE, 21 keys).
</Tldr>

## Why an index can replace a sort

| Plan | Work for `WHERE status = 'paid' ORDER BY created_at DESC LIMIT 20` |
|---|---|
| Index on `(status, created_at)` | Descend to the end of the paid section, read 20 entries backwards, fetch 20 rows |
| No suitable index | Read every paid row (350,000), keep the newest 20 in a top-N heap |

An index helps `ORDER BY … LIMIT n` when, **after the equality conditions fix the leading columns**, the remaining index columns are exactly the ORDER BY columns, in order (all ascending, or all reversed).

| Term | Meaning |
|---|---|
| Top-N heapsort | A sort that keeps only the best n rows; cheap on memory, but every row must still be read |
| Incremental Sort (PostgreSQL) | When the index provides a prefix of the ORDER BY, rows are sorted only within groups of equal prefix |
| **✓ Index order = ORDER BY** | Walk the index, stop after LIMIT |
| **✗ Order differs** | Read all matches, then sort |

Directions: an index can be read forwards or backwards, so `(status, created_at)` serves both `ORDER BY created_at` and `ORDER BY created_at DESC` after `status = ?`. **Mixed** directions on two sort columns (`ORDER BY created_at ASC, id DESC`) need an index declared with those directions, `(status, created_at, id DESC)`; otherwise PostgreSQL falls back to an Incremental Sort on top of the index (still cheap when the groups are small, as in the lab: 13 buffers).

## MongoDB

| Term | Meaning |
|---|---|
| Blocking `SORT` stage | Reads every matching document's key before returning the first; limited to 100 MB of memory unless `allowDiskUse` |
| `SORT_MERGE` | Merges several already-sorted index stretches (one per `$in` value) into one sorted stream |
| **✓ Index provides the sort / ✗ SORT stage** | As before |

## The engines side by side

| Query | PostgreSQL 17 | MySQL 8.4 | MongoDB 8.0 |
|---|---|---|---|
| `status = 'paid'` newest 20 | Index Scan Backward, 4 buffers | Backward index scan, 0.35 ms | IXSCAN, 20 keys |
| `status IN (paid, shipped)` newest 20 | Seq Scan + sort, 65 ms | ALL + filesort | SORT_MERGE, 21 keys |
| Newest 20 overall (no status) | Needs an index on `created_at` | Same | Same |
| `customer_id = 7 ORDER BY created_at DESC LIMIT 5` with `(customer_id, created_at)` | Index Scan Backward, 8 buffers | — | — |

<Pitfall>
An `ORDER BY … LIMIT` query that is fast for one filter value can be slow for another. With `(created_at, status)` instead of `(status, created_at)`, "newest 20 paid" walks the newest entries and skips non-paid ones: instant for `paid` (35%), but for a rare status it may walk most of the index before finding 20. Equality columns first makes the cost the same for every value.
</Pitfall>

## Real-world scenario: an activity feed

A feed shows `WHERE user_id = ? ORDER BY created_at DESC LIMIT 30`, with "load more" pages. With only an index on `user_id`, power users with 200,000 events take 300 ms per page; others are fast.

| Index | Page 1 for a power user | Page 100 (keyset: `AND created_at < :last`) |
|---|---|---|
| `(user_id)` | Fetch 200,000 rows, top-N sort | Same: every page re-sorts everything |
| `(user_id, created_at)` | Walk 30 entries backwards | Descend to `(user_id, :last)`, walk 30 |

Combined with keyset pagination (Session 2, Concept 5), every page costs the same, whatever the user and the page number.

## Key takeaways

1. An index can replace a sort when, after the equality columns, its columns match the ORDER BY in order (or all reversed).
2. Then `LIMIT n` stops the walk after n entries: a few pages instead of all matches plus a sort.
3. Measured: 4 buffers vs 62 ms (PostgreSQL), 0.35 ms vs 135 ms (MySQL), 20 keys (MongoDB).
4. `IN` lists produce several sorted stretches: PostgreSQL 17 and MySQL sort; MongoDB merges them (SORT_MERGE).
5. ORDER BY without the leading index columns cannot use the index order.
6. Mixed directions need matching directions in the index definition.
7. Equality-first indexes make "top N" cost the same for every filter value.
