<Tldr>
For a query with equalities, a sort and a range, order the index fields **Equality → Sort → Range**. Concept 3 said "range last"; ESR adds that the **sort field goes before the range field**, because a range in front of the sort field destroys the order and forces a blocking sort. For "paid orders over 400, newest 20", the ESR index `{ status, created_at, amount }` examined **114 keys in 1 ms**; `{ status, amount, created_at }` (E-R-S) examined **70,000 keys plus an in-memory SORT, 24 ms**. The same rule held in PostgreSQL (6 buffers vs 13.8 ms) and MySQL (0.41 ms vs 87 ms).
</Tldr>

## The three kinds of field

| Letter | Field kind | Example | Why this position |
|---|---|---|---|
| **E** | Equality (`status: 'paid'`, `$in` with few values) | `status` | Fixes one stretch (Concept 1) |
| **S** | Sort (`sort({ created_at: -1 })`) | `created_at` | Inside the stretch, entries are already in sort order (Concept 4) |
| **R** | Range (`$gt`, `$lt`, `$ne`, regex) | `amount` | Checked on each key while walking in sort order; does not break the order |

The trade-off: with S before R, the range no longer narrows the seek (it becomes a per-key check), so the scan may read more keys than match. With R before S, the seek is tight but the order is lost, so **every** matching key must be read and sorted before the first result. With a `LIMIT`, stopping early almost always wins.

## Four index orders, one query

`db.orders.find({ status: "paid", amount: { $gt: 400 } }).sort({ created_at: -1 }).limit(20)`: 70,000 documents match.

| Index (hinted) | Order | Stages | Keys examined | Docs examined | Time |
|---|---|---|---|---|---|
| `{ status: 1, created_at: -1, amount: 1 }` | **E S R** | LIMIT ← FETCH ← IXSCAN | 114 | 20 | 1 ms |
| `{ status: 1, created_at: -1 }` | E S (range checked on the document) | LIMIT ← FETCH ← IXSCAN | 114 | 114 | 0 ms |
| `{ status: 1, amount: 1, created_at: -1 }` | E R S | FETCH ← SORT ← IXSCAN | 70,000 | 20 | 24 ms |
| `{ amount: 1, status: 1, created_at: -1 }` | R E S | FETCH ← SORT ← IXSCAN | 76,499 | 20 | 42 ms |

With `limit(1000)`: ESR 5,000 keys, 2 ms; ERS still 70,000 keys, 24 ms. The ERS cost does not depend on the limit: it always reads every match.

| Term | Meaning |
|---|---|
| Blocking SORT | Must consume all input before emitting the first document; memory-limited (100 MB) |
| Non-blocking | Documents flow out as they are found; LIMIT stops the scan |
| **✓ ESR order** | Sort comes from the index; the range is checked per key |
| **✗ Range before sort** | Tight seek, but a blocking SORT over all matches |

## The same rule in PostgreSQL and MySQL

`WHERE status = 'paid' AND amount > 400 ORDER BY created_at DESC LIMIT 20`:

| | Index `(status, created_at, amount)` (E-S-R) | Index `(status, amount, created_at)` (E-R-S) |
|---|---|---|
| PostgreSQL 17 | Index Scan Backward, `Index Cond` includes `amount > 400`: 6 buffers, 0.04 ms | Bitmap of 69,674 rows + top-N sort: 10,448 buffers, 13.8 ms |
| MySQL 8.4 | `ref`, Backward index scan: 0.41 ms | `range`, Using filesort: 87 ms |

## When ESR is not the answer

| Situation | Better choice |
|---|---|
| The range is extremely selective (a few matches) and there is no LIMIT | E-R-S: the tight seek reads only those matches; sorting a few is cheap |
| No sort in the query | E-R (Concept 3): equality, then range |
| `$in` with many values on the "E" field | Each value is a separate stretch; with a sort, MongoDB must merge or sort; consider treating it as a range |
| `$ne`, `$nin`, unanchored regex | These are ranges (or worse); put them last |

<Pitfall>
MongoDB's planner does not apply ESR for you. In the lab it picked `{ status, created_at }` (E-S, with the range checked on each document) over the ESR index after a trial; both were fast here, but the planner only chooses among indexes you created. Design the index with ESR, then check `explain()` for a `SORT` stage and for `totalKeysExamined` far above `nReturned`.
</Pitfall>

## Real-world scenario: an order search screen

A seller searches their orders: status filter, minimum amount, newest first, 50 per page. The collection has `{ seller_id: 1, status: 1, amount: 1 }` and the screen times out for big sellers.

| Index | Big seller, 2M orders, 600k matching |
|---|---|
| `{ seller_id, status, amount }` (E E R, then sort) | Reads 600k keys, blocking SORT, may exceed the 100 MB sort limit |
| `{ seller_id, status, created_at, amount }` (E E S R) | Walks newest first, checks amount per key, stops after 50 matches |

## Key takeaways

1. ESR: equality fields first, then sort fields, then range fields.
2. Sort before range keeps index order, so LIMIT can stop early; the range becomes a per-key check.
3. Range before sort gives a tight seek but a blocking SORT over every match, whatever the limit.
4. Measured: 114 keys / 1 ms (ESR) vs 70,000 keys + SORT / 24 ms (ERS) in MongoDB; 6 buffers vs 13.8 ms in PostgreSQL; 0.41 ms vs 87 ms in MySQL.
5. ESR applies to SQL engines too: it is Concepts 3 and 4 combined.
6. Exceptions: tiny result sets without LIMIT, queries without a sort, many-valued `$in`.
