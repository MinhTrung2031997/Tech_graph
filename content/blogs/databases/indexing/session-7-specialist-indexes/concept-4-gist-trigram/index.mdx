<Tldr>
A **leading wildcard** (`LIKE '%00123'`) defeats every B-tree (Session 3). The `pg_trgm` extension splits text into **trigrams** (`SKU-000123` → `" sk"`, `sku`, `000`, `123`, …) and a GIN index on them turns the search into "rows containing all the pattern's trigrams": the lab query went from a Seq Scan of **10,205 buffers to 291**. **GiST** is a framework for indexes over things that overlap or contain each other, ranges and geometry, rather than things that sort. Its showcase is the **exclusion constraint**: `EXCLUDE USING gist (room WITH =, during WITH &&)` rejected an overlapping booking at insert time. MySQL has no trigram or exclusion support (FULLTEXT ngram, application locks); MongoDB scans the whole index for unanchored regexes and has 2dsphere for geometry.
</Tldr>

## Trigrams

`show_trgm('SKU-000123')` returns the trigrams PostgreSQL indexes for that value: `"  0"`, `"  s"`, `" 00"`, `" sk"`, `000`, `001`, `012`, `123`, `"23 "`, `"ku "`, `sku`. A pattern `'%00123'` contains the trigrams `001`, `012`, `123`, `"23 "`: only rows containing all of them can match.

| Term | Meaning |
|---|---|
| Trigram | Three consecutive characters (the value is padded with spaces at both ends) |
| `gin_trgm_ops` / `gist_trgm_ops` | Operator classes to index trigrams with GIN (faster lookups) or GiST (supports similarity ordering) |
| Similarity (`%`, `<->`) | Fraction of shared trigrams; for fuzzy matching and "did you mean" |
| **✓ Trigrams narrow it / ✗ No trigrams** | Patterns with at least one full trigram can use the index; very short patterns cannot |

## GiST and exclusion constraints

A B-tree needs a total order. Ranges, rectangles and points do not have one that helps "does this overlap that?". **GiST** (Generalized Search Tree) stores bounding boxes or covering ranges at each level, so a search descends only into subtrees whose bounding range overlaps the query.

| Term | Meaning |
|---|---|
| `tstzrange` | A range of timestamps, e.g. `[2025-06-01 14:00, 2025-06-03 11:00)` |
| `&&` | Overlaps |
| Exclusion constraint | Generalised uniqueness: no two rows may satisfy all the listed operators against each other |
| `btree_gist` | Extension letting GiST handle plain equality (`room WITH =`) alongside ranges |
| **✓ No conflict / ✗ Overlap found** | Insert accepted or rejected |

## MySQL and MongoDB

| Need | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| `LIKE '%…%'` / substring | Trigram GIN or GiST | No index; FULLTEXT with the `ngram` parser indexes n-grams for word-like search (mainly CJK) | Unanchored regex scans the whole index (Session 3) |
| Fuzzy / similarity | `pg_trgm` `%`, `<->` | — | Atlas Search |
| No overlapping ranges | Exclusion constraint (GiST) | Not supported: application locking (`SELECT … FOR UPDATE`) or triggers | Not supported: application logic or transactions |
| Geometry | GiST (PostGIS) | Spatial R-tree index | `2dsphere` / `2d` indexes |

<Pitfall>
Trigram indexes are large (18 MB for a short `sku` column; often bigger than the table column itself for long text) and slow to update, and patterns shorter than three characters cannot use them. Use them for genuine substring search on columns users type into, not as a general replacement for B-trees.
</Pitfall>

## Real-world scenario: search-as-you-type on product names

A back-office search box filters products by any part of the name (`ILIKE '%' || $1 || '%'`). It is fast in testing and scans 5M rows in production.

| Option | Effect |
|---|---|
| B-tree on `name` | Unused: leading wildcard |
| `CREATE INDEX ON products USING gin (name gin_trgm_ops)` | Substring and ILIKE searches become index scans; fuzzy matching with `%` |
| Full-text (`tsvector` GIN) | Word search with stemming, but no partial words |
| External search engine | Ranking, typo tolerance, facets at scale |

## Key takeaways

1. `pg_trgm` indexes trigrams; a GIN trigram index serves `LIKE`/`ILIKE` with wildcards on both sides (10,205 → 291 buffers in the lab).
2. Trigram matches are candidates rechecked on the heap; patterns need at least one full trigram.
3. GiST indexes overlap and containment: ranges, geometry, similarity ordering.
4. Exclusion constraints use GiST to forbid overlapping ranges per key, like a generalised unique index.
5. MySQL has no trigram or exclusion support; FULLTEXT ngram and spatial R-trees cover other needs.
6. MongoDB scans the whole index for unanchored regexes; 2dsphere covers geometry; substring search needs Atlas Search or derived fields.
