<Tldr>
A **BRIN** index does not point at rows. It splits the table into ranges of 128 pages and stores the **min and max** value of each range: for `orders.created_at`, range 0 holds 1–5 January, range 1 holds 5–10 January, and so on. A query for one day reads the BRIN (3 pages, **24 kB** in total vs 21 MB for a B-tree), keeps only the ranges whose min–max overlaps the day, and scans those pages: **349 lossy pages and 31,273 rows rechecked** to return 2,740. It only works if values follow the physical order (correlation 0.98 for `created_at`); on `customer_id` (correlation −0.005) every range spans 5–100,000, and a forced BRIN scan read **6,528 pages** to find 7 rows. MySQL has no BRIN (use range partitioning); MongoDB has time-series collections.
</Tldr>

## A summary per block range

| Range | Heap pages | `created_at` min … max (from `brin_page_items`) |
|---|---|---|
| 0 | 0–127 | 2025-01-01 00:00 … 2025-01-05 15:00 |
| 1 | 128–255 | 2025-01-05 15:00 … 2025-01-10 06:00 |
| … | … | … |

| | B-tree on `created_at` | BRIN on `created_at` |
|---|---|---|
| Entries | One per row (1M) | One per 128 pages (≈ 80) |
| Size | 21 MB | **24 kB** |
| Result | Exact rows | Candidate pages ("lossy"): every row on them is rechecked |
| Needs | Nothing special | Values correlated with physical order |

| Term | Meaning |
|---|---|
| Block range | `pages_per_range` heap pages (128 by default) summarised by one BRIN entry |
| Lossy | BRIN returns pages, not rows: `Heap Blocks: lossy=…`, `Rows Removed by Index Recheck` |
| Correlation | `pg_stats.correlation`: 1 = physical order matches value order |
| **✓ Range overlaps / ✗ Range excluded** | Read the range's pages or skip them |

### Keeping BRIN effective

| Risk | Effect | Mitigation |
|---|---|---|
| Updates or deletes move rows (non-HOT versions land anywhere) | Ranges widen; correlation drops (1.0 → 0.98 after the Session 5 updates) | BRIN suits append-mostly data: logs, events, metrics |
| New pages at the end are not yet summarised | They are always scanned until summarised | `autosummarize = on`, or VACUUM / `brin_summarize_new_values()` |
| Range too coarse | More lossy pages per query | Smaller `pages_per_range` (e.g. 32): bigger index, fewer pages read |

## MySQL: no BRIN; partition instead

MySQL has no block-range index. The closest tool for "skip the old data" is **range partitioning**: each partition is its own table, and the optimizer prunes partitions that cannot match.

## MongoDB: time-series collections

MongoDB has no BRIN either. For time-ordered data, a **time-series collection** stores measurements in buckets grouped by time and metadata, keeping per-bucket min and max of the time field: the same "summary per block" idea, built into the storage format.

<Pitfall>
Creating a BRIN on a column because "it is tiny" without checking `pg_stats.correlation` gives an index that the planner either ignores or, worse, uses on a skewed estimate. Check that the column is close to ±1.0 and that the table is append-mostly.
</Pitfall>

## Real-world scenario: a 2 TB event log

An append-only `events` table grows 5 GB a day; queries always filter on a time window. A B-tree on `created_at` is 300 GB and slows every insert.

| Option | Size | Query for one hour |
|---|---|---|
| B-tree on `created_at` | ≈ 300 GB | Exact rows |
| BRIN on `created_at` (`pages_per_range` 32) | A few MB | A few block ranges, rechecked |
| Monthly partitions + BRIN | A few MB | Prune to one partition, then BRIN |

## Key takeaways

1. BRIN stores min/max per block range (128 pages by default), not per row: 24 kB vs 21 MB for 1M orders.
2. It returns candidate pages; every row on them is rechecked (lossy).
3. It works only when values follow physical order: correlation 0.98 worked; −0.005 read 6,528 pages for 7 rows.
4. Ideal for append-mostly time-series and logs; updates and deletes erode it.
5. MySQL's closest equivalent is range partitioning; MongoDB's is time-series collections with per-bucket bounds.
