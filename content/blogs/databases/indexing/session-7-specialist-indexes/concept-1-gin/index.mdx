<Tldr>
A B-tree maps **one value per row** to that row. Many columns hold **several** searchable things per row: an array of tags, the keys of a JSON document, the words of a description. A **GIN** (Generalized Inverted Index) stores one entry per element with a compressed **posting list** of the rows containing it, and answers "rows containing X and Y" by intersecting lists. On 100,000 products, `tags @> '{clearance,gift}'` read **7 index pages and 22 heap pages** instead of 4,835 for a Seq Scan; a jsonb containment query read 13 index pages; a 3-word full-text search read 42. The price is writes: 50,000 inserts took **296 ms with four GIN indexes vs 169 ms without**. MySQL has multi-valued indexes and FULLTEXT; MongoDB has multikey, wildcard and text indexes.
</Tldr>

## B-tree vs inverted index

| | B-tree | GIN |
|---|---|---|
| Entries per row | One (the column's value) | One per element / key / word |
| Entry | value → row | element → posting list of rows |
| Good at | Equality, ranges, ordering | "Contains", "has key", "matches words"; intersecting several elements |
| Not good at | Elements inside a value | Ranges and ordering |

| Lab table `products` (100,000 rows, 31 MB) | GIN index | Size |
|---|---|---|
| `tags text[]` (3–5 tags each) | `USING gin (tags)` | 576 kB |
| `attrs jsonb` | `USING gin (attrs)` (`jsonb_ops`) | 1.28 MB |
| `attrs jsonb` | `USING gin (attrs jsonb_path_ops)` | 800 kB |
| `fts tsvector` (from `description`) | `USING gin (fts)` | 6.4 MB |

| Term | Meaning |
|---|---|
| Posting list | Compressed, sorted list of row addresses for one element |
| `@>` | Contains: `tags @> '{a,b}'`, `attrs @> '{"brand": "brand7"}'` |
| `jsonb_ops` vs `jsonb_path_ops` | Default operator class indexes every key and value (supports `?`, `?|`, `?&`, `@>`); `jsonb_path_ops` indexes value paths only (smaller, supports `@>` and jsonpath only) |
| Pending list (`fastupdate`) | New entries are buffered and merged into the main index in batches, to cheapen inserts |
| **✓ Intersect lists / ✗ No index match** | GIN narrows to rows containing every element; otherwise a scan |

## MySQL: multi-valued indexes and FULLTEXT

| Need | MySQL feature | Lab |
|---|---|---|
| Elements of a JSON array | Multi-valued index: `INDEX ((CAST(tags->'$' AS CHAR(12) ARRAY)))` | `'clearance' MEMBER OF (tags->'$')`: `ref`, rows 500; `JSON_CONTAINS`: `range` |
| Words in text | `FULLTEXT` index (InnoDB) | `MATCH … AGAINST ('+waterproof +boots +travel' IN BOOLEAN MODE)`: type `fulltext`, 5,000 rows |

## MongoDB: multikey, wildcard and text

| Need | MongoDB index | Lab (100,000 items) |

<Pitfall>
A GIN index on a jsonb column does not help ordinary comparisons on a field inside it: `attrs->>'brand' = 'brand7'` is an expression, not containment, so it needs a B-tree expression index (Session 5) or must be rewritten as `attrs @> '{"brand": "brand7"}'`. Write queries in the operator family the index supports.
</Pitfall>

## Real-world scenario: flexible product attributes

A marketplace stores product attributes as jsonb because each category has different fields. Filters combine 2–4 attributes.

| Option | Behaviour |
|---|---|
| B-tree expression index per attribute | Fast for the indexed attributes only; one index per field |
| GIN `jsonb_path_ops` on `attrs` + `@>` queries | One index serves any combination of equality filters; intersects them |
| Separate attribute table `(product_id, key, value)` | Classic, B-tree friendly; more joins |

## Key takeaways

1. GIN is an inverted index: one entry per element, key or word, each with a posting list of rows.
2. It answers containment (`@>`), key existence (`?`) and full-text matches (`@@`), intersecting lists for several elements.
3. Lab: 29 buffers vs 4,835 for an array containment; 13 index pages for jsonb; 42 for a 3-word text search.
4. `jsonb_path_ops` is smaller but supports only containment and jsonpath; `jsonb_ops` also supports key existence.
5. GIN makes writes more expensive (296 vs 169 ms for 50,000 inserts); the pending list softens inserts.
6. MySQL: multi-valued indexes (query must use the same expression) and FULLTEXT. MongoDB: multikey, wildcard and text indexes.
