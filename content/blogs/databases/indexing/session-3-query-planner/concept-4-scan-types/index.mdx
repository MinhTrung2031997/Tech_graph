<Tldr>
PostgreSQL has three ways to read a table. An **Index Scan** fetches rows in index order, one heap page at a time: best for a few rows, or many rows that are physically ordered. A **Bitmap Heap Scan** first collects every matching page from one or more indexes, then reads those pages once, in file order: best for a few hundred to a few hundred thousand scattered rows, and the only way to **combine** two indexes (BitmapAnd/BitmapOr). A **Seq Scan** reads everything: best when most pages are needed anyway. In the lab, `customer_id ≤ 5000 AND status = 'shipped'` used both indexes at once and ran in **4.3 ms**. MySQL approximates the bitmap idea with Multi-Range Read (29 ms vs 41 ms); MongoDB has IXSCAN → FETCH or COLLSCAN.
</Tldr>

## The three scans

| | Index Scan | Bitmap Heap Scan | Seq Scan |
|---|---|---|---|
| Order of heap pages | Index order (random unless correlated) | File order, each page once | File order, every page |
| Rows come out | Sorted by the index key | In physical order (no sort for free) | In physical order |
| Can stop early (`LIMIT`) | ✓ | ✗ (bitmap built first) | ✓ |
| Combine two indexes | ✗ | ✓ BitmapAnd / BitmapOr | — |
| Wins when | Few rows, or ordered rows, or `ORDER BY … LIMIT` | Many scattered rows, or several conditions | Most of the table |

The lab sweep, `customer_id <= N` (scattered) and `created_at < date` (ordered):

| Selectivity | `customer_id` (correlation −0.01) | `created_at` (correlation 1.0) |
|---|---|---|
| 0.001% – 0.3% | Bitmap Heap Scan | Index Scan |
| 1% – 20% | Bitmap Heap Scan | Index Scan |
| ≈ 50% | Seq Scan | Index Scan |
| ≈ 75% | Seq Scan | Seq Scan |

## PostgreSQL: how a bitmap scan works

| Term | Meaning |
|---|---|
| Bitmap Index Scan | Reads the index and sets one bit per matching row (exact) or per matching page (lossy) |
| BitmapAnd / BitmapOr | Intersect or merge bitmaps from several indexes before touching the heap |
| Exact vs lossy | If the bitmap would exceed `work_mem`, pages degrade to "some row on this page matches": every row on them must be rechecked |
| `Heap Blocks: exact=… lossy=…` | How many heap pages were read with exact vs lossy bits |
| **✓ Exact** | Only the matching rows are checked |
| **✗ Lossy** | Every row on the page is checked again (`Rows Removed by Index Recheck`) |

## MySQL InnoDB: ref/range, MRR, full scan

InnoDB has no bitmap heap scan, but **Multi-Range Read (MRR)** applies the same idea to secondary-index lookups: collect the primary keys from the index range, sort them, then look up the rows in primary-key order, which is clustered-index order.

| Term | Meaning |
|---|---|
| `type: ref / range` | Secondary-index access; each entry → a clustered-index lookup in index order |
| MRR (`Using MRR`) | Buffer the primary keys, sort them, look up rows in key order: fewer, more sequential page visits |
| `mrr_cost_based` | On by default: MRR is used only when the optimizer estimates it cheaper, which is rarely |
| index_merge | MySQL's way of combining two indexes (union, intersection), like BitmapOr/BitmapAnd |
| **✓ MRR / ✗ No MRR** | Sorted lookups vs lookups in index order |

## MongoDB: IXSCAN → FETCH or COLLSCAN

| Term | Meaning |
|---|---|
| `IXSCAN` → `FETCH` | Index order, one document fetch per key (like an Index Scan) |
| `COLLSCAN` | Every document in RecordId order (like a Seq Scan) |
| Index intersection (`AND_SORTED`, `AND_HASH`) | Exists, but is rarely chosen; compound indexes are the intended way to serve several conditions |
| **✓ Index applies / ✗ None** | With an applicable index, MongoDB uses it (Concept 1) |

<Pitfall>
A Bitmap Heap Scan cannot deliver rows in index order and cannot stop early. For `ORDER BY created_at LIMIT 20`, the planner needs an Index Scan on a matching index (Session 4); if it chooses a bitmap, it must collect and sort all matches first. When a "top N" query is slow, check whether the plan is an Index Scan feeding the Limit or a Bitmap followed by a Sort.
</Pitfall>

## Real-world scenario: two indexes vs one composite

An orders search filters on `merchant_id` and `status`, with separate single-column indexes. PostgreSQL uses a BitmapAnd of both and the query runs fine; on MySQL the same query picks one index and filters, and is slower; MongoDB picks one index after a trial.

| Engine | With two single-column indexes | With one composite `(merchant_id, status)` |
|---|---|---|
| PostgreSQL | BitmapAnd: reads both index ranges, then the intersection | One index range: only matching entries |
| MySQL | One index + filter, or index_merge intersection | One index range |
| MongoDB | One index + filter (intersection rarely chosen) | One index range |

**Lesson:** bitmaps make PostgreSQL forgiving, but a composite index is the portable answer for conditions that always appear together (Session 4).

## Key takeaways

1. Index Scan: heap pages in index order, rows sorted, can stop early; best for few or ordered rows.
2. Bitmap Heap Scan: collect matching pages first, read them once in file order; best for many scattered rows; can AND/OR several indexes.
3. Seq Scan: every page once; best when most pages hold matches.
4. Bitmaps go lossy when they exceed `work_mem`: every row on lossy pages is rechecked.
5. MySQL's MRR sorts primary keys before lookups (29 ms vs 41 ms in the lab) but is off unless judged cheaper; index_merge combines indexes.
6. MongoDB has IXSCAN → FETCH and COLLSCAN; it uses an applicable index without costing a COLLSCAN.
