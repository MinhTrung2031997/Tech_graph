<Tldr>
A cost-based planner prices every candidate plan in **abstract units** (pages read × a cost per page + rows processed × a cost per row) and runs the cheapest. PostgreSQL's Seq Scan of `orders` costs 10,102 + 10,000 + 2,500 = **22,602**; an Index Scan for `customer_id = 7` costs **48.62**, and both numbers can be recomputed by hand from the documented constants. The constants are assumptions about your hardware: lowering `random_page_cost` from 4 to 1.1 made PostgreSQL pick an Index Scan that ran **3–4× slower** than the Seq Scan it replaced. MySQL prices plans the same way with different constants; MongoDB does not price plans at all, it scores them after a trial run.
</Tldr>

## PostgreSQL: the constants

| Setting | Default | Charged for |
|---|---|---|
| `seq_page_cost` | 1.0 | A page read in file order (the unit) |
| `random_page_cost` | 4.0 | A page read out of order |
| `cpu_tuple_cost` | 0.01 | Each row produced by a scan |
| `cpu_index_tuple_cost` | 0.005 | Each index entry processed |
| `cpu_operator_cost` | 0.0025 | Each operator or function evaluation (a `WHERE` comparison) |
| `effective_cache_size` | 4 GB | Not a cost: a hint of how much data is likely cached, which lowers the cost of repeated page reads in index scans |
| `parallel_setup_cost` / `parallel_tuple_cost` | 1,000 / 0.1 | Starting workers / passing each row to the leader |

`EXPLAIN` prints two numbers per node, `cost=startup..total`: the cost before the first row and the cost to produce all rows.

## Three plans priced by hand

| Plan | Pages | CPU | Total (EXPLAIN) |
|---|---|---|---|
| Seq Scan, any filter | 10,102 pages × 1.0 = 10,102 | 1M rows × (0.01 + 0.0025) = 12,500 | **22,602** |
| Index Scan, `customer_id = 7` (11 rows) | 1 index page × 4.0 + 11 heap pages × 4.0 = 48 | 11 × (0.005 + 0.0025 + 0.01) ≈ 0.19; descent 0.42 | **48.62** |
| Index Scan, `created_at < '2025-07-01'` (494,454 rows, correlation 1.0) | ≈ 1,350 index pages × 4.0 + ≈ 4,991 heap pages read **in order**: 4.0 + 4,990 × 1.0 | ≈ 494,454 × 0.0175 ≈ 8,650 | ≈ 19,050 (**19,083**) |

The heap part of an Index Scan is priced between two extremes using the column's correlation c: **max** = every heap page a random read (uncorrelated), **min** = one random read then sequential pages (perfectly ordered), and **cost = max + c² × (min − max)**. With c = 1.0 for `created_at`, it is the cheap end; with c ≈ 0 for `customer_id`, the expensive end.

| Term | Meaning |
|---|---|
| Startup cost | Work before the first row (an index descent, building a bitmap or hash) |
| Total cost | Work for all rows; what the planner compares (unless a `LIMIT` makes startup matter) |
| **✓ Cheapest** | The plan with the lowest total cost is executed |
| **✗ Rejected** | Every other candidate |

## MySQL: read cost + evaluate cost

| Constant (`mysql.server_cost`, `mysql.engine_cost`) | Default | Charged for |
|---|---|---|
| `io_block_read_cost` | 1.0 | A page read from disk |
| `memory_block_read_cost` | 0.25 | A page already in the buffer pool |
| `row_evaluate_cost` | 0.1 | Evaluating each row against the conditions |
| `key_compare_cost` | 0.05 | Comparing keys (sorting, index lookups) |

`EXPLAIN FORMAT=JSON` shows `read_cost`, `eval_cost` and `query_cost`; `EXPLAIN FORMAT=TREE` shows `cost=` per step.

| Term | Meaning |
|---|---|
| `read_cost` | Pages to read × block cost (memory or disk, from how much of the index InnoDB reports as cached) |
| `eval_cost` | Rows × `row_evaluate_cost` |
| **✓ Cheapest / ✗ Rejected** | As in PostgreSQL |

## MongoDB: a score, not a cost

| Term | Meaning |
|---|---|
| `works` | Units of work a plan did in the trial (roughly one index key or document per unit) |
| `advanced` | Results the plan returned in the trial |
| Score | 1 (base) + advanced / works (productivity) + small bonuses (no FETCH needed, no in-memory SORT, finished early) |
| **✓ Highest score / ✗ Lower score** | The winner is cached; the others are listed as `rejectedPlans` |

<Pitfall>
Do not tune cost constants to fix one query. `random_page_cost = 1.1` is reasonable when most data is cached **and** you have checked that index plans really are cheap on your workload; in the lab it made a 50%-selectivity query 3–4× slower. Change constants with `SET` in a session, compare `EXPLAIN ANALYZE` across representative queries, then decide.
</Pitfall>

## Real-world scenario: the plan that flips at month end

A report query `WHERE created_at >= :start` uses an Index Scan for a one-week window and a Seq Scan for a month. It is fast in both cases. A team member forces the index with `SET enable_seqscan = off` "because indexes are faster", and month-end reports slow down.

| Window | Rows | Planner's choice | Forced index |
|---|---|---|---|
| 1 week | ≈ 2% | Index Scan (cheap) | Same |
| 1 month | ≈ 8% | Index Scan or Bitmap (correlated data) | Same |
| 9 months | ≈ 75% | Seq Scan (22,602 < index cost) | Index Scan of 75% of the table |

**Lesson:** the cost model's job is exactly this switch. `enable_*` settings are for experiments, never for production queries.

## Key takeaways

1. A cost-based planner prices each candidate in abstract units and runs the cheapest.
2. PostgreSQL: pages × `seq_page_cost` (1.0) or `random_page_cost` (4.0), plus rows × `cpu_tuple_cost` (0.01), entries × `cpu_index_tuple_cost` (0.005), operators × `cpu_operator_cost` (0.0025).
3. Seq Scan of `orders` = 22,602; Index Scan for `customer_id = 7` = 48.62; both reproducible by hand.
4. Correlation moves an Index Scan's heap cost between all-random and almost-all-sequential.
5. MySQL prices `read_cost` (pages × 0.25 cached or 1.0 disk) + `eval_cost` (rows × 0.1).
6. MongoDB scores trial runs by results per unit of work instead of estimating costs.
7. Cost constants are assumptions; changing them changes plans, not always for the better.
