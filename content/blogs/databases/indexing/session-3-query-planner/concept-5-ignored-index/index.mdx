<Tldr>
"The database ignores my index" has two different causes. **Either the index cannot serve the condition as written**: the column is wrapped in a function or cast (`created_at::date = …`, `id = 7.0`, `sku = 123` in MySQL), the pattern starts with a wildcard, the collation does not support `LIKE` prefixes, or an `OR` includes an unindexed column. **Or the index could serve it, but a scan is cheaper**: too many rows, a tiny table, or stale statistics. The first kind is fixed by rewriting the query or indexing the expression; the second is usually the planner being right. In MongoDB a type mismatch does not even slow down: `customer_id: "7"` uses the index and silently returns **nothing**.
</Tldr>

## Two questions the planner asks

| Question | If no |
|---|---|
| 1. **Can** this index serve the condition? The condition must compare the indexed column (or indexed expression), unchanged, with an operator the index supports | The index is not a candidate at all |
| 2. **Should** it, given the cost? Index route cheaper than the alternatives (Concept 3)? | The planner picks a scan, deliberately |

A condition the index can serve is called **sargable** (Search ARGument ABLE).

## The cases, measured

| Condition | PostgreSQL | MySQL | MongoDB | Kind |
|---|---|---|---|---|
| `created_at::date = '2025-03-01'` / `DATE(created_at) = …` | Seq Scan | `ALL` | (`$expr` with `$dayOfMonth`: COLLSCAN) | Function on the column |
| `created_at >= '2025-03-01' AND created_at < '2025-03-02'` | Index Scan | `range` | IXSCAN | Same question, sargable |
| `customer_id + 0 = 7` | Seq Scan | `ALL` | — | Expression on the column |
| `id = 7.0` (numeric literal on a `bigint`) | Seq Scan | — | — | Column cast to the literal's type |
| `sku = 123` (number vs `VARCHAR`) | — | `ALL` | — | Column converted to a number |
| `customer_id: "7"` (string vs number) | — | — | IXSCAN, **0 results** | Type mismatch: wrong answer, fast |
| `sku LIKE 'SKU-00012%'` | Seq Scan (en_US collation); Index Scan with `text_pattern_ops` | `range` | `/^SKU-00012/`: 2,001 keys | Prefix: collation-dependent |
| `sku LIKE '%00123'` | Seq Scan | `ALL` | `/00123$/`: all 1,000,000 keys scanned | Leading wildcard |
| `customer_id = 7 OR amount = 12.34` | Seq Scan | `ALL` | COLLSCAN | OR with an unindexed column |
| `customer_id = 7 OR status = 'refunded'` | BitmapOr | `index_merge` (union) | OR of two IXSCANs | OR, both indexed |
| `status <> 'delivered'` | Seq Scan (65% of rows) | — | IXSCAN over two ranges, 650,001 keys | Negation |
| `status = 'delivered'` | Bitmap (cheaper than Seq) | `ref`, **slower** than a scan | IXSCAN | Low selectivity |

## MongoDB: types, regexes and $or

| Term | Meaning |
|---|---|
| Type bracketing | A query value only matches values of the same BSON type: `"7"` (string) never equals `7` (number) |
| Anchored regex | `/^SKU-00012/`: becomes a tight index range |
| Unanchored or case-insensitive regex | `/00123$/`, `/^sku/i`: the whole index is scanned, each key tested |
| `SUBPLAN` | Plans each `$or` branch separately; if one branch has no index, the whole query falls back to COLLSCAN |
| **✓ Tight bounds / ✗ No usable bounds** | Whether the index narrows the search |

<Pitfall>
Do not "fix" a correct Seq Scan. Before rewriting a query or adding hints, check which question failed: if `EXPLAIN` shows the index **is** a candidate (forcing it with `SET enable_seqscan = off` makes the planner use it) and the forced plan is slower, the planner was right. Only a "cannot serve" case is a bug in the query or the index.
</Pitfall>

## A checklist when an index is ignored

| Check | How |
|---|---|
| Is the column wrapped in a function, cast or arithmetic? | Rewrite as a range or comparison on the bare column; or index the expression |
| Does the literal or parameter type match the column type? | Compare `id = 7` vs `id = 7.0`; in MySQL quote string values; in MongoDB check BSON types |
| Leading wildcard or case-insensitive pattern? | Needs a trigram/text index (Session 7) or a stored normalised column |
| `LIKE 'prefix%'` in PostgreSQL with a non-C collation? | Index with `text_pattern_ops` |
| `OR` with an unindexed branch? | Index it or split into `UNION` |
| Are statistics current? | `ANALYZE`; compare estimated vs actual rows |
| Is the condition selective at all? | Count matching rows; above ≈ 10–20% a scan is usually right |
| Composite index with the leading column missing from the query? | Session 4 |

## Real-world scenario: the timezone cast

An API filters orders by "today in the user's timezone": `WHERE (created_at AT TIME ZONE 'Asia/Ho_Chi_Minh')::date = $1`. It is fast in development (small table) and scans 40M rows in production.

| | Condition | Plan |
|---|---|---|
| Before | `(created_at AT TIME ZONE 'Asia/Ho_Chi_Minh')::date = $1` | Seq Scan: the indexed column is transformed |
| After | `created_at >= $start AND created_at < $end`, with `$start`/`$end` computed in the app as the day's boundaries in that timezone | Index Scan on `created_at` |

## Key takeaways

1. An unused index means either the index cannot serve the condition, or a scan is cheaper.
2. Sargable conditions compare the bare indexed column with a constant using a supported operator.
3. Functions, casts and arithmetic on the column hide it: `created_at::date`, `id = 7.0`, MySQL `sku = 123`.
4. Rewrite as ranges on the bare column, or index the expression.
5. `LIKE 'prefix%'` needs byte-ordered indexes in PostgreSQL under non-C collations; leading wildcards need specialist indexes.
6. An `OR` with any unindexed branch forces a full scan in all three engines.
7. MongoDB type mismatches return wrong (empty) results quickly, rather than slow results.
8. Low selectivity and tiny tables are the planner being right, not a problem to fix.
