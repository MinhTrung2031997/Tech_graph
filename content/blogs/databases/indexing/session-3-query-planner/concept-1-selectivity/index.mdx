<Tldr>
**Selectivity** is the fraction of rows a condition keeps (`status = 'shipped'`: 5%). **Cardinality** is how many rows a plan step returns (1M × 5% = 50,000). An index pays off when selectivity is **low**: few rows, so few table pages. In the lab, PostgreSQL used an index for `customer_id <= N` up to about **20%** of the table and switched to a Seq Scan at 50%; for the physically ordered `created_at` it kept the index up to 50%. Planners never know these numbers exactly; they **estimate** them, and a bad estimate is the most common reason for a bad plan.
</Tldr>

## Two words, one idea

| Term | Meaning | `status = 'shipped'` on 1M orders |
|---|---|---|
| Selectivity | Fraction of rows that satisfy a condition, 0 to 1 | 0.05 |
| Cardinality (of a step) | Rows the step returns = input rows × selectivity | 50,000 |
| Cardinality (of a column) | Number of distinct values; PostgreSQL calls it `n_distinct` | `status`: 5, `customer_id`: ≈ 100,000 |
| "Highly selective" | Keeps very few rows (low selectivity number) | `customer_id = 7`: 0.001% |

The two uses of "cardinality" are related: an equality on a column with many distinct values is usually highly selective (1 / 100,000 for `customer_id`), and one on a column with few values is not (≈ 1/5 for `status`).

## Estimates vs reality on the lab

PostgreSQL's estimate is the `rows=` in `EXPLAIN`; the real count is `actual … rows=`.

| Condition | Estimated rows | Actual rows | Selectivity |
|---|---|---|---|
| `status = 'shipped'` | 51,000 | 50,000 | 5% |
| `status = 'pending'` | 199,267 | 200,000 | 20% |
| `status = 'refunded'` | 1 | 0 | 0% |
| `customer_id = 7` | 11 | 7 | 0.001% |
| `customer_id BETWEEN 1 AND 1000` | 8,314 | 9,956 | 1% |
| `created_at < '2025-02-01'` | 86,170 | 84,931 | 8.5% |
| `status = 'shipped' AND channel = 'web'` | 17,060 | 16,666 | 1.7% |
| `id <= 100000 AND created_at < '2025-02-07'` | 10,654 | **100,000** | 10% |

Most estimates are within a few percent. The last one is off by **9.4×**: the planner multiplies the two selectivities (10% × 10% = 1%) as if the columns were independent, but `created_at` rises with `id`, so the second condition removes nothing. Concept 2 shows where each estimate comes from.

## How selectivity picks the plan

| Selectivity | Pages the index route touches | Typical winner |
|---|---|---|
| Tiny (a few rows) | Height + a few table pages | Index Scan |
| Small (≈ 0.1–20%), rows scattered | Many table pages, but fewer than all | Bitmap Heap Scan (PostgreSQL) |
| Large (≈ 20%+), rows scattered | Almost every table page, randomly | Full scan |
| Large, rows physically ordered | A contiguous stretch of the table | Index Scan can still win |

| Term | Meaning |
|---|---|
| **✓ Selective** | Few enough rows that an index route reads fewer, cheaper pages than a full scan |
| **✗ Not selective** | So many rows that reading the whole table in order is cheaper |

### MySQL: rows and filtered

| Term | Meaning |
|---|---|
| `rows` | Estimated rows the access method reads |
| `filtered` | Estimated % of those rows that survive the remaining conditions |
| Index dive | For a range on an indexed column, the optimizer descends the index to the range's ends and estimates the rows between them |
| **✓ Selective / ✗ Not** | Same decision: index range/ref vs full table scan (`type: ALL`) |

### MongoDB: no estimates, a race

| Term | Meaning |
|---|---|
| Candidate plans | One per usable index (and combinations); a collection scan is considered only when no index applies |
| Trial period | Candidates run side by side until one returns 101 documents or does 10,000 units of work (or a fraction of the collection) |
| Score | Based on documents returned per unit of work; the best scorer wins and is cached |
| **✓ Index applies / ✗ No index applies** | IXSCAN candidates vs COLLSCAN |

<Pitfall>
"Add an index on every column in the WHERE clause" ignores selectivity. An index on `status` (5 values) helps only for the rare values; for `delivered` (35%), PostgreSQL's planner reads most of the table anyway, MySQL can pick the index and be **slower** than a full scan, and MongoDB will use it without checking. Index the conditions that keep few rows.
</Pitfall>

## Real-world scenario: the "status" index on a queue table

A `jobs` table has 50M rows: 49.9M `done`, 100,000 `pending`. Workers poll `WHERE status = 'pending' ORDER BY created_at LIMIT 100`. An index on `status` helps that query a lot (0.2% selectivity) but is 98% entries for `done` that no query ever reads.

| Option | Size | Selectivity it serves |
|---|---|---|
| Index on `(status)` | Entries for all 50M rows | Good for `pending`, useless for `done` |
| Partial index `ON jobs (created_at) WHERE status = 'pending'` (Session 5) | 100,000 entries | Exactly the polling query, already ordered |

## Key takeaways

1. Selectivity = fraction of rows a condition keeps; cardinality = rows a step returns (or distinct values of a column).
2. Low selectivity favours an index; high selectivity favours a full scan; physical order shifts the crossover.
3. In the lab, PostgreSQL kept an index route up to ≈ 20% for scattered rows and ≈ 50% for ordered rows.
4. Planners estimate selectivity; most estimates were within a few percent, but correlated columns were off by 9.4×.
5. MySQL estimates with index dives and index statistics, and can pick a low-selectivity index that is slower than a full scan.
6. MongoDB does not estimate: it races candidate plans and caches the winner; a single applicable index is always used.
