<Tldr>
A planner cannot count rows before choosing a plan, so it keeps a **summary** of each column. **PostgreSQL**'s `ANALYZE` samples 30,000 rows and stores the most common values with their frequencies, a 100-bucket histogram, the number of distinct values and the physical correlation. **InnoDB** stores per-index distinct-value counts sampled from 20 pages, dives into the index for ranges, and uses optional histograms for unindexed columns. **MongoDB** keeps no statistics: it races plans and caches the winner. When the data changes faster than the summary, estimates go wrong: in the lab, 300,000 new rows were estimated as **1**.
</Tldr>

## What each engine keeps

| | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| Stored where | `pg_statistic` (readable view: `pg_stats`), `pg_class.reltuples / relpages` | `mysql.innodb_table_stats`, `mysql.innodb_index_stats`, `information_schema.column_statistics` | Nothing persistent; the plan cache in memory |
| Per column | Null fraction, width, distinct count, most common values + frequencies, histogram, correlation | Histogram only if created with `ANALYZE TABLE … UPDATE HISTOGRAM` | — |
| Per index | Size; uses column statistics | Distinct values per key prefix (`n_diff_pfx01` …), leaf pages | — |
| Refreshed by | `ANALYZE`, autovacuum (after 50 + 10% of rows change) | `ANALYZE TABLE`, automatically after 10% of rows change | Plans re-raced when the cache entry is evicted or performs badly |
| Sample | 300 × `default_statistics_target` (100) = 30,000 rows | 20 pages per index (`innodb_stats_persistent_sample_pages`) | — |

## PostgreSQL: pg_stats on the lab

```sql
SELECT attname, n_distinct, most_common_vals, most_common_freqs, correlation
FROM pg_stats WHERE tablename = 'orders' AND attname IN ('status', 'customer_id', 'created_at');
```

| Column | `n_distinct` | Most common values (frequency) | Histogram | `correlation` |
|---|---|---|---|---|
| `status` | 5 | delivered 0.352, paid 0.349, pending 0.199, shipped 0.051, cancelled 0.049 | none (every value is in the MCV list) | 0.29 |
| `customer_id` | 91,474 (real: 100,000) | none: no value is common enough | 101 bounds: 4, 1188, 2198, 3319 … | −0.01 |
| `created_at` | −1 (= every row distinct) | none | 101 bounds | 1.0 |

| Term | Meaning |
|---|---|
| MCV list | Most common values and their frequencies, up to `default_statistics_target` entries |
| Histogram | Bounds splitting the remaining values into 100 buckets with equal numbers of rows |
| `n_distinct` | Distinct values; a negative number is a fraction of the rows (−1 = all distinct) |
| **✓ In the MCV list** | The value's frequency is read directly |
| **✗ Not in the MCV list** | Assume the value is as frequent as an average non-MCV value |

### When the summary is not enough

| Problem | Symptom | Fix |
|---|---|---|
| Skewed column (a few huge values among many small ones) | Estimates for big values far too low | `ALTER TABLE orders ALTER COLUMN customer_id SET STATISTICS 1000; ANALYZE orders;` (bigger MCV list and histogram) |
| Correlated columns | Combined conditions underestimated (9.4× in Concept 1) | `CREATE STATISTICS orders_dep (dependencies, mcv) ON status, channel FROM orders; ANALYZE orders;` (helps equality conditions) |
| Bulk load or big delete | Estimates from the old data | Run `ANALYZE` right after the load; autovacuum waits for 50 + 10% of the rows to change (100,050 for `orders`) |
| Expression in WHERE | No statistics on `lower(email)` | An expression index gathers statistics on the expression (Session 5) |

## MySQL InnoDB: index statistics, dives and histograms

```sql
SELECT index_name, stat_name, stat_value, sample_size FROM mysql.innodb_index_stats
WHERE table_name = 'orders' AND stat_name LIKE 'n_diff%';
```

| Index | `n_diff_pfx01` (distinct first column) | Sample pages | Reality |
|---|---|---|---|
| `orders_customer_idx` | 99,661 | 20 | 100,000 |
| `orders_status_idx` | 4 | 6 | 5 |
| `orders_sku_idx` | 4,979 | 20 | 5,000 |

| Term | Meaning |
|---|---|
| Index statistics | Distinct values per key prefix, from sampled leaf pages; used for equality (`ref`) estimates: rows ≈ table rows / distinct values |
| Index dive | For a range or a short `IN` list (≤ `eq_range_index_dive_limit` = 200 values) on an indexed column, descend the index to the range ends and estimate the entries between |
| Histogram | Bucket statistics for a column, created explicitly; used for conditions on **unindexed** columns |
| **✓ Indexed column / ✗ Not indexed** | Indexed: statistics or dives. Not indexed: histogram if present, otherwise a fixed guess |

## MongoDB: the plan cache instead of statistics

| Term | Meaning |
|---|---|
| Query shape | The filter, sort and projection with values removed: `{ status: ?, customer_id: { $lte: ? } }` |
| Plan cache entry | The winning plan for a shape, with the work it took (`works`) |
| Inactive → active | A new entry starts inactive; when the shape runs again within that work, it becomes active and is reused |
| Replanning | If an active plan needs more than 10× its recorded work, MongoDB races the candidates again |
| **✓ Active entry / ✗ No usable entry** | Reuse the cached plan, or run a trial |

<Pitfall>
After a bulk load, an `ANALYZE` (PostgreSQL) or `ANALYZE TABLE` (MySQL) is part of the load, not an optional extra. Automatic re-analysis only happens after enough changes **and** some time, and the first queries on the new data run with the old statistics.
</Pitfall>

## Real-world scenario: the nightly import

Every night a job truncates `daily_sales` and loads 5M rows, then dashboards query it. On the first morning query the plan is a nested loop estimated at 1 row; by 9 am it is a hash join and fast.

| Time | What happened |
|---|---|
| 02:00 | `TRUNCATE` + `COPY` of 5M rows: statistics still describe yesterday's data, or an empty table |
| 08:00 | First dashboard query: estimates from stale statistics → nested loop |
| 08:05 | Autovacuum notices the changes and runs `ANALYZE` |
| 09:00 | Same query: correct estimates → hash join |

**Fix:** end the import job with `ANALYZE daily_sales;` (seconds for 5M rows). In MySQL, `ANALYZE TABLE daily_sales`.

## Key takeaways

1. Planners estimate rows from summaries, not counts.
2. PostgreSQL keeps most common values, a 100-bucket histogram, `n_distinct` and correlation per column, from a 30,000-row sample.
3. A value in the MCV list gets its own frequency; others get an average; ranges interpolate in the histogram.
4. InnoDB keeps distinct counts per index prefix from 20 sampled pages, dives into indexes for ranges, and can use histograms for unindexed columns.
5. MongoDB keeps no statistics; it caches the winning plan per query shape and replans when it degrades.
6. Stale statistics after bulk changes give wild estimates (1 vs 300,000); run `ANALYZE` after loads.
7. Extended statistics and higher statistics targets fix correlated and skewed columns.
