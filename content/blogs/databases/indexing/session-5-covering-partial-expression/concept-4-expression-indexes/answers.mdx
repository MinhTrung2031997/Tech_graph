<Tldr>
Index the exact, deterministic expression your queries filter on, or rewrite the query so it filters on the bare column.
</Tldr>

## Q1. Index or rewrite

**Question:** when should you create an expression index instead of rewriting the query?

Rewrite when an equivalent condition on the bare column exists (a date range instead of `::date`). Index the expression when no such rewrite exists or it is awkward: case-insensitive comparison (`lower(email)`), a value extracted from JSON (`data->>'country'`), a calendar day in a specific time zone, or when the query is generated by code you cannot change.

> **Common mistake:** adding expression indexes for conditions that a simple range rewrite would serve with an existing index.

## Q2. created_at::date rejected

**Question:** why did PostgreSQL refuse `CREATE INDEX ON orders ((created_at::date))`, and what made the UTC version acceptable?

Casting a `timestamptz` to `date` depends on the session's `TimeZone`: the same instant is 1 March in UTC and 2 March in Asia/Ho_Chi_Minh late in the evening. An index entry must not depend on who reads it, so PostgreSQL only accepts IMMUTABLE expressions and refused ("functions in index expression must be marked IMMUTABLE"). `(created_at AT TIME ZONE 'UTC')::date` fixes the time zone inside the expression, so its result depends only on the row: immutable.

> **Common mistake:** marking a wrapper function IMMUTABLE to bypass the check; the index then gives wrong answers when the setting changes.

## Q3. Which conditions use lower(sku)

**Question:** with an index on `lower(sku)`, which of these can use it: `lower(sku) = 'sku-1'`; `upper(sku) = 'SKU-1'`; `sku ILIKE 'sku-1'`?

Only `lower(sku) = 'sku-1'`. The planner matches the indexed expression textually; `upper(sku)` and `ILIKE` mean the same thing to a human but are different expressions or operators to the planner.

> **Common mistake:** expecting the planner to understand that two expressions are equivalent.

## Q4. Statistics on expressions

**Question:** what extra benefit does an expression index give the PostgreSQL planner, beyond an access path?

`ANALYZE` collects statistics on the indexed expression (most common values, histogram, distinct count), stored under the index's name in `pg_stats`. Without them the planner guesses selectivity for `lower(sku) = …` with a default; with them it estimates accurately, which also helps when the index is not used (joins, filters elsewhere in the plan).

> **Common mistake:** creating extended statistics (`CREATE STATISTICS … ON (lower(sku))`) when an expression index already provides them; useful only if you want the statistics without the index.

## Q5. LOWER(sku) in MySQL

**Question:** why is an index on `LOWER(sku)` often unnecessary in MySQL?

MySQL's default collation `utf8mb4_0900_ai_ci` is case-insensitive (and accent-insensitive). `sku = 'sku-000123'` already matches `'SKU-000123'`, and a plain index on `sku` serves it: the lab returned all 200 rows through `ref` access on a plain index. `LOWER()` is needed only on columns with a case-sensitive (`_cs` or `_bin`) collation.

> **Common mistake:** porting PostgreSQL habits (`lower()` everywhere) to MySQL and adding redundant functional indexes.

## Q6. The unused collation index

**Question:** a MongoDB collation index exists, but a case-insensitive lookup still does a COLLSCAN and returns nothing. What is missing?

The query's collation. Without `.collation({ locale: 'en', strength: 2 })` (or a matching collection default), MongoDB compares strings binary-wise: `'sku-000123'` does not equal `'SKU-000123'`, and an index built with a different collation cannot serve the query. Result in the lab: COLLSCAN, 0 documents.

> **Common mistake:** assuming the index's collation applies to every query on that field.

## Q7. Case-insensitive unique emails

**Question:** how would you make emails unique regardless of case in PostgreSQL and in MongoDB?

| Engine | Index | Queries |
|---|---|---|
| PostgreSQL | `CREATE UNIQUE INDEX ON users (lower(email));` | `WHERE lower(email) = lower($1)` |
| MongoDB | `db.users.createIndex({ email: 1 }, { unique: true, collation: { locale: 'en', strength: 2 } })` | with `.collation({ locale: 'en', strength: 2 })` |

Both reject `A@x.com` once `a@x.com` exists. (PostgreSQL's `citext` type is an alternative.)

> **Common mistake:** a plain unique index plus lowercasing in the application; one code path that forgets to lowercase lets duplicates in.
