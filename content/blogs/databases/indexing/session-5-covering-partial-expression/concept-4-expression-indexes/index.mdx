<Tldr>
Session 3 showed that a function on a column hides it from the index (`created_at::date = …` → Seq Scan). When the query cannot be rewritten, **index the expression itself**. In PostgreSQL, `CREATE INDEX ON orders (lower(sku))` turned a parallel Seq Scan into a Bitmap scan over 207 rows; MySQL's functional key parts do the same (`((LOWER(sku)))`, `ref`, 200 rows). The expression must be **deterministic**: PostgreSQL rejected `created_at::date` (it depends on the session time zone) and accepted `(created_at AT TIME ZONE 'UTC')::date`. MongoDB has no expression indexes: use a **case-insensitive collation index** (200 keys) or store the computed value in a field.
</Tldr>

## When to index an expression

| Query | Plain index on the column | Expression index |
|---|---|---|
| `WHERE lower(email) = lower($1)` | ✗ function hides the column | `ON users (lower(email))` |
| `WHERE (created_at AT TIME ZONE 'UTC')::date = $1` | ✗ | `ON orders (((created_at AT TIME ZONE 'UTC')::date))` |
| `WHERE created_at >= $1 AND created_at < $2` | ✓ already sargable | Not needed: prefer this rewrite |
| `WHERE data->>'country' = 'VN'` (JSON) | ✗ | `ON events ((data->>'country'))` |

Prefer rewriting the query (Session 3, Concept 5) when you can; index the expression when the expression is the natural way to ask, or the query is outside your control.

| Term | Meaning |
|---|---|
| Expression index | Entries hold the computed value, sorted by it |
| IMMUTABLE | A function whose result depends only on its arguments, never on settings, time or data; required for index expressions in PostgreSQL |
| Exact match | The query must contain the same expression as the index (`lower(sku)`, not `upper(sku)`) |
| **✓ Same expression / ✗ Different** | Index usable or not |

## MySQL: functional key parts

MySQL 8.0.13+ indexes expressions written in double parentheses; internally each is a hidden virtual generated column.

| Term | Meaning |
|---|---|
| Functional key part | `INDEX ((expr))`; the query must use the same expression |
| Generated column | The older way: `ALTER TABLE … ADD day DATE AS (DATE(created_at))`, then index `day` |
| **✓ Same expression / ✗ Different** | As in PostgreSQL |

## MongoDB: collations and computed fields

MongoDB indexes fields, not expressions. Two substitutes:

| Need | Substitute |
|---|---|
| Case-insensitive match | An index with a collation of strength 1 or 2; the query must specify the same collation |
| Any other derived value (day, normalised text, JSON path) | Store it as its own field at write time and index that field |

| Term | Meaning |
|---|---|
| Collation strength 2 | Compares letters ignoring case (but not accents) |
| **✓ Same collation / ✗ Default collation** | The index is used only by queries with a matching collation |

<Pitfall>
An expression index is maintained on every insert and on every update that changes its input columns, and the function runs each time. Expensive functions (regexes, JSON parsing of large documents) make writes slower. Index the expression only if queries really use it; otherwise rewrite the query.
</Pitfall>

## Real-world scenario: case-insensitive email login

Login does `WHERE email = $1`, and users type their address with random capitalisation. The team adds `lower()` to the query and logins become full scans.

| Engine | Fix |
|---|---|
| PostgreSQL | `CREATE UNIQUE INDEX users_email_lower ON users (lower(email));` and query `WHERE lower(email) = lower($1)`; the unique index also stops `A@x.com` and `a@x.com` from both registering. Alternative: the `citext` type |
| MySQL | Usually nothing: the default `_ci` collation already compares case-insensitively, and a unique index on `email` already rejects case variants |
| MongoDB | Unique index on `email` with collation strength 2, queries with that collation; or store `email_lower` and index it |

## Key takeaways

1. An expression index stores computed values, so queries filtering on the same expression can seek.
2. PostgreSQL requires IMMUTABLE expressions: `created_at::date` on `timestamptz` was rejected; `(created_at AT TIME ZONE 'UTC')::date` worked.
3. The query must use the same expression as the index; planners match it textually.
4. PostgreSQL gathers statistics on indexed expressions, improving estimates.
5. MySQL 8.0.13+ has functional key parts (hidden generated columns); default `_ci` collations often make `LOWER()` unnecessary.
6. MongoDB has no expression indexes: use collation indexes for case-insensitivity, stored fields for other derived values.
