<Tldr>
A PostgreSQL index entry says where a row version is, not whether your transaction may see it (Session 2, Concept 4). An **index-only scan** therefore checks the **visibility map**, one bit per heap page meaning "every row here is visible to everyone". Bit set: skip the heap. Bit cleared: fetch the row after all. VACUUM sets the bits; any change to a page clears them. In the lab, updating **1% of the rows** (one per page) cleared the bit on 98% of pages: the same covering query went from **0 heap fetches and 53 buffers to 9,967 heap fetches and 10,014 buffers**, slower than not covering at all, until VACUUM ran. InnoDB and MongoDB solve visibility differently and have no such map.
</Tldr>

## Why the index cannot answer alone

| Fact | Consequence |
|---|---|
| Index entries have no `xmin`/`xmax` | The index cannot tell a live row from a deleted, updated or uncommitted one |
| Visibility is decided on the heap tuple | Normally every index lookup visits the heap |
| The visibility map marks pages where every tuple is visible to all transactions | For those pages, the heap visit can be skipped |

| Term | Meaning |
|---|---|
| Visibility map (VM) | A small file per table: 2 bits per heap page, "all-visible" and "all-frozen" |
| `Heap Fetches` | Rows an Index Only Scan still had to check in the heap |
| VACUUM | Removes dead tuples and sets the all-visible bit on pages it leaves fully visible |
| Index cleanup bypass | Since PostgreSQL 14, VACUUM may skip index vacuuming when very few pages have dead items; those pages then stay not all-visible |
| **✓ All-visible / ✗ Not all-visible** | Skip the heap / fetch the row |

### Keeping index-only scans index-only

| Table pattern | Visibility map | What to do |
|---|---|---|
| Append-only (logs, events) | New pages need one VACUUM to be marked | PostgreSQL 13+ autovacuums after inserts too (`autovacuum_vacuum_insert_scale_factor`); nothing else needed |
| Mostly static with rare updates | Mostly all-visible | Default autovacuum is fine |
| Hot updates spread over the table | Bits constantly cleared | Lower `autovacuum_vacuum_scale_factor` for the table; check `Heap Fetches` in plans; consider whether index-only scans are realistic here |

## MySQL InnoDB: page-level transaction ids

InnoDB secondary indexes also lack per-row visibility, but InnoDB checks visibility per **index page**: each secondary page records the largest transaction id that modified it (`PAGE_MAX_TRX_ID`).

| Term | Meaning |
|---|---|
| Read view | The set of transactions a statement may see |
| `PAGE_MAX_TRX_ID` | Newest transaction that changed this secondary index page |
| **✓ Page older than the read view** | Every entry on it is safe: answer from the index |
| **✗ Page possibly newer** | Look up the clustered record (and undo log) to decide visibility |

## MongoDB: no map needed

WiredTiger keeps recent versions of index entries and documents in memory (update chains) and reads each at the query's snapshot. A covered query reads index entries as of its snapshot and never needs the document to decide visibility.

| | PostgreSQL | InnoDB | MongoDB |
|---|---|---|---|
| Where visibility lives | Heap tuple (`xmin`/`xmax`) | Clustered record + undo log | WiredTiger versions of each key and document |
| Index-only / covered read must | Check the visibility map, else fetch the row | Check the page's max trx id, else fetch the row | Read the index at its snapshot |
| Maintenance that matters | VACUUM (sets VM bits) | Purge (removes delete-marked entries) | Checkpoints / eviction (not visibility-related) |

<Pitfall>
"Index Only Scan" in a PostgreSQL plan is a plan **type**, not a promise. Always look at `Heap Fetches`. An index-only plan on a table with fresh changes can do as many heap visits as a normal Index Scan, in index order, which is worse than a Bitmap Heap Scan.
</Pitfall>

## Real-world scenario: the dashboard that is fast at 9 am and slow at 11 am

A covering index serves a dashboard query on `orders`. Overnight, autovacuum runs and the query takes 2 ms. During the morning, status updates touch rows all over the table, and by 11 am the query takes 80 ms; at 1 pm, after autovacuum, it is fast again.

| Check | Finding |
|---|---|
| `EXPLAIN (ANALYZE, BUFFERS)` at 11 am | Index Only Scan, `Heap Fetches` ≈ rows returned |
| `pg_visibility_map('orders')` | Most pages not all-visible |
| `pg_stat_user_tables.last_autovacuum` | Hours ago; scale factor 0.2 = 20% of the table must change first |

**Fix:** `ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.02);` so autovacuum runs after 2% changes, keeping the visibility map fresh during the day.

## Key takeaways

1. PostgreSQL index entries carry no visibility information; an index-only scan checks the visibility map instead of the heap.
2. VACUUM sets a page's all-visible bit; any change to the page clears it.
3. Updating 1% of rows, spread out, cleared 98% of the bits: 0 → 9,967 heap fetches, 53 → 10,014 buffers.
4. VACUUM may bypass index cleanup when few pages have dead items, leaving those pages not all-visible; `INDEX_CLEANUP ON` forces it.
5. Check `Heap Fetches`, not just the plan name.
6. InnoDB checks visibility per secondary page via its max transaction id; MongoDB reads index versions at the query snapshot; neither has a visibility map.
