<Tldr>
Session 2 showed that the expensive part of an index lookup is often the **second step**, fetching each row. A **covering index** removes it: it contains every column the query filters on **and** returns. For 9,956 rows of customers 1–1,000, PostgreSQL went from **6,404 buffers to 53** with `INCLUDE (amount)`, MySQL from **40,014 page requests to 1,133**, and MongoDB from **10,000 documents fetched to 0**. The price is a bigger index (39 MB vs 30 MB) and more work on every write.
</Tldr>

## What "covering" means

| Query | Index | Covered? |
|---|---|---|
| `SELECT created_at, amount FROM orders WHERE customer_id = 7` | `(customer_id, created_at)` | ✗ `amount` is missing: a row fetch per match |
| same | `(customer_id, created_at) INCLUDE (amount)` | ✓ |
| same | `(customer_id, created_at, amount)` | ✓ (amount as a key column) |
| `SELECT * …` | any normal index | ✗ |

## Key columns vs INCLUDE columns (PostgreSQL)

| | Key column | `INCLUDE` column |
|---|---|---|
| Stored in | Every level of the tree | Leaf entries only |
| Sorted by it, searchable, usable for `ORDER BY` | ✓ | ✗ |
| Counts toward uniqueness in a `UNIQUE` index | ✓ | ✗ (so `UNIQUE (email) INCLUDE (name)` still means unique emails) |
| Use for | Columns you filter or sort on | Columns you only return |

MySQL and MongoDB have no `INCLUDE`: extra columns are added as trailing key columns, which works the same for covering but makes internal pages wider.

| Term | Meaning |
|---|---|
| Index-only scan | PostgreSQL plan that answers from the index; still checks the visibility map (Concept 2) |
| `Using index` | MySQL's EXPLAIN marker for a covering index |
| `PROJECTION_COVERED` | MongoDB's stage when no document is fetched |
| **✓ Covered / ✗ Needs the row** | Whether the second step can be skipped |

## What covering costs

| Cost | Lab |
|---|---|
| Size | PostgreSQL: 30 MB → 39 MB with `INCLUDE (amount)`; MongoDB `cust_cov` 26 MB vs `customer_id_1` 6.8 MB |
| Writes | Every insert writes the extra bytes; every update of an included column updates the index (and in PostgreSQL makes the update non-HOT) |
| Visibility (PostgreSQL only) | Index-only scans need all-visible pages (Concept 2) |

<Pitfall>
Covering is for **specific, frequent** queries. "Add every column to INCLUDE" turns the index into a second copy of the table that must be maintained on every write, and any update to an included column can no longer be a HOT update. Cover the queries on your hot path, not the table.
</Pitfall>

## Real-world scenario: the order-list API

The mobile app's order list shows id, date, status and total for a user's 20 latest orders: `SELECT id, created_at, status, amount FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 20`.

| Index | Work per call |
|---|---|
| `(user_id)` | All the user's rows + sort |
| `(user_id, created_at)` | 20 entries + 20 row fetches |
| PostgreSQL: `(user_id, created_at) INCLUDE (status, amount)`; MySQL: `(user_id, created_at, status, amount)`; MongoDB: `{ user_id: 1, created_at: -1, status: 1, amount: 1 }` + `_id` in the index or excluded | 20 index entries, no row fetch |

## Key takeaways

1. A covering index contains every column a query filters on and returns, so the row fetch is skipped.
2. PostgreSQL's `INCLUDE` adds return-only columns to leaf entries without affecting order or uniqueness.
3. MySQL and MongoDB cover with trailing key columns; InnoDB entries already include the primary key.
4. MongoDB queries are covered only with `_id` excluded or indexed.
5. Measured gains: 6,404 → 53 buffers, 40,014 → 1,133 page requests, 10,000 → 0 documents.
6. Covering costs size, write work and (in PostgreSQL) HOT updates on included columns.
