<Tldr>
A **partial index** contains entries only for rows matching a condition. Queries about cancelled orders need only the 50,000 cancelled rows indexed, not 1M: `CREATE INDEX … ON orders (created_at) WHERE status = 'cancelled'` is **1.1 MB** against **35 MB** for `(status, created_at)`, and answers "oldest 100 cancelled orders" in 23 buffers. The planner uses it only when it can **prove** the query's WHERE implies the index's WHERE: a literal `status = 'cancelled'` works, a generic prepared statement with `status = $1` does not. MongoDB has the same feature (`partialFilterExpression`, 2.4 MB vs 12 MB); MySQL has none, and its `CASE` expression workaround saved nothing (1,059 pages vs 1,123).
</Tldr>

## Why index only some rows

| Situation | Full index | Partial index |
|---|---|---|
| Queue: `WHERE status = 'pending' ORDER BY created_at` | Entries for 1M rows, 80% never queried | Entries for the 200,000 pending only |
| Soft deletes: `WHERE deleted_at IS NULL` | Entries for deleted rows too | Live rows only |
| Rare flag: `WHERE needs_review` | Mostly `false` entries | The few `true` rows |
| Unique only among active rows | Impossible as a plain unique index | `UNIQUE … WHERE active` |

Smaller index = fewer pages to cache, faster maintenance: rows outside the condition are never written into it.

| PostgreSQL index | Rows indexed | Size |
|---|---|---|
| `(status, created_at)` | 1,000,000 | 35 MB (4,461 leaves) |
| `(created_at) WHERE status = 'pending'` | 200,000 | 4.4 MB (547 leaves) |
| `(created_at) WHERE status = 'cancelled'` | 50,000 | 1.1 MB (137 leaves) |

## PostgreSQL: CREATE INDEX … WHERE

| Term | Meaning |
|---|---|
| Index predicate | The index's `WHERE` clause |
| Predicate implication | The planner must prove from the query's conditions that every row it wants satisfies the index predicate |
| Generic plan | A prepared statement's plan built once without knowing parameter values (`plan_cache_mode`, or after 5 executions if no cheaper) |
| **✓ Implied / ✗ Not provable** | Partial index usable or not |

### Partial unique indexes

```sql
-- At most one pending order per customer
CREATE UNIQUE INDEX one_pending_per_customer ON orders (customer_id) WHERE status = 'pending';
-- ERROR:  could not create unique index "one_pending_per_customer"
-- DETAIL: Key (customer_id)=(66865) is duplicated.
```

The lab data violates the rule (customers have several pending orders), so the index cannot be built: the constraint is checked over existing rows first. On a table that follows the rule, it enforces "unique among pending rows only", something no plain unique index can express.

## MySQL: no partial indexes

InnoDB indexes every row, and indexes `NULL` values too, so the usual tricks do not shrink anything:

| Attempt | Result in the lab |
|---|---|
| Functional index on `(CASE WHEN status = 'pending' THEN created_at END)` | 1,059 pages: the same size as a full date index (1,123), because non-pending rows get a `NULL` entry |
| Generated column + index | Same: one entry per row |

| Term | Meaning |
|---|---|
| **✓ Supported / ✗ Not supported** | MySQL has no `CREATE INDEX … WHERE` |

## MongoDB: partialFilterExpression

| Term | Meaning |
|---|---|
| `partialFilterExpression` | The index's filter: only matching documents get entries |
| Usability | The query must include the filter condition (or a stricter one); MongoDB does not use it otherwise |
| Sparse index | Older, narrower form: index only documents that have the field |
| **✓ Query matches the filter / ✗ Does not** | As in PostgreSQL |

<Pitfall>
A partial index that queries cannot prove they match is dead weight that still costs writes. After creating one, check the plans of the **real** application queries, with the parameters the driver actually sends, not hand-written literals.
</Pitfall>

## Real-world scenario: soft deletes

A `products` table keeps deleted rows with `deleted_at` set; 70% of rows are deleted. Every query has `WHERE deleted_at IS NULL`. The index on `(merchant_id, name)` is mostly deleted products.

| PostgreSQL | Effect |
|---|---|
| `CREATE INDEX ON products (merchant_id, name) WHERE deleted_at IS NULL` | ≈ 30% of the size; every application query matches the predicate |
| `CREATE UNIQUE INDEX ON products (merchant_id, sku) WHERE deleted_at IS NULL` | SKUs unique among live products; a deleted product's SKU can be reused |

MongoDB: the same with `partialFilterExpression: { deleted_at: null }` (accepted by MongoDB 8.0 in the lab), and queries that include `deleted_at: null`. MySQL: keep the composite index, or move deleted rows to an archive table.

## Key takeaways

1. A partial index stores entries only for rows matching its WHERE condition.
2. Lab: cancelled-only index 1.1 MB vs 35 MB for the full composite; 23 buffers for the oldest 100 cancelled orders.
3. PostgreSQL uses it only when the query provably implies the predicate; generic plans with `status = $1` cannot.
4. Partial unique indexes enforce uniqueness among a subset of rows.
5. MongoDB has `partialFilterExpression` with the same "query must match" rule.
6. MySQL has no partial indexes; expression or generated-column tricks still index every row.
