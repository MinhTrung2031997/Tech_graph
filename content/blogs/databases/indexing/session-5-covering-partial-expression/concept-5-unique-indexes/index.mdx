<Tldr>
A unique constraint is implemented **by** a unique index: before inserting a key, the engine descends the index to where the key would go (the "missing key" lookup of Session 2) and fails if it is already there. The rules differ on **NULL**: PostgreSQL and MySQL allow any number of NULLs (unless PostgreSQL 15+'s `NULLS NOT DISTINCT`), while MongoDB indexes a missing field as `null`, so a second document without the field is a duplicate. Unique indexes are also what make **upserts** safe under concurrency. With the index in memory, the check was free in PostgreSQL and MySQL in the lab (within noise) and cost MongoDB about 50% on a bulk load.
</Tldr>

## How an insert is checked

| Step | What happens |
|---|---|
| 1. Descend | Find the leaf where the new key belongs |
| 2. Look for equal keys | If a visible row with the same key exists: error (or, for an upsert, take the update path) |
| 3. Uncommitted duplicate? | If another transaction inserted the same key and has not committed, wait for it: fail if it commits, continue if it aborts |
| 4. Insert | Add the entry |

| Engine | Primary key | NULLs in a unique index |
|---|---|---|
| PostgreSQL | Unique + NOT NULL | Distinct by default: many NULLs allowed. `UNIQUE NULLS NOT DISTINCT` (v15+): one NULL |
| MySQL | Unique + NOT NULL; also the clustered index | Many NULLs allowed |
| MongoDB | `_id`, always unique | A missing field is indexed as `null`: only one document may lack it (unless the index is partial or sparse) |

Measured in the lab: PostgreSQL accepted two `NULL` emails and rejected the second `'a@x'`; with `NULLS NOT DISTINCT` it rejected the second `NULL`. MySQL accepted two `NULL`s. MongoDB rejected the second document without an `email` field.

| Term | Meaning |
|---|---|
| Unique violation | PostgreSQL `23505`, MySQL `1062`, MongoDB `E11000` |
| Upsert | Insert, or update if the key exists: `ON CONFLICT`, `ON DUPLICATE KEY UPDATE`, `upsert: true` |
| **✓ Key absent / ✗ Key present** | Insert proceeds / violation or update path |

## MySQL

| Term | Meaning |
|---|---|
| `ON DUPLICATE KEY UPDATE` | MySQL's upsert; fires on a conflict with **any** unique index, including the primary key |
| Change buffer | Defers secondary-index changes for pages not in memory; cannot be used for unique indexes (the page must be read to check), and is off by default since 8.4 |
| **✓ Key absent / ✗ Key present** | As before |

## What the check costs

Bulk-inserting 500,000 rows with random values into a table with one secondary index on that column, unique vs not (the index fits in memory):

| Engine | Plain index | Unique index |
|---|---|---|
| PostgreSQL 17 | 609 ms | 564 ms (within noise) |
| MySQL 8.4 | 1,256 ms | 1,263 ms (within noise) |
| MongoDB 8.0 | 1,286 ms | 1,914 ms (+49%) |

With the index cached, the lookup is cheap because the insert must descend to the same leaf anyway. The cost grows when the index does not fit in memory (each check may be a random read that a non-unique insert could have deferred) and under concurrency (waits on uncommitted duplicates; in InnoDB, extra gap locking for unique checks).

<Pitfall>
"Check then insert" in application code (`SELECT … WHERE email = ?`, then `INSERT` if none) is a race: two requests can both see nothing and both insert. Only a unique index makes it safe. Let the database reject the duplicate (or use an upsert) and handle the error.
</Pitfall>

## Real-world scenario: idempotent webhooks

A payment provider retries webhooks, sometimes concurrently. Each payment must be recorded once.

| Approach | Result |
|---|---|
| `SELECT` by `provider_event_id`, insert if missing | Occasional duplicate payments under concurrent retries |
| Unique index on `provider_event_id` + `INSERT … ON CONFLICT DO NOTHING` (PostgreSQL) / `INSERT IGNORE` or `ON DUPLICATE KEY` (MySQL) / upsert with a unique index (MongoDB) | Exactly one row per event, whatever the timing |

## Key takeaways

1. A unique constraint is enforced by a unique index: every insert descends it and fails on an existing visible key.
2. Concurrent inserts of the same key wait for each other, which is what makes the constraint and upserts race-free.
3. NULLs: PostgreSQL and MySQL allow many (PostgreSQL 15+ can forbid with `NULLS NOT DISTINCT`); MongoDB treats a missing field as `null`, allowing only one, unless the index is partial or sparse.
4. Upserts (`ON CONFLICT`, `ON DUPLICATE KEY UPDATE`, `upsert: true`) need a unique index to be safe.
5. With the index in memory the check is cheap (PostgreSQL, MySQL within noise; MongoDB +49% on bulk load); it costs more on large uncached indexes.
6. Never enforce uniqueness with check-then-insert in application code.
