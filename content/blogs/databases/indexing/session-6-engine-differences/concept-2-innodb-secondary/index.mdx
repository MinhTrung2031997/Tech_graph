<Tldr>
Session 1 established that InnoDB's table **is** the primary-key B-tree and every secondary entry is `(indexed columns, primary key)`. This concept looks at maintenance. The primary key is copied into **every** entry of **every** secondary index: the same 1M-row index on an `INT` column took **1,078** leaves with a `BIGINT` key, **1,570** (+46%) with `BINARY(16)` and **2,866** (+166%) with a `CHAR(36)` UUID. An update to an indexed column delete-marks the old entry and inserts a new one in that index only (twice the page writes of a non-indexed update in the lab); an update to the **primary key** moves the row and rewrites its entry in every secondary index. Delete-marked entries wait for the **purge** thread, much as PostgreSQL's dead entries wait for VACUUM.
</Tldr>

## The primary key is in every entry

| Secondary index on `c INT`, 1M rows (built after loading) | Entry | Leaf pages |
|---|---|---|
| `id BIGINT` | 4 + 8 bytes + header | **1,078** |
| `id BINARY(16)` | 4 + 16 bytes + header | **1,570** (+46%) |
| `id CHAR(36)` | 4 + 36 bytes + header | **2,866** (+166%) |

The cost is paid once per secondary index: a table with five secondary indexes and a `CHAR(36)` key pays it five times, plus in the clustered index itself. That is why a wide primary key hurts InnoDB much more than PostgreSQL, whose index entries carry a fixed 6-byte ctid.

| Term | Meaning |
|---|---|
| Delete-mark | InnoDB does not remove a secondary entry immediately on update or delete; it flags it, because older transactions may still need it |
| Purge | Background threads that remove delete-marked entries and undo records once no read view needs them |
| History list length | Undo logs waiting for purge (`SHOW ENGINE INNODB STATUS`); grows when long transactions hold old read views |
| Change buffer | Defers changes to non-unique secondary index pages not in memory; **off by default since 8.4** (`innodb_change_buffering = none`) |
| **✓ Only this index / ✗ Every index** | Which secondary indexes an update touches |

## The same events in PostgreSQL and MongoDB

| Event | InnoDB | PostgreSQL | MongoDB |
|---|---|---|---|
| Update a non-indexed column | No secondary change | No index change if HOT; otherwise a new entry in **every** index | No index change |
| Update an indexed column | That index: delete-mark + insert | **Every** index gets a new entry | That index: remove + insert |
| Update the primary key | Row moves; every secondary entry rewritten | Like any indexed column | `_id` is immutable |
| What the entry points at | Primary key value | ctid (6 bytes) | RecordId |
| Wide primary key costs | Every secondary index | Only the primary-key index | Only the `_id` index |
| Cleanup | Purge | VACUUM | WiredTiger, transparently |

<Pitfall>
A long-running transaction (an analytics query, a forgotten open session in a client tool) stops purge for everything newer than its read view. Delete-marked secondary entries and undo records pile up, and index scans get slower as they step over entries that are logically gone. Watch the history list length and kill idle transactions.
</Pitfall>

## Real-world scenario: CHAR(36) primary keys

A service stores UUIDs as `CHAR(36)` primary keys in InnoDB, with four secondary indexes. Its database is twice the size of a similar service using `BIGINT` keys.

| | `BIGINT` | `BINARY(16)` time-ordered | `CHAR(36)` random |
|---|---|---|---|
| Bytes of key in every secondary entry | 8 | 16 | 36 (more with a multi-byte charset) |
| One secondary index (lab, 1M rows) | 1,078 leaves | 1,570 | 2,866 |
| Clustered index fill (Session 2) | ≈ 15/16 | ≈ 15/16 | ≈ ⅔ (random inserts) |

**Fix:** store UUIDs as `BINARY(16)` with `UUID_TO_BIN(uuid, 1)` (time-ordered), or use a `BIGINT` key and keep the UUID as a unique secondary column for external references (Concept 4).

## Key takeaways

1. Every InnoDB secondary entry contains the primary key: key width multiplies every secondary index (+46% for `BINARY(16)`, +166% for `CHAR(36)` in the lab).
2. Updating a non-indexed column touches no secondary index.
3. Updating an indexed column delete-marks the old entry and inserts a new one, in that index only.
4. Updating the primary key moves the row and rewrites its entry in every secondary index.
5. Purge removes delete-marked entries once no read view needs them; long transactions delay it.
6. The change buffer is off by default since MySQL 8.4.
