<Tldr>
Session 1 introduced the rule: PostgreSQL never updates a row in place, it writes a **new version**. This concept measures what that does to indexes. Updating every row of a 200,000-row table **doubled** the heap (1,471 → 2,942 pages) and the `customer_id` index (191 → 381 pages), although no customer id changed: each non-HOT version needs its own entry in **every** index. With fill factor 90, a 5% update was **100% HOT**, with no index entries and no heap growth; with fill factor 100 it was 0% HOT. Changing an indexed column is never HOT. InnoDB (undo log) and MongoDB (update chains in memory) keep old versions elsewhere, so their indexes only change when indexed values change.
</Tldr>

## The life of a row version

| Step | Heap | Indexes |
|---|---|---|
| INSERT | Version 1 written | Entry in every index → version 1 |
| UPDATE, page has room, no indexed column changed (HOT) | Version 2 on the **same page**, chained from version 1 | Untouched: entries still point at version 1, which leads to version 2 |
| UPDATE otherwise (non-HOT) | Version 2 on any page with room | **New entry in every index** → version 2; old entries stay |
| Old version no longer visible to anyone | Dead tuple, still occupying space | Dead entries, still in the index |
| VACUUM | Space marked reusable, VM bits set | Dead entries removed (unless bypassed, Session 5) |

| Term | Meaning |
|---|---|
| Dead tuple | A row version no transaction can see any more (`n_dead_tup`) |
| HOT update | Heap-Only Tuple: new version on the same page, no index changes (Session 1) |
| Fill factor | How full INSERTs pack heap pages; the rest is kept for future HOT updates |
| Bottom-up deletion | PostgreSQL 14+: before splitting a leaf, the B-tree removes entries it can prove point to dead versions |
| **✓ HOT / ✗ Not HOT** | Same page and no indexed column changed, or not |

## Measured: one table, three kinds of update

Table `acct (id, customer_id, status, balance, updated_at)`, 200,000 rows, indexes on `id`, `customer_id`, `status`.

| Experiment | HOT | Heap pages | `customer_id` index pages |
|---|---|---|---|
| Fill factor 100, update `balance` on **every** row | 0% | 1,471 → **2,942** | 191 → **381** |
| Fill factor 90, update `balance` on every row | 11% | 1,640 → 3,091 | 191 → 381 |
| Fill factor 100, update `balance` on **5%** of rows | 0% | 1,471 → 1,545 | 191 |
| Fill factor 90, update `balance` on 5% of rows | **100%** | 1,640 (unchanged) | 191 |
| Fill factor 90, update `status` (indexed) on 50% of rows | 0% | — | 381 → **542** |

Three lessons: the `customer_id` index grows when **unrelated** columns change (non-HOT); fill factor 90 only absorbs as many updates as the reserved 10% can hold (≈ 12 rows per page here, so 11% when every row changes); and an update to an indexed column is never HOT, adding entries to **every** index, not just that column's.

## The other engines keep old versions elsewhere

| | PostgreSQL | MySQL InnoDB | MongoDB WiredTiger |
|---|---|---|---|
| Where the new version goes | A new heap tuple | In place, in the clustered index | In memory, on the key's update chain |
| Where the old version goes | Stays in the heap as a dead tuple | Undo log | Older entries of the update chain (and history store if evicted) |
| Index entries on an update of a non-indexed column | New entry in every index, unless HOT | None | None |
| Index entries on an update of an indexed column | New entry in every index | Old entry delete-marked, new entry inserted, in that index only | Old key removed, new key inserted, in that index only |
| Cleanup | VACUUM | Purge thread | Checkpoints / history store pruning |

<Pitfall>
On PostgreSQL, "add an index on `updated_at`" for a table where every write sets `updated_at` makes **every** update non-HOT, so every index on the table gets a new entry on every update. Check `n_tup_hot_upd / n_tup_upd` before and after adding indexes to hot-update tables.
</Pitfall>

## Real-world scenario: a counters table

A `product_stats` table is updated thousands of times per minute (`views = views + 1`). It has indexes on `product_id` (primary key), `category_id` and `updated_at`.

| Setting | HOT ratio | Effect |
|---|---|---|
| Fill factor 100, index on `updated_at`, every update sets `updated_at` | 0% | Three index entries per update; indexes and heap bloat; heavy VACUUM |
| Fill factor 80, drop the `updated_at` index (or stop updating it) | ≈ 100% | No index writes; dead versions pruned on the page |

## Key takeaways

1. PostgreSQL writes a new row version for every update; old versions stay in the heap until VACUUM.
2. A non-HOT version gets a new entry in every index, including indexes on columns that did not change.
3. HOT requires room on the same page and no change to any indexed column.
4. Fill factor 90 made a 5% update 100% HOT; fill factor 100 made it 0% HOT; when every row changes, 10% free space covers only ≈ 11%.
5. Updating an indexed column is never HOT and grows every index.
6. InnoDB updates in place with undo; WiredTiger keeps versions on update chains; neither touches unrelated indexes.
