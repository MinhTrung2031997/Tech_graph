<Tldr>
Session 1's deep dive explained **why** random keys hurt B-trees; here are the measurements per engine, 1M inserts each. PostgreSQL primary-key index: `bigint` **21 MB at 90% fill**, UUIDv4 **38 MB at 71%**, UUIDv7 with sub-millisecond ordering **30 MB at 90%**. A UUIDv7 that is ordered only to the millisecond (random within it) was **37 MB at 73%**, almost as bad as v4 at 600 inserts per millisecond. InnoDB: `BIGINT` 70 MB, random `BINARY(16)` **128 MB and 2.3× slower**, time-ordered `BINARY(16)` 79 MB. MongoDB: ObjectId `_id` index 10 MB, UUIDv4 25 MB and 2.5× slower to insert. Rule: **narrow, monotonically increasing, immutable**.
</Tldr>

## The candidates

| Key | Size | Order | Generated by |
|---|---|---|---|
| `bigint` identity / `AUTO_INCREMENT` | 8 bytes | Increasing | The database |
| UUIDv4 | 16 bytes | Random | Anyone (no coordination) |
| UUIDv7 | 16 bytes | Increasing by time (48-bit ms timestamp first) | Anyone |
| MongoDB ObjectId | 12 bytes | Increasing by time (4-byte seconds + random + counter) | Client driver |
| UUID as `CHAR(36)` text | 36 bytes | Depends on version | — (never store this way) |

| Term | Meaning |
|---|---|
| Monotonic | Each new key is larger than the previous one: inserts append at the right edge of the B-tree |
| Sub-millisecond ordering | UUIDv7 option (RFC 9562 method 3; PostgreSQL 18's `uuidv7()` uses 12 extra bits of time) that keeps keys increasing within one millisecond |
| **✓ Appends at the right edge / ✗ Lands anywhere** | Rightmost splits (pages stay full) vs middle splits (≈ ⅔ full) |

## PostgreSQL: 1M inserts per key type

| Key | Insert time | PK index | Leaf pages | Fill |
|---|---|---|---|---|
| `bigint` identity | 0.75 s | 21 MB | 2,733 | 90.1% |
| UUIDv4 (`gen_random_uuid()`) | 1.69 s | 38 MB | 4,847 | 71.3% |
| UUIDv7, millisecond only (random within the ms) | — | 37 MB | 4,733 | 73.0% |
| UUIDv7 with sub-millisecond ordering | — | **30 MB** | 3,832 | **90.0%** |

(UUIDv7 here comes from a SQL function, `uuidv7_lab()`, because PostgreSQL 17 has no built-in `uuidv7()`; its insert times measure the function, not the key, so they are omitted. PostgreSQL 18's built-in `uuidv7()` includes sub-millisecond ordering.)

The 16-byte UUID index is still ≈ 40% bigger than the `bigint` one when both are 90% full: that is width. The jump from 30 MB to 38 MB is order.

## MySQL InnoDB: the key is the table

| Key | Insert time | Clustered index | Leaves |
|---|---|---|---|
| `BIGINT AUTO_INCREMENT` | 1.38 s | 70 MB | 4,445 |
| `BINARY(16)` random (`RANDOM_BYTES(16)`, like v4) | **3.11 s** | **128 MB** | 7,126 |
| `BINARY(16)` time-ordered (`UUID_TO_BIN(UUID(), 1)`) | 1.66 s | 79 MB | 4,976 |

In InnoDB the damage is bigger than in PostgreSQL because the B-tree being split holds the **whole rows**, and every secondary index also carries the key (Concept 2).

## MongoDB: ObjectId vs UUID

| `_id` | Insert time (1M) | `_id` index | Collection |
|---|---|---|---|
| ObjectId (default) | 1.72 s | 10.2 MB | 9.9 MB |
| UUIDv4 (`UUID()`) | **4.37 s** | **25.0 MB** | 24.6 MB |

ObjectIds start with a 4-byte timestamp, so they increase over time: new `_id` entries append, and the 12-byte values compress well. Random UUIDs scatter inserts over the `_id` index (more cache misses and page rewrites) and compress poorly, which also makes the collection bigger. In a **clustered** collection, a random `_id` would split the collection itself, like InnoDB.

## Recommendations per engine

| Engine | Default choice | If ids must be generated outside the database |
|---|---|---|
| PostgreSQL | `bigint GENERATED ALWAYS AS IDENTITY` | UUIDv7 (`uuidv7()` in 18+); random UUIDv4 costs only the PK index, not the heap |
| MySQL InnoDB | `BIGINT AUTO_INCREMENT` | UUIDv7 or `UUID_TO_BIN(UUID(), 1)` as `BINARY(16)`; never random, never `CHAR(36)` |
| MongoDB | ObjectId | UUIDv7 as BinData if a UUID is required; avoid random UUIDs, especially in clustered collections |

<Pitfall>
UUIDv7 and ObjectId leak creation time to anyone who sees the id. If ids are public (URLs, APIs) and creation time is sensitive, keep an internal ordered primary key and expose a separate random identifier, indexed as a unique secondary column.
</Pitfall>

## Real-world scenario: merging data from many services

Several services create orders independently and replicate them into one database. Integer ids would collide, so the team picks UUIDs.

| Choice | Effect |
|---|---|
| UUIDv4 everywhere | No collisions; InnoDB tables 1.8× larger, inserts 2× slower, cache needs grow with the whole index |
| UUIDv7 everywhere (sub-ms ordered) | No collisions; inserts append; near-integer size in PostgreSQL, near-`BIGINT` in InnoDB when stored as `BINARY(16)` |

## Key takeaways

1. Measured, 1M inserts: random keys made the PostgreSQL PK index 38 MB vs 21 MB (bigint) and 30 MB (ordered UUIDv7).
2. A UUIDv7 ordered only to the millisecond behaved almost like v4 at high insert rates; sub-millisecond ordering fixed it.
3. InnoDB: random `BINARY(16)` 128 MB and 2.3× slower; time-ordered `BINARY(16)` 79 MB vs 70 MB for `BIGINT`.
4. MongoDB: ObjectId `_id` index 10 MB vs 25 MB for UUIDv4, inserts 2.5× faster.
5. Order decides fill and cache behaviour; width decides the remaining size gap.
6. Pick narrow, monotonically increasing, immutable keys; mind the creation-time leak of time-ordered ids.
