<Tldr>
MongoDB's `explain()` comes in three verbosities: `queryPlanner` (the chosen plan, nothing executed), `executionStats` (runs the winner and counts), `allPlansExecution` (also shows the trial of every candidate). Read the **stage tree** bottom-up (IXSCAN or COLLSCAN at the leaf, then FETCH, SORT, PROJECTION, LIMIT), then compare four numbers: **nReturned**, **totalKeysExamined**, **totalDocsExamined**, **executionTimeMillis**. A healthy indexed query has keys ≈ docs ≈ returned. Keys ≫ returned means loose bounds (an unanchored regex: 1,000,000 keys for 200 results). Docs ≫ returned means filtering after FETCH (114 docs for 20). A `SORT` stage means the index does not provide the order (70,000 keys for 20 results). Docs = 0 means covered.
</Tldr>

## The three verbosities

| Mode | Runs the query? | Shows |
|---|---|---|
| `explain()` / `"queryPlanner"` | No | `winningPlan` stage tree, `rejectedPlans`, index bounds |
| `"executionStats"` | Yes, the winning plan | Plus counts and time per stage and in total |
| `"allPlansExecution"` | Yes, plus every candidate's trial | Plus `works`, `advanced` and `score` of each candidate (Session 3) |

## The fields that matter

| Field | Meaning | Healthy |
|---|---|---|
| Stage tree (`executionStages`, nested `inputStage`) | The plan, leaf first: IXSCAN / COLLSCAN → FETCH → SORT → PROJECTION → LIMIT | No COLLSCAN on big collections, no SORT for `sort()+limit()` queries |
| `nReturned` | Documents returned | — |
| `totalKeysExamined` | Index keys read | ≈ nReturned |
| `totalDocsExamined` | Documents fetched | ≈ nReturned (0 if covered) |
| `executionTimeMillis` | Server time | Compare runs in the same cache state |
| `indexBounds` | The ranges scanned per field | Tight ranges, not `[MinKey, MaxKey]` |
| `isMultiKey`, `multiKeyPaths` | Array fields in the index (Concept 3) | — |
| `works`, `advanced`, `needTime`, `isEOF` | Per-stage work units, results produced, units spent without a result, finished | `advanced` close to `works` |

| Term | Meaning |
|---|---|
| Blocking stage | `SORT` (and `GROUP`): consumes all input before producing output |
| **✓ Healthy / ✗ Red flag** | Ratios close to 1 vs a large gap |

## The profiler: explain for production

`db.setProfilingLevel(1, { slowms: 100 })` records slow operations in `system.profile` with the same signals, without running explain by hand:

| Field | Lab example (two queries) |
|---|---|
| `planSummary` | `IXSCAN { status: 1, created_at: -1 }` · `IXSCAN { amount: 1, status: 1, created_at: -1 }` |
| `keysExamined` / `docsExamined` / `nreturned` | 9 / 9 / 3 (channel filtered after FETCH) · 20 / 20 / 20 |
| `millis` | 1 · 0 |

A `planSummary` of `COLLSCAN`, or `docsExamined` far above `nreturned`, in the profiler is the cue to run a full `explain("executionStats")`.

## The same signals in PostgreSQL and MySQL

| Signal | MongoDB | PostgreSQL | MySQL |
|---|---|---|---|
| Full scan | `COLLSCAN` | `Seq Scan` | `type: ALL` |
| Read much, return little | `totalKeysExamined` / `totalDocsExamined` ≫ `nReturned` | `Rows Removed by Filter` ≫ `rows`; Buffers | `rows` × `filtered` ≪ `rows` |
| Sort not from the index | `SORT` stage | `Sort` node | `Using filesort` |
| Covered | `PROJECTION_COVERED`, docs 0 | `Index Only Scan`, `Heap Fetches: 0` | `Using index` |
| Candidate plans | `rejectedPlans`, `allPlansExecution` | Not shown (one cheapest plan) | `EXPLAIN FORMAT=JSON` costs |

<Pitfall>
`explain()` without arguments does not run the query: it shows the plan, not the work. Use `explain("executionStats")` to see keys and documents examined; for reads it executes the query, so mind expensive queries on production. For writes (`db.orders.explain("executionStats").updateMany(…)`), MongoDB reports what the operation would do without applying the changes.
</Pitfall>

## Real-world scenario: a slow endpoint

An endpoint `GET /orders?status=paid&min=400` takes 900 ms. The profiler shows `planSummary: IXSCAN { status: 1 }`, `keysExamined: 350000`, `docsExamined: 350000`, `nreturned: 20`.

| Reading | Conclusion |
|---|---|
| IXSCAN on `{ status: 1 }` | The index matches only the equality |
| keys = docs = 350,000 ≫ 20 | Every paid order is fetched to test `amount` and to sort |
| (explain) SORT stage | `created_at` order not provided |
| Fix | `{ status: 1, created_at: -1, amount: 1 }` (ESR): ≈ 114 keys, 20 docs, no SORT |

## Key takeaways

1. `queryPlanner` shows the plan without running it; `executionStats` runs it and counts; `allPlansExecution` adds every candidate's trial.
2. Read the stage tree from the leaf: IXSCAN or COLLSCAN, then FETCH, SORT, PROJECTION, LIMIT.
3. Compare nReturned with totalKeysExamined and totalDocsExamined: both close to nReturned is healthy.
4. keys ≫ returned: loose index bounds; docs ≫ returned: filtering after FETCH; SORT: wrong index order; docs = 0: covered.
5. `indexBounds` shows whether each field narrows the scan.
6. The profiler records the same counts for slow production operations.
7. PostgreSQL and MySQL show the same signals under different names.
