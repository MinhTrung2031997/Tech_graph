<Tldr>
Running `EXPLAIN` yourself shows the plan **you** get, with your values, cache and settings. To see what production ran, capture plans where they happen. **PostgreSQL:** `auto_explain` logged the order-detail query at **29 ms**: a parallel sequential scan of `order_items` removing 669,004 rows per worker to find 2. It also exposed a regression that no ranking shows by shape: the weekly-revenue report kept the **same plan** but read **1,161** heap pages instead of **384**, because 7 BRIN ranges added by new orders had not been summarized. **MySQL:** `EXPLAIN ANALYZE` gives actual rows and time per step; the optimizer trace shows the alternatives (table scan cost **101,940** vs index range **3,719**). **MongoDB:** the slow query log said `planSummary: EXPRESS_IXSCAN { _id: 1 }` for a query that examined **2,000,225** documents: the cost was inside `$lookup`, visible only in its explain stage (`collectionScans: 1`, `indexesUsed: []`).
</Tldr>

## What each tool shows

| Tool | Shows | Cost to run |
|---|---|---|
| `EXPLAIN` (all engines) | The plan the optimizer would choose now, with estimates | None |
| `EXPLAIN ANALYZE` / `executionStats` | Plan + actual rows, loops, time, pages or keys | Runs the statement |
| PostgreSQL `auto_explain` | The plan of statements over a duration, logged as they run | Small; large if `log_analyze` with timing is on |
| MySQL optimizer trace | Every access path the optimizer costed and why it chose one | Per session, for one statement |
| MongoDB slow query log / profiler | Per operation: planSummary, keys and docs examined, duration | Proportional to what is logged |

| Term | Meaning |
|---|---|
| Plan regression | Same statement, worse plan or same plan reading more, after data, statistics or settings changed |
| BRIN summarization | Recording min/max for a 128-page range; unsummarized ranges always match, so they are always read (Session 7) |
| **✓ Captured / ✗ Missed** | The plan that ran is in the log, or the statement stayed under the threshold |

## PostgreSQL: auto_explain

`auto_explain` must be loaded (`shared_preload_libraries`, or `LOAD 'auto_explain'` in a session). Its settings can be set per session by a superuser, or for a database or role with `ALTER DATABASE … SET` / `ALTER ROLE … SET`.

## MySQL: EXPLAIN ANALYZE and the optimizer trace

MySQL has no built-in equivalent of `auto_explain`; the slow query log records the statement and its counters, not the plan. Capture the statement from the digest table or slow log, then run `EXPLAIN ANALYZE` and, when the choice itself is in question, the optimizer trace.

<Pitfall>
A plan you get by pasting a statement into `EXPLAIN` can differ from what production ran: different parameter values (selectivity), a generic prepared-statement plan, a cold cache, different session settings, or statistics that changed since. Capture plans where they run (`auto_explain`, profiler) and compare **counters** (pages, rows, docs examined), not only the shape: the BRIN regression kept the same shape and read 3× the pages.
</Pitfall>

## Real-world scenario: "it was fast yesterday"

| Symptom | Capture | Typical cause |
|---|---|---|
| Same statement, new plan | `auto_explain` before/after, profiler `planSummary` | Statistics changed, a new index, a parameter value with a different selectivity |
| Same plan, more pages | Buffers per call over time (`pg_stat_statements`), docs/keys examined | Unsummarized BRIN ranges, bloat, lost visibility-map bits (Session 5) |
| Summary looks fine, counters do not | Slow log fields | Cost inside a sub-stage (`$lookup`, subquery, trigger) |

## Key takeaways

1. `auto_explain` logs the real plan of slow statements; keep `log_timing` off and sample on busy servers.
2. Thresholds hide frequent fast statements; rank first (Concept 1), then capture.
3. Compare counters, not only plan shapes: the BRIN report read 1,161 pages instead of 384 with an identical plan.
4. MySQL: `EXPLAIN ANALYZE` for what ran, the optimizer trace for what was considered.
5. MongoDB: `planSummary` describes the first stage; check docs/keys examined and explain each stage.
