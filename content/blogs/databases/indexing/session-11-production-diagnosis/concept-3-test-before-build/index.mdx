<Tldr>
A candidate index has two questions: **will the planner use it** for the target query, and **what does it cost** on every write. **PostgreSQL:** the `hypopg` extension creates a hypothetical index visible only to `EXPLAIN` in your session: the order-detail plan's estimated cost fell from **28,190** to **16.55**, in milliseconds, with nothing built. It cannot run the query (`EXPLAIN ANALYZE` ignores it), and its size estimate was **56 MB** for an index that turned out to be **39 MB**. **MySQL:** no hypothetical indexes, but an **invisible** index plus `SET SESSION optimizer_switch = 'use_invisible_indexes=on'` lets one session test it: 211 ms table scan elsewhere, 0.01 ms lookup in that session. It is fully built and maintained, though. **MongoDB:** neither; a hidden index cannot even be hinted (`BadValue`). Test on a copy, then compare with `hideIndex()` / `unhideIndex()` (273 ms vs 0 ms). The write side, measured with `pg_stat_statements.wal_bytes`: the `order_items (order_id)` index added a steady **137 bytes** of WAL per checkout; `(customer_id, created_at)` cost nothing extra at first, then up to **+250 bytes** per order while its pages, built 90% full, were splitting, then little again once its leaves had settled at **54%** density, and the index had grown from 30 MB to 72 MB.
</Tldr>

| Engine | Plan with an index that does not exist | Plan with an index others cannot see | Quick on/off for an existing index |
|---|---|---|---|
| PostgreSQL | ✓ `hypopg` (extension) | — | — (no invisible indexes; Session 8) |
| MySQL | — | ✓ invisible + `use_invisible_indexes=on` in one session | ✓ `ALTER INDEX … INVISIBLE / VISIBLE` |
| MongoDB | — | — | ✓ `hideIndex()` / `unhideIndex()` (not hintable while hidden) |

| Term | Meaning |
|---|---|
| Hypothetical index | Catalog entry that exists only in your session's memory; the planner costs it, nothing is built |
| Invisible / hidden index | Built and maintained on every write, ignored by the optimizer (unless a session opts in, MySQL) |
| `wal_bytes` | Bytes of WAL generated per statement, in `pg_stat_statements` (PostgreSQL 13+) |
| **✓ Planner would use it / ✗ Not tested by this** | What the method answers, and what it cannot |

## The other half: write cost

Every method above answers "would reads improve". The write side has to be measured with the writes. `pg_stat_statements.wal_bytes` gives WAL per statement; the checkout script (one order, two items) was run 20,000 times per measurement, with each index set.

| Indexes on the written tables | `order_items` insert (2 rows) | `orders` insert | Notes |
|---|---|---|---|
| Before: `orders` pkey, `(customer_id)`, `(status, created_at)`; `order_items` pkey | 326 B in every run | 333–343 B | `(customer_id)` has ≈ 10 entries per key: when a leaf fills, deduplication merges them into posting lists instead of splitting (Session 2) |
| After, right after building: `orders` pkey, `(customer_id, created_at)`, `(status, created_at)`, BRIN; `order_items` pkey, `(order_id)` | 463 B in every run | 340–378 B | New index pages built 90% full still have room |
| After, while `(customer_id, created_at)` splits (≈ 60,000–200,000 inserts after the build) | 463 B | 415–593 B | Each order lands in a random place in the index (one customer of 100,000); full leaves split, and splits are logged |
| After, settled | 463 B | 338–353 B | Leaves at 54% density: 2–4 splits per 20,000 inserts; the index has grown from 30 MB to 72 MB |

`order_items (order_id)` adds a steady **137 bytes** per checkout: `order_id` grows with every order, so its entries go to the rightmost leaf, as with an increasing primary key (Session 2); its leaves stayed at 90% density. `(customer_id, created_at)` costs little per insert once settled, but it paid with **a burst of page splits** and **2.4× its size**, as random-insert B-trees do (Session 2, Concept 6). The BRIN index made no measurable difference in either direction (dropping it did not change the `orders` numbers). Runs that included a checkpoint showed thousands of full-page images and were not compared.

<Pitfall>
A hypothetical or invisible index answers only the **read** question, and only in **estimated** (hypopg) or **single-session** (MySQL) form. It says nothing about the WAL, page splits, replication lag, buffer-pool pressure or build time the real index brings, and a single benchmark right after building measures none of it correctly: the same index cost almost nothing, then up to +250 bytes per insert, then almost nothing again, over ≈ 300,000 inserts. Measure on a copy with production-like writes, for long enough to see the steady state.
</Pitfall>

## Real-world scenario: "can we add this index?"

| Question | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Will the planner use it? | `hypopg` + `EXPLAIN` | Invisible + session switch | Test copy |
| How much faster? | Build on a copy, `EXPLAIN (ANALYZE, BUFFERS)` | `EXPLAIN ANALYZE` in the switched session | explain on the copy |
| What does it cost on writes? | `wal_bytes` per statement over time; `pgstatindex` density | Redo bytes (`Innodb_os_log_written`) per workload | Oplog and insert latency on the copy |
| How do we roll back? | `DROP INDEX CONCURRENTLY` | `INVISIBLE`, then drop | `hideIndex`, then drop |

## Key takeaways

1. `hypopg` plans with an index that does not exist: the plan and estimated cost, not real pages or size.
2. MySQL invisible indexes can be tested by one session (`use_invisible_indexes=on`) while others ignore them, but they are fully built and maintained.
3. MongoDB has no hypothetical indexes and hidden indexes cannot be hinted: test on a copy, compare with hide/unhide.
4. Write cost depends on the key pattern: an increasing key cost a steady 137 bytes per checkout; a random key cost a burst of splits and 2.4× its size.
5. Measure the write side over time, not in one run right after the build.

7. Why is one benchmark right after building an index not enough to know its write cost?
