<Tldr>
This session is the course in one exercise. A small shop runs **8 query shapes** against `orders` (1M), `customers` (100k) and `order_items` (2M), the tables from [Session 9](/blogs/databases/indexing/session-9-indexes-for-joins/lab). Step one is finding which statements cost the most **in total**. In a 60-second PostgreSQL run, `pg_stat_statements` put the **order-detail query** (39 ms mean, nothing alarming) at **69%** of database time: 3,990 calls, each reading **16,707 buffers**, which is all of `order_items`, to return 2 rows. The **login by email** (4.6 ms) was second at 12%, reading the whole 854-page `customers` table every time. Ranked by mean time instead, the list starts with a weekly report that is only 10% of the load. MySQL's digest table and MongoDB's profiler show the same picture, with their own traps: counters that accumulate since server start, a `sys` view that sorts latencies as **text**, and `$queryStats`, which returned **0 documents** on a self-managed 8.0 server.
</Tldr>

## The workload

The same 8 statements run in all three engines, with these weights (pgbench for PostgreSQL, a generated script for MySQL, a seeded loop for MongoDB; [lab](/blogs/databases/indexing/session-11-production-diagnosis/lab)):

| # | Query | Share of calls | Session that covers its index |
|---|---|---|---|
| Q1 | Login: customer by `email` | 30% | 2 (point lookup), 5 (unique) |
| Q2 | Order history: a customer's newest 20 orders | 25% | 4 (equality + ORDER BY + LIMIT) |
| Q3 | Order detail: one order joined to its items | 20% | 9 (joins) |
| Q4 | Admin search: pending orders of one day, newest 50 | 4% | 4 (equality before range) |
| Q5 | Daily revenue for one week | 1% | 7 (BRIN), 5 (covering) |
| Q6 | Top 10 SKUs of one week | 1% | 9 (joins), 10 (aggregation) |
| Q7 | Latest order of each gold customer in one country | 2% | 9 (lateral join), 10 (top-N per group) |
| Q8 | Checkout: insert one order and two items | 17% | 8 (write cost) |

Starting indexes: primary keys, `orders (customer_id)` and `orders (status, created_at)`. Nothing on `customers.email` or `order_items.order_id` (the lab removes the indexes the Session 9 lab added, to start from this state).

| Term | Meaning |
|---|---|
| Normalized statement | Constants replaced by placeholders (`$1`, `?`), so all executions of one query shape share one row: `queryid` (PostgreSQL), digest (MySQL), `queryHash` / query shape (MongoDB) |
| Total time | Calls × mean time: the database time that query shape consumed |
| Per-call evidence | Buffers (PostgreSQL), rows examined (MySQL), docs/keys examined (MongoDB) per call, compared with rows returned |
| Snapshot diff | Copy the counters before a period, subtract afterwards: measures that period only |
| **✓ Ranked by total / ✗ Ranked by mean** | Finds what the server spends its time on, or what looks slow once |

## PostgreSQL: pg_stat_statements

`pg_stat_statements` must be listed in `shared_preload_libraries` (server restart), then `CREATE EXTENSION pg_stat_statements` in the database you query it from.

## MongoDB: the profiler, grouped by query shape

The profiler writes operations of one database into its `system.profile` collection: level 1 records operations slower than `slowms`, level 2 records all. The default `system.profile` is a 1 MB capped collection; create a bigger one before a measurement. `slowms`, `sampleRate` and `filter` apply to the whole `mongod`, while the level is per database.

<Pitfall>
Rank by **total** time over a **known period**. Mean time favours rare reports; cumulative counters mix last month with today and include one-off migrations; a threshold-based log (`log_min_duration_statement`, MySQL's slow log, `slowms`) never shows the 4.6 ms login that cost more than the 121 ms report. Measure a window: reset your own counters or snapshot and subtract.
</Pitfall>

## Real-world scenario: "the database is slow"

| Step | Tool | Finding in the lab |
|---|---|---|
| Which statements? | `pg_stat_statements` / digest diff / profiler | One join (order detail) is two thirds of the load |
| Why that one? | Buffers or rows examined per call | It reads all of `order_items` to return 2 rows |
| Second? | Same list | The login reads all of `customers` to return 1 |
| What to ignore for now? | Share of total | The weekly reports: slow per call, 15% together |

## Key takeaways

1. Rank by total time (calls × mean): in the lab a 39 ms query was 69% of database time and a 4.6 ms one 12%.
2. Per-call evidence (buffers, rows or docs examined vs returned) shows why a statement is expensive.
3. Measure a window: reset your own database's counters (PostgreSQL), snapshot and subtract (MySQL), profile a period (MongoDB).
4. `sys.statement_analysis` sorts formatted text; use `sys.x$statement_analysis` for ordering.
5. `$queryStats` collected nothing on a self-managed 8.0 server; the profiler and slow query log are the tools there.
