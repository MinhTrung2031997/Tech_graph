<Tldr>
The workload from Concept 1 (login, order history, order detail, admin search, two weekly reports, a CRM query, checkout), measured, fixed and measured again. **PostgreSQL**, 60 s runs with 4 clients: **336 tps** at the start; **3,333** after iteration 1 (four indexes from the top of `pg_stat_statements`, one redundant index dropped); **5,038** after iteration 2 (a cost-model setting, not an index, fixed the top-SKU report, and a BRIN regression was caught); **5,944** after iteration 3 (one 704 kB index). Database time per transaction fell from **11.3 ms to 0.37 ms**. The price: 5 → 9 indexes on the three tables, ≈ 110 → 175 MB, and a steady **+137 bytes of WAL** per checkout, plus a burst of page splits that grew one new index from 30 to 72 MB (Concept 3). **MySQL** (same design, a B-tree where PostgreSQL used BRIN): 21.9 s → 0.55 s for the same 500 statements. **MongoDB**: 45.5 s → 0.87 s, three report timeouts → none. What remained on top in PostgreSQL were the two weekly reports, **81%** of database time at 2% of calls: the point to stop adding indexes and change how reports are produced.
</Tldr>

## The loop

| Step | Tool | Course session |
|---|---|---|
| 1. Measure a window | pgbench + `pg_stat_statements` / digest diff / profiler | 11 (Concept 1) |
| 2. Rank by total time, read per-call evidence | Buffers, rows, docs examined | 3, 11 |
| 3. Capture the plan | `EXPLAIN (ANALYZE, BUFFERS)`, `auto_explain`, explain stages | 3, 11 (Concept 2) |
| 4. Design | Checklist: operator → type, equality → sort → range, covering, write cost | 2, 4, 5, 7, 8 |
| 5. Test | `hypopg`, invisible index, copy | 11 (Concept 3) |
| 6. Build online, verify, re-measure | `CONCURRENTLY`, `ALGORITHM=INPLACE, LOCK=NONE`, rolling builds | 8 |

| Term | Meaning |
|---|---|
| Iteration | One pass of measure → rank → fix → re-measure; the ranking changes after every fix |
| Database time per transaction | Sum of `total_exec_time` over all statements / transactions: how much server time one unit of work costs |
| **✓ Fixed by an index / ✗ Not an index problem** | Per-call reads fell to what the result needs, or the remaining cost is inherent to the query |

## Final index sets

| Query | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Q1 login | `UNIQUE (email)` 3.9 MB | `UNIQUE (email)` 3.5 MB | `{ email: 1 }` unique, 2.4 MB |
| Q2, Q7 per customer | `(customer_id, created_at)` 30 MB, replaces `(customer_id)` | `(customer_id, created_at)` 25.6 MB, replaces `(customer_id)` | `{ customer_id: 1, created_at: -1 }` 13.8 MB, replaces `{ customer_id: 1 }` |
| Q3, Q6 joins | `order_items (order_id)` 39 MB | `order_items (order_id)` 47.6 MB | `{ order_id: 1 }` 14.4 MB |
| Q4 admin | `(status, created_at)` (existing) | `(status, created_at)` (existing) | `{ status: 1, created_at: -1 }` (existing) |
| Q5, Q6 date ranges | BRIN `(created_at)` 24 kB, autosummarize | `(created_at, amount)` 26.6 MB | `{ created_at: 1, amount: 1 }` 23.8 MB |
| Q7 CRM filter | `(country, tier)` 704 kB | `(country, tier)` 2.5 MB | `{ country: 1, tier: 1 }` 0.6 MB |
| Not an index | `random_page_cost = 1.1` for the database; reports → summary table | Reports → summary table; COMMIT cost is the redo flush | Reports → `$merge` into a daily summary collection |

Sizes as built (PostgreSQL) or right after the runs (MySQL, MongoDB).

<Pitfall>
Every fix changes the ranking, so re-measure after each one: the top-SKU report went from 10% to 69% of database time without getting slower, because everything around it got faster. And know when to stop: once the top statements read about what their result needs (a week of orders for a weekly report), further indexes add write cost without removing work. Change what the query has to do instead.
</Pitfall>

## Real-world scenario: presenting the result

| Slide | Content from this case |
|---|---|
| Problem | 336 tps; one join and one login lookup were 81% of database time |
| Change | 4 indexes added, 1 replaced, 1 per-database setting; all built online |
| Result | 5,944 tps; database time per transaction 11.3 → 0.37 ms |
| Cost | ≈ +65 MB of indexes when built (more as random-key indexes split), +137 B of WAL per checkout |

## Why this matters for indexes

| Course part | Where it showed up here |
|---|---|
| Sessions 1–3: pages, B-trees, the planner | Buffers per call as evidence; `random_page_cost`; page splits |
| Sessions 4–5: column order, covering, unique | `(customer_id, created_at)`, `UNIQUE (email)`, `(created_at, amount)` |
| Sessions 6–7: engines, BRIN | B-tree vs BRIN for the same reports; `$lookup` |
| Session 8: when indexes hurt | Redundant index dropped, WAL measured, online builds |
| Sessions 9–10: joins, aggregation | Join-column indexes, lateral top-1, covered `$group` |

## Key takeaways

1. Iterate: measure a window, rank by total time, fix the top, re-measure; the ranking changes every time.
2. In the lab, four indexes plus one replacement took PostgreSQL from 336 to 3,333 tps; the next 78% came from a cost setting and one small index.
3. An index that exists is not an index that is used: the top-SKU report needed `random_page_cost` before it used `order_items (order_id)`.
4. Engine differences change the design: BRIN (24 kB) in PostgreSQL vs a covering B-tree (≈ 24–27 MB) in MySQL and MongoDB.
5. Stop when the top statements read what their result requires; then change the work (summaries, replicas), not the indexes.

## Check questions
