<Tldr>
In a nested loop, the inner side runs **once per outer row**, so its cost is multiplied: **outer rows × (one index descent + the rows fetched behind it)**. In PostgreSQL that product decides the plan: up to 300 customers the nested loop wins (3,895 buffers), from 1,000 customers a hash join reading all of `orders` once is cheaper (≈ 10,300 buffers, whatever the count). Within the nested loop, the index design decides the multiplier. For "paid orders of SG gold customers" (513 customers), an index on `(customer_id)` alone costs **13 buffers per customer** and discards 7 of every 10 rows it fetches; **`(customer_id, status)`** puts both conditions into the descent (**6.5 per customer**, 3,691 buffers in total); adding the returned columns with `INCLUDE` makes it an index-only lookup (**3 per customer**, 1,927 buffers). MySQL shows the same steps in its handler counters (5,643 → 2,393 index reads), and MongoDB's `$lookup` with a `pipeline` filter needs the same compound index starting with the `foreignField` (5,130 → 1,880 keys, 0 documents when covered).
</Tldr>

## The multiplier

| Term | Meaning |
|---|---|
| Outer rows | Rows coming out of the driving side, after its own filters |
| Inner lookup | One execution of the inner side for one outer row: `loops=N` in PostgreSQL, `loops=N` in MySQL's EXPLAIN ANALYZE |
| Per-loop cost | Buffers (or keys and documents) read by one inner lookup: the descent plus the fetches |
| Join key + filter index | A composite index on the inner table: the join column first, then the inner filter columns (Session 4: equality columns together) |
| **✓ Narrow lookup** | Each descent lands only on rows that match both the join and the inner filter |
| **✗ Wide lookup** | Each descent fetches every row for the join key, then discards most of them |

Nested loop cost ≈ **outer rows × per-loop cost**. You can cut it in two ways: fewer outer rows (a better filter or index on the outer side, Concept 4) or a cheaper per-loop lookup (this concept).

## PostgreSQL: where nested loop stops paying

Same join, growing number of customers (`WHERE c.id <= N`), with only `orders_customer_idx` on the inner side:

| Customers (N) | Plan chosen | Buffers | Time |
|---|---|---|---|
| 1 | Nested Loop, bitmap scan of orders_customer_idx | 18 | 0.2 ms |
| 10 | Nested Loop | 136 | 1.1 ms |
| 100 | Nested Loop, Index Scan orders_customer_idx | 1,313 | 7 ms |
| 300 | Nested Loop | 3,895 | 16 ms |
| 1,000 | **Hash Join**, Seq Scan orders | 10,344 | 27 ms |
| 3,000 | Hash Join | 10,410 | 24 ms |
| 10,000 | Hash Join | 10,318 | 66 ms |
| 100,000 | Hash Join, Seq Scan customers too | 11,060 | 128 ms |

The nested loop costs ≈ 13 buffers per customer (one descent of ≈ 3 pages plus ≈ 10 heap pages for 10 orders); the hash join costs one pass over `orders` (10,205 pages) plus the customers. Forcing each plan at the boundary (`enable_hashjoin`, `enable_nestloop`):

| Customers | Nested loop forced | Hash join forced |
|---|---|---|
| 300 | 3,895 buffers, cost 12,184 | 10,320 buffers, cost 16,771 |
| 1,000 | 12,963 buffers, cost 31,172 | 10,344 buffers, cost 17,473 |
| 10,000 | 130,354 buffers, cost 53,105, ≈ 54 ms | 10,318 buffers, cost 23,336, ≈ 63 ms |

The planner switches where the buffer counts cross. The last row is the honest exception: with every page already in memory, 130,354 buffer hits were not slower than the hash join. The cost model prices random reads for disk (Session 3), so it protects you from the case where those pages are not cached.

## MySQL: the same steps in handler counters

MySQL always used the index nested loop here, at every size: 100 customers ≈ 6 ms, 1,000 ≈ 35 ms, 10,000 ≈ 0.25 s, 100,000 ≈ 2.9 s (Concept 1: it does not switch to a hash join while an index exists). So the inner index design is the only lever. `Handler_read_key` counts descents, `Handler_read_next` counts entries read after each descent, `Handler_read_rnd_next` counts rows read by table scans.

## MongoDB: $lookup with a filter on the foreign side

A `$lookup` can combine `localField` / `foreignField` with a `pipeline` that filters the foreign documents. MongoDB runs it as "equality on `foreignField`, plus the pipeline's `$match`" per outer document, so the best index is the same as in SQL: **`foreignField` first, then the filter fields** (equality fields in any order, Session 4), then the returned fields to cover.

Without a filter, the cost grows linearly with the outer documents and never switches strategy (the 1M-document `orders` collection is far above the HashJoin limit): 100 customers 1,100 keys ≈ 2 ms, 1,000 → 11,000 keys ≈ 14 ms, 10,000 → 110,000 keys ≈ 113 ms, 100,000 → 1,100,000 keys ≈ 1.1 s.

<Pitfall>
The inner index must start with the **join column**. An index on `(status, created_at)` serves "paid orders in June" on its own, but inside a nested loop it cannot be searched by `customer_id`, so each outer row would scan the whole paid-in-June range. Design inner indexes as join key first, then the inner filters, then (optionally) the returned columns, and check `loops=` and the per-loop buffers in the plan.
</Pitfall>

## Real-world scenario: the account page

An account page shows a customer's open orders with their items: `customers (1 row) → orders (open ones) → order_items`. Two nested loops, each with few outer rows.

| Inner side | Index | Per-loop cost |
|---|---|---|
| orders for the customer, `status IN ('pending', 'paid')`, newest first | `(customer_id, status, created_at)` | One descent per status value, rows already in date order |
| items of each order | `order_items (order_id)` | One descent, 2 rows |

Measured in PostgreSQL for customer 4242 (15 orders, 9 of them pending or paid): 57 buffers with `(customer_id)`, of which 6 orders were fetched and discarded; 51 buffers with `(customer_id, status, created_at)`; the 9 item lookups cost 36 of them. The gain is small for a customer with 15 orders and grows with the history: with `(customer_id)` alone the first loop fetches every order the customer ever placed. Without `order_items (order_id)`, each of the 9 orders would scan 2M items instead (Concept 1).

## Key takeaways

1. Nested loop cost ≈ outer rows × (descent + fetches); in PostgreSQL the hash join took over between 300 and 1,000 customers.
2. Put the inner filter into the inner index after the join key: 13 → 6.5 buffers per customer in PostgreSQL, 5,643 → 2,393 index reads in MySQL, 5,130 → 1,880 keys in MongoDB.
3. Cover the returned columns to skip the fetch: 3 buffers per customer, `Using index`, 0 documents examined.
4. MySQL never switches to a hash join while an index exists, so its inner index design matters at every size.
5. Covering indexes cost space and write time (47 MB here): add them for hot joins, not by default.
