<Tldr>
A join has an **outer** input and an **inner** input, and there are only three ways to combine them. A **nested loop** looks up the inner input once per outer row, so it needs an **index on the inner join column**: one customer and their orders cost **21 buffers**. A **hash join** reads both inputs once and matches them in a memory hash table, so it needs no index at all: all 100k customers joined to 1M orders cost **12,815 buffers**, about one sequential read of each table. A **merge join** walks two inputs that are already sorted on the join key, side by side: 200,000 orders joined to their 400,000 items through two indexes read **10,850 buffers**, against **23,691 buffers plus a 4.7 MB sort spilled to disk** for the hash join it replaced. PostgreSQL has all three. MySQL has nested loop and hash join, and only uses hash join when **no index** fits the join. MongoDB's `$lookup` runs as an indexed loop, a hash join (foreign collection ≤ 10,000 documents) or a plain nested loop that scans the foreign collection **once per outer document**: 10,000,005 documents examined to join 5 orders to their items.
</Tldr>

## Three algorithms

| Term | Meaning |
|---|---|
| Outer (driving) input | The side read first; for each of its rows the join looks for partners |
| Inner input | The side searched for partners of each outer row |
| Nested loop | For each outer row, search the inner input. With an index on the inner join column each search is one descent; without one it is a full scan per outer row |
| Hash join | Read the smaller input (the **build** side) into a hash table keyed on the join column, then read the other (the **probe** side) once and look each row up in the table |
| Merge join | Read both inputs sorted on the join key and advance them together, like merging two sorted lists |
| **✓ Index serves the join** | The inner side is reached by descents, so the cost grows with the outer row count, not the table size |
| **✗ No usable index** | The engine must hash, sort, or rescan the inner input |

| Algorithm | Needs | Cost grows with | Best when |
|---|---|---|---|
| Nested loop | An index on the inner join column (or a tiny inner input) | Outer rows × (descent + fetch) | Few outer rows |
| Hash join | Memory for the build side (`work_mem` in PostgreSQL, `join_buffer_size` in MySQL) | Size of both inputs, read once | Many rows on both sides, equality join |
| Merge join | Both inputs sorted on the key (from an index, or a Sort step) | Size of both inputs, read once in order | Both sides large and already ordered by indexes |

Session 3 explained how the planner prices each plan. Here the same cost model decides between join algorithms: a nested loop pays a random descent per outer row (`random_page_cost` = 4), a hash join pays a sequential read of each table (`seq_page_cost` = 1) plus CPU for hashing.

## MySQL: index nested loop, or hash join when no index fits

MySQL 8.4 has no merge join. Every join is a nested loop, and since 8.0.18 the old block nested loop (rescanning the inner table from a join buffer) is replaced by a **hash join**. The hash join is used **only when no index can serve the join condition**: as soon as an index exists, MySQL picks the index nested loop.

## MongoDB: $lookup and its three strategies

`$lookup` is MongoDB's join: for each document coming out of the earlier stages, find the documents in another collection whose `foreignField` equals the `localField`. When the slot-based engine (SBE) runs it, `explain` shows an `EQ_LOOKUP` stage with a `strategy`:

| Strategy | When | Cost |
|---|---|---|
| `IndexedLoopJoin` | An index on `foreignField` exists | One index descent per outer document |
| `HashJoin` | No index, and the foreign collection has ≤ 10,000 documents and ≤ 100 MB (`internalQueryCollectionMaxNoOfDocumentsToChooseHashJoin`, `…MaxDataSizeBytesToChooseHashJoin`) | Foreign collection read once into a hash table |
| `NestedLoopJoin` | No index, foreign collection too big to hash | **One collection scan per outer document** |

When a pipeline cannot run in SBE (for example a `$lookup` with its own `pipeline`, or followed by `$unwind`), the classic engine runs it. `explain` then has no `strategy`, but the `$lookup` stage still reports `indexesUsed`, `totalKeysExamined`, `totalDocsExamined` and `collectionScans`, which answer the same question.

<Pitfall>
"The join is slow, so add an index" is right for a nested loop and wrong for a hash join. When the query joins most of both tables (a report, a nightly aggregate), reading each table once is the cheapest plan, and in MySQL an index can even **remove** the hash join: the full-table aggregate took 1.3–2.0 s through `orders_customer_idx` and 0.24 s with the index hinted away. Check how many outer rows the join really has before reaching for an index.
</Pitfall>

## Real-world scenario: the order detail page vs the monthly report

| Query | Outer rows | Right algorithm | Index needed |
|---|---|---|---|
| Order detail page: one order and its items | 1 | Nested loop | `order_items (order_id)` |
| "My orders" page: one customer's last 20 orders with items | 20 | Nested loop | `orders (customer_id, created_at)` (Session 4), `order_items (order_id)` |
| Monthly revenue by country | All | Hash join (or merge join on sorted indexes) | None for the join; maybe one for the date filter |
| Nightly export of all orders with items | All | Merge join if both sides have indexes in key order; otherwise hash | Optional; avoids a large sort |

The same two tables need an index for the first two queries and are better off without one for the third.

## Why this matters for indexes

| Later topic | Why this concept matters |
|---|---|
| Concept 2: the inner index | Nested loop cost = outer rows × inner lookup; that lookup is what an index design controls |
| Concept 3: foreign keys | Every foreign-key check is a nested-loop lookup on the child table |
| Concept 4: join order | Which side is outer decides which index is used |
| Session 10: pagination and aggregation | GROUP BY after a join; merge join's sorted output saves a sort |

## Key takeaways

1. Nested loop: one inner lookup per outer row; it needs an index on the inner join column (21 buffers for one customer).
2. Hash join: both inputs read once, no index needed; best when many rows join (12,815 buffers for the full join).
3. Merge join: two inputs sorted on the key, advanced together; indexes on both sides remove every sort (10,850 vs 23,691 buffers + spill).
4. MySQL uses a hash join only when no index serves the join; for a full-table join that can make the index the slower plan.
5. MongoDB `$lookup`: IndexedLoopJoin with an index on `foreignField`, HashJoin for small collections, otherwise a full scan of the foreign collection per outer document.
