<Tldr>
With filters on both tables, the join should start from the side whose filter leaves **fewer rows**, and the other side needs an index on the join column. For "orders of SKU-000123 with their customers", starting from `orders` (200 rows through an index on `sku`) and looking up each customer by primary key cost **201 index descents and ≈ 1.2 ms** in MySQL; forcing it to start from `customers` cost **100,001 descents and 1,000,000 index reads, ≈ 2.5 s**, for the same 200 rows. SQL optimizers choose the order from **row estimates**, so estimate errors carry into the join: two correlated filters on customers made PostgreSQL estimate **242** customers instead of **5,000**, pick a nested loop, and read **64,584 buffers** instead of the **10,485** of a hash join. For "customers who have at least one paid order", `EXISTS` lets the engine stop at the first match: MySQL's semi-join with `(customer_id, status)` read **10,050** index entries instead of 360,050. MongoDB does not reorder: the pipeline starts at the collection you call `aggregate` on, so starting from the selective side is your job (**4 ms vs 2.7 s**), and grouping before a `$lookup` cut a 1M-document join to 100,000 lookups (**10.5 s → 1.4 s**).
</Tldr>

## Choosing the outer side

| Term | Meaning |
|---|---|
| Driving (outer) side | Read first; its row count is the number of inner lookups in a nested loop, or the size of the hash build side |
| Filter selectivity | Fraction of a table's rows that pass its own filters (Session 3) |
| Join order | Which table is outer at each step; SQL optimizers choose it, MongoDB pipelines fix it |
| Semi-join | "Rows of A that have **at least one** match in B" (`EXISTS`, `IN`): B's matches are not returned, so the search can stop at the first |
| **✓ Selective side drives** | Few outer rows, each with one cheap lookup into the other side's join index |
| **✗ Wrong side drives** | Many outer rows, most finding nothing that passes the other side's filter |

The general rule for a two-table join with a filter on each side:

| Filter that leaves fewer rows | Outer side | Index needed on the inner side |
|---|---|---|
| On `orders` (`sku = 'SKU-000123'`: 200 rows) | orders, via `orders (sku)` | `customers` primary key (exists) |
| On `customers` (`country = 'SG' AND tier = 'gold'`: 513 rows) | customers, via `customers (country, tier)` | `orders (customer_id, …)` (Concept 2) |
| On both, combined result small | The smaller one | The join column of the other |
| Neither selective | Either; a hash join reads both once | None |

## MongoDB: you choose the driving collection

A MongoDB semi-join ("customers with at least one paid order") is a `$lookup` whose pipeline ends in `{ $limit: 1 }`, followed by `{ $match: { "p.0": { $exists: true } } }`. For the 10,050 SG customers: 100,500 keys without the limit, 69,153 with it (customers with no paid order still read all their orders), **3,483** with `$limit: 1` and an index `{ customer_id: 1, status: 1 }`.

<Pitfall>
A query that is fast with one filter value can be slow with another, because the best driving side changes. "Orders of SKU-000123 by SG customers" should start from orders; "orders of any SKU by the 3 customers of a new market" should start from customers. SQL optimizers handle this with statistics (and get it wrong when estimates are wrong, as above); a MongoDB pipeline written for one case runs the same way for the other. Keep both join indexes, `orders (sku)` and `orders (customer_id)`, when both shapes are common.
</Pitfall>

## Real-world scenario: the marketplace search page

A seller dashboard lists orders filtered by seller and date, joined to customers for the buyer's country, optionally filtered by country.

| Filter combination | Selective side | Needed indexes |
|---|---|---|
| Seller + last 7 days | orders | `orders (seller_id, created_at)`, `customers` primary key |
| Seller + last 7 days + country = SG | orders (still) | the same; country checked per joined customer |
| Country = SG + tier = gold, all sellers | customers | `customers (country, tier)`, `orders (customer_id, created_at)` |

Run `EXPLAIN ANALYZE` for each combination the page allows, compare estimated and actual rows on the outer side, and make sure each combination has the index its driving side needs.

## Key takeaways

1. Start from the side whose filter leaves the fewest rows; give the other side an index on the join column.
2. Wrong order is expensive: 201 vs 100,001 descents in MySQL, 400 vs 1,000,000 keys in MongoDB, for the same 200 rows.
3. SQL optimizers choose the order from estimates; correlated filters (242 estimated vs 5,000 actual) can flip the algorithm.
4. `EXISTS` stops at the first match; with an index on (join key, filter) MySQL's FirstMatch read 10,050 entries instead of 360,050.
5. MongoDB runs the pipeline as written: choose the starting collection, filter early, and group before `$lookup` when the result is aggregated.
