<Tldr>
A foreign key `order_items.order_id → orders.id` is enforced in **both directions**. Inserting an item looks up its parent through `orders`' primary key, which always exists. Deleting an order (or changing its `id`) must find the **children**, which is a lookup on `order_items.order_id`, and **PostgreSQL does not create that index**. In the lab, deleting 100 orders with `ON DELETE CASCADE` ran the foreign-key trigger 100 times, and each run was a full scan of the 2M-row `order_items`: **5.5 seconds** and ≈ 200 million rows read. After `CREATE INDEX ON order_items (order_id)`: **2 ms**. MySQL InnoDB **requires** an index on the child column, creates one if none exists, and refuses to drop it (`ERROR 1553`). MongoDB has no foreign keys; an application-level cascade `deleteMany({ order_id: { $in: … } })` scanned **2,000,000 documents** without the index and **200** with it. Separately, a child insert **locks the parent row** until it commits: `FOR KEY SHARE` in PostgreSQL (non-key updates of the parent still run), a shared record lock in InnoDB (any update of the parent waits).
</Tldr>

## Two directions of checking

| Term | Meaning |
|---|---|
| Parent / referenced table | `orders`; the referenced column must have a primary key or unique index |
| Child / referencing table | `order_items`; `order_id` is the foreign key column |
| Child-side check | On INSERT or UPDATE of a child row: "does the parent exist?" A lookup on the parent's primary key |
| Parent-side check | On DELETE of a parent row, or UPDATE of its key: "do children exist?" (and with `ON DELETE CASCADE`, delete them). A lookup on the **child column** |
| RI trigger | PostgreSQL's referential-integrity triggers that run these checks; `EXPLAIN ANALYZE` shows them as `Trigger for constraint …: time=… calls=…` |
| **✓ Child column indexed** | Each parent-side check is one index descent |
| **✗ Not indexed** | Each parent-side check scans the whole child table |

| Engine | Parent key index | Child column index |
|---|---|---|
| PostgreSQL | Required (primary key or unique) | **Not created**; your job |
| MySQL InnoDB | Required | **Created automatically** if no index starts with the column; cannot be dropped while the FK exists |
| MongoDB | (no foreign keys) | Your job, for every lookup or cascade your application does |

## MongoDB: no foreign keys, same index

If items are always read and deleted with their order, MongoDB's other answer is to **embed** them in the order document: no second collection, no index, no cascade. Referencing (a separate collection plus an index) fits when items are queried on their own or grow without bound.

<Pitfall>
The cost of a missing child index does not show up in `SELECT` testing. Reads by `order_id` may be rare, and inserts are fine (they check the parent's primary key). It shows up when someone deletes or archives parents, often in a batch job, as one full scan of the child table **per deleted parent row**, while holding locks. In PostgreSQL, check every foreign key for a matching index (query below) before that job runs.
</Pitfall>

```sql
-- PostgreSQL: foreign keys whose referencing columns are not the leading columns of any index.
SELECT c.conrelid::regclass AS child_table, c.conname, a.attname AS fk_column
FROM pg_constraint c
JOIN pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = c.conkey[1]
WHERE c.contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i
    WHERE i.indrelid = c.conrelid
      AND i.indkey[0] = c.conkey[1]          -- the index starts with the FK column
  );
```

The query checks single-column foreign keys (the first key column); for a composite foreign key, the index must start with all its columns.

## Real-world scenario: the data-retention job

A retention job deletes orders older than two years, 50,000 per night, with `ON DELETE CASCADE` to `order_items`, `payments` and `shipments`. In development it was instant (small tables). In production, `payments.order_id` had no index: 50,000 trigger calls, each a full scan of `payments`. The job ran for hours, held row locks on the deleted orders, and kept a transaction open that stopped VACUUM. The fix was one `CREATE INDEX CONCURRENTLY` per child table, found with the query above.

## Key takeaways

1. Deleting or re-keying a parent row checks the child table by its foreign key column.
2. PostgreSQL does not index that column: 100 cascaded deletes took 5.5 s (100 full scans), 2 ms with the index.
3. MySQL InnoDB creates the index if none starts with the column, and refuses to drop it (ERROR 1553).
4. MongoDB has no foreign keys; application cascades need the same index (2,000,000 → 200 documents examined).
5. A child insert locks its parent row until commit: `FOR KEY SHARE` in PostgreSQL (non-key updates still run), a shared record lock in InnoDB (any update waits).
