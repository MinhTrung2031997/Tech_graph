<Tldr>
Every session so far showed what an index saves on reads. This one shows what it costs on writes. Inserting 200,000 rows into the same table with **0, 2, 5 and 8** secondary indexes took **305 → 526 → 1,013 → 1,486 ms** in PostgreSQL and generated **39 → 164 MB of WAL**; MySQL **630 → 1,942 ms** with **45 → 99 MB** of redo; MongoDB **574 → 1,493 ms**. Each index adds a B-tree insert (often into a random leaf), log records, dirty pages to flush and replicate. Updates add more: in PostgreSQL a non-HOT update writes to **every** index (Session 6). The rule: every index must pay for itself in reads.
</Tldr>

## Measured: inserts vs number of indexes

Table with 8 extra columns, 200,000 rows inserted in one statement, indexes on 0, 2, 5 or 8 of the columns (plus the primary key):

| Secondary indexes | PostgreSQL time | WAL | Index size | MySQL time | Redo | MongoDB time |
|---|---|---|---|---|---|---|
| 0 | 305 ms | 39 MB | 4.4 MB | 630 ms | 45 MB | 574 ms |
| 2 | 526 ms | 67 MB | 14 MB | 920 ms | 57 MB | 729 ms |
| 5 | 1,013 ms | 121 MB | 35 MB | 1,487 ms | 84 MB | 1,139 ms |
| 8 | 1,486 ms (4.9×) | 164 MB (4.2×) | 47 MB | 1,942 ms (3.1×) | 99 MB (2.2×) | 1,493 ms (2.6×) |

| Term | Meaning |
|---|---|
| Write amplification | Bytes and operations the database writes per logical change; each index multiplies it |
| WAL / redo | The log every change is written to first (PostgreSQL WAL, InnoDB redo, WiredTiger journal); also what replicas replay |
| Full-page write | PostgreSQL logs a whole 8 KB page the first time it changes after a checkpoint; random index inserts touch many pages, so many full-page writes |
| **✓ Index pays for itself / ✗ Pure cost** | Reads it speeds up outweigh the writes it adds, or not |

## Updates multiply it further

| Engine | Update of a column with no index | Update of an indexed column |
|---|---|---|
| PostgreSQL | 0 index writes if HOT; **every** index if not (Session 6) | **Every** index |
| InnoDB | 0 | That index: delete-mark + insert |
| MongoDB | 0 | That index: remove + insert |

So in PostgreSQL the cost of an index is paid by updates of **other** columns too, whenever the update cannot be HOT.

<Pitfall>
Benchmarks of read queries never show write amplification. Before adding an index to a write-heavy table, measure insert and update throughput, WAL or redo volume, and replication lag with and without it, under realistic concurrency.
</Pitfall>

## Real-world scenario: the ingestion table with nine indexes

An events table ingests 20,000 rows/s. Over two years it collected nine indexes, one per dashboard filter. Ingestion lags, replicas fall behind, and the WAL archive fills disks.

| Step | Effect |
|---|---|
| List index usage (Concept 2) | 4 indexes never used since the last stats reset weeks ago |
| Drop them | Insert time and WAL roughly halved (lab: 8 → 5 indexes ≈ −32% time) |
| Replace 3 single-column indexes with 1 composite | Same queries served, fewer writes |
| Move rare reports to a replica or warehouse | Their indexes live only there |

## Key takeaways

1. Every index adds a B-tree insert per row on every insert, plus log records and dirty pages.
2. Lab, 200,000 inserts with 0 → 8 secondary indexes: PostgreSQL 4.9× slower and 4.2× WAL; MySQL 3.1× and 2.2× redo; MongoDB 2.6×.
3. Random-key indexes cost more than sequential ones (more pages touched, more full-page writes, more splits).
4. Replicas, backups and checkpoints all pay for the extra log volume.
5. In PostgreSQL, non-HOT updates write to every index, even for unrelated columns.
6. An index must save more on reads than it costs on writes.
