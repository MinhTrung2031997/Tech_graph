<Tldr>
After seven sessions of experiments, the lab's `orders` table has **12 indexes**. `pg_stat_user_indexes` shows one used **300,048** times and one never (`orders_pending_created`, 4.4 MB), with most of the rest used once or twice, by the lab exercises themselves. Every unused index still costs every insert (Concept 1). **Bloat** is the other waste: `orders_status_created_idx` had drifted to **86% leaf density** after updates, and `REINDEX CONCURRENTLY` rebuilt it to **90%** online in 0.4 s. The trap: usage counters **reset** (PostgreSQL on stats reset, MySQL and MongoDB at every restart), so "unused" only means "unused since". Drop safely: make the index **invisible** (MySQL) or **hidden** (MongoDB) first, watch, then drop.
</Tldr>

## Two kinds of waste

| Waste | Symptom | Measure | Fix |
|---|---|---|---|
| Unused index | Never chosen by any plan | PostgreSQL `idx_scan`; MySQL `sys.schema_unused_indexes`; MongoDB `$indexStats.accesses.ops` | Drop (after a hiding period) |
| Redundant index | A leftmost prefix of another index (Session 4) | MySQL `sys.schema_redundant_indexes`; compare definitions | Drop the shorter one |
| Bloated index | Low leaf density, many empty or dead entries | `pgstatindex()` `avg_leaf_density`, size vs a fresh build | `REINDEX CONCURRENTLY` (PostgreSQL), `OPTIMIZE TABLE` / rebuild (InnoDB), `compact` (MongoDB) |

Lab, PostgreSQL `orders` after Sessions 1–7:

| Index | `idx_scan` | Size |
|---|---|---|
| `orders_customer_idx` | 300,048 | 9 MB |
| `orders_cust_created_incl` | 13 | 39 MB |
| `orders_pkey` | 10 | 21 MB |
| `orders_status_created_idx` | 8 | 35 MB |
| `orders_sku_trgm` | 2 | 18 MB |
| `orders_pending_created` | **0** | 4.4 MB |
| … 6 more | 1–3 each | 24 kB – 30 MB |

| Term | Meaning |
|---|---|
| `idx_scan` | Number of index scans started on that index since the last statistics reset |
| Leaf density | `pgstatindex().avg_leaf_density`: fresh B-trees ≈ 90% (fill factor), random inserts ≈ 66% |
| Invisible / hidden index | Maintained on writes but ignored by the planner; reversible test before dropping |
| **✓ Earns its keep / ✗ Waste** | Used by important queries, or not |

PostgreSQL has no invisible indexes. To see a plan without an index, you can `BEGIN; DROP INDEX …; EXPLAIN …; ROLLBACK;`, but `DROP INDEX` takes an exclusive lock on the **table** until the rollback: do it only on a test copy.

<Pitfall>
"0 scans" is not proof. Counters reset (restarts in MySQL and MongoDB, stats resets in PostgreSQL), are per server (replicas have their own), and miss rare-but-critical queries (month-end close, yearly audit). Hide first, wait through a full business cycle, then drop.
</Pitfall>

## Real-world scenario: the index audit

A team inherits a database with 60 indexes on 12 tables and slow writes.

| Step | Query / tool | Typical finding |
|---|---|---|
| Unused | `idx_scan = 0`, `$indexStats`, `sys.schema_unused_indexes` (after checking the counting period) | 15% of indexes never used |
| Redundant | Prefix duplicates (`(a)` next to `(a, b)`) | Several |
| Bloated | `pgstatindex` density < 60% on churned tables | A few large ones |
| Act | Hide / make invisible → wait → drop; `REINDEX CONCURRENTLY` the bloated ones | Faster writes, less WAL, smaller backups |

## Key takeaways

1. Unused and redundant indexes cost every write and save nothing.
2. PostgreSQL `idx_scan`, MySQL `sys.schema_unused_indexes`, MongoDB `$indexStats` show usage, since a reset point.
3. Check the counting period, replicas and rare jobs before trusting "unused".
4. `pgstatindex` density reveals bloat; `REINDEX CONCURRENTLY` rebuilds online (86% → 90% in 0.4 s in the lab).
5. Test removals reversibly: invisible indexes (MySQL), hidden indexes (MongoDB); PostgreSQL has no equivalent.
