<Tldr>
An index is a decision with a read side and a write side. The checklist: **(1)** start from the queries that cost the most in total, not from columns; **(2)** read their plans and measure pages or keys examined vs rows returned; **(3)** pick the index type from the operator (`=`/range/sort → B-tree, contains → GIN, overlaps → GiST, append-only time ranges → BRIN, substrings → trigram); **(4)** order columns **equality → sort → range**; **(5)** add covering columns, a partial predicate or an expression only when the query needs it; **(6)** check write cost and redundancy; **(7)** deploy online with a lock timeout; **(8)** verify the plan and keep auditing. Every step has appeared in this course; this page puts them in order.
</Tldr>

## The checklist

| # | Step | Question to answer | Session |
|---|---|---|---|
| 1 | Find the queries | Which statements cost the most **in total** (calls × time)? | 3, 6 |
| 2 | Read the plan | Full scan? Rows/keys examined ≫ returned? A Sort? Heap or document fetches? | 1, 3, 6 |
| 3 | Is an index the answer? | Selective enough? Small table? Would a rewrite (sargable condition) fix it? | 3 |
| 4 | Pick the type | Which operator: `=`, range, `ORDER BY`, contains, overlaps, `LIKE '%…%'`, time range on an append-only table? | 2, 7 |
| 5 | Order the columns | Equality columns, then sort columns, then one range column | 4 |
| 6 | Variants | Cover hot queries (`INCLUDE` / extra columns)? Partial for a fixed subset? Expression for a function? Unique for a rule? | 5 |
| 7 | Count the cost | Write amplification, HOT updates lost, redundant with an existing index? | 6, 8 |
| 8 | Deploy | `CONCURRENTLY` / online DDL, lock timeout, no long transactions | 8 |
| 9 | Verify | Plan uses it; pages/keys examined dropped; write latency and WAL acceptable | all |
| 10 | Audit | Unused, redundant, bloated indexes, periodically | 8 |

| Term | Meaning |
|---|---|
| Total time | Calls × mean time: a 2 ms query run 10 million times a day costs more than a 10 s report run once |
| **✓ Index justified / ✗ Not justified** | Reads saved outweigh writes added, or another fix is better |

## Worked example: a seller's order list

Query: "a seller's orders with a given status, amount above X, newest first, 50 per page".

| Step | Decision |
|---|---|
| Operators | `seller_id =`, `status =`, `amount >`, `ORDER BY created_at DESC LIMIT 50` |
| Type | B-tree |
| Order (ESR) | `seller_id`, `status` (equality) → `created_at` (sort) → `amount` (range) |
| Covering? | The list shows id, created_at, status, amount: cover it if the endpoint is hot |
| Partial? | If only `status = 'pending'` is ever listed, a partial index (PostgreSQL / MongoDB) is smaller |
| Pagination | Keyset on `(created_at, id)`, not OFFSET (Session 2) |
| Write cost | Replaces the old `(seller_id)` and `(status)` indexes → fewer indexes overall |
| Deploy | Online, with a lock timeout |

| Engine | Index |
|---|---|
| PostgreSQL | `CREATE INDEX CONCURRENTLY ON orders (seller_id, status, created_at DESC, amount) INCLUDE (id);` (the `id` is in every heap tuple but not in the index, so include it for index-only scans) |
| MySQL | `ALTER TABLE orders ADD INDEX (seller_id, status, created_at, amount), ALGORITHM=INPLACE, LOCK=NONE;` (`id` is already in every entry) |
| MongoDB | `db.orders.createIndex({ seller_id: 1, status: 1, created_at: -1, amount: 1 })`, projection with `_id: 0` or `_id` added to the index for covering |

<Pitfall>
The most common index mistakes in this course, in one list: indexing low-selectivity columns alone (Session 3); a function or type mismatch hiding the column (Session 3); range before equality or sort (Session 4); `SELECT *` defeating covering (Session 5); forgetting `_id: 0` (Session 5); random primary keys (Session 6); indexing every column of a write-heavy table (Session 8); plain `CREATE INDEX` on a busy table (Session 8).
</Pitfall>

## Real-world scenario: the quarterly index review

A team reviews indexes every quarter with one query per engine and a short meeting.

| Check | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Top queries by total time | `pg_stat_statements` | Statement digests | Profiler / Atlas Query Insights |
| Unused indexes (counting period known) | `pg_stat_user_indexes.idx_scan` | `sys.schema_unused_indexes` | `$indexStats` |
| Redundant indexes | Prefix comparison | `sys.schema_redundant_indexes` | Prefix comparison |
| Bloat | `pgstatindex` density | Table rebuild size estimates | `compact` candidates |
| Write health | WAL rate, HOT ratio | Redo rate, history list length | Oplog window, replication lag |

## Key takeaways

1. Start from queries ranked by total cost, not from columns.
2. Read the plan: pages or keys examined vs rows returned, sorts, fetches.
3. Choose the index type by operator, then order columns equality → sort → range.
4. Add covering, partial, expression or unique variants only for a concrete need.
5. Count the write cost and remove redundant indexes when adding new ones.
6. Deploy online with lock timeouts; verify with the same measurements you started from.
7. Audit regularly: unused, redundant, bloated.
