<Tldr>
Creating an index on a live table is an operational event. In PostgreSQL, a plain `CREATE INDEX` holds a **ShareLock** for the whole build: in the lab an INSERT sat **waiting** (`wait_event: relation`) until the build's transaction ended. `CREATE INDEX CONCURRENTLY` takes a weaker **ShareUpdateExclusiveLock**: an INSERT during the build went through in 87 ms. It is slower, must wait for older transactions ("waiting for old snapshots"), and if it fails (a duplicate in a unique build) it leaves an **INVALID** index that still costs writes. MySQL's online DDL lets writes continue, but needs a brief **metadata lock**: behind a long transaction the ALTER waited, and a plain SELECT queued behind the ALTER. MongoDB's hybrid builds took a 10 ms insert in their stride.
</Tldr>

## Lock modes that matter

| Operation | PostgreSQL lock on the table | Blocks |
|---|---|---|
| `SELECT` | AccessShare | Only ACCESS EXCLUSIVE |
| `INSERT` / `UPDATE` / `DELETE` | RowExclusive | Share and stronger |
| `CREATE INDEX` | **Share** | All writes, for the whole build |
| `CREATE INDEX CONCURRENTLY` | **ShareUpdateExclusive** | Other DDL and VACUUM; not reads or writes |
| `ALTER TABLE … ADD COLUMN`, `DROP INDEX` | AccessExclusive | Everything, including SELECT |

| Term | Meaning |
|---|---|
| Lock queue | A waiting lock request blocks every later request that conflicts with it, even ones compatible with the current holder |
| INVALID index | Left by a failed `CONCURRENTLY` build: not used by queries but maintained on writes |
| Metadata lock (MySQL) | Protects table definitions; DDL needs an exclusive one, at least briefly |
| `lock_timeout` | PostgreSQL setting that makes a statement give up instead of waiting indefinitely for a lock |
| **✓ Writes continue / ✗ Writes wait** | During the build |

<Pitfall>
Always set a lock timeout for DDL on production: `SET lock_timeout = '5s'` (PostgreSQL), `SET lock_wait_timeout = 5` (MySQL). A DDL statement that cannot get its lock quickly should fail and be retried, rather than sit in the lock queue blocking every query behind it.
</Pitfall>

## Real-world scenario: the 2 am index that took the site down

An engineer runs `CREATE INDEX ON orders (merchant_id)` on a 400 GB PostgreSQL table during low traffic. The build takes 25 minutes; all checkouts fail because order INSERTs wait on the ShareLock.

| Better plan | Why |
|---|---|
| `SET lock_timeout = '5s'; CREATE INDEX CONCURRENTLY …;` | Writes continue; gives up quickly if blocked |
| Kill idle-in-transaction sessions first | Otherwise CONCURRENTLY waits on old snapshots |
| Monitor `pg_stat_progress_create_index` | See the phase and progress |
| Afterwards: check `indisvalid` | Drop and retry if it failed |

## Key takeaways

1. PostgreSQL `CREATE INDEX` holds a ShareLock that blocks all writes for the whole build.
2. `CREATE INDEX CONCURRENTLY` allows writes (87 ms INSERT in the lab) but is slower, waits for older transactions, cannot run in a transaction block, and leaves an INVALID index if it fails.
3. MySQL online DDL allows writes but needs brief exclusive metadata locks; behind a long transaction, it queues every later query.
4. MongoDB hybrid builds take only brief locks; writes continue.
5. Use lock timeouts for DDL, clear long transactions first, and verify the result.
