<Tldr>
A **sequential** read takes the next page in the file; a **random** read jumps somewhere else. Sequential reads are cheaper **per page** because neighbouring pages can be fetched in one large request (read-ahead), while every jump is a separate small request. So an index that reads **fewer** pages, but in random order, can be **slower** than a full scan. On the lab table, an index scan returning 1% of the rows read 6,387 pages at 7.3 µs each and lost to a Seq Scan that read all 10,102 pages at 2.1 µs each. Whether an index wins depends on how many pages it touches **and** in what order.
</Tldr>

## Two ways to read pages

| | Sequential | Random |
|---|---|---|
| Which page comes next | The next page in the file | A page somewhere else in the file |
| Requests | Many pages per request: Postgres combines up to 16 pages (128 kB), InnoDB reads a whole 1 MB extent, the OS reads ahead | One request per page |
| Who reads this way | Seq Scan, InnoDB full scan, COLLSCAN, Bitmap Heap Scan (mostly) | Index Scan following an index whose order differs from the table's |

### What one read costs

Typical orders of magnitude; your hardware will differ.

| Storage | One random read | Sequential throughput | Why sequential is cheaper |
|---|---|---|---|
| RAM (a cache hit) | ≈ 0.1 µs | ≈ 10+ GB/s | Hardly any difference |
| Local NVMe SSD | ≈ 20–100 µs | ≈ 2–7 GB/s | Fewer, larger requests; no per-request overhead for each page |
| Cloud network disk (e.g. AWS EBS gp3) | ≈ 0.5–1 ms | 125 MB/s baseline | A round trip over the network per request; volumes are also limited in operations per second (3,000 IOPS baseline on gp3), and one large sequential request counts as one operation |
| Hard disk | ≈ 5–10 ms (seek + rotation) | ≈ 150–250 MB/s | The head moves only once, then the pages stream past it |

On a cloud disk, 6,000 random reads at about 1 ms each take about **6 s**; reading the whole 80 MB table sequentially at 125 MB/s takes about **0.65 s**.

### How PostgreSQL's planner models it

| Setting | Default | Meaning |
|---|---|---|
| `seq_page_cost` | 1.0 | Cost of a page read in file order (the unit in Concept 3) |
| `random_page_cost` | 4.0 | Cost of a page read out of order: 4× a sequential one |

The 4.0 dates from spinning disks with most pages cached; on SSDs many teams lower it to about 1.1–1.5. Session 3 shows how this one number moves the planner between Seq Scan and Index Scan.

## How many pages does 1% of the rows touch?

The lab query is `WHERE customer_id BETWEEN 1 AND 1000`: 1% of the customers, 9,956 of the 1M rows. The orders of each customer are **spread evenly over the whole table** (a customer orders now and then over the year), so the matching rows land all over the 10,102 pages.

If k matching rows are spread at random over P pages, the expected number of pages touched is:

**pages touched ≈ P × (1 − e^(−k / P))**

| | Value |
|---|---|
| P (pages) | 10,102 |
| k (matching rows) | 9,956 |
| k / P | 0.986 |
| 1 − e^(−0.986) | 0.627 |
| Pages touched | 10,102 × 0.627 ≈ **6,330** (measured: 6,376) |

**1% of the rows touch 63% of the pages.** A page holds 99 rows, so a page escapes only if none of its 99 rows matches: (0.99)^99 ≈ 37%.

A column whose values follow the table's physical order behaves completely differently. `created_at` rises with `id`, and rows were inserted in `id` order, so the first 9,931 rows by `created_at` sit on the first 101 pages. PostgreSQL measures this as `pg_stats.correlation`: **1.0** for `created_at`, **−0.008** for `customer_id`.

## PostgreSQL: the order heap pages are read in

| Term | Meaning |
|---|---|
| **Index Scan** | Walks the index in key order and fetches each row's heap page as it goes |
| **Bitmap Heap Scan** | First collects every matching page number from the index into a bitmap, then reads those pages in **file order** |
| **Correlation** | How closely the column's order matches the heap's physical order: 1 = same order, 0 = unrelated |
| **✓ Forward** | The next page read is the next or a nearby page further on in the file: cheap, can be combined or read ahead |
| **✗ Jump** | The next page is far away, possibly behind: a separate random read |

## MySQL InnoDB: full scan vs secondary-index lookups

| Term | Meaning |
|---|---|
| **On-demand read** | A page read because a query needs it right now: one 16 KB request (`Innodb_buffer_pool_reads`) |
| **Read-ahead** | Pages read in the background in 1 MB extents because InnoDB saw a sequential pattern (`Innodb_buffer_pool_read_ahead`) |
| **Secondary-index lookup** | `customer_id` index → primary key `id` → descend the clustered index to the leaf with that `id` (Concept 2) |
| **✓ Read-ahead** | The leaf was already fetched as part of an extent |
| **✗ On-demand** | The leaf had to be fetched on its own |

## MongoDB: COLLSCAN vs IXSCAN → FETCH

| Term | Meaning |
|---|---|
| `IXSCAN` → `FETCH` | Walk the index in key order, then fetch each document from the collection B-tree by its `RecordId` |
| `pages read into cache` | WiredTiger's counter of pages it had to read from disk (`db.serverStatus().wiredTiger.cache`) |
| **✓ In cache** | The leaf holding the document is already in the WiredTiger cache |
| **✗ Read from disk** | The leaf must be read (and decompressed) first |

## The three engines side by side

Same query, `customer_id` 1–1,000 (1% of rows), cold cache, same laptop:

| | Full scan | Index, uncorrelated | Index, correlated (`created_at`) |
|---|---|---|---|
| PostgreSQL 17 | 40 ms (Bitmap: 35 ms) | 51 ms | 1.3 ms |
| MySQL 8.4 | 167 ms | 41 ms | 4.1 ms |
| MongoDB 8.0 | 197 ms | 68 ms | 6 ms |

| What the numbers show | Why |
|---|---|
| The correlated index wins by far everywhere | Few pages, read in order |
| The uncorrelated index touches almost the whole table | 1% of the rows spread over 63% (Postgres) to ≈ 100% (InnoDB, MongoDB: fewer, bigger pages) of the pages |
| PostgreSQL's full scan is fastest among the three | Cheap per-row filtering; InnoDB and MongoDB spend most of the full scan on CPU |
| On this laptop, random reads are cheap | Local NVMe. On a network disk (≈ 1 ms per random read) every "uncorrelated" number grows by seconds, while full scans grow far less |

<Pitfall>
**Benchmarks on a laptop lie about random I/O.** A plan that reads 6,000 pages randomly costs a few tens of milliseconds on local NVMe and several seconds on a cloud disk. Compare plans by **pages read and their order** (Concept 1: compare pages, not time), then check timings on production-like storage.
</Pitfall>

## Real-world scenario: fast in development, slow in production

A dashboard query `WHERE customer_id = ANY(:ids)` for 200 customers (≈ 4,000 orders, spread over a large table) takes 30 ms on a developer laptop and 4 s in production. The plans are identical: an Index Scan on `customer_id`.

| | Laptop | Production |
|---|---|---|
| Storage | Local NVMe, data mostly in the OS cache | Network disk, data larger than RAM |
| Heap pages read | ≈ 4,000, randomly | ≈ 4,000, randomly |
| Cost per random read | ≈ 5 µs | ≈ 1 ms |
| Time | ≈ 30 ms | ≈ 4 s |

**Fixes, from cheapest:**

| Fix | Effect |
|---|---|
| Keep the working set in memory (more `shared_buffers` / RAM) | Random reads become cache hits; works until data outgrows RAM |
| Let Postgres use a Bitmap Heap Scan (do not disable it; lower `random_page_cost` only to match real storage) | Same pages, read in file order |
| Covering index (Session 5) | The heap is not visited at all: no random heap reads |
| Store related rows together: `CLUSTER orders USING orders_customer_idx` in PostgreSQL (one-off, takes a full lock, not maintained), a primary key starting with `customer_id` in InnoDB, a clustered collection in MongoDB | Makes `customer_id` correlated, so one customer's rows share pages |

| Later topic | Why this concept matters |

| Session 3: query planner | `random_page_cost`, correlation and Bitmap Heap Scan are how Postgres prices this exact trade-off |

## Key takeaways

1. A sequential read fetches the next page in the file; a random read jumps elsewhere. Sequential pages arrive many per request, random pages one per request.
2. Per page, sequential is several times cheaper: 2.1 µs vs 7.3 µs on the lab's NVMe, and far more on cloud disks and hard disks.
3. Rows spread evenly over the table make a small fraction of rows touch a large fraction of pages: pages ≈ P × (1 − e^(−k/P)); 1% of rows touched 63% of pages.
4. Correlation decides how many pages an index scan touches: the same 9,931 rows cost 131 pages through `created_at` and 6,387 through `customer_id`.
5. A Bitmap Heap Scan reads the pages an index points at in file order, once each.
6. PostgreSQL's planner models the gap with `seq_page_cost = 1.0` and `random_page_cost = 4.0`.
7. Fast local storage hides random I/O; compare plans by pages and order, not laptop timings.
