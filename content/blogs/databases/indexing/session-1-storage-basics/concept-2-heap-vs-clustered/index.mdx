<Tldr>
Concept 1 showed how rows sit **inside** a page. This concept is about **which page** a row goes to. PostgreSQL stores a table as a **heap**: rows go into any page with room, in no order, and every index (the primary key included) points at the row's physical address, its ctid. MySQL InnoDB stores the table **as a B-tree on the primary key**: rows live in the leaf pages, sorted by primary key, and secondary indexes point at the primary key value. That one choice decides what inserts, lookups and updates cost.
</Tldr>

## Two ways to store a table

| | PostgreSQL: heap | MySQL InnoDB: clustered index | MongoDB WiredTiger |
|---|---|---|---|
| Where the rows live | Heap file: pages in no particular order | Leaf pages of the primary-key B-tree, sorted by primary key | A B-tree keyed by an internal `RecordId` |
| Where a new row goes | Any page with enough free space | The leaf page where its primary key belongs | The end of the `RecordId` order (it only grows) |
| What the primary key is | Just another index, separate from the table | The table itself | The `_id` index: a separate index → `RecordId` |
| What a secondary index stores | key → ctid `(page, slot)` | key → primary key value | key → `RecordId` |
| Find a row by primary key | PK index → heap page | One B-tree descent | `_id` index → collection B-tree |
| Find a row by secondary index | Index → heap page | Index → primary key → PK B-tree | Index → collection B-tree |

You only need one fact about B-trees for now (Session 2 covers the rest): a **B-tree is a sorted tree of pages**. A small root page routes you down to the right **leaf page** in about 3–4 page reads, even for millions of rows.

## PostgreSQL: the table is a heap

| Term | Meaning |
|---|---|
| Heap | The table file: a sequence of 8 KB pages with rows in no particular order |
| Free space map (FSM) | A small side file recording roughly how many free bytes each heap page has |
| ctid `(page, slot)` | A row's physical address in the heap; what every PostgreSQL index stores |
| **✓ Room** | The FSM finds a page with enough free space; the row goes there |
| **✗ None** | No page has room; Postgres adds a new page at the end of the file |

Because the heap has no order, a PostgreSQL primary key does not decide where rows are stored. If rows happen to be inserted in id order, the heap ends up roughly in id order too, but nothing keeps it that way. (`CLUSTER` reorders a table once; later inserts and updates are not kept in order.)

## MySQL InnoDB: the table is the primary-key B-tree

| Term | Meaning |
|---|---|
| Clustered index | The B-tree on the primary key whose **leaf pages hold the full rows**, sorted by primary key. In InnoDB this *is* the table |
| Leaf page | A 16 KB page at the bottom of the tree; leaves are linked to their neighbours in key order |
| Page split | A full leaf receives a key in the middle: InnoDB moves about half its rows to a new page to make room |
| **✓ Room** | The target leaf has space; the row is added to it |
| **✗ Full** | The target leaf has no space; InnoDB adds a page (sequential key) or splits the page (random key) |

If a table has no primary key, InnoDB uses the first `UNIQUE` index whose columns are all `NOT NULL`. If there is none, it generates a hidden 6-byte row id and clusters on that.

## MongoDB: a B-tree keyed by RecordId

WiredTiger stores each collection as a B-tree keyed by an internal 64-bit **`RecordId`** that only grows, so documents are appended in insertion order, much like a heap that grows at the end. The `_id` index is a separate index mapping `_id` → `RecordId`, and every secondary index also stores the `RecordId`. When a document is updated, its `RecordId` stays the same, so indexes on unchanged fields are not touched.

| Term | Meaning |
|---|---|
| `RecordId` | Internal 64-bit document id; the collection's B-tree is sorted by it. New documents get the highest one so far |
| `_id` index | An ordinary index mapping `_id` → `RecordId`; it does not decide where the document is stored |
| Version (update) | WiredTiger keeps the old version of a document for readers that still need it (in cache, then the history store) |
| **✓ Room** / **✗ Full** | The rightmost leaf has space for the document / it does not, so a new leaf is started |
| **✓ Not indexed** / **✗ Indexed** | The updated field is in no index, so no index changes / it is in an index, so only that index changes |

## Updating a row

| Term | Meaning |
|---|---|
| MVCC | Readers see a consistent snapshot, so the old version of a row must stay available until no transaction needs it |
| Dead tuple | A PostgreSQL row version that no transaction can see any more; it still takes space until VACUUM |
| HOT update | Heap-only tuple: the new version is on the **same page** and **no indexed column changed**, so no index is touched |
| Undo log | InnoDB's store of old values; old versions are rebuilt from it, and *purge* discards it later |
| **✓ HOT** | Both HOT conditions hold |
| **✗ Not HOT** | An indexed column changed or the page is full: every index gets a new entry |

<Pitfall>
Updating the **primary key** in InnoDB is expensive: the row must move to a different place in the clustered index (a delete plus an insert), and every secondary index entry storing the old key must change too. Primary keys that never change are part of good InnoDB design.
</Pitfall>

## Real-world scenario: choosing a primary key

A team gives every table a random UUIDv4 primary key so ids can be generated by the app. Months later, MySQL inserts slow down and the tables are bigger than expected. PostgreSQL copes better, though not perfectly.

| | Auto-increment `BIGINT` | Random UUIDv4 | Time-ordered UUIDv7 |
|---|---|---|---|
| InnoDB insert position | Always the rightmost leaf | A random leaf anywhere | Near the rightmost leaf |
| InnoDB page splits | None (new page on the right) | Constant, all over the tree | Rare |
| InnoDB page fill | ≈ 15/16 | Between 1/2 and 15/16 | ≈ 15/16 |
| Cost in every InnoDB secondary index entry | 8 B | 16 B as `BINARY(16)`, 36 B as `CHAR(36)` | 16 B as `BINARY(16)` |
| PostgreSQL heap | Appends | **Still appends:** the heap ignores the key | Appends |
| PostgreSQL PK index | Inserts at the right edge | Random inserts and page splits in the **index only** | Inserts near the right edge |

**What to do:**
- **InnoDB:** use `BIGINT AUTO_INCREMENT`, or a time-ordered UUID stored as `BINARY(16)`. MySQL's `UUID_TO_BIN(uuid, 1)` reorders a version-1 UUID so its time part comes first.
- **PostgreSQL:** a UUIDv4 key hurts only the primary-key index, not the table, but UUIDv7 is still the better choice. PostgreSQL 18 generates one with `uuidv7()`.
- **Both:** never store a UUID as text (`CHAR(36)`) as a key. It more than doubles the key size, and in InnoDB every secondary index carries that cost.

## Why this matters for indexes

| Later topic | Why this concept matters |
|---|---|
| Session 2: B-tree internals | The InnoDB table *is* a B-tree, so the same mechanics (splits, fill) apply to the table itself |
| Session 4: composite indexes | Every InnoDB secondary index silently ends with the primary key columns |
| Session 5: covering indexes | Covering means "skip the second step": the heap visit in PostgreSQL, the second tree descent in InnoDB |
| Session 8: when indexes hurt | Every PostgreSQL index adds cost to non-HOT updates; every InnoDB index carries the primary key |

## Key takeaways

1. **PostgreSQL:** the table is an unordered heap; every index, the primary key included, points at a physical ctid.
2. **InnoDB:** the table is the primary-key B-tree; rows live in its leaves in key order, and secondary indexes point at the primary key.
3. **MongoDB:** documents live in a B-tree keyed by `RecordId`; every index, `_id` included, points at the `RecordId` (unless the collection is clustered).
4. A PostgreSQL index lookup costs index pages + 1 heap page; an InnoDB secondary lookup costs two tree descents.
5. Random primary keys cause page splits in InnoDB's table and in PostgreSQL's PK index; sequential or time-ordered keys avoid them.
6. A PostgreSQL update writes a new row version; unless it is HOT, every index gets a new entry. InnoDB updates in place and keeps the old value in the undo log.
