<Tldr>
A UUIDv4 is random, so each new key belongs at a **random place in a sorted B-tree**. Wherever a B-tree is sorted by that key, inserts hit random leaf pages and full pages **split**: pages end up about 69% full, writes multiply, and once the tree outgrows memory almost every insert first reads a page from disk. In **InnoDB** (and a MongoDB clustered collection) that B-tree is the whole table. In **PostgreSQL** and a normal MongoDB collection it is only the primary-key index, so the damage is smaller but real. A time-ordered **UUIDv7** always lands at the right edge and avoids all of it.
</Tldr>

## The example used in every animation

To keep the steps readable, **one page holds 4 entries** (a real 16 KB InnoDB leaf holds about 100 rows; a real PostgreSQL index leaf holds a few hundred entries). Ten rows arrive in this order, with each UUIDv4 shortened to its first two hex characters:

`7c, 2a, e1, 55, 91, 0f, 63, 3b, c4, 88`

| Key type | Example values | Where a new key belongs in sorted order |
|---|---|---|
| `BIGINT AUTO_INCREMENT` | 1, 2, 3, … | Always after every existing key: the right edge |
| UUIDv4 | `7c…`, `2a…`, `e1…` | Anywhere: 122 of its 128 bits are random |
| UUIDv7 | `0192f3a1-…`, `0192f3a2-…` | (Almost) always the right edge: the first 48 bits are a millisecond timestamp |

## InnoDB: the table itself splits

| Term | Meaning |
|---|---|
| Leaf page (P1–P4) | A page of the clustered index holding **full rows**, sorted by primary key. P1–P4 are numbered in the order they were created, which is also their order in the file |
| Room check | Is the leaf where the new key belongs already full? |
| **✓ Room** | The row is added to that leaf, kept in key order inside the page |
| **✗ Full** | Sequential key: start a new page on the right. Key in the middle of the page: **page split**, half the rows move to a new page |

**Why it matters in InnoDB:** the clustered index *is* the table. Every split moves **whole rows**, the extra ~35% of pages is extra table, and every secondary index entry also carries the 16-byte key.

## PostgreSQL: the heap is fine, the primary-key index splits

| Term | Meaning |
|---|---|
| Heap page 0–2 | Where the **rows** go: any page with room, in arrival order. The key is ignored |
| Index leaf L1–L4 | Leaf pages of `orders_pkey`, a B-tree of `id → ctid` entries sorted by `id` |
| Room check | Is the index leaf where the new key belongs already full? |
| **✓ Room** / **✗ Full** | Add the entry to that leaf / split the leaf (or start a new rightmost leaf if the key is the largest) |

**Why it matters in PostgreSQL:** the PK index grows about a third larger and needs to stay in memory to keep inserts fast. Random inserts also inflate the WAL: after each checkpoint, the first change to every page writes the whole 8 KB page into the WAL, and random keys touch thousands of different index pages instead of one.

## MongoDB: depends on the collection type

| Term | Meaning |
|---|---|
| Collection leaf | Where documents are stored in a normal collection, sorted by `RecordId` (which only grows) |
| `_id` index leaf | A leaf of the `_id` index: `_id → RecordId` entries sorted by `_id` |
| Clustered collection | A collection stored as a B-tree on `_id` itself (5.3+): its leaves hold the whole documents |
| **✓ Room** / **✗ Full** | Add to the leaf / split it |

## Why it matters: the cache cliff

The splits are only half the story. The bigger production problem is **which page each insert has to touch, and whether that page is in memory**.

| Term | Meaning |
|---|---|
| Buffer pool | InnoDB's page cache in RAM (`shared_buffers` in PostgreSQL, the WiredTiger cache in MongoDB) |
| **✓ In memory** | The leaf the insert needs is already cached: change it in RAM |
| **✗ Not in memory** | The leaf must first be read from disk, and a cached page evicted to make room |

The same flow applies to PostgreSQL and normal MongoDB collections, but for the **primary-key index only**. A 100M-row PK index is a few GB rather than a 50 GB table, so PostgreSQL and MongoDB hit the cliff much later than InnoDB.

## Each database at a glance

| | InnoDB | MongoDB clustered | PostgreSQL | MongoDB normal |
|---|---|---|---|---|
| What is sorted by the key | The table | The collection | Only the PK index | Only the `_id` index |
| What moves in a split | Whole rows | Whole documents | Index entries (~28 B) | Index entries |
| Page fill with UUIDv4 | ~69% instead of ~94% | ~69% | ~69% in the PK index | ~69% in the `_id` index |
| Cache cliff | When the table outgrows memory | When the collection does | When the PK index does | When the `_id` index does |
| Other indexes | Carry the 16 B key in every entry | Carry the key | Unaffected | Unaffected |
| Severity | High | High | Medium (plus extra WAL) | Medium |

## How to check an existing system

| Engine | What to run | Sign of trouble |
|---|---|---|
| PostgreSQL | `CREATE EXTENSION pgstattuple;` then `SELECT avg_leaf_density FROM pgstatindex('orders_pkey');` | Leaf density near 70% instead of near 90% |
| MySQL | `SET GLOBAL innodb_monitor_enable = 'index_page_splits';` then `SELECT name, count FROM information_schema.INNODB_METRICS WHERE name = 'index_page_splits';` | The count keeps climbing during normal inserts |
| MongoDB | `db.orders.stats({ indexDetails: true })` and compare the `_id` index size with the number of documents | The `_id` index much larger than expected for its entry count |

## The fix

| Situation | Do this |
|---|---|
| New table, any engine | Use `BIGINT` identity / `AUTO_INCREMENT`, or a UUIDv7 if the app must generate ids |
| PostgreSQL 18+ | `id uuid DEFAULT uuidv7()`; older versions generate UUIDv7 in the application |
| MySQL | Store UUIDs as `BINARY(16)`, never `CHAR(36)`; generate UUIDv7 in the application, or use `UUID_TO_BIN(UUID(), 1)`, which reorders MySQL's time-based UUIDv1 so the timestamp comes first |
| MongoDB | Keep the default `ObjectId` (time-ordered), or use UUIDv7; use clustered collections only with an increasing `_id` |
| Existing UUIDv4 table | Switching keys is a migration; meanwhile, size memory so the PK index (PostgreSQL, MongoDB) or table (InnoDB) stays cached, and rebuild bloated indexes (`REINDEX CONCURRENTLY`, `OPTIMIZE TABLE`) |

<Pitfall>
UUIDv7 exposes the creation time of each row in its first 48 bits. If ids are shown to users and creation time is sensitive, keep a separate random public id and use the time-ordered key internally.
</Pitfall>
