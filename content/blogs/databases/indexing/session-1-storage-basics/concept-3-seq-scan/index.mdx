<Tldr>
With no usable index, the database answers a query by reading **every page of the table, in order**, and checking every row against the `WHERE` clause. That is a **Seq Scan** in PostgreSQL, `type: ALL` in MySQL and `COLLSCAN` in MongoDB. Its cost depends on **how many pages the table has**, not on how many rows the query returns: one matching row or a million, the scan reads the same 10,300 pages. Every index in this course is a way to avoid this.
</Tldr>

## What a full scan is

| Engine | Name in EXPLAIN | What it walks | In what order |
|---|---|---|---|
| PostgreSQL | `Seq Scan` | Every page of the heap file | File order: page 0, 1, 2, … |
| MySQL InnoDB | `type: ALL` ("Table scan") | Every leaf page of the clustered index | Primary-key order, following each leaf's "next page" pointer |
| MongoDB | `COLLSCAN` | Every document in the collection B-tree | `RecordId` order (`_id` order for a clustered collection) |

The running example is the `orders` table from Concept 1: **1M rows of about 80 bytes, ≈ 97 rows per page, ≈ 10,300 pages ≈ 80 MB**. `status = 'shipped'` matches 5% of the rows (50,000).

## PostgreSQL: Seq Scan

For each page, Postgres runs two checks on every row:

| Term | Meaning |
|---|---|
| **Visible** | MVCC check: this row version belongs to the snapshot the query sees (Concept 2: an UPDATE leaves the old version behind) |
| **✓ Visible / ✗ Dead** | A dead version (deleted, or replaced by a newer version) is skipped, but it was still read: it sits in the page |
| **Filter** | The `WHERE` condition, checked on each visible row |
| **✓ Match / ✗ No match** | A match goes to the result; a non-match is counted in `Rows Removed by Filter` |
| **LIMIT reached** | With `LIMIT n`, the scan stops after the n-th match; otherwise it runs to the last page |

<Pitfall>
"It's fast, it has a `LIMIT`" is not a plan. `LIMIT` only stops a Seq Scan early when matches come early. For a rare value, or a value that appears only at the end of the table, the same query reads the whole table.
</Pitfall>

### Reading a Seq Scan in EXPLAIN

```sql
SET max_parallel_workers_per_gather = 0;  -- show the plain plan, without parallel workers
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'shipped';
```

```text
Seq Scan on orders  (cost=0.00..22800.00 rows=50000 width=56) (actual time=0.021..98.4 rows=49870 loops=1)
  Filter: (status = 'shipped'::text)
  Rows Removed by Filter: 950130
  Buffers: shared read=10300
```

| Part | Meaning |
|---|---|
| `cost=0.00..22800.00` | Planner's estimate in arbitrary units: cost to the first row (0, a scan can return a row at once) and to the last row |
| `rows=50000 width=56` | Estimated rows returned and average row width in bytes (data only, without the 24 B row header) |
| `actual … rows=49870` | Rows really returned |
| `Rows Removed by Filter: 950130` | Rows read and thrown away. 49,870 + 950,130 = 1,000,000: every row was checked |
| `Buffers: shared read=10300` | Pages touched: the whole table |

**The red flag:** `Rows Removed by Filter` much larger than `rows`. Here 95% of the work is thrown away, which is what an index would avoid (Session 3 shows how the planner decides).

### How the planner prices a Seq Scan

The cost is per page plus per row. With the default settings:

| Part | Formula | `orders` |
|---|---|---|
| Read the pages | pages × `seq_page_cost` (1.0) | 10,300 × 1.0 = **10,300** |
| Process each row | rows × `cpu_tuple_cost` (0.01) | 1,000,000 × 0.01 = **10,000** |
| Evaluate the filter | rows × operators × `cpu_operator_cost` (0.0025) | 1,000,000 × 1 × 0.0025 = **2,500** |
| **Total** | | **22,800** |

The unit is "one sequential page read = 1.0", not milliseconds. Notice that nothing in the formula depends on how many rows match: the estimate for one matching row is the same 22,800. The page and row counts come from `pg_class.relpages` and `reltuples`, which `ANALYZE` and `VACUUM` keep up to date.

### Parallel Seq Scan

On a table larger than `min_parallel_table_scan_size` (8 MB by default), the planner may split the scan across worker processes: `Gather` → `Parallel Seq Scan`. Each worker takes the next chunk of pages, so the **pages read are the same**; only the elapsed time is shared out. That is why the example above turns parallelism off to show the plain plan.

## Keeping a big scan from flushing the cache

A full scan reads every page once and rarely needs it again. If those pages pushed out the pages other queries use all the time, one report could make everything else slow. PostgreSQL and InnoDB both guard against this, in different ways.

### PostgreSQL: the ring buffer

| Term | Meaning |
|---|---|
| `shared_buffers` | Postgres's page cache (Concept 1). The default is 128 MB = 16,384 slots of 8 KB |
| **Ring buffer** | A small set of slots (256 KB = 32 pages) that a big scan reuses in turn instead of taking slots from everyone else |
| **✓ ≤ ¼ shared_buffers** | The table is small enough: its pages go into normal slots and stay cached |
| **✗ > ¼ shared_buffers** | The table is big: the scan uses the ring, so its pages do not stay cached |

### InnoDB: the old sublist

InnoDB's buffer pool is one LRU list split in two. New pages enter in the middle, and only pages used again later move to the front.

| Term | Meaning |
|---|---|
| **Young sublist** | The front ⅝ of the list: pages that have proved they are used repeatedly |
| **Old sublist** | The back ⅜ (`innodb_old_blocks_pct = 37`): where every newly read page starts, at its head (the "midpoint") |
| `innodb_old_blocks_time` | 1,000 ms by default: a page must be touched again **at least 1 s after its first access** to move to the young sublist |
| **✓ Touched again after 1 s** | The page is moved to the head of the young sublist |
| **✗ Not touched after 1 s** | The page drifts to the tail of the old sublist and is evicted first |

MongoDB documents no equivalent rule for the WiredTiger cache, so treat a large `COLLSCAN` as something that can push other data out.

## MySQL InnoDB: full table scan

InnoDB's table is the clustered index (Concept 2), so a full scan walks its leaf pages. Each leaf stores the page numbers of the previous and next leaf, so after descending once to the **leftmost leaf**, InnoDB follows the "next" pointers to the end.

| Term | Meaning |
|---|---|
| Leftmost leaf | The leaf holding the smallest primary keys: where the scan starts, after a descent from the root |
| Next pointer | Each leaf page's header holds the page number of the next leaf in key order |
| **Linear read-ahead** | When InnoDB sees pages of one 1 MB extent (64 pages) read in order (`innodb_read_ahead_threshold`, 56 pages by default), it reads the **whole next extent** in the background |
| **✓ Leaves in file order** | The next leaf is the next page in the file, so read-ahead works |
| **✗ Leaves scattered** | The next leaf is somewhere else in the file, so each leaf is a separate random read |

## When a full scan is the right plan

A full scan is not always bad. Session 3 shows how the planner chooses; the short version:

| Situation | Why a full scan wins |
|---|---|
| Small table (a few pages) | Reading 5 pages in order beats descending an index and then visiting the table |
| The query returns a large share of the rows | An index would visit table pages one at a time and many of them repeatedly; reading all pages in order once is cheaper (Concept 4: sequential vs random I/O) |
| The whole table is needed anyway | `SELECT count(*)`, reports, exports, `pg_dump` |
| No usable index | The only option, which is what Sessions 2–5 fix |

## Real-world scenario: the purge that did not speed anything up

A team keeps 30 days of `events`. The table has grown to 10M rows of about 120 B (≈ 65 rows per page, ≈ 154,000 pages ≈ 1.2 GB). They delete the 9M oldest rows and VACUUM runs. A report that scans the table is just as slow as before.

| | Before the purge | After DELETE + VACUUM |
|---|---|---|
| Live rows | 10M | 1M |
| Pages in the file | ≈ 154,000 | **≈ 154,000** |
| Rows per page | ≈ 65 | ≈ 6.5 (most pages nearly empty) |
| Pages a Seq Scan reads | ≈ 154,000 | **≈ 154,000** |

**Why:** VACUUM makes the space of dead rows **reusable** for future inserts, but it only shrinks the file by cutting off **completely empty pages at the end**. The deleted rows were the oldest, at the start of the file, so nothing was cut off. A Seq Scan reads every page in the file, empty or not.

**How to check:**

```sql
-- Live rows per page: about 65 is healthy here; about 6.5 means the table is mostly empty space
SELECT relpages, reltuples, reltuples / NULLIF(relpages, 0) AS rows_per_page
FROM pg_class WHERE relname = 'events';
```

**Fixes, by impact:**

| Fix | Effect | Cost |
|---|---|---|
| `VACUUM FULL events` | Rewrites the table compactly: ≈ 15,400 pages (120 MB) | Locks the table against reads and writes while it runs |
| `pg_repack` (extension) | The same rewrite, online | Needs about twice the table's space during the rewrite |
| Partition by day or month, drop old partitions | Dropping a partition removes its file instantly; no dead rows, no bloat | Changes the schema; queries should filter on the partition key |
| Do nothing | New inserts refill the empty pages through the free space map, so the table stops growing for a while | Scans stay slow until it refills |

**In the other engines:** InnoDB merges a leaf with its neighbour when it falls below half full, so its scan walks fewer leaves after a big delete, but the `.ibd` file keeps its size until `OPTIMIZE TABLE` rebuilds it. MongoDB likewise keeps the space for reuse; `compact` releases it.

## Key takeaways

1. A full scan reads **every page** of the table (PostgreSQL heap pages, InnoDB clustered-index leaves, MongoDB collection B-tree), whatever the query returns.
2. Its cost follows **pages in the table**, not rows returned: one row or 50,000, the same 10,300 pages.
3. `LIMIT` stops a scan only when a match is found; with no match, the whole table is read.
4. The red flag in a plan is **rows thrown away ≫ rows returned**: `Rows Removed by Filter`, `filtered`, or `totalDocsExamined` vs `nReturned`.
5. PostgreSQL prices a Seq Scan as pages × 1.0 + rows × 0.01 + rows × 0.0025 per operator.
6. Big scans do not flush the cache: PostgreSQL uses a 32-slot ring for tables over ¼ of `shared_buffers`; InnoDB keeps scan pages in the old sublist.
7. Deleting rows does not make a PostgreSQL Seq Scan faster until the table is rewritten: the empty pages are still read.
