<Tldr>
Each layer has its own unit: an 8 KB database page, 4 KB OS pages, 4 KB SSD blocks, 512-byte HDD sectors. A request from one layer is split into the units of the layer below, and the same bytes come back up. Because the sizes are powers of two, one 8 KB page is exactly 2 OS pages, 2 SSD blocks or 16 HDD sectors.
</Tldr>

## One 8 KB page in every layer's units

The request goes **down** the stack; the same bytes come back **up**. Nothing is read twice; the bytes are only counted in different chunk sizes.

| Layer | Unit | One Postgres page (8,192 B) is… |
|---|---|---|
| PostgreSQL | 8 KB page | 1 page |
| OS page cache | 4 KB page | 2 OS pages |
| SSD | 4 KB logical block | 2 blocks |
| HDD | 512 B sector | 16 sectors |

8,192 = 2 × 4,096 = 16 × 512. Every larger unit divides exactly into the smaller ones, so nothing is wasted at the edges.

## The missing layer: the file system

Between the OS cache and the disk sits the **file system** (ext4, XFS, APFS). A table is just a file; the file system knows which disk blocks hold each part of that file.

| OS page cache | Meaning | Cost |
|---|---|---|
| **✓ Hit** | Both 4 KB OS pages are already in kernel RAM; the file system and disk are skipped | A few µs |
| **✗ Miss** | At least one is not in RAM; the file system maps it to disk blocks and the disk is read | ~100 µs on SSD, ~10 ms on HDD |

| Step | Layer | Receives | Does |
|---|---|---|---|
| 1 | PostgreSQL | "page 12 of `orders`" | 12 × 8,192 = byte 98,304; asks the OS for 8,192 bytes |
| 2 | OS page cache | "8,192 bytes at 98,304" | Splits into OS pages #24 and #25; checks RAM |
| 3 | File system | "file pages #24, #25 missing" | Maps them to disk blocks |
| 4 | SSD / HDD | "read these blocks" | Returns 2 × 4 KB (or 16 × 512 B) |
| 5 | Back up | — | Blocks fill OS pages, which are copied into `shared_buffers` |

**Analogy:** you order one carton (8 KB). The warehouse stores goods in boxes (4 KB), so your carton is two boxes. The shelf map (file system) says which aisle each box is in, and the forklift (disk) moves one box at a time.

## Consequence 1: Postgres caches data twice

After a read, the page sits in both `shared_buffers` and the OS page cache. A `shared read` in `EXPLAIN` therefore often still comes from RAM, not from the disk.

| Engine | Uses the OS page cache? | Typical cache sizing |
|---|---|---|
| PostgreSQL | Yes, so data is cached twice | `shared_buffers` ≈ 25% of RAM; the OS cache uses most of the rest |
| MySQL InnoDB | Usually no: `innodb_flush_method = O_DIRECT` skips it | Buffer pool ≈ 60–80% of RAM |
| MongoDB WiredTiger | Yes | WiredTiger cache ≈ 50% of RAM; the OS cache holds compressed data |

## Consequence 2: the OS reads ahead

When the OS sees a file being read in order, it fetches the next pages before they are asked for, often 128 KB or more at a time. This is a large part of why a sequential scan is cheaper per page than jumping around (Concept 4).

## Consequence 3: torn pages

Postgres writes an 8 KB page, but the disk only guarantees each 4 KB block is written in one piece. A crash between the two blocks leaves half a new page and half an old one: a **torn page**.

| Engine | Protection |
|---|---|
| PostgreSQL | `full_page_writes`: the first change to a page after a checkpoint writes the whole page into the WAL |
| MySQL InnoDB | Doublewrite buffer: pages are written to a separate area first, then to their real place |

This problem exists only because the database page and the disk block are different sizes.

<Pitfall>
An SSD exposes 4 KB logical blocks, but its flash chips work in larger internal units (often 16 KB). The SSD controller hides that, so 4 KB is the unit that matters to the database and the OS.
</Pitfall>
