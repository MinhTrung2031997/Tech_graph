<Tldr>
A database never reads a single row. It reads and caches fixed-size **pages** (8 KB in PostgreSQL, 16 KB in InnoDB) that hold many rows each. Query cost is therefore measured in **pages touched**, and every index trick in later sessions is a way to touch fewer of them.
</Tldr>

## Why pages exist: the hardware forces it

Every layer under the database already works in blocks, so the database groups rows into pages to make each block read useful.

| Layer | Smallest unit it reads |
|---|---|
| Your query | 1 row (say 80 bytes) |
| Database | 1 page: **8 KB** (PostgreSQL) / **16 KB** (InnoDB) |
| OS page cache | 4 KB page |
| SSD / HDD | 4 KB block / 512 B–4 KB sector |

An SSD physically cannot return 80 bytes. Since a whole block comes back anyway, packing many rows into it means one read brings back lots of useful data.

| Engine | Page size | Configurable? |
|---|---|---|
| PostgreSQL | 8 KB | Compile time only, effectively fixed |
| MySQL InnoDB | 16 KB | `innodb_page_size`, fixed when the instance is initialised |
| MongoDB WiredTiger | Variable, leaf pages up to ~32 KB | Per collection, rarely changed |

## Reading one row, end to end

Step through what happens when a query needs one row whose address is already known (how the address is found is Session 2). Each cache answers with its own hit or miss. Pick a case to see its path on its own.

| Term | Meaning |
|---|---|
| **Hit** | The page is already in that cache's memory. It is served from RAM, and the layer below is never asked. |
| **Miss** | The page is not in that cache. The cache has to ask the layer below and wait for it. |

| Cache | Hit means | Miss means | `EXPLAIN (BUFFERS)` shows |
|---|---|---|---|
| `shared_buffers` (Postgres memory) | Page already in a Postgres slot: ~100 ns | Pick a slot, ask the OS | Hit: `shared hit` · Miss: `shared read` |
| OS page cache (kernel memory) | Kernel copies the page from RAM: a few µs | Kernel reads the disk: ~100 µs on SSD | Nothing: both look like `shared read` |

## Inside an 8 KB PostgreSQL page

A page has four regions. Line pointers grow from the front, row data grows from the back, and the page is full when they meet.

| Region | Size | Purpose |
|---|---|---|
| Page header | 24 bytes | Free-space pointers, checksum, LSN |
| Line pointers | 4 bytes each | Directory: "slot N lives at byte offset X, length L" |
| Free space | Whatever is left | Shrinks from both sides as rows are added |
| Row data | Each row: 23-byte header + data + alignment padding | The rows themselves, filled from the end of the page |

A row costs more than its data. With a 24-byte header (23, padded), 8-byte alignment and a 4-byte line pointer, a row carrying about 50 bytes of data takes about **84 bytes** of the page, so one page holds roughly **97 rows**.

The header records where the free space starts and ends, so an INSERT always knows where to write:

| Term | Meaning |
|---|---|
| `pd_lower` | Byte where free space starts; the next line pointer is written here |
| `pd_upper` | Byte where free space ends; the next row is written just below it |
| Line pointer `[N]` | 4 bytes at offset 24 + (N − 1) × 4, saying "row N is at byte X, length L" |
| ctid `(page, N)` | A row's address: which page, which line pointer |
| **✓ Fits** | Row + pointer ≤ `pd_upper − pd_lower`: the row goes on this page |
| **✗ Full** | Not enough room: the row goes on another page; a row is never split across pages |

## Pages are also the unit of caching

Recently used pages are kept in RAM: `shared_buffers` (plus the OS cache) in PostgreSQL, `innodb_buffer_pool_size` in InnoDB, the WiredTiger cache in MongoDB. `EXPLAIN (ANALYZE, BUFFERS)` reports exactly this:

| Field | Meaning |
|---|---|
| `shared hit=A` | A pages were already in RAM |
| `shared read=B` | B pages had to be loaded from the OS or disk |
| A + B | Total pages the query touched: the real measure of its work |

## Why this matters for indexes

| Situation | Cost in pages |
|---|---|
| Seq Scan | Every page of the table |
| Index lookup | A few index pages + the table pages that hold the matches |
| Fat rows | Fewer rows per page, so more pages to scan |
| Few matching rows spread over many pages | One page read per match |

The reason a B-tree wins (Session 2) comes down to one thing: it touches very few pages.

## Key takeaways

1. The unit of I/O and caching is the **page** (8 KB in PostgreSQL, 16 KB in InnoDB), never the row.
2. Reading one row costs one full page.
3. Rows carry overhead (header, line pointer, padding), so rows per page are fewer than page size ÷ data size.
4. Query cost ≈ **pages touched**, which `Buffers: hit + read` shows.
