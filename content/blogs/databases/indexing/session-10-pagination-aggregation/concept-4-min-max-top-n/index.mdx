<Tldr>
The largest value of an indexed column is the **last entry** of the index: `max(created_at)` read 5 buffers in PostgreSQL (rewritten as `ORDER BY … DESC LIMIT 1`), was answered **before execution** in MySQL, and examined 1 key in MongoDB with `sort + limit(1)`. But MongoDB's `$group: { $max }` scanned 1M documents. The same idea, repeated per group, solves "latest order per customer": a **LATERAL** subquery does one descent of `(customer_id, created_at)` per customer. For the 513 gold customers in Singapore it read 2,428 buffers (1.7 ms warm) where `ROW_NUMBER()` joined and sorted their 5,151 orders found through a full scan of `orders` (10,920 buffers, ≈ 41–53 ms). For all 100,000 customers the window still read **every** order (≈ 1M heap fetches, 567 ms) against 168 ms for LATERAL. MongoDB does it in one plan: `$sort` + `$group` with `$first` became a **DISTINCT_SCAN** of 1,023 keys and 0 documents.
</Tldr>

## One entry, not a scan

| Query | What the index gives | Cost |
|---|---|---|
| `max(created_at)` | The last entry of an index on `created_at` | One descent |
| `max(created_at) WHERE status = 'paid'` | The last entry of the `paid` stretch in `(status, created_at)` | One descent |
| `max(amount) WHERE status = 'paid'` | No index has `amount` after `status`: walk `(amount, id)` from the top until a paid row | Few rows if paid is common, many if rare |
| Latest order **per customer** | The last entry of each customer's stretch in `(customer_id, created_at)` | One descent **per customer** |

| Term | Meaning |
|---|---|
| InitPlan + Limit | PostgreSQL rewrites `min()`/`max()` into `ORDER BY col LIMIT 1` subplans |
| "Select tables optimized away" | MySQL resolved MIN/MAX from the index during optimization |
| LATERAL | A subquery that runs once per outer row and can reference it (`WHERE customer_id = c.id`) |
| Top-N per group | The first N rows of each group in some order (latest order, 3 cheapest items) |
| **✓ Descent per group / ✗ Every row** | Cost follows the number of groups, or the number of rows |

**DISTINCT ON and matching index direction.** `SELECT DISTINCT ON (customer_id) … ORDER BY customer_id, created_at DESC` is PostgreSQL's short form of the window query, and it also reads every order. With an index on `(customer_id, created_at)` the plan needed an Incremental Sort, because the query mixes ASC and DESC; an index on `(customer_id, created_at DESC)` removed the sort (545 → 377 ms) but not the 1M heap fetches. Only LATERAL reads one row per customer.

<Pitfall>
`ROW_NUMBER() … WHERE rn = 1` is the textbook answer to "latest row per group", and it reads every row of every group. It is the right plan when you need **all** groups and they are small; when you need a few groups, or groups are large, use one descent per group (LATERAL, or MongoDB's `$sort` + `$group` `$first`).
</Pitfall>

## Real-world scenario: the customer list with "last order"

A CRM screen lists 50 customers with their last order date and amount. The query used a window function over orders joined to the page of customers; as order history grew to 50M rows, the page slowed down every month.

| Change | Effect |
|---|---|
| Index `(customer_id, created_at)` | Each customer's latest order is the end of its stretch |
| LATERAL subquery with `LIMIT 1` (or `$sort` + `$group` `$first`) | 50 descents per page, whatever the history size |
| Optionally store `last_order_at` on customers | A write on every order, but reads become free (trade-off from Session 8) |

## Key takeaways

1. MIN/MAX on an indexed column reads one end of the index: PostgreSQL InitPlan + Limit (5 buffers), MySQL "Select tables optimized away".
2. MongoDB's `$group: { $max }` scanned 1M documents; `sort` + `limit(1)` read 1 key.
3. Window functions and `DISTINCT ON` read every row of every group, even with a matching index (1M heap fetches).
4. LATERAL + `ORDER BY … LIMIT 1` does one index descent per group: 168 ms vs 567 ms for all customers in PostgreSQL.
5. MongoDB turns `$sort` + `$group` `$first` into a DISTINCT_SCAN: one key per group, documents only if you ask for them.
