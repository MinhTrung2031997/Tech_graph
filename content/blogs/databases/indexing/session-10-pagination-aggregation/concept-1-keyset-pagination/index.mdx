<Tldr>
Session 2 showed that `OFFSET` walks and discards every skipped row, and that keyset pagination starts where the last page ended. Real lists sort by a **non-unique** column (date, price), so the keyset must be **two columns**: the sort column plus a unique **tie-breaker** (`id`). Without it, rows with the same value are skipped or repeated (17 orders at 499.97 vanished in the lab). How you write the two-column condition decides whether the index can seek: PostgreSQL turns `(created_at, id) < ($1, $2)` into an **Index Cond** (4 buffers at page 10,001 instead of 3,557) but treats the expanded `OR` form as a filter (3,557 buffers). MySQL 8.4 is the **opposite**: the row constructor walked 200,020 entries (90 ms), the expanded `OR` was a range scan (0.7 ms). The form `a <= x AND (a < x OR id < y)` seeks in both. MongoDB needs the `$or` form and merges two index scans (20 keys).
</Tldr>

## Where Session 2 stopped

Session 2, Concept 5 and Session 4, Concept 4 paged by `id` alone: `WHERE id < :last ORDER BY id DESC LIMIT 20`. That works because `id` is unique and is the sort key. Two things change in a real list endpoint:

| Real requirement | Problem |
|---|---|
| Sort by `created_at`, `amount`, `updated_at` | Not unique: many rows can share a value |
| Stable pages while you click | The position must be exact, not "values below X" |
| Filters (`status = 'shipped'`, one customer) | The index must lead with the filter, then the sort, then the tie-breaker |
| Previous page | The same index walked in the other direction |

Lab setup for this concept (per engine): an index on `(created_at, id)` and one on `(amount, id)`; in InnoDB a secondary index on `(created_at)` already ends with the primary key, so it **is** `(created_at, id)`.

## Why the tie-breaker is required

`amount` has 50,000 distinct values over 1M orders: about 20 orders share each price. Sorted by `amount DESC`, page 2 ended in the middle of the 19 orders at 499.97 (the last one shown was id 941,872).

| Page 3 condition | Result |
|---|---|
| `WHERE amount < 499.97` | Starts at 499.96: the **17** remaining orders at 499.97 are never shown |
| `WHERE amount <= 499.97` | Shows the 2 orders at 499.97 from page 2 **again** |
| `WHERE (amount, id) < (499.97, 941872)` with `ORDER BY amount DESC, id DESC` | Starts exactly after id 941,872: the 17 remaining orders come first |

| Term | Meaning |
|---|---|
| Keyset (cursor) | The sort values of the last row shown, e.g. `(created_at, id)`, sent back by the client |
| Tie-breaker | A unique column appended to the sort so every row has a distinct position (`id`, `_id`) |
| Row-value comparison | `(a, b) < (x, y)`: true when `a < x`, or `a = x AND b < y` |
| Expanded form | The same logic written out: `a < x OR (a = x AND b < y)` |
| Portable form | `a <= x AND (a < x OR b < y)`: a plain range on `a` plus a check |
| **✓ Seek / ✗ Walk** | The index starts at the cursor, or reads from the start and discards |

| Page | OFFSET (buffers) | Keyset, row comparison (buffers) |
|---|---|---|

| 10,001 (skip 200,000) | 3,557 | 4 |

**With a filter in front.** For `status = 'shipped'` (5% of orders), the index must lead with the equality column: `(status, created_at, id)`. Then `status = 'shipped' AND (created_at, id) < (…)` is one Index Cond (8 buffers). The same page with `OFFSET 20000` read 4,247 buffers, because every skipped shipped order sits on a different heap page. Without the composite, PostgreSQL walked `(created_at, id)` and discarded the 95% that were not shipped (380 rows removed for 20 kept): fine for a common status, bad for a rare one. This is the equality → sort order rule from Session 4.

**Previous page.** Flip the comparison and the direction, then reverse the 20 rows: `WHERE (created_at, id) > (first row shown) ORDER BY created_at, id LIMIT 20`, wrapped in an outer `ORDER BY created_at DESC, id DESC`. Index Scan (forward) on the same index, 5 buffers, plus a 20-row sort.

<Pitfall>
A keyset that uses the index in one engine can silently walk the whole range in another. The same condition was an Index Cond in PostgreSQL and a 200,020-entry Filter in MySQL, and the reverse for the `OR` form. Check `EXPLAIN ANALYZE` (actual rows) or `totalKeysExamined` on a deep page, not page 1, where every form looks instant.
</Pitfall>

## Real-world scenario: the admin order list

An admin screen lists orders newest first, 50 per page, with filters for status and customer, and a "Next" button. Support staff paging back through last month see the same orders twice and miss others, and deep pages time out.

| Fix | Detail |
|---|---|
| Sort by `(created_at DESC, id DESC)` | The tie-breaker makes positions exact |
| Cursor = last row's `(created_at, id)`, encoded in the URL | No page numbers; "Next" and "Previous" only |
| Index per filter: `(status, created_at, id)`, `(customer_id, created_at, id)` | Equality, then sort, then tie-breaker |
| Condition in the form the engine seeks on | PostgreSQL row value; MySQL expanded `OR`; MongoDB `$or`; or `a <= x AND (a < x OR id < y)` everywhere |
| Jump to a date instead of a page number | `WHERE created_at < :date` is also a seek |

## Key takeaways

1. Keyset needs the sort column plus a unique tie-breaker; without it, ties are skipped or repeated (17 rows lost in the lab).
2. The index must be `(filter columns…, sort column, tie-breaker)`, in the sort direction or its exact reverse.
3. PostgreSQL seeks on `(a, b) < (x, y)` and filters the expanded `OR`; MySQL 8.4 does the opposite.
4. `a <= x AND (a < x OR b < y)` seeks in PostgreSQL, MySQL and MongoDB.
5. MongoDB's `skip` discards index keys before fetching, which is cheaper than SQL `OFFSET` but still linear (200,020 keys).
6. MySQL abandoned the index for `OFFSET` beyond ≈ 4,500 rows and sorted the whole table.
