<Tldr>
Indexes are used by the **scan at the bottom** of a plan. A filter written on the outside of a view, CTE, subquery or later pipeline stage helps only if the planner can **push it down** to that scan without changing the result. It can when the filter is on a **grouping key** or **partition key** (PostgreSQL: 18 buffers, MySQL: a 10-row lookup, MongoDB: 10 keys), or on an **original field** after `$addFields`/`$lookup`/`$unwind`. It cannot when the filter is on an **aggregate** or **computed** value, when a `LIMIT` sits in between, or when the window is not partitioned by the filtered column: those read everything first (1M rows). PostgreSQL's `MATERIALIZED` CTE is an optimization fence (10,102 buffers instead of 18); MySQL pushed the same condition into its materialized CTE anyway. MongoDB coalesced `$sort` + `$limit` into a top-20 sort that kept 3 kB in memory.
</Tldr>

## The rule

A condition can move below an operator when applying it first gives the same result as applying it after.

| Between the filter and the scan | Filter on… | Can move down? | Why |
|---|---|---|---|
| `GROUP BY k` | `k` | ✓ | Removing other groups' rows does not change group `k` |
| `GROUP BY k` | `count(*)`, `sum(x)` | ✗ | The aggregate is unknown until the group is complete |
| Window `PARTITION BY k` | `k` | ✓ | Each partition is computed independently |
| Window without that partition | any column | ✗ | Removing rows changes the row numbers and running totals |
| `LIMIT n` inside | any column | ✗ | "Filter the first n" ≠ "first n of the filtered" |
| Computed column | the computed value | ✗ (unless an expression index matches, Session 5) | The index stores the original value |
| CTE | any | Depends: inlined ✓, materialized ✗ in PostgreSQL | A materialized CTE is computed once, then scanned |

| Term | Meaning |
|---|---|
| Predicate pushdown | Moving a WHERE / `$match` condition closer to the table scan |
| Optimization fence | A construct the planner does not push conditions through |
| Derived table | MySQL's name for a subquery in FROM (and for CTEs); can be **merged** or **materialized** |
| Coalescence | MongoDB merging adjacent stages (`$sort` + `$limit` → top-k sort) |
| **✓ Pushed / ✗ Fenced** | The condition reached the index, or was applied after reading everything |

## MongoDB: the pipeline optimizer moves $match

Only the stages at the **start** of a pipeline (`$match`, `$sort`, plus `$limit`/`$skip` next to them) can use an index; everything after works on the documents they produce. The optimizer therefore moves `$match` as early as it safely can.

**`$sort` + `$limit`.** Without an index on `amount`, `[{ $sort: { amount: -1 } }, { $limit: 20 }]` still read all 1M documents (206 ms), but the two stages were coalesced into a SORT with `limitAmount: 20` that kept only the current top 20 (3,174 bytes) instead of sorting everything. A `$project` between them did not stop the coalescence (the limit moved before the projection). With an index on `amount` (created for the test, then dropped) the same pipeline became LIMIT ← FETCH ← IXSCAN: 20 keys, 20 documents, 4 ms.

<Pitfall>
Views, CTEs and pipeline stages make queries readable, but each layer is a possible fence. When a query on a view is slow, check where the condition appears in the plan: in an `Index Cond` / `IXSCAN` bounds (pushed) or in a `Filter` / later `$match` above a full scan (fenced). Rewriting the condition on a stored column, or moving it inside the subquery, is usually enough.
</Pitfall>

## Real-world scenario: the reporting view

A team defines `customer_stats` as a view (`GROUP BY customer_id` with order counts, totals and a `ROW_NUMBER()` ranking by total) and the customer page queries `SELECT * FROM customer_stats WHERE customer_id = ?`. It takes seconds.

| Finding | Fix |
|---|---|
| The ranking window is not partitioned by customer: the filter cannot pass it | Remove the global rank from the per-customer view; compute rankings in a separate (cached) query |
| Without the rank, `customer_id` is the grouping key | The filter is pushed down: one index lookup per page view |
| A MongoDB version filters on a `$addFields` total | Filter on stored fields before computing |

## Key takeaways

1. An index serves only conditions that reach the scan; a condition stuck above a fence filters after reading everything.
2. Filters on grouping keys and partition keys are pushed down in all three engines (18 buffers, 10-row lookups, 10 keys).
3. Filters on aggregates, computed values, unpartitioned windows and across `LIMIT` cannot be pushed: that is semantics, not a planner weakness.
4. PostgreSQL `MATERIALIZED` CTEs are fences (10,102 vs 18 buffers); MySQL pushed conditions even into materialized derived tables.
5. MongoDB only uses indexes in the leading stages, and moves `$match` forward when it can: `$group` keys, original fields after `$addFields`, `$lookup` + `$unwind`.
