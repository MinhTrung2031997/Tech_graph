<Tldr>
Keyset pagination (Concept 1) makes every page cheap, but a "Page 3 of 50,000" label needs a **count**, and an exact count reads every matching entry. None of the three engines keeps an exact row count, because MVCC means the answer depends on who is asking. PostgreSQL counted 1M orders with an **index-only scan of its smallest index** (`orders_sku_idx` from Session 9, 7 MB: 871 buffers instead of the 10,102-page table); InnoDB counted inside the storage engine, and `EXPLAIN` named its smallest secondary index; MongoDB's `countDocuments({})` did a **COLLSCAN** of 1M documents (111 ms) while `estimatedDocumentCount()` answered from metadata in 1 ms. Filtered counts are covering index scans: 50,000 shipped orders took 196 buffers, 350,000 paid orders 1,348. For a Next button, fetch **LIMIT n+1** and skip the count; for a total, show an **estimate**.
</Tldr>

## Why an exact count is never free

| Engine | Why it cannot keep a counter | What an exact `COUNT(*)` reads |
|---|---|---|
| PostgreSQL | Each transaction sees a different set of row versions | Every matching index entry (plus heap pages not all-visible) |
| InnoDB | Same: consistent reads see different versions | Every entry of the smallest index that can answer |
| MongoDB | Count with a filter must honour the snapshot | Every matching index key, or every document for `{}` |

| Term | Meaning |
|---|---|
| Exact count | Reads every qualifying entry; cost grows with the result |
| Estimate | From statistics or metadata: `reltuples`, `EXPLAIN` rows, `table_rows`, collection metadata |
| Index-only / covering count | Counts index entries without visiting rows (Session 5) |
| `LIMIT n+1` | Fetch one extra row: if it exists, there is a next page |
| **✓ Cheap / ✗ Reads everything** | Cost independent of the table size, or proportional to it |

## LIMIT n+1: a Next button without a count

Most lists only need to know whether **another page exists**:

```sql
-- Ask for 21 rows to display 20: the 21st only answers "is there a next page?"
SELECT id, created_at, amount FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 21;
```

The extra row costs one more index entry on a page the scan is already reading. Show "Next" if 21 rows came back, and display the first 20. For totals, show an estimate ("about 350,000 paid orders") or compute the exact number in the background and cache it.

<Pitfall>
Pagination APIs often return `total` on every page "for convenience". With keyset pages costing 4 buffers and a filtered count costing 1,348, the count becomes 99% of the endpoint's work, and it is repeated on every click. Make the total optional, estimated or cached.
</Pitfall>

## Real-world scenario: the seller dashboard

A seller dashboard shows "12,345 orders · page 1 of 618" for the seller's orders in the last 90 days, refreshed on every page change. For large sellers each page takes seconds.

| Change | Effect |
|---|---|
| Drop "page X of Y"; keyset + `LIMIT n+1` for Next/Previous | Page cost constant |
| Show the total from a cached nightly count, or `EXPLAIN` rows ("about 12,000") | No count per click |
| Exact count only on demand (export, reconciliation), using an index on `(seller_id, created_at)` | Count reads the seller's stretch only, covering |

## Key takeaways

1. No engine keeps an exact row count usable under MVCC; an exact count reads every match.
2. PostgreSQL counted through its smallest index and InnoDB counted every entry inside the storage engine; MongoDB's `countDocuments({})` scanned every document.
3. A filtered count is a covering index scan: cost follows the number of matches (196 vs 1,348 buffers).
4. Estimates are free: `reltuples`, `EXPLAIN` rows, `table_rows`, `estimatedDocumentCount()`.
5. For Next/Previous, fetch `LIMIT n+1` instead of counting.
