<Tldr>
Grouping needs rows with the same key **next to each other**. Without an index the engine hashes (or sorts) every row; with an index on the group key the rows already arrive grouped, so groups can be emitted as the scan goes and a `LIMIT` stops it early: the first 10 customers' order counts took **104 index entries (5 buffers)** instead of a full scan with a 2.5 MB spill to disk. `DISTINCT` on a column with few values is better still: jump from one value to the next instead of reading the entries in between. MySQL does it automatically (**"Using index for group-by"**, 0.7 ms vs 191 ms), MongoDB too (**DISTINCT_SCAN**, 5 keys), PostgreSQL 17 does not, but a **recursive CTE** emulates it: 20 buffers instead of 10,110. Catch in MongoDB: `$group` with a `$sum` count ignored the index and scanned 1M documents.
</Tldr>

## Three ways to group

| Strategy | How | Needs | Can stop early? |
|---|---|---|---|
| Hash aggregate | Build a hash table keyed by the group, one pass over all rows | Memory (spills to disk when too large) | No |
| Sort + group | Sort all rows by the key, then aggregate runs | A sort over all rows | No |
| Streaming over an index | Read the index in key order; emit each group when the key changes | An index whose leading columns are the group key | **Yes**, with `ORDER BY key LIMIT n` |
| Skip / loose scan | Read the first entry of a key, then **seek** to the next key | Few distinct values, an index on the key | Reads one entry per group |

| Term | Meaning |
|---|---|
| GroupAggregate | PostgreSQL node aggregating sorted input group by group |
| HashAggregate | PostgreSQL node aggregating unsorted input in a hash table; `Batches > 1` = spilled to disk |
| Loose index scan | Jump from group to group in the index (MySQL "Using index for group-by", MongoDB DISTINCT_SCAN) |
| **✓ Index walk / ✗ Every row** | Cost follows the groups you need, or the whole table |

PostgreSQL 18's skip scan (Session 4) is for a missing **leading column in a WHERE** clause; it does not turn `DISTINCT` into jumps. The recursive CTE remains the tool when you need distinct values of a low-cardinality column often.

<Pitfall>
An index on the group key only helps if the plan **uses its order**. A hash aggregate (PostgreSQL), a temporary table (MySQL) or a COLLSCAN (MongoDB) over all rows means the index was not used for grouping. Look for GroupAggregate over an index scan, "Using index for group-by", or DISTINCT_SCAN / covered IXSCAN.
</Pitfall>

## Real-world scenario: filter dropdowns

A product listing shows filter dropdowns: every status, every channel, every country that has orders. Each dropdown runs `SELECT DISTINCT col FROM orders`, on every page load.

| Engine | Fix |
|---|---|
| MySQL | An index on each filter column: loose index scan, a few index reads each |
| MongoDB | An index on each column: `distinct()` uses DISTINCT_SCAN |
| PostgreSQL | An index plus the recursive CTE, or keep the values in a small lookup table (statuses rarely change) |
| All | Cache the lists; they change far less often than they are read |

## Key takeaways

1. An index on the group key delivers rows already grouped: no hash table, no sort, and `LIMIT` can stop the scan (104 entries instead of 1M).
2. Hash aggregation reads everything and can spill to disk (5 batches in the lab).
3. MySQL ("Using index for group-by") and MongoDB (DISTINCT_SCAN) jump between distinct values automatically: 5 values in 5–7 index reads.
4. PostgreSQL 17 reads every row for `DISTINCT`; a recursive CTE emulates the jump (20 vs 10,110 buffers).
5. MongoDB's `$group` with an accumulator scanned the collection; a leading `$sort` made it a covered index scan.
