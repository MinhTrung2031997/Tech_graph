<Tldr>
An index on disk is judged by **how many pages it reads** per lookup. A **B-tree** packs hundreds of sorted keys into each page, so every page read narrows the search hundreds of times: 1M keys need **3 levels**, 100M need 4. A binary tree narrows by 2 per read (≈ 20 reads), binary search over sorted pages by 2 per read (≈ 14 reads) and cannot absorb inserts, and a hash finds one key in ≈ 1 read but cannot do ranges or sorting. The B-tree is the only one that is fast, ordered **and** cheap to update, which is why PostgreSQL, InnoDB and MongoDB all use it by default.
</Tldr>

## What an index structure must do

| Requirement | Why it matters |
|---|---|
| Few page reads per lookup | Each read is a trip to `shared_buffers`, the OS or the disk (Session 1) |
| Equality: `id = 500000` | The most common query |
| Ranges and order: `BETWEEN`, `<`, `ORDER BY … LIMIT` | Dashboards, pagination, time windows |
| Cheap inserts and deletes | The index changes with every write to the table |
| Stays balanced | Every lookup must cost the same, whatever was inserted |

## Four candidate structures

| Structure | Keys per page read | Reads to find 1 key in 1M | Range / order | Inserts |
|---|---|---|---|---|
| Sorted pages + binary search | Halves the pages each read | log₂(10,102 pages) ≈ **14** | ✓ | ✗ shifting rows to keep order |
| Binary search tree | 1 key per node, halves each read | log₂(1M) ≈ **20** (worse if unbalanced) | ✓ | ✓ but unbalances without rotations |
| Hash table | — | ≈ **1–2** | ✗ no order at all | ✓ |
| B-tree | Hundreds of keys per page | **3** (measured) | ✓ | ✓ splits keep it balanced |

**The key number is fan-out**: how many children one page points to. A binary tree has fan-out 2. A B-tree internal page of `orders_pkey` holds about **286** separator keys, so each read divides the remaining search by 286 instead of 2.

| Term | Meaning |
|---|---|
| Fan-out | Children per internal page (286 measured in `orders_pkey`) |
| Height / levels | Pages read from root to leaf (3 for 1M keys) |
| B+tree | The variant all three engines use: entries only in the leaves, internal pages hold only separator keys, leaves linked to their neighbours |
| **✓ Found** | The key's entry is reached |
| **✗ Not supported** | The structure cannot answer this kind of query |

## How tall does a B-tree get?

With fan-out f, each level multiplies the keys reachable by f. Using the lab's numbers (≈ 366 keys per leaf, ≈ 286 children per internal page):

| Levels | Leaves reachable | Keys reachable |
|---|---|---|
| 2 (root + leaves) | 286 | ≈ 105,000 |
| 3 | 286² ≈ 82,000 | ≈ 30 million |
| 4 | 286³ ≈ 23 million | ≈ 8.6 billion |

**height ≈ 1 + ⌈log_f(N / keys per leaf)⌉.** Growth is so slow that almost every real index has 2–4 levels, and the root and upper levels are hot enough to stay cached: a lookup usually costs one leaf read from disk at most. Wider keys (a 36-byte UUID string instead of an 8-byte integer) lower the fan-out and can add a level.

## The three engines

| | PostgreSQL | MySQL InnoDB | MongoDB (WiredTiger) |
|---|---|---|---|
| Default index | B-tree (`nbtree`, Lehman-Yao B+tree with right-links) | B+tree; the table itself is one (clustered index) | B-tree for every index and for the collection |
| Page size | 8 KB | 16 KB | Up to 16 KB for index pages, 32 KB for collection leaf pages (default maxima) |
| Measured height, 1M rows | 3 levels (`bt_metap`: root level 2) | 3 (primary-key lookup = 3 page requests) | 3 (`maximum tree depth` of `_id_`) |
| Hash option | `CREATE INDEX … USING hash`: equality only, crash-safe since v10, rarely worth it | Adaptive hash index: built automatically in memory over hot B-tree pages; you cannot create one | "Hashed" index = a B-tree over hash values, used to spread shard keys evenly; still no ranges |

<Pitfall>
"Hash indexes are faster for equality" is true by one or two page reads at best. Since the upper levels of a B-tree are almost always cached, a B-tree equality lookup is usually one disk read too, and it also serves ranges, sorting and uniqueness. Reach for a hash index only after measuring a real gain.
</Pitfall>

## Real-world scenario: an index on a long text key

A team indexes `external_ref varchar(200)`, filled with 120-character strings, on a 50M-row table. Lookups need one more page read than on the integer primary key, and the index is several times larger.

| | `bigint` key | 120-byte text key |
|---|---|---|
| Entry size (key + header + pointer) | ≈ 16 B | ≈ 130 B |
| Entries per 8 KB leaf (90% full) | ≈ 366 | ≈ 55 |
| Leaves for 50M entries | ≈ 137,000 | ≈ 910,000 (≈ 7 GB) |
| Internal fan-out | ≈ 286 | ≈ 55 |
| Height | 4 (root → 2 → 478 → leaves) | 5 (root → 6 → 301 → 16,500 → leaves) |

**Fixes:** index a fixed-size hash of the value as a B-tree on `md5(external_ref)::uuid` (16 bytes) when only equality is needed (an expression index, Session 5); or keep the text index and accept the size when prefix searches are needed. PostgreSQL's B-tree deduplication (Concept 2) helps only when values repeat.

## Key takeaways

1. On disk, an index structure is judged by page reads per lookup.
2. Fan-out is everything: a B-tree page holds hundreds of keys, so 1M keys need 3 levels; a binary tree needs ≈ 20.
3. Binary search over a sorted table is fast to read but impossible to keep sorted under inserts.
4. A hash finds a key in ≈ 1 read but destroys order: no ranges, no `ORDER BY`, no prefixes.
5. All three engines use B+trees: entries in linked leaves, internal pages with separators only.
6. Height grows with log_fanout(N), so real indexes have 2–4 levels and their upper levels stay cached.
7. Wide keys lower fan-out: bigger index, sometimes one more level.
