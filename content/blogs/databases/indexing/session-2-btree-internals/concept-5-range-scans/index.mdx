<Tldr>
A range scan **descends once** to the first key of the range, then **walks right along the linked leaves**, entry by entry, and **stops at the first key past the end**. It never goes back up the tree. The entries come out sorted, so `ORDER BY` on the indexed column is free, and walking left gives `ORDER BY … DESC`. In the lab, `id BETWEEN 200000 AND 201000` (1,001 rows) read 6 index pages in PostgreSQL: root, one internal page, four leaves. The rest of the cost is fetching the rows, which is cheap here only because ids and heap order match.
</Tldr>

## Descend once, then walk

| Phase | What happens | `id BETWEEN 200000 AND 201000` in PostgreSQL |
|---|---|---|
| 1. Descend | A point lookup for the **lower bound** (Concept 3) | Root 412 → internal 411 → leaf 550 |
| 2. Walk | Read entries in order; at the end of a leaf, follow its right-link | Leaves 550 → 551 → 552 → 553 |
| 3. Stop | The first entry above the **upper bound** ends the scan | 201,001 on leaf 553 |
| Rows | Fetch each row (Concept 4) | Heap pages 2,020–2,030 |

Without a lower bound (`id < 500`), the descent goes to the leftmost leaf. Without an upper bound (`id > 999000`), the walk runs to the rightmost leaf.

## PostgreSQL: walking orders_pkey

| Term | Meaning |
|---|---|
| Right-link / left-link | Each leaf's special space holds its right and left neighbours' block numbers (Concept 2) |
| Index Scan Backward | The same walk to the left, for `ORDER BY … DESC` |
| **✓ In range** | The entry is ≤ the upper bound: return it (fetch its row) and continue |
| **✗ Past the end** | The entry is above the upper bound, or a `LIMIT` is satisfied: stop |

## MySQL InnoDB: ranges on the clustered and secondary indexes

| Term | Meaning |
|---|---|
| `type: range` | EXPLAIN access type for a range scan on an index |
| Clustered range | The leaves are the rows: walking them returns rows directly |
| Secondary range | Walk the secondary leaves; each entry costs a primary-key lookup unless the index covers the query |
| **✓ In range / ✗ Past the end** | Same rule as PostgreSQL |

## MongoDB: IXSCAN with bounds

| Term | Meaning |
|---|---|
| `indexBounds` | The range the IXSCAN walks, e.g. `_id: [100000, 101000]` |
| `direction` | `forward` or `backward`: the walk direction along the index |
| `SORT` stage | Appears when the index cannot provide the order; absent when it can |
| **✓ In bounds / ✗ Past the bound** | Same rule as the SQL engines |

## The engines side by side

| | PostgreSQL | InnoDB | MongoDB |
|---|---|---|---|
| Leaf links | Right-link and left-link in each page | Doubly linked leaf pages | Cursor moves through the tree (no stored sibling pointers needed) |
| Rows for a primary-key range | Heap pages (consecutive here: 11 pages) | In the leaves already | FETCH per document |
| `ORDER BY` on the indexed column | Free (no Sort node) | Free (no `Using filesort`) | Free (no `SORT` stage) |
| Descending order | Index Scan Backward | Backward index read | IXSCAN `direction: backward` |

<Pitfall>
A range scan is cheap on the **index** side no matter what; the **row** side depends on how the rows are laid out. `id BETWEEN 200000 AND 201000` touched 11 heap pages because ids follow insert order. `customer_id BETWEEN 1 AND 1000` touched 63% of the table for 1% of the rows (Session 1, Concept 4). The same range scan, very different cost.
</Pitfall>

## Real-world scenario: pagination with OFFSET

A list endpoint pages through orders with `ORDER BY id DESC LIMIT 20 OFFSET :n`. Page 1 is instant; page 5,000 takes seconds.

| Query | What the scan does |
|---|---|
| `ORDER BY id DESC LIMIT 20 OFFSET 0` | Walk left from the end, return 20 entries |
| `ORDER BY id DESC LIMIT 20 OFFSET 100000` | Walk left 100,020 entries, fetching and discarding the first 100,000 rows, then return 20 |
| `WHERE id < :last_seen_id ORDER BY id DESC LIMIT 20` (keyset) | Descend to `last_seen_id`, walk left 20 entries |

**Fix:** keyset pagination: remember the last id of the previous page and start the range there. Every page costs one descent plus 20 entries, whatever its number. The same works in MySQL and in MongoDB (`find({ _id: { $lt: lastId } }).sort({ _id: -1 }).limit(20)`).

## Key takeaways

1. A range scan descends once to the lower bound, walks the linked leaves in key order and stops at the first key past the upper bound.
2. It never returns to upper levels; the index cost is the height plus the leaves covered.
3. Entries come out sorted, so `ORDER BY` on the indexed column needs no sort, ascending or descending.
4. `ORDER BY … LIMIT n` stops after n entries: a few pages, however big the table.
5. The row part of a range scan depends on physical layout: consecutive rows are cheap, scattered rows are not.
6. `OFFSET` pagination walks and discards every skipped entry; keyset pagination starts the range where the last page ended.
