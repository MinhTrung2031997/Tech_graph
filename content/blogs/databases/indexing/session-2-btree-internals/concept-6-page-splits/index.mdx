<Tldr>
A B-tree stays balanced by **splitting** pages, never by rebalancing the whole tree. When an insert finds its leaf full, the leaf's entries are divided between it and a **new page**, and the parent gets a separator for the new page. If the parent is full it splits too, and a root split adds a level. Where the insert lands decides the split: at the **right edge** (sequential keys) PostgreSQL leaves the old page 90% full; in the **middle** (random keys) it divides 50/50. In the lab, 1M random inserts left the index 38% bigger and 66% full; 1M sequential inserts left it 90% full.
</Tldr>

## Three kinds of split

| Split | When | Result |
|---|---|---|
| **Middle split** | An insert lands inside a full leaf | Entries divided roughly in half: two pages ≈ 50% full |
| **Rightmost split** | An insert lands at the right end of the rightmost leaf (increasing keys) | PostgreSQL keeps the old page at the fill factor (90%) and starts a nearly empty new page |
| **Root split** | The root itself is full | A new root above the two halves: the tree is one level taller |

The new page always takes the next free block, usually at the **end of the index file**, so after many middle splits, leaves that are neighbours in key order are far apart on disk.

## PostgreSQL: splits measured on split_demo

The lab table `split_demo (id bigint PRIMARY KEY)` was filled with multiples of 10 (10, 20, 30, …), so there is room to insert keys in between.

| Term | Meaning |
|---|---|
| Split point | Where the entries are divided; chosen to balance free space (middle) or to respect the fill factor (rightmost) |
| Downlink | The parent's new entry: separator key → new page |
| **✓ Room** | The leaf has enough free space for the entry: insert in place |
| **✗ Full** | Not enough space: split (PostgreSQL first tries cheaper fixes, such as removing dead duplicates or deduplicating) |

### Sequential vs random: 1M inserts each

| `bigint` primary key, 1M rows | Sequential inserts | Random-order inserts | After `REINDEX` of the random one |
|---|---|---|---|
| Leaf pages | 2,733 | 3,711 | 2,733 |
| Average leaf density | 90.1% | 66.4% | 90.1% |
| Leaf fragmentation (leaves out of disk order) | 0% | 50% | 0% |
| Index size | 21 MB | 29 MB | 21 MB |

Random inserts split pages in the middle, and half-full pages fill up again only partly before splitting again: the steady state is about **⅔ full** (66.4% measured, ln 2 ≈ 69% in theory). `REINDEX` rebuilds from sorted input (Concept 2) and restores 90%.

## MySQL InnoDB: splits and merges

| Term | Meaning |
|---|---|
| `index_page_splits` | InnoDB metric counting splits (enable with `innodb_monitor_enable`) |
| Sequential insert split | When the last page fills during increasing inserts, InnoDB starts a new page without moving records; the metric still counts it as a split |
| `MERGE_THRESHOLD` | When a page drops below 50% full (default) after deletes or updates, InnoDB tries to merge it with a neighbour |
| **✓ Room / ✗ Full** | As in PostgreSQL |

## MongoDB: WiredTiger splits in memory

| Term | Meaning |
|---|---|
| In-memory page | WiredTiger edits pages in its cache, in a different format from the on-disk blocks |
| In-memory split | A cached page that grows too large is split in memory (`memory_page_max`) |
| Reconciliation | When a page is evicted or checkpointed, WiredTiger writes it out as freshly packed blocks of up to `leaf_page_max` |
| **✓ Room / ✗ Too large** | Whether the in-memory page can take the insert without splitting |

## The engines side by side

1M integer keys, inserted in order vs in random order:

| | PostgreSQL index | InnoDB clustered index | MongoDB `_id` index |
|---|---|---|---|
| Sequential | 21 MB, 90% full | 70 MB (4,445 leaves) | 11.9 MB |
| Random | 29 MB, 66% full (+38%) | 114 MB (6,347 leaves, +43%) | 12.5 MB (+4%) |
| What splits | Index pages only (the heap is unaffected) | The table itself | In-memory pages; disk blocks rewritten packed |
| Undo the damage | `REINDEX` (`CONCURRENTLY` online) | `OPTIMIZE TABLE` (rebuilds the table) | Usually unnecessary; `compact` releases free space |

<Pitfall>
Splits are not only a space problem. Each split writes two pages plus the parent, logs them (WAL / redo), and briefly locks the pages involved. Random keys on a hot table mean a steady stream of splits on many different pages, and in PostgreSQL each first change to a page after a checkpoint writes the full 8 KB page to WAL.
</Pitfall>

## Real-world scenario: an index that keeps growing on a table that does not

An `events` table keeps a steady 10M rows: new events in, old ones deleted. Its index on `(user_id)` grows every month although the row count is flat.

| Cause | Why |
|---|---|
| Random-key inserts | `user_id` values arrive in random order: middle splits, pages ≈ ⅔ full |
| Deletes do not merge PostgreSQL pages | Emptied leaves are only recycled once completely empty; partly empty leaves stay partly empty |
| Old dead entries | Index entries for deleted rows stay until VACUUM removes them |

**Check:** `SELECT avg_leaf_density, leaf_fragmentation FROM pgstatindex('events_user_idx')`. **Fix:** `REINDEX INDEX CONCURRENTLY events_user_idx` during a quiet period; consider `fillfactor` below 90 for indexes with random inserts, so new keys find room before splitting.

## Key takeaways

1. A full leaf splits: entries are divided between it and a new page, and the parent gets a downlink; a root split adds a level at the top.
2. Middle splits leave two pages about half full; PostgreSQL's rightmost split keeps the old page at the fill factor (90%).
3. The new page goes wherever a free block is, usually the end of the file, so leaf order and disk order drift apart.
4. Random inserts settle at ≈ ⅔ full: +38% size in the PostgreSQL index, +43% in the InnoDB table.
5. InnoDB counts a page split for every new page, even sequential ones that move nothing; it merges pages below 50% full.
6. WiredTiger splits in memory and writes packed blocks, so random inserts barely grow a MongoDB index on disk.
7. `REINDEX` / `OPTIMIZE TABLE` rebuild from sorted input and restore compact pages.
