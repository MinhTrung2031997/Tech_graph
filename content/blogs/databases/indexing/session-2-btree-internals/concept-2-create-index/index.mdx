<Tldr>
All three engines build an index the same way: **read every row, sort the (key, row pointer) pairs, then write the leaf pages left to right and build each upper level from the first key of every page below.** Building from sorted input is why `CREATE INDEX` on 1M rows takes well under a second, and why a fresh index is compact: PostgreSQL leaves are 90% full, InnoDB pages 15/16. A B-tree page is the same slotted page as a heap page (Session 1), holding `key → pointer` entries in key order, plus pointers to its left and right neighbours.
</Tldr>

## The build in four steps

| Step | What happens | Lab, PostgreSQL `orders_customer_idx` |
|---|---|---|
| 1. Scan | Read every row; extract (key, row pointer) | 1M (customer_id, ctid) pairs from 10,102 heap pages |
| 2. Sort | Sort the pairs by key, in memory if they fit, otherwise in sorted runs on disk merged together | Fits in `maintenance_work_mem` (64 MB) |
| 3. Leaves | Write leaf pages left to right, each filled to the fill factor | 1,130 leaves, 90.4% full |
| 4. Upper levels | Each page's first key becomes an entry one level up, until one page (the root) remains | 5 internal pages including the root: 3 levels |

It took **163 ms**. Inserting the same 1M keys one by one, in random order, would split pages constantly and leave them about 66% full (Concept 6).

## PostgreSQL: CREATE INDEX

| Term | Meaning |
|---|---|
| `maintenance_work_mem` | Memory for the sort (64 MB by default) |
| **✓ Fits in memory** | All pairs are sorted with one in-memory quicksort |
| **✗ Spills to disk** | The pairs are sorted in memory-sized chunks ("runs"), written to temp files, and merged |
| Fill factor | How full each leaf is written: 90% by default, leaving room for later inserts |
| Metapage | Block 0 of the index file: records which block is the root and the tree's height |

### Inside a PostgreSQL B-tree page

An index page uses the same layout as a heap page, with a 16-byte **special space** at the end holding the tree links.

| Part | Leaf block 1,373 of `orders_pkey` | Internal block 1,270 |
|---|---|---|
| Header | Bytes 0–23 | Bytes 0–23 |
| Line pointers | 367 × 4 B: bytes 24–1,491 | 286 × 4 B: bytes 24–1,167 |
| Free space | 808 B (the 10% fill-factor reserve) | 2,436 B (internal pages are built 70% full) |
| Entries | `id → heap ctid`, 16 B each, bytes 2,304–8,175 | `separator id → child block`, 16 B each |
| Special space (bytes 8,176–8,191) | prev leaf 1,372, next leaf 1,374, level 0 | prev 984, next 1,556, level 1 |
| First entry | **High key 500,323**: upper bound of this page, not a real entry | "Minus infinity" downlink to the leftmost child |

| Term | Meaning |
|---|---|
| High key | On every page except the rightmost of a level: the smallest key allowed on the **next** page. A search for a bigger key moves right |
| Right-link | The "next" pointer: lets a search that raced with a split recover by moving right (Lehman–Yao), and lets range scans walk the leaves |
| Posting list | One entry holding a key once and many ctids: deduplication of equal keys |

## MySQL InnoDB: sorted index build

| Term | Meaning |
|---|---|
| Sorted index build | Since MySQL 5.7: secondary indexes are built bottom-up from sorted input instead of row-by-row inserts |
| `innodb_sort_buffer_size` | Memory per sort run (1 MB by default); bigger data spills to temp files and is merged |
| `innodb_fill_factor` | How full pages are written (100 by default, which still leaves 1/16 of each page free) |
| Online log | Online DDL (`ALGORITHM=INPLACE, LOCK=NONE`): writes during the build are recorded here and applied at the end |
| **✓ Fits in the sort buffer / ✗ Merge** | Small input sorts in one buffer; larger input is sorted in runs and merged |

## MongoDB: createIndex

| Term | Meaning |
|---|---|
| Hybrid index build | Since MongoDB 4.2: an exclusive lock only at the very start and end; reads and writes continue in between |
| External sorter | Collects keys in memory up to `maxIndexBuildMemoryUsageMegabytes` (200 MB by default), spilling sorted runs to disk beyond that |
| Side-writes table | Records writes made during the build; drained into the index before it finishes |
| Prefix compression | WiredTiger stores a key's shared prefix with the previous key only once, shrinking indexes on repetitive keys |
| **✓ Fits in 200 MB / ✗ Spill** | Same decision as the SQL engines |

## The engines side by side

Lab, same 1M rows, index on `customer_id`:

| | PostgreSQL 17 | MySQL 8.4 | MongoDB 8.0 |
|---|---|---|---|
| Build time | 163 ms | ≈ 1.5 s | 577 ms |
| Size | 9.1 MB (deduplicated; 21 MB without) | 1,251 pages × 16 KB ≈ 19.5 MB | 6.8 MB (prefix-compressed) |
| Leaves | 1,130, 90% full | 1,078, ≈ 15/16 full | not reported |
| What blocks during the build | Writes to the table (reads continue); `CONCURRENTLY` avoids it (Session 8) | Nothing for long: online DDL, short metadata locks at start and end | Nothing for long: brief exclusive locks at start and end |
| Memory knob | `maintenance_work_mem` | `innodb_sort_buffer_size` | `maxIndexBuildMemoryUsageMegabytes` |

<Pitfall>
A plain `CREATE INDEX` in PostgreSQL blocks **every INSERT, UPDATE and DELETE** on the table until it finishes. On a big production table that can be minutes of failed or queued writes. Use `CREATE INDEX CONCURRENTLY` there (Session 8 covers its trade-offs).
</Pitfall>

## Real-world scenario: the index that was twice as big as expected

A team adds an index on `status` to a 200M-row PostgreSQL 12 table and is surprised it takes 5 GB for five distinct values. After upgrading to PostgreSQL 16 and running `REINDEX`, it shrinks to about 1.4 GB.

| | Without deduplication (≤ v12, or `deduplicate_items = off`) | With deduplication (v13+) |
|---|---|---|
| Entry per row | 16 B + 4 B line pointer | Key once per posting list + 6 B per ctid |
| Lab, 1M rows, `status` | 25 MB | 6.8 MB |

**What to check:** `pgstatindex` and index sizes after major upgrades: deduplication only applies to indexes built or rebuilt on v13+. And ask whether a five-value column needs an index at all; usually a partial index (Session 5) or a composite one (Session 4) serves the real query better.

## Key takeaways

1. Every engine builds an index by scanning the table, sorting (key, row pointer) pairs and writing leaves left to right, then each upper level.
2. The sort runs in memory if it fits (`maintenance_work_mem`, `innodb_sort_buffer_size`, 200 MB in MongoDB), otherwise as sorted runs merged from disk.
3. A fresh B-tree is compact: PostgreSQL leaves 90% full, internal pages 70%; InnoDB pages 15/16.
4. A B-tree page is a slotted page: header, line pointers, entries in key order, and links to its neighbours; non-rightmost pages start with a high key.
5. PostgreSQL 13+ deduplicates equal keys into posting lists; MongoDB uses prefix compression; both shrink indexes on repetitive keys.
6. A plain PostgreSQL `CREATE INDEX` blocks writes; InnoDB and MongoDB build online with brief locks.
