<Tldr>
An index entry is only a pointer. Getting the row costs a second step, and it is often the expensive one: **PostgreSQL** reads the heap page named by the ctid and checks that the row version is visible to the query; **InnoDB** takes the primary key from the secondary entry and descends the clustered index; **MongoDB** takes the RecordId and descends the collection B-tree. For 7 rows of one customer, PostgreSQL's index part cost 3 pages and the heap part 7. Each engine can skip the second step when the index alone answers the query: an index-only scan, a covering index, a covered query.
</Tldr>

## The second step in each engine

| | PostgreSQL | InnoDB (secondary index) | MongoDB |
|---|---|---|---|
| Leaf entry holds | key → ctid `(page, slot)` | key + primary key | key → RecordId |
| Second step | Read heap page, follow line pointer | Descend the clustered index by primary key | Descend the collection B-tree by RecordId |
| Cost per row | 1 page (if not already read) | ≈ 3 pages | ≈ 3 pages |
| Visibility (MVCC) | Checked on the heap row: the index has no visibility information | Checked on the clustered record (undo log for old versions) | Handled by WiredTiger's own versioning |
| Skipping it | Index-only scan (needs the visibility map) | Covering index (`Using index`) | Covered query (`PROJECTION_COVERED`) |

## PostgreSQL: ctid → heap

| Term | Meaning |
|---|---|
| ctid | `(page, slot)`: heap page number and line pointer number |
| Visibility check | Is this row version visible to my snapshot? Based on the row's `xmin` / `xmax` (Session 1, Concept 2) |
| HOT chain | After a HOT update, the index still points at the old slot; the old slot leads to the new version on the same page |
| Redirect line pointer | Once VACUUM removes the old version, its line pointer is left as a redirect to the chain's live version |
| Visibility map | One bit per heap page: "all rows on this page are visible to everyone"; lets an index-only scan skip the heap |
| **✓ Visible / ✗ Not visible** | The version belongs to the query's snapshot or not; an invisible one is skipped |
| **✓ All-visible / ✗ Not** | Visibility-map bit set or not, for index-only scans |

## MySQL InnoDB: secondary entry → clustered index

| Term | Meaning |
|---|---|
| Primary-key lookup | Descend the clustered index with the primary key taken from the secondary entry: ≈ 3 page requests per row |
| Covering index | Every column the query needs is in the secondary entry (indexed columns + primary key): no clustered lookup. EXPLAIN shows `Using index` |
| Index condition pushdown (ICP) | Conditions on indexed columns are checked on the secondary entry **before** the primary-key lookup. EXPLAIN shows `Using index condition` |
| **✓ Passes / ✗ Fails ICP** | Only entries that pass the pushed-down condition pay for the row lookup |

## MongoDB: RecordId → FETCH

| Term | Meaning |
|---|---|
| `IXSCAN` | Reads index entries: key → RecordId |
| `FETCH` | Descends the collection B-tree by RecordId to load the document, then applies any remaining filter |
| Covered query | Every field the query filters on and returns is in the index, and `_id` is excluded from the projection: `PROJECTION_COVERED`, `totalDocsExamined: 0` |
| **✓ Covered / ✗ Needs the document** | Whether the FETCH stage can be skipped |

## The engines side by side

Customer 7 in the lab:

| | Rows | Index part | Row part | Without the row part |
|---|---|---|---|---|
| PostgreSQL | 7 | 3 pages | 7 heap pages (10 in total) | Index-only scan: 4 pages, Heap Fetches 0 |
| InnoDB | 10 | ≈ 9 page requests | ≈ 4 per row (≈ 50 in total) | Covering: ≈ 9 page requests |
| MongoDB | 10 | 10 keys | 10 documents fetched | Covered: 0 documents |

<Pitfall>
`SELECT *` turns every index lookup into "index + row". On a query returning thousands of rows through a secondary index, the row part dominates: in InnoDB each row is a full clustered-index descent. Select only the columns you need; it is the precondition for covering indexes (Session 5).
</Pitfall>

## Real-world scenario: the index scan that got slower every week

An order-status dashboard runs `SELECT * FROM orders WHERE customer_id = $1`. It is fast after a deploy and slower every week. The table receives heavy `UPDATE`s to `status` and `updated_at`.

| Cause | Effect on the second step |
|---|---|
| Non-HOT updates (pages full, or an indexed column changed) | Every update adds a new entry to every index; old entries point at dead versions |
| VACUUM not keeping up | Index lookups visit heap pages only to find invisible versions (✗ not visible) |
| Visibility map bits cleared | Index-only scans fall back to heap fetches |

**Fixes:** tune autovacuum for the table (Session 8), lower `fillfactor` so updates stay HOT, don't index frequently updated columns unless needed, and check `n_tup_hot_upd / n_tup_upd` and `Heap Fetches` in plans.

| Later topic | Why this concept matters |

## Key takeaways

1. An index entry is a pointer; fetching the row is a second step that often costs more than the index part.
2. PostgreSQL follows a ctid to a heap page and checks visibility there; indexes have no visibility information.
3. HOT chains and redirect line pointers keep index entries valid across same-page updates.
4. Index entries for dead versions cost heap reads until VACUUM removes them.
5. InnoDB secondary entries hold the primary key; every row costs a clustered-index descent unless the index covers the query.
6. ICP checks indexed conditions before the row lookup.
7. MongoDB FETCHes by RecordId; a covered query (with `_id: 0`) skips it.
