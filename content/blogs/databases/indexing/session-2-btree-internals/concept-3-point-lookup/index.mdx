<Tldr>
A point lookup reads **one page per level**: root, internal pages, leaf. On each page it binary-searches the sorted keys (about 9 comparisons for 300 keys) to pick the one child to follow. In the lab, `WHERE id = 500000` reads root block 412 → internal block 1,270 → leaf block 1,373 → heap page 5,050: **4 pages**, `Buffers: shared hit=4`. A missing key costs the same descent and **no** table visit (3 pages). InnoDB ends at the leaf because the leaf is the row; MongoDB, on a normal collection, descends two B-trees: the `_id` index, then the collection.
</Tldr>

## One page per level

| Level | What the page holds | What the search does on it |
|---|---|---|
| Root | A few separators (10 in `orders_pkey`) | Binary search → the child whose range contains the key |
| Internal | Hundreds of separators (286 in block 1,270) | Same, one level down |
| Leaf | Entries `key → row pointer` (366 in block 1,373) | Binary search → the entry, or the place it would be |
| Table (PostgreSQL heap, MongoDB collection) | The row | Fetch it by its pointer (Concept 4) |

Inside a page, the keys are sorted, so the search is a **binary search**: ⌈log₂(366)⌉ = 9 comparisons on the leaf, 9 on the internal page, 4 on the root. About 20 comparisons in total, a few hundred nanoseconds. The page reads are what cost.

## PostgreSQL: descending orders_pkey

| Term | Meaning |
|---|---|
| Metapage | Block 0: holds the root's block number (412) and level (2). Read once per connection, then cached |
| Separator | An internal-page key: "everything from this key up to the next separator is under this child" |
| High key | The first item of a non-rightmost page: the upper bound of keys on that page (Concept 2) |
| **✓ Found** | The leaf has an entry for the key; Postgres fetches the heap row |
| **✗ Not found** | The leaf has no entry; the search stops with no heap visit |
| **Move right** | The key is above this page's high key (a split happened during the descent): follow the right-link |

## MySQL InnoDB: descending the clustered index

| Term | Meaning |
|---|---|
| Page directory | An array of slots at the end of each InnoDB page, each pointing at every 4th–8th record; InnoDB binary-searches the slots, then walks at most 8 records |
| Leaf = row | The clustered index leaf holds the whole row (Session 1, Concept 2), so the descent ends with the data |
| Adaptive hash index (AHI) | An in-memory hash InnoDB builds over B-tree pages it sees searched repeatedly; a hit jumps straight to the record |
| **✓ AHI hit / ✗ AHI miss** | Hit: skip the descent. Miss (or AHI off): descend normally |
| **✓ Found / ✗ Not found** | Whether the leaf has a record with that key |

## MongoDB: _id lookup

| Term | Meaning |
|---|---|
| `EXPRESS_IXSCAN` | MongoDB 8.0's fast path for simple equality lookups on `_id` (and some unique indexes): skips query planning |
| Two B-trees | Normal collection: `_id` index (key → RecordId), then the collection B-tree (RecordId → document) |
| Clustered collection | The collection B-tree is keyed by `_id` itself: one descent (Session 1, Concept 2) |
| **✓ Found / ✗ Not found** | Whether the `_id` index has the key |

## The engines side by side

`WHERE id = 42` / `{ _id: 42 }` on the lab's 1M rows:

| | PostgreSQL | InnoDB | MongoDB (normal) | MongoDB (clustered) |
|---|---|---|---|---|
| Trees descended | 1 (index), then a direct heap page | 1 (the table) | 2 (`_id` index, collection) | 1 |
| Pages for a found key | 3 + 1 heap = 4 | 3 | ≈ 3 + 3 | ≈ 3 |
| Pages for a missing key | 3 | 3 | ≈ 3 | ≈ 3 |
| Shortcut | Root location cached per connection | Adaptive hash index (off by default in 8.4) | Express path skips planning, not pages |

<Pitfall>
Measuring a lookup with a fresh connection each time (`psql -c` in a loop, a connection pool that reconnects) overstates its cost: the first index access in a PostgreSQL connection also reads the metapage and builds relation caches. In the lab, the same lookup showed 7 buffers on a new connection and 4 after a warm-up query.
</Pitfall>

## Real-world scenario: why "it's indexed" can still mean 5 ms

A lookup by primary key takes 0.05 ms in testing and 5 ms in production under load, with the same plan.

| Cause | Why | Check |
|---|---|---|
| Leaf and heap pages not cached | 3 index levels are hot, but with a big table the leaf and heap page come from disk: 2 random reads | `Buffers: shared read=` in `EXPLAIN (ANALYZE, BUFFERS)` |
| New connection per request | Metapage and catalog reads on every first query | Use a connection pool that keeps connections open |
| Many lookups instead of one | An N+1 loop of 200 lookups × 4 pages | Batch: `WHERE id = ANY($1)` |

## Key takeaways

1. A point lookup reads one page per level: root, internal pages, leaf; a few levels even for millions of rows.
2. Inside each page, a binary search over sorted keys picks the child; comparisons are cheap, page reads are not.
3. PostgreSQL finds the root via the metapage (cached per connection); `id = 500000` costs 3 index pages + 1 heap page.
4. A missing key costs the descent only: no table visit.
5. Lehman–Yao high keys and right-links let readers move right instead of blocking on splits.
6. InnoDB ends at the leaf because the leaf is the row; its adaptive hash index can skip the descent for hot keys.
7. A normal MongoDB collection needs two descents (`_id` index, then collection); a clustered one needs one.
