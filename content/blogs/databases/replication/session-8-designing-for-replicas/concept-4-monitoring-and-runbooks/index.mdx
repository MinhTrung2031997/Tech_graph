<Tldr>
Monitor **positions, not reported seconds**: LSN differences, GTID sets still missing, optime differences. Then monitor what keeps history alive or lets it vanish: **slots** (retained WAL, inactive slots), **binlog and oplog windows** in hours against your slowest reader, and **apply errors** (a stopped subscription, a replica SQL thread error). Then the durability guards: number of **synchronous standbys** streaming, **semi-sync status**, w:'majority' **write-concern errors**. And the routing signals from Concept 2: **fallback rate** of own-writes reads. Each signal below comes with the query and the incident from this course that it would have caught. Three runbooks close the course: lag, retention, failover.
</Tldr>

| `now() - pg_last_xact_replay_timestamp()` 42.7 s | Nothing behind; the primary was idle | 3 |

| Slot `active = f`, nothing alarming | 206 MB WAL retained, growing with every write | [7, Concept 2](/blogs/databases/replication/session-7-logical-replication-cdc/concept-2-logical-decoding-and-slots) |

## The checklist

### PostgreSQL

| Signal | Query | Alert when |
|---|---|---|
| Standby position lag | `SELECT application_name, pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) FROM pg_stat_replication;` | bytes grow for several minutes, or above what replays in your RTO |
| Standby missing | `SELECT count(*) FROM pg_stat_replication WHERE state = 'streaming';` | below the expected count; for `ANY 1 (s1, s2)`, below 2 |
| Sync state | `sync_state` column (`sync`, `quorum`, `potential`, `async`) | no `sync`/`quorum` standby while synchronous commit is configured |
| Slot retention | `SELECT slot_name, active, wal_status, pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) FROM pg_replication_slots;` | inactive slot, retained bytes above a few GB, `wal_status` not `reserved` |
| Subscription health (subscriber) | `SELECT subname, apply_error_count, sync_error_count FROM pg_stat_subscription_stats;` | counter increases |
| Hot-standby cancellations (standby) | `SELECT datname, confl_snapshot, confl_lock FROM pg_stat_database_conflicts;` | increases on replicas serving users (Session 6) |

### MySQL

| Signal | Query | Alert when |
|---|---|---|
| Transactions missing on a replica | `SELECT GTID_SUBTRACT(<source gtid_executed>, <replica gtid_executed>);` (or a heartbeat table) | non-empty for longer than your bound |
| Threads running | `SHOW REPLICA STATUS` → `Replica_IO_Running`, `Replica_SQL_Running`, `Last_IO_Errno`, `Last_SQL_Errno` | not Yes, or any error (1236, 13114, 1062) |
| Applier detail | `performance_schema.replication_applier_status_by_worker` | `LAST_ERROR_NUMBER` ≠ 0 |
| Semi-sync | `SHOW STATUS LIKE 'Rpl_semi_sync_source_status'`, `Rpl_semi_sync_source_no_tx` | status OFF, or no_tx increasing |
| Binlog window | oldest file in `SHOW BINARY LOGS` vs slowest reader's position | slowest reader within hours of the oldest file |
| Errant GTIDs | replica `gtid_executed` minus source `gtid_executed` | non-empty (blocks failover, Session 5) |
| Replicas writable | `SELECT @@super_read_only` on replicas | 0 |

### MongoDB

| Signal | Query | Alert when |
|---|---|---|
| Secondary lag | `rs.printSecondaryReplicationInfo()` or optime differences from `rs.status()` | above the bounded-staleness limit you route with |
| Member health | `rs.status().members[].stateStr`, `health` | fewer than a majority healthy, or any member not PRIMARY/SECONDARY |
| Oplog window | `rs.printReplicationInfo()` "log length start to end" | below the longest expected CDC or secondary outage |
| Majority writes failing | driver errors `WriteConcernFailed` (64), server `serverStatus().metrics.getLastError.wtimeouts` | any increase |
| Change-stream consumers | consumer's lag = now − cluster time of the last processed event | approaching the oplog window |

### Application

| Signal | Where | Alert when |
|---|---|---|
| Own-writes fallback rate | router metric (Concept 2) | rising: replicas lagging, primary about to take more load |
| Stale-read complaints | support tags | any pattern after deploys |
| CDC consumer lag | connector metrics (Debezium `MilliSecondsBehindSource`, offsets) | approaching retention (binlog age, oplog window, slot limit) |

**Runbook: log retention.** A PostgreSQL slot retains WAL, or a MySQL / MongoDB reader approaches the end of the binlog / oplog.

1. Identify the reader: slot name and `active`; connector name and stored position; replica host.
2. If the reader is gone for good: drop the slot (PostgreSQL) — never delete WAL files by hand.
3. If it is coming back: compare its expected catch-up time with free WAL space (PostgreSQL) or with the remaining binlog/oplog window (MySQL, MongoDB). If it will not make it, plan the resnapshot now.
4. Afterwards: `max_slot_wal_keep_size` set, alert on inactive slots, binlog/oplog window sized for the slowest reader.

**Runbook: failover.** From Session 5.

1. Confirm the primary is really down from more than one place (avoid failing over on a network partition seen from one side).
2. Fence the old primary first: stop it, block its port, or revoke its storage, so two writable primaries cannot exist (Session 5, Concept 5).
3. Promote the most up-to-date candidate: highest replayed LSN / most complete GTID set; MongoDB elects by itself.
4. Repoint applications and replicas; drop own-writes session tokens (Concept 2); check logical slots exist on the new primary (Session 7: failover slots, `synchronized_standby_slots` reset).
5. Record what was lost: async commits after the last replicated position, MongoDB rollback files, MySQL errant GTIDs on the old source.
6. Rebuild the old primary as a replica (`pg_rewind` or re-clone; for MySQL, remove errant transactions or re-clone).

<Pitfall>
Alerting on lag in seconds only. Every misleading value in the first table above came from a seconds metric. Alert on positions (bytes of WAL, GTIDs missing, optime difference), and add a **heartbeat** (a row updated every second on the primary, read on each replica) if you need lag in time that is right even when the primary is idle.
</Pitfall>

## Real-world scenario: the Monday after a long weekend

Over a three-day holiday, the analytics team's Debezium connector stopped on Friday night when their Kafka cluster ran out of disk. On Monday at 09:00 the OMS primary's WAL volume is at 92 %, a reporting replica is 2 hours behind after a weekend bulk import, and the semi-sync status on the MySQL catalog database is OFF since Saturday.

| Signal | Would have fired | Action |
|---|---|---|
| Inactive slot, retained bytes | Saturday morning | Drop or fix the connector before the disk fills; `max_slot_wal_keep_size` as a backstop |
| Reporting replica position lag | Sunday during the import | It is class 4 (analytics): fine if routing kept users off it |
| `Rpl_semi_sync_source_status = OFF` | Saturday | Find the replica that stopped acknowledging; until fixed, the catalog's RPO is not 0 |
| Own-writes fallback rate | Never: users were on healthy replicas | — |

## Key takeaways

1. Alert on positions (bytes, GTIDs, optimes), not on reported seconds.
2. Watch what keeps history: slots in PostgreSQL; binlog and oplog windows against the slowest reader in MySQL and MongoDB.
3. Watch durability guards: streaming synchronous standbys, semi-sync status, majority write errors.
4. Lag has three causes with different fixes: not receiving, not applying, applying too slowly.
5. Failover: confirm, fence, promote, repoint, record losses, rebuild.
