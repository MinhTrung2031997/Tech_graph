<Tldr>
To let a user read their own write from a replica, the app keeps the write's **position** in the user's session (a *session token*: PostgreSQL LSN, MySQL GTID set, MongoDB cluster time) and, before reading a replica, waits until the replica has applied it. Measured with the same client against each engine: an immediate replica read was stale **98–100 %** of the time; the position wait removed every stale read and cost a median of **2.18 ms** (PostgreSQL), **2.26 ms** (MySQL) and **1.67 ms** for the whole write-plus-read in a MongoDB causal session (against 0.24 ms for write plus primary read). Under load the tail matters: with 2,819 writes/s on the primary the PostgreSQL wait reached **162 ms**; with 1,636 writes/s the MySQL replica could not keep up, fell **105,700 transactions** behind, and the GTID wait timed out every time. A router therefore needs a **time limit** with a **fallback to the primary**, and must expire tokens.
</Tldr>

| Term | Meaning |
|---|---|
| Session token | Position of the user's last write, stored with their session (cookie, JWT claim, server-side session) |
| Position wait | Replica-side check that it has applied at least the token: `pg_last_wal_replay_lsn() >= token`, `WAIT_FOR_EXECUTED_GTID_SET(token, timeout)`, MongoDB `afterClusterTime` in a causal session |
| Fallback | Read the primary when the wait exceeds its limit |
| Token expiry | After N seconds normal lag is far below N, so the token is dropped and reads go anywhere |
| **✓ / ✗** | Fresh / stale or timed out |

## The experiment

A Python client in a container on the lab network, one connection to the primary and one to the replica. For each iteration and strategy: update one random order's `status` to a unique token on the primary, then read the row back.

| Strategy | PostgreSQL 17 | MySQL 8.4 | MongoDB 8.0 (write + read timed) |
|---|---|---|---|
| Replica at once | **499/500 stale**, p50 0.07 ms | **300/300 stale**, p50 0.07 ms | **295/300 stale**, p50 0.28 ms |
| Primary | 0 stale, p50 0.04 ms | 0 stale, p50 0.05 ms | 0 stale, p50 0.24 ms |
| Position wait on the replica | 0 stale, p50 **2.18 ms**, p95 4.28, max 17.5 | 0 stale, p50 **2.26 ms**, p95 8.29, max 29.0 | causal session, w:majority + majority read on a secondary: 0 stale, p50 **1.67 ms**, p95 3.12, max 12.9 |
| How the position was obtained | `pg_current_wal_lsn()` after the commit | `@@global.gtid_executed` after the commit (with `session_track_gtids = OWN_GTID` set) | the driver's session `operationTime` / `clusterTime` |

PostgreSQL 17 has no built-in "wait for LSN" function, so the client polled `pg_last_wal_replay_lsn()` every 0.5 ms (1.2 polls on average). Session 3 wrapped the same loop in a server-side function; MySQL's `WAIT_FOR_EXECUTED_GTID_SET` waits on the server; MongoDB's driver attaches `afterClusterTime` to reads in a causal session automatically.

## When the replica cannot keep up (MySQL)

On the MySQL pair, eight threads updated random orders on the source at 1,562–1,636 updates/s. The replica (4 parallel applier workers, the 8.4 default) applied about **1,165 transactions/s** on this laptop, so the gap grew for as long as the load ran:

| Time | Missing on the replica (`GTID_SUBTRACT`) |
|---|---|
| About 20 s into the load | 56,095 transactions |
| About 87 s (load ends at 90 s) | 105,686 |
| 90 s after the load ended | 0 |

`WAIT_FOR_EXECUTED_GTID_SET(token, 1)` returned 1 (timeout) on the first iteration; with a 10 s limit it timed out too. `Seconds_Behind_Source` showed 3 s and later 37 s. For own-writes routing that is fine **if** the router falls back to the source; without a fallback every own-writes read would have waited 10 s or failed. For bounded-staleness routing (Concept 1, class 3) this replica should have been taken out of the pool.

| Engine | Wait primitive | Bounded | Fallback needed |
|---|---|---|---|
| PostgreSQL 17 | Poll `pg_last_wal_replay_lsn()` (client loop or a PL/pgSQL function) | Your loop's limit | Yes |
| MySQL 8.4 | `WAIT_FOR_EXECUTED_GTID_SET(gtid_set, timeout)` returns 0 or 1 | Timeout argument | Yes |
| MongoDB 8.0 | Causal session; reads carry `afterClusterTime` | `maxTimeMS` on the read | Driver retries elsewhere only with your logic |

<Pitfall>
A position wait without a limit turns replica lag into page latency, and lag can be minutes (the MySQL replica above, or any replica blocked by a lock as in Session 3). Always bound the wait (50–200 ms is typical for user pages), fall back to the primary, and count fallbacks: a rising fallback rate is an early lag alarm and a warning that the primary is about to receive the replicas' load.
</Pitfall>

## Designing the token

| Decision | Recommendation |
|---|---|
| Scope | Per user (or per tenant/seller), not global: other users do not need this user's write |
| Content | Highest position the user wrote: LSN, GTID set (only this server's UUID interval if possible), or MongoDB cluster time |
| Transport | Server-side session or a signed cookie; must survive load balancers sending the next request to another app server |
| Expiry | 10–30 s after the write: normal lag is milliseconds, and an expired token means "any replica" |
| Multi-region | A token from region A means nothing to a replica in region B unless both replicate from the same primary |
| Failover | Positions from the old primary may never appear on the new one (Session 5 rollbacks, errant GTIDs): drop tokens after a failover |

## Real-world scenario: seller edits a price

A seller changes the price of a SKU from 199,000 VND to 179,000 VND and is redirected to the listing page, which reads from a replica. Without a token they see 199,000 and edit again; two price-change events go to the marketplaces.

| With a token | Measured basis |
|---|---|
| Write returns LSN; app stores it in the seller's session for 30 s | `pg_current_wal_lsn()` after commit |
| Listing page waits up to 100 ms for the replica | p50 2.18 ms idle, p95 6.47 ms under 2,819 writes/s |
| Timeout → read primary, increment `own_writes_fallback_total` | Max 162 ms under load; MySQL replica timed out under sustained load |
| Other sellers' reads unaffected | Token is per session |

## Key takeaways

1. Immediate replica reads were stale 98–100 % of the time; a position wait made them 0 %.
2. The wait cost about 2 ms median in PostgreSQL and MySQL, and a MongoDB causal session cost 1.67 ms for write plus read.
3. Under load the tail grew to 162 ms (PostgreSQL), and a MySQL replica that could not keep up made every wait time out.
4. Bound the wait, fall back to the primary, and count fallbacks.
5. Scope tokens per user, expire them, and drop them after a failover.
