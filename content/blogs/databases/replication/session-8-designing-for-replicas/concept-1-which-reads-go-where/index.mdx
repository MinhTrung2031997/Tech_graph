<Tldr>
Replicas add read capacity and a failover target; they never add freshness. In the capstone runs, a read on the replica **immediately after** a write was stale **99.8 %** of the time on a PostgreSQL standby, **100 %** on a MySQL replica and **98.3 %** on a MongoDB secondary, with all three replicas only milliseconds behind: the read simply arrived before the change was applied. So the design question is not "is the replica fresh?" but "**what may this page show that is a little old?**" Sort every read into one of four classes: **primary** (decisions that move money or stock), **own writes** (the user must see what they just did: a replica with a position wait, or the primary for a while), **bounded staleness** (seconds are fine: dashboards, listings, with a maximum lag), **analytics** (minutes are fine: a separate replica or a CDC copy). The routing rule, not the database, decides which class a read gets.
</Tldr>

## What the earlier sessions measured

| Evidence | Session | Design consequence |
|---|---|---|
| Read right after write: stale 499/500 (PostgreSQL), 300/300 (MySQL), 295/300 (MongoDB); replicas 1–3 ms behind | this session's lab | A replica is always slightly in the past; "immediately" is too soon |
| MongoDB secondary read after a w:1 write: old value 7 of 20 times; delayed replicas stale until the delay passed | [Session 3, Concept 3](/blogs/databases/replication/session-3-replica-lag/concept-3-stale-reads) | Stale reads are normal, not a fault |
| Lag reports mislead: PostgreSQL `replay_lag` frozen at 0.23 s with 15 MB unreplayed; MySQL `Seconds_Behind_Source` 0 with 5 transactions missing | [Session 3, Concept 1](/blogs/databases/replication/session-3-replica-lag/concept-1-measuring-lag) | Route on positions (LSN, GTID, optime), not on reported seconds |
| One secondary 2 minutes behind: 19–23 of 40 reads stale with `secondary` / `secondaryPreferred`; 0 with `maxStalenessSeconds = 90` | [Session 4, Concept 2](/blogs/databases/replication/session-4-read-write-concerns/concept-2-read-preference) | Bounded staleness needs an explicit bound |
| w:1 writes rolled back after failover: 19,333 writes; w:majority writes all kept | [Session 5, Concept 2](/blogs/databases/replication/session-5-failover/concept-2-lost-writes-and-rollback) | A read of an unconfirmed write can show data that later disappears |
| MySQL replica under 1,636 updates/s applied about 1,165/s: about 105,700 transactions behind after 90 s, about 90 s to catch up (laptop shared with other containers) | this session's lab | A read replica can fall behind for minutes under sustained load; routing must notice |

| Term | Meaning |
|---|---|
| Primary read | Read from the server that accepts writes: always current |
| Own-writes read | The user sees at least their own last write: replica + position wait, or primary for N seconds |
| Bounded staleness | Replica allowed if its lag is under a stated limit (e.g. 10 s); otherwise go elsewhere |
| Analytics read | Minutes of lag acceptable; must not disturb the primary or the OLTP replicas |
| **✓ / ✗** | Read allowed here / not allowed |

## The page-by-page table

| Read | Class | Where | Why (evidence) |
|---|---|---|---|
| Stock check that decides an order | 1 | Primary, in the write transaction | Replica stock is old by definition; overselling is a cost (Transactions Session 7) |
| Payment / refund status before acting | 1 | Primary | A refund issued twice is real money |
| Buyer's order page right after checkout | 2 | Replica with LSN/GTID/causal wait, fallback primary | Immediate replica read stale 98–100 % |
| Seller's listing after editing price | 2 | Same | The seller retries the edit if they see the old price |
| Product detail page for buyers | 3 | Replica, lag bound ~10 s | Prices seconds old are acceptable; cached anyway |
| Seller dashboard tiles (today's orders, GMV) | 3 | Replica, bound ~30–60 s | Counts minutes old are normal for dashboards |
| Order search in seller center | 3 or CDC | Replica, or search index fed by CDC | Search index is seconds behind by design (Session 7) |
| Finance export, daily GMV reconciliation | 4 | Analytics replica or warehouse | Long scans; must not touch OLTP |
| Marketplace stock sync (Shopee, Lazada, TikTok Shop) | CDC | Change stream / slot, not polling replicas | Ordered, complete, resumable feed (Session 7) |

<Pitfall>
Do not route by SQL text ("SELECT goes to the replica, everything else to the primary"). The stock check at checkout is a SELECT, and reading it from a replica is how flash sales oversell. Route by **what the read is used for**, which only the application knows: tag queries or use separate connection pools per class.
</Pitfall>

## Real-world scenario: a flash sale at 12:12

At 12:00 traffic is 20× normal. The team adds two read replicas and points "all SELECTs" at them through a proxy. Between 12:00 and 12:05:

| Symptom | Read | Class it needed | Cause |
|---|---|---|---|
| 340 orders accepted for 300 units | stock check | 1 | Replica stock was 0.5–2 s old under load |
| Buyers re-submitting orders | order page after checkout | 2 | New order not on the replica yet |
| Seller dashboard GMV jumping backwards | dashboard tiles | 3 | Proxy alternated between a replica 1 s behind and one 40 s behind |
| Replica 2 falling minutes behind | everything | — | Same as the MySQL lab: apply slower than the write rate |

Fix: class tags in the code, the stock check moved to the primary, own-writes tokens for the order page, a 10 s staleness bound in the proxy, and an alert on replica position lag.

## Key takeaways

1. A replica read right after a write was stale 98–100 % of the time even with millisecond lag.
2. Classify reads by what they decide: primary, own writes, bounded staleness, analytics.
3. Decisions that move money or stock read the primary, inside the write transaction.
4. Own-writes reads carry a position; bounded-staleness reads need an explicit lag bound.
5. Analytics gets its own copy; integrations get a change feed, not a polling replica.
