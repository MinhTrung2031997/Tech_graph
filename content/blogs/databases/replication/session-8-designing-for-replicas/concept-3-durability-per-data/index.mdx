<Tldr>
"Is the write safe?" has three answers: on the primary's disk, on one other server, on a majority. Each step costs a network round trip and buys a smaller loss window at failover. Measured earlier in this course: waiting for a replica **20 ms away** cost **23–26 ms per commit** in PostgreSQL, MySQL and MongoDB ([Session 2](/blogs/databases/replication/session-2-sync-vs-async/concept-4-quorums)); not waiting lost **8,207 and 15,883** acknowledged PostgreSQL commits, **1,615** MySQL transactions and **19,333** MongoDB w:1 writes when the primary failed ([Session 5](/blogs/databases/replication/session-5-failover/concept-3-promoting-postgresql)). The traps are in failure handling: one unreachable synchronous standby **stopped every PostgreSQL commit** (statement_timeout did not help), MySQL semi-sync **silently became asynchronous after 10 s**, MongoDB w:'majority' failed after its `wtimeout` and the primary stepped down. Decide per data class, and use a quorum of **any one of two** replicas so one replica failure costs latency, not availability.
</Tldr>

## The evidence

| Setting | Commit cost (replica 20 ms away) | Loss at failover | When a replica is unreachable | Session |
|---|---|---|---|---|
| PostgreSQL async (`synchronous_commit = local`) | 1.05 ms | 8,207 / 15,883 commits (standby cut off 2 s before the crash) | Nothing changes | [2](/blogs/databases/replication/session-2-sync-vs-async/concept-1-postgresql-synchronous-commit), [5](/blogs/databases/replication/session-5-failover/concept-3-promoting-postgresql) |
| PostgreSQL sync, one standby (`on`) | 26.2 ms | 0 | **Every commit waits indefinitely**; cancel after 122 s: committed locally anyway | 2, 5 |
| PostgreSQL `ANY 1 (s1, s2)` | 23–26 ms; 53–55 ms if the near standby is down | 0 while one standby answers | Uses the other standby | [2](/blogs/databases/replication/session-2-sync-vs-async/concept-4-quorums) |
| MySQL async | 2.5 ms | 1,615 of 2,818 transactions; errant GTIDs | Nothing changes | [5](/blogs/databases/replication/session-5-failover/concept-4-promoting-mysql) |
| MySQL semi-sync (AFTER_SYNC) | 25.0 ms | 0 while semi-sync is active | First commit waits 10 s, then **silently async** | [2](/blogs/databases/replication/session-2-sync-vs-async/concept-2-mysql-semi-sync) |
| MongoDB w:1 | 0.19 ms | 19,333 writes rolled back | Writes succeed; primary steps down when it loses the majority | [2](/blogs/databases/replication/session-2-sync-vs-async/concept-3-mongodb-write-concern), [5](/blogs/databases/replication/session-5-failover/concept-2-lost-writes-and-rollback) |
| MongoDB w:'majority' (default) | 26.7 ms | 0 (all 1,000 kept) | WriteConcernFailed after `wtimeout` (2,017 ms), write stays on the primary | 2, 5 |

| Term | Meaning |
|---|---|
| RPO | Recovery point objective: how much acknowledged data a failover may lose |
| RTO | Recovery time objective: how long writes may be unavailable |
| Quorum commit | Commit waits for k of n replicas (`ANY 1 (s1, s2)`, w:'majority') |
| Data class | Group of tables/collections with the same loss tolerance |
| **✓ / ✗** | Commit acknowledged / waits or fails |

## Durability per data class

| Data | Loss tolerance | Recommended | Why |
|---|---|---|---|
| Orders, payments, refunds, wallet balances | None | Quorum: `ANY 1 (s1, s2)` / semi-sync with 2 replicas / w:'majority' | A lost order or payment is customer-visible and financial |
| Stock movements (reservations, deductions) | None, or reconcilable from orders | Quorum, same transaction as the order | Lost decrements oversell |
| Seller listings, prices | Small; sellers re-save | w:'majority' (MongoDB default) / async acceptable in SQL | Cheap to re-enter, but visible |
| Sessions, carts | Minutes | Async, or a cache | Recreated by the user |
| Clickstream, logs, metrics | Minutes to hours | Async, often a separate store | Volume matters more than every row |
| Derived data (search index, aggregates) | Fully rebuildable | Async or CDC | Rebuild from the source of truth (Session 7) |

PostgreSQL lets one server mix classes: `synchronous_commit` can be set per transaction (`SET LOCAL synchronous_commit = local` for a clickstream insert; from the documentation). MongoDB takes `writeConcern` per operation. MySQL semi-sync is a server-wide setting, so mixing classes means separate servers or accepting the stronger setting for all.

<Pitfall>
"Synchronous with one standby" is the configuration that most often turns a replica problem into an outage: the standby's disk fills, the network blips, and every commit on the primary stops. If you need zero loss, give the primary **two** candidates and wait for **any one** (`synchronous_standby_names = 'ANY 1 (s1, s2)'`, semi-sync with `rpl_semi_sync_source_wait_for_replica_count = 1` and two replicas, or a 3-member MongoDB set with w:'majority'). And know your engine's failure mode: PostgreSQL waits forever, MySQL falls back to async silently (alert on `Rpl_semi_sync_source_status = OFF`), MongoDB fails the write after `wtimeout`.
</Pitfall>

## Failover is the other half

| Engine | Measured failover behaviour | Session |
|---|---|---|
| MongoDB | Clean stepdown in milliseconds; crashed primary noticed after `electionTimeoutMillis`, one write waited 11.4 s; retryable writes hid the failover from the app | [5, Concept 1](/blogs/databases/replication/session-5-failover/concept-1-mongodb-elections) |
| PostgreSQL | No built-in failover; `pg_promote()` 0.14–0.26 s; old primary needs `pg_rewind` or re-clone | [5, Concept 3](/blogs/databases/replication/session-5-failover/concept-3-promoting-postgresql) |
| MySQL | Promotion 0.06–0.08 s; old source's leftovers become errant GTIDs (error 1062 on rejoin) | [5, Concept 4](/blogs/databases/replication/session-5-failover/concept-4-promoting-mysql) |
| All | Two writable primaries after a promotion without fencing | [5, Concept 5](/blogs/databases/replication/session-5-failover/concept-5-split-brain-and-fencing) |

The durability setting decides **what** survives a failover; the failover tooling (Patroni, Orchestrator / MySQL InnoDB Cluster, the MongoDB replica set itself) decides **how long** writes are unavailable and whether the old primary is fenced. A design review needs both numbers per data class: RPO from the commit setting, RTO from the failover mechanism.

## Real-world scenario: one cluster, two durability needs

An OMS database holds orders (no loss allowed) and an `order_events` table that receives 20 tracking updates per order from carriers (rebuildable from carrier APIs). Running everything with one synchronous standby made each tracking insert wait 26 ms and, during a standby maintenance window, stopped checkout.

| Change | Effect |
|---|---|
| Two standbys, `synchronous_standby_names = 'ANY 1 (s1, s2)'` | Standby maintenance no longer stops commits |
| `SET LOCAL synchronous_commit = local` in the tracking-update transactions | Tracking inserts back to about 1 ms; orders still wait for a standby |
| Alert when fewer than 2 standbys are streaming | Know when the quorum has no spare |
| Failover runbook states RPO 0 for orders, up to a few seconds for tracking | Explicit, agreed loss tolerance |

## Key takeaways

1. Waiting for one replica costs about one network round trip (23–26 ms at 20 ms away) and removes the failover loss window.
2. Not waiting lost thousands of acknowledged writes in each engine's failover test.
3. One synchronous standby is a single point of failure for commits; use any one of two.
4. Engines fail differently when the quorum is missing: wait forever, silently go async, or error after a timeout.
5. Set durability per data class; PostgreSQL and MongoDB can do it per transaction or operation.
