<Tldr>
MongoDB fails over by itself: the members of a replica set elect a new primary. How long writes stop depends on **how** the primary went away. A planned `rs.stepDown()` or a clean shutdown (`docker stop`, SIGTERM) asks a caught-up secondary to take over at once: the new primary was elected **9 ms** after the old one refused a write, and no write took longer than **216 ms**. A **crash** (`docker kill`) is only noticed when heartbeats have been missing for `electionTimeoutMillis` (10 s by default): one write **waited 11.4 s**. Whether the application sees an error depends on **retryable writes**, and on the kind of failure. With `retryWrites=true` (the driver default) planned handovers produced **no errors**. Crashes did: in **5 of 10** crash runs one write still failed with `connection … closed`, and in the run where it was checked, that "failed" write **had been stored**. With `retryWrites=false` the write in flight failed on every failover, stepdowns included.
</Tldr>

## The setup

`rpc-mongo1`, `rpc-mongo2`, `rpc-mongo3`: one replica set, default settings (`electionTimeoutMillis` 10000, `heartbeatIntervalMillis` 2000). A client in a fourth container inserts one document at a time with `w: "majority"` for 15–30 s, about 600 writes per second, and records every write slower than 50 ms and every error. Five seconds in, the primary is taken away.

| Term | Meaning |
|---|---|
| Election | Members vote for a new primary; it needs votes from a majority (2 of 3) |
| `electionTimeoutMillis` | How long a secondary waits without hearing from the primary before calling an election (10 s) |
| Step-up request | A primary that is stepping down asks the most caught-up secondary to run for election immediately (`stepUpRequestSkipDryRun`) |
| Retryable write | The driver tags each write with a session and transaction number and retries it **once** on the new primary after a network or "not primary" error; the server applies it at most once |
| **✓ / ✗** | Write succeeded / failed or waited |

## Measured

Each run: 15–30 s of single-document inserts with `w: "majority"`; the primary was removed 5 s in.

| How the primary left | Election reason | `retryWrites` | Failed writes | Slowest write |
|---|---|---|---|---|
| `rs.stepDown(60)` | stepUpRequestSkipDryRun | true | 0 | 117 ms |
| `rs.stepDown(60)` | stepUpRequestSkipDryRun | false | 1 (InterruptedDueToReplStateChange) in one run, 0 in another | 24 ms / 216 ms |
| `docker stop` (SIGTERM) | stepUpRequestSkipDryRun | true | 0 | 134 ms |
| `docker kill` | electionTimeout | true | 0 in 5 of 10 runs; 1 (`connection … closed`) in the other 5 | **5,856–11,395 ms** |
| `docker kill` | electionTimeout | false | 1 (`read ECONNRESET`), document not stored in that run | 10,074 ms (the next write) |

Two more things showed up in the write rate:

- After a crash the set has two of three members, and `w: "majority"` needs **both**: writes went from about 600–650 per second to about 200–400 per second until the third member came back. Every write now waited for the one remaining secondary instead of the faster of two.
- The killed member rejoined as a secondary by itself after `docker start` and caught up from the oplog.

**An error is not a failure.** In one crash run with `retryWrites=true`, write number 3511 returned `connection 1 to 192.168.164.2:27017 closed`. After the failover the collection contained exactly one copy of it. The driver retries a write only once; when that attempt also hits a dead connection, the error reaches the application even though the first attempt may have been applied and replicated. The ECONNRESET write in the `retryWrites=false` run, by contrast, was not stored. Same error class, opposite outcomes.

<Pitfall>
"The driver retries, so failover is invisible" holds only for **retryable** operations: single-document writes, `insertMany`/`bulkWrite` without multi-document updates, and commit of a transaction. `updateMany`/`deleteMany` with `multi: true` and commands like `aggregate` with `$out` are **not** retried (from the documentation). And a retry happens **once**: if the second attempt also finds no primary within `serverSelectionTimeoutMS` (30 s by default), the application gets the error. A crash costs about `electionTimeoutMillis` + a few hundred ms, so lowering that setting shortens the stall but makes elections more likely on a slow network.
</Pitfall>

## Real-world scenario: a checkout during a cloud host failure

The host running the primary of the `orders` replica set dies at 20:00:00 during a flash sale. Checkout writes with `w: "majority"`. The secondaries notice at about 20:00:10 and elect a new primary in milliseconds.

| Application setting | What customers see |
|---|---|
| `retryWrites=true` (driver default), request timeout 30 s | Checkouts in progress pause for up to about 11 s. Most then succeed with no duplicates; a few still get a network error for an order that **was** saved, so the order code must look it up before retrying |
| `retryWrites=false`, no retry in code | Every checkout in flight at 20:00:00 fails with a network error. Some of them may or may not have been written, so the support team gets "I was charged but have no order" tickets |
| `retryWrites=false`, naive retry in code | Same failures, but the retry can create **two** orders when the first write did reach the primary and replicate before the crash |
| Request timeout 5 s at the load balancer | The 11 s pause turns into HTTP 504 errors even though the database recovers by itself |

## Key takeaways

1. A planned stepdown or clean shutdown hands over to a caught-up secondary: the stall was milliseconds.
2. A crash is noticed only after `electionTimeoutMillis` (10 s): one write waited 11.4 s.
3. With retryable writes (the default), planned handovers caused no errors; crashes still returned one error in 5 of 10 runs, for a write that could have been stored. Without them, the write in flight failed on every failover.
4. After a crash, a failed write's outcome is unknown to the client: one checked "failed" write was stored, another was not.
5. With one member of three down, `w: "majority"` writes need every remaining member, and throughput dropped by about half.
