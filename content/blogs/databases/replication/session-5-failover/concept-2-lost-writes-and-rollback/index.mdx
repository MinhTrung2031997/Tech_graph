<Tldr>
A failover can **remove data the old primary had already confirmed**. With the primary cut off from the other two members, it stayed primary for **9.5 s** and confirmed **19,332** writes made with `w: 1`. The other side elected a new primary and carried on. When the old primary reconnected, it found its history had forked, went back to the last common point and **rolled back all 19,333 writes** it had made alone (the `w: 1` writes plus one `w: "majority"` write that had timed out). They were not merged; MongoDB wrote them to a BSON file under `/data/db/rollback/` and left recovering them to you. Writes confirmed with `w: "majority"` are never rolled back: the 1,000 documents written that way before the cut were all still there.
</Tldr>

## The setup

1,000 documents written with `w: "majority"` to collection `lab.r`. Then the primary (`rpc-mongo1`) is disconnected from the Docker network. A script running **on** that node keeps writing to it through `localhost` for 20 s:

1. one insert with `w: "majority", wtimeout: 3000`,
2. then inserts with `w: 1` as fast as possible.

Meanwhile the other two members elect a new primary and take 500 more writes. Then the old primary is reconnected.

| Term | Meaning |
|---|---|
| `w: 1` | Confirmed when the primary alone has applied the write |
| `w: "majority"` | Confirmed when a majority of voting members have it; such a write survives any failover |
| `wtimeout` | How long to wait for the write concern; on timeout the write is **not undone**, the client just stops waiting |
| Rollback | A former primary removes the writes that the new primary never received, back to the last common oplog entry |
| Rollback file | BSON copies of the removed documents, in `<dbpath>/rollback/<collection UUID>/` |
| **✓ / ✗** | Kept / lost |

## Measured

| | Count | Fate |
|---|---|---|
| Written with `w: "majority"` before the cut | 1,000 | ✓ kept |
| `w: "majority"` write on the cut-off primary (WriteConcernFailed after 3,016 ms) | 1 | ✗ rolled back |
| `w: 1` writes confirmed on the cut-off primary in 9,478 ms | 19,332 | ✗ rolled back |
| Written on the new primary | 500 | ✓ kept |
| Documents in `lab.r` after the old primary rejoined | 1,500 | on every member |

A second run gave the same picture: 20,327 `w: 1` writes confirmed in 9,389 ms, the majority write timed out after 3,018 ms, and all 20,328 were rolled back, this time in 0.5 s instead of 9.2 s.

In the first run the rollback directory held one file, `removed.2026-11-24T15-33-17.0.bson` (1,179,307 bytes). `bsondump` printed `19333 objects found`, for example:

```json
{"_id":{"$oid":"6b05ae2489a26a34d6db8519"},"k":"w1-after-cut","i":{"$numberInt":"3613"},"at":{"$date":{"$numberLong":"1795534372227"}}}
```

<Pitfall>
A `w: "majority"` write that **times out** is not a failed write. `wtimeout` only stops the client waiting: the document is on the primary and will be kept if a majority eventually receives it, or rolled back if not. Treat it like a network error (Concept 1, Q3): outcome unknown. And rollback files are never applied automatically; if nobody looks in `/data/db/rollback/` after an incident, the data in them is gone for good.
</Pitfall>

## Real-world scenario: order status updates with `w: 1`

A fulfilment service writes order status changes ("packed", "shipped") with `w: 1` to save a millisecond per write. During a network partition in the data center, the primary in rack A keeps accepting those writes for 10 s while the members in rack B elect a new primary. 3,000 status changes are confirmed to the service and then rolled back.

| What breaks | Why |
|---|---|
| Orders shown as "packed" again after being shipped | The "shipped" updates were rolled back; the service believes they succeeded and never resends them |
| Carrier pickups booked twice | A retry job reads the old status from the new primary and books again |
| Nobody notices for days | The rolled-back documents sit in a BSON file on one server |

| Fix | Effect |
|---|---|
| `w: "majority"` for anything a customer or another system will act on | A confirmed write survives the failover (here: 2 ms median per write on a healthy set) |
| Alert on the log message "Rollback summary" and on files in the rollback directory | Rollbacks become an incident, not a silent loss |
| Keep `w: 1` only for data you can rebuild (counters, caches, logs) | The loss is acceptable by design |

## Key takeaways

1. A primary cut off from the majority keeps accepting `w: 1` writes until it notices, about `electionTimeoutMillis` later: 9.5 s and 19,332 writes here.
2. When it rejoins, every write the new primary does not have is rolled back: all 19,333.
3. Rolled-back documents are saved to `/data/db/rollback/`, never reapplied automatically.
4. Writes confirmed with `w: "majority"` are never rolled back.
5. A `w: "majority"` write that times out has an unknown outcome; here it was rolled back.
