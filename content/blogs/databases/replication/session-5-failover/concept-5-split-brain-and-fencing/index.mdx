<Tldr>
**Split brain** is two servers both accepting writes as primary. It happened as soon as a PostgreSQL standby was promoted while the old primary was still alive behind a network cut: the old primary kept **timeline 1** and accepted client 201's rows, the new one started **timeline 2** and accepted client 202's rows, and nothing in either server noticed. PostgreSQL's documentation says it does "not provide the system software required to identify a failure on the primary and notify the standby database server". **MongoDB** guards against this inside the database: a primary needs to reach a majority to stay primary, and the cut-off one **stepped down by itself after 9.7 s**, **189 ms before** the new primary was elected. That window still allowed `w: 1` writes that were later rolled back (Concept 2). **MySQL** with plain replication behaves like PostgreSQL. The fix is **fencing**: before or while promoting, make sure the old primary cannot accept writes, by shutting it down, cutting it off from clients, or making it read-only.
</Tldr>

## The setup

PostgreSQL: the standby `rpc-pg2` is disconnected from the network and promoted with `pg_promote()`, then reconnected. The old primary `rpc-pg1` was never stopped. Ten rows are inserted on each server.

MongoDB: the run from Concept 2, with the primary cut off from the other two members.

| Term | Meaning |
|---|---|
| Split brain | Two nodes act as primary at the same time and accept writes |
| Fencing | Making a node that should not be primary unable to write: power off, network isolation, read-only, revoked lease |
| STONITH | "Shoot the other node in the head": a fencing method that powers off the old primary through its host or hypervisor |
| Lease | A primary may write only while it holds a lease renewed in a consensus store (etcd, ZooKeeper) or from a majority |
| **✓ / ✗** | Accepts writes / refuses writes |

## MySQL

Plain asynchronous or semi-synchronous replication has no notion of a primary at all; any server with `read_only = 0` accepts writes. In the lab a fresh replica had `read_only = 0` and `super_read_only = 0`, and a single write on it stopped replication with error 1062 (Concept 4). A former source that is restarted after a failover comes back with whatever its configuration file says, which is writable unless `super_read_only` is set there. MySQL Group Replication / InnoDB Cluster adds majority-based membership like MongoDB's (from the documentation; not set up in this lab).

## Fencing options (from the documentation)

| Method | How it fences | Used by |
|---|---|---|
| Leader lease in a consensus store | The primary must renew a key in etcd/Consul/ZooKeeper every few seconds; if it cannot, it demotes itself | Patroni (PostgreSQL) |
| Watchdog | If the demotion does not happen in time, a hardware or software watchdog reboots the node | Patroni with `/dev/watchdog` |
| STONITH | The failover manager powers off the old primary's VM or host before promoting | Pacemaker, cloud failover scripts |
| Majority membership in the database | A node that cannot reach a majority stops being primary | MongoDB replica sets, MySQL Group Replication |
| Read-only by default | Every server starts read-only (`super_read_only = ON`, `default_transaction_read_only` in PostgreSQL); only the failover tool turns writes on | Orchestrator, custom tooling |
| Routing switch | Clients reach the primary only through a proxy or a virtual IP that the failover tool moves | HAProxy, ProxySQL, PgBouncer, cloud load balancers |

<Pitfall>
Moving only the virtual IP or DNS name is not fencing. Connection pools keep existing connections to the old primary, and a batch job with a hard-coded host name keeps writing to it, exactly like "Clients A" in the flow. Fencing has to act on the **server**: stop it, make it read-only, or cut it off from every client. Do it **before** promoting, or accept that some writes will land on the losing side.
</Pitfall>

## Real-world scenario: two primaries for 40 minutes

A home-made failover script on a PostgreSQL pair checks "can the standby reach the primary on port 5432?" every 10 s and promotes after three failures. A network switch between the two racks fails; both servers stay up and reachable from the application servers in their own rack.

| Time | Event |
|---|---|
| 00:00 | Switch fails. The standby cannot reach the primary |
| 00:30 | The script promotes the standby and updates DNS |
| 00:30–40:00 | Application servers in rack A still use the old primary (cached DNS, open pool connections); rack B uses the new one. Orders are written on both |
| 40:00 | Switch replaced. The team finds two diverged databases; one side must be rewound, and its 40 minutes of orders reconciled by hand from its data directory |

What would have prevented it: a lease (Patroni with etcd across three racks), so the old primary demotes itself when it loses the lease, and a quorum of three locations, so a single cut cannot leave both sides believing they are in charge.

## Key takeaways

1. Promoting a PostgreSQL standby does nothing to the old primary: both accepted writes, on timelines 1 and 2.
2. MySQL's plain replication is the same; servers are writable unless configured otherwise.
3. MongoDB requires a majority to stay primary: the cut-off primary stepped down after 9.7 s, before the new one was elected.
4. Fencing, making the old primary unable to write, must come from the failover tooling: leases, watchdogs, STONITH, read-only defaults.
5. Moving a VIP or DNS name is routing, not fencing.
