<Tldr>
Asynchronous replication means a replica answers from its own past: a committed write is visible on the primary at once and on a replica only after it has been received **and applied**. Even a tiny lag is visible to a user who writes and then reads: on a healthy MongoDB set, a read on a secondary immediately after a `w: 1` update returned the **old value 7 times out of 20**, although the median time until the secondary had it was 1.04 ms. With a lag of seconds, every such read is stale: replicas delayed by 5 s returned the old status on all reads right after the write in **PostgreSQL** (new value visible after about 5.0 s) and **MySQL**, and a MongoDB member delayed 10 s showed the new value after **10.02–10.22 s** while `w: "majority"` writes were acknowledged in 3–12 ms. Stale reads do not throw errors; they look like lost updates.
</Tldr>

## What "stale" means

| Term | Meaning |
|---|---|
| Stale read | A read that returns a value older than one already committed and acknowledged |
| Read-your-writes | A client sees its own acknowledged writes in later reads (Concept 4) |
| Monotonic reads | A client never sees data go backwards between two reads (broken when consecutive reads hit replicas with different lag) |
| Delayed replica | A replica configured to apply changes only after N seconds (used here to make lag reproducible) |
| **✓ / ✗** | The read returns the new value / the old value |

The experiment is the same in every engine: flip the status of one order on the primary, read it from a replica immediately, then poll the replica until the new value appears.

MongoDB drivers never send reads to a delayed member: in MongoDB 8.0 the primary's `hello` response listed only `rpb-mongo1` and `rpb-mongo2` while `rpb-mongo3` had a delay, so the lab read it over a direct connection. A secondary that is merely slow is a normal read target; Session 4 shows how often a driver picked a 2-minute-old secondary.

## Comparison

| | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Healthy replica, read about 50 ms after the write | ✓ 9 of 9 | ✓ (GTID wait 0 ms) | — |
| Healthy replica, read immediately | — | — | ✗ 7 of 20 stale, visible after 1.04 ms |
| Replica 5–10 s behind, read immediately | ✗ every time | ✗ every time | ✗ every time |
| New value visible after | about 5.0 s (delay 5 s) | 5.56–5.63 s (delay 5 s) | 10.02–10.22 s (delay 10 s) |
| Error on a stale read | none | none | none |

<Pitfall>
Stale reads are silent and look like the application lost the write. A seller edits a price, the page reloads from a replica 200 ms behind and shows the old price, the seller edits it again, and support receives "your system doesn't save my changes". Before routing a read to a replica, decide whether that read may be stale: catalogue browsing usually may; the page shown right after a write, payment status, and anything used to decide a write (stock, balance) may not.
</Pitfall>

## Real-world scenario: "My orders" is empty after checkout

A marketplace serves "My orders" from MongoDB secondaries with `readPreference: secondaryPreferred` to offload the primary. On a normal day the secondaries are milliseconds behind and nobody notices. During a flash sale, one secondary falls 8 seconds behind. Buyers who pay and are redirected to "My orders" see an empty list about half the time (one secondary of two), and many pay a second time.

| Fix | Effect |
|---|---|
| Read the order page from the primary for the session's next N seconds after a write | Read-your-writes for the buyer; replicas still serve browsing |
| Pass the write's position and wait for it on the replica (Concept 4) | Fresh read from a replica, bounded wait |
| Causally consistent session (Session 4) | MongoDB waits on the secondary automatically |
| `maxStalenessSeconds` (Session 4) | Excludes the 8 s-old secondary from reads, at 90 s minimum granularity |

## Key takeaways

1. A replica returns data as of its last applied change; a read inside the lag window returns the old value with no error.
2. Even 1 ms of lag matters when the read follows the write at once: 7 of 20 reads were stale on a healthy MongoDB set.
3. With seconds of lag, every read right after a write is stale (PostgreSQL and MySQL delayed 5 s, MongoDB delayed 10 s).
4. `w: "majority"` acknowledgement does not make every secondary fresh; only `w` equal to the member count does.
5. Decide per read whether it may be stale; pages shown right after a write and inputs to later writes usually may not.
