<Tldr>
Carry the write's position to the read, wait briefly, and fall back to the primary. Make writes wait for replicas only when every reader everywhere must be fresh.
</Tldr>

## Q1. Which LSN to pass

**Question:** which LSN should the PostgreSQL writer pass to the reader, and why not `pg_current_wal_lsn()` from another connection?

`pg_current_wal_insert_lsn()` read in the writer's own session right after COMMIT: it is at or past the end of that transaction's commit record, so a standby that has replayed up to it has the write. `pg_current_wal_lsn()` is the position already written to the OS, which can be slightly behind the insert position; and any LSN read from another connection is either earlier (you would wait for too little) or includes other sessions' work (you wait for more than needed). The write position belongs to the session that wrote.

> **Common mistake:** waiting on `pg_last_wal_receive_lsn()`. Received is not replayed; a read can still miss the row.

## Q2. Short limit and fallback

**Question:** why is a short limit plus a primary fallback better than waiting until the replica catches up?

The wait is spent by the user. With a standby 5 s behind, waiting it out took 4.93–4.96 s per read; with a 200 ms limit the function gave up after 206–217 ms and the read went to the primary, which has the write by definition. When replicas are healthy the wait costs about 1 ms and the primary gets no extra load; when they are behind, the primary takes only the reads that need freshness.

> **Common mistake:** no fallback, so a lagging replica turns into multi-second page loads for exactly the users who just did something.

## Q3. A cancelled wait

**Question:** why can a long wait on a busy standby be cancelled, and what error did the lab see?

The wait runs as a query on the standby and holds a snapshot. If replay reaches WAL that removes row versions that snapshot could still need (vacuum or pruning on the primary), the startup process waits up to `max_standby_streaming_delay` (30 s) and then cancels the query. While the standby replayed a 200 MB backlog, a waiting call was cancelled after about 14 s with `ERROR: canceling statement due to conflict with recovery` / `DETAIL: User query might have needed to see row versions that must be removed.` The backlog WAL was already old when replay resumed, so little of the 30 s was left. Short waits rarely hit this; long ones on busy standbys do (Session 6).

> **Common mistake:** retrying the same long wait in a loop. Fall back to the primary instead.

## Q4. WAIT_FOR_EXECUTED_GTID_SET on timeout

**Question:** what does `WAIT_FOR_EXECUTED_GTID_SET` return on timeout, and what must the caller do?

It returns 1 (0 means the set has been applied); it does not raise an error. In the lab it returned 1 after 201–203 ms with a 0.2 s limit. The caller must test the return value and read from the source when it is 1. A caller that ignores the value reads stale data exactly when the replica is behind.

> **Common mistake:** calling it without a timeout. Without one it waits indefinitely (from the documentation), so a stopped replica hangs every request that uses it.

## Q5. WriteConcernFailed and retries

**Question:** a `w: 3` write failed with WriteConcernFailed. Is the data written? What should the retry look like?

Yes, on the primary at least: in the lab the order changed to "cancelled" and the primary read it back after the error. WriteConcernFailed means "not confirmed on enough members within wtimeout", not "not done". The write will usually reach the other members once they recover; it could also be rolled back if the primary fails before a majority has it (Session 4 and Session 5). A retry must therefore be idempotent: `$set` to a target value is; `$inc` or an insert without a unique key is not.

> **Common mistake:** retrying `$inc: { stock: -1 }` after a write-concern error and decrementing twice.

## Q6. remote_apply vs a read-side wait

**Question:** compare the cost of `synchronous_commit = remote_apply` with a read-side wait when one replica is 5 s behind.

With `remote_apply`, every commit on the primary waits for the standby to apply it: 5,003–5,011 ms per single-row commit in the lab, for every writer, whether or not anyone reads the replica. With a read-side wait, writers commit in milliseconds; only reads that carry a position and go to that replica wait, and with a 200 ms limit they fall back to the primary. Write-side synchronous apply suits a small number of critical writes with immediate replica reads; read-side waits suit everything else.

> **Common mistake:** enabling `remote_apply` globally to fix one page's stale read.
