<Tldr>
Read-your-writes on replicas needs one of three things. **Route** the user's reads to the primary for a short time after they write: always correct, costs primary capacity. **Wait** on the replica until it has applied the write's position, with a time limit and a fallback to the primary: PostgreSQL 17 has no built-in wait (no `pg_wal_replay_wait`), so the lab used a small `wait_for_lsn()` function: **1 ms** on a healthy standby, **4.93–4.96 s** on a standby 5 s behind, or `false` after **206–217 ms** with a 200 ms limit. MySQL's `WAIT_FOR_EXECUTED_GTID_SET` gave 0 ms, 5.56–5.63 s, or a timeout after 201–203 ms. **Make the write wait** until every replica has it: MongoDB `w: 3` took 2.25 ms instead of 0.51 ms on a healthy set, **10.0 s** with a member delayed 10 s, and with a frozen member failed with `WriteConcernFailed` after 2015 ms **while the write stayed on the primary**. PostgreSQL's equivalent, `synchronous_commit = remote_apply`, made commits take 5.0 s against a standby 5 s behind. MongoDB's causally consistent sessions do the waiting automatically (Session 4).
</Tldr>

## Three strategies

| Term | Meaning |
|---|---|
| Position | Where the write is in the log: PostgreSQL LSN, MySQL GTID set, MongoDB operationTime |
| Wait-for-position | Before reading on a replica, wait until it has applied at least that position |
| Sticky primary | Send a user's reads to the primary for N seconds after their last write |
| Fallback | If the wait times out, read from the primary instead of returning stale data |
| **✓ / ✗** | Caught up within the limit / gave up |

| Strategy | Who waits | Fresh guaranteed | Cost |
|---|---|---|---|
| Sticky primary | nobody | yes | primary load for recent writers |
| Wait-for-position on the replica | the reader, bounded by a timeout | yes (or falls back) | position must travel from writer to reader |
| Synchronous apply on every replica | the writer, on every write | yes | every write pays the slowest replica |

## PostgreSQL

PostgreSQL 17 has no function that waits for replay (checked: `pg_proc` has only `pg_last_wal_replay_lsn`, `pg_wal_replay_pause/resume`, `pg_is_wal_replay_paused`, `pg_get_wal_replay_pause_state`). A plain PL/pgSQL loop does the job:

```sql
-- Created on the primary; replicated to the standby like any function.
CREATE OR REPLACE FUNCTION wait_for_lsn(target pg_lsn, timeout_ms int DEFAULT 1000) RETURNS boolean
LANGUAGE plpgsql AS $$
DECLARE deadline timestamptz := clock_timestamp() + timeout_ms * interval '1 millisecond';
BEGIN
  IF NOT pg_is_in_recovery() THEN RETURN true; END IF;     -- on a primary there is nothing to wait for
  WHILE pg_last_wal_replay_lsn() < target LOOP
    IF clock_timestamp() > deadline THEN RETURN false; END IF;
    PERFORM pg_sleep(0.005);
  END LOOP;
  RETURN true;
END $$;
```

The writer captures the position right after its commit, in the same session: `SELECT pg_current_wal_insert_lsn();` (at or after the commit record).

The alternative is to make the **writer** wait: with `synchronous_standby_names = 'walreceiver'` and `SET synchronous_commit = remote_apply`, COMMIT returns only after the standby has applied the commit. Against the 5 s-delayed standby, single-row commits took **5,003–5,011 ms** and the standby read right after returned the new value; with `on` (flush only) commits took 2.7–5.8 ms and the standby read was stale. Session 4 compares the levels.

## MySQL InnoDB

```sql
-- On the source, after COMMIT: a GTID set that contains the write
SELECT @@global.gtid_executed;
-- On the replica: 0 = applied, 1 = timeout (seconds, fractions allowed)
SELECT WAIT_FOR_EXECUTED_GTID_SET('<that set>', 0.2);
```

`@@global.gtid_executed` contains every transaction the source has executed, so the replica waits for a little more than necessary. To wait for exactly your own transaction, set `session_track_gtids = OWN_GTID` and read the GTID the server returns with the OK packet (a driver feature; from the documentation, not used in the lab).

The read-side option in MongoDB is a causally consistent session: the driver carries the write's `operationTime` to the next read and the secondary waits for it, like `wait_for_lsn` above but built in. Session 4 measures it.

## Comparison

| | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Position to carry | LSN: `pg_current_wal_insert_lsn()` | GTID set: `@@global.gtid_executed` or `OWN_GTID` | `operationTime` (session) |
| Built-in wait on the replica | none in 17 (own loop) | `WAIT_FOR_EXECUTED_GTID_SET(set, timeout)` | causal session (Session 4) |
| Healthy replica, wait | 1 ms | 0 ms | — |
| Replica 5 s behind, short limit | false after 206–217 ms | 1 after 201–203 ms | — |
| Make the writer wait | `remote_apply`: 5.0 s commit at 5 s lag | semi-sync waits for receipt, not apply (Session 2) | `w: 3`: 2.25 ms healthy, 10.0 s delayed, error when frozen |

<Pitfall>
A write-side guarantee turns one slow replica into a slow (or failing) write path for everyone: `w: 3` took 10 s per write with one delayed member and failed outright with a frozen one, and `remote_apply` commits took 5 s. Prefer read-side waits with a short limit and a primary fallback; they only slow the reads that need freshness, and only while a replica is behind.
</Pitfall>

## Real-world scenario: the seller edits a listing

A seller saves a new price; the next page view should show it. The application tags the seller's session with the write's position (PostgreSQL LSN or MySQL GTID set) for 30 seconds. Reads for that session go to a replica with "wait up to 100 ms for this position, else read from the primary". Other users' reads of the same listing go to replicas without waiting: a buyer seeing the old price for a second is acceptable, a seller seeing their own edit disappear is not.

| Decision | Reason |
|---|---|
| Only the writer's session carries the position | Read-your-writes is per user; global freshness would need synchronous replication |
| Limit 100 ms, then primary | Bounded latency; primary load only while replicas lag |
| Expire the position after 30 s | After that, normal lag (milliseconds) is far below it |

## Key takeaways

1. Read-your-writes on replicas: route to the primary after a write, wait for the write's position on the replica, or make the write wait for every replica.
2. PostgreSQL 17 has no built-in replay wait; a loop on `pg_last_wal_replay_lsn()` with a limit works (1 ms healthy, false after about 0.2 s when 5 s behind).
3. MySQL's `WAIT_FOR_EXECUTED_GTID_SET` returns 0 or 1; check it and fall back.
4. MongoDB `w: <all members>` costs little when healthy (2.25 ms vs 0.51 ms) but makes every write wait for the slowest member (10 s) or fail.
5. A write-concern timeout is not a rollback: the write stayed on the primary.
