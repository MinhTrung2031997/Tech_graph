<Tldr>
Applying changes is cheaper than producing them: the standby replayed **192–205 MB of WAL in 0.60–0.67 s**, three times faster than the primary generated it, because replay does no query work. So steady-state lag is small; lag comes from the replica being **stopped**. Three kinds of stop were measured. **Not receiving**: a frozen PostgreSQL standby left 9.9 MB in the slot after 70 s and caught up in about 0.1 s once unfrozen; a MySQL replica that lost the network caught up only 28 s after the network came back, because the I/O thread retries every 60 s. **Not applying**: one row locked by `SELECT … FOR UPDATE` on the MySQL replica blocked the applier for 20 s, and with `replica_preserve_commit_order = 1` five unrelated transactions waited behind it ("Waiting for preceding transaction to commit"), `Seconds_Behind_Source` 1 → 17. A MongoDB secondary under `fsyncLock` fell 30 s behind while `w: "majority"` writes still succeeded through the other secondary. **Delayed on purpose**: `recovery_min_apply_delay`, `SOURCE_DELAY`, `secondaryDelaySecs`.
</Tldr>

## Producing vs applying

| Term | Meaning |
|---|---|
| Receive | The replica gets the log over the network (PostgreSQL walreceiver, MySQL I/O thread, MongoDB oplog fetcher) |
| Apply / replay | The replica changes its data from the log (PostgreSQL startup process, MySQL applier workers, MongoDB oplog applier) |
| Backlog | Log received but not yet applied, or not yet received |
| **✓ / ✗** | The step runs / is stopped |

| Workload | Primary / source | Replica |
|---|---|---|
| PostgreSQL: 8 × UPDATE of 100,000 rows, 192–205 MB WAL, replay paused then resumed | 1.95 s to generate | **0.60–0.67 s** to replay the backlog (3 runs) |
| PostgreSQL: one UPDATE of 100,000 rows, 25 MB WAL | 0.21–0.31 s | replayed 43–92 ms after the commit returned (`replay_lag`) |
| MySQL: one transaction, 3 × UPDATE of 100,000 rows | 514 ms | applied in 0.87 s, starting 25 ms after the source commit |
| MongoDB: single-document update, w:1 | 0.51 ms ack | visible on a secondary after 1.04 ms (median of 20) |

Two consequences. A replica on equal hardware keeps up with normal traffic, so if it is behind, look for something that **stopped** it. And a replica applies a transaction only after the source commits it: a statement that runs for an hour on the source arrives as a one-hour job on the replica, and the replica is behind by at least that long while it applies it (MySQL also applies row events serially within one transaction).

Something else stops replay on a busy standby: a query that needs row versions the WAL wants to remove. While measuring, a polling query on the standby was cancelled with `ERROR: canceling statement due to conflict with recovery` / `DETAIL: User query might have needed to see row versions that must be removed.` Replay waits up to `max_standby_streaming_delay` (30 s here) for such queries before cancelling them; that wait is lag (Session 6 covers it).

## Comparison

| Cause | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Replica not receiving | slot keeps WAL on the primary; caught up in about 0.1 s | reconnect waits for `Connect_Retry` (60 s): 28 s here | (not measured) |
| Replica not applying | replay paused or waiting on a query conflict | applier blocked by a replica-side lock; commit order makes others wait | `fsyncLock`, or a slow disk |
| Big transaction | replayed after commit (25 MB: 43–92 ms) | applied after commit, row events in order (300k rows: 0.87 s) | many oplog entries, applied in batches (from the documentation) |
| Delayed on purpose | `recovery_min_apply_delay` | `SOURCE_DELAY` | `secondaryDelaySecs` (priority 0) |

<Pitfall>
Pointing reporting or "read-only" application traffic at a replica is not free: on MySQL a single `SELECT … FOR UPDATE` held for 20 s on the replica made it 17 s stale for **everyone**, because the applier waited for the row and the other workers waited for commit order. In PostgreSQL a long query on a standby makes replay wait up to `max_standby_streaming_delay` (Session 6). Treat the replica's own workload as a cause of lag.
</Pitfall>

## Real-world scenario: the 2 a.m. backfill

A data team backfills `seller_id` on 50 million orders with one `UPDATE` at 02:00. On the source it runs 40 minutes. Nothing reaches the MySQL replicas until it commits at 02:40; then the replicas spend a similar time applying it (in the lab, 300,000 rows took 0.51 s on the source and 0.87 s on the replica), while every order placed after 02:40 queues behind it. From 02:40 the product pages served from replicas show data that is up to 40 minutes old.

| Fix | Effect |
|---|---|
| Backfill in batches of a few thousand rows, committed separately | The replica applies small transactions interleaved with normal traffic |
| Throttle on measured position lag (stop when the replica is more than N transactions behind) | Lag stays bounded |
| Run the backfill when replica reads can go to the primary | Stale reads are not visible |

## Key takeaways

1. Applying is cheaper than producing: 192–205 MB of WAL replayed in 0.60–0.67 s. If a replica is behind, something stopped it.
2. A frozen PostgreSQL standby leaves the backlog in the primary's slot; catch-up took about 0.1 s.
3. A MySQL replica that loses the network can stay behind for up to `Connect_Retry` (60 s) after the network returns.
4. One row lock on a MySQL replica stopped every later transaction because of commit ordering: SBS 17 s after 20 s.
5. In MongoDB a frozen or delayed member does not slow majority writes; it only serves stale data.
