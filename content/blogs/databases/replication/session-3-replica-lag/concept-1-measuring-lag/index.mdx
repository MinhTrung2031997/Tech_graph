<Tldr>
Lag has two units: **how much** has not been applied (bytes, transactions, oplog entries) and **how old** the replica's data is (seconds). The seconds are easier to read and easier to get wrong. In the lab, **PostgreSQL**'s `replay_lag` is refreshed only when the standby sends a reply: it showed 0.23 s while 15 MB of WAL sat unreplayed, and **NULL** for 50 s while the standby was frozen (the row still said `streaming`). `now() − pg_last_xact_replay_timestamp()` read 42.7 s on a standby that was 0 bytes behind. **MySQL**'s `Seconds_Behind_Source` stayed **0** with `Replica_IO_Running: Yes` for 40–50 s after the replica lost the network, while 5 transactions were missing. **MongoDB**'s `rs.status()` showed a healthy secondary 2–3 s behind right after a write (the primary's view comes from heartbeats), and 0 a second later. Trust the counters that compare **positions**: LSN difference, `GTID_SUBTRACT`, optimes, and alert on both units.
</Tldr>

## Two units of lag

| Term | Meaning |
|---|---|
| Position lag | How much log the replica has not applied: WAL bytes (LSN difference), GTIDs not executed, oplog entries |
| Time lag | How old the newest data on the replica is, in seconds |
| write / flush / replay | PostgreSQL's three steps on the standby: WAL written to the OS, flushed to disk, applied to data |
| Heartbeat view | What one node believes about another, refreshed by periodic messages (MongoDB heartbeats every 2 s, PostgreSQL standby replies on new WAL or every `wal_receiver_status_interval` = 10 s) |
| **✓ / ✗** | The reading matches reality / misleads |

Time lag is what users feel ("my edit is not there"). Position lag is what you can measure without clocks. Every time-lag number below is computed from some message, and is only as fresh as the last message.

## PostgreSQL

Lab: primary `rpb-pg1`, standby `rpb-pg2` (streaming, slot `standby1`), table `orders` with 100,000 rows. Three readings were compared on the primary and the standby:

```sql
-- On the primary: what the standby last reported, and the byte distance
SELECT write_lag, flush_lag, replay_lag,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS bytes_behind
FROM pg_stat_replication;
-- On the standby: the "naive" lag many dashboards use
SELECT now() - pg_last_xact_replay_timestamp();
```

## MySQL InnoDB

Lab: source `rpb-my1`, replica `rpb-my2` (GTID auto-position, 4 parallel workers, `replica_preserve_commit_order = 1`), database `shop`.

```sql
-- The precise per-transaction lag (MySQL 8.0+), on the replica
SELECT LAST_APPLIED_TRANSACTION,
       TIMESTAMPDIFF(MICROSECOND, LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
                     LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP) / 1000 AS lag_ms
FROM performance_schema.replication_applier_status_by_worker
ORDER BY LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP DESC LIMIT 1;
-- What the replica is missing: run on the replica with the source's gtid_executed pasted in
SELECT GTID_SUBTRACT('<source @@global.gtid_executed>', @@global.gtid_executed);
```

## Comparison

| | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Position lag (trust this) | `pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)` | `GTID_SUBTRACT(source set, replica set)` | optime difference |
| Built-in time lag | `replay_lag`: refreshed only on standby replies, NULL when idle or frozen | `Seconds_Behind_Source`: 0 when the I/O thread silently stalls | `rs.status()`: heartbeat view, 1 s units |
| Exact per-transaction delay | not built in | `replication_applier_status_by_worker` timestamps | measure a write-then-read |
| Dead replica looks like | "streaming", NULL lags, then the row disappears after 60 s | "Yes", 0 s, then "Connecting", NULL | lag grows every 10 s (no-op) |

<Pitfall>
An alert on "lag above 30 s" built on `replay_lag` or `Seconds_Behind_Source` stays green for a dead replica: NULL is not above 30, and neither is 0. Alert on the position (bytes, missing GTIDs) **and** on the replica being absent or not running, and treat NULL as a failure, not as zero. For PostgreSQL also alert on `pg_replication_slots` retained WAL: a slot whose standby is gone keeps WAL on the primary's disk until it fills.
</Pitfall>

## Real-world scenario: the dashboard that said 0

A marketplace runs product pages from a MySQL replica. The monitoring graph is `Seconds_Behind_Source`. A switch reboots and the replica's connection to the source goes silent. For a minute the graph shows 0, sellers' price changes stop appearing on product pages, and support tickets start. Then the graph shows a gap (NULL), which the alert rule ignores. The replica reconnects 60 s later on its own retry interval.

| Fix | Effect |
|---|---|
| Alert on missing GTIDs from a probe that reads both servers | Catches the silent stall within one probe interval |
| Alert when `Replica_IO_Running` ≠ Yes or SBS is NULL | Catches the reconnect phase |
| Lower `replica_net_timeout` / heartbeat period | The I/O thread notices a dead connection sooner (from the documentation; not measured) |
| A heartbeat table written every second on the source, read on the replica | Time lag from your own clock, independent of engine counters |

## Key takeaways

1. Lag has two units: position (bytes, GTIDs, optimes) and time (seconds). Time readings are computed from messages and are only as fresh as the last message.
2. PostgreSQL's `replay_lag` is NULL both for an idle standby and a frozen one; `now() − pg_last_xact_replay_timestamp()` grows on an idle primary.
3. MySQL's `Seconds_Behind_Source` stayed 0 for 40–50 s with 5 transactions missing after a network cut; GTIDs showed the truth.
4. MongoDB's `rs.status()` is the primary's heartbeat view: off by 2–3 s right after a write, accurate over longer periods because of the 10 s no-op.
5. Alert on position lag and on the replica's presence, and treat NULL as an outage.
