<Tldr>
One synchronous replica turns that replica into a single point of failure for writes. With **two** replicas and a commit that waits for **any one**, the nearest healthy replica sets the latency and one outage costs latency instead of availability. Measured with replicas **20 ms** and **50 ms** away: wait-for-any-one took **22.8–25.5 ms** (PostgreSQL `ANY 1 (s1, s2)`), **26.3 ms** (MySQL `wait_for_replica_count = 1`) and **23.5–26.7 ms** (MongoDB `w: "majority"` on 3 members). With the near replica paused, the same settings took **53.4 ms**, **55.5 ms** and **53.2 ms**: the far replica answered, nothing hung and nothing fell back to async. Waiting for both took **57.5 ms**, **55.7 ms** and **55.3 ms**. PostgreSQL's `FIRST 1 (s2, s1)` waits for the first **listed** healthy standby, here the far one: **55.7 ms**.
</Tldr>

## The numbers

Single-row commits, replicas delayed 20 ms ("near") and 50 ms ("far") with `netem`, medians of 3 runs (PostgreSQL pgbench 5 s, MySQL 300 commits, MongoDB 300 inserts).

| Wait for | PostgreSQL | MySQL semi-sync | MongoDB |
|---|---|---|---|
| Nothing (async / `local` / `w: 1`) | 1.05 ms | 2.24 ms | 0.19 ms |
| Any 1 of 2, both up | 22.8–25.5 ms `ANY 1 (s1, s2)` | 26.3 ms `count = 1` | 23.5–26.7 ms `"majority"` |
| Any 1 of 2, near one down | 53.4 ms | 55.5 ms | 53.2 ms |
| A fixed one (listed first) | 55.7 ms `FIRST 1 (s2, s1)` | n/a | n/a |
| Both | 57.5 ms `ANY 2 (s1, s2)` | 55.7 ms `count = 2` | 55.3 ms `w: 3` |

| Term | Meaning |
|---|---|
| Quorum commit | Wait for any k of n replicas; the k-th fastest decides latency |
| Priority commit | PostgreSQL `FIRST k (…)`: the first k healthy standbys **in list order** are synchronous, the rest are potential |
| Majority | MongoDB: more than half of the voting members, counting the primary |
| **✓ / ✗** | Acknowledged before the commit returns / not waited for |

## When no quorum is possible

| | PostgreSQL | MySQL semi-sync | MongoDB |
|---|---|---|---|
| Commit when required replicas are down | Waits without limit (`SyncRep`) | Waits `rpl_semi_sync_source_timeout` (10 s) once, then async | Waits until `wtimeout`, error `WriteConcernFailed`, write kept |
| Primary keeps accepting writes | Yes, but they all hang | Yes, unprotected | No: steps down after ~10 s without a majority |
| A cancelled or timed-out commit | Committed locally | Committed (async) | Written on the primary, outcome unknown |

<Pitfall>
`FIRST 1 (s2, s1)` and `ANY 1 (s1, s2)` look alike and behave differently. With FIRST, the list order picks the synchronous standby: here every commit waited for the far standby (55.7 ms) while the near one was idle as "potential". Use `ANY` when any standby is an acceptable copy; use `FIRST` only when one standby must be preferred, for example the one in the failover zone.
</Pitfall>

## Real-world scenario: two zones, three replicas

An order database runs in one primary zone with one replica in the same zone (1 ms away) and one in a second zone (8 ms away). Waiting for "any one" will nearly always be satisfied by the same-zone replica, so commits stay fast, but a zone outage takes both the primary and the replica that acknowledged most commits. If the requirement is "a committed order survives the loss of a zone", the acknowledgement must come from the other zone: `FIRST 1 (zone_b_standby, zone_a_standby)` in PostgreSQL, a write concern with tag sets in MongoDB (custom `getLastErrorModes`, from the documentation), and in MySQL a semi-sync replica placed only in the other zone. The price is the cross-zone round trip on every commit, which these measurements show is the whole cost.

## Key takeaways

1. Waiting for any one of two replicas cost the near replica's round trip: 23–26 ms in all three engines at 20 ms.
2. With the near replica down, the far one answered (53–55 ms): one outage costs latency, not availability.
3. Waiting for all replicas costs the slowest round trip (55–57 ms) and makes every replica critical.
4. PostgreSQL's `FIRST` follows list order, not speed.
5. When no quorum is possible, PostgreSQL waits, MySQL falls back to async, MongoDB errors per write and the primary steps down.
