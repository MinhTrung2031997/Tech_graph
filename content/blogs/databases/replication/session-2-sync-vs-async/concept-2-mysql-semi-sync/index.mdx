<Tldr>
MySQL replication is asynchronous unless you load the **semisync** plugins. Then a commit waits until a replica confirms it has the transaction **in its relay log** (received and written, not applied). With 20 ms of delay to the replica, single-row commits took **2.5 ms** async and **25.0 ms** semi-sync (2.3 vs 2.4 ms without delay). The wait point matters: with **AFTER_SYNC** (default) the row stays invisible to other sessions until the replica acknowledges; with **AFTER_COMMIT** another session saw it during the wait, so a reader could see a row that a failover then loses. Semi-sync has a **timeout**: with the replica paused, the first commit waited **10.04 s** (`rpl_semi_sync_source_timeout = 10000`), then the source switched to **asynchronous** (`Rpl_semi_sync_source_status = OFF`) and the next commits took **0.09 s** and **0.06 s**, with only an error-log line to show for it. It switched back on as soon as the replica reconnected.
</Tldr>

## Turning it on

```sql
-- source
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SET GLOBAL rpl_semi_sync_source_enabled = ON;
-- each replica
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';
SET GLOBAL rpl_semi_sync_replica_enabled = ON;
STOP REPLICA IO_THREAD; START REPLICA IO_THREAD;   -- reconnect as a semi-sync replica
```

On the source: `Rpl_semi_sync_source_clients = 1`, `Rpl_semi_sync_source_status = ON`; defaults `rpl_semi_sync_source_timeout = 10000` (ms), `rpl_semi_sync_source_wait_for_replica_count = 1`, `rpl_semi_sync_source_wait_point = AFTER_SYNC`.

| Setup (single-row autocommit INSERT, median of 3 × 300) | Commit time |
|---|---|
| Async, no delay | 2.31 ms |
| Semi-sync, no delay | 2.43 ms |
| Async, replica +20 ms | 2.53 ms |
| Semi-sync AFTER_SYNC, replica +20 ms | 24.95 ms |
| Semi-sync AFTER_COMMIT, replica +20 ms | 25.98 ms |

| Term | Meaning |
|---|---|
| Semi-sync ACK | The replica's I/O thread acknowledges after writing the events to its relay log |
| AFTER_SYNC | Wait for the ACK after the binlog is flushed, **before** the storage engine commit (row invisible meanwhile) |
| AFTER_COMMIT | Wait for the ACK **after** the storage engine commit (row already visible to others) |
| Fallback | After `rpl_semi_sync_source_timeout` without an ACK the source continues asynchronously |
| **✓ / ✗** | Done / waiting or skipped |

<Pitfall>
Semi-sync's default is to fail open. After 10 s without an acknowledgement the source keeps committing asynchronously, and the commits made in that window (`Rpl_semi_sync_source_no_tx`) exist only on the source. If the source dies during that window, promoting the replica loses them, even though "semi-sync is enabled". Alert on `Rpl_semi_sync_source_status = OFF`. If you would rather stop than lose commits, raise `rpl_semi_sync_source_timeout` to a very large value, which turns a replica outage into a write outage, like PostgreSQL's synchronous standby (Concept 1).
</Pitfall>

## What the ACK means

The replica acknowledges after its I/O thread has **written the events to the relay log** (from the documentation: written and flushed to the relay log), not after applying them. So semi-sync gives:

| Guarantee | Semi-sync AFTER_SYNC |
|---|---|
| A committed transaction is on at least one replica | ✓ (while status = ON) |
| It is visible to queries on the replica | ✗ the applier may be behind |
| Others saw it only after a replica had it | ✓ (✗ with AFTER_COMMIT) |
| Commits continue when every replica is down | ✓ after the timeout, unprotected |

## Real-world scenario: "semi-sync" that was off for a week

A payment service runs MySQL with semi-sync to one replica in another zone. A network change raises the round trip above normal for a few seconds, one commit hits the 10-second timeout, and the source falls back to async. The replica reconnects and semi-sync comes back, but a second incident a week later leaves a replica with a broken relay log, and semi-sync stays OFF for days. When the source's disk fails, the newest transactions are only on the dead source. Fixes: two semi-sync replicas with `wait_for_replica_count = 1` (Concept 4), monitoring of `Rpl_semi_sync_source_status` and `Rpl_semi_sync_source_no_tx`, and a deliberate choice of `rpl_semi_sync_source_timeout` rather than the default.

## Key takeaways

1. Semi-sync makes a commit wait for one replica's relay-log write: 25 ms instead of 2.5 ms with 20 ms of delay.
2. AFTER_SYNC (default) hides the row until the ACK; AFTER_COMMIT lets others see it first.
3. The ACK means "received", not "applied": reads on the replica can still be stale.
4. After `rpl_semi_sync_source_timeout` (10 s) without an ACK the source silently becomes asynchronous; it turns semi-sync back on when a replica reconnects.
5. Monitor `Rpl_semi_sync_source_status` and `Rpl_semi_sync_source_no_tx`.
