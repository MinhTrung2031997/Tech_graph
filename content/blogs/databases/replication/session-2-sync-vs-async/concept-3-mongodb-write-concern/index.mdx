<Tldr>
In MongoDB the client chooses, per operation, how many members must confirm a write: the **write concern**. MongoDB 8.0's default is `{ w: "majority", wtimeout: 0 }` (read from `getDefaultRWConcern` on the lab set). On a 3-member set with secondaries **20 ms** and **50 ms** away, single-document inserts took **0.19 ms** with `w: 1`, **1.24 ms** with `w: 1, j: true`, **26.7 ms** with `w: "majority"` (primary + nearest secondary) and **55.3 ms** with `w: 3` (the slowest member too). With both secondaries paused, `w: 1` still succeeded in 5 ms; `w: "majority"` with `wtimeout: 2000` failed after **2,017 ms** with **WriteConcernFailed (64)** "waiting for replication timed out", yet the document **was written** on the primary. Without a majority in sight, the primary **stepped down after 9.6 s** and then refused even `w: 1` writes with **NotWritablePrimary (10107)**.
</Tldr>

## The options

| Write concern | Acknowledged when | No delay (median / p95) | Secondaries +20 / +50 ms |
|---|---|---|---|
| `w: 1` | Primary applied it (in memory) | 0.21 / 0.48 ms | 0.19 / 0.39 ms |
| `w: 1, j: true` | + primary's journal flushed | 1.20 / 1.63 ms | 1.24 / 2.48 ms |
| `w: "majority"` (default) | Majority of voting members applied it, journaled | 1.39 / 1.74 ms | 26.68 / 31.41 ms |
| `w: 3` | All three members applied it | 0.60 / 1.81 ms | 55.26 / 60.70 ms |

300 inserts per row, client on the primary's host, one document per insert. Without delay `w: 3` was faster than `"majority"` because majority writes are also journaled on each acknowledging member (`writeConcernMajorityJournalDefault`, from the documentation) while `w: 3` without `j` is not.

| Term | Meaning |
|---|---|
| `w` | Number of members (or `"majority"`) that must acknowledge |
| `j` | Wait for the journal (on-disk) on acknowledging members |
| `wtimeout` | Give up waiting after this many ms; the write is **not** undone |
| Majority commit point | The newest write known to be on a majority; it survives any election |
| Step down | A primary that cannot see a majority of voting members becomes secondary |
| **✓ / ✗** | Acknowledged / not acknowledged |

<Pitfall>
`WriteConcernFailed` does not mean the write failed. The document `p-maj` was on the primary after the timeout, and after the secondaries returned and rpa-mongo2 was elected, the new primary had it too. An application that retries on this error, or reports "payment failed" to the user, can duplicate or contradict a write that actually happened. Treat a write-concern timeout as **unknown outcome**: make the write idempotent (a unique business key), and check before retrying.
</Pitfall>

## Real-world scenario: flash-sale writes with w: 1

To survive a flash sale, an order service lowers its write concern to `w: 1` (0.19 ms instead of 26.7 ms in this lab's distances). During the sale the primary's host fails. A secondary is elected within about ten seconds, but orders acknowledged by the old primary in its last moments had not reached any secondary. When the old primary rejoins, MongoDB rolls those writes back into a rollback directory (Session 5): customers hold confirmation e-mails for orders that no longer exist. Keep `w: "majority"` for orders and payments; use `w: 1` for data that can be lost (view counters, events), and reduce majority latency with placement (the nearest secondary decides the latency) rather than by lowering the write concern.

## Key takeaways

1. Write concern is chosen per operation; MongoDB 8.0 defaults to `w: "majority"`.
2. `w: "majority"` waits for the nearest secondary on a 3-member set: 26.7 ms with 20 ms of delay; `w: 3` waits for the slowest: 55.3 ms.
3. `wtimeout` turns an endless wait into an error, but the write is not undone.
4. A primary that cannot see a majority steps down (after about 10 s here) and refuses all writes.
5. Writes acknowledged with `w: 1` can be rolled back by a failover; majority-acknowledged writes cannot.
