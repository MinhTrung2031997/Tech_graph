<Tldr>
PostgreSQL replication is asynchronous until you name a synchronous standby in `synchronous_standby_names`. Then `synchronous_commit` decides how far a commit waits: **local** (own WAL flushed), **remote_write** (standby wrote the WAL), **on** (standby flushed it), **remote_apply** (standby replayed it). With the standby's replies delayed 20 ms, a single-row INSERT took **1.05 ms** (local), **23.8 ms** (remote_write), **26.2 ms** (on) and **26.0 ms** (remote_apply); `off` took **0.008 ms** because it does not even wait for the local flush. Without network delay the levels were 1.1–2.1 ms. When the synchronous standby stopped responding, commits **waited forever** (`wait_event = SyncRep`): `statement_timeout = 3s` did not end the wait. Cancelling after 122 s printed *"canceling wait for synchronous replication due to user request … The transaction has already committed locally"* and the client saw `INSERT 0 1`. `synchronous_commit = local` in one session still committed in 0.05 s.
</Tldr>

## The levels

| `synchronous_commit` | COMMIT returns after | Lab latency, standby +20 ms | Lab latency, no delay |
|---|---|---|---|
| `off` | WAL written to memory; flushed later by the WAL writer | 0.008 ms | 0.008 ms |
| `local` | WAL flushed on the primary | 1.05 ms | 1.12 ms |
| `remote_write` | + standby has written the WAL (not fsynced) | 23.8 ms | 2.06 ms |
| `on` (default) | + standby has flushed the WAL | 26.2 ms | 1.41 ms |
| `remote_apply` | + standby has replayed it: visible to queries there | 26.0 ms | 1.66 ms |

Measured with `pgbench`, one client, a single-row INSERT per transaction, median of three 5-second runs; `synchronous_standby_names = 's1'` and `rpa-pg2` connected as `application_name = s1`. The delay is Linux `netem` on the standby's outgoing traffic (the lab's `delay.sh`). Without `synchronous_standby_names`, every level except `off` behaves like `local` (1.12–1.23 ms here).

| Term | Meaning |
|---|---|
| Synchronous standby | A standby listed in `synchronous_standby_names`; `pg_stat_replication.sync_state = sync` |
| SyncRep wait | A committing backend waits with `wait_event = SyncRep` until the standby reports the required LSN |
| **✓ / ✗** | Step done before COMMIT returns / not waited for |

<Pitfall>
A synchronous standby that is down stops **all** commits that wait for it, and there is no built-in timeout: here a commit sat in `SyncRep` for 122 s and would have waited longer. Two consequences. First, one synchronous standby with no alternative makes the standby as critical as the primary: list two and wait for one (Concept 4). Second, a cancelled or timed-out wait does **not** roll back: the transaction is committed on the primary, the client is told so with a WARNING it probably logs nowhere, and the standby may not have it.
</Pitfall>

## Choosing per transaction

`synchronous_commit` is a session and transaction setting, so one cluster can mix levels:

```sql
-- Payment confirmation: must survive the loss of the primary
BEGIN; SET LOCAL synchronous_commit = on; … COMMIT;
-- Click tracking, page views: lose a few on a crash, never wait
BEGIN; SET LOCAL synchronous_commit = off; … COMMIT;
```

`off` is not "no durability": the WAL is still written and flushed within a short delay by the WAL writer (from the documentation: at most three times `wal_writer_delay`, 200 ms by default), and a crash cannot corrupt data, only lose the most recent commits.

## Real-world scenario: checkout stalls during a standby reboot

A team turns on synchronous replication for orders with `synchronous_standby_names = 'standby1'`. During routine OS patching the standby reboots; for four minutes every checkout hangs on COMMIT, the connection pool fills, and the shop goes down while the primary is perfectly healthy. Fixes: name two standbys with `ANY 1 (s1, s2)` so either can acknowledge (Concept 4); have the patching runbook clear `synchronous_standby_names` before taking the last synchronous standby down; and give the application its own timeout and alerting on `wait_event = 'SyncRep'`, knowing that a commit it gives up on may still have happened.

## Key takeaways

1. Replication is asynchronous until `synchronous_standby_names` names a standby; then `synchronous_commit` picks the wait.
2. Each remote level adds a round trip: about 24–26 ms with 20 ms of delay; `local` stayed near 1 ms, `off` 0.008 ms.
3. `remote_apply` is the only level that makes the row visible on the standby when COMMIT returns.
4. A non-responding synchronous standby blocks commits indefinitely; `statement_timeout` does not end the wait.
5. A cancelled synchronous wait leaves the transaction committed on the primary.
