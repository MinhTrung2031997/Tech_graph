<Tldr>
**Physical** replication (PostgreSQL) ships what changed on disk: row versions, every index entry, page pruning, and full-page images after checkpoints. **Logical** replication (MySQL binlog, MongoDB oplog) ships the changed rows or documents; the replica does its own index and page work. On the same writes: a single-row INSERT cost **272 B** (WAL), **338 B** (binlog) and **397 B** (oplog); a 1,000-row INSERT **~240 KB**, **41 KB** and **217 KB**; an UPDATE of all 100,000 rows **34.0–46.8 MB** of WAL (**39.9 MB** with `wal_compression = lz4` instead of 45.5 MB), **8.2 MB** of binlog (**1.6 MB** MINIMAL, **343 B** statement) and **18.5 MB** of oplog in **100,000 entries**. Small writes cost about the same everywhere; bulk changes and checkpoints are where the engines differ.
</Tldr>

## The numbers

All on the 100,000-row `orders` table (PostgreSQL: primary key plus `created_at` index; MySQL and MongoDB: the same two indexes), measured as the change in WAL LSN, binlog position, and the `bsonsize` of new oplog entries.

| Write | PostgreSQL WAL | MySQL binlog (ROW, FULL) | MongoDB oplog |
|---|---|---|---|
| 1-row INSERT, warm | 272–296 B | 338 B | 397 B (retryable write) |
| 1-row INSERT, first after a checkpoint | 8,760–16,680 B | 338 B | 397 B |
| 1-row UPDATE, warm | 168–176 B | 381 B (315 B MINIMAL) | 334 B |
| 1,000-row INSERT | 238–249 KB | 41.5 KB | 217 KB (2 applyOps entries) |
| UPDATE of 100,000 rows | 34.0–34.7 MB warm, 45.5–46.8 MB after a checkpoint | 8.2 MB (1.6 MB MINIMAL, 1.5 MB zstd, 343 B STATEMENT) | 18.5 MB, 100,000 entries |
| Local log not shipped | none: the WAL is the replication stream | InnoDB redo 10.1 MB for the UPDATE | WiredTiger journal (not measured) |

| Term | Meaning |
|---|---|
| Physical | The replica applies byte-level page changes; it must be an identical copy |
| Logical | The replica applies row or document changes through its own storage engine |
| Write amplification | Bytes logged per byte of data changed: indexes, page images, before-images |
| **✓ / ✗** | Shipped to the replica / not shipped |

## Physical vs logical

| | Physical (PostgreSQL streaming) | Logical (MySQL binlog, MongoDB oplog) |
|---|---|---|
| Unit shipped | Page changes | Rows / documents |
| Index maintenance | Shipped (records for every index) | Done again on the replica |
| Checkpoint effect | Full-page images: 8.7–16.7 KB for one INSERT | None |
| Bulk UPDATE of 100,000 rows | 34–47 MB | 8.2 MB (binlog), 18.5 MB (oplog) |
| Replica must match | Same major version and architecture, whole cluster | Can differ in version (within limits), indexes, even tables |
| Replica CPU per change | Low: write the bytes into the page | Higher: find the row, update indexes |
| Replica writable | No | MySQL: yes unless `super_read_only`; MongoDB: no |

<Pitfall>
Do not size the network link or the replica from the size of the data change. One UPDATE that changed a 2-byte number in 100,000 rows produced 34 to 47 MB of WAL, 8.2 MB of binlog and 18.5 MB of oplog per secondary. Measure the log volume of your real workload: `pg_stat_wal.wal_bytes` or LSN differences in PostgreSQL, binlog file growth in MySQL, and `getReplicationInfo()` usage over time in MongoDB.
</Pitfall>

## Real-world scenario: the nightly price update

A seller-tools service recalculates promotional prices every night with one UPDATE across 8 million SKU rows. On PostgreSQL the job writes several GB of WAL in minutes, the standby in another availability zone falls behind by minutes, and the WAL archive grows by the same amount. Options measured in this concept: update only rows whose price actually changes (`WHERE price IS DISTINCT FROM new_price`), batch the job so checkpoints do not fall in the middle of fresh page images, enable `wal_compression`, and leave free space in pages (`fillfactor`) so new versions stay on the same page as HOT updates and skip index entries. On MySQL, `binlog_row_image = MINIMAL` shrank the same pattern 5×; on MongoDB, the job's 8 million oplog entries also eat into the oplog window.

## Key takeaways

1. Single-row writes cost a few hundred bytes in all three engines.
2. PostgreSQL ships page changes: index entries and full-page images make bulk writes 34–47 MB for a 100,000-row UPDATE.
3. MySQL ships rows from the binlog; its redo log stays local. Row image settings changed the bulk UPDATE from 8.2 MB to 1.6 MB; statement format to 343 bytes.
4. MongoDB ships one idempotent entry per document: 100,000 entries, 18.5 MB per secondary.
5. Physical replicas are exact copies; logical replicas redo index and page work themselves and can differ.
