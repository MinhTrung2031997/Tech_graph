<Tldr>
PostgreSQL streaming replication is **physical**: the standby gets the same WAL bytes the primary wrote for crash recovery, and replays them into an identical copy of every data file. Nothing is translated, so everything the primary changes on disk is shipped: the row, **every index entry**, page pruning, and after each checkpoint a **full-page image** of every page touched for the first time. Measured on the 100,000-row `orders` table: a warm single-row INSERT wrote **272 bytes** (heap INSERT 103 B, two B-tree INSERT_LEAF records of 64 B, COMMIT 34 B); the same INSERT right after a CHECKPOINT wrote **8,760–16,680 bytes**. A **replication slot** makes the primary keep WAL until the standby has it: with the standby stopped, three bulk updates left **96 MB** of WAL retained, and the standby replayed it within **0.5 s** of starting.
</Tldr>

## The moving parts

| Term | Meaning |
|---|---|
| WAL | Write-ahead log: every change to a data page is first written as a WAL record in `pg_wal/` |
| LSN | Log sequence number, a byte position in the WAL (`0/B1CB1C8`). The difference between two LSNs is a number of bytes |
| walsender | Process on the primary that reads WAL and streams it to one standby |
| walreceiver | Process on the standby that receives WAL and writes it to the standby's `pg_wal/` |
| startup process | Process on the standby that replays WAL records into the data files (`startup recovering …`) |
| Replication slot | A named bookmark on the primary (`restart_lsn`): WAL after it is kept until that standby confirms it |
| Full-page image (FPW) | A copy of the whole 8 KB page, added to the first WAL record that touches a page after a checkpoint |
| **✓ / ✗** | Step done / waiting or not possible |

`pg_stat_replication` on the primary reports four positions for each standby, one per stage. With the lab idle, all four were equal:

```text
application_name | walreceiver      state      | streaming
sent_lsn         | 0/B1D2380        write_lsn  | 0/B1D2380
flush_lsn        | 0/B1D2380        replay_lsn | 0/B1D2380
sync_state       | async
```

Inside the containers, the processes are named after their job: `walsender postgres 192.168.163.3(43886) streaming 0/B1D2380` on the primary, `walreceiver streaming 0/B1D2380` and `startup recovering 00000001000000000000000B` on the standby.

## What "physical" means for you

| Property | Consequence |
|---|---|
| The standby is a byte copy of the cluster | Same major version, same CPU architecture; you cannot replicate one database or one table |
| Indexes and page maintenance are in the WAL | A single-row INSERT ships 3 records for 2 indexes; VACUUM and pruning on the primary are shipped too |
| Full-page images after checkpoints | WAL volume, and so replication traffic, jumps right after each checkpoint |
| The standby cannot write | It is in recovery: `pg_is_in_recovery()` returned `t` |
| Slots keep WAL for absent standbys | Safe catch-up, but an abandoned slot fills the primary's disk; `max_slot_wal_keep_size` caps it |

<Pitfall>
A slot does not expire. A standby that is decommissioned without `pg_drop_replication_slot('standby1')` keeps every byte of WAL the primary writes from that moment, until `pg_wal` fills the disk and the **primary** stops. Here three bulk updates cost 96 MB in a minute. Monitor `pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)` for every slot, and set `max_slot_wal_keep_size` so that a forgotten slot is invalidated (`wal_status = lost`) instead of taking the primary down.
</Pitfall>

## Real-world scenario: replication traffic doubles every five minutes

An order service writes about 2 MB of WAL per second, but the network graph between the primary and the standby shows spikes to 6 MB/s right after each checkpoint (`checkpoint_timeout = 5min` here). Those are full-page images: after a checkpoint, every hot page is logged once in full before its normal small records resume. Options, in order of effort: turn on `wal_compression` (on a 100,000-row update it cut WAL from 45.5 MB to 39.9 MB, Concept 4), spread checkpoints further apart (`checkpoint_timeout`, `max_wal_size`), or accept the spikes and size the link for them. Never turn off `full_page_writes` to save traffic: it protects the primary against torn pages after a crash.

## Key takeaways

1. A PostgreSQL standby replays the primary's own WAL: physical, byte-for-byte, the whole cluster.
2. Every change on disk is in the WAL: one INSERT into a table with two indexes was four records, 272 bytes.
3. The first change to a page after a checkpoint ships the whole 8 KB page: the same INSERT cost 8,760–16,680 bytes cold.
4. `pg_stat_replication` shows four positions per standby: sent, written, flushed, replayed.
5. A replication slot keeps WAL for a standby that is away (96 MB here); drop slots you no longer need or cap them with `max_slot_wal_keep_size`.
