<Tldr>
MongoDB replication is **logical and pulled**. Every write on the primary also inserts an entry into `local.oplog.rs`, a capped collection, in the same storage transaction. Each secondary fetches new entries from its sync source, stores them in its own oplog and applies them in batches. Entries are **idempotent**: an `$inc` is logged as the resulting value, so applying an entry twice gives the same document. Measured on 100,000 `orders` documents: `insertOne` wrote **1 entry of 397 bytes**; `updateMany` with `$inc` on all documents wrote **100,000 entries of 185 bytes (18.5 MB)**; `insertMany` of 1,000 documents became **2 `applyOps` entries** of 500 inserts each (108,649 bytes each); a transaction updating 3 documents became **1 `applyOps` entry of 653 bytes**. The oplog here was **29.6 GB** (capped), and a secondary refused a write with **NotWritablePrimary (10107)**.
</Tldr>

## The moving parts

| Term | Meaning |
|---|---|
| Oplog | `local.oplog.rs`, a capped collection on every member; one document per operation, ordered by `ts` |
| `op` | `i` insert, `u` update, `d` delete, `c` command (`applyOps`, `drop`, `create` …), `n` no-op |
| `o` / `o2` | The change (`$v: 2` diff, or a full document) / the target (`_id`) |
| Idempotent | Applying the entry once or twice gives the same result: `$inc: 1` is logged as `amount: 81.07` |
| Sync source | The member a secondary pulls from (here both pulled from the primary, `syncSourceHost: rpa-mongo1:27017`) |
| `applyOps` | One entry that wraps several operations: used for transactions and batched inserts |
| Oplog window | Time span between the oldest and newest entry; a secondary away longer than the window must resync |
| **✓ / ✗** | Done / refused |

## The oplog is a collection you can read

```js
// The most recent entry for orders
db.getSiblingDB('local').oplog.rs.find({ ns: 'shop.orders' }).sort({ $natural: -1 }).limit(1)

// Size and window
db.getSiblingDB('local').getReplicationInfo()   // logSizeMB: 29617, usedMB: 39, timeDiffHours: 0.01
```

The oplog is capped: when it reaches its size (29,617 MB here, chosen by mongod from the disk size; set `--oplogSizeMB` or `replSetResizeOplog` to change it), the oldest entries are removed. The **oplog window**, how far back it reaches in time, is what matters operationally: a secondary that is down longer than the window cannot catch up from the oplog and needs an initial sync (Session 3 measures lag).

<Pitfall>
"One updateMany" is not one replication event. Updating 100,000 documents wrote 100,000 oplog entries, 18.5 MB, which every secondary fetches and applies one document at a time. A nightly job that rewrites a large collection with `updateMany` can shrink the oplog window from days to hours, because it fills the capped oplog with entries, and it creates a burst of replication lag. Batch large rewrites, and check `getReplicationInfo().timeDiffHours` after the job.
</Pitfall>

## Real-world scenario: an analytics secondary falls off the oplog

A hidden secondary used for nightly exports is stopped for a disk replacement. The primary's oplog is sized for normal traffic, about 20 hours of window, but the same night a migration script runs `updateMany` on 40 million order documents: 40 million entries, about 7 GB at the 185 bytes per entry measured here, which pushes the window down to a few hours. When the secondary comes back, its last applied entry is no longer in the primary's oplog and it must resync from scratch. Before maintenance, compare the planned downtime with the window (`getReplicationInfo()`), resize the oplog if needed (`replSetResizeOplog`, online), and schedule bulk rewrites away from it.

## Key takeaways

1. Every write on the primary adds an entry to `local.oplog.rs` in the same storage transaction; secondaries pull and apply entries.
2. Entries are idempotent: `$inc` is logged as the resulting value.
3. A multi-document update is one entry per document: 100,000 entries and 18.5 MB here.
4. Transactions and batched inserts become `applyOps` entries that are applied as a unit.
5. Secondaries refuse client writes; a drop on the primary reached a secondary in 6 ms.
6. The oplog is capped; its time window decides how long a secondary can be away.
