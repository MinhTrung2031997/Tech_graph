<Tldr>
MySQL replication is **logical**. InnoDB's redo log stays on the source; at commit the source also writes the transaction to the **binary log** as events, each transaction tagged with a **GTID** (`server_uuid:number`). A Binlog Dump thread sends the events, the replica's I/O thread stores them in a **relay log**, and applier threads re-execute them on the replica's own InnoDB. Measured on 100,000 `orders` rows: a single-row INSERT was **338 bytes** in five events. An UPDATE of all 100,000 rows was **8.2 MB** in row format with full before/after images, **1.6 MB** with `binlog_row_image = MINIMAL`, **1.5 MB** with binlog transaction compression, and **343 bytes** in statement format, while InnoDB wrote **10.1 MB of redo** for it that no replica ever sees. A replica is an ordinary writable server: a row inserted there by mistake made the source's later INSERT of the same key fail on the replica with **error 1062** and replication stopped. `super_read_only = ON` refuses such writes (**ERROR 1290**).
</Tldr>

## The moving parts

| Term | Meaning |
|---|---|
| Binary log (binlog) | Logical log of committed transactions in `binlog.000005` …, written by the source at commit; separate from InnoDB's redo log |
| Event | One entry in the binlog: `Gtid`, `Query` (BEGIN or a statement), `Table_map`, `Write_rows` / `Update_rows` / `Delete_rows`, `Xid` (COMMIT) |
| GTID | Global transaction id `source_uuid:n`. A replica records which GTIDs it has executed and asks for the rest (`SOURCE_AUTO_POSITION = 1`) |
| Binlog Dump thread | Thread on the source that sends binlog events to one replica |
| `replica_io` | Replica thread that receives events and writes them to the relay log (`Retrieved_Gtid_Set`) |
| `replica_sql` + workers | Coordinator and 4 worker threads (default `replica_parallel_workers = 4`) that apply the relay log (`Executed_Gtid_Set`) |
| Row / statement format | Log the changed rows (default `ROW`) or the SQL text (`STATEMENT`) |
| `binlog_row_image` | `FULL` logs every column before and after; `MINIMAL` logs the key before and the changed columns after |

On the replica, `performance_schema.threads` showed `thread/sql/replica_io` "Waiting for source to send event", `thread/sql/replica_sql` "Replica has read all relay log; waiting for more updates" and four `thread/sql/replica_worker` "Waiting for an event from Coordinator". On the source, one connection in state "Source has sent all binlog to replica; waiting for more updates".

## What "logical" means for you

| Property | Consequence |
|---|---|
| The replica runs its own InnoDB | Its pages, redo and indexes are its own; it may even have extra indexes |
| Events carry rows, not pages | No full-page images; index entries are rebuilt on the replica, so a 1,000-row INSERT was 41,472 bytes |
| Each transaction has a GTID | The replica knows exactly which transactions it has; repointing it to a new source needs no file positions |
| The replica is writable by default | Writes there create errant GTIDs and can stop replication later; set `super_read_only` |
| Statement format re-executes SQL | Tiny binlog, but non-deterministic statements can produce different rows on the replica |

<Pitfall>
Statement format is not a free compression switch. It was 343 bytes instead of 8.2 MB for the 100,000-row UPDATE, but the replica re-ran the UPDATE, and any statement whose result depends on row order, time or randomness can change different rows on the replica. MySQL only adds a Note (1592) when it notices; the default `binlog_format = ROW` avoids the problem, and `MINIMAL` row images or `binlog_transaction_compression` get most of the size back.
</Pitfall>

## Real-world scenario: replica broken by a support script

A support engineer connects a reporting tool to the replica and "fixes" a seller's order status there. Hours later the source updates the same order and the replica’s applier stops with an error such as the 1062 above; `Seconds_Behind_Source` shows NULL and the dashboards on the replica freeze at the time of the error. Fixes: set `super_read_only = ON` in the replica's configuration (the replication threads are not affected), give reporting users only `SELECT`, and compare `@@gtid_executed` on source and replica: any GTID with the replica's own `server_uuid` is an errant transaction to investigate before the replica is ever promoted.

## Key takeaways

1. MySQL replicates the binary log, a logical log separate from InnoDB's redo log; the redo log never leaves the source.
2. A single-row INSERT was 5 events, 338 bytes; each transaction carries a GTID.
3. Row format with full images shipped 8.2 MB for a 100,000-row UPDATE; MINIMAL 1.6 MB; statement format 343 bytes, at the price of re-execution and unsafe statements.
4. The replica applies events with a coordinator and worker threads through its own InnoDB.
5. A replica accepts writes unless `super_read_only` is on; a stray write stopped replication with error 1062.
