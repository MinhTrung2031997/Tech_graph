<Tldr>
In PostgreSQL and MySQL the **server** you read from is the read concern: the primary returns the newest committed data, an asynchronous replica returns its past. Choosing the server is the application's job (connection pools, a proxy, an ORM's replica setting), which plays the role of MongoDB's read preference, without `maxStalenessSeconds` unless you build it. On the write side, PostgreSQL's `synchronous_commit` is the write concern. With a synchronous standby delayed 5 s: `local` committed in 2.3–3.6 ms and `on` in 2.7–5.8 ms, and a standby read right after returned the **old** value; `remote_apply` committed in **5,003–5,011 ms** and the standby read returned the **new** value. With no delay all three committed in 2–8 ms. Read-your-writes on a replica is a wait for the write's LSN or GTID set ([Session 3](/blogs/databases/replication/session-3-replica-lag/concept-4-reading-your-own-writes)), which is what a MongoDB causal session automates. MySQL semi-sync waits for the replica to **receive**, not apply; MySQL Group Replication's `group_replication_consistency` is the closest thing to per-transaction read concerns (from the documentation, not run).
</Tldr>

## Mapping the vocabulary

| MongoDB | PostgreSQL | MySQL |
|---|---|---|
| `readPreference: primary` | connect to the primary | connect to the source |
| `readPreference: secondary` | connect to a standby (hot standby) | connect to a replica |
| `maxStalenessSeconds` | none built in: check `pg_last_wal_replay_lsn()` or a heartbeat row before routing | none built in: check missing GTIDs or a heartbeat table |
| `readConcern: local` on a secondary | a standby read | a replica read |
| `readConcern: majority` | no equivalent for reads; with quorum commit (`ANY k (…)`) a committed write is on k standbys, but reads on the primary can still show it first (from the documentation) | no equivalent in async replication |
| Causal session (`afterClusterTime`) | wait for the write's LSN on the standby | `WAIT_FOR_EXECUTED_GTID_SET`; Group Replication `BEFORE` (from the documentation) |
| `w: 1` | `synchronous_commit = local` (or no sync standby) | asynchronous replication |
| `w: "majority"` / `w: 2` | `synchronous_commit = on` with a sync standby (flushed there) | semi-sync `AFTER_SYNC` (received and logged) |
| `w: <all>` with apply | `synchronous_commit = remote_apply` | Group Replication `AFTER` (from the documentation) |

## PostgreSQL

Lab: `synchronous_standby_names = 'walreceiver'` on the primary (the standby connects with that application name), so `pg_stat_replication.sync_state = sync`. The standby has `recovery_min_apply_delay = '5s'` to make the difference between "flushed there" and "applied there" visible. Each run: one UPDATE with `\timing`, then a read of the same row on the standby.

`synchronous_commit` is a session (even per-transaction) setting, like a per-operation write concern: an application can commit a payment with `remote_apply` and everything else with `local`. [Session 2](/blogs/databases/replication/session-2-sync-vs-async/concept-1-postgresql-synchronous-commit) measures what each level costs and what happens when the synchronous standby is down (commits wait).

## MySQL InnoDB

Asynchronous replication gives MySQL exactly two read "concerns": the source (newest) and a replica (its past). The lab's replica, delayed with `SOURCE_DELAY = 5`, returned the previous status on every read right after a write; waiting for the write's GTID set on the replica gave a fresh read after 5.56–5.63 s, or a timeout (1) after 201–203 ms with a 0.2 s limit (Session 3, Concept 4).

Write side: semi-synchronous replication (`rpl_semi_sync_source_wait_point = AFTER_SYNC`) makes COMMIT wait until a replica has written the transaction to its relay log, roughly `w: 2` for durability, but nothing about the replica having **applied** it ([Session 2](/blogs/databases/replication/session-2-sync-vs-async/concept-2-mysql-semi-sync)). Group Replication adds `group_replication_consistency` with values `EVENTUAL`, `BEFORE`, `AFTER`, `BEFORE_AND_AFTER`: `BEFORE` makes a transaction wait until the member has applied everything committed before it (like a causal read), `AFTER` makes a commit wait until all members have applied it (like `remote_apply`) (from the documentation; Group Replication is not part of this lab).

## Comparison

| Need | MongoDB | PostgreSQL | MySQL (async) |
|---|---|---|---|
| Choose the server per read | read preference | application routing | application routing / ProxySQL |
| Exclude stale replicas | `maxStalenessSeconds` (≥ 90 s) | own check | own check |
| Read your own write on a replica | causal session | LSN wait | GTID wait |
| Write not lost on failover | `w: "majority"` | sync standby (`on`), quorum with `ANY k` | semi-sync (`AFTER_SYNC`) |
| Every replica read fresh after commit | `w: <all>` (applied) | `remote_apply` | Group Replication `AFTER` |

<Pitfall>
"We use synchronous replication, so the standby is consistent" is only true for `remote_apply`. With `synchronous_commit = on` the commit returned in 2.7–5.8 ms while the standby still showed the old value for 5 s: the WAL was safe there, but not applied. If reads go to the standby, the write side must say `remote_apply`, or the read side must wait for the LSN.
</Pitfall>

## Real-world scenario: moving a MongoDB habit to PostgreSQL

A team used MongoDB causal sessions for "save then view" pages and is moving the orders service to PostgreSQL with one standby for reads. They first set `synchronous_commit = on` globally, expecting fresh standby reads, and still see stale pages during busy hours (the standby is synchronous for durability but applies a few hundred milliseconds behind). They switch to: `local` or `on` for normal writes, the write's LSN returned to the client, and an LSN wait of up to 100 ms before standby reads for that user, falling back to the primary.

| Option | Write latency | Standby read after write |
|---|---|---|
| `on` globally | flush round trip | can be stale |
| `remote_apply` globally | waits for apply on every commit | fresh |
| LSN wait for the writer's next reads | unchanged | fresh, or primary fallback |

## Key takeaways

1. PostgreSQL and MySQL have no read concern: the server you read decides freshness, and routing is the read preference.
2. `synchronous_commit` is the write concern; `on` makes the standby durable, only `remote_apply` makes it visible.
3. Against a standby 5 s behind: `local`/`on` 2.3–5.8 ms and stale standby reads; `remote_apply` 5,003–5,011 ms and fresh reads.
4. LSN and GTID waits are hand-made causal reads; MySQL semi-sync waits for receipt, not apply.
5. Group Replication's consistency levels are MySQL's closest match to read/write concerns (documentation only here).
