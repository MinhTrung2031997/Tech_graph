<Tldr>
A **causally consistent session** is MongoDB's built-in read-your-writes for secondaries. Every operation returns an `operationTime`; the session sends the latest one with its next read as `afterClusterTime`, and the member that serves the read waits until it has data at least that new. In the lab, `rpb-mongo3` was frozen for 5 s and each read was pinned to it with a tag. Outside a session: the read returned the **old value after 2 ms**. Inside a causal session: it **waited 5,044 ms** and returned the new value. With `maxTimeMS(1000)`: **MaxTimeMSExpired after 1,012 ms**. On a healthy set both forms took 2 ms. The guarantees (read your writes, monotonic reads, monotonic writes, writes follow reads) hold when the session uses `readConcern: "majority"` and `writeConcern: "majority"` (from the documentation); this is the MongoDB counterpart of waiting for an LSN or GTID set in [Session 3](/blogs/databases/replication/session-3-replica-lag/concept-4-reading-your-own-writes).
</Tldr>

## How it works

| Term | Meaning |
|---|---|
| Session | A client-side context (`startSession()`) that groups operations |
| `operationTime` | The cluster time of the session's last operation, returned by the server |
| `afterClusterTime` | Sent with a read: "do not answer before you have data at least this new" |
| Causal consistency | Inside one session: you see your own writes, reads never go backwards, writes apply in session order, a write that follows a read sees that read's data |
| **✓ / ✗** | Read returns the session's own write / does not |

```js
const c = new Mongo('mongodb://rpb-mongo1:27017,rpb-mongo2:27017,rpb-mongo3:27017/shop?replicaSet=rpbrs');
const s = c.startSession({ causalConsistency: true });
const sdb = s.getDatabase('shop');
sdb.orders.updateOne({ _id: 12 }, { $set: { note: v } }, { writeConcern: { w: 'majority' } });
s.getOperationTime();   // {"$timestamp":"7711767256329355265"}
sdb.orders.find({ _id: 12 }).readPref('secondary', [{ name: 'm3' }]).readConcern('majority').toArray();
```

The members carry tags `m1`, `m2`, `m3` so the read can be pinned to the lagging member. `rpb-mongo3` is frozen with `db.fsyncLock()` and released by `db.fsyncUnlock()` 5 s later; the write's majority comes from the primary and `rpb-mongo2`.

## Which concerns make it causal

| Session read / write concern | Read your own writes | Guarantees survive failover |
|---|---|---|
| `majority` / `majority` | ✓ | ✓ all four guarantees |
| `majority` / `w: 1` | ✓ while no failover | ✗ a `w: 1` write can be rolled back |
| `local` / `majority` | ✓ while no failover | ✗ a read can return data that is later rolled back |
| `local` / `w: 1` | ✓ while no failover | ✗ |

The lab measured only `majority` / `majority`; the other rows are from the documentation. Outside a failover, any combination makes the read wait for the session's operationTime. Only majority/majority keeps the guarantees across an election, because both sides then deal only in data that cannot disappear (Concept 4).

## Across processes

A session lives in one client. When a web request writes and a later request (another process) reads, pass the times along: read `session.getClusterTime()` and `session.getOperationTime()` after the write, store them (cookie, cache), and in the reader call `session.advanceClusterTime(…)` and `session.advanceOperationTime(…)` before reading (from the documentation; the lab used one process). This is the same pattern as carrying an LSN or GTID set in Session 3.

<Pitfall>
A causal read on a lagging secondary waits as long as the lag: 5 s here, minutes during an incident. Always set `maxTimeMS` on causal secondary reads and fall back to the primary on MaxTimeMSExpired, or combine with `maxStalenessSeconds` so a badly lagging member is not chosen in the first place.
</Pitfall>

## Real-world scenario: "edit listing" then "view listing"

A seller's browser session writes a listing change through one API server and, a moment later, loads the listing through another. Product reads go to secondaries. The write handler returns the session's `operationTime` and `clusterTime` to the client; the read handler advances a new causal session to them and reads with `readConcern: "majority"`, `readPreference: "secondaryPreferred"`, `maxTimeMS: 200`, falling back to the primary on timeout. Buyers' reads skip the token and get plain secondary reads.

| Piece | Role |
|---|---|
| `operationTime` + `clusterTime` in the response | The position of the seller's write |
| `advanceOperationTime` in the reader | Makes the secondary wait for that position |
| `maxTimeMS: 200` + primary fallback | Bounds the wait when a secondary lags |

## Key takeaways

1. A causal session sends its last `operationTime` as `afterClusterTime`; the serving member waits until it has caught up.
2. On a member frozen for 5 s: plain read stale after 2 ms, causal read fresh after 5,044 ms.
3. On a healthy set the session added no measurable time (2 ms either way).
4. Bound causal reads with `maxTimeMS` (MaxTimeMSExpired after 1,012 ms with 1000) and fall back to the primary.
5. Use majority read and write concerns for guarantees that survive failover.
