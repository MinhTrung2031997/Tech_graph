<Tldr>
**Read preference** is chosen in the driver and picks the member: `primary` (default), `primaryPreferred`, `secondary`, `secondaryPreferred`, `nearest`, optionally narrowed by **tags** and by **`maxStalenessSeconds`**. It says nothing about freshness by itself. With `rpb-mongo3` frozen about 115 s behind and `rpb-mongo2` current, 40 reads right after a write returned the **old value 19 times** with `secondary`, 23 with `secondaryPreferred` and 7 with `nearest` (which also uses the primary); `maxStalenessSeconds = 90` excluded the lagging member: **0 stale**. Values under 90 are rejected by the driver (`Option "maxStalenessSeconds" must be at least 90 seconds`). With both secondaries 188 s and 305 s behind, `secondaryPreferred` served **3–5-minute-old data 40 of 40 times**; with `maxStalenessSeconds = 90`, `secondary` failed (`Server selection timed out after 5000 ms`) and `secondaryPreferred` fell back to the primary. Members with `secondaryDelaySecs` are left out of `hello` and are never chosen: a tag pointing at one timed out after 30 s.
</Tldr>

## Modes and filters

| Term | Meaning |
|---|---|
| `primary` | Only the primary (default); fails if there is none |
| `primaryPreferred` | Primary; a secondary if there is no primary |
| `secondary` | Only secondaries; fails if none is eligible |
| `secondaryPreferred` | Secondaries; the primary if none is eligible |
| `nearest` | Any member within `localThresholdMS` (15 ms) of the fastest, primary included |
| Tag set | Restricts eligible members to those with matching `tags` in the replica set config |
| `maxStalenessSeconds` | Excludes secondaries whose estimated staleness exceeds it; minimum 90 s |
| Staleness estimate | The driver's estimate from each member's `lastWrite` in `hello` responses, refreshed every `heartbeatFrequencyMS` (10 s) |
| **✓ / ✗** | Read returned the value just written / an older value |

The test: write a new value with `w: "majority"` on the primary, then read the same document 40 times through a replica-set connection with the given options, and count fresh vs stale answers.

```js
const c = new Mongo('mongodb://rpb-mongo1:27017,rpb-mongo2:27017,rpb-mongo3:27017/shop?replicaSet=rpbrs'
                    + '&readPreference=secondary&maxStalenessSeconds=90');
c.getDB('shop').orders.findOne({ _id: 11 });   // 40 times
```

## When every secondary is stale

Both secondaries frozen until they were 188 s and 305 s behind (writes for this test used `w: 1`, since a majority was unavailable):

| Options | Result |
|---|---|
| `secondaryPreferred` | ✗ 40 of 40 stale: data 3–5 minutes old, no error |
| `secondaryPreferred&maxStalenessSeconds=90` | ✓ 40 of 40 fresh: no eligible secondary, so the driver used the primary |
| `secondary&maxStalenessSeconds=90` | ✗ `Server selection timed out after 5000 ms` (with `serverSelectionTimeoutMS=5000`) |

## Delayed members are invisible to drivers

With `rpb-mongo3` configured `priority: 0, secondaryDelaySecs: 120, hidden: false`, the primary's `db.hello().hosts` listed only `rpb-mongo1` and `rpb-mongo2`. Reads with `secondary` went to `rpb-mongo2` 40 of 40 times (checked with `explain().serverInfo.host`), and a read with the tag set `[{ name: 'm3' }]` failed with `MongoServerSelectionError: Server selection timed out after 30000 ms`. A delayed member is for recovery, not for serving reads; only a direct connection reaches it.

## Comparison of choices

| Goal | Read preference | Add |
|---|---|---|
| Never stale from replication | `primary` | — |
| Offload reads that can be minutes old | `secondaryPreferred` | `maxStalenessSeconds` to cap "minutes" |
| Bounded staleness, never the primary | `secondary` | `maxStalenessSeconds` and handle selection errors |
| Lowest latency across regions | `nearest` | tags for the local region |
| Read-your-writes on secondaries | any secondary mode | causally consistent session (Concept 3) |

<Pitfall>
`secondaryPreferred` without `maxStalenessSeconds` has no upper bound: in the lab it served 5-minute-old data with no error and no warning. And `maxStalenessSeconds` is a coarse safety net (90 s minimum, estimated from heartbeats every 10 s); it cannot give read-your-writes. Use it to stop a broken secondary from serving, and a causal session or the primary for freshness.
</Pitfall>

## Real-world scenario: seller analytics on a lagging secondary

A seller dashboard reads with `secondaryPreferred` to keep load off the primary. A nightly index build makes one secondary fall 20 minutes behind. Half the dashboard requests show yesterday's numbers; sellers report "orders missing". With `maxStalenessSeconds = 120`, the driver stops using that secondary as soon as its estimated staleness passes 2 minutes, and the healthy secondary (or the primary) serves instead.

| Setting | Effect on the incident |
|---|---|
| `secondaryPreferred` only | 20-minute-old data for half the requests |
| `+ maxStalenessSeconds=120` | lagging member excluded within about a heartbeat after crossing 120 s |
| `+ tags` for an analytics member | dashboard traffic isolated from the members serving checkout |

## Key takeaways

1. Read preference picks the member; it does not bound staleness by itself.
2. With one secondary 2 minutes behind, `secondary` returned stale data in 19 of 40 reads, `nearest` in 7.
3. `maxStalenessSeconds` (minimum 90) removed the lagging member; with no eligible secondary, `secondaryPreferred` fell back to the primary and `secondary` failed server selection.
4. `secondaryPreferred` alone served 3–5-minute-old data without any error.
5. Delayed members are not advertised in `hello` and never serve driver reads.
