<Tldr>
A **read concern** says which version of the data a read may return. `local` (the default) and `available` return the newest data on the node, even if it could still be rolled back. `majority` and `snapshot` return only data acknowledged by a majority of members, so they never show a write that a failover could undo. `linearizable` additionally confirms, at read time, that the node is still the primary and the majority agrees. In the lab both secondaries were frozen with `fsyncLock`, so the **majority commit point stopped**: a `w: 1` update was acknowledged in 4 ms; `local`/`available` returned the new status, `majority`/`snapshot` the **old** one, and `linearizable` hung until `maxTimeMS` (**MaxTimeMSExpired after 3006 ms**). A `w: "majority"` write in the same state failed with WriteConcernFailed after its 3 s `wtimeout`; without a `wtimeout` (the default) it would wait forever. On a healthy set `local`, `majority` and `snapshot` cost 0.19–0.25 ms (median); `linearizable` 1.91 ms.
</Tldr>

## The levels

| Term | Meaning |
|---|---|
| Majority commit point | The newest oplog entry known to be applied on a majority of voting members; data at or before it survives any failover |
| `local` | Newest data on this node. Default for reads (the `getDefaultRWConcern` result in the lab: `defaultReadConcern: local`) |
| `available` | Same as `local` on a replica set; on sharded clusters it may also return orphaned documents (from the documentation) |
| `majority` | Data as of the majority commit point |
| `snapshot` | Majority-committed data from one point in time across the whole operation; required inside multi-document transactions with majority writes |
| `linearizable` | Majority data **and** a check that no newer majority write exists: the read waits for a majority acknowledgement of a no-op write. Primary only |
| **✓ / ✗** | Returns the newest acknowledged value / returns an older value or waits |

Every level returns committed data; the difference is **committed where**. A `w: 1` write is committed on the primary only, and can still disappear in a failover (Concept 4).

## Experiment

Order 9 starts as `delivered` on all three members (written with `w: 3`). Both secondaries are frozen with `db.fsyncLock()`, which stops them applying the oplog while they keep answering heartbeats, so the primary stays primary. Then:

```js
db.orders.updateOne({ _id: 9 }, { $set: { status: 'cancelled' } }, { writeConcern: { w: 1 } });   // ack in 4 ms
// read the same document at each level, with a 3 s limit
db.runCommand({ find: 'orders', filter: { _id: 9 }, readConcern: { level: L }, maxTimeMS: 3000 });
```

## Writes in the same state

| Write concern | Result with both secondaries frozen |
|---|---|
| `w: 1` | acknowledged in 4 ms |
| `w: "majority", wtimeout: 3000` | WriteConcernFailed after 3014 ms; the write is applied on the primary anyway |
| `w: "majority"` with no `wtimeout` (the implicit default: `w: majority, wtimeout: 0`) | blocked; a lab script using it hung for over 3 minutes until it was stopped |

The write and read concerns pair up: data written with `w: "majority"` is visible to `majority` reads as soon as the write is acknowledged; data written with `w: 1` becomes visible to `local` reads at once and to `majority` reads only when a majority has it.

## Which level for which read

| Read | Level | Why |
|---|---|---|
| Product page, search | `local` | Fast; a value that might be rolled back is harmless |
| Order status after payment, shown to the buyer | `majority` | Never show a payment that a failover could undo |
| Read used to decide a write (stock, balance) on the primary | `majority` in a transaction, or a single atomic update | Avoid acting on data that disappears |
| "Is this coupon still unused?" across failovers | `linearizable` with `maxTimeMS` | Rare; when the read must reflect every acknowledged majority write |
| Reports that read several collections consistently | `snapshot` | One point in time across the operation |

<Pitfall>
`majority` does not mean "fresh". With the commit point stuck, `majority` returned the old value instantly and without an error, which is correct (the old value is the newest one that cannot be rolled back) and easy to misread as data loss. If a read must reflect a write that was itself acknowledged with `w: 1`, a `majority` read may not show it; pair `majority` reads with `majority` writes.
</Pitfall>

## Real-world scenario: the refund that came back

A marketplace writes refunds with `w: 1` for speed and shows the refund page with the default `local` read. The primary acknowledges a refund, the page shows "Refunded", then the primary fails before any secondary has the entry. The new primary never had the refund; the old primary rolls it back when it rejoins (Concept 4). The buyer saw "Refunded"; the ledger says otherwise.

| Fix | Effect |
|---|---|
| Write refunds with `w: "majority"` (the default since MongoDB 5.0) and a `wtimeout` | The acknowledgement means the refund survives failover |
| Read the confirmation with `readConcern: "majority"` | The page never shows a refund that could be rolled back |
| Treat WriteConcernFailed as "unknown", not "failed" | Retry idempotently; the write may exist |

## Key takeaways

1. `local` and `available` return the newest data on the node; `majority` and `snapshot` return only majority-committed data; `linearizable` also confirms with a majority at read time.
2. With the majority commit point stuck, `majority` returned the older value with no error, and `linearizable` waited until `maxTimeMS` (3006 ms).
3. On a healthy set `majority` reads cost the same as `local` (about 0.2 ms); `linearizable` about 1.9 ms.
4. A `w: "majority"` write with no `wtimeout` waits forever when a majority is unavailable; set `wtimeout` and treat the error as "unknown outcome".
5. Pair majority reads with majority writes.
