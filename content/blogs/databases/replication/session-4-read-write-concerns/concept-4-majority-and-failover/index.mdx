<Tldr>
"Majority" is the line between data that survives a failover and data that may not. In the lab the primary `rpb-mongo1` was disconnected from the network and, still believing it was primary, accepted a `w: 1` insert (`lost-1`) in **7 ms**. On that node, **`readConcern: "local"` returned `lost-1`; `readConcern: "majority"` did not.** A `w: "majority"` insert (`lost-2`) on the same node failed with **WriteConcernFailed after 5,013 ms**, yet was applied locally too. The isolated node stepped down 7.6–9.2 s after the cut and `rpb-mongo2` was primary by 10.9 s: neither document existed there. When `rpb-mongo1` rejoined, it **rolled back both in 218 ms** and wrote them to `/data/db/rollback/…/removed.*.bson`. Anyone who read `lost-1` with `local` saw an order that, as far as the replica set is concerned, never happened; no `majority` read could have. Session 5 measures the rollback itself at scale.
</Tldr>

## The guarantee

| Term | Meaning |
|---|---|
| Majority-committed | Applied on a majority of voting members; any newly elected primary must have it, because an election needs votes from a majority and members only vote for a candidate at least as up to date as themselves |
| Rollback | A former primary undoing writes that the new primary never received, after it rejoins |
| Dirty read across failover | Reading a write that is later rolled back; possible with `local`, impossible with `majority` |
| **✓ / ✗** | The document is visible / not visible |

| Data | After a failover |
|---|---|
| Acknowledged with `w: "majority"` | kept (from the documentation; Session 5 kept all 1,000 such documents) |
| Acknowledged with `w: 1` only | may be rolled back |
| Write that failed its `w: "majority"` timeout | may be kept or rolled back: unknown outcome |
| Returned by a `majority` read | kept |
| Returned by a `local` read | may be rolled back |

## Experiment

```bash
docker network disconnect rpb-net rpb-mongo1     # the primary loses both secondaries
```

Then, on `rpb-mongo1` through its local shell, immediately:

```js
db.orders.insertOne({ _id: 'lost-1', status: 'paid', amount: NumberDecimal('99.00') }, { writeConcern: { w: 1 } });
db.runCommand({ find: 'orders', filter: { _id: 'lost-1' }, readConcern: { level: 'local' } });
db.runCommand({ find: 'orders', filter: { _id: 'lost-1' }, readConcern: { level: 'majority' } });
db.orders.insertOne({ _id: 'lost-2', status: 'paid' }, { writeConcern: { w: 'majority', wtimeout: 5000 } });
```

## What each reader saw

| Reader | Saw `lost-1`? | Correct in hindsight? |
|---|---|---|
| `local` read on `rpb-mongo1` during the cut | yes | ✗ it was rolled back |
| `majority` read on `rpb-mongo1` during the cut | no | ✓ |
| Any read on `rpb-mongo2` after the election | no | ✓ |
| Client of the `w: "majority"` insert (`lost-2`) | got an error | ✓ "unknown", and it was in fact rolled back |
| Client of the `w: 1` insert (`lost-1`) | got success | ✗ success for a write that was undone |

<Pitfall>
A `w: 1` acknowledgement and a `local` read can both report data that a failover will erase, with no error to anyone. Rollbacks need a network partition or a crash at the wrong moment, so they are rare and therefore untested. If an order, payment or stock change must not "un-happen", write it with `w: "majority"` (the default since 5.0) and read it with `majority` where the read leads to action; do not lower the write concern for speed on those collections.
</Pitfall>

## Real-world scenario: the voucher that was used twice

A promotions service writes "voucher used" with `w: 1` and checks vouchers with default `local` reads. During a network blip the primary is isolated for 9 s. A buyer redeems a voucher on the isolated primary (acknowledged). The new primary never sees it, and the same voucher is redeemed again on the new primary by a second buyer. When the old primary rejoins, the first redemption is rolled back into a BSON file nobody reads. The ledger shows one redemption; two orders got the discount.

| Fix | Effect |
|---|---|
| `w: "majority"` for redemptions | The first redemption could not be acknowledged during the partition |
| Unique index on the redemption record, written in the order transaction | The second redemption fails on the new primary if the first survived |
| Alert on rollback files (log id 21612 "Rollback summary") | Rollbacks are noticed and reconciled |

## Key takeaways

1. Only majority-committed data is guaranteed to survive a failover.
2. An isolated primary accepted a `w: 1` insert in 7 ms; a `local` read showed it, a `majority` read did not.
3. A `w: "majority"` insert failed after its `wtimeout` but was applied locally; its outcome was unknown until the rollback.
4. The rejoining node rolled back both inserts in 218 ms and saved them to a BSON file.
5. Use majority writes, and majority reads where the read leads to an action.
