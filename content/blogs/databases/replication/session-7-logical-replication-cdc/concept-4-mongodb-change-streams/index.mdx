<Tldr>
MongoDB exposes the oplog to applications as **change streams**: `db.orders.watch()` returns a cursor of events (`insert`, `update`, `replace`, `delete`, …), each with a **resume token** (`_id`). Measured on a 3-member replica set: an insert reached a watcher after **3 ms** (median, p95 10 ms). A change stream only returns **majority-committed** changes: with both secondaries paused, a `w: 1` insert was acknowledged and readable on the primary, but the stream showed it only after they were unpaused, **5.1 s** later. An update event carries only `updateDescription` (the changed fields). `fullDocument: 'updateLookup'` fetches the document **when the event is read**: both of two updates showed the second state, and after a delete it was `null`. **Pre- and post-images** gave the exact before and after of each update, at the cost of a document in `config.system.preimages` per change. Resuming with a saved token works while the oplog still holds that point; with a 10 MB oplog it stopped working after about 29 MB of writes: **ChangeStreamHistoryLost (286)**.
</Tldr>

| Term | Meaning |
|---|---|
| Change stream | Aggregation cursor over the oplog: `collection.watch()`, `db.watch()` or a whole deployment |
| Resume token | Event `_id`; `resumeAfter` / `startAfter` continue after it |
| `updateDescription` | Default content of an update event: `updatedFields`, `removedFields`, `truncatedArrays` |
| `fullDocument: 'updateLookup'` | Read the current version of the document when the event is returned |
| Pre/post images | With `changeStreamPreAndPostImages` on the collection, the document before and after each change, stored in `config.system.preimages` |
| Majority commit point | Newest oplog entry known to be on a majority of voting members; change streams never go past it |
| Oplog window | Time between the oldest and newest oplog entry: how long a consumer can be away |

This is the safe default: a `w: 1` write that is later rolled back in a failover (Session 5) never reaches a consumer. The price is that change-stream lag includes replication lag to a majority.

## Update events and the full document

Order 200001 was inserted, updated to `paid`, updated to `shipped`, deleted. A stream resumed from before the insert, read after the delete:

| Event | Default | `fullDocument: 'updateLookup'` |
|---|---|---|
| insert | full document, status `placed` | same |
| update | `updatedFields: { status: 'paid' }` | `fullDocument: null` |
| update | `updatedFields: { status: 'shipped' }` | `fullDocument: null` |
| delete | `documentKey` only | same |

With order 10 updated to `paid` then `shipped` and read afterwards, **both** update events had `fullDocument.status = 'shipped'`: the lookup reads the document as it is now, not as it was at the event. With pre- and post-images enabled on the collection (`collMod … changeStreamPreAndPostImages: { enabled: true }`) and `fullDocument: 'required'`, `fullDocumentBeforeChange: 'required'`:

| Event | `fullDocumentBeforeChange.status` | `fullDocument.status` |
|---|---|---|
| first update | delivered | **paid** |
| second update | paid | shipped |

| Pre/post images cost (measured) | Value |
|---|---|
| Documents in `config.system.preimages` after 10,000 updates | 10,003 (one per change), 2,255 KB |
| 5,000 single updates, with vs without images, 3 alternating rounds | 12.6–16.6 s vs 8.2–13.0 s (slower in every round; noisy laptop numbers) |
| Retention | Expire with `expireAfterSeconds` or when the oplog entry is gone (from the documentation) |

## Resume tokens and the oplog window

A consumer stores the token of the last event it processed and resumes after it. That only works while the oplog still contains that point.

The oplog window is what matters, in time: `rs.printReplicationInfo()` on the lab's default set showed an oplog of 29,175 MB (5 % of free disk) but only 544 s of history, because the set was 9 minutes old. On a production set the window is "oplog size / write rate". Like MySQL and unlike a PostgreSQL slot, MongoDB does not keep oplog for a slow consumer (except a fixed `oplogMinRetentionHours`, from the documentation).

<Pitfall>
Do not build state from `updatedFields` plus `updateLookup` and assume each event shows the document at that moment. Under concurrent updates every event shows the latest version, and after a delete the lookup returns `null`. If consumers need exact before and after values (audit, sync to another store), enable pre- and post-images on those collections and pay the extra write.
</Pitfall>

## Real-world scenario: stock events for marketplace sync

A warehouse service writes stock levels in MongoDB; a sync worker watches the `stock` collection and pushes changes to Shopee, Lazada and TikTok Shop APIs. During a marketplace API outage the worker is stopped for 14 hours; the oplog window at peak is 9 hours. On restart: ChangeStreamHistoryLost, and the worker has no idea which SKUs changed.

| Control | Effect |
|---|---|
| Store the resume token after each successful push (not before) | Restart resumes exactly; a crash repeats at most the last event |
| Monitor the oplog window in hours against the worker's lag | Know before the token expires |
| Fallback full sync from the collection, with a `last_modified` field | A defined recovery when history is lost |
| Pre/post images only on collections whose consumers need them | Keeps the write cost where it buys something |

## Key takeaways

1. A change stream is a cursor over the oplog; each event has a resume token.
2. Events are delivered only once majority-committed: 3 ms normally, 5.1 s when the secondaries were paused for 5 s.
3. Update events carry only the changed fields; `updateLookup` returns the current document, not the one at the event.
4. Pre- and post-images give exact before and after values for an extra write per change.
5. Resuming works only inside the oplog window; outside it the error is ChangeStreamHistoryLost (286).
