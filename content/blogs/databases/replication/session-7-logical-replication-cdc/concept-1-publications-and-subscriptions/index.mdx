<Tldr>
Physical streaming (Session 1) ships WAL blocks to an exact, read-only copy of the whole server. **Logical replication** decodes the WAL into row changes (`INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`) for the tables in a **publication**, and a **subscription** on another, writable server applies them. In the lab the first copy of 100,000 orders took **0.41 s**, and single-row inserts arrived after **2.24 ms** (median; p95 5.0 ms). What it does **not** carry is the main source of incidents: **DDL** (one `ADD COLUMN` on the publisher stopped all apply until the subscriber had the column), **sequence values** (the subscriber's sequence stayed at 1, so its first insert failed with a duplicate key), and **conflicts** (a row written on the subscriber stopped apply until the transaction was skipped). Updates and deletes need a **replica identity**; a row filter on a column outside it blocks every `UPDATE` on the publisher.
</Tldr>

## Physical vs logical

| | Physical streaming (Session 1) | Logical replication |
|---|---|---|
| What is sent | WAL records: changed 8 KB pages | Row changes decoded from WAL |
| Target | Byte-identical standby, read-only | Any PostgreSQL server, writable, may have other tables and indexes |
| Scope | Whole server | Chosen tables, rows (row filter), columns (column list) |
| Versions | Same major version | Across major versions (used for upgrades) |
| DDL, sequences | Replicated (they are in the WAL) | **Not** replicated |
| Needs | `wal_level = replica` | `wal_level = logical` on the publisher |

| Term | Meaning |
|---|---|
| Publication | Named set of tables (and optional row filter / column list) whose changes are published: `CREATE PUBLICATION … FOR TABLE …` |
| Subscription | On the target: connection string + publications. Creates a **logical replication slot** on the publisher |
| Walsender | Publisher process that decodes WAL for one slot and streams it (plugin `pgoutput`) |
| Apply worker | Subscriber process that applies the stream, one transaction at a time, in commit order |
| Tablesync worker | Subscriber process that does the initial `COPY` of one table, then catches up |
| Replica identity | Which old-row columns are written to WAL for UPDATE/DELETE so the subscriber can find the row: primary key (default), a unique index, or FULL |
| **✓ / ✗** | Change applied / stuck or rejected |

<Pitfall>
Order DDL for a logical replica the way you order it for an old and a new application version: **add on the subscriber first, then on the publisher** (new columns, new tables); **drop on the publisher first** (and stop writing the column), then on the subscriber. A table added to the publication but missing on the subscriber fails the same way: `ERROR: logical replication target relation "public.audit_log" does not exist`, every 5 s.
</Pitfall>

## What is not replicated

| Object | What happened in the lab | Consequence |
|---|---|---|
| DDL | `ADD COLUMN` on the publisher only: apply stopped with "missing replicated column" | Run schema changes on both sides, in the right order |
| Sequence values | 1,000 rows copied into `refunds`; publisher `last_value` 1000, subscriber `last_value` 1, `is_called` f. First insert on the subscriber: `ERROR: duplicate key value violates unique constraint "refunds_pkey"`, `Key (id)=(1) already exists.` | Before switching writes to the subscriber (upgrade, migration), set every sequence with `setval` |
| Rows that existed before a table joined the publication, without `REFRESH PUBLICATION` | `audit_log` had row a before it was added; only later changes flowed. An UPDATE of both rows changed 2 rows on the publisher and 1 on the subscriber, with no error | Always `ALTER SUBSCRIPTION … REFRESH PUBLICATION` after adding a table: it runs the initial copy |
| Large objects, materialized views | Not tested; from the documentation: not replicated | Keep them out of logical designs |

## Replica identity: updates and deletes need a key

To apply an UPDATE or DELETE, the subscriber must find the old row, so the publisher writes the **replica identity** columns of the old row into the WAL.

| Table | Publisher statement | Result |
|---|---|---|
| `audit_log`, no primary key, default identity | `UPDATE audit_log SET msg = 'c'` | `ERROR: cannot update table "audit_log" because it does not have a replica identity and publishes updates`, HINT: set REPLICA IDENTITY using ALTER TABLE |
| same | `DELETE FROM audit_log` | `ERROR: cannot delete from table "audit_log" because it does not have a replica identity and publishes deletes` |
| same, `REPLICA IDENTITY FULL` | `UPDATE …` | ✓ UPDATE 2 (the whole old row is logged; the subscriber searches by all columns) |
| `orders`, default identity (primary key) | UPDATE of 10,000 rows | 2,447–2,553 kB of WAL, **251–261 bytes per row** (3 runs) |
| `orders`, `REPLICA IDENTITY FULL` | same UPDATE | 2,963–2,993 kB, **303–306 bytes per row**: +18 % |

These errors are raised on the **publisher**, to the application, the moment the table is in any publication that publishes updates or deletes. Adding a key-less table to a publication can break a production write path.

## Row filters and column lists

A publication can send only some rows (`WHERE`) and some columns (column list). Two rules, both measured:

1. A column used in the row filter must be part of the replica identity, or **every UPDATE and DELETE on the table fails on the publisher**. Creating `shopee_pub FOR TABLE orders … WHERE (marketplace = 'shopee')` with the default identity (primary key `id`) made `UPDATE orders SET status = status WHERE id = 1` fail with `ERROR: cannot update table "orders"`, `DETAIL: Column used in the publication WHERE expression is not part of the replica identity.` No subscriber existed yet.
2. With `REPLICA IDENTITY FULL`, a column list that leaves out a column fails the same way: `DETAIL: Column list used by the publication does not cover the replica identity.`

The fix used in the lab: a unique index that includes the filter column, used as the identity.

```sql
CREATE UNIQUE INDEX orders_id_mkt ON orders (id, marketplace);
ALTER TABLE orders REPLICA IDENTITY USING INDEX orders_id_mkt;
CREATE PUBLICATION shopee_pub FOR TABLE orders (id, seller_id, marketplace, status, amount, created_at)
  WHERE (marketplace = 'shopee');
```

## Conflicts: the subscriber is writable

Nothing stops an application from writing to the subscriber. In the lab, order 200000 was inserted on the subscriber, then a different order 200000 on the publisher:

```text
ERROR:  duplicate key value violates unique constraint "orders_pkey"
DETAIL:  Key (id)=(200000) already exists.
CONTEXT:  processing remote data for replication origin "pg_16395" during message type "INSERT"
          for replication target relation "public.orders" in transaction 942, finished at 0/535FAA8
```

Apply stopped there and retried every 5 s; a later ping did not arrive. PostgreSQL 17 does not resolve such conflicts. The two ways out are to fix the data on the subscriber (delete the local row) or to skip the remote transaction:

```sql
ALTER SUBSCRIPTION orders_sub SKIP (lsn = '0/535FAA8');
-- log: logical replication starts skipping transaction at LSN 0/535FAA8
-- log: logical replication completed skipping transaction at LSN 0/535FAA8
```

The ping arrived, and the copies now **disagree**: seller 1 / tiktok on the subscriber, seller 7 / shopee on the publisher. Skipping drops the **whole** remote transaction, including any other rows it changed. An UPDATE or DELETE whose row is missing on the subscriber produces no error at all in PostgreSQL 17: it is silently skipped (the `audit_log` case above).

## Real-world scenario: a reporting copy of orders

A marketplace team replicates `orders` and `order_items` to a reporting server with logical replication, so analysts can add their own indexes and tables. Three months later a developer adds `orders.voucher_code` in a migration that runs only on the primary. Reporting stops updating at the first order with a voucher; the slot on the primary holds WAL until the disk alert fires (Concept 2).

| Control | Effect |
|---|---|
| Migrations run against the subscriber first, then the publisher | New columns exist before the first row needs them |
| Alert on `pg_stat_subscription_stats.apply_error_count` increasing and on slot retained WAL | Minutes, not days, to notice |
| Reporting users get read-only roles on the subscriber | No local writes, no duplicate-key stops |
| Every replicated table has a primary key; key-less tables use `REPLICA IDENTITY FULL` knowingly (+18 % WAL per update here) | UPDATE/DELETE do not fail on the publisher |

## Key takeaways

1. Logical replication sends row changes for chosen tables to a writable server; the initial copy of 100,000 rows took 0.41 s and changes arrived in about 2 ms.
2. DDL is not replicated. A column added only on the publisher stops all apply; add on the subscriber first.
3. Sequence values are not replicated; set them before moving writes to the subscriber.
4. UPDATE and DELETE need a replica identity; without one they fail **on the publisher**. FULL works and costs WAL (+18 % per updated row here).
5. A row-filter column must be in the replica identity, or every UPDATE on the table fails.
6. Local writes on the subscriber cause conflicts that stop apply; skipping a transaction leaves the copies different.
