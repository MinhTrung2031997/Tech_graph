<Tldr>
MySQL has no slots and no decoding plugin: the **binlog** itself is the change stream. A CDC tool (Debezium, Maxwell, or the Python library used here) connects as if it were a replica, sends a `server_id` and a starting position (file and offset, or a GTID set), and receives row events. Measured on MySQL 8.4 with `binlog_format = ROW`: with `binlog_row_metadata = MINIMAL` the consumer saw `UNKNOWN_COL0 … UNKNOWN_COL5`; with **FULL** it saw column names. Each transaction came with its **GTID**, and an `ALTER TABLE` arrived as a statement, so unlike PostgreSQL the consumer **does see DDL**. `binlog_row_image = MINIMAL` made a 10,000-row update **5× smaller** (161,046 vs 822,952 bytes) but the consumer then got only the key before and the changed column after. The binlog is kept by **age** (`binlog_expire_logs_seconds`, 30 days by default) or by an explicit `PURGE`, never for a slow consumer: after a purge, the consumer and a stopped replica both failed with **error 1236**.
</Tldr>

| Term | Meaning |
|---|---|
| Binary log (binlog) | Ordered files `binlog.000001`, `binlog.000002`, … of committed transactions; feeds replicas, point-in-time recovery and CDC |
| `binlog_format = ROW` | Logs changed rows, not SQL text (default; needed for CDC) |
| `binlog_row_image` | FULL: all columns before and after (default). MINIMAL: key before, changed columns after. NOBLOB: FULL without unchanged BLOB/TEXT |
| `binlog_row_metadata` | MINIMAL (default): types only. FULL: also column names, primary key, enum/set strings |
| GTID | Global transaction id `source_uuid:n`; a consumer can resume from "all GTIDs I have seen" |
| `server_id` | Every binlog reader, replica or CDC tool, needs a unique id |
| Error 1236 | Source cannot serve the requested position: usually the binlog file was purged |

## Reading the binlog as a consumer

The `mysql:8.4` Docker image does not ship `mysqlbinlog`, so the lab uses the `mysql-replication` Python library (1.0.17) in a separate container on the same network: a 30-line consumer that prints each GTID, each statement and each row change. Debezium's MySQL connector works the same way.

```python
stream = BinLogStreamReader(
    connection_settings={"host": "rpd-my1", "port": 3306, "user": "root", "passwd": "lab"},
    server_id=99,                      # unique, like a replica
    log_file=sys.argv[1], log_pos=int(sys.argv[2]), resume_stream=True, blocking=False,
    only_events=[GtidEvent, QueryEvent, WriteRowsEvent, UpdateRowsEvent, DeleteRowsEvent])
```

## Row image: size against completeness

The same `UPDATE shop.orders SET amount = amount + 1 WHERE id <= 10000`, measured as the growth of the binlog position (3 runs each, identical):

| `binlog_row_image` | Bytes in the binlog | Per row | What a consumer gets for one UPDATE |
|---|---|---|---|
| FULL (default) | 822,952 | 82 | All 6 columns before and after |
| MINIMAL | 161,046 | 16 | Before: `id` only. After: `status` only; the other columns are `None` ("cols bitmap") |

MINIMAL is attractive for replication bandwidth, and a replica only needs the key and the changes. A CDC consumer that writes complete rows to a search index or a warehouse cannot rebuild the row from it. `binlog_row_image` can be set per session; CDC needs it FULL for every session that writes the captured tables, which in practice means the global default.

## Retention: the source does not wait

PostgreSQL keeps WAL for a slot until the consumer confirms it (Concept 2). MySQL has no such bookkeeping: a binlog file is removed when it is older than `binlog_expire_logs_seconds` (2,592,000 s, 30 days, in this lab) or when someone runs `PURGE BINARY LOGS`, whether or not a reader still needs it.

| | PostgreSQL logical slot | MySQL binlog reader |
|---|---|---|
| Source keeps the log for a slow reader | Yes, until confirmed (or `max_slot_wal_keep_size`) | No: by age or PURGE only |
| Failure mode of a dead reader | Source disk fills | Reader falls off the end and must resnapshot |
| Position | Slot's `confirmed_flush_lsn` (on the source) | File + offset or GTID set (kept by the reader) |
| DDL in the stream | No | Yes, as a statement event |
| Column names | Always (from the catalog via the slot) | Only with `binlog_row_metadata = FULL` |

<Pitfall>
Size binlog retention for your **slowest** reader, not for replicas that are normally seconds behind: a CDC connector that is paused over a holiday weekend, or one whose Kafka cluster is down, needs the binlog to still be there when it comes back. Alert on the consumer's lag in time against `binlog_expire_logs_seconds`, and never run `PURGE BINARY LOGS` without checking every reader's position (replicas: `SHOW REPLICAS` on the source; CDC tools: their offsets topic or state).
</Pitfall>

## Real-world scenario: syncing orders to a search index

A seller center shows orders from Elasticsearch, fed by Debezium from the MySQL primary. The DBA switches `binlog_row_image` to MINIMAL to cut replication traffic. The next day, edited orders in the seller center show blank buyer names and prices: each update event now carries only the changed column, and the connector writes those partial rows into the index.

| Setting for a CDC source | Why |
|---|---|
| `binlog_format = ROW` | Row changes, not SQL text |
| `binlog_row_image = FULL` | Consumers get the complete row before and after |
| `binlog_row_metadata = FULL` | Column names travel with the events; safer across DDL |
| `gtid_mode = ON` | Consumers resume by GTID set, also after a failover to a replica |
| `binlog_expire_logs_seconds` above the longest expected consumer outage | No error 1236 after a long pause |

## Key takeaways

1. A MySQL CDC tool is a binlog reader with its own `server_id`, like a replica.
2. Use `binlog_format = ROW`, `binlog_row_image = FULL` and `binlog_row_metadata = FULL` for CDC; MINIMAL images were 5× smaller and incomplete.
3. Every transaction has a GTID, and DDL appears in the stream as a statement.
4. The source keeps binlogs by age, not by reader: after a purge both the consumer and the replica failed with error 1236.
5. The reader owns its position; store it durably and alert on its lag in time.
