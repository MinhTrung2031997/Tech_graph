<Tldr>
Every CDC consumer does two things: **act** on a change (publish to Kafka, call an API, write elsewhere) and **confirm** its position (slot LSN, binlog GTID set, resume token). Confirm before acting and a crash **loses** events (at-most-once); act before confirming and a crash **repeats** them (at-least-once). Measured with an outbox relay on a PostgreSQL slot: five orders committed with five outbox rows; the relay peeked and published three, then "crashed" without confirming; after restart it saw **all five** again (three duplicates). Advancing the slot to the third transaction's COMMIT LSN left **exactly two**. `pg_logical_slot_get_changes` confirmed both remaining events in the same call that read them. PostgreSQL subscriptions get **exactly-once apply** by storing their position (replication origin) in the same transaction as the applied rows (from the documentation); a Kafka pipeline gets at-least-once, so consumers need **idempotency keys**.
</Tldr>

| Term | Meaning |
|---|---|
| At-most-once | Each change is delivered zero or one time: confirm, then act |
| At-least-once | Each change is delivered one or more times: act, then confirm |
| Exactly-once effect | At-least-once delivery + an idempotent action, or position and effect committed atomically |
| Outbox table | Table the application writes events into, in the same transaction as the business change; CDC publishes it |
| Logical message | `pg_logical_emit_message(transactional, prefix, content)`: an event in the WAL with no table |
| Replication origin | PostgreSQL's record of how far a subscriber has applied, updated in the same transaction as the applied changes |

## The outbox, captured by CDC

The dual-write problem: an order service updates `orders` and then publishes "OrderShipped" to Kafka. If it crashes between the two, the database and Kafka disagree. With an outbox, the event is a row in the **same transaction**, and CDC publishes committed outbox rows:

```sql
BEGIN;
UPDATE orders SET status = 'shipped' WHERE id = 1;
INSERT INTO outbox (aggregate_id, type, payload) VALUES (1, 'OrderShipped', '{"order_id": 1}');
COMMIT;
```

Concept 2 showed the alternative without a table: `pg_logical_emit_message(true, 'outbox', …)` inside the transaction appeared in the stream only if the transaction committed. Debezium's outbox event router and most relays use a table, because a table can be inspected, replayed and cleaned up.

## The same rule in every engine

| Engine | What the consumer confirms | At-least-once means |
|---|---|---|
| PostgreSQL slot | `confirmed_flush_lsn` (streaming feedback, `pg_replication_slot_advance`, or `get_changes`) | Advance after the action, to a COMMIT LSN |
| PostgreSQL subscription | Replication origin, committed **with** each applied transaction | Exactly-once apply, by design (from the documentation) |
| MySQL binlog reader | GTID set or file + offset, stored by the reader | Store after the action; on restart, send the stored GTID set |
| MongoDB change stream | Resume token, stored by the consumer | Store the token after the action |

The PostgreSQL subscription is exactly-once because its "action" (writing rows into the subscriber) and its "confirm" (advancing the replication origin) are one local transaction. Any consumer that writes into a database can copy that design: store the position in the same transaction as the effect. A consumer whose effect is outside a database (Kafka, an HTTP API) cannot, so it must make the effect idempotent.

## Making duplicates harmless

| Technique | How |
|---|---|
| Event id from the source | Use the outbox `id` (or LSN / GTID / resume token) as the message key; consumers keep a processed-ids table with a unique constraint |
| Idempotent writes | `INSERT … ON CONFLICT DO NOTHING` / `upsert` by business key; "set status = shipped" instead of "increment shipped count" |
| Ordering per key | Partition Kafka by `aggregate_id`, so all events of one order stay in order even when some are repeated |
| Version numbers | Carry the order's version; consumers ignore events with a version they already have |

<Pitfall>
Do not use the time an event was **received** to deduplicate. After a restart the duplicates arrive seconds or hours later. Use an id that the source assigned once: the outbox row id, or the change's LSN / GTID / resume token.
</Pitfall>

## Real-world scenario: marketplace order sync

An OMS publishes "OrderShipped" for every shipped order so that a sync service can push tracking numbers to Shopee, Lazada and TikTok Shop. After a relay restart, 3,000 events are published again; the sync service calls the marketplaces' "ship order" API twice for 3,000 orders. Two marketplaces return "already shipped" errors that page the on-call engineer; one accepts a duplicate tracking update.

| Fix | Effect |
|---|---|
| Relay confirms the slot only after Kafka acknowledges, to a COMMIT LSN | No lost events; duplicates limited to the last unconfirmed batch |
| Message key = outbox id; sync service keeps `processed_events (event_id PRIMARY KEY)` | Second delivery is a no-op |
| Sync service treats "already shipped" as success | Idempotent against the marketplace API too |
| Outbox rows deleted after N days by a job, not by the relay | Replays possible for incident recovery |

## Key takeaways

1. Delivery semantics come from the order of "act" and "confirm", not from the database.
2. A relay that confirmed nothing repeated three events after a crash; one that read with `get_changes` would have lost two.
3. Advance a PostgreSQL slot to a COMMIT LSN, after the action.
4. PostgreSQL subscriptions are exactly-once because the position commits with the applied rows; copy that when your effect is in a database.
5. Everything else needs idempotent consumers keyed by an id the source assigned.
