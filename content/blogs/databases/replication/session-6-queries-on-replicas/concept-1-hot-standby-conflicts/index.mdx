<Tldr>
A PostgreSQL standby must replay the primary's WAL exactly, including VACUUM removing old row versions. A long query on the standby may still need those versions. When the two collide, the standby can either **pause replay** or **cancel the query**. `max_standby_streaming_delay` decides how long it pauses before cancelling. With the default **30 s**, a 60-second report was cancelled after **33.5 s** with `canceling statement due to conflict with recovery` / `User query might have needed to see row versions that must be removed`, and for those 30 s replay stood still: the standby fell **29 s** behind. With **-1** (wait forever) the report finished and replay was blocked for **58 s**. With **5 s** the report died after **8.4 s** and replay barely lagged. DDL on the primary causes the same conflict through locks: adding a column cancelled a standby query with `User was holding a relation lock for too long`. There is no setting that gives both fresh replicas and unlimited queries.
</Tldr>

## The setup

`rpc-pg1` streams to `rpc-pg2`. Table `orders`, 1,000,000 rows, 73 MB. On the standby a report runs in one `REPEATABLE READ` transaction: count the new orders, `pg_sleep(60)`, count again. Three seconds in, the primary marks 100,000 orders as paid and runs `VACUUM orders`. A loop inserts a row on the primary every second and reads the standby's replay lag.

| Term | Meaning |
|---|---|
| Hot standby | A standby that accepts read-only queries while replaying WAL |
| Recovery conflict | Replaying a WAL record would remove data, or take a lock, that a running standby query still uses |
| `max_standby_streaming_delay` | How long replay waits for conflicting queries before cancelling them (default 30 s; -1 = forever) |
| Replay lag | `now() - pg_last_xact_replay_timestamp()`: how old the newest replayed commit is |
| `pg_stat_database_conflicts` | Per-database counters of cancelled queries by cause (snapshot, lock, buffer pin, deadlock) |
| **✓ / ✗** | Runs / waits or is cancelled |

## Measured

Same report and the same UPDATE + VACUUM each time; only the standby's setting changed.

| `max_standby_streaming_delay` | Report | Report ended after | Worst replay lag during the report |
|---|---|---|---|
| 30 s (default) | ✗ cancelled | 33.5 s | 29 s |
| 5 s | ✗ cancelled | 8.4 s | under 1 s (as sampled) |
| -1 | ✓ finished | 60.1 s | 58 s |

The replay lag is in **seconds of commits**, not bytes: the WAL waiting behind the conflict was only about 1.1 MB, because the primary was nearly idle. On a busy primary everything written during the pause waits: in Concept 2, five update rounds left the standby **122 MB** behind.

## Locks conflict too

Any command that takes an ACCESS EXCLUSIVE lock on the primary (ALTER TABLE, DROP, TRUNCATE, VACUUM truncating the end of a table) is replayed by taking the same lock on the standby. With the delay at 5 s, a 30-second standby query on `orders` and `ALTER TABLE orders ADD COLUMN note2 text` on the primary:

```
ERROR:  canceling statement due to conflict with recovery
DETAIL:  User was holding a relation lock for too long.
```

after 7.1 s. `pg_stat_database_conflicts` on the standby afterwards: `confl_snapshot = 2`, `confl_lock = 1`.

<Pitfall>
`max_standby_streaming_delay` is not a per-query timeout. It is the total time replay may fall behind **since the last WAL it received**, shared by every conflicting query. And a standby used for failover should not have -1: a standby that is far behind must replay everything it has received before it can serve as primary (from the documentation: WAL available locally is replayed before promotion completes), and WAL it has not received is the loss window from Session 5. Use separate replicas for long reports and for failover.
</Pitfall>

## Real-world scenario: the monthly seller report

A marketplace runs its monthly seller statements (a 40-minute query) on the only standby, which is also the failover target. It is cancelled every month with "conflict with recovery".

| Option | Effect |
|---|---|
| Raise `max_standby_streaming_delay` to 60 min | The report finishes; for 40 minutes the standby is up to 40 minutes stale, and failover would replay all of it first |
| `hot_standby_feedback = on` | No snapshot cancels; the primary keeps dead rows for 40 minutes (Concept 2). Lock conflicts still cancel |
| A second standby only for reports, with `-1` and no failover role | The report is safe and the failover standby stays fresh; costs one more server |
| Run the report from a logical replica or a nightly copy | No conflict with the primary at all; data is as old as the copy |

## Key takeaways

1. A standby must replay VACUUM's removals; a query whose snapshot still needs those versions conflicts with replay.
2. Replay waits up to `max_standby_streaming_delay`, then cancels the query: 33.5 s with the default 30 s, 8.4 s with 5 s.
3. With -1 the query always finishes and replay can fall behind without limit (58 s here).
4. ACCESS EXCLUSIVE locks replayed from the primary cancel standby queries the same way.
5. Fresh replicas and long queries pull in opposite directions; separate the roles.
