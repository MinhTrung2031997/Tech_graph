<Tldr>
An InnoDB replica serves reads from MVCC snapshots, so long queries do not block **row** changes coming from the source: during a 20-second SELECT, 100,000 updated rows arrived and `Seconds_Behind_Source` stayed **0**. There are no cancellations like PostgreSQL's. **DDL** is different: an `ALTER TABLE` from the source needs an exclusive metadata lock on the replica, so it waited for a 30-second SELECT, the applier showed **"Waiting for table metadata lock"**, and **everything behind it stopped**, including inserts into an unrelated table: lag climbed to **25 s** and caught up only when the SELECT ended. Apply speed is the other limit. Eight clients wrote 40,000 single-row transactions on the source in about 13–20 s; a replica with **1 worker** needed a median **73.4 s** to apply them, with **4 workers** (the default in 8.4) **28.3 s**, with 8 **35.7 s**.
</Tldr>

## The setup

`rpc-my1` → `rpc-my2`, GTID, row-based binlog, `replica_parallel_type = LOGICAL_CLOCK`, `replica_preserve_commit_order = 1`, and on both servers `sync_binlog = 1`, `innodb_flush_log_at_trx_commit = 1`, `log_replica_updates = 1`. Table `lab.orders`, 1,000,000 rows; table `lab.ev` for single-row inserts.

| Term | Meaning |
|---|---|
| Applier (SQL thread) | Reads the relay log and applies the source's transactions on the replica |
| `replica_parallel_workers` | Number of worker threads applying transactions in parallel (default 4 in MySQL 8.4) |
| Metadata lock (MDL) | Table-level lock every statement holds; DDL needs it exclusively |
| `Seconds_Behind_Source` | How old the transaction being applied is; 0 when the applier is idle |
| **✓ / ✗** | Applied / waiting |

## Measured: applying a backlog

The applier was stopped (`STOP REPLICA SQL_THREAD`), 8 clients each wrote 5,000 single-row autocommit inserts on the source, then the applier was started with a given number of workers and timed until the replica had all 40,000 rows. Three rounds; this laptop also ran other databases, so the spread is large.

| `replica_parallel_workers` | Apply time, 3 rounds | Median | Rate (median) |
|---|---|---|---|
| 1 | 55.5, 73.4, 92.4 s | 73.4 s | 545 txn/s |
| 4 (default) | 28.3, 46.5, 28.2 s | 28.3 s | 1,413 txn/s |
| 8 | 35.7, 21.7, 44.3 s | 35.7 s | 1,120 txn/s |

The source wrote the same 40,000 transactions in 12.5–20.3 s (about 2,000–3,200 per second). A single-threaded replica could not keep up with 8 writers: it would fall behind steadily under that load. Four workers more than doubled the apply rate; eight were no better on a laptop whose cores were shared with the source, the client and other containers.

Parallel apply works here because MySQL 8.4 tracks which transactions touch different rows (write sets) and lets those run on different workers, while `replica_preserve_commit_order = 1` still commits them in source order.

<Pitfall>
`Seconds_Behind_Source` reads 0 whenever the applier has caught up with what the replica has **received**, even if the newest transactions have not arrived yet because the network link is slow or stalled; it only becomes NULL when the replication threads stop. It also jumps from 0 to large values when a big transaction arrives (both from the documentation). For an honest lag figure compare GTID sets (`gtid_executed` on both sides) or use a heartbeat table written on the source every second (Session 3). And an online DDL that runs for 20 minutes on the source runs for about 20 minutes again on the replica, as one blocking event, after it has finished on the source (from the documentation).
</Pitfall>

## Real-world scenario: the nightly migration and the BI replica

A BI tool runs 10-minute queries on a MySQL replica. The team runs `ALTER TABLE orders ADD COLUMN …` on the source at 02:00, which finishes instantly there.

| What happens on the replica | Why |
|---|---|
| The ALTER waits for the BI query holding `orders` | Exclusive metadata lock vs the query's shared lock |
| All replication stops, for all tables | The applier applies DDL as a barrier |
| New BI queries on `orders` also wait | They queue behind the pending exclusive lock (the same lock queue as on a single server) |
| Application reads routed to the replica see data up to 10 minutes old | Lag grows for the whole duration |

| Fix | Effect |
|---|---|
| `max_execution_time` (or a kill script) for BI sessions during migration windows | Bounds the wait |
| A separate replica for BI, excluded from read routing | The stall hits only BI |
| Check `performance_schema.metadata_locks` on replicas before DDL | Know who will block the applier |

## Key takeaways

1. Long SELECTs on an InnoDB replica do not block row changes from the source: lag stayed 0.
2. DDL from the source waits for the metadata lock held by replica queries, and stops replication of every table behind it.
3. A single applier thread applied about 545 transactions per second, well below what 8 clients wrote on the source.
4. Four parallel workers (the 8.4 default) more than doubled the apply rate; more workers did not help on a small machine.
5. `Seconds_Behind_Source` is a rough indicator; use GTID comparison or a heartbeat for real lag.
