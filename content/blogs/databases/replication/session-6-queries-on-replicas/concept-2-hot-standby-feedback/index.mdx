<Tldr>
`hot_standby_feedback = on` makes the standby tell the primary the oldest transaction its queries still need, and the primary's VACUUM then keeps those row versions. Snapshot conflicts disappear, so a long report is no longer cancelled and replay does not pause. The price is paid **on the primary**: during one 75-second report, five rounds of updating 100,000 rows left **500,000 dead rows "not yet removable"**, and the table grew from **73 MB to 110 MB**. It did not shrink after the report ended: VACUUM then removed the 500,000 rows but kept the space. The alternative trade, feedback off with `max_standby_streaming_delay = -1`, kept the primary at **80 MB** and left the **standby 122 MB of WAL behind**. Feedback is a bloat setting as much as a replication setting.
</Tldr>

## The setup

`orders` recreated before each run (1,000,000 rows, 73 MB). On the standby, a report holds a `REPEATABLE READ` snapshot for 75 s. On the primary, five rounds, 5 s apart: `UPDATE orders SET status = 'rN' WHERE id <= 100000; VACUUM (VERBOSE) orders;`. Two standby configurations:

| Run | `hot_standby_feedback` | `max_standby_streaming_delay` | Who waits |
|---|---|---|---|
| feedback | on | 30 s | the primary's VACUUM |
| delay | off | -1 | the standby's replay |

| Term | Meaning |
|---|---|
| `hot_standby_feedback` | The standby regularly reports the oldest xmin its queries need to the primary (every `wal_receiver_status_interval`, 10 s by default) |
| xmin horizon | The oldest transaction id any snapshot still needs; VACUUM cannot remove row versions newer than it |
| Dead but not yet removable | VACUUM's count of dead row versions it had to keep because of the horizon |
| Bloat | Space in the table taken by dead versions or left empty after they are removed |
| **✓ / ✗** | Works / pays the cost |

## Measured

| | feedback on, delay 30 s | feedback off, delay -1 |
|---|---|---|
| Dead rows VACUUM had to keep, after round 1 → round 5 | 100,000 → 500,000 | 0 |
| Primary table size, before → after round 5 | 73 MB → 110 MB | 73 MB → 80 MB |
| Standby replay backlog after round 5 | 0 bytes | 122 MB |
| Report | ✓ finished | ✓ finished |
| After the report ended, VACUUM | removed 500,000; table **stayed 110 MB** | nothing left to remove; 80 MB |

The extra 30 MB is permanent until something rewrites the table (`VACUUM FULL`, `pg_repack`, or a dump and reload). Later inserts and updates reuse the free space inside it.

<Pitfall>
Feedback also travels through **cascading** standbys and survives short disconnects through the slot: a slot's `xmin` keeps holding back VACUUM even while the standby is down, until the standby reconnects with a newer horizon or the slot is dropped (from the documentation). A forgotten standby with feedback on and a slot is one of the classic causes of a primary that bloats without any long transaction visible in its own `pg_stat_activity`. Check `pg_replication_slots.xmin` and `pg_stat_replication.backend_xmin` whenever `n_dead_tup` keeps climbing.
</Pitfall>

## Real-world scenario: an analytics team on the standby

The analytics team runs 2-hour queries on the standby, and turned on `hot_standby_feedback` because their queries kept being cancelled. Three weeks later the primary's `orders` table is 3× its normal size and checkout queries are slower.

| Finding | From this concept |
|---|---|
| `n_dead_tup` on `orders` in the millions, VACUUM logs "dead but not yet removable" | The standby's xmin, visible in `pg_replication_slots.xmin`, holds the horizon for 2 hours at a time |
| No long transaction on the primary | The holder is on the standby |
| Table does not shrink after the queries stop | VACUUM frees space for reuse but does not return it |

| Fix | Effect |
|---|---|
| A separate analytics replica with feedback **off** and delay -1 | The primary is unaffected; only the analytics replica lags during long queries |
| Logical replication into an analytics database | Long queries there do not touch the primary's horizon at all (Session 7) |
| `statement_timeout` for the analytics role | Bounds how long the horizon can be held |
| `pg_repack` once the cause is gone | Gets the space back without a long ACCESS EXCLUSIVE lock (from the documentation) |

## Key takeaways

1. `hot_standby_feedback = on` prevents snapshot conflicts by making the primary keep row versions that standby queries need.
2. The cost lands on the primary: 500,000 dead rows kept and 73 → 110 MB in one 75-second report.
3. The space stays allocated after the report ends.
4. The alternative (-1 without feedback) keeps the primary clean and lets the standby fall behind: 122 MB of WAL.
5. With a slot, the standby's horizon shows in `pg_replication_slots.xmin` and persists while the standby is away.
