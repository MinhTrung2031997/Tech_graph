<Tldr>
MongoDB secondaries apply the oplog in batches and serve reads from a storage-engine snapshot, so a long read and replication do not wait for each other: replication lag stayed **0–2 s** whether or not a seller aggregation was running on the secondary, and nothing was cancelled. The read itself pays for sharing the node: the aggregation over 1,000,000 orders took **151–182 ms** on an idle secondary and **418–577 ms** while 8 writers updated about 6,300–7,000 orders per second on the primary (all on one laptop, so part of that is shared CPU). The real limit is **history**: a read with `readConcern: "snapshot"` must finish within `minSnapshotHistoryWindowInSeconds`. With the default **300 s** a 28-second snapshot read succeeded; with the window lowered to **5 s** the same read failed after 15 s with **SnapshotTooOld**. Reads without snapshot read concern have no such limit, but they are not a single point in time either.
</Tldr>

## The setup

Replica set `rpcrs` (3 members). Collection `lab.orders`, 1,000,000 documents (`seller_id`, `status`, `amount`). The reads run on `rpc-mongo2`, a secondary, with read preference `secondary`. Writers run in a separate container: 8 processes, each updating random orders with `w: 1` for 30 s.

```js
// the report: GMV per seller
db.orders.aggregate([{ $group: { _id: '$seller_id', n: { $sum: 1 }, gmv: { $sum: '$amount' } } }, { $count: 'sellers' }])
```

| Term | Meaning |
|---|---|
| Read preference | Which member a read goes to: `primary`, `primaryPreferred`, `secondary`, `secondaryPreferred`, `nearest` |
| Oplog batch application | A secondary fetches oplog entries and applies them in parallel batches; readers see the state at a batch boundary |
| `readConcern: "snapshot"` | All batches of a cursor read the same point in time |
| `minSnapshotHistoryWindowInSeconds` | How long WiredTiger keeps old versions for snapshot reads (default 300) |
| Hidden member | A member that receives the oplog but is invisible to clients' read preference; used for analytics or backups |
| **✓ / ✗** | Runs / fails or slows down |

## Measured

| Secondary workload | Aggregation over 1M orders | Secondary lag (sampled each second) |
|---|---|---|
| idle | 151–182 ms | 0 |
| 8 writers on the primary, no report | — | 0–2 s |
| 8 writers + report looping on the secondary | 418–577 ms | 0–2 s |

| Snapshot read on the secondary (1M documents, 15 s pause, 4 writers) | Result |
|---|---|
| `minSnapshotHistoryWindowInSeconds = 300` (default) | ✓ 1,000,000 documents in 28,082 ms |
| `minSnapshotHistoryWindowInSeconds = 5` | ✗ SnapshotTooOld after 15,042 ms |

Compared with the other engines on the same kind of test:

| | PostgreSQL standby | MySQL replica | MongoDB secondary |
|---|---|---|---|
| Long read vs replicated row changes | conflict: pause replay or cancel the query (Concept 1) | no conflict | no conflict |
| Long read vs replicated DDL | lock conflict, cancel after the delay | applier waits, replication stops (Concept 3) | DDL is replicated as an oplog entry; collection drops kill cursors (Partitioning and sharding Session 4) |
| Limit on a single long read | `max_standby_streaming_delay` or feedback bloat | none from replication | snapshot reads: `minSnapshotHistoryWindowInSeconds` |

<Pitfall>
Without `readConcern: "snapshot"`, a long query on a secondary (or a primary) is **not** a point-in-time read. Its cursor yields between batches and can see documents that changed after it started; a report summing balances while transfers run can count money twice or not at all (from the documentation on read isolation). Raising `minSnapshotHistoryWindowInSeconds` to make long snapshot reads possible keeps more old versions in the WiredTiger cache on **every** member, which increases cache pressure under heavy writes. For hour-long analytics, use a hidden member or an analytics node with its own tag, and accept that its reports are as of "now-ish".
</Pitfall>

## Real-world scenario: seller dashboards on secondaries

A marketplace serves seller dashboards from secondaries (`readPreference: secondaryPreferred`) to keep load off the primary, and runs a nightly GMV export on the same secondaries.

| Observation | From this concept |
|---|---|
| Dashboards slow down during flash-sale traffic, though nothing is "blocked" | The secondaries apply the primary's write load too; reads share the machine (aggregation 3× slower under writes) |
| The export never gets cancelled, unlike on the old PostgreSQL setup | Secondaries do not cancel reads for replication |
| The export's totals do not match the primary's at any single moment | It reads without snapshot read concern over minutes |
| Switching the export to `readConcern: "snapshot"` would make it fail once it runs past 5 minutes | `SnapshotTooOld` when a read outlives the 300 s history window |

A fix: a **hidden** fourth member (priority 0, `hidden: true`) for exports, so dashboards and the export no longer compete, and exports split per seller range, each a short snapshot read.

## Key takeaways

1. A MongoDB secondary neither cancels long reads nor pauses replication for them: lag stayed 0–2 s with an aggregation running.
2. Reads on a secondary share the node with oplog application: the aggregation took 3× longer under write load here.
3. Snapshot reads must finish within `minSnapshotHistoryWindowInSeconds` (300 s by default); past it they fail with SnapshotTooOld.
4. Reads without snapshot read concern have no time limit but are not a consistent point in time.
5. For heavy analytics, use a hidden or tagged member so it does not slow the members serving the application.
