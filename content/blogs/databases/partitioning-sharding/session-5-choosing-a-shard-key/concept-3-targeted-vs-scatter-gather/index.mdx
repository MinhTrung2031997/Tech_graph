<Tldr>
The router (MongoDB `mongos`, the Citus coordinator) can send a query to **one shard** only when the filter pins the shard key to one value (or a range, for ranged keys). Every other query is **scatter-gather**: sent to all shards, results merged by the router. On MongoDB `explain` says `SINGLE_SHARD` or `SHARD_MERGE`; on Citus `EXPLAIN` shows `Task Count: 1` or `Task Count: 32`. The same "seller 42 in March" query ran **5,228 vs 3,908 queries/s** on MongoDB (key `seller_id` vs hashed `_id`, two shards) and **8,898 vs 576 transactions/s** on Citus (distributed by `seller_id` vs `id`, 32 shards). The reverse holds too: a lookup by order id dropped from **9,349 to 651 tps** on the table distributed by seller. **Pick the key your most frequent queries filter on.**
</Tldr>

## The setup

The five MongoDB copies from Concepts 1–2, each with the same secondary indexes (`{ seller_id: 1, created_at: 1 }` and `{ created_at: 1 }`) so that only routing differs, and two Citus tables with the same indexes:

| Collection / table | Shard key / distribution column |
|---|---|
| `o_hashed` | `{ _id: 'hashed' }` |
| `o_range` | `{ _id: 1 }` |
| `o_seller` | `{ seller_id: 1 }` |
| `o_mkt` | `{ marketplace: 1 }` |
| `o_seller_time` | `{ seller_id: 1, created_at: 1 }` |
| `c_by_id` (Citus) | `id` |
| `c_by_seller` (Citus) | `seller_id` (primary key `(seller_id, id)`, plus an index on `id`) |

| Term | Meaning |
|---|---|
| Targeted query | The router can compute the single shard that holds every possible match from the filter |
| Scatter-gather | The router sends the query to every shard and merges the answers |
| `SINGLE_SHARD` / `SHARD_MERGE` | MongoDB explain: top stage for a targeted / scatter-gather query |
| Router query / `Task Count` | Citus: a query answered by one shard; Task Count is how many shard queries the coordinator runs |
| **✓ Asked / ✗ Skipped** | The router sends the query to that shard / does not |

## Measured: which queries are targeted

MongoDB `explain('executionStats')` through `mongos` (1 = `SINGLE_SHARD`, 2 = `SHARD_MERGE` on both shards). Latency is the median of 5 runs and is 0–3 ms for every small query; the month query returns 42,408 documents and took 87–119 ms on every key.

| Query | hashed `_id` | ranged `_id` | `seller_id` | `marketplace` | `{ seller_id, created_at }` |
|---|---|---|---|---|---|
| `_id: 777777` | **1** | **1** | 2 | 2 | 2 |
| `seller_id: 42` | 2 | 2 | **1** | 2 | **1** |
| March 2025 | 2 | 2 | 2 | 2 | 2 |
| seller 42 + March | 2 | 2 | **1** | 2 | **1** |
| lazada + seller 42 | 2 | 2 | **1** | **1** | **1** |

Throughput of "seller 42 in March" with random sellers:

| System | Targeted | Scatter-gather | Ratio |
|---|---|---|---|
| MongoDB, 2 shards: 4 clients × 1,500 queries, median of 5 rounds (includes client start-up) | 5,228 q/s (`o_seller`) | 3,908 q/s (`o_hashed`) | 1.3× |
| Citus, 32 shards: pgbench 4 clients, median of 3 | 8,898 tps (`c_by_seller`) | 576 tps (`c_by_id`) | 15× |

Why the gap differs: on MongoDB scatter-gather here means 2 shard queries instead of 1; on Citus it means 32 shard queries instead of 1. The cost of a fan-out grows with the number of shards, and adding shards makes targeted queries cheaper per shard but scatter-gather queries more expensive. (The Citus containers run under amd64 emulation on this Mac, which inflates per-task overhead; compare the ratio, not the absolute numbers, with other systems.)

<Pitfall>
"Our month report is a scatter-gather query, so it is slow" is usually the wrong conclusion. A report that reads a large share of the data is scatter-gather by nature and benefits from shards working in parallel (Concept 2 showed a 10,000-row range finishing faster on two shards). The queries to protect are the **small, frequent** ones (a seller's dashboard, an order lookup): those should hit one shard, because fanning them out multiplies their cost by the shard count while their result stays tiny.
</Pitfall>

## Real-world scenario: seller centre vs customer service

A marketplace operations platform has two hot read paths: the seller centre ("my orders this month", by seller) and customer service ("look up order 123456789", by order id). Sharding by `seller_id` makes the first targeted and the second a fan-out. Common fixes:

| Option | Effect |
|---|---|
| Put the seller id into the order number or the lookup request | Customer service sends `seller_id` + `id`: targeted |
| A small lookup collection / table `order_id → seller_id`, sharded by order id | Two targeted queries instead of one fan-out |
| Accept the fan-out for the rare path | Fine if order lookups are a small share of traffic |

## Key takeaways

1. A query is targeted only if its filter pins the shard key; otherwise every shard is asked.
2. MongoDB explain shows `SINGLE_SHARD` or `SHARD_MERGE`; Citus shows `Task Count`.
3. A shard with no matching data is still asked (0 keys examined) if the key is not in the filter.
4. Fan-out cost grows with shard count: 1.3× on 2 MongoDB shards, 15× on 32 Citus shards.
5. Choose the key your small, frequent queries filter on; let big reports fan out.
