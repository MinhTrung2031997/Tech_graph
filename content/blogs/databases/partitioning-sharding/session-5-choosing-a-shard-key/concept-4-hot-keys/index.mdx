<Tldr>
**Frequency** is the second property of a shard key: how many rows share one value. All rows with the same key value live in the same range or shard, so the biggest value sets a floor on one shard's data and write load. With one seller owning **20% of the orders (200,153 of 1,000,000)**: MongoDB refused to move that seller's range (**"the maximum number of documents for a chunk is 71088 … Found 200153 documents"**); Citus put it in one shard of **24 MB** against a median of **3.4 MB**; and all **50,000 new orders** for the seller went to **one shard** in both systems. A compound key `{ seller_id, created_at }` let MongoDB cut the seller's **stored** orders into 6 time slices that can move, but new orders still all hit the latest slice. A hashed `_id` spread them **25,088 / 24,912**, at the cost of fanning out every seller query (Concept 3).
</Tldr>

## The setup

Copies of the 1M orders where every fifth order belongs to seller 1, the way one brand's flagship store can dominate a marketplace account:

```js
const hot = d => { if (d._id % 5 === 0) d.seller_id = 1; return d; };   // seller 1: 200,153 orders
sh.shardCollection('pt5.o_hot_s',  { seller_id: 1 })
sh.shardCollection('pt5.o_hot_st', { seller_id: 1, created_at: 1 })
```

```sql
CREATE TABLE c_hot (LIKE orders);
ALTER TABLE c_hot ADD PRIMARY KEY (seller_id, id);
SELECT create_distributed_table('c_hot', 'seller_id');
INSERT INTO c_hot SELECT id, CASE WHEN id % 5 = 0 THEN 1 ELSE seller_id END, marketplace, status, amount, created_at FROM orders;
```

Then 50,000 new orders for seller 1 (ids from 2,000,001, timestamps from 2026-01-01) are inserted and counted per shard.

| Term | Meaning |
|---|---|
| Frequency | Share of rows with the same key value; here seller 1 has 20% |
| Hot key | A key value that receives a large share of reads or writes |
| Compound shard key | Several fields; ranges can be cut between values of the second field when the first is equal |
| Tenant isolation | Citus: `isolate_tenant_to_new_shard` gives one distribution value its own shard |
| **✓ / ✗** | The shard receives / does not receive the rows |

## Measured

| | `{ seller_id }` (MongoDB) | `{ seller_id, created_at }` (MongoDB) | hashed `_id` (MongoDB) | `seller_id` (Citus) |
|---|---|---|---|---|
| Where seller 1's 200,153 stored orders live | 1 range on sh1 | 6 ranges | both shards | 1 shard, 24 MB (median 3.4 MB) |
| Can that data be moved in pieces? | **No**: moveRange refused (max 71,088 docs) | Yes: one slice, 35,543 docs, moved in 320 ms | not needed | Only as one shard (isolate, then move: 0.93 s + 1.24 s) |
| 50,000 new seller-1 orders | sh1 +50,000 / sh2 0 | sh1 +50,000 / sh2 0 | 25,088 / 24,912 | w1 +50,000 / w2 0 |
| Seller 1's queries | targeted | targeted | scatter-gather | targeted |

<Pitfall>
A compound key with a timestamp second (`{ seller_id: 1, created_at: 1 }`) is the standard answer to "one tenant is too big", and it does fix **storage**: the big seller's history can be cut and spread. It does not fix **write load**: the newest orders of a seller always sort into that seller's last range. If one seller's write rate is more than one shard can take, the key must put something before the seller (a hash of the order id, or a bucket number such as `id % 8`) and seller queries must then ask several shards.
</Pitfall>

## A checklist for choosing a key

| Check | How to test it on your data | Warning sign |
|---|---|---|
| **Cardinality** | `count(DISTINCT key)` | Fewer distinct values than shards you will ever want (Concept 1) |
| **Frequency** | Top 10 values by `count(*)` and their share | One value above (1 / number of shards) of rows or writes |
| **Monotonicity** | Is the key a sequence, timestamp or ObjectId? | Ranged sharding on it: every insert hits one shard (Concept 2) |
| **Query targeting** | List the 5 most frequent queries; does each filter on the key? | A frequent small query that does not (Concept 3) |
| **Write spread** | Where does the next 1% of inserts go? | All to one range / one shard |
| **Uniqueness needs** | Must something be unique across all shards? | A unique value that is not the key (Session 3's rule applies again) |

For `orders` in a marketplace business the measurements point to:

| Option | Seller queries | Order lookups | New-write spread | Hot seller |
|---|---|---|---|---|
| `seller_id` (Citus) / `{ seller_id, created_at }` (MongoDB) | **targeted** | fan-out unless seller is known | even across sellers | stuck on one shard |
| hashed order id | fan-out | **targeted** | **even** | spread |
| `marketplace`, `created_at` | — | — | uneven / one shard | — (rejected in Concepts 1–2) |

Most seller-facing platforms choose the seller as the key and handle the few giant sellers separately (isolation, or a bucket added to their key). Sessions 6–8 build on this: moving data between shards, sharding with Citus in practice, and what breaks when one operation needs two shards.

## Real-world scenario: the flagship store

A brand's official store accounts for a fifth of all orders on a marketplace account. On a mega-sale day its order rate triples. With a seller key, one shard takes that whole burst while the others idle, and its range or shard cannot be split to share the load. Two practical paths, both measured above in their basic form: give the store its own shard and the strongest machine (Citus tenant isolation, or a MongoDB zone for that seller), or key the store's orders by `{ seller_id, bucket }` with a small bucket number so its writes spread over several ranges.

## Key takeaways

1. All rows with the same key value stay together: the most frequent value sets a floor on one shard's load.
2. MongoDB refused to move a 200,153-document single-seller range (limit 71,088 at 4 MB ranges).
3. A compound key with time lets the seller's history be cut and moved, but new orders still go to one shard.
4. Citus can isolate a tenant into its own shard (colocated tables split too) and move it, but cannot split it.
5. Only a key that does not start with the hot value spreads its writes, and then its queries fan out.
