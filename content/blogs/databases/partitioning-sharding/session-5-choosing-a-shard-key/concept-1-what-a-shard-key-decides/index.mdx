<Tldr>
A **shard key** (MongoDB) or **distribution column** (Citus) is the field the cluster uses to decide which shard owns a row. It decides three things at once: **where the data sits**, **where each write goes** and **which queries can be answered by one shard**. You cannot spread data more finely than the key's distinct values. Sharding 1,000,000 orders by `marketplace` (3 values) gave MongoDB **3 ranges, 2 of them marked jumbo**, and a split of **800,496 vs 199,504 documents (90 MB vs 22 MB)** that the balancer can never fix. Citus hashed `shopee` and `tiktok` into the **same shard**, so **2 of 32 shards** held all the rows (59 MB on one worker, 15 MB on the other). With `seller_id` (5,000 values) both systems spread the same data evenly.
</Tldr>

## The setup

The lab clusters from the [Session 5 lab](/blogs/databases/partitioning-sharding/session-5-choosing-a-shard-key/lab): MongoDB with two shards (`sh1`, `sh2`) behind a `mongos` router, and Citus with a coordinator and two workers (`w1`, `w2`). Each holds the same 1,000,000 `orders` (2024–2025, 5,000 sellers, `marketplace` shopee 50% / tiktok 30% / lazada 20%). The MongoDB copies were sharded while empty, then loaded in id order; each collection's range size was set to 4 MB so 113 MB of data is enough for the balancer to act:

```js
sh.shardCollection('pt5.o_mkt', { marketplace: 1 })
db.adminCommand({ configureCollectionBalancing: 'pt5.o_mkt', chunkSize: 4 })   // MB, this collection only
```

| Term | Meaning |
|---|---|
| Shard key / distribution column | The field (or fields) whose value decides which shard owns a row |
| Range (chunk) | MongoDB: a contiguous interval of shard-key values, owned by one shard, listed in `config.chunks` |
| Hash shard | Citus: a range of hash values of the distribution column (32 by default), placed on one worker |
| Cardinality | How many distinct values the key has: 3 for `marketplace`, 5,000 for `seller_id`, 1,000,000 for `id` |
| Jumbo range | A range bigger than the range size that cannot be split, because every row in it has the same key value |
| Balancer | MongoDB background process that moves ranges until shards hold similar amounts of data (difference under 3 × range size) |
| **✓ / ✗** | The shard receives / does not receive the rows |

## Measured

| Key | System | Ranges / shards with data | Split between the two shards |
|---|---|---|---|
| `marketplace` (3 values) | MongoDB | 3 ranges, 2 jumbo | **800,496 / 199,504 docs** (90 / 22 MB) |
| `marketplace` (3 values) | Citus | **2 of 32** shards | 59 MB / 15 MB |
| `seller_id` (5,000 values) | MongoDB | 8 ranges after 7 migrations | 524,687 / 475,313 docs (59 / 53 MB) |
| `seller_id` (5,000 values) | Citus | 32 of 32 | 16 shards per worker, 4.8–6.2 MB each |
| `id` (1,000,000 values) | Citus | 32 of 32 | 5.5–5.8 MB each |

The three properties to check for any candidate key:

| Property | Question | Bad here |
|---|---|---|
| **Cardinality** | How many distinct values? It caps how many pieces the data can be cut into | `marketplace`: 3 |
| **Frequency** | Does one value hold a large share of rows? That value's rows can never be split | A seller with 20% of orders (Concept 4) |
| **Monotonicity** | Do new values always go up (ids, timestamps)? With ranges, every insert hits the last range | Ranged `_id`, `created_at` (Concept 2) |

<Pitfall>
A low-cardinality key looks fine on day one: three ranges on two shards is "balanced enough". It becomes a dead end when you add a third, fourth or tenth shard: with three values there are never more than three units to move, and the biggest value's share (here shopee, 50%) is the floor for one shard's load. Changing the key later means resharding the whole collection (Session 6) or redistributing the table.
</Pitfall>

## Real-world scenario: sharding by country or marketplace

A team sharding a multi-country order table proposes `country` as the key because "every query filters on it". With Vietnam, Thailand and a handful of other markets, that key has single-digit cardinality and very uneven frequency: the largest market's rows can never leave one shard. Keep `country` as a **query filter**, and pick a key with many values that the main queries also filter on (a seller or shop id), or a compound key with `country` first and a high-cardinality field second.

## Key takeaways

1. The shard key decides data placement, write routing and query targeting at once.
2. Data can be cut into at most as many pieces as the key has distinct values.
3. `marketplace` (3 values): MongoDB ended with 2 jumbo ranges and an 80/20 split; Citus filled 2 of 32 shards.
4. `seller_id` (5,000 values) spread evenly in both systems.
5. Check cardinality, frequency and monotonicity before choosing.
