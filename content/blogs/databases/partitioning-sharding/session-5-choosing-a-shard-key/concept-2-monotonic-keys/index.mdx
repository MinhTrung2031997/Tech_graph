<Tldr>
A **monotonic** key only grows: order ids, `created_at`, ObjectIds. With **range** sharding, the newest values all fall into the **top range**, which one shard owns, so that shard takes every insert. Measured on MongoDB: after loading 1M orders by ranged `_id`, inserting the next **100,000 orders put 100,000 on `sh2` and 0 on `sh1`**. A **hashed** `_id` split the same inserts **50,097 / 49,903**, and Citus, which always hashes, split them **50,063 / 49,937** across its workers (3,027–3,235 per shard). Hashing has a price: a query for a **range** of ids is targeted with ranged sharding (one shard, 10,000 docs) and goes to every shard with hashing (2 MongoDB shards; 32 Citus shards).
</Tldr>

## The setup

Two MongoDB copies of the 1M `orders`, sharded while empty and loaded in id order (4 MB range size), and the Citus table `c_by_id` distributed on `id`:

```js
sh.shardCollection('pt5.o_range',  { _id: 1 })          // ranged
sh.shardCollection('pt5.o_hashed', { _id: 'hashed' })   // hashed
```

```sql
SELECT create_distributed_table('c_by_id', 'id');       -- Citus: always hash
```

New orders are the next 100,000 ids (1,000,001 – 1,100,000), inserted with balancing switched off **for that collection only** (`sh.disableBalancing('pt5.o_range')`) so nothing moves during the count. Per-shard counts come from `$collStats` and `$shardedDataDistribution`.

| Term | Meaning |
|---|---|
| Monotonic key | Each new value is larger than all earlier ones (ids from a sequence, timestamps, ObjectIds) |
| Ranged sharding | Each shard owns contiguous intervals of the key; neighbouring values live together |
| Hashed sharding | Each shard owns intervals of **hash(key)**; neighbouring values are scattered |
| Top range | The range ending at MaxKey; every value larger than all existing ones falls into it |
| Owned / orphan documents | Documents a shard is responsible for / copies left behind after a range moved away, deleted later |
| **✓ / ✗** | The shard receives / does not receive the new rows |

## Citus: the hash is built in

## Measured

| | Ranged `_id` (MongoDB) | Hashed `_id` (MongoDB) | Hash on `id` (Citus) |
|---|---|---|---|
| Where 100,000 new orders went | **sh2 100,000 / sh1 0** | 50,097 / 49,903 | w1 50,063 / w2 49,937 |
| Migrations to balance the 1M load | 13, then 1 more after the new batch | 0 | 0 (shards are fixed hash ranges) |
| Query `_id` / `id` from 500,000 to 509,999 | **1 shard**, 10,000 docs, 51 ms | 2 shards (5,047 + 4,953 docs), 26 ms | 32 tasks |
| Lookup of one id | 1 shard | 1 shard | 1 task |

Two honest notes on this lab:

- Both MongoDB shards run on one laptop, so the 1M load took the same time either way (8.5 s ranged, 8.3 s hashed). On separate machines, ranged inserts are limited by **one** shard's write capacity no matter how many shards you add; that conclusion follows from the routing above, not from a timing here.
- The id-range query was **faster** hashed (26 ms vs 51 ms) because both shards worked in parallel on a 10,000-row result. Scatter-gather costs more total work and more connections (Concept 3), but for a large result it can finish sooner.

<Pitfall>
`created_at` is monotonic too. Sharding orders by `{ created_at: 1 }` "so monthly reports are targeted" sends every new order to the shard that owns the present, and that shard also serves most reads, because recent orders are the hot ones. A compound key that starts with a high-cardinality field (`{ seller_id: 1, created_at: 1 }`) or a hashed key avoids the single hot shard.
</Pitfall>

## Real-world scenario: flash sale on a ranged key

On a 12.12 sale the order rate jumps tenfold. With a ranged, monotonic key every one of those inserts hits the shard holding the top range; the other shards are idle for writes, and the balancer starts moving freshly written ranges off the busy shard at the worst moment, adding migration work to it. With a hashed key or a seller-first compound key, the same burst spreads over all shards from the first second.

## Key takeaways

1. With ranged sharding, a monotonic key sends every new insert to the shard that owns the top range: 100,000 vs 0 here.
2. The balancer moves data only after it is written, so it never removes the insert hotspot.
3. Hashed sharding (MongoDB `'hashed'`, every Citus table) spread the same inserts about 50/50.
4. Hashing turns a range query on the key into a query to every shard.
5. A hashed collection that is empty when sharded starts with ranges on every shard, so no migrations are needed.
