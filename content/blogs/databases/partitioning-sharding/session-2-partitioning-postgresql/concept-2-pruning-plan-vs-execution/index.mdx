<Tldr>
**Partition pruning** removes partitions that cannot contain matching rows. PostgreSQL does it at three moments, and EXPLAIN shows each differently. **While planning**, when the key is compared with a constant: the plan lists only `orders_p_2025_03`. **When the executor starts**, when the value is known only then (a parameter in a generic plan, `now()`): `Subplans Removed: 23`. **During execution**, when the value changes per row (a nested loop over two promo days, a sub-select): the other partitions show `(never executed)`. On the month query, pruning read **1,982 buffers in 8.5 ms instead of 46,736 in 71.0 ms** when each partition is read in full. But the plain `orders` table with an index on `created_at` answered the same query in **8.6 ms**: on reads, pruning mostly buys what a good index already gives.
</Tldr>

## The setup

`orders_p` from Concept 1: 24 monthly partitions, each with its own index on `created_at`. The query sums one month:

```sql
SELECT count(*), sum(amount) FROM orders_p
WHERE created_at >= '2025-03-01' AND created_at < '2025-04-01';   -- 212,039 rows
```

| Term | Meaning |
|---|---|
| Plan-time pruning | The planner compares constants in the WHERE clause with each partition's bounds and leaves non-matching partitions out of the plan |
| Initial (executor-startup) pruning | The plan contains all partitions; when execution starts and parameter values are known, non-matching ones are removed. EXPLAIN: `Subplans Removed: N` |
| Execution-time pruning | The value changes while the query runs (e.g. per outer row of a nested loop); partitions that never match are skipped. EXPLAIN ANALYZE: `(never executed)` |
| Generic plan | A plan for a prepared statement built without knowing parameter values, reused across executions |
| `enable_partition_pruning` | Session setting (default on) that allows all three kinds |
| **✓ Scanned / ✗ Pruned** | The partition is read / it is skipped |

## What pruning is worth here

Median of 5 runs, `max_parallel_workers_per_gather` at its default (2):

| Query | `orders` (plain, index on `created_at`) | `orders_p` (pruned) | `orders_p` (pruning off) |
|---|---|---|---|
| One month (212,039 rows) | **8.6 ms**, 3,113 buffers | **8.4 ms**, 1,982 buffers | 8.6 ms |
| One day (6,840 rows) | 0.4 ms | 0.5 ms | not measured |
| Whole table | **92.1 ms** | **118.9 ms** | — |
| One month, index scans disabled | 67.0 ms, 46,729 buffers | **8.5 ms**, 1,982 buffers | 71.0 ms, 46,736 buffers |

Two honest conclusions:

1. Pruning is a **coarse index**: it skips 23 of 24 partitions, which is worth 8× when the alternative is reading everything.
2. Here the plain table already had that: `orders` is stored in `created_at` order (ids grow with time), so an index range scan touches only March's pages. Pruning helped reads only marginally (1,982 vs 3,113 buffers), and reading the **whole** table was 29% slower partitioned. The bigger wins of partitioning are elsewhere: dropping a month (Session 4) and per-partition maintenance.

<Pitfall>
`EXPLAIN` without `ANALYZE` shows plan-time and executor-startup pruning, but not per-row pruning in a join: the plan lists all partitions and only `EXPLAIN ANALYZE` shows which were `(never executed)`. When a query "scans every partition" in a plain EXPLAIN, run it with ANALYZE before concluding pruning failed.
</Pitfall>

## Real-world scenario: an ORM with prepared statements

A service runs `SELECT … FROM orders_p WHERE created_at >= $1 AND created_at < $2` through a driver that prepares statements. After a few executions PostgreSQL may switch to a generic plan. Reads stay fast (startup pruning removes 23 partitions), but every execution of a generic plan **locks all 24 partitions and their indexes** before pruning, which matters with hundreds of partitions (Concept 4: 1,466 locks instead of 6). Options:

| Option | Effect |
|---|---|
| Keep the default (`auto`) | Fine with tens of partitions |
| `plan_cache_mode = force_custom_plan` for that role or session | Plans every execution with the values: plan-time pruning, few locks, a little more planning time |
| Fewer, larger partitions | Fewer locks either way |

## Key takeaways

1. Pruning happens while planning (constants), at executor startup (parameters, `now()`, generic plans) or per row (nested loops, sub-selects).
2. EXPLAIN shows them as a short plan, `Subplans Removed: N`, and `(never executed)` respectively.
3. Pruning turned a full read (71.0 ms) into one partition (8.5 ms), much like an index does.
4. On a time-ordered table with an index on the key, the plain table was just as fast for a month (8.6 ms vs 8.4 ms) and faster for the whole table.
5. Generic plans prune at startup but lock every partition first.
