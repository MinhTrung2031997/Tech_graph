<Tldr>
Pruning works only when the WHERE clause compares the **bare partition key** with a value of a compatible type, using operators the partitioning understands (`=`, `<`, `>=`, `IN`, …). Wrap the key in a function and every partition is read: `date_trunc('month', created_at) = '2025-03-01'` **24 partitions, 131.5 ms**; `created_at::date = '2025-03-15'` **24, 99.0 ms**; the same day as a range **1 partition, 0.3 ms**. A filter on another column cannot prune either: `WHERE id = 777777` read all 24 (55.2 ms; the plain table's primary key answers in microseconds). `… OR seller_id = 42` read 24 (70.9 ms), while an OR of two months read 2. A `timestamp` literal against the `timestamptz` key still pruned, but only at executor startup. On list partitions by marketplace, reaching the key through a **hash join** read all 4 partitions (70.7 ms) instead of 1 (21.7 ms).
</Tldr>

## The setup

`orders_p` (24 monthly partitions by `created_at`, index on `created_at` in each) and, for the join, `orders_l` (list partitions by `marketplace`, index on `marketplace`). Times are medians of 3 runs; "scanned" counts partitions that were actually read (EXPLAIN ANALYZE).

| Term | Meaning |
|---|---|
| Bare key | The partition key column on its own on one side of the comparison: `created_at >= …` |
| Expression on the key | `date_trunc('month', created_at)`, `created_at::date`, `extract(year FROM created_at)`: the planner cannot map these back to bounds |
| Immutable / stable | Immutable functions always return the same result for the same input; stable ones can depend on settings such as `TimeZone` (pruned only at execution) |
| **✓ Pruned / ✗ Not pruned** | The query reads only matching partitions / it reads all of them |

## Summary of measured shapes

| WHERE clause on `orders_p` | Partitions read | Median |
|---|---|---|
| `created_at >= '2025-03-01' AND created_at < '2025-04-01'` | 1 (plan time) | 7.2 ms |
| `date_trunc('month', created_at) = '2025-03-01'` | 24 | 131.5 ms |
| `created_at::date = '2025-03-15'` | 24 | 99.0 ms |
| `created_at >= '2025-03-15' AND created_at < '2025-03-16'` | 1 | 0.3 ms |
| `extract(year FROM created_at) = 2025` | 24 | 153.1 ms |
| `timestamp` literals instead of `timestamptz` | 1 (executor startup) | 8.5 ms |
| `id = 777777` | 24 | 55.2 ms |
| month range `OR seller_id = 42` | 24 | 70.9 ms |
| two month ranges joined by `OR` | 2 | 10.8 ms |

## Joins that reach the key indirectly

Pruning through a join needs the key's value to arrive as a parameter, which only a nested loop does. On `orders_l` (list partitions by marketplace):

```sql
SELECT count(*) FROM orders_l o JOIN marketplaces m ON o.marketplace = m.code
WHERE m.owner = 'alibaba';                                  -- lazada only
```

| Form | Plan | Partitions read | Median |
|---|---|---|---|
| Join as written | Hash Join | all 4 (5M index entries) | 70.7 ms |
| `WHERE o.marketplace = ANY (ARRAY(SELECT code FROM marketplaces WHERE owner = 'alibaba'))` | value computed first | 1 with rows, 3 probed and empty | 15.0 ms |
| `WHERE o.marketplace = 'lazada'` | plan-time pruning | 1 | 21.7 ms |

(The ARRAY form was faster than the literal here only because the planner chose a parallel index-only scan for it and a parallel sequential scan of `orders_l_lazada` for the literal; both read one partition's worth of rows.)

<Pitfall>
Reports and dashboards are where pruning silently disappears: `GROUP BY date_trunc('day', created_at)` is fine, but `WHERE date_trunc('month', created_at) = $1` or `WHERE created_at::date BETWEEN $1 AND $2` reads every partition. Write filters as half-open ranges on the bare key: `created_at >= $1 AND created_at < $2`.
</Pitfall>

## Real-world scenario: "order detail is slow since we partitioned"

The order detail page runs `SELECT … FROM orders WHERE id = $1`. After partitioning by month, it went from a primary-key lookup to 24 scans. Options, from best to worst:

| Option | Effect |
|---|---|
| Carry `created_at` (or the month) with the id wherever orders are referenced, and query `WHERE id = $1 AND created_at = $2` | 1 partition, index lookup |
| Encode time in the id (e.g. UUIDv7 or a sequence per month) and derive the partition from it | 1 partition, but only if the query also states the derived range |
| An index on `id` in every partition | 24 index probes instead of 24 scans: fast enough at 24 partitions, worse at 700 |
| Leave it | 55 ms per page view |

## Key takeaways

1. Pruning needs the bare key compared with a value: no function, cast or expression around the column.
2. A filter on another column (`id`, `seller_id`) never prunes; every partition is searched.
3. `OR` keeps pruning only if every branch restricts the key.
4. A type mismatch such as `timestamp` vs `timestamptz` moves pruning to execution time.
5. Joins prune only through a nested loop; a hash join reads every partition.
