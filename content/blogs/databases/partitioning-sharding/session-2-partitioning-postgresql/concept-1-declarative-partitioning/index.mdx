<Tldr>
A partitioned table in PostgreSQL is a **parent with no storage** plus one ordinary table per partition. `PARTITION BY RANGE (created_at)` with 24 monthly partitions took 23 ms to create; `INSERT … SELECT` of 5M rows routed every row to its month (212,039 rows in March 2025, 198,358 in February 2024). The parent stayed at **0 bytes**. A row for January 2026 failed: `no partition of relation "orders_p" found for row`. An `UPDATE` of `created_at` **moved** order 777777 from `orders_p_2024_04` to `orders_p_2025_07`. Routing is cheap: bulk loads took a median of 2.95 s partitioned vs 2.90 s plain, within the noise of a shared server. **List** partitioning by marketplace gave 2.50M / 1.50M / 1.00M rows; **hash** partitioning by seller gave 8 partitions of 571k–656k rows, and pruned only for equality (`seller_id = 42` → 1 partition, `BETWEEN 1 AND 10` → all 8).
</Tldr>

## The setup

The data is the course's `orders` table (5,000,000 rows, 2024-01-01 to 2025-12-31, about 208k per month; setup and seeds in the [Session 1 lab](/blogs/databases/partitioning-sharding/session-1-why-split-data/lab)). We build a partitioned copy, `orders_p`, by month:

```sql
CREATE TABLE orders_p (
  id bigint NOT NULL, seller_id integer NOT NULL, marketplace text NOT NULL,
  status text NOT NULL, amount numeric(12,2) NOT NULL, created_at timestamptz NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_p_2025_03 PARTITION OF orders_p
  FOR VALUES FROM ('2025-03-01 00:00+00') TO ('2025-04-01 00:00+00');   -- × 24, generated in a DO block

INSERT INTO orders_p SELECT * FROM orders;
CREATE INDEX ON orders_p (created_at);   -- creates one index per partition
```

| Term | Meaning |
|---|---|
| Parent (partitioned table) | `orders_p`: the name queries use. It has a partition key and bounds, but no rows of its own |
| Partition | An ordinary table attached to the parent with bounds, e.g. `orders_p_2025_03` |
| Partition key | The column(s) the bounds are defined on: `created_at` here |
| Range bounds | `FROM` is inclusive, `TO` is exclusive, so consecutive months share a boundary value without overlap |
| Tuple routing | On INSERT, PostgreSQL finds the partition whose bounds contain the key and writes the row there |
| **✓ Routed / ✗ No partition** | A partition exists for the row's key / none does, and the statement fails |

## Does routing cost anything?

Each bulk load ran into an empty table with no indexes, three times, on a server shared with other lab sessions:

| Load of 5M rows | Run 1 | Run 2 | Run 3 | Median |
|---|---|---|---|---|
| `orders_copy` (plain table) | 2.51 s | 2.90 s | 4.50 s | **2.90 s** |
| `orders_p` (24 partitions) | 2.79 s | 3.95 s | 2.95 s | **2.95 s** |

100,000 single-row INSERTs from a PL/pgSQL loop: 309 and 538 ms plain, 368 and 400 ms partitioned. The difference is smaller than the run-to-run noise. Finding the partition is a binary search over the bounds; it is not where the time goes.

## List and hash partitioning

The same rows, split two other ways:

```sql
CREATE TABLE orders_l (LIKE orders) PARTITION BY LIST (marketplace);
CREATE TABLE orders_l_shopee PARTITION OF orders_l FOR VALUES IN ('shopee');   -- + tiktok, lazada
CREATE TABLE orders_l_other  PARTITION OF orders_l DEFAULT;                   -- catches anything else

CREATE TABLE orders_h (LIKE orders) PARTITION BY HASH (seller_id);
CREATE TABLE orders_h_0 PARTITION OF orders_h FOR VALUES WITH (MODULUS 8, REMAINDER 0);   -- … remainder 7
```

| | Range (`created_at`, monthly) | List (`marketplace`) | Hash (`seller_id`, modulus 8) |
|---|---|---|---|
| Rows per partition | 191,518–212,039 (February 2025 smallest) | shopee 2,499,789 · tiktok 1,500,190 · lazada 1,000,021 | 570,664–656,073 |
| Unknown key | ✗ error (no partition) | ✗ error for `'amazon'` until a `DEFAULT` partition exists | Impossible: every hash has a remainder |
| Pruned by `=` | ✓ | ✓ `= 'lazada'` → 1 | ✓ `seller_id = 42` → 1, `IN (1, 2)` → 2 |
| Pruned by a range | ✓ | ✓ for `<>` too: `<> 'shopee'` → 3 of 4 | ✗ `BETWEEN 1 AND 10` → all 8 |
| Typical use | Time: retention by dropping old months | A few known categories (tenant, region, channel) | Spreading writes or maintenance evenly when no natural range exists |

Hash partitions are only as even as the keys: 5,000 sellers spread over 8 remainders left a 15% gap between the smallest and largest partition. One huge seller would land entirely in one partition.

<Pitfall>
A `DEFAULT` partition turns "no partition" errors into silently accepted rows. That feels safer, but rows in the default partition are invisible to retention scripts that drop old ranges, and they block attaching a new partition whose range they overlap (Session 4). Use a default partition to catch mistakes you will monitor, not as a substitute for creating partitions.
</Pitfall>

A marketplace integration stores 6M orders a month and keeps 24 months. The team partitions `orders` by `created_at` monthly. Day one, three things surprise them:

## Key takeaways

1. A partitioned parent stores nothing; each partition is an ordinary table with bounds.
2. Every inserted row must match a partition, or the statement fails (or lands in `DEFAULT`, if one exists).
3. Updating the partition key moves the row: a delete in one partition plus an insert in another.
4. Routing rows costs nothing measurable next to writing them (2.95 s vs 2.90 s for 5M rows).
5. Range suits time and retention, list suits a few known values, hash spreads load but prunes only on equality.
