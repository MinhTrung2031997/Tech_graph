<Tldr>
**MySQL** has partitioning built into InnoDB tables, with stricter rules than PostgreSQL. `PRIMARY KEY (id)` was rejected: `ERROR 1503: A PRIMARY KEY must include all columns in the table's partitioning function`; with `PRIMARY KEY (id, created_at)` the 24 monthly partitions loaded 5M rows in 14.6–16.6 s (plain copy: 10.8–12.3 s). A row for 2026 failed with `ERROR 1526: Table has no partition for value from column_list`. `EXPLAIN` lists the partitions read: a month read **only `p2025_03`, 19.1 ms**, while the plain table used its secondary index plus a primary-key lookup per row, **103.9 ms**. Prepared statements prune with their parameters. `DATE(created_at) = …` and `YEAR(created_at) = 2025` read all 24 partitions. **MongoDB** has no table partitioning: a collection is one set of documents and indexes (sharding, Sessions 5–8, splits it across servers). The month query was an index range scan of 212,039 keys and documents, 62 ms. Its single-server alternatives (time-series collections, TTL indexes, a collection per month) are Session 3.
</Tldr>

## The setup

Database `pt2` in `idx-mysql` and `idx-mongo`, same 5M `orders` as in PostgreSQL. The MySQL partitioned copy:

```sql
CREATE TABLE orders_p (
  id BIGINT NOT NULL, seller_id INT NOT NULL, marketplace VARCHAR(8) NOT NULL, status VARCHAR(10) NOT NULL,
  amount DECIMAL(12,2) NOT NULL, created_at DATETIME NOT NULL,
  PRIMARY KEY (id, created_at),
  KEY orders_p_created_at_idx (created_at)
) PARTITION BY RANGE COLUMNS (created_at) (
  PARTITION p2024_01 VALUES LESS THAN ('2024-02-01'),
  -- … one per month …
  PARTITION p2025_12 VALUES LESS THAN ('2026-01-01')
);
INSERT INTO orders_p SELECT * FROM orders;
```

| Term | Meaning |
|---|---|
| `RANGE COLUMNS` | Range partitioning directly on column values (dates, strings), instead of an integer expression like `TO_DAYS(created_at)` |
| `VALUES LESS THAN` | Each partition's exclusive upper bound; partitions must be listed in increasing order |
| `partitions` column | In `EXPLAIN`, the partitions the statement will read; `NULL` for a non-partitioned table |
| Clustered index | InnoDB stores rows in primary-key order; a secondary index entry holds the primary key, so each match needs a second lookup |
| **✓ Read / ✗ Pruned** | Partition listed in `EXPLAIN` / not listed |

## Three engines side by side

| | PostgreSQL 17 | MySQL 8.4 | MongoDB 8.0 |
|---|---|---|---|
| Table partitioning | Declarative: range, list, hash; sub-partitions | Range, list, hash, key (+ `COLUMNS` variants), sub-partitions; InnoDB and NDB tables only | None (sharding instead, across servers) |
| Primary key without the partition column | ✗ rejected (Session 3) | ✗ ERROR 1503 | n/a |
| Insert with no partition | ✗ `no partition of relation … found for row` | ✗ ERROR 1526 | n/a |
| Where to see pruning | Plan shape, `Subplans Removed`, `(never executed)` | `partitions` column of `EXPLAIN` | n/a |
| Month query (212,039 rows), plain vs partitioned | 8.6 ms vs 8.4 ms | 103.9 ms vs 19.1 ms | 62 ms (index, no partitions) |
| Load 5M rows, plain vs partitioned | 2.90 s vs 2.95 s (medians) | 10.8–12.3 s vs 14.6–16.6 s (2 runs) | not compared |

Why MySQL gained more from pruning: InnoDB secondary indexes point to the primary key, so 212,039 index matches meant 212,039 lookups in the clustered index ([Indexing Session 6](/blogs/databases/indexing/session-6-engine-differences/concept-2-innodb-secondary)). PostgreSQL's index points straight at heap pages, which were already in time order. The partitioned load was slower in MySQL partly because its primary key is wider (`id, created_at`), which also widens every secondary index entry.

<Pitfall>
In MySQL, adding `created_at` to the primary key to satisfy ERROR 1503 changes what the key promises: `(id, created_at)` allows two rows with the same `id` in different months. If `id` must be unique, something else has to enforce it (Session 3 covers the options).
</Pitfall>

## Real-world scenario: one schema, two engines

A data team runs the same orders schema on PostgreSQL (operational) and MySQL (a legacy reporting replica). After partitioning both by month:

| Report | PostgreSQL | MySQL |
|---|---|---|
| Monthly sales for one month | About as fast as before | About 5× faster: one partition scan instead of a secondary index plus lookups |
| Order lookup by id | Slower: 24 partitions searched | Still fast with `PRIMARY KEY (id, created_at)`: 24 primary-key probes, 0.063 ms vs 0.035 ms |
| `WHERE DATE(created_at) = ?` | All partitions | All partitions |

## Key takeaways

1. MySQL partitions InnoDB tables with `PARTITION BY RANGE COLUMNS` and shows pruning in `EXPLAIN`'s `partitions` column.
2. MySQL rejects a primary key that lacks the partition column (ERROR 1503) and inserts with no partition (ERROR 1526).
3. Pruning helped MySQL more (103.9 → 19.1 ms) because its secondary-index range scans pay a primary-key lookup per row.
4. Functions on the key (`DATE()`, `YEAR()`) defeat pruning in MySQL as in PostgreSQL.
5. MongoDB has no table partitioning; on one server, indexes do the skipping, and sharding splits data across servers.
