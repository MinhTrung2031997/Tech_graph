<Tldr>
Each partition is a table, and each of its indexes is another relation: **731 daily partitions with one index made 1,464 relations**, against 50 for 24 monthly ones. A query that prunes to one partition while planning does not care (6 locks either way, warm planning 0.031 ms vs 0.017 ms). A query that cannot prune pays per partition: `WHERE id = 777777` locked **1,466 relations instead of 52**, and its first plan on a new connection took **392.7 ms instead of 2.1 ms** while it loaded metadata for every partition. A **generic plan** for a one-day query locked all 1,466 before pruning to one. Only 16 locks per backend fit in the fast path; the rest go to the shared lock table. Maintenance scales too: `ANALYZE` took **4.99 s vs 0.82 s** (0.14 s unpartitioned). Choose the partition size from retention and query ranges, then keep the count in the tens or low hundreds unless queries reliably prune at plan time.
</Tldr>

## The setup

Two partitioned copies of `orders`, both with an index on `created_at`:

| Table | Partitions | Relations (tables + indexes, incl. parent) | Size | Created in |
|---|---|---|---|---|
| `orders_p` | 24 (monthly) | 50 | 474 MB | 23 ms |
| `orders_d` | 731 (daily) | 1,464 | 514 MB | 503 ms |

Loading 5M rows took 2.75 s into `orders_d`, like `orders_p`. The first `VACUUM ANALYZE` after the load took 13.6 s on `orders_d` and 1.2 s on `orders_p`.

| Term | Meaning |
|---|---|
| Relation lock | Every table and index a query uses is locked (`AccessShareLock` for reads) until the transaction ends |
| Fast-path slot | A per-backend array for weak relation locks: 16 slots in PostgreSQL 17. Locks beyond that go to the shared lock table |
| Shared lock table | One table in shared memory for all sessions, sized for about `max_locks_per_transaction` (64 here) × the number of connections |
| Cold / warm | First query on a new connection (metadata for each partition must be loaded into the backend's cache) / later queries on the same connection |
| **✓ Few / ✗ Many** | Locks or work proportional to the partitions kept / to all partitions |

## Measured on both layouts

| | `orders` (1 table) | `orders_p` (24) | `orders_d` (731) |
|---|---|---|---|
| One day, planning cold / warm | 1.31 / 0.010 ms | 0.65 / 0.017 ms | 6.59 / 0.031 ms |
| One day, execution warm | 0.45 ms | 0.49 ms | 0.34 ms |
| `id = 777777`, planning cold / warm | 0.22 / 0.007 ms | 2.06 / 0.14 ms | **392.7 / 3.8 ms** |
| `id = 777777`, execution warm | 0.009 ms (primary key) | 112.1 ms | 128.9 ms |
| Whole table, planning cold / warm | 0.42 / 0.034 ms | 2.05 / 0.11 ms | 50.3 / 3.3 ms |
| Whole table, execution warm | 100.8 ms | 131.9 ms | 159.8 ms |
| Locks: one day literal / no key / generic plan | 5 / 5 / not measured | 6 / 52 / 52 | 6 / **1,466** / **1,466** |
| `ANALYZE` (median of 3) | 0.14 s | 0.82 s | **4.99 s** |
| `VACUUM` with nothing to do | 2.3 ms | 0.9 ms | 42.9 ms |

Cold = first query on a fresh connection; warm = median of the next 5. Timings come from a lab server shared with other sessions. Lock counts include the `pg_locks` view and the virtual transaction id of the session that counts them; the plain table's 5 are the table, its two indexes and those two.

`ANALYZE` on a partitioned table samples each partition for its own statistics and then the whole hierarchy for the parent's, so it grows with the partition count. Autovacuum analyzes partitions but, per the documentation, never the partitioned parent: run `ANALYZE orders_p` yourself after large changes.

<Pitfall>
Connection poolers hide the cold cost until they recycle connections. With 731 partitions, every new backend paid 392.7 ms on its first query that could not prune. Short-lived connections (serverless functions, a pooler with a short `server_lifetime`) pay it again and again.
</Pitfall>

## Real-world scenario: daily partitions "for faster deletes"

A team partitions an events table by day and keeps 3 years: 1,096 partitions. Retention is fast. Then:

| Symptom | Cause |
|---|---|
| Admin queries by `event_id` take seconds on the first try | Planning opens 1,096 partitions and their indexes on a new connection |
| Occasional `out of shared memory` with `You might need to increase max_locks_per_transaction` | Many concurrent queries each taking 2,000+ locks |
| Nightly `ANALYZE` job grows month after month | One more partition every day |

Monthly partitions (36) would still let them drop old data a month at a time, with a twentieth of the overhead. Daily partitions make sense when queries always name the day and old data must go within a day.

## Key takeaways

1. Each partition and each of its indexes is a relation that is planned, locked and maintained.
2. Plan-time pruning makes the count nearly irrelevant: 6 locks with 24 or 731 partitions.
3. Queries that cannot prune pay per partition: 1,466 locks and 392.7 ms of cold planning at 731.
4. Generic plans lock every partition before pruning at startup.
5. `ANALYZE` grows with the count (0.82 s → 4.99 s); autovacuum does not analyze the parent.
6. Size partitions from retention and typical query ranges, then prefer fewer, larger ones.
