<Tldr>
A transaction that writes to **one shard** commits like a transaction on one server. A transaction that writes to **two shards** needs **two-phase commit** (2PC): every shard prepares, a coordinator records the decision, then every shard commits. Measured on the lab clusters (two shards, all containers on one laptop):

- **MongoDB**, transfer between two sellers' balances (300 transactions per run, 3 runs): same shard **3.1–4.5 ms** median, two shards **22.1–23.3 ms** median. mongos counted 50 `singleShard` and 50 `twoPhaseCommit` commits for 50 + 50 transactions; the commit step alone averaged **2.6 ms** vs **14.9 ms**.
- **Citus**, the same transfer (pgbench, median of 6 runs): same shard **2.3 ms**, two shards on the same worker **1.9 ms**, two workers **6.0 ms**. Only the last one wrote 2PC records: **2 rows per transaction** in `pg_dist_transaction`.
- A second transaction writing the same document got **WriteConflict (112)** at once, with the label **TransientTransactionError**: retry, do not wait.

Cross-shard transactions work. They cost several times more, and they fail more often, so a good shard key keeps the usual transaction on one shard.
</Tldr>

## The setup

A `seller_balances` table, one row per seller (5,000 sellers, balance 1,000.00), sharded by seller id. The balance moves when an order is refunded from one seller and credited to another, or when a platform fee moves between accounts.

- **MongoDB** (database `pt8` on `pt-mongos`): `seller_balances` sharded on `_id` (the seller id), split at 2501, sellers 1–2500 on shard **sh2**, 2501–5000 on **sh1**. Balancing is off for this collection, so the ranges stay put.
- **Citus** (database `pt8` on `pt-citus`): `create_distributed_table('seller_balances', 'seller_id')`, 32 shards, 16 on each worker. Seller 8 and seller 20 are in the same shard (102072 on `pt-citus-w1`), seller 31 is in another shard on the same worker, seller 1 is on `pt-citus-w2`.

The lab builds both: [Session 8 lab](/blogs/databases/partitioning-sharding/session-8-operations-across-shards/lab). The Citus containers run under x86 emulation on the lab's ARM laptop, so compare Citus numbers with each other, not with MongoDB.

| Term | Meaning |
|---|---|
| Participant | A shard that the transaction wrote to |
| Single-shard commit | Only one participant: the router just tells it to commit |
| Two-phase commit (2PC) | Phase 1: every participant **prepares** (makes the changes durable but not visible). Phase 2: once all said yes, the coordinator records "commit" and every participant commits |
| Coordinator | Who decides and remembers the outcome. MongoDB: the first shard the transaction wrote to. Citus: the coordinator node |
| In-doubt transaction | Prepared but not yet committed or aborted, for example after a crash; it keeps its locks until resolved |
| **✓ / ✗** | Stays on one shard / needs work on several shards |

## Comparison

| Transfer between two sellers | MongoDB (median) | Citus (median, emulated) | Commit protocol |
|---|---|---|---|
| Two writes, no transaction | 5.1–7.2 ms | 2.5 ms | one commit per write |
| Transaction, one shard | 3.1–4.5 ms | 2.3 ms | single participant |
| Transaction, two shards on one server | n/a (a MongoDB shard is one replica set) | 1.9 ms | local commit |
| Transaction, two shards / two workers | **22.1–23.3 ms** | **6.0 ms** | two-phase commit |

The MongoDB "no transaction" row is slower than the one-shard transaction because each of the two writes waits for its own majority write concern; the transaction waits once, at commit.

<Pitfall>
2PC protects atomicity, not availability. If the coordinator dies between prepare and commit, the participants keep the prepared transaction and **its locks** until the decision is recovered: MongoDB's coordinator shard writes its decision to `config.transaction_coordinators` and resumes after failover; Citus's maintenance daemon reads `pg_dist_transaction` and finishes or rolls back prepared transactions on the workers every `citus.recover_2pc_interval` (1 min in the lab). Until then, rows touched by the in-doubt transaction cannot be written. Transactions S8 shows the same with MySQL XA.
</Pitfall>

## Real-world scenario: refunds between seller wallets

A marketplace keeps a wallet per seller and moves money on every refund, chargeback and fee. Wallets are sharded by seller id. Most movements are platform → seller (the platform's fee account is one hot row), and a small share are seller → seller.

| Design | Effect |
|---|---|
| Fee account as a normal row | Every fee transaction touches the platform's shard plus the seller's shard: almost every transaction is 2PC, and all of them conflict on one row |
| ✓ Ledger rows sharded by seller, platform totals aggregated asynchronously | The common transaction (order + fee line for one seller) stays on the seller's shard |
| ✓ Seller → seller transfers as two single-shard steps with an idempotent transfer id | No 2PC; a failed second step is retried from the transfer record (outbox pattern) |

## Key takeaways

1. One participant means an ordinary commit; two or more means two-phase commit, in both MongoDB and Citus, automatically.
2. Measured cost of crossing shards: MongoDB 3–4.5 ms → 22–23 ms; Citus 2.3 ms → 6.0 ms.
3. Citus decides by **worker**, not by shard: two shards on one worker still commit locally.
4. MongoDB write conflicts fail fast with `TransientTransactionError`; the client must retry the whole transaction.
5. A prepared transaction keeps its locks until the coordinator's decision is applied, so coordinator failures turn into blocked rows.
