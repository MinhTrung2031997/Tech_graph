<Tldr>
On one server, `bigserial` is the easy answer. Across shards there is no single counter that every writer can call cheaply, so the id either comes from **one place** (a coordinator sequence), carries **where it was made** (a node number inside the id), or is **random enough** never to collide (UUID). What it costs is decided by **where new ids land in the B-tree**:

| 1,000,000 inserts, PostgreSQL 17 (3 runs) | Time | WAL | Primary key | Leaf density |
|---|---|---|---|---|
| bigint identity (one sequence) | 1.12–1.53 s | 143.1 MB | **21 MB** | 90.1% |
| Snowflake-style bigint | 1.42–1.90 s | 144.2–144.4 MB | 23 MB | 82.7% |
| UUIDv4 (`gen_random_uuid()`) | 2.90–3.90 s | 171.5–171.8 MB | **38 MB** | 70.8% |
| UUIDv7 layout, 423 rows per ms | 2.55–2.89 s | 166.1–166.8 MB | 40 MB | 68.2% |
| UUIDv7 layout, at most 1 row per ms | 1.57–1.67 s | 157.2 MB | 30 MB | 90.0% |

- **Citus** `bigserial`: through the coordinator, ids 1, 2, 3; through worker group 1, **281474976710657** (1 shifted left by 48, plus 1); through worker group 2, 562949953421313. No collisions, no round trip to the coordinator.
- **PostgreSQL 17 has no `uuidv7()`** (`ERROR: function uuidv7() does not exist`); the lab builds the layout with a SQL function.
- **MongoDB** (1M documents): ObjectId **2.1–2.5 s**, int64 2.1–2.4 s, UUIDv4 **5.9–6.0 s**; `_id` index 10.2 / 11.4 / **25.9 MB**.
</Tldr>

## The setup

- `idx-pg`, database `pt8` (PostgreSQL 17.11, native ARM): four tables with the same columns and a different primary key (`id_seq`, `id_snow`, `id_uuid4`, `id_uuid7`, plus `id_uuid7_1ms`), each loaded with `INSERT … SELECT` of 1,000,000 rows, measured with `EXPLAIN (ANALYZE, WAL)`, index density with `pgstatindex()` (extension `pgstattuple`).
- `idx-mongo`, database `pt8`: 1,000,000 documents per collection in batches of 10,000, sizes read after the next WiredTiger checkpoint.
- `pt-citus`, database `pt8`: a `bigserial` column on a distributed table.

The id generators used in the lab:

```sql
-- UUIDv7 layout (RFC 9562): 48 bits of Unix milliseconds, version 7, then random bits
CREATE FUNCTION uuid_v7() RETURNS uuid LANGUAGE sql VOLATILE AS $$
  SELECT encode(set_bit(set_bit(
           overlay(uuid_send(gen_random_uuid())
                   placing substring(int8send((extract(epoch FROM clock_timestamp()) * 1000)::bigint) FROM 3)
                   FROM 1 FOR 6),
           52, 1), 53, 1), 'hex')::uuid
$$;
-- Snowflake-style: 41 bits of ms since 2024-01-01, 10 bits of node id, 12 bits of sequence
CREATE SEQUENCE snow_seq;
CREATE FUNCTION snowflake(node int) RETURNS bigint LANGUAGE sql VOLATILE AS $$
  SELECT (((extract(epoch FROM clock_timestamp()) * 1000)::bigint - 1704067200000) << 22)
         | ((node & 1023)::bigint << 12) | (nextval('snow_seq') & 4095)
$$;
```

| Term | Meaning |
|---|---|
| Monotonic id | Each new id is larger than the previous one, so inserts go to the rightmost B-tree leaf |
| Rightmost split | When the last leaf fills, PostgreSQL leaves it about 90% full and starts a new one |
| 50/50 split | A full leaf in the middle splits into two half-full leaves; random keys cause these |
| Leaf density | How full the index leaf pages are on average (`pgstatindex().avg_leaf_density`) |
| UUIDv7 | 128-bit id starting with a millisecond timestamp, then random bits (RFC 9562) |
| Snowflake id | 64-bit id: timestamp, node number, per-node sequence (Twitter's design) |
| **✓ / ✗** | New keys append at the right edge / land anywhere in the index |

## MongoDB

| 1,000,000 documents (2 runs) | Insert time | `_id` index | Collection |
|---|---|---|---|
| ObjectId (default: 4-byte seconds, 5 random bytes, 3-byte counter) | 2.09–2.50 s | 10.2 MB | 15.4 MB |
| int64 from the application | 2.09–2.37 s | 11.4 MB | 15.7 MB |
| UUIDv4 (`UUID()`) | 5.86–6.03 s | 25.9 MB | 32.3 MB |

ObjectId is time-ordered by second with a counter inside, so it appends like a sequence and needs no coordination: each `mongos` client or driver makes its own. Sizes were read after a WiredTiger checkpoint; WiredTiger compresses keys, so the int64 and ObjectId indexes are about the same size although the keys are 8 and 12 bytes.

## Choosing

| Id | Unique across shards | Time-ordered | Key size | Coordination |
|---|---|---|---|---|
| One sequence on the coordinator | ✓ | ✓ | 8 bytes | every insert passes the coordinator |
| Citus worker ranges (`group << 48`) | ✓ | ✗ across nodes | 8 bytes | none |
| Sequence per shard with step N | ✓ if configured right | ✗ across shards | 8 bytes | none, but fragile |
| Snowflake-style bigint | ✓ if node ids are unique | ✓ to the ms | 8 bytes | assign node ids once |
| ObjectId | ✓ (random part per process) | ✓ to the second | 12 bytes | none |
| UUIDv4 | ✓ (122 random bits) | ✗ | 16 bytes | none |
| UUIDv7 | ✓ | ✓ to the ms (monotonic generators: fully) | 16 bytes | none |

<Pitfall>
A time-ordered id as a **hashed** shard key is fine, but as a **ranged** shard key it sends every new insert to the shard holding the highest range: the same right-edge effect, one level up. Time-ordered ids are good for the B-tree on each shard and bad for ranged sharding. [Session 5, Concept 2](/blogs/databases/partitioning-sharding/session-5-choosing-a-shard-key/concept-2-monotonic-keys) measures that hot shard.
</Pitfall>

## Real-world scenario: order ids for three marketplaces

Orders are created by importers running in Vietnam and Thailand, sharded by seller, and the ids are shown to support staff and used in URLs.

| Choice | Why |
|---|---|
| ✓ Snowflake-style bigint, node id per importer process | 8 bytes, time-ordered, no central counter, fits JavaScript's safe integers only if you keep it under 2^53, so send it as a string to browsers |
| ✗ UUIDv4 | 16 bytes, random index inserts, 1.8 times the index size measured |
| ✓ Monotonic UUIDv7 (PostgreSQL 18, or a library) | When a standard format matters more than size |
| ✓ Keep the platform's `order_sn` as a separate column | Unique per `(seller_id, marketplace)` (Concept 2), not as the primary key |

## Key takeaways

1. Across shards, ids must be unique without a shared counter: node ranges, snowflake ids, ObjectId or UUIDs.
2. What matters for the index is order: right-edge appends kept the primary key at 21–30 MB; random keys made it 38–40 MB.
3. A UUIDv7 is only time-ordered between milliseconds unless the generator adds a counter; at 423 rows per ms it behaved like UUIDv4.
4. Citus `bigserial` puts the worker group in the top 16 bits for rows inserted through workers.
5. PostgreSQL 17 has no `uuidv7()`; write a function or upgrade.
