<Tldr>
Shards drift out of balance: one seller grows, a new shard is added, a server is retired. Rebalancing **copies** data to another shard, **catches up** with writes made during the copy, then **switches** the routing. Measured on the lab clusters:

- **MongoDB** `moveRange` of sellers 1–1249 (**252,264 documents, 30.0 MB**) from sh2 to sh1: **2.03 s**, of which the clone took 1.77 s and the critical section (writes to the range paused) **12 ms**. A client inserting into that range the whole time saw median **3.1 ms**, p99 15 ms, max **218 ms**. The old copies stayed on sh2 as **orphans** until range deletion ran 15 minutes later (`orphanCleanupDelaySecs` 900).
- **Citus** `citus_move_shard_placement` in its default mode failed here: `logical decoding requires "wal_level" >= "logical"` (the lab workers run `wal_level = replica`, and changing it needs a restart). With `shard_transfer_mode := 'block_writes'` one shard group (29,618 orders plus the colocated balances shard) moved in **1.16–1.83 s**. Writes to that shard stalled up to **1.73 s**; writes to another shard (max 0.22 s) and reads of the moving shard (max 0.16 s) carried on.

Adding a shard or a worker was **not** done in the lab (other builders shared the clusters); it is described from the documentation below.
</Tldr>

## The setup

- **MongoDB** `pt8.orders_by_seller`, sharded on `{ seller_id: 1 }`, balancing disabled for the collection so the moves are manual. Before: sellers 2501–5000 on sh1, everything below 2501 on sh2.
- **Citus** `pt8.orders_dist`, the 1M orders distributed by `seller_id` (32 shards, 16 per worker), colocated with `seller_balances` (same column type, same shard count, so Citus puts them in colocation group 3).
- Write load: a client inserting orders for one seller in the moving range (MongoDB seller 100; Citus seller 8 with pgbench, logging every transaction's latency).

| Term | Meaning |
|---|---|
| Range / chunk | A contiguous span of shard key values owned by one shard (MongoDB) |
| Shard group | All colocated shards for the same hash range (Citus); they always move together |
| Clone | Copying the documents or rows to the recipient while the donor keeps serving |
| Catch-up | Applying the writes that happened during the clone |
| Critical section | The short pause in which the last writes are applied and the routing table changes |
| Orphan | A copy left on the donor after the move, deleted later |
| **✓ / ✗** | Traffic carries on / traffic waits |

## Comparison

| | MongoDB `moveRange` | Citus `block_writes` | Citus `force_logical` / `auto` |
|---|---|---|---|
| Unit moved | one range of one collection | one shard group (all colocated tables) | same |
| Lab size | 252,264 docs, 30.0 MB | 29,618 orders + 1 balances shard | not run (wal_level replica) |
| Duration | 2.03 s | 1.16–1.83 s | — |
| Writes to the moving data | continue; critical section 12 ms; max 218 ms | blocked for the copy: max 1.73 s | documented: continue, short block at the switch |
| Old copy | orphans deleted after 15 min | old placement dropped by Citus's background cleanup | same |
| Who starts it | balancer (automatic) or `moveRange` | `citus_rebalance_start()` or by hand | same |

## Adding a shard (from the documentation, not run)

| Step | MongoDB | Citus |
|---|---|---|
| 1. Add the node | Start a new shard replica set, then `sh.addShard("sh3/host:port")` | `SELECT citus_add_node('new-worker', 5432);` |
| 2. Move data | The balancer moves ranges until each shard is within the migration threshold | `SELECT citus_rebalance_start();` moves shard groups in the background; `citus_rebalance_status()` reports progress |
| 3. New tables | New collections are placed on the database's primary shard until sharded | New shards for new distributed tables include the new worker immediately |
| Planning | `sh.balancerCollectionStatus(ns)` | `get_rebalance_table_shards_plan()`: in the lab it returned 0 moves (32 shards per worker, already even) |

<Pitfall>
Rebalancing fixes **how many ranges** each shard has, not **how much traffic** each gets. One giant seller in one range, or a ranged shard key that is always increasing, keeps one shard hot however many times you rebalance. Fix the key ([Session 5, Concept 4](/blogs/databases/partitioning-sharding/session-5-choosing-a-shard-key/concept-4-hot-keys)), not the placement. And plan moves for the quiet hours: even the 12 ms critical section becomes long when the range is large or the recipient is slow, and every moved byte is written again on the recipient and its replicas.
</Pitfall>

## Real-world scenario: 11.11 sale preparation

Before the 11.11 campaign a brand-heavy marketplace adds a third shard for the expected traffic.

| Plan | Why |
|---|---|
| ✓ Add the shard two weeks before, let the balancer finish | Migrations compete with the sale's writes; finish them in quiet days |
| ✓ Set a balancer window (02:00–06:00) for the migration period | Migrations only run off-peak |
| ✓ On Citus: `wal_level = logical` set at provisioning | Online shard moves need it, and it needs a restart; do not discover this during the incident |
| ✗ Rebalance during the sale "because shard 1 is hot" | If the hot spot is one mega-seller, moving it moves the problem |

## Key takeaways

1. Moving data between shards is copy, catch up, switch; the switch is the only moment writes must pause.
2. MongoDB moved 30 MB in 2.03 s with a 12 ms critical section; writes into the range peaked at 218 ms.
3. Citus moves whole shard groups. Its online mode needs `wal_level = logical`; without it, `block_writes` stalls writes to that group for the copy.
4. MongoDB leaves orphans for 15 minutes by default; anything that reads shards directly sees them.
5. Rebalancing evens out data, not hot keys.
