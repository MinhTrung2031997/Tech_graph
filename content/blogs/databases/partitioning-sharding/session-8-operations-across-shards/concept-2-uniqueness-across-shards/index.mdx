<Tldr>
A unique index is a B-tree **per shard**. A shard can check a new key against its own index, but it cannot see the other shards' indexes, so a value can be unique on every shard and still appear twice in the cluster. Both engines therefore only allow unique keys that **include the shard key**: then equal values always land on the same shard.

- **MongoDB**, orders sharded by `seller_id`: `createIndex({ order_no: 1 }, { unique: true })` failed with **CannotCreateIndex (67)** (`cannot create index with 'unique' … over { order_no: 1 } with shard key pattern { seller_id: 1 }`). `_id` is the exception that is **not** checked across shards: a second document with `_id: 1` for seller 4000 was accepted on sh1, and `find({ _id: 1 })` returned **two** documents.
- **Citus**, orders distributed by `seller_id`: `PRIMARY KEY (id)` failed ("Distributed relations cannot have UNIQUE, EXCLUDE, or PRIMARY KEY constraints that do not include the partition column"); a unique index on `id` alone failed too.
- **Workaround measured on MongoDB**: a claim collection sharded by the order id, written in the same transaction as the order. Duplicates were refused (E11000), at a cost: median **7.7–12.2 ms** per order instead of **1.4–5.5 ms**, and **47–52%** of the transactions needed two-phase commit.
</Tldr>

## The setup

In database `pt8`:

- **MongoDB** `orders_by_seller`: the 1M orders sharded on `{ seller_id: 1 }`, ranges set by hand: sellers 1–1249 and 2501–5000 on **sh1**, sellers 1250–2500 on **sh2** (balancing off for the collection).
- **Citus** `orders_d` / `orders_dist`: the orders distributed by `seller_id`.

| Term | Meaning |
|---|---|
| Local unique index | Each shard checks the key against its own index only |
| Shard key prefix | The unique key starts with (MongoDB) or contains (Citus) the shard key, so equal keys hash or range to the same shard |
| Claim collection / table | A separate collection sharded **by the value that must be unique**; inserting the value there "claims" it cluster-wide |
| Orphan document | A copy left on the old shard after a migration, until range deletion removes it (Concept 4) |
| **✓ / ✗** | Uniqueness enforced / not enforced across shards |

## Ways to keep a value unique

| Approach | How | Cost |
|---|---|---|
| ✓ Make the value the shard key | Shard by order id | Every query by seller becomes a fan-out (Concept 5) |
| ✓ Unique within the shard key | (seller_id, order_no) unique | Enough when the value is only meaningful per seller, like a seller's own SKU code |
| ✓ Unique by construction | Ids from one sequence, ObjectId, UUID, snowflake (Concept 3) | No check at all; collisions are prevented, not detected |
| ✓ Claim collection / table | Insert the value into a collection sharded by it, in the same transaction | Measured: 7.7–12.2 ms vs 1.4–5.5 ms per order, about half the transactions two-phase |
| ✗ Check with a query first | find, then insert | Two concurrent inserts both find nothing; no lock spans shards |

<Pitfall>
Orphans take part in the local check. The first attempt to duplicate an order (`_id: 5`, seller 3945, moved from sh2 to sh1 minutes earlier) was **rejected** with E11000 on sh2, because the old copy was still physically on sh2 waiting for range deletion. A few minutes later the same insert would have been accepted. Neither outcome is a uniqueness guarantee.
</Pitfall>

## Real-world scenario: marketplace order numbers

Orders arrive from Shopee, Lazada and TikTok Shop with the platform's order number (`order_sn`), and the importer must never create the same order twice, even when a webhook and a polling job deliver it at the same moment. Orders are sharded by seller.

| Design | Result |
|---|---|
| ✗ Unique index on `order_sn` | Refused on a sharded collection (MongoDB) or a distributed table (Citus) |
| ✓ Unique on `(seller_id, marketplace, order_sn)` | Allowed: a platform order belongs to exactly one shop, so the seller is known before insert and both deliveries land on the same shard |
| ✓ Upsert keyed on that triple | Two concurrent deliveries end as one order, with no cross-shard transaction |

## Key takeaways

1. Unique indexes are checked per shard. Both engines refuse unique keys that do not contain the shard key.
2. MongoDB's `_id` is the exception: always unique per shard, never checked across shards unless `_id` is the shard key.
3. Prefer keys that contain the shard key, or ids that are unique by construction.
4. A claim collection works but turns every insert into a transaction, about half of them two-phase.
5. Check-then-insert never guarantees uniqueness across shards.
