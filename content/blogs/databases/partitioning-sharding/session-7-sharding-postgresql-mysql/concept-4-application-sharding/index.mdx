<Tldr>
MySQL has no built-in way to spread one table over several servers. The simplest way is **application-level sharding**: N independent databases with the same schema, and a **routing function** in the application that picks the database from the shard key. In the lab, `pt7_s0` holds the 500,192 orders of even `seller_id`s and `pt7_s1` the 499,808 of odd ones; a Python router (PyMySQL) talks to both. Routed queries are as fast as before (**0.12 ms vs 0.11 ms** for a seller's month). Everything that does not carry the shard key becomes the application's job: a lookup by order id asks every shard (**0.25 ms**); a report fans out and the application **merges** (GMV per marketplace **16 ms** in parallel vs **25 ms** unsharded, **25 ms** if the shards are queried one after the other). Merging is where bugs hide: adding up each shard's **top 10 days** gave **3 of the 10 right days and 0 correct totals**; the right answer needed every day from every shard (730 rows). Page 101 of a list needed **1,010 rows from each shard**. This is the work Citus did in Concept 3.
</Tldr>

## The setup

All on `idx-mysql` (MySQL 8.4), three databases created for this session: `pt7_all` holds the 1,000,000 orders unsharded (the baseline); `pt7_s0` and `pt7_s1` are the shards; each has an index on `(seller_id, created_at)`. In production the shards would be separate servers; here they share one, so parallel fan-out uses two server threads on the same machine.

```python
SHARDS = [connect("pt7_s0"), connect("pt7_s1")]   # shard n holds seller_id % 2 = n

def shard_for(seller_id):
    """The only place that knows the sharding rule."""
    return SHARDS[seller_id % 2]

def fan_out_parallel(sql, args):
    """Send the same query to every shard at once; one thread and one connection per shard."""
    return list(pool.map(lambda c: run(c, sql, args), PARALLEL_SHARDS))
```

| Term | Meaning |
|---|---|
| Shard key | The column the routing function uses: `seller_id` |
| Routing function | Code that maps a shard key value to a database: `seller_id % 2` here; a directory table in Concept 5 |
| Fan-out | Sending one query to every shard |
| Merge | Combining the shards' results in the application: adding counts, re-sorting, re-limiting |
| Scatter-gather | Fan-out plus merge |
| **✓ / ✗** | Shard queried / not queried |

## Measured

PyMySQL from the host, median of 200 runs for lookups, 30 for reports, 10 to 50 for the rest, two runs of the script (ranges show both).

| Query | Unsharded `pt7_all` | Sharded | How |
|---|---|---|---|
| Seller 1673, December | 0.11–0.19 ms | 0.12–0.17 ms | routed to 1 shard |
| Order by id | 0.11–0.18 ms | 0.25–0.34 ms | both shards, one after the other |
| GMV per marketplace, December | 25–31 ms | 25–28 ms sequential, 16–17 ms parallel | fan-out, add |
| Top 10 days of 2025 | 127 ms | 70 ms | parallel fan-out of every day, add, sort |
| Page 101 (10 rows after 1,000) | 0.41 ms | 3.65 ms | 1,010 rows from each shard, sort, skip |

| Merge question | Correct with per-shard LIMIT? | Measured |
|---|---|---|
| Top 10 sellers | yes: a seller lives in one shard | identical to unsharded |
| Top 10 days | no: a day spans shards | naive 3/10 days, 0/10 totals; full merge identical |
| Page 101 | only with LIMIT offset + 10 per shard | identical; 2,020 rows shipped for 10 |

<Pitfall>
The routing function becomes part of every code path: background jobs, admin tools, data fixes, BI exports, migrations. One script that writes to the wrong database, or a report that forgets one shard, silently corrupts or undercounts data. Keep routing in one library, make every query go through it, and give each shard a check (for example a constraint or a periodic audit that `seller_id % 2` matches the shard). Merges need the same care as SQL: partial aggregates must combine (sum and count, not averages), and LIMIT can only be pushed to the shards when the group lives in one shard.
</Pitfall>

## Real-world scenario: an order service on sharded MySQL

| Requirement | What the team must build |
|---|---|
| Write an order | Router from `seller_id`; the order id must be unique across shards (Session 8) |
| Seller dashboards | Routed queries; nothing new |
| "Find order" for support | Fan-out, or a global `order_id → seller_id` lookup table |
| Daily finance report for all sellers | Fan-out + merge; or replicate all shards into a warehouse and report there |
| A seller grows too big for its shard | Move it (Concept 5): copy, switch routing, delete |
| Schema change | Run the migration on every shard, and handle the window where shards differ |

That list is the case for a sharding layer: Citus (Concepts 1–3) or, for MySQL, Vitess (Concept 5).

## Key takeaways

1. Application-level sharding is N ordinary databases plus a routing function in the code.
2. Queries with the shard key are as cheap as before; everything else is a fan-out.
3. The application must merge correctly: combine sums and counts, not averages; only push LIMIT down when a group lives in one shard.
4. Deep pagination costs OFFSET + LIMIT rows from every shard.
5. Every tool that touches the data must use the same router.
