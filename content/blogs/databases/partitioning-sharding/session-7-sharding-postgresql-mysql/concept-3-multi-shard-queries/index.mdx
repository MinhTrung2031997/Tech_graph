<Tldr>
A multi-shard query is split in two: a **worker part** run once per shard, and a **coordinator part** that merges. The coordinator can only merge cheaply if the worker part reduces the data first. `GROUP BY marketplace` with `count`, `sum` and `avg` returned **96 rows (4,796 bytes)** from 32 shards; top 10 sellers by GMV **320 rows**, because each shard sends its own top 10 (correct only because a seller lives in one shard); `count(DISTINCT seller_id)` **32 rows**. Some queries cannot be reduced: `ORDER BY created_at LIMIT 10 OFFSET 100000` made every shard send up to 100,010 rows, which here was **all 1,000,000 rows (15 MB, 906 ms vs 24 ms on the plain table)**; `percentile_cont` pulled **7.8 MB**. Keyset pagination (`WHERE (created_at, id) > …`) brought it back to **320 rows, 4.6 ms**. On this single laptop, full-table aggregates were about **2× slower** distributed (129 ms vs 68 ms for GMV per marketplace): the workers share the same CPUs, so there is only overhead to gain. `CREATE INDEX` on the distributed table built **32 shard indexes** in about the same time as one on the plain table.
</Tldr>

## How the coordinator splits a query

| Term | Meaning |
|---|---|
| Worker part | The SQL each task runs on its shard, possibly with partial aggregation, LIMIT and ORDER BY |
| Coordinator part | What runs on the coordinator over the tasks' results (`remote_scan`): final aggregation, sort, LIMIT |
| Partial aggregate | A per-shard result that can be combined: a count, a sum, a sum and count for avg |
| Pushdown | Moving work (filter, aggregation, limit) into the worker part |
| `Tuple data received from nodes` | EXPLAIN ANALYZE line: bytes the coordinator received from all tasks |
| **✓ / ✗** | Reduced on the worker / shipped raw to the coordinator |

## What travels to the coordinator

All on `orders_d` (1M rows, 32 shards), EXPLAIN ANALYZE, one run each:

| Query | Rows received | Bytes received | Pushed down |
|---|---|---|---|
| `GROUP BY marketplace` with count, sum, avg | 96 | 4,796 | ✓ partial aggregates |
| `GROUP BY seller_id ORDER BY sum DESC LIMIT 10` | 320 | 5,754 | ✓ complete groups + limit |
| `ORDER BY amount DESC, id LIMIT 10` | 320 | 6,400 | ✓ limit |
| `count(DISTINCT seller_id)` | 32 | 256 | ✓ distinct on the distribution column is per shard |
| `count(DISTINCT status)` | 96 | 832 | ✓ per-shard distinct values, de-duplicated on the coordinator |
| window `OVER (PARTITION BY marketplace …)`, one day | 1,367 | 45 kB | ✗ rows shipped, window on coordinator |
| `percentile_cont(0.5)` over the table | 1,000,000 | 7.8 MB | ✗ every value shipped |
| `ORDER BY created_at LIMIT 10 OFFSET 100000` | 1,000,000 | 15 MB | ✗ up to OFFSET + LIMIT rows per shard |
| keyset page, `WHERE (created_at, id) > …` | 320 | 5,120 | ✓ limit |

## Measured latency

pgbench, one connection, three repetitions, middle value. Same laptop for every column.

| Query | Plain `orders` | `orders_d`, 32 shards | `orders_d4`, 4 shards |
|---|---|---|---|
| December GMV (index on `created_at`) | 5.3 ms | 10.0 ms | 7.3 ms |
| GMV per marketplace, full table | 68 ms | 129 ms | 93 ms |
| Top 10 sellers, full table | 67 ms | 139 ms | |
| Page with OFFSET 100000 | 24 ms | 906 ms | |
| Keyset page | | 4.6 ms | |

The full-table aggregates are slower distributed **on this machine**: both workers and the coordinator run on the same 10 cores under emulation, so splitting the scan into 32 tasks adds coordination without adding hardware. On real separate servers the scan work divides by the number of workers; the coordination overhead stays. The 4-shard copy shows that overhead shrinking with fewer tasks.

## Writes and DDL across shards

| Statement | Measured |
|---|---|
| `CREATE INDEX … ON orders_d (amount)` | 545 ms; created on all 32 shards (`run_command_on_shards` found it on 32); plain table 495 ms |
| `CREATE INDEX CONCURRENTLY` on `orders_d` | works, 515 ms |
| `UPDATE orders_d … WHERE created_at >= '2025-12-31'` | 1,367 rows on every shard, one transaction, 78 ms |

A multi-shard UPDATE or DDL runs on every worker inside one distributed transaction; Session 8 looks at how Citus commits it (two-phase commit).

<Pitfall>
Deep `OFFSET` pagination is bad on one server ([Indexing Session 10, Concept 1](/blogs/databases/indexing/session-10-pagination-aggregation/concept-1-keyset-pagination)) and much worse when sharded: the coordinator must collect OFFSET + LIMIT rows **from every shard**, so the cost grows with the page number times the shard count. Here page 10,001 transferred the whole table. Use keyset pagination for any list that users page through across shards, and treat medians, percentiles and window functions over the whole table as "ship every row" operations: run them on a pre-aggregated table or with an approximation.
</Pitfall>

## Real-world scenario: the group-wide dashboard

A brand partner wants a dashboard across all their sellers' shops: GMV by marketplace and day, top SKUs, median order value, and an order list with paging.

| Widget | Behaviour on a table distributed by `seller_id` | What to do |
|---|---|---|
| GMV by marketplace and day | Partial aggregates, small transfer | Fine as is |
| Top 10 sellers | Per-shard top 10, correct | Fine as is |
| Top 10 SKUs across sellers | A SKU spans shards: every shard must send every SKU's partial sum | Fine for thousands of SKUs; for millions, pre-aggregate daily |
| Median order value | Every amount shipped to the coordinator | Pre-aggregate, or an approximate percentile extension |
| Order list, page 500 | OFFSET collects 500 pages from every shard | Keyset pagination |

## Key takeaways

1. A multi-shard query runs a worker part on every shard and a coordinator part that merges.
2. Counts, sums, averages, min/max, grouped results and ORDER BY … LIMIT are reduced on the workers; little data travels.
3. Grouping by the distribution column is complete per shard, so per-shard top N is correct.
4. OFFSET, percentiles and many window functions ship rows to the coordinator: the OFFSET query here moved the whole table.
5. On one machine sharding only adds overhead; the gain comes from more machines.
