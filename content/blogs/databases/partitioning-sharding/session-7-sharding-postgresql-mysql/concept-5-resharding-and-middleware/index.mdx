<Tldr>
The routing rule decides how painful growth is. **Modulo** (`seller_id % N`) is simple, but changing N moves most of the data: **2 → 4 shards moves 2,500 of the 5,000 sellers (500,022 of 1,000,000 rows)**, **2 → 3 moves 3,333 sellers (666,012 rows)**. A **directory table** (`seller_id → shard`) moves only the sellers you pick: copying seller 1673 (**247 rows**) between the lab's MySQL shards kept its writes frozen for **34 ms** (358 ms on a cold first run), at the price of a directory lookup on every request (**0.29 ms**, or a cache). **Citus** never changes a row's hash; it keeps 32 fixed hash ranges and moves or **splits** shards: `isolate_tenant_to_new_shard('orders_d4', 1673)` split one 40 MB shard into three and gave seller 1673 its own shard in **2.2 s**, during which an INSERT for that seller waited **1.7 s** (mode `block_writes`; the default mode needs `wal_level = logical` and failed). For MySQL, **Vitess** puts the router, the directory (vindexes) and online resharding into a proxy layer; **ProxySQL** routes queries but does not merge results. Both are described here from their documentation only; neither was run in the lab.
</Tldr>

## Modulo vs directory, measured

On `pt7_all` (1,000,000 orders, 5,000 sellers):

| Change | Sellers that change shard | Rows to move |
|---|---|---|
| `% 2` → `% 4` | 2,500 (50%) | 500,022 |
| `% 2` → `% 3` | 3,333 (67%) | 666,012 |
| Directory: move one big seller | 1 | 247 (seller 1673) |
| Directory: add a third shard, move a third of the sellers | 1,667, your choice | about 333,000 |

With modulo, a new shard count changes the answer of the routing function for half or more of the keys at once, so the move must happen for all of them together, typically with downtime or dual writes. A directory changes one key at a time.

| Term | Meaning |
|---|---|
| Resharding | Changing the number of shards or which keys each shard owns |
| Directory (lookup table) | A table mapping each shard key value to its shard; the router reads it |
| Freeze | Stopping writes for the keys being moved, so the copy cannot miss a change |
| Shard split | Cutting one shard's key range into several shards (Citus, Vitess) |
| Tenant isolation | Giving one key (a large seller) a shard of its own |
| **✓ / ✗** | Reads and writes allowed / blocked for the moving keys |

## Citus: split a shard instead of rehashing

Citus never changes the hash of a row. To grow, it **moves** whole shards to new workers (Session 8) or **splits** a shard's hash range. `isolate_tenant_to_new_shard` splits the shard that holds one value into three: the range below it, the value alone, the range above it.

## Middleware for MySQL (from documentation, not run in the lab)

**Vitess** (used for large MySQL fleets) moves the router into a proxy. The terms below are from the Vitess documentation:

| Vitess component | Role | Lab equivalent |
|---|---|---|
| vtgate | Stateless proxy that speaks the MySQL protocol; routes, scatters and merges | `shard_for()` + app merge |
| vttablet | Agent next to each mysqld | none |
| Topology service (etcd, ZooKeeper or Consul) | Stores which shards exist and where | config in the app |
| VSchema | Declares which tables are sharded and by what | the code |
| Primary vindex | Function from a column to a keyspace ID (e.g. `hash` on `seller_id`); shards own keyspace ID ranges such as `-80` and `80-` | `seller_id % 2` |
| Lookup vindex | A table-backed index from another column (e.g. `order_id`) to the keyspace ID, so those lookups route to one shard | the `order_id → seller_id` lookup table of Concept 1 |
| Reshard workflow (VReplication) | Copies data to the new shards, keeps them in sync from the binlog, compares (VDiff), then switches reads and writes with a short write pause | the mover script, without the freeze per seller |

**ProxySQL** (also from its documentation) can route queries to different MySQL backends (hostgroups) by rules on the schema name, the user or a comment in the query, so it can send "shard 1" queries to the right server. It does not know the shard key's meaning, cannot scatter a query to all shards and merge the results, and does not move data. The application still owns the routing decision (by choosing the schema or adding the comment) and every cross-shard merge.

## Comparison

| | Application sharding (lab) | Citus (lab) | Vitess (docs) |
|---|---|---|---|
| Routing | Code in every client | Coordinator | vtgate proxy |
| Cross-shard queries | Written by hand (Concept 4) | Planned and pushed down (Concept 3) | Scatter + merge in vtgate, with limits |
| Joins | In the app | Colocated, reference, repartition (Concept 2) | Within a shard, or with reference tables; limited across shards |
| Resharding | Manual: modulo moves 50%+, directory moves chosen keys | Fixed hash ranges; move or split shards | Reshard workflow, online |
| Unique ids across shards | Your problem (Session 8) | Your problem (Session 8) | Sequences in an unsharded keyspace |

<Pitfall>
Picking `seller_id % N` because it is the simplest router is a decision about every future migration: the first time N changes, half or more of the data moves, and every key whose shard changed must be frozen or dual-written during the move. If you shard in the application, start with a directory (cached) or with many logical shards mapped to few servers (for example 64 logical shards on 2 servers, `seller_id % 64` → server map), so growth means moving logical shards, not rehashing rows. This is what Citus's 32 hash ranges and Vitess's keyspace ID ranges do for you.
</Pitfall>

## Real-world scenario: the seller that outgrew its shard

A brand runs a mega-sale campaign and its orders grow tenfold. Its shard now has three times the load of the others.

| Setup | What you can do |
|---|---|
| `seller_id % N` in the app | Nothing targeted: changing N moves half the sellers |
| Directory in the app | Move that seller to a new, empty shard; freeze its writes for the copy |
| Citus | `isolate_tenant_to_new_shard` (2.2 s for 250,000 rows here, writes blocked for that shard), then move the new shard to its own worker |
| Vitess | Reshard the range that holds it, online, using VReplication |

## Key takeaways

1. With modulo routing, changing the number of shards moves half (2 → 4) or two thirds (2 → 3) of the data at once.
2. A directory moves only the keys you choose, with a short write freeze per key, at the cost of a lookup or cache.
3. Citus keeps fixed hash ranges and grows by moving or splitting shards; splitting one tenant out took 2.2 s here and blocked that shard's writes.
4. Non-blocking shard splits need `wal_level = logical` on the workers.
5. Vitess moves routing, merges and online resharding into a proxy; ProxySQL only routes.
