<Tldr>
A join can run inside each shard only if **every pair of matching rows lives in the same shard group**. Two tables distributed on the same column type with the same shard count are **colocated**: hash range N of both tables sits on the same worker. Joining `orders_d` and `items_s` (both by `seller_id`) **on `seller_id` and the order id** ran as 32 local joins: **192 ms** for December 2025. The same join **on the order id alone**, or against `items_o` distributed by `order_id`, needs rows moved between workers: Citus refused it ("the query contains a join that requires repartitioning") and, with `citus.enable_repartition_joins = on`, took about **10 s**: 50 times slower. Small shared tables go in a **reference table**, copied to every node: the sellers join took **41 ms**, close to the colocated `sellers_dist` (38 ms), while a plain local table on the coordinator had to be shipped to all 32 tasks (70 ms). The price of a reference table is on writes: **5.9 ms** per single-row UPDATE against **1.7 ms** on a distributed table.
</Tldr>

## The tables

All in database `pt7`, next to `orders_d` (1M orders, 32 shards by `seller_id`, Concept 1):

| Table | Rows | How it is stored |
|---|---|---|
| `items_s` | 2,000,000 (2 per order) | distributed by `seller_id`, `colocate_with => 'orders_d'` |
| `items_o` | 2,000,000 (same rows) | distributed by `order_id`, `colocate_with => 'none'` |
| `sellers_ref` | 5,000 | reference table: one full copy on the coordinator and on each worker |
| `sellers_dist` | 5,000 | distributed by `seller_id`, colocated with `orders_d` |
| `sellers_local` | 5,000 | plain table on the coordinator only |

`citus_tables` showed `orders_d`, `items_s` and `sellers_dist` with the same `colocation_id` (2), `items_o` with its own (5), and `sellers_ref` as `reference` with one shard placed on all three nodes.

| Term | Meaning |
|---|---|
| Colocation group | Tables with the same distribution column type and shard count whose shard N always sits on the same worker |
| Colocated join | A join on the distribution columns of colocated tables: Citus runs it as one join per shard pair, on the worker |
| Repartition join | A join on another column: workers re-hash both sides by the join key and send rows to each other (MapMergeJob) |
| Reference table | A small table copied in full to every node, so any shard can join to it locally |
| Local table join | A join with a plain coordinator table: Citus first ships the needed local rows to the workers (a "distributed subplan") |
| **✓ / ✗** | Runs on the worker without moving rows / needs rows moved or is refused |

## Measured

pgbench, one connection, three repetitions, middle value. Ratios only (see Concept 1 for why).

| Join | How the second table is stored | Latency | Rows moved between nodes |
|---|---|---|---|
| orders + items, on seller and order id | colocated (`items_s`) | 192 ms | none, 32 partial results |
| orders + items, on order id only | `items_o` by `order_id` (repartition on) | 10.0 s | both tables re-hashed |
| orders + sellers by country | reference (`sellers_ref`) | 41 ms | none |
| orders + sellers by country | colocated (`sellers_dist`) | 38 ms | none |
| orders + sellers by country | local on coordinator (`sellers_local`) | 70 ms | 5,000 rows to every task |
| same, no Citus (`orders` + `sellers_local`) | plain tables, coordinator | 17 ms | none |

| Single-row UPDATE | Latency |
|---|---|
| `sellers_ref` (3 copies) | 5.9 ms |
| `sellers_dist` (1 shard) | 1.7 ms |
| `sellers_local` | 1.2 ms |

<Pitfall>
Distributing `order_items` by its own key (`order_id`) looks natural and is wrong for this schema: every join with `orders` becomes a repartition join, refused by default and 50 times slower when allowed. Put the parent's distribution column into the child table (`order_items.seller_id`), distribute both by it, `colocate_with` the parent, and **include it in the join condition**. Note that `items_s` joined on the order id alone was still refused: Citus checks the join condition, not your data.
</Pitfall>

## Real-world scenario: the e-commerce schema in Citus

| Table | Choice | Reason |
|---|---|---|
| `orders`, `order_items`, `payments`, `returns` | distributed by `seller_id`, colocated | Seller dashboards are router queries; joins between them stay on one shard |
| `sellers` | distributed by `seller_id` (colocated) or reference | Joined to everything by `seller_id`; either works, colocated is cheaper to write |
| `marketplaces`, `countries`, `fx_rates`, `categories` | reference | Small, joined from every shard, rarely written |
| `products` shared across sellers (brand catalogue) | reference if small; otherwise its own distribution with care | A catalogue joined on `sku` from every seller is a repartition join if distributed by `sku` |

## Key takeaways

1. Tables distributed on the same column type with the same shard count can be colocated: shard N of each sits on the same worker.
2. A join stays on the workers only if its condition includes the distribution columns of colocated tables.
3. Anything else needs a repartition join: refused by default, about 50 times slower here when allowed.
4. Small tables joined from every shard belong in reference tables: fast joins, slower writes (one copy per node).
5. Joining a plain coordinator table works but ships it to the workers on every query.
