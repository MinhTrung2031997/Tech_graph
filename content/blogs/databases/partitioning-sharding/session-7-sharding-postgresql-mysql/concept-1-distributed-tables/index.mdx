<Tldr>
Citus turns one PostgreSQL table into many ordinary tables (**shards**) on **worker** nodes. `create_distributed_table('orders_d', 'seller_id')` cut the 1M orders into **32 shards** by a hash of `seller_id`, 16 per worker. The **coordinator** keeps the hash range of every shard and rewrites each query: with `seller_id = 1673` in the WHERE clause it sends **one task** to one shard (a *router query*); without it, it sends **32 tasks**. Measured on the lab (one connection, pgbench, best of 3): seller lookup **0.62 ms** distributed vs **0.20 ms** on a plain table; lookup by `id` only **1.96 ms** (32 tasks) vs **0.11 ms**; with `seller_id` added **0.54 ms**; single-row INSERT **1.45 ms** vs **0.89 ms**. A primary key must include the distribution column, and an INSERT without it fails.
</Tldr>

## The setup

All numbers in this session come from database `pt7` on the lab Citus cluster: coordinator `pt-citus` and workers `pt-citus-w1`, `pt-citus-w2`, Citus 13.0 on PostgreSQL 17.2, all on one laptop. The Citus image is built for amd64 and runs under emulation on the lab's arm64 Mac, and the two "servers" share the same 10 CPU cores. So **only ratios measured on Citus are meaningful**; never compare a Citus time with a time from `idx-pg` in earlier sessions. The plain table `orders` (1,000,000 rows, an index on `seller_id` added for this session) stays on the coordinator as the single-node baseline.

```sql
CREATE TABLE orders_d (LIKE orders INCLUDING DEFAULTS);
ALTER TABLE orders_d ADD PRIMARY KEY (id);
SELECT create_distributed_table('orders_d', 'seller_id');
-- ERROR:  cannot create constraint on "orders_d"
-- DETAIL:  Distributed relations cannot have UNIQUE, EXCLUDE, or PRIMARY KEY constraints
--          that do not include the partition column (with an equality operator if EXCLUDE).

ALTER TABLE orders_d DROP CONSTRAINT orders_d_pkey;
ALTER TABLE orders_d ADD PRIMARY KEY (seller_id, id);
SELECT create_distributed_table('orders_d', 'seller_id');   -- 206 ms, empty table
INSERT INTO orders_d SELECT * FROM orders;                  -- 2.4 s
CREATE INDEX orders_d_created_at_idx ON orders_d (created_at);
CREATE INDEX orders_d_id_idx ON orders_d (id);
```

This is the same rule as on a partitioned table ([Session 3, Concept 3](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/concept-3-unique-keys)): each shard can only check uniqueness inside itself. Session 8 deals with keeping `id` unique anyway.

Distributing a table that already holds data also works (1.9 s for 1M rows), but the original rows stay on the coordinator's disk, hidden: `SELECT count(*) FROM ONLY orders_d2` still returned 1,000,000 until `truncate_local_data_after_distributing_table` was run.

| Term | Meaning |
|---|---|
| Coordinator | The node clients connect to. Holds the metadata, plans the query, sends tasks, merges results |
| Worker | A PostgreSQL server that stores shards and runs tasks |
| Shard | An ordinary table on a worker, e.g. `orders_d_102033`, holding one hash range |
| Distribution column | The column whose hash picks the shard: `seller_id` here. Citus also calls it the partition column |
| Router query | A query the coordinator can send whole to one shard, because the WHERE clause fixes the distribution column |
| Multi-shard query | A query sent as one task per shard, results merged on the coordinator |
| Task | One SQL statement run against one shard |
| **✓ / ✗** | Shard or worker receives a task / is skipped |

## Where a row goes

`pg_dist_shard` splits the 32-bit hash space into 32 equal ranges. Seller 1673 hashes to `hashint4(1673) = 1274531150`, which falls in shard 102033's range `1207959552 … 1342177279`, and that shard lives on `pt-citus-w2`. `get_shard_id_for_distribution_column('orders_d', 1673)` returns the same answer without any arithmetic.

| Measured on `orders_d` | Value |
|---|---|
| Shards per worker | 16 and 16 |
| Size per worker | 70 MB and 71 MB |
| Sellers per shard | 134 to 173 (5,000 in total) |
| Rows per shard | 26,707 to 34,950 (mean 31,250, largest/smallest 1.31) |

Equal hash ranges do not mean equal shards: 5,000 sellers hashed into 32 buckets landed unevenly. With few distinct values, or one huge seller, the spread gets worse: that is the shard-key question of Session 5.

## Measured latency

One pgbench connection, 200 runs per query (500 for INSERT), three repetitions; the table shows the middle value.

| Query | Plain `orders` (coordinator) | `orders_d`, 32 shards | Ratio |
|---|---|---|---|
| `WHERE seller_id = 1673` (count, sum) | 0.20 ms | 0.62 ms (1 task) | 3.1× |
| `WHERE id = 777777` | 0.11 ms | 1.96 ms (32 tasks) | 18× |
| `WHERE seller_id = 145 AND id = 777777` | n/a | 0.54 ms (1 task) | |
| `WHERE id = 777777`, 4-shard copy | n/a | 0.92 ms (4 tasks) | |
| Single-row INSERT | 0.89 ms | 1.45 ms (1 task) | 1.6× |

A router query costs one extra network hop and the coordinator's planning: here about 0.4 ms. A multi-shard query costs that hop once per task. On one laptop the cluster cannot be faster for small queries; it is built for data that does not fit one server, where every worker brings its own disks, memory and CPUs.

<Pitfall>
Distributing a table does not distribute your queries. If the hot query in the application is "order by id" and the table is distributed by `seller_id`, every lookup fans out to all shards: here 18 times slower than the single-node table, and the gap grows with the shard count. Before choosing a distribution column, list the top queries and check that most of them carry it in the WHERE clause (Session 5 covers how to choose).
</Pitfall>

## Real-world scenario: a seller analytics product

A marketplace enabler stores orders for thousands of sellers across Shopee, TikTok Shop and Lazada. Every dashboard request is "for seller X": GMV, top products, returns. Distributing by `seller_id`:

| Need | With `seller_id` as distribution column |
|---|---|
| Seller dashboard | Router queries: one shard, cost close to a single-node query |
| Write path | Each order goes to its seller's shard; writes spread over all workers |
| Support tool "find order 123" | Fan-out to every shard, unless the tool also knows the seller (store `seller_id` in the order number or the ticket) |
| Group-wide report | Multi-shard query; Concept 3 shows which ones push down well |

## Key takeaways

1. `create_distributed_table` hashes the distribution column into a fixed number of shards (32 by default) placed on the workers.
2. A query whose WHERE clause fixes the distribution column is a router query: one task on one shard.
3. Without the distribution column, the coordinator sends one task per shard; more shards means more tasks.
4. Primary keys and unique constraints must include the distribution column; INSERTs must supply it.
5. Equal hash ranges do not guarantee equal shards: here 26,707 to 34,950 rows per shard.
