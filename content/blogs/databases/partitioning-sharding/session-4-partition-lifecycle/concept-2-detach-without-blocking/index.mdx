<Tldr>
Dropping a partition needs **ACCESS EXCLUSIVE on the parent table**, not just on the partition. One open transaction that read **any** partition (here: December 2025) makes the DROP wait, and every query that arrives after the DROP waits behind it: a read of December that normally takes milliseconds took **10.2 s**. `ALTER TABLE … DETACH PARTITION … CONCURRENTLY` takes only SHARE UPDATE EXCLUSIVE on the parent: it still waited 11 s for the old reader to finish, but new reads ran in **0.10 s**. It cannot run inside a transaction block; if interrupted, it leaves the partition "pending detach" until `… FINALIZE`. **MySQL** `DROP PARTITION` queues on the table's metadata lock the same way (reader 10.2 s); `SET SESSION lock_wait_timeout = 2` made the job fail with **ERROR 1205** after 2.09 s and the reader waited 1.08 s. **MongoDB** `drop()` took **2 ms**; an open cursor on the dropped collection failed with **QueryPlanKilled**.
</Tldr>

## The setup

Three sessions on `orders_p` (24 monthly partitions):

- **T1** reads December 2025 (`count(*) … WHERE created_at >= '2025-12-01'`) and keeps its transaction open for 12 s: a report, or a request whose transaction is left open.
- **T2**, one second later, removes January 2024.
- **T3**, one more second later, runs the same December read as T1.

| Term | Meaning |
|---|---|
| ACCESS EXCLUSIVE | PostgreSQL's strongest table lock: conflicts with everything, including plain SELECT |
| SHARE UPDATE EXCLUSIVE | Conflicts with schema changes and VACUUM, not with SELECT, INSERT, UPDATE, DELETE |
| Lock queue | A waiting lock request blocks later requests that conflict with it, even if they are compatible with the current holder |
| Metadata lock (MDL) | MySQL's table-level lock held by every statement and kept by a transaction until it ends; DDL needs it EXCLUSIVE |
| **✓ / ✗** | Runs at once / waits |

| T2 statement | Lock on `orders_p` | T2 waited | T3 (new December read) |
|---|---|---|---|
| `DROP TABLE orders_p_2024_01` | AccessExclusiveLock | 11.2 s | ✗ 10.2 s |

| `DETACH … CONCURRENTLY` inside `BEGIN` | — | ERROR: cannot run inside a transaction block | — |

`DETACH … CONCURRENTLY` also adds a CHECK constraint to the detached table that copies its old bound (`orders_p_2024_01_created_at_check`). That matters if you attach it again (Concept 3).

MySQL has no `DROP PARTITION CONCURRENTLY`. `DROP PARTITION` accepts `ALGORITHM=INPLACE, LOCK=NONE` (tested), which allows concurrent DML **while it runs**, but like every DDL it still needs the exclusive metadata lock to start and finish: the queue above happens anyway. The defence is a short `lock_wait_timeout` and a retry loop.

## Comparison

| | PostgreSQL DROP | PostgreSQL DETACH CONCURRENTLY | MySQL DROP PARTITION | MongoDB drop() |
|---|---|---|---|---|
| Lock on the whole table | ACCESS EXCLUSIVE | SHARE UPDATE EXCLUSIVE | EXCLUSIVE metadata lock | collection X lock, brief |
| Waits for an old reader | yes | yes (for its transaction to end) | yes | no |
| Blocks new readers while waiting | **yes** | no | **yes** | no |
| Effect on the old reader | none | none | none | cursor killed |
| Inside a transaction | yes | no | n/a (DDL commits implicitly) | n/a |

<Pitfall>
"It only takes 5 ms" is about the work, not the wait. A retention job that runs `DROP TABLE` on a partition at 02:00, while a 30-minute report is reading the table, freezes **every** query on that table for up to 30 minutes. In PostgreSQL use `DETACH … CONCURRENTLY` then drop the detached table, or at least `SET lock_timeout = '2s'` and retry. In MySQL set `lock_wait_timeout` to a few seconds for the job's session. The same lock queue hits `CREATE INDEX` and other DDL: see [Indexing Session 8, Concept 3](/blogs/databases/indexing/session-8-when-indexes-hurt/concept-3-concurrently-locking).
</Pitfall>

## Real-world scenario: the retention job and the BI extract

A nightly BI extract opens a transaction at 01:00 and reads all orders of the last month until 01:40. The retention job runs at 01:30: `ALTER TABLE orders DETACH PARTITION orders_2024_09; DROP TABLE orders_2024_09;`. From 01:30 to 01:40 checkout cannot read or write `orders`, the connection pool fills, and the on-call engineer sees "too many clients".

| Fix | Effect |
|---|---|
| `DETACH PARTITION … CONCURRENTLY`, then `DROP TABLE` the detached table | The job waits until 01:40; checkout never waits |
| `SET lock_timeout = '2s'` in the job and retry every few minutes | If something must take ACCESS EXCLUSIVE, the stall is at most 2 s |
| Monitor `inhdetachpending` | A cancelled detach is visible and finished with `FINALIZE` |
| Keep the extract out of a single long transaction | Fewer old snapshots to wait for (also helps VACUUM) |

## Key takeaways

1. Dropping or detaching a partition (non-concurrently) locks the **parent** in ACCESS EXCLUSIVE mode, so it waits for readers of any partition.
2. A waiting ACCESS EXCLUSIVE request blocks every later query on the table: a millisecond read took 10.2 s.
3. `DETACH … CONCURRENTLY` takes SHARE UPDATE EXCLUSIVE and waits for old transactions without blocking new ones. It cannot run in a transaction block, and an interrupted one needs `FINALIZE`.
4. MySQL's `DROP PARTITION` queues on the metadata lock; there is no concurrent variant, so use a short `lock_wait_timeout`.
5. MongoDB's `drop()` does not wait: it kills open cursors on the collection.
