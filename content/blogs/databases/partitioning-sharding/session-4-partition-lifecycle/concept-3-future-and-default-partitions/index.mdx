<Tldr>
A range-partitioned table only accepts rows for ranges that exist: an order dated 2026-01-05 failed with **"no partition of relation "orders_p" found for row"** in PostgreSQL and **ERROR 1526** in MySQL. So future partitions are created ahead of time, and **how** you create them matters:

- **PostgreSQL** `CREATE TABLE … PARTITION OF` takes **ACCESS EXCLUSIVE** on the parent: behind one 12-second reader, it waited 11.1 s and a new read waited 10.1 s. `CREATE TABLE … (LIKE …)` + `ATTACH PARTITION` takes **SHARE UPDATE EXCLUSIVE**: 0.09 s, nobody blocked.
- **ATTACH** checks every row of the incoming table (10–16 ms for 212,039 rows) unless a matching CHECK constraint proves the range (about 1 ms).
- A **DEFAULT partition** catches rows with no partition, then gets in the way. With 1M rows in it: a new partition for a month that had rows in DEFAULT **failed** ("updated partition constraint for default partition … would be violated"); any other new partition **scanned DEFAULT** (26–30 ms) under ACCESS EXCLUSIVE on it, unless a CHECK on DEFAULT ruled the range out (**1.5 ms**).
- **MySQL** has no DEFAULT; a `MAXVALUE` partition plays that role, and splitting it with `REORGANIZE PARTITION` **copied** its rows: 1.56 s for 1M rows, writes to the table waiting 1.43 s, against 0.04 s when it was empty.
- **MongoDB**: a month collection created by the first insert has only the `_id` index; find on `created_at` was a **COLLSCAN**.
</Tldr>

## The setup

`orders_p` has monthly partitions for 2024-01 … 2025-12. It is now January 2026, and new orders must go somewhere.

| Term | Meaning |
|---|---|
| Future partition | A partition created before any row for its range exists |
| `ATTACH PARTITION` | Turn an existing table into a partition; verifies that every row fits the bound |
| DEFAULT partition | PostgreSQL catch-all for rows that match no other partition |
| `MAXVALUE` partition | MySQL's open-ended last range, the closest thing to DEFAULT |
| Implied by constraints | PostgreSQL skips the verification scan when a CHECK constraint already proves it |
| **✓ / ✗** | Proceeds without blocking or scanning / blocks, scans or fails |

The verification scan of ATTACH, on the January 2024 table (212,039 rows) re-attached:

| ATTACH of `orders_p_2024_01` | Time | `client_min_messages = debug1` says |
|---|---|---|
| No CHECK constraint, 3 runs | 15.8, 11.0, 10.1 ms | `verifying table "orders_p_2024_01"` |
| With `CHECK (created_at >= '2024-01-01' AND created_at < '2024-02-01')` | 1.1 ms | `partition constraint … is implied by existing constraints` |

The scan runs under ACCESS EXCLUSIVE on the table being attached (not on the parent), so it only matters for tables that are big or in use. Concept 4 measures it on 5M rows.

## Comparison

| | PostgreSQL | MySQL | MongoDB (collection per month) |
|---|---|---|---|
| Row with no partition | ERROR, row rejected | ERROR 1526 | collection created implicitly, no indexes |
| Catch-all | DEFAULT partition | `MAXVALUE` partition | — |
| Adding a month, no catch-all | `ATTACH`: SHARE UPDATE EXCLUSIVE, 0.09 s | `ADD PARTITION`: 0.11 s, metadata lock | `createCollection` + indexes: 26 ms |
| Adding a month, catch-all with rows | DEFAULT scanned (26–30 ms per 1M rows), or ERROR if the month is in it | `REORGANIZE` copies pmax (1.56 s per 1M rows), writes wait | — |
| Tooling | pg_partman `premake` (not installed here) | event scheduler or cron | your scheduler |

PostgreSQL 17 has no `SPLIT PARTITION` or `MERGE PARTITIONS`: both are syntax errors on 17.11 (`syntax error at or near "SPLIT"`). The extension **pg_partman** (described from its documentation, not run here) creates future partitions ahead (`premake`, default 4) from a scheduled `run_maintenance()` and can drop or detach old ones by a retention setting.

<Pitfall>
A DEFAULT partition turns a missed maintenance run from a loud failure (inserts error out today) into a silent one (inserts succeed, and next month's DDL fails or scans and locks DEFAULT). If you keep one, monitor that it stays empty (`SELECT count(*) FROM orders_p_default` should be 0) and alert on the first row. Better: create partitions several months ahead and have no DEFAULT.
</Pitfall>

## Real-world scenario: the campaign month

The partition job creates next month's partition on the 25th. In November it failed silently (a permission change). On 1 December, during a mega-sale, every insert into `orders` started failing with "no partition of relation "orders" found for row": checkout was down until someone created the partition by hand, which waited 40 s for the ACCESS EXCLUSIVE lock behind a dashboard query.

| Fix | Effect |
|---|---|
| Create partitions 3 months ahead, not 1 | Two missed runs are still safe |
| Use `CREATE TABLE … (LIKE …)` + `ATTACH PARTITION` | No ACCESS EXCLUSIVE on the parent |
| Alert when fewer than 2 future partitions exist | A failed job is noticed weeks before it matters |
| No DEFAULT partition | Missing partitions fail loudly instead of corrupting the scheme |

## Key takeaways

1. Range partitions must exist before their rows arrive; a missing one rejects inserts in PostgreSQL and MySQL.
2. In PostgreSQL, `CREATE TABLE … PARTITION OF` locks the parent ACCESS EXCLUSIVE; `CREATE TABLE` + `ATTACH PARTITION` takes SHARE UPDATE EXCLUSIVE.
3. ATTACH verifies every row unless a CHECK constraint already proves the bound.
4. A DEFAULT partition makes each new partition scan and lock DEFAULT, and fails it if DEFAULT holds rows of the new range.
5. MySQL's MAXVALUE partition has to be split with `REORGANIZE`, which copies its rows and blocks writes; keep it empty.
6. In MongoDB, create next month's collection and its indexes ahead of time, or the first insert creates it without them.
