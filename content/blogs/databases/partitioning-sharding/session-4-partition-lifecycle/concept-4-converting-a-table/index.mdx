<Tldr>
Partitioning is decided when a table is created. Converting `orders` (5,000,000 rows, 579 MB with indexes) later, three ways:

- **PostgreSQL, copy:** create a partitioned table and `INSERT … SELECT`: **6.1 s**, **1.22 GB of WAL**, **624 MB** of new space, and the writes made during the copy still have to be caught up.
- **PostgreSQL, attach in place:** the old table becomes **one partition** covering everything before 2026, and new months get their own partitions. The slow steps run without blocking writes: `CREATE UNIQUE INDEX CONCURRENTLY (id, created_at)` **0.88 s**, `ADD CONSTRAINT … CHECK … NOT VALID` + `VALIDATE` **0.14 s**. The switch transaction took **about 33 ms**, because ATTACH found the range "implied by existing constraints". Without the CHECK, ATTACH scanned the 5M rows (140–276 ms) under ACCESS EXCLUSIVE.
- **MySQL:** `PARTITION BY` failed with **ERROR 1503** until the primary key included `created_at`. That took a **6.3 s** rebuild; then `PARTITION BY` copied every row (**9.4–10.3 s**). Only ALGORITHM=COPY with LOCK=SHARED is allowed, so an insert waited **8.5 s**.
- **MongoDB:** no partitioned collections to convert to. `$out` copied one month to its own collection in 0.44–0.78 s, and `collMod` made the existing `created_at` index a TTL index in **1 ms**.
</Tldr>

## The setup

`orders_c` is a copy of `orders`: `PRIMARY KEY (id)`, index on `created_at`, 5,000,000 rows from 2024-01-01 to 2025-12-31. The target is monthly partitions on `created_at`, with the application still writing.

| Term | Meaning |
|---|---|
| Copy migration | Build the partitioned table next to the old one and copy all rows |
| Attach in place | Make the existing table one (large) partition of a new partitioned parent |
| `NOT VALID` + `VALIDATE` | Add a constraint without checking old rows (instant), then check them under a lock that allows writes |
| `CONCURRENTLY` | Build an index without blocking writes |
| **✓ / ✗** | Writes continue / writes blocked |

| Step (attach in place) | Time | Lock on the old table | Writes |
|---|---|---|---|
| `CREATE UNIQUE INDEX CONCURRENTLY` | 880 ms | SHARE UPDATE EXCLUSIVE | ✓ |
| `ADD CONSTRAINT … NOT VALID` | 3.3 ms | ACCESS EXCLUSIVE, brief | ✗ for 3 ms |
| `VALIDATE CONSTRAINT` | 141.7 ms | SHARE UPDATE EXCLUSIVE | ✓ |
| Switch transaction | ≈ 33 ms | ACCESS EXCLUSIVE | ✗ for 33 ms |
| Same ATTACH **without** the CHECK (3 runs) | 276, 141, 139 ms | ACCESS EXCLUSIVE | ✗ for the whole scan |

What went wrong on the first try: keeping the old `PRIMARY KEY (id)` and adding the parent's key failed with **"multiple primary keys for table "orders_legacy" are not allowed"**. The old key must be replaced by the (id, created_at) index inside the switch, which also means `id` alone is no longer enforced unique by the database (Session 3, Concept 3 covers ways to keep it).

After the switch, `orders_legacy` holds 2024–2025 and every new month gets its own partition. When the newest row in `orders_legacy` passes the retention period, the whole legacy partition is dropped at once. No row ever has to be moved.

## Comparison

| Convert 5M rows to monthly partitions | Data rewritten | Write blocking | Time (lab) |
|---|---|---|---|
| PostgreSQL copy | all rows, 1.22 GB WAL | none during copy; catch-up needed | 6.1 s |
| PostgreSQL attach in place | none | 3 ms + 33 ms | 0.88 s + 0.14 s + 0.03 s |
| MySQL `PARTITION BY` | all rows, twice (PK, then partitions) | the whole copy | 6.3 s + 9.4 s |
| MySQL online tool | all rows, in background | the final swap | not measured |
| MongoDB `$out` per month | one month at a time | none | 0.44–0.78 s per month |
| MongoDB TTL via `collMod` | none | none | 1 ms |

<Pitfall>
The lab table is 579 MB and cached. On a 500 GB table, the copy is hours of WAL or binlog that every replica replays, and the MySQL `PARTITION BY` blocks writes for those hours. In PostgreSQL, never let ATTACH do the validation: without the CHECK constraint the full scan runs under ACCESS EXCLUSIVE (here 140–276 ms for 5M rows, linearly more for more). Run `VALIDATE CONSTRAINT` first, when writes are still allowed.
</Pitfall>

## Real-world scenario: partitioning order history at 800 million rows

An order table has grown to 800M rows over five years. Retention is now 3 years, and deleting 2 years of rows would take days of DELETE and VACUUM.

| Step | How |
|---|---|
| 1. Unique index `(id, created_at)` | `CREATE UNIQUE INDEX CONCURRENTLY` (hours, writes continue) |
| 2. `CHECK (created_at < '2026-02-01') NOT VALID`, then `VALIDATE` | One full scan, writes continue |
| 3. Switch transaction with `lock_timeout = '2s'` | Seconds, retried until it gets the lock |
| 4. New monthly partitions from 2026-02 | Created 3 months ahead (Concept 3) |
| 5. Old data | Option A: wait until all legacy rows are past 3 years and drop the legacy partition. Option B: copy the most recent 3 years out of legacy month by month into proper partitions, then drop legacy. |

## Key takeaways

1. Copying into a partitioned table rewrites every row (1.22 GB of WAL for 5M rows) and leaves the "writes during the copy" problem to you.
2. In PostgreSQL the existing table can become one partition: index it concurrently, validate a CHECK, and the switch is milliseconds.
3. ATTACH without a matching CHECK scans the whole table under ACCESS EXCLUSIVE; with it, ATTACH is a catalog change.
4. MySQL first requires the partition column in every unique key, then rebuilds the table with ALGORITHM=COPY and writes blocked; large tables need an online schema-change tool.
5. MongoDB has nothing to convert: either move months into collections or turn the existing index into a TTL index with `collMod`.
