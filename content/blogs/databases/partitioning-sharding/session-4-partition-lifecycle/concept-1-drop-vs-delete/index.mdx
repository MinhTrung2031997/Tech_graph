<Tldr>
Deleting a month row by row is a **write of every row**, and it leaves the space behind. On `orders` (5M rows, 24 months), removing January 2024 (**212,039 rows**) measured:

- **PostgreSQL:** DELETE 88–104 ms, **11.4 MB** of WAL (27.6 MB on a cold run), then a VACUUM of 0.69 s and another **10.9 MB** of WAL. The table file stayed **365 MB** and the indexes 214 MB. `DROP TABLE orders_p_2024_01` took **4–16 ms**, about **44 KB** of WAL, and gave its 26 MB back.
- **MySQL:** DELETE **0.47 s** and **8.7 MB** of binlog, with the tablespace file unchanged at 404 MiB. `DROP PARTITION` took **0.02–0.06 s** and wrote **215 bytes** of binlog.
- **MongoDB:** `deleteMany` took **0.76–1.17 s**, and `storageSize` stayed 146.4 MB. Dropping a month collection took **1–2 ms**. A TTL index also removes the month, document by document, in the background.

At this size every option finishes in about a second. The difference is what it **scales with**: DELETE with the rows, DROP with nothing.
</Tldr>

## The setup

Two copies of the same data in database `pt4`: `orders` (one table) and `orders_p` (24 monthly range partitions, `orders_p_2024_01` … `orders_p_2025_12`). The job: remove everything before 2024-02-01. Setup and seeds are in the [Session 1 lab](/blogs/databases/partitioning-sharding/session-1-why-split-data/lab); the partitioned copy is built in this [session's lab](/blogs/databases/partitioning-sharding/session-4-partition-lifecycle/lab).

| Term | Meaning |
|---|---|
| Retention | Keeping only the last N months; older data is removed on a schedule |
| Row-by-row removal | DELETE / deleteMany: each row is found, marked deleted, logged |
| Partition removal | DROP / TRUNCATE / DETACH of a whole partition: a catalog change plus a file removal |
| WAL / binlog | Logs every change for crash recovery and replicas; its volume is what replicas must replay |
| Dead tuple | A PostgreSQL row version that is deleted but still occupies space until VACUUM |
| **✓ / ✗** | Cheap and independent of row count / costs work per row |

## Comparison

| Remove 212,039 rows (one month) | Time | Log volume | Space after |
|---|---|---|---|
| PostgreSQL DELETE | 88–104 ms (489 ms cold) | 11.4–27.6 MB WAL | 365 MB, 212,039 dead tuples |
| + VACUUM | 0.69 s | 10.9 MB WAL | 365 MB, reusable inside |
| PostgreSQL DROP partition | 4–16 ms | ≈ 44 KB WAL | 26 MB returned |
| MySQL DELETE | 0.46–0.62 s | 8.7 MB binlog | 404 MiB file unchanged |
| MySQL DROP PARTITION | 0.02–0.06 s | 215 B binlog | .ibd file removed |
| MongoDB deleteMany | 0.76–1.17 s | 1 oplog entry per doc on a replica set | 146.4 MB unchanged |
| MongoDB TTL | ≤ 60 s delay, one pass | same as deleteMany | same as deleteMany |
| MongoDB drop month collection | 1–2 ms | one entry | files removed |

<Pitfall>
The lab numbers make DELETE look harmless: half a second. They scale with the month. At 50 million orders a month the same DELETE writes about 2.7 GB of WAL in PostgreSQL (11.4 MB × 236) and 2 GB of binlog in MySQL, every replica replays it, and in PostgreSQL VACUUM then reads every index in full. DROP stays at milliseconds. Partition by the column you expire on, with partitions no larger than your retention step.
</Pitfall>

## Real-world scenario: 13 months of marketplace orders

A seller dashboard keeps 13 months of orders. The nightly job ran `DELETE FROM orders WHERE created_at < now() - interval '13 months'`: about 1.6M rows a night. Replicas fell 20 minutes behind every night, autovacuum ran on the table most of the day, and the table never got smaller even though the row count was flat.

| Change | Effect |
|---|---|
| Partition `orders` by month on `created_at` | Each month is its own file |
| Retention job: `DETACH PARTITION … CONCURRENTLY`, dump to object storage, `DROP TABLE` | Milliseconds of catalog work, no WAL per row (Concept 2 covers the locks) |
| Keep daily granularity out of the partition scheme; delete at month boundaries | The 13-month rule becomes "13 or 14 months", agreed with the business |

## Key takeaways

1. A DELETE writes, logs and later cleans up **every row**; a DROP or TRUNCATE of a partition is a catalog change plus a file removal.
2. PostgreSQL: 11.4 MB of WAL for the DELETE plus 10.9 MB for its VACUUM, against about 44 KB for DROP.
3. MySQL: 8.7 MB of binlog (full row images) against 215 bytes for DROP PARTITION.
4. After a DELETE the file does not shrink in any engine; the space is only reused.
5. In MongoDB, a TTL index automates the deletes but does the same per-document work; only one collection per period gives a drop.
