<Tldr>
MongoDB splits data across servers (sharding, later in this course) but has no way to partition a collection on one server. There are three ways to lay out time-ordered orders:
- **A plain collection** with an index on `created_at`: 146.4 MB of data plus 115.1 MB of indexes. `_id` is unique, and a lookup by id takes 0.28 ms.
- **A time-series collection** (`timeField: created_at`, `metaField: marketplace`): 5,000,000 documents were stored in 5,002 compressed buckets, **32.0 MB with 0.2 MB of indexes**. A month's GMV by marketplace took **10.7 ms instead of 73.7 ms**. It **refused unique indexes** (`Unique indexes are not supported on time-series collections`) and stored the same `order_id` twice. A lookup by order id read all 5,002 buckets (2.1 ms).
- **One collection per month** (`orders_2024_01` …): about the same size as the plain collection. A month is a collection you can drop instantly. But `_id` is unique only inside each month, and a lookup by id needs `$unionWith` over 24 collections (1.38 ms).
</Tldr>

## The three layouts

| Term | Meaning |
|---|---|
| Time-series collection | A collection stored as **buckets**: up to 1,000 measurements with the same `metaField` value and nearby times, compressed column by column |
| `timeField` / `metaField` | The timestamp (`created_at`) and the grouping field (`marketplace`) that decide the bucket |
| Bucket | One internal document in `system.buckets.orders_ts` holding many orders, with min/max per field |
| Collection per period | A naming convention (`orders_2025_03`): the application picks the collection |
| `$unionWith` | Aggregation stage that appends another collection's results: how you query across months |
| **✓ / ✗** | Works / does not work for that query or constraint |

```js
// time-series copy (11.2 s with $out)
db.orders.aggregate([
  { $project: { _id: 0, order_id: '$_id', seller_id: 1, marketplace: 1, status: 1, amount: 1, created_at: 1 } },
  { $out: { db: 'pt3', coll: 'orders_ts',
            timeseries: { timeField: 'created_at', metaField: 'marketplace', granularity: 'minutes' } } }
]);
// one collection per month (24 × $out + createIndex({ created_at: 1 }): 10.9 s)
db.orders.aggregate([{ $match: { created_at: { $gte: ISODate('2025-03-01'), $lt: ISODate('2025-04-01') } } },
                     { $out: 'orders_2025_03' }]);
```

## Comparison

| | Plain collection | Time-series collection | Collection per month |
|---|---|---|---|
| Storage (data + indexes) | 146.4 + 115.1 MB | 32.0 + 0.2 MB | 145.7 + 104.8 MB (24 collections) |
| One-day count | 0.88 ms | 0.70 ms | 0.92 ms |
| Month GMV by marketplace | 73.7 ms | 10.7 ms | 36.3 ms |
| Lookup by order id | 0.28 ms | 2.1 ms (all buckets) | 1.38 ms (24 collections) |
| Unique order id | ✓ `_id` | ✗ no unique indexes | ✗ only per month |
| Dropping a month | `deleteMany` (row by row) or TTL | TTL removes whole buckets (`expireAfterSeconds`, per the manual) | `drop()` one collection |
| Query across months | Normal | Normal | `$unionWith` per month |

Session 4 measures dropping a month in each layout: `deleteMany`, a TTL index, and `drop()`.

## Same problems, in MySQL and PostgreSQL

Collection per month is the same idea as a partitioned table, except that the application does the routing. It has the same costs as Concepts 1 and 3: a lookup without the month asks every month, and uniqueness stops at the month boundary. A time-series collection behaves like a columnar, compressed store. PostgreSQL and MySQL have nothing equivalent built in.

<Pitfall>
A time-series collection is not a drop-in replacement for `orders`. It is built for append-mostly data read by time range. It refuses unique indexes, so it can't stop a re-sent order from being stored twice, and a lookup by order id reads every bucket unless you add a (non-unique) index. Keep the operational orders in a plain collection with its unique `_id`. Copy them into a time-series collection for analytics and dashboards, where 4.6× less data (8× counting indexes) and 7× faster month scans pay off.
</Pitfall>

## Real-world scenario: the dashboard collection

A brand dashboard shows GMV per marketplace per hour for the last 13 months. It currently aggregates over the operational `orders` collection, and the 13-month view takes seconds while competing with checkout for cache.

| Option | Effect (from this lab's numbers) |
|---|---|
| Nightly `$merge` of new orders into a time-series collection (`metaField` holding marketplace and brand) | Month scans ~7× faster, data ~4.6× smaller, checkout collection untouched |
| Duplicates from re-runs | Possible (no unique index). Make the job idempotent: only copy `created_at` after the last copied time |
| Retention | Set `expireAfterSeconds` on the time-series collection for 13 months |

## Key takeaways

1. MongoDB has no table partitioning on one server; time-series collections and one collection per period are the usual substitutes.
2. A time-series collection stored the 5M orders in 32 MB (vs 146 + 115 MB) and summed a month 7× faster, but refused every unique index.
3. One collection per month gives instant drops, but no cross-month uniqueness and a `$unionWith` per month for lookups by id.
4. A plain collection keeps a global unique `_id` and the fastest id lookups; deleting old data from it is the expensive part (Session 4).
