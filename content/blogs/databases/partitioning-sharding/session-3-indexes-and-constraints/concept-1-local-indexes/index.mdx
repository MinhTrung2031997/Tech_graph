<Tldr>
`CREATE INDEX ON orders_p (seller_id)` created **one partitioned index with no entries** plus **24 ordinary indexes**, one per monthly partition; partitions added later got theirs automatically. Neither PostgreSQL nor MySQL has a global index across partitions. So a query that does not filter on the partition key (`created_at`) has to **probe every partition's index**: `WHERE id = 2500000` read **73 buffers in 24 index scans** instead of 4 buffers in one, and took **0.137 ms instead of 0.013 ms** (pgbench, best of 5). MySQL showed the same: `EXPLAIN` listed all 24 partitions, `Handler_read_key` went from 1 to 24, and a lookup went from **10.1 to 43.6 µs**. Adding the month to the query brought it back to 1 partition and 4 buffers. Queries that read many rows (one seller's ~1,000 orders, one day's 6,840) cost about the same either way.
</Tldr>

## The setup

`orders` is the plain 5M-row table from the [Session 1 lab](/blogs/databases/partitioning-sharding/session-1-why-split-data/lab). `orders_p` is the same data in 24 monthly range partitions on `created_at` (`orders_p_2024_01` … `orders_p_2025_12`), built as in [Session 2](/blogs/databases/partitioning-sharding/session-2-partitioning-postgresql/concept-1-declarative-partitioning). Both tables got the same indexes on `id`, `seller_id` and `created_at`.

| Term | Meaning |
|---|---|
| Partitioned index | The index you create on the parent. In PostgreSQL it is catalog-only (`relkind = 'I'`): it holds no entries, only links to the partition indexes |
| Partition index (local index) | An ordinary B-tree on one partition, holding that partition's rows only |
| Global index | One index over all partitions' rows. **Neither engine has one** |
| Probe | One descent from the root of one B-tree to a leaf |
| **✓ Probed / ✗ Pruned** | Did the query descend this partition's index? |

## PostgreSQL

```sql
CREATE INDEX orders_p_seller_idx ON orders_p (seller_id);
SELECT count(*) FILTER (WHERE relkind = 'I') AS parent, count(*) FILTER (WHERE relkind = 'i') AS leaf,
       pg_size_pretty(sum(pg_relation_size(oid)))
FROM pg_class WHERE relname LIKE 'orders_p%seller%';
--  parent | leaf | size
--       1 |   24 | 35 MB         (orders_seller_idx on the plain table: 35 MB)
```

### What each partition index looks like

Each partition index is smaller, but not by as much as you might think. B-trees grow by **levels**, and each level multiplies capacity by a few hundred:

| Index | Rows | `bt_metap` level (root height) | Probe cost |
|---|---|---|---|
| `orders_pkey` (plain, id) | 5,000,000 | 2 (3 levels) | 3 pages + heap |
| `orders_p_2024_01_id_idx` | 212,039 | 2 (3 levels) | 3 pages |
| `orders_seller_idx` (plain) | 5,000,000 | 2 (3 levels) | 3 pages |
| `orders_p_2024_01_seller_id_idx` | 212,039 | 1 (2 levels) | 2 pages |

A partition index saves at most one level per probe. Probing 24 of them costs far more than that saving.

### Queries that read many rows

| Query (PostgreSQL) | `orders` | `orders_p` | Why |
|---|---|---|---|
| `WHERE id = :i` (1 row) | 0.013 ms, 4 buffers | 0.137 ms, 73 buffers | 24 probes for 1 row |
| `WHERE seller_id = :s` (~1,000 rows, count + sum) | 1.28 ms | 1.44 ms | 4 vs 48 index buffers, but ~950 heap pages either way |
| `created_at` within one day (6,840 rows) | 0.274 ms | 0.305 ms | Pruned to 1 partition |
| `CREATE INDEX … (seller_id)` | 0.75 s | 0.60 s | Same total work, best of 3 |

The probe overhead is fixed per partition, so it dominates a 1-row lookup and disappears in a query that reads hundreds of rows. A seller's orders are spread over all 24 months anyway, so the plain table reads about the same heap pages (949 vs 991).

## MySQL

InnoDB stores each partition as its own tablespace with its own clustered index and secondary indexes. MySQL has no partitioned-index object at all: `ALTER TABLE orders_p ADD INDEX` builds 24 indexes.

### InnoDB secondary indexes get wider

In InnoDB every secondary index entry stores the primary key, to find the row. A partitioned InnoDB table must have `created_at` in its primary key ([Concept 3](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/concept-3-unique-keys)), so **every secondary index entry gets wider**. From `mysql.innodb_index_stats` after `ANALYZE TABLE`:

| Index | `orders` (PK id) | `orders_p` (PK id, created_at), sum of 24 | Change |
|---|---|---|---|
| PRIMARY | 301.9 MB | 315.1 MB | +4% |
| `created_at` | 89.7 MB | 107.4 MB | +20% |
| `seller_id` | 96.6 MB | 132.4 MB | +37% |
| `ADD INDEX (seller_id)`, online | 2.9 s | 6.3 s | best of 2 |

The [Indexing course](/blogs/databases/indexing/session-6-engine-differences/concept-2-innodb-secondary) covers why InnoDB secondary indexes carry the primary key.

## MongoDB

MongoDB has no table partitioning, so it has no partition indexes either. Inside one collection every index is global. [Concept 5](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/concept-5-mongodb-alternatives) covers what MongoDB offers instead: time-series collections and one collection per period.

## Comparison

| | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Index on a partitioned table | 1 catalog-only parent + 1 per partition | 1 per partition, no parent object | n/a (no partitions) |
| Global index across partitions | No | No | Every index in a collection is global |
| Lookup without the partition key | 24 probes, 73 buffers, ~10× slower | 24 probes, ~4× slower | n/a |
| New partitions | Get every index automatically | Get every index automatically | n/a |

<Pitfall>
Partitioning by `created_at` and then looking orders up by `id` (from an API, a payment callback or a join) turns every lookup into one probe per partition. With 24 partitions that cost 10× in PostgreSQL. With daily partitions over two years it would be about 730 probes. Before choosing the partition key, list the hot queries and check that each one can include it. If the hottest query cannot, either carry the partition key alongside the id (for example, encode the month in the order number, or send `created_at` with the request) or choose a different key.
</Pitfall>

## Real-world scenario: the payment webhook

An order service partitions `orders` by month. The payment gateway calls back with the order id only, and the webhook runs `UPDATE orders SET status = 'paid' WHERE id = $1`. After 36 months of partitions, webhook latency has grown with every month added, while the dashboard (which filters by date) got faster.

| Fix | Effect |
|---|---|
| Put the order month in the id or reference you send to the gateway, and add `AND created_at >= … AND created_at < …` | 1 partition probed |
| Keep a small `order_id → created_at` lookup table (PK on id) | 1 probe there + 1 partition |
| Partition by `id` range instead (ids grow with time) | `id` lookups prune; date queries need an id range to prune ([Concept 3](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/concept-3-unique-keys)) |

## Key takeaways

1. An index on a partitioned table is a set of per-partition (local) indexes. Neither PostgreSQL nor MySQL has a global index.
2. A query without the partition key probes every partition's index: 24 probes, 73 buffers and 10× the time for a one-row lookup in PostgreSQL; 24 handler reads and 4× in MySQL.
3. With the partition key in the query, the cost matches the plain table.
4. Queries that read many rows barely notice the per-partition overhead.
5. In InnoDB the partition key joins the primary key, which widens every secondary index (+20% to +37% here).
