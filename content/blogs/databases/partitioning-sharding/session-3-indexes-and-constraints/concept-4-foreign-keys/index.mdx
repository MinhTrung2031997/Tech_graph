<Tldr>
**From** a partitioned table to a plain one works like on any table. `orders_p.seller_id REFERENCES sellers` validated 5M rows in about 0.25 s, and PostgreSQL created **27 constraint rows** (the parent plus one per partition). **To** a partitioned table is harder, because an FK must reference a unique key and the only unique key is `(id, created_at)` ([Concept 3](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/concept-3-unique-keys)). `REFERENCES orders_p (id)` failed with "there is no unique constraint matching given keys", so `order_items` had to carry `order_created_at`. Inserting 410,397 items then took **6.68 s**, against 1.93 s with an FK to the plain `orders` and 0.17 s without an FK. Retention then gets blocked. `DETACH PARTITION orders_p_2024_01` failed ("removing partition … violates foreign key constraint") and so did `DROP TABLE`, while an unreferenced month detached in 57 ms. **MySQL** refuses foreign keys on partitioned tables in every direction, with `ERROR 1506: Foreign keys are not yet supported in conjunction with partitioning`.
</Tldr>

## The setup

Two new tables in the lab database:

| Table | Rows | Relationship |
|---|---|---|
| `sellers (id PRIMARY KEY, name)` | 5,000 | `orders_p.seller_id` references it |
| `order_items (order_id, order_created_at, sku, qty)` | 410,397 (one per order in Jan–Feb 2024) | References `orders_p` |

| Term | Meaning |
|---|---|
| Referencing table (child) | The table with the FK column: `order_items` |
| Referenced table (parent) | The table with the unique key: `orders_p` |
| RI trigger | The internal trigger that checks an FK on every insert, update or delete |
| Detach / drop a partition | How Session 4 removes an old month in milliseconds |
| **✓ Allowed / ✗ Refused** | Outcome of the statement |

### Deleting a parent row needs an index on the child

Every delete or key update on `orders_p` checks `order_items` for references. Without an index on `order_items (order_id, order_created_at)` that check is a sequential scan of the child table:

| `DELETE FROM orders_p WHERE id = 300000` (referenced, so it fails) | Time to the FK error |
|---|---|
| No index on `order_items (order_id, order_created_at)` | 33.6 ms |
| With that index | 0.76 ms |

PostgreSQL does not create this index for you ([Indexing Session 9](/blogs/databases/indexing/session-9-indexes-for-joins/concept-3-foreign-keys)).

Without foreign keys, integrity moves to the application, or to triggers (not measured here) and periodic orphan checks:

```sql
-- items whose order no longer exists (e.g. after a partition was dropped)
SELECT i.order_id FROM order_items i
LEFT JOIN orders_p o ON o.id = i.order_id AND o.created_at = i.order_created_at
WHERE o.id IS NULL LIMIT 10;
```

## MongoDB

MongoDB has no foreign keys at all, partitioned or not. References between collections are checked by the application, which is the situation MySQL partitioned tables are in.

## Comparison

| | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| FK from a partitioned table | ✓ (one constraint per partition) | ✗ ERROR 1506 | No FKs |
| FK to a partitioned table | ✓ must include the partition key | ✗ ERROR 1506 | No FKs |
| Insert cost of the check (410k child rows) | 6.68 s vs 1.93 s to a plain parent | n/a | n/a |
| Detach / drop a referenced partition | ✗ refused while children exist | n/a | n/a |

<Pitfall>
An FK **to** a partitioned table ties retention together: you can't drop March's orders until March's items are gone. Partition the child table by the same key (`order_created_at`, same monthly bounds) and drop both months together, child first. If the child keeps rows longer than the parent (e.g. invoices kept 10 years, orders 2 years), don't use an FK into the partitioned table. Check integrity in the application or in a periodic orphan query instead.
</Pitfall>

## Real-world scenario: the retention job that stopped working

A team partitions `orders` monthly and schedules "drop the partition older than 24 months" (Session 4). Months later someone adds `refunds.order_id → orders` for a finance feature, with `order_created_at` carried along. The next retention run fails with "removing partition … violates foreign key constraint", nobody notices, and old partitions pile up for three months until disk alerts fire.

| Fix | Effect |
|---|---|
| Partition `refunds` by `order_created_at` with the same bounds; retention drops the `refunds` month first, then `orders` | FK kept, retention works |
| Keep refunds longer: drop the FK, archive the order rows that refunds need | Retention works, integrity by job |
| Alert on the retention job's exit status | The failure is seen the same day |

## Key takeaways

1. PostgreSQL supports FKs from and to partitioned tables; MySQL refuses both (ERROR 1506), and MongoDB has no FKs.
2. An FK to a partitioned table must reference a key that includes the partition key, so child rows carry it (`order_created_at`).
3. The check is more expensive: 6.68 s for 410k child inserts, vs 1.93 s against a plain parent.
4. A referenced partition cannot be detached or dropped; plan child retention with the parent (same partition bounds, drop child first).
5. Index the child's FK columns: deleting a parent row took 33.6 ms without the index and 0.76 ms with it.
