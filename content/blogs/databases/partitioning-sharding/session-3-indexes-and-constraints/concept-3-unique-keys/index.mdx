<Tldr>
A unique index can only check the partition a row lands in, so both engines require every unique key to **contain the partition key**. `ALTER TABLE orders_p ADD PRIMARY KEY (id)` failed in PostgreSQL ("unique constraint on partitioned table must include all partitioning columns"), and in MySQL with ERROR 1503. With the accepted key `(id, created_at)`, a second **order 2500000** dated June 2025 was **accepted** even though order 2500000 already existed in December 2024. Only an exact `(id, created_at)` repeat was rejected. There are three ways to get a global unique id back:
- **A lookup table `order_ids (id PRIMARY KEY)` filled by a trigger.** It rejected the duplicate, but 100k inserts went from 290 to 668 ms, and the table takes 281 MB for 5M ids.
- **Partitioning by `id` itself.** `PRIMARY KEY (id)` is then allowed, but a one-day query scanned all 24 partitions (0.88 ms instead of 0.31 ms) unless it also gave an id range.
- **Ids unique by construction**, such as an identity column or UUIDv7. These avoid collisions but enforce nothing.
</Tldr>

## Why the rule exists

Each partition's index only contains that partition's rows ([Concept 1](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/concept-1-local-indexes)). An insert goes to exactly one partition, chosen by `created_at`, and is checked against that partition's unique index only. If the unique key contains the partition key, two rows with equal keys necessarily have equal `created_at` and land in the **same** partition, so the local check is a global check. If it does not, equal ids can land in different partitions and no index sees both.

| Term | Meaning |
|---|---|
| Partition key | The column(s) in `PARTITION BY RANGE (created_at)` that route each row |
| Local uniqueness | Unique within one partition: what a partition index can enforce |
| Global uniqueness | Unique across the whole table: what `PRIMARY KEY (id)` means on a plain table |
| Lookup table | A separate plain table with `PRIMARY KEY (id)` used only to claim ids |
| **✓ Accepted / ✗ Rejected** | Outcome of the insert |

## PostgreSQL

```sql
ALTER TABLE orders_p ADD PRIMARY KEY (id);
-- ERROR:  unique constraint on partitioned table must include all partitioning columns
-- DETAIL:  PRIMARY KEY constraint on table "orders_p" lacks column "created_at" which is part of the partition key.
CREATE UNIQUE INDEX orders_p_id_uq ON orders_p (id);       -- same error, "UNIQUE constraint"
ALTER TABLE orders_p ADD PRIMARY KEY (id, created_at);     -- OK, 784 ms (24 + 2 partition indexes)
```

### Partition by the unique column instead

If `id` is the partition key, `PRIMARY KEY (id)` is allowed and is globally unique. In this dataset ids grow with time, so 24 equal id ranges look like months, but the planner only knows the id bounds:

```sql
CREATE TABLE orders_pid (LIKE orders INCLUDING DEFAULTS, PRIMARY KEY (id)) PARTITION BY RANGE (id);
-- 24 partitions of 208,334 ids each, plus an index on created_at
```

| One-day count (6,840 rows), best of 6 | Partitions scanned | Time |
|---|---|---|
| `orders` (plain) | – | 0.274 ms |
| `orders_p` (by `created_at`) | 1 | 0.305 ms |
| `orders_pid` (by `id`) | 24 | 0.881 ms |
| `orders_pid` + `AND id BETWEEN 2906978 AND 2913817` | 1 | – |

You trade one problem for its mirror image. Lookups by id now prune, date queries don't, and dropping a month means knowing its id range.

### The three options

| Option | Enforces global uniqueness | Cost measured here | Watch out for |
|---|---|---|---|
| Lookup table + trigger | Yes | Inserts 2.3× slower, +281 MB | Cleanup when partitions are dropped; one more hot table |
| Partition by the unique column | Yes | Date queries scan every partition (0.31 → 0.88 ms) | Retention by date becomes retention by id range |
| Ids unique by construction (identity, sequence, UUIDv7) | No, avoids collisions | None | Manual inserts, imports and merges can still collide |

The same three options apply in MySQL. A trigger on a partitioned InnoDB table can insert into a plain `order_ids` table. That was not timed here.

## MongoDB

A plain collection's `_id` index is global, so `_id` is always unique (an insert of `_id: 2500000` failed with `E11000 duplicate key error`). Global uniqueness gets lost once you split data in MongoDB:

- **Time-series collections** refuse unique indexes altogether.
- **Collection per period** has a separate `_id` index in each collection.

[Concept 5](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/concept-5-mongodb-alternatives) covers both cases.

<Pitfall>
`PRIMARY KEY (id, created_at)` looks like the same key with an extra column. It is a weaker constraint: it no longer says "one row per id". Code that upserts by id (`INSERT … ON CONFLICT (id, created_at)`) also changes meaning. A retried insert with a slightly different `created_at` (the retry's `now()`) creates a second order instead of hitting the conflict. Generate `created_at` once, in the client or the first attempt, and reuse it on retries.
</Pitfall>

## Real-world scenario: the marketplace import

A seller-center import re-sends the last 3 days of orders from Shopee every night, using Shopee's order number as `id`. The orders table was just partitioned by `created_at` with `PRIMARY KEY (id, created_at)`. The import computes `created_at` from a timestamp that Shopee rounds differently on re-sends (seconds vs milliseconds). Every night, about 2% of orders get inserted a second time, and finance's GMV report drifts up.

| Fix | Result |
|---|---|
| Upsert key = the marketplace's order number + the **partition key value exactly as first stored** | No duplicates, if `created_at` is truncated consistently (e.g. to seconds) |
| `order_ids` lookup table with `PRIMARY KEY (marketplace, external_id)` | Duplicates rejected whatever the timestamp |
| Partition by a hash of the external id instead | Global key, but date queries and monthly retention no longer prune |

## Key takeaways

1. A partition index can only check its own partition, so every unique key must include the partition key (PostgreSQL error above; MySQL ERROR 1503).
2. `PRIMARY KEY (id, created_at)` allows the same id in two partitions: order 2500000 was inserted twice.
3. Global uniqueness needs a separate mechanism: a lookup table (2.3× slower inserts), partitioning by the unique column (date queries stop pruning), or ids unique by construction (no enforcement).
4. Upserts and retries keyed on `(id, created_at)` depend on `created_at` being identical on every attempt.
