<Tldr>
On a busy partitioned table, the one-line `CREATE INDEX ON orders_p (amount)` is the wrong tool. PostgreSQL rejects `CONCURRENTLY` on a partitioned table (`cannot create index on partitioned table "orders_p" concurrently`), and the plain build took a **SHARE lock on the parent and all 25 partitions up front**, held until the end: an insert into June 2025 **waited 849 ms** of the 1.38 s build (reads were fine). The online recipe has three steps. First, `CREATE INDEX … ON ONLY orders_p` creates an **invalid** parent index with no children. Then `CREATE INDEX CONCURRENTLY` runs on each partition (76 ms for one month, while an insert into that month took **2.0 ms**). Finally, `ALTER INDEX … ATTACH PARTITION` attaches each one. The parent flipped to **valid** once every partition had an attached index (about 3.9 s for 25 builds and attaches; a partition created meanwhile got its index automatically). In MySQL, `ALTER TABLE orders_p ADD INDEX …, ALGORITHM=INPLACE, LOCK=NONE` works on the partitioned table directly: an insert during the 8.1 s build took 7.2 ms.
</Tldr>

## Why it matters

The [Indexing course](/blogs/databases/indexing/session-8-when-indexes-hurt/concept-3-concurrently-locking) showed `CREATE INDEX CONCURRENTLY` keeping a plain table writable during a build. Partitioned tables are usually the biggest and busiest tables you have, and that shortcut does not exist for them in PostgreSQL.

| Term | Meaning |
|---|---|
| `SHARE` lock | Table lock taken by `CREATE INDEX`: allows reads, blocks INSERT/UPDATE/DELETE |
| `CREATE INDEX … ON ONLY parent` | Creates the parent's index without touching partitions; marked invalid (`indisvalid = false`) |
| `CREATE INDEX CONCURRENTLY` | Builds without blocking writes (`SHARE UPDATE EXCLUSIVE`), slower, cannot run in a transaction block |
| `ALTER INDEX parent_idx ATTACH PARTITION part_idx` | Links a partition's existing index to the parent index |
| **✓ Free / ✗ Blocked** | Can a writer insert into that partition right now? |

## MongoDB

No partitions, so this does not apply. Per the MongoDB manual, `createIndex` on a collection holds an exclusive lock only briefly at the start and end of the build (not measured in this session).

<Pitfall>
Do not run the one-line `CREATE INDEX ON parent` on a production partitioned table in PostgreSQL. It holds a SHARE lock on **every** partition until it commits, including the current month that takes all the inserts. Script ON ONLY → CIC per partition → ATTACH instead, and check `indisvalid` on the parent at the end. A partitioned index stuck at `indisvalid = false` usually means one partition was skipped or its CIC failed and left an INVALID index.
</Pitfall>

## Real-world scenario: the index for a new report

Finance asks for a report by `amount` band on the 3-year, monthly-partitioned `orders` table at 10:00. A developer runs `CREATE INDEX ON orders (amount)` from a migration. The build takes 20 minutes on production data, and checkout inserts into the current month queue behind its SHARE lock for those 20 minutes.

| Step | Lock | Checkout |
|---|---|---|
| `CREATE INDEX orders_amount_idx ON ONLY orders (amount)` | Brief | Unaffected |
| `CREATE INDEX CONCURRENTLY` on each old month (off-peak) | One partition, writes allowed | Unaffected |
| `CREATE INDEX CONCURRENTLY` on the current month | Writes allowed | Unaffected, slower build |
| `ALTER INDEX … ATTACH PARTITION` for each | Brief | Unaffected |
| Check `indisvalid` on the parent | none | Done |

## Key takeaways

1. PostgreSQL has no `CREATE INDEX CONCURRENTLY` for a partitioned table.
2. A plain `CREATE INDEX` on the parent locks the parent and every partition in SHARE mode until it commits: reads continue, writes wait (849 ms here).
3. The online recipe: `ON ONLY` parent index → `CREATE INDEX CONCURRENTLY` per partition → `ALTER INDEX … ATTACH PARTITION`. The parent becomes valid after the last attach.
4. Attached partition indexes are used immediately; partitions created in the meantime get the index automatically.
5. MySQL's `ALTER TABLE … ADD INDEX, ALGORITHM=INPLACE, LOCK=NONE` stays online on a partitioned table (insert 7.2 ms during the build).
