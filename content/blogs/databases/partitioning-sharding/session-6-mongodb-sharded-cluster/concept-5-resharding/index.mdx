<Tldr>
There are two ways to change a shard key. **`refineCollectionShardKey`** appends fields to the existing key: `{ seller_id: 1 }` → `{ seller_id: 1, created_at: 1 }` needed an index starting with the new key (1,211 ms to build), then took **110 ms** and moved nothing; the 15 chunk bounds just gained `created_at: MinKey`. It refuses anything that does not *extend* the key (reordering, removing a field). **`reshardCollection`** picks any new key and rewrites the collection: `orders_r` (1M orders, all on sh1 under `{ seller_id: 1 }`) to `{ _id: 'hashed' }` took **332.2 s**: 301.5 s cloning, 30.0 s applying the oplog, **0.53 s blocking writes**, 0.07 s committing. It ended at **500,405 / 499,595** documents per shard. A workload of reads and updates by `_id` ran throughout: update median 2.34 ms, worst **543 ms**, at the switch. Resharding needs room for a second full copy on the recipients while it runs.
</Tldr>

## Terms

| Term | Meaning |
|---|---|
| Refine | Add suffix fields to the current shard key; metadata only, ranges keep their owners |
| Reshard | Build a new copy of the collection under a new key on the recipient shards, then switch |
| Coordinator | Runs on the config server primary and moves the operation through its states |
| Cloning / applying | Recipients copy the documents / then apply oplog entries written since the clone started |
| Blocking writes | Short final state: writes wait while the last oplog entries are applied, then the new collection replaces the old |
| **✓ / ✗** | Allowed / refused or held |

## Refining the key

```js
db.adminCommand({ refineCollectionShardKey: 'pt6.orders_s', key: { seller_id: 1, created_at: 1 } })
// MongoServerError: … Please create an index that starts with the proposed shard key before refining the collection's shard key.
db.orders_s.createIndex({ seller_id: 1, created_at: 1 })                    // 1,211 ms
db.adminCommand({ refineCollectionShardKey: 'pt6.orders_s', key: { seller_id: 1, created_at: 1 } })   // ok, 110 ms
// chunk bounds now: { seller_id: MinKey, created_at: MinKey } → { seller_id: 178, created_at: MinKey } …  (15 chunks, unchanged owners)
db.adminCommand({ refineCollectionShardKey: 'pt6.orders_s', key: { created_at: 1, seller_id: 1 } })
// refineCollectionShardKey shard key { created_at: 1, seller_id: 1 } does not extend the current shard key { seller_id: 1, created_at: 1 }
db.adminCommand({ refineCollectionShardKey: 'pt6.orders_s', key: { seller_id: 1 } })
// refineCollectionShardKey shard key { seller_id: 1 } does not extend the current shard key { seller_id: 1, created_at: 1 }
```

Refining fixes one specific problem: a key with too few distinct values. All orders of one seller share `seller_id`, so no range can ever be cut inside one seller, and a seller with millions of orders becomes one unsplittable (jumbo) chunk; with `created_at` appended, a range can be cut between two dates of the same seller. It cannot fix a key that targets the wrong queries.

## Measured

| | `refineCollectionShardKey` | `reshardCollection` |
|---|---|---|
| New key | must start with the current key | any key |
| Prerequisite | index starting with the new key (1,211 ms on 1M) | none: it created the `_id: 'hashed'` index and rebuilt the existing indexes on the new copy |
| Duration on 1M orders | 110 ms | 332.2 s |
| Data moved | none | the whole collection, into a new collection |
| Extra disk while running | none | a full copy on the recipients |
| Write pause | none observed | 0.53 s blocking writes; worst update 543 ms |
| Spread afterwards | unchanged | 50.04% / 49.95% |

`moveCollection` (Concept 4) and 8.0's `unshardCollection` use the same machinery: one collection rewritten under a new placement, with the same 300 s minimum. `unshardCollection` was not run in the lab.

<Pitfall>
Resharding is online, not free. For its duration the recipients hold a second copy of the collection and its indexes, the donors keep oplog that the recipients still need, and every write is applied twice. On a large collection that is hours of extra disk, I/O and oplog. Check free disk on every recipient for the full collection, make sure the oplog window covers the whole operation, and run it when write load is lowest. And choose the key carefully the first time (Session 5): `refineCollectionShardKey` can only add fields at the end.
</Pitfall>

## Real-world scenario: sharded by marketplace

An order service sharded `orders` on `{ marketplace: 1 }` because every query filtered by it. With three values (Shopee, TikTok, Lazada), the collection can have at most three ranges: the Shopee range grows into a jumbo chunk the balancer cannot split, and its shard fills up.

| Option | Effect |
|---|---|
| Refine to `{ marketplace: 1, seller_id: 1 }` | 110 ms-class metadata change after an index build; the Shopee range can now be split by seller and balanced |
| Reshard to `{ seller_id: 1, created_at: 1 }` | Hours-class rewrite on real data; queries by marketplace become broadcasts |
| Keep the key, add shards | Does nothing: the Shopee range still cannot be split |

Refining keeps every query targeted that was targeted before and adds split points; it is the first thing to try when the key's first field is right but too coarse.

## Key takeaways

1. `refineCollectionShardKey` appends fields to the key: metadata only (110 ms), needs a supporting index, never reorders or removes fields.
2. `reshardCollection` rewrites the collection under any new key: 332.2 s for 1M orders, never under the 300 s minimum.
3. Reads and writes continue during resharding; writes are held only at the end (0.53 s here).
4. Resharding needs a second full copy's worth of disk on the recipients and enough oplog to cover the operation.
5. `moveCollection` and `unshardCollection` (8.0) use the same machinery.
