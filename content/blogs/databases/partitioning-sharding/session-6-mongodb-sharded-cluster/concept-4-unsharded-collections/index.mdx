<Tldr>
Every database in a sharded cluster has a **primary shard** (`config.databases`), and every collection you do not shard lives entirely there. `pt6`'s primary is sh1, so the unsharded `orders` was answered only by sh1 (`SINGLE_SHARD`). MongoDB 8.0 can move one unsharded collection with **`moveCollection`**: it registers the collection as *tracked* (`unsplittable: true`, key `_id`) and copies it with the resharding machinery. For 1M orders it took **332.7 s**: 301 s cloning (resharding never finishes in less than `reshardingMinimumOperationDurationMillis`, 300,000 ms by default), 30 s applying, **0.96 s blocking writes**, 0.15 s committing. The worst write during it took 1,074 ms. **`movePrimary`** moves the primary role and every *untracked* unsharded collection with it: 5.3 s and 5.0 s for the 1M orders, but writes to them **failed** with error code 319 (`movePrimary is in progress for namespace pt6.orders`): 8,626 failed updates in 4.9 s. Reads kept working.
</Tldr>

## Terms

| Term | Meaning |
|---|---|
| Primary shard | Per database: the shard that stores its unsharded collections; chosen when the database is created |
| Untracked collection | Unsharded collection with no entry in `config.collections`; it lives on the primary shard |
| Tracked unsharded | 8.0: unsharded collection registered in `config.collections` with `unsplittable: true`; it can live on any shard |
| `moveCollection` | 8.0: move one unsharded collection to a named shard (online, resharding-based) |
| `movePrimary` | Change a database's primary shard; moves its untracked unsharded collections |
| **✓ / ✗** | Request served / request rejected or held |

## Where unsharded data lives

```js
db.getSiblingDB('config').databases.findOne({ _id: 'pt6' })      // primary: 'sh1'
db.orders.find({ _id: 5 }).explain().queryPlanner.winningPlan      // SINGLE_SHARD, shards: [ 'sh1' ]
db.getSiblingDB('config').collections.countDocuments({ _id: 'pt6.orders_u' })   // 0: untracked
```

On a cluster where many databases share the same primary shard, all their unsharded collections pile up on one shard. In this lab, sh1 was the primary of `pt6`, sh2 of three other databases: placement is decided when a database is created, not by load.

## The two commands side by side

| 1M orders, 113 MiB | `moveCollection` (one collection) | `movePrimary` (whole database's untracked collections) |
|---|---|---|
| Total time | 332.7 s | 5.0–5.3 s |
| Writes during the copy | allowed (median 2.29 ms) | **rejected**, code 319, for 4.9 s |
| Write pause at the end | 0.96 s (blocking-writes), worst write 1,074 ms | (the whole copy) |
| Reads | allowed | allowed |
| What moves | the named collection | every untracked unsharded collection of the database |
| Works on a sharded collection | no: `MoveCollection can only be called on an unsharded collection.` | sharded and tracked collections are not moved |

<Pitfall>
`movePrimary` looks like the quick option, and on a small database it is. But it rejects writes instead of queueing them, for as long as the copy takes, and the copy grows with every unsharded collection in the database. Run it only for databases whose unsharded collections are small or can stop taking writes, with an application that retries on error 319. For one large collection, `moveCollection` is online but takes at least five minutes and a full copy: plan disk on the recipient for the whole collection.
</Pitfall>

## Real-world scenario: one shard full of side collections

A seller platform shards `orders` and `order_items`, but its 40 other collections (`sellers`, `promotions`, `sessions`, `audit_log`, …) were never sharded. All databases were created when the cluster had one shard, so every one of them has sh1 as primary. Two years later sh1 holds 70% of the data and its disk alerts fire, while the sharded collections are perfectly balanced.

| Fix | Effect |
|---|---|
| `moveCollection` the large unsharded collections (e.g. `audit_log`) to other shards | Online; spreads the side data one collection at a time |
| `movePrimary` for small databases, in a write-pause window, with retries | Moves all their untracked collections in seconds |
| Shard the collections that will keep growing | The balancer spreads them from then on |
| Check `$collStats` per shard, not only `sh.status()` for sharded collections | Unsharded data is where imbalance hides |

## Key takeaways

1. Unsharded collections live on their database's primary shard; databases do not spread themselves.
2. `moveCollection` (8.0) moves one unsharded collection online, by registering it as tracked and resharding it: 332.7 s for 1M orders, with a 0.96 s write block at the end.
3. Resharding-based operations never finish before `reshardingMinimumOperationDurationMillis` (300 s by default).
4. `movePrimary` moves every untracked unsharded collection in seconds, but rejects writes with code 319 meanwhile.
5. Check per-shard data size including unsharded collections when judging balance.
