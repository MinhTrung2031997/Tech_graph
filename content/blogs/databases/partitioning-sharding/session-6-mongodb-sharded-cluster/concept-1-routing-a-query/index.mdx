<Tldr>
The application talks only to **mongos**. mongos keeps a cached copy of the **routing table** (which shard owns which range of the shard key, stored in `config.chunks` on the config servers) and uses the query's filter on the shard key to pick shards. With `pt6.orders_s` sharded on `{ seller_id: 1 }`: a query for one seller went to **one shard** (`SINGLE_SHARD`); a lookup by `_id` went to **both** (`SHARD_MERGE`). Counted with the profiler, 500 lookups by `_id` ran **500 queries on each shard**; the same 500 lookups with `seller_id` added ran **272 + 228**. On two shards on one laptop the latency difference was small (median 0.29 ms vs 0.23–0.28 ms), but every broadcast query costs work on every shard, and that work grows with the number of shards. A sort with a limit is merged on mongos (`SHARD_MERGE_SORT`), and an aggregation is split into a `shardsPart` and a `mergerPart`.
</Tldr>

## The cluster

| Term | Meaning |
|---|---|
| mongos | The router. Stateless; applications connect to it as if it were one server |
| Config servers | A replica set (`cfg`) holding the cluster metadata: databases, sharded collections, chunks |
| Shard | A replica set holding part of the data (`sh1`, `sh2`, one member each in the lab) |
| Shard key | The field(s) whose value decides which shard owns a document (`seller_id` here) |
| Chunk / range | A contiguous range of shard-key values owned by one shard, e.g. sellers `[178, 355)` |
| Routing table | mongos's cached copy of the chunk list, refreshed when a shard reports it is stale |
| **✓ / ✗** | Shard receives the query / shard is skipped |

The lab collection `pt6.orders_s` is a copy of the 1,000,000 orders, sharded on `{ seller_id: 1 }` and balanced into 14 chunks (Concept 2). At the time of these measurements `sh2` owned sellers below 2303 and `sh1` owned 2303 and above.

## What explain shows

| Query on `orders_s` | Top stage | Shards | Returned | Work per shard |
|---|---|---|---|---|
| `seller_id: 4321` | SINGLE_SHARD | sh1 | 212 | 212 keys, 212 docs |
| `seller_id: { $in: [100, 4321] }` | SHARD_MERGE | sh1, sh2 | 403 | sh2 192 keys, sh1 405 keys (orphans of seller 100 filtered out) |
| `seller_id` from 1000 to 1099 | SINGLE_SHARD | sh2 | 20,075 | 20,075 keys |
| `_id: 777777` | SHARD_MERGE | sh1, sh2 | 1 | 1 key each |
| June 2025 by `created_at` | SHARD_MERGE | sh1, sh2 | 41,040 | sh2 18,831 keys; sh1 41,040 keys for 22,209 rows |
| Latest 10 by `created_at` | SHARD_MERGE_SORT | sh1, sh2 | 10 (20 received) | 18 and 10 keys |

A range on the shard key is targeted too: sellers 1000–1099 lived in sh2's ranges, so only sh2 ran it. `$in` touches every shard that owns one of the values.

## Aggregations are split

```js
db.orders_s.explain('executionStats').aggregate([
  { $match: { created_at: { $gte: ISODate('2025-06-01'), $lt: ISODate('2025-07-01') } } },
  { $group: { _id: '$marketplace', gmv: { $sum: '$amount' }, n: { $sum: 1 } } }
])
// mergeType: 'mongos'
// shardsPart: [ $match, $group { gmv: $sum amount, n: $sum 1 } ]        runs on each shard
// mergerPart: [ $mergeCursors, $group { gmv: $sum $$ROOT.gmv, n: $sum $$ROOT.n, $doingMerge: true } ]
```

Each shard computes a partial GMV per marketplace; mongos adds the partials. Only 3 documents per shard cross the network, not 41,040.

## Latency on the lab cluster

| 500 point lookups through mongos (median / p95 ms, 3 rounds) | Round 1 | Round 2 | Round 3 |
|---|---|---|---|
| Unsharded `orders`, by `_id` | 0.350 / 2.317 | 0.213 / 0.863 | 0.194 / 0.717 |
| `orders_s`, by `_id` only (both shards) | 0.381 / 1.508 | 0.288 / 1.208 | 0.294 / 1.210 |
| `orders_s`, by `seller_id` + `_id` (one shard) | 0.275 / 1.165 | 0.268 / 1.234 | 0.227 / 0.976 |

Two shards on one machine hide most of the cost: the two shard queries run in parallel and the network is a local bridge. The profiler count is the number to remember. With 20 shards, a query without the shard key is 20 queries, the slowest shard sets the latency, and the cluster's total query capacity no longer grows when you add shards.

<Pitfall>
"Sharding scales reads" holds only for queries that carry the shard key. A lookup by order id on a collection sharded by seller is a broadcast: it costs one query per shard, forever. Either include the shard key in the application's queries (store `seller_id` next to every order reference), choose a key that the hot queries carry (Session 5), or keep a small lookup collection keyed by order id that returns the seller.
</Pitfall>

## Real-world scenario: order detail page

A marketplace back office shards orders by `seller_id` because every seller dashboard filters by seller. The customer-service tool opens an order by its number only. With 2 shards nobody notices; after growing to 12 shards, each order-detail view runs 12 queries, the busiest shard's queue sets the response time, and adding shards makes the tool slower, not faster.

| Fix | Effect |
|---|---|
| Put `seller_id` in the order reference the tool already has (URL, ticket) | The lookup becomes SINGLE_SHARD |
| Lookup collection `order_seller` sharded on `_id` | Two targeted queries instead of N |
| Leave it, but measure | Fine at low volume; check `explain` and the per-shard profiler before scaling out |

## Key takeaways

1. Applications connect to mongos; mongos routes with a cached copy of the chunk ranges stored on the config servers.
2. A filter with the shard key (equality, `$in` or a range) goes only to the shards that own those values: `SINGLE_SHARD`.
3. A filter without the shard key goes to every shard: `SHARD_MERGE`. 500 lookups by `_id` ran 1,000 shard queries.
4. Sorts with a limit are merged on mongos (`SHARD_MERGE_SORT`); aggregations are split into a per-shard part and a merger part.
5. Indexes are per shard: a missing index makes every shard scan.
