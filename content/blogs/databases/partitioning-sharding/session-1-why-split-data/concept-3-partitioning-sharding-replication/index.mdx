<Tldr>
**Partitioning** splits one table into smaller tables **inside one database server**; queries still use one table name, and the planner skips partitions that cannot match. It fixes whole-table and retention work (Concepts 1 and 2), not the limits of the server: the lab's monthly `orders_m` is 24 partitions of 24–26 MB, **624 MB** in total against **596 MB** for the plain table, all on the same disk and CPU. **Sharding** splits rows **across servers** by a shard key, so each server holds and writes only its part: it is the only one of the three that adds write capacity and disk space, and it makes every query that does not name the shard key go to every shard. **Replication** copies **all** the data to more servers: more read capacity and failover, but every copy applies every write and stores everything. PostgreSQL and MySQL have partitioning and replication built in and shard through add-ons (Citus, Vitess) or the application; MongoDB has no partitioning but built-in sharding.
</Tldr>

## Three different splits

| Term | Meaning |
|---|---|
| Partition | One piece of a partitioned table, on the same server (e.g. `orders_m_2025_03`) |
| Partition key | The column(s) that decide which partition a row goes to (`created_at` here) |
| Pruning | The planner skipping partitions whose range cannot match the WHERE clause |
| Shard | One server (normally a replica set) holding part of the rows |
| Shard key | The field(s) that decide which shard a row lives on (e.g. `seller_id`) |
| Router | Whatever sends a query to the right shard(s): `mongos`, the Citus coordinator, Vitess `vtgate`, or the application |
| Replica | A full copy of the data on another server, kept up to date from the primary's log |
| **✓ Touched / ✗ Skipped** | Whether a piece receives work for a given statement |

## What each one fixes

| Problem | Partitioning | Sharding | Replication |
|---|---|---|---|
| Deleting old data (Concept 2) | ✓ drop a partition | ✗ each shard still deletes rows (unless also partitioned) | ✗ every copy replays the deletes |
| Whole-table maintenance (Concept 1) | ✓ one partition at a time | ✓ each shard does its share, in parallel | ✗ every copy holds everything |
| Queries on one time range | ✓ pruning | only if the shard key matches | ✗ |
| Read capacity | ✗ same server | ✓ | ✓ reads from replicas |
| Write capacity | ✗ same server | ✓ writes spread across shards | ✗ every copy applies every write |
| Data larger than one server | ✗ | ✓ | ✗ every copy holds it all |
| Server failure | ✗ | ✗ by itself (each shard needs replicas) | ✓ failover |
| New costs | rules for keys and indexes ([Session 3](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/lab)), more objects to plan | cross-shard queries, joins and transactions, a router, rebalancing | more servers, replication lag |

Real systems combine them: a production MongoDB sharded cluster is several shards, each one a replica set; a large PostgreSQL deployment is often a partitioned table on a primary with replicas.

## What each engine has built in

| | PostgreSQL 17 | MySQL 8.4 | MongoDB 8.0 |
|---|---|---|---|
| Partitioning | ✓ declarative RANGE / LIST / HASH | ✓ RANGE / LIST / HASH / KEY (no foreign keys) | ✗ none; time-series collections, TTL, one collection per period ([Session 3](/blogs/databases/partitioning-sharding/session-3-indexes-and-constraints/lab)) |
| Sharding | ✗ not in core: Citus extension, `postgres_fdw`, the application | ✗ not in core: Vitess, the application | ✓ sharded clusters (`mongos`, config servers, chunks, balancer) |
| Replication | ✓ streaming (physical) and logical | ✓ binary log replication, Group Replication | ✓ replica sets |

The lab built the same monthly partitioned table in both SQL engines (Concept 4): PostgreSQL 624 MB vs 596 MB plain, MySQL 423 MB vs 392 MB plain. Partitioning **added** a little size in both (a wider primary key that must include `created_at`, and per-partition overhead): it organizes data, it does not shrink it.

<Pitfall>
"We'll partition it so it scales" mixes up two things. Partitioning keeps everything on one server: if the problem is CPU, memory, disk or write throughput of that server, partitioning does nothing for it (and Concept 4 shows it can make some queries slower). Only sharding adds servers to the write path. Replication adds servers for reads and availability, never for writes.
</Pitfall>

## Real-world scenario: picking the right split

| Symptom on a marketplace orders database | First tool |
|---|---|
| Nightly retention delete takes hours, tables never shrink | Partition by month |
| Dashboards slow down the checkout writes | Replica for the dashboards |
| Primary at 90% CPU on writes after a 10× growth in sellers | Shard (by seller) |
| Index builds and VACUUM no longer fit maintenance windows | Partition (smaller units of work) |
| One region's primary fails, checkout is down | Replication with automatic failover |
| A single 8 TB table, disk nearly full, 2 years of data needed online | Partition first (and compress or archive old partitions), shard if it still does not fit |

## Key takeaways

1. Partitioning: many tables, one server. Fixes retention and per-table maintenance; adds no capacity.
2. Sharding: rows spread across servers by a shard key. Adds write capacity and storage; queries without the key go everywhere.
3. Replication: full copies. Adds read capacity and availability; every copy does every write.
4. PostgreSQL and MySQL: partitioning and replication built in, sharding by add-on. MongoDB: sharding and replication built in, no partitioning.
5. Production designs usually combine two or three of them.
