<Tldr>
Every orders table eventually gets a retention rule: "keep two years". With one big table, the only tool is `DELETE … WHERE created_at < …`, which works **row by row**: deleting one month (**212,039** rows) cost PostgreSQL **75 ms and 27 MB of WAL**, then a **0.66 s VACUUM and 10 MB more WAL**, and the table file stayed **365 MB**. MySQL took **0.6 s** and wrote **8.3 MB of binary log** that every replica must replay. MongoDB's `deleteMany` took **1.04 s**. The same month stored as its own table was gone in **7 ms with 4,288 bytes of WAL** (PostgreSQL), **0.04 s** (MySQL) and **4 ms** (MongoDB): dropping a table is a metadata change plus a file delete, whatever it contains. On a real table, multiply the row-by-row numbers by the size of your month. Partitioning (Session 2) turns the first kind of delete into the second.
</Tldr>

## The setup

January 2024 is orders 1 to 212,039 of `orders`. Each engine:

1. copied January into a backup table,
2. ran `DELETE` (or `deleteMany`) for `created_at < '2024-02-01'` on the 5M-row table and measured it,
3. created a separate month-sized table with the same rows and indexes and measured `DROP TABLE` (or `drop()`) on it,
4. put January back.

| Term | Meaning |
|---|---|
| Row-by-row delete | Every matching row is found, marked deleted, logged, and later cleaned up, one at a time |
| Drop | The table's files are removed and its catalog entry deleted: cost does not depend on the row count |
| WAL / redo / binary log | Logs every change for crash recovery (WAL, redo) and replication (WAL, binary log). Bigger log = more disk writes and more for replicas to replay |
| Dead tuple | PostgreSQL: a deleted row version still in its page until VACUUM removes it |
| Purge | InnoDB: background removal of delete-marked records once no transaction needs them |
| **✓ Cheap / ✗ Proportional to rows** | Whether a step's cost depends on how many rows are deleted |

## PostgreSQL

| | DELETE one month | DROP a month-sized table |
|---|---|---|
| Rows | 212,039 | 212,039 |
| Statement time | 74.8 ms | 7.1 ms |
| WAL written | 27 MB | 4,288 bytes |
| Follow-up work | VACUUM: 0.66 s, 10 MB WAL, 1,982 heap pages + 581 pages in each index | none |
| Table file afterwards | 365 MB (unchanged) | file removed |

## MySQL InnoDB

| | DELETE one month | DROP a month-sized table |
|---|---|---|
| Statement time (3 runs) | 0.60 / 0.67 / 0.59 s | 0.04 s |
| Binary log for the transaction | 8.3 MB (2,132 `Delete_rows` events) | one DDL statement event |
| Undo | every deleted row is kept in undo: `ROLLBACK` of the same delete took 0.47 s | none |
| Follow-up work | purge removes the delete-marked records in the background | none |

The redo log counter (`Innodb_redo_log_current_lsn`) is server-wide; other workloads were writing at the same time, so the redo volume of the delete is not reported here.

## MongoDB

| | `deleteMany` one month | `drop()` a month-sized collection |
|---|---|---|
| Time (2 runs) | 1,106 / 1,037 ms | 4 ms |
| Work | removes 212,039 documents and their `_id` and `created_at` index entries one by one | removes the collection's files and catalog entry |
| On-disk size afterwards | `storageSize` 146 MB (unchanged) | files removed |

In a replica set, each deleted document is also one oplog entry, replayed by every secondary (this lab's `idx-mongo` is standalone, so that part was not measured).

## Comparison

| One month (212,039 rows) | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Row-by-row delete | 75 ms + VACUUM 0.66 s | 0.6 s + purge | 1.04 s |
| Log volume of the delete | 27 MB WAL (+10 MB for VACUUM) | 8.3 MB binary log | one oplog entry per document (replica sets) |
| Drop a table holding the month | 7.1 ms, 4,288 bytes WAL | 0.04 s | 4 ms |
| File size after the delete | unchanged (365 MB) | unchanged | unchanged (146 MB) |

<Pitfall>
The lab numbers look small because one month here is 212k rows. Retention deletes grow with **your** month: at 50M rows a month, the same `DELETE` writes gigabytes of WAL or binary log, holds a transaction open for many minutes (blocking VACUUM and purge for everyone, see [Transactions Session 4](/blogs/databases/transactions/session-4-mvcc-internals/concept-4-long-transactions)), makes replicas lag while they replay it, and leaves the files as big as before. Teams then batch it into small deletes that run all night. Dropping a table of that month stays a few milliseconds.
</Pitfall>

## Real-world scenario: the nightly purge that never finishes

A platform keeps 18 months of order events. The purge job runs `DELETE FROM order_events WHERE created_at < NOW() - INTERVAL 18 MONTH LIMIT 10000` (MySQL) in a loop every night.

| Symptom | Cause |
|---|---|
| Purge runs 5 hours and overlaps the morning peak | One month is 60M rows; each batch scans the index, deletes, logs, commits |
| Replica lag alerts every night | The replicas replay every deleted row |
| Disk usage never goes down | Deleted space is reused, never returned |
| Autovacuum constantly busy on this table | Every deleted row is a dead tuple to clean |

With one table per month, the job becomes "drop the table from 19 months ago": milliseconds, a few kilobytes of log, and the disk space comes back. That is the core promise of partitioning, built in [Session 2](/blogs/databases/partitioning-sharding/session-2-partitioning-postgresql/lab).

## Key takeaways

1. A row-by-row delete costs per row: index lookups, a log record per row, undo or dead tuples, and later cleanup.
2. Dropping a table costs per table: a catalog change and a file removal (7 ms, 0.04 s, 4 ms here).
3. Deleting rows does not shrink files in any of the three engines; dropping a table does.
4. Retention deletes also hurt replicas (8.3 MB of binary log for one small month) and other transactions.
5. If data leaves by age, store it so that an age range is a table: that is time-based partitioning.
