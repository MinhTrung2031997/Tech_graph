<Tldr>
Partitioning is not a query accelerator. On the one-month sum (212,039 rows of 5M) the partitioned table scanned only its March partition, and a plain table with the **right index** was just as fast: PostgreSQL **7.4 ms** (index-only scan on `(created_at) INCLUDE (amount)`, 820 buffers) vs **8.2 ms** (partition scan, 1,982 buffers); MySQL **25 ms** vs **25 ms**; MongoDB has no partitions and did it in **43 ms** with a covering index. Queries that do not filter on the partition key pay instead: a lookup by `id` probed **all 24 partitions** (PostgreSQL 76 buffers and 0.22 ms vs 7 buffers and 0.04 ms, plus 2–4 ms of planning in a new session; MySQL 24 index reads vs 1), and a seller report with no index went from 51–60 ms to 66–116 ms. Split data when you need what Concepts 1–3 showed (cheap retention, smaller maintenance units, more servers), not to speed up queries an index can serve.
</Tldr>

## The setup

`orders_m` is a copy of `orders` partitioned by month on `created_at` (24 partitions); the lab shows how it is built. Because a primary key on a partitioned table must include the partition key, its primary key is `(id, created_at)`. Each query ran 3–5 times in a new session (best or range shown).

| Term | Meaning |
|---|---|
| Partition key | `created_at`: the column the partitions are split on |
| Pruning | Skipping partitions whose range cannot match: only possible when the WHERE clause constrains the partition key |
| Covering index | An index holding every column the query needs, so the table is not read (index-only scan / covered query) |
| Append | PostgreSQL plan node that runs one child scan per partition and concatenates the results |
| **✓ Scanned / ✗ Pruned** | Whether a partition (or index) is read for the query |

## PostgreSQL

| Query | `orders` (plain) | `orders_m` (24 partitions) |
|---|---|---|
| Sum of one month, index on `created_at` | 9.7–13.3 ms, 3,009 buffers | 8.2–9.2 ms, 1,982 buffers (one partition) |
| Sum of one month, covering index `(created_at) INCLUDE (amount)` | **7.4–7.7 ms, 820 buffers**, 0 heap fetches | (not needed) |
| Lookup by `id` | 0.04–0.05 ms, 7 buffers, planning 0.16–0.21 ms | 0.22–0.24 ms, 76 buffers, planning 2.0–3.7 ms |
| Lookup by `id` and the month | | 0.05 ms, 7 buffers (one partition) |
| Sum for one seller (no index) | 51–60 ms | 66–116 ms |

The planning cost of `orders_m` falls to 0.08–0.19 ms when the same session repeats the query (the partition metadata is then cached), so it matters most for short-lived connections.

## MySQL InnoDB

| Query | `orders` (plain) | `orders_m` (24 partitions) |
|---|---|---|
| Sum of one month, index on `created_at` | 107–154 ms (secondary index range scan + a clustered-index lookup per row) | 25–31 ms (table scan of `p2025_03` only) |
| Sum of one month, covering index `(created_at, amount)` | **25 ms** | (not needed) |
| Lookup by `id` | `const`, 1 index read (`Handler_read_key` +1) | EXPLAIN `partitions`: all 24, `Handler_read_key` +24, 0.03 ms |
| Sum for one seller (no index) | 0.35–0.42 s | 0.41 s |

InnoDB is where partitioning looked best at first: a secondary-index range scan has to look up each of the 212,039 rows in the clustered index, so the partition scan was 4× faster. A covering index removes those lookups and closes the gap completely.

## MongoDB

MongoDB has no partitioned collections, so its answer to "one month is slow" is an index:

| Query | Time | Plan |
|---|---|---|
| Sum of one month, no usable index (`hint: { $natural: 1 }`) | 711–1,255 ms | COLLSCAN, 5,000,000 documents examined |
| Sum of one month, index `{ created_at: 1 }` | 65–82 ms | IXSCAN + FETCH, 212,039 keys and documents |
| Sum of one month, index `{ created_at: 1, amount: 1 }` | 43 ms | IXSCAN + PROJECTION_COVERED, 0 documents examined |
| Lookup by `_id` | 0 ms | 1 key |

## Comparison

| | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Month sum: best plain-table index | 7.4 ms | 25 ms | 43 ms |
| Month sum: one partition | 8.2 ms | 25 ms | (no partitions) |
| Lookup by id without the partition key | 24 index probes, 76 vs 7 buffers | 24 vs 1 index reads | n/a |
| Full report without the partition key | slower (66–116 vs 51–60 ms) | same (0.41 vs 0.35–0.42 s) | n/a |

## A checklist before splitting

| Question | If yes |
|---|---|
| Are the slow queries fixed by an index (composite, covering)? | Add the index; do not split |
| Do most queries filter on one column with a natural range (date, tenant)? | That column is a partition key candidate |
| Is old data removed by age, in large amounts? | Partition by time (Concept 2) |
| Do whole-table jobs (index builds, vacuum, backups) no longer fit their window? | Partition, so each job handles one partition |
| Does one server lack CPU, disk or write throughput even with good indexes? | Sharding (Sessions 5–8), not partitioning |
| Do many queries look rows up by a key that is **not** the partition key? | Expect them to probe every partition, or add the key to them |

<Pitfall>
The most common partitioning mistake is choosing a partition key that the queries do not use. Partitioning `orders` by month and then looking orders up by id, by seller or by customer turns each of those queries into one probe or one scan **per partition**: 24 here, hundreds with daily partitions (Session 2 measures planning time with ~730 partitions). Check the query mix first; partition on the column that most queries, and the retention job, filter on.
</Pitfall>

## Real-world scenario: partitioned for speed, got slower

A team partitioned a 300M-row `orders` table by month "to make it faster". After the migration, the order detail page (lookup by `order_id`) got slower and CPU went up.

| Finding | Fix |
|---|---|
| Order detail lookups by `order_id` probed 36 partitions | Encode the month in the order id, or keep a small `order_id → created_at` lookup table and add the date to the query |
| Month dashboards were not faster | They were already served by a composite index; partitioning added nothing |
| The real win was retention | Dropping a month went from a 6-hour delete to milliseconds |

## Key takeaways

1. With the right index, a plain table answered the month query as fast as a pruned partition in PostgreSQL and MySQL.
2. Queries that do not constrain the partition key touch every partition: 24 index probes for one lookup by id.
3. Partitioning adds planning work (2–4 ms in a new session for 24 partitions here).
4. In InnoDB, a covering index removed the primary-key lookups that made the plain table 4× slower than the partition.
5. Split data for retention, maintenance units or capacity, after the indexes are right.
