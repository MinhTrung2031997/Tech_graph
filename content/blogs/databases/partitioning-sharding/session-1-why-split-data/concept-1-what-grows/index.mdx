<Tldr>
Two kinds of work behave very differently as a table grows. **Lookups through an index** barely notice: a B-tree adds one level for roughly every 100× more rows, so finding order 42 cost **7 buffers and 0.041 ms** at 5M rows against **6 buffers and 0.035 ms** at 50k (PostgreSQL). **Work that touches every row** grows with the table: at 100× the rows, `CREATE INDEX` took **69×** longer in PostgreSQL (9.9 → 683 ms), **29×** in MySQL (0.11 → 3.14 s) and **107×** in MongoDB (40 ms → 4.3 s); a full-table `VACUUM` took 34× longer. Once the table outgrows memory (PostgreSQL `shared_buffers` and the InnoDB buffer pool are 128 MB, the table 579 MB / 392 MB), full scans get slower than linear: MySQL's full `SUM` took 20× longer for 10× the rows. Partitioning attacks the second kind of work, not the first.
</Tldr>

## The setup

The course table `orders` has 5,000,000 rows over two years (see the [lab](/blogs/databases/partitioning-sharding/session-1-why-split-data/lab)). For this concept two smaller copies were made from its first rows: `o500k` (500,000) and `o50k` (50,000), with the same primary key and `created_at` index. Every timing is the best of 3 runs on a laptop while other workloads ran; 5M rows is not "big data", so read the **ratios** between the columns, not the absolute numbers.

| Term | Meaning |
|---|---|
| B-tree level | Height of an index tree. PostgreSQL's `bt_metap().level` is the root's level: level 2 means root → internal → leaf, three pages to reach a leaf |
| Lookup | Finding one row through an index: cost depends on tree height, not on row count |
| Whole-table work | Anything that reads every row: full scans, `CREATE INDEX`, `VACUUM` with page skipping disabled, `validate`, backups, copies |
| Buffer cache | `shared_buffers` (PostgreSQL, 128 MB here), the InnoDB buffer pool (128 MB), the WiredTiger cache (5,495 MB in this container) |
| **✓ In cache / ✗ Not in cache** | Whether the pages a step needs are already in the engine's memory |

## PostgreSQL

| `orders` at | 50k | 500k | 5M | 5M ÷ 50k |
|---|---|---|---|---|
| Table + 2 indexes | 6 MB | 59 MB | 579 MB | 97× |
| Primary key root level (`bt_metap`) | 1 | 2 | 2 | +1 level |
| Lookup by id: buffers / execution | 6 / 0.035 ms | 7 / 0.037 ms | 7 / 0.041 ms | 1.2× |
| `SELECT sum(amount)` (full scan, 2 parallel workers) | 2.3 ms | 10.6 ms | 69.8 ms | 30× |
| `VACUUM (DISABLE_PAGE_SKIPPING)` | 2.7 ms | 13.4 ms | 90.6 ms | 34× |
| `CREATE INDEX … (seller_id)` | 9.9 ms | 57.5 ms | 683 ms | 69× |
| `ANALYZE` | 22.5 ms | 30.0 ms | 72.8 ms | 3.2× |

`ANALYZE` is the exception that proves the rule: it reads a **sample** of 30,000 rows (300 × `default_statistics_target`), so it hardly grows. Everything that reads every row grows with the row count.

## MySQL InnoDB

| `orders` at | 50k | 500k | 5M | 5M ÷ 50k |
|---|---|---|---|---|
| Table + index (`data_length + index_length`) | 5 MB | 40 MB | 392 MB | 78× |
| PRIMARY leaf pages (`innodb_index_stats`) | n/a | n/a | 19,234 (300 MB) | |
| Lookup by id | `const`, 0.00 s | `const`, 0.00 s | `const`, 0.00 s | ≈ 1× |
| `SELECT SUM(amount)` (full scan) | 0.01 s | 0.03 s | 0.59 s | 59× |
| `ALTER TABLE … ADD INDEX (seller_id)` | 0.11 s | 0.69 s | 3.14 s | 29× |
| `ANALYZE TABLE` | ≤ 0.01 s | ≤ 0.02 s | ≤ 0.06 s | sampled |

Between 500k and 5M rows the full scan took **20× longer for 10× the rows**: the 300 MB clustered index no longer fits the 128 MB buffer pool, so each scan reads most pages back in. `ANALYZE TABLE` samples 20 pages per index (`innodb_stats_persistent_sample_pages`), so its cost barely moves.

## MongoDB

| `orders` at | 50k | 500k | 5M | 5M ÷ 50k |
|---|---|---|---|---|
| Data (uncompressed) / indexes | 6 MB / 1 MB | 57 MB / 6 MB | 567 MB / 115 MB | |
| Lookup by `_id`: keys / time | 1 / 0 ms | 1 / 0 ms | 1 / 0 ms | 1× |
| `$group` sum of `amount` (collection scan) | 8 ms | 76 ms | 1,077 ms | 135× |
| `createIndex({ seller_id: 1 })` | 40 ms | 369 ms | 4,273 ms | 107× |
| `validate()` | 48 ms | 486 ms | 5,600 ms | 117× |

WiredTiger's cache is 5,495 MB in this container, so the whole collection fits in memory and nothing is read from disk; the growth is pure CPU work per document (decompressing pages, converting BSON). `stats().wiredTiger.btree["maximum tree depth"]` reported 3 for all three sizes.

## Comparison

| 100× more rows (50k → 5M) | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Lookup by primary key | 1.2× (+1 level) | ≈ 1× | 1× |
| Full scan | 30× | 59× | 135× |
| Build an index | 69× | 29× | 107× |
| Whole-table check | `VACUUM` 34× | (not measured) | `validate` 117× |
| Statistics | `ANALYZE` 3.2× (sampled) | sampled | (not applicable) |

<Pitfall>
"The table is too big" is not a diagnosis. If the slow queries are lookups through a good index, 100× more rows costs one more tree level, and splitting the table will not help. Check **which work** is slow: if it is whole-table work (index builds, vacuum, scans, backups, deleting old rows), splitting can help, because each piece can be handled alone. Concept 4 measures the opposite case.
</Pitfall>

## Real-world scenario: the index that now takes an hour

A marketplace orders table grew from 20M to 2B rows over four years. Queries by order id and by seller with recent dates are still fast. What broke:

| Job | Then | Now | Why |
|---|---|---|---|
| Add an index for a new report | minutes | hours | Reads and sorts every row |
| Anti-wraparound `VACUUM` | minutes | most of a day | Reads every page that is not frozen |
| Restore a backup to a test server | 20 min | 2 days | Copies every byte |
| Delete orders older than 3 years | quick | hours, plus bloat | Concept 2 |

None of these got slower because of tree depth. They got slower because they touch every row, and there are 100× more rows.

## Key takeaways

1. B-tree depth grows logarithmically: 100× more rows added one level (PostgreSQL) and no measurable lookup time.
2. Whole-table work grows linearly or worse: index builds 29×–107×, scans 30×–135×, vacuum/validate 34×–117× for 100× the rows.
3. When the table outgrows the buffer cache, scans pay to re-read pages each time (MySQL: 20× for 10× the rows past the 128 MB pool).
4. Sampled jobs (`ANALYZE`) barely grow.
5. Splitting data is a remedy for whole-table work, not for slow lookups.
