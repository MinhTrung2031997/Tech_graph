<Tldr>
Every transaction should survive six questions. **Scope:** what exactly must be all-or-nothing, and nothing more. **Isolation:** which anomalies would break it (Sessions 2–3), and which level or lock prevents them. **Concurrency control:** atomic statement, row lock or version check, chosen by contention (Session 7: thousands of optimistic retries on one hot row, a handful across 1,000 rows). **Retries:** which errors are retried, with the whole transaction re-run (Session 7: a MySQL 1205 that was not rolled back committed half a transfer). **Duration:** how long it can live, with timeouts that enforce it (this session: one idle transaction queued an unrelated SELECT; one old snapshot grew a table 3.5×). **Boundaries:** no network call to another system inside it; use an outbox (this session: dual writes lost 62 events per 1,000). The flows below walk a checkout through the list in each engine.
</Tldr>

## The checklist

| # | Question | Good answer | Course reference |
|---|---|---|---|
| 1 | **Scope:** which changes must commit together? | The smallest set that keeps an invariant (order + stock + payment record), nothing else | Session 1 |
| 2 | **Isolation:** which anomaly would break it? | Named anomaly → level or lock that prevents it; default level only if none applies | Sessions 2–3 |
| 3 | **Concurrency control:** how are conflicting writers handled? | Atomic guarded statement first; `FOR UPDATE` on hot rows; version check for low contention or long think time | Sessions 5, 7 |
| 4 | **Retries:** what happens on 40001 / 40P01 / 1213 / 1205 / TransientTransactionError? | Whole-transaction retry with cap and jitter; explicit ROLLBACK; idempotency key for client retries | Sessions 6, 7 |
| 5 | **Duration:** how long can it live, and what enforces that? | Milliseconds; no user or network waits inside; timeouts on the role; bulk work in batches | Sessions 4, 8 |
| 6 | **Boundaries:** does it touch another system? | No: events via an outbox or CDC, consumers idempotent | Session 8 |
| + | **Indexes:** do its statements find rows by index? | Every WHERE in a locking statement uses an index, or it locks far more rows than it changes | Session 5, Indexing course |
| + | **Monitoring:** how would you see it go wrong? | Retry counts, lock waits, oldest transaction age, history list / dead tuples, outbox lag | Sessions 4, 8 |

| Term | Meaning |
|---|---|
| Invariant | A rule the data must always satisfy (stock ≥ 0, debits = credits, one active subscription per user) |
| Scope creep | Work added to a transaction that does not need its atomicity (logging, emails, reads for display) |
| Safety net | A database-side limit that bounds damage when application code misbehaves (timeouts) |
| **✓ Ship / ✗ Redesign** | The transaction passes every question, or one answer forces a change |

## Safety nets per engine

| Setting | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Idle inside a transaction | `idle_in_transaction_session_timeout` | (none) `wait_timeout` per session | `transactionLifetimeLimitSeconds` (60 s) |
| Whole transaction | `transaction_timeout` (17+) | (none) | `transactionLifetimeLimitSeconds` |
| One statement | `statement_timeout` | `max_execution_time` (SELECT only) | `maxTimeMS` |
| Waiting for a lock | `lock_timeout` | `innodb_lock_wait_timeout`, `lock_wait_timeout` (metadata) | `maxTransactionLockRequestTimeoutMillis` |
| Oldest snapshot | Monitor `backend_xmin` age, slots, prepared xacts | Monitor history list length | `minSnapshotHistoryWindowInSeconds` (300 s) |

Set them per **role** or per **connection** for the application, looser for humans and batch jobs, and alert when they fire: each firing is a transaction that broke rule 5.

## Worked example: reviewing four transactions

| Transaction | Finding | Change |
|---|---|---|
| "Transfer between accounts" | Read balance, check, two UPDATEs in request order | Guarded debit (`WHERE balance >= amt`), update in id order, retry 40P01/1213 |
| "Generate monthly statements" | One transaction over 2M accounts, 40 minutes | Batches of 5,000 by id; statements idempotent per (account, month) |
| "Sign up user" | INSERT user, then call email API, then COMMIT | Commit, then outbox row → relay sends the email |
| "Reserve a seat" | `SELECT … WHERE seat_id = ? AND status = 'free'` then UPDATE | One guarded UPDATE, or `FOR UPDATE`; unique (event, seat) for bookings |

<Pitfall>
The checklist is about each transaction **as written in the code**, including what the framework adds. Transaction-per-request middleware, ORM lazy loading after the transaction began, `@Transactional` on a method that calls another service, and connection pools that do not roll back on return all change the answers to questions 1, 5 and 6 without appearing in the SQL. Read the generated statements (`log_statement`, the general log, the profiler) for a real request.
</Pitfall>

## Real-world scenario: the transaction review in code review

A team adds four lines to its pull-request template for any change that opens a transaction:

| Line | Reviewer checks |
|---|---|
| Invariant | Which rule this transaction protects, in one sentence |
| Conflict handling | Atomic statement, lock, or version; why |
| Retry | Which errors, where the loop is, why it is safe to repeat |
| Outside calls | None inside; how events leave (outbox) |

Production incidents caused by transactions (deadlock storms, idle sessions, lost updates) dropped mostly because the questions are asked before the code ships, not after.

## Key takeaways

1. Six questions: scope, isolation, concurrency control, retries, duration, boundaries; plus indexes and monitoring.
2. Prefer one guarded atomic statement; it answers questions 2 and 3 at once.
3. Retries re-run the whole transaction and need idempotency; MySQL 1205 needs an explicit ROLLBACK.
4. Keep transactions short and enforce it with database-side timeouts; batch bulk work.
5. Never call another system inside a transaction; use an outbox or CDC with idempotent consumers.
