<Tldr>
The most damaging transaction is often one that does **nothing**: it ran an UPDATE, then the application went off to call an API, wait for a user, or crashed without closing the connection. Its locks stay held. In the lab one such session (A) in PostgreSQL blocked an **UPDATE of the same row** (B), an **`ALTER TABLE`** (C), and, because C was queued, a **plain SELECT of a different row** (D): `pg_blocking_pids` showed the chain A → B, A → C, C → D. MySQL showed the same queue as `Waiting for table metadata lock` on both the ALTER and the SELECT. Timeouts are the fix: with `idle_in_transaction_session_timeout = '5s'` PostgreSQL terminated A after 5 s and B, C and D all completed at **5.01 s**; `transaction_timeout` (PostgreSQL 17) ended a busy transaction after **2.00 s**; MySQL has no idle-transaction timeout, but `wait_timeout = 5` closed A's connection and released the queue at **5.03 s**. MongoDB aborts any transaction older than `transactionLifetimeLimitSeconds` (60 s): a plain write waiting on A's document finished after **≈ 80 s**, and A's commit got `NoSuchTransaction`.
</Tldr>

## What an idle transaction holds

| Held by an idle transaction | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Row locks from its writes | ✓ until COMMIT/ROLLBACK | ✓ | ✓ (document write intents) |
| Table-level lock (blocks DDL) | ✓ RowExclusiveLock (any statement takes one) | ✓ shared metadata lock | ✓ intent locks (DDL waits) |
| An old snapshot (blocks cleanup) | Only if REPEATABLE READ, or a statement is running; a transaction **that wrote** holds its xid (Concept 2) | ✓ its read view, if it read under RR | ✓ its snapshot |
| A connection | ✓ | ✓ | ✓ session |

| Term | Meaning |
|---|---|
| Idle in transaction | A session inside `BEGIN … COMMIT` that is not running a statement, waiting for the client |
| Lock queue | A waiting lock request also blocks later requests that conflict with **it**, even if they are compatible with the current holder |
| `idle_in_transaction_session_timeout` | PostgreSQL: terminate a session idle inside a transaction for longer than this |
| `transaction_timeout` | PostgreSQL 17+: terminate a session whose transaction (active or idle) has lasted longer than this |
| `wait_timeout` | MySQL: close a connection idle (between statements) for longer than this, rolling back its transaction |
| **✓ Released / ✗ Waiting** | The blocked statements completed, or are still queued |

## Finding idle transactions

| Engine | Query | Look for |
|---|---|---|
| PostgreSQL | `SELECT pid, usename, application_name, state, now() - xact_start AS xact_age, now() - state_change AS idle_for, query FROM pg_stat_activity WHERE state LIKE 'idle in transaction%' ORDER BY xact_start` | `xact_age` of seconds or more; `query` is the **last** statement, a hint to the code path |
| PostgreSQL | `SELECT pid, pg_blocking_pids(pid) FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0` | Who blocks whom |
| MySQL | `SELECT t.trx_mysql_thread_id, t.trx_started, p.command, p.time FROM information_schema.innodb_trx t JOIN information_schema.processlist p ON p.id = t.trx_mysql_thread_id WHERE p.command = 'Sleep'` | Open transactions on sleeping connections |
| MySQL | `SELECT * FROM sys.innodb_lock_waits` / `sys.schema_table_lock_waits` | Row waits / metadata lock waits with the blocker's id |
| MongoDB | `$currentOp` with `idleSessions: true`, filter on `transaction` | `active: false` with a large `timeInactiveMicros` |

<Pitfall>
The usual sources are in the application, not the database: a request handler that opens a transaction and then calls an HTTP API; an ORM that begins a transaction on first query and commits at the end of the request; a test or console session left open; an exception path that never rolls back and returns the connection to a pool that does not reset it. Set `idle_in_transaction_session_timeout` (for the application role) as a safety net, but fix the code path the `query` column points to.
</Pitfall>

## Connection pools and transactions

| Pool mode | One transaction holds | Risk |
|---|---|---|
| Session pooling (default in most app pools) | One server connection for the client's session | Idle-in-transaction connections reduce the pool for everyone |
| Transaction pooling (PgBouncer `pool_mode = transaction`) | A server connection only while a transaction is open | Session state (SET, prepared statements, session advisory locks, Session 7) does not survive between transactions; an idle open transaction pins a server connection |
| Statement pooling | A server connection per statement | Multi-statement transactions are not allowed |

## Real-world scenario: the migration that took the site down

A deploy runs `ALTER TABLE orders ADD COLUMN …`, which should take milliseconds. Instead the site's order pages time out for six minutes. A support engineer had a psql session open since the morning with `BEGIN; SELECT * FROM orders WHERE id = …;` and gone to lunch.

| Lesson | Setting / practice |
|---|---|
| The ALTER queued behind an idle transaction, and all reads queued behind the ALTER | `SET lock_timeout = '3s'` in migrations; retry later |
| Nobody noticed the idle session | Alert on `idle in transaction` older than 1 minute |
| Humans open transactions by hand | `idle_in_transaction_session_timeout` for human roles (e.g. 10 min), much lower for the application role |

## Key takeaways

1. An idle transaction keeps its locks: it blocked a same-row UPDATE, an ALTER TABLE and, through the lock queue, an unrelated SELECT.
2. `pg_stat_activity` (state `idle in transaction`, `pg_blocking_pids`), `innodb_trx` joined with processlist, and `$currentOp` with `idleSessions` find it.
3. PostgreSQL: `idle_in_transaction_session_timeout` and, from 17, `transaction_timeout` end it (5.01 s and 2.00 s in the lab).
4. MySQL has no idle-transaction timeout; `wait_timeout` per session (5.03 s in the lab) and short `lock_wait_timeout` for DDL limit the damage.
5. MongoDB caps transactions at 60 s (`transactionLifetimeLimitSeconds`), enforced by a periodic job: the waiting write finished after ≈ 80 s.
