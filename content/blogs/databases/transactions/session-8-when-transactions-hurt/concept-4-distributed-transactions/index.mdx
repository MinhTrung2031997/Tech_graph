<Tldr>
"Save the order **and** publish an `OrderCreated` event" touches two systems, and no local transaction covers both. In a simulation of 1,000 orders with a 5% chance of crashing between the two writes, **database first** lost **62** events (orders nobody heard about) and **publish first** produced **52** phantom events (for orders that never existed). **Two-phase commit** makes both systems prepare, then commit: PostgreSQL ships it **disabled** (`max_prepared_transactions = 0`: "prepared transactions are disabled"), and in MySQL a prepared XA branch survived its client's disconnect, **kept its row lock** (another update got 1205 after 2 s) until someone ran `XA COMMIT` by hand. The **outbox pattern** writes the event into an `outbox` table **in the same local transaction** as the order; a relay publishes it afterwards and marks it sent. With failures and relay crashes injected, all **1,000** events arrived, as **1,377** deliveries: at least once, never zero, so consumers must be idempotent (Session 7). In MongoDB, a **change stream** is a ready-made relay: after a simulated crash at event 400 it resumed from its token and delivered all 1,000 in order.
</Tldr>

## The problem

| Approach | Failure between the two writes | Lab result (1,000 orders, 5% crash) |
|---|---|---|
| ✗ Commit to the database, then publish | Order exists, event never sent | **62 lost events** |
| ✗ Publish, then commit | Event sent, order never stored | **52 phantom events** |
| Two-phase commit (2PC / XA) | Both systems prepared; a coordinator must finish them | Needs every system to support it; in-doubt transactions hold locks |
| ✓ Transactional outbox | Event row commits with the order; relay retries until sent | **0 lost**, 1,000 distinct events, 377 duplicate deliveries |
| ✓ Change data capture (change streams, logical decoding, binlog readers) | The database log is the outbox | **0 lost**, resumed without gaps after a crash |

| Term | Meaning |
|---|---|
| Dual write | Writing to two systems in sequence, with no transaction across them |
| Two-phase commit | Phase 1: every participant prepares (durably promises it can commit); phase 2: the coordinator tells all to commit or roll back |
| In-doubt (prepared) transaction | Prepared but not yet committed or rolled back: holds its locks indefinitely |
| Outbox | A table written in the same transaction as the business change, holding the events to publish |
| Relay | A process that reads unsent outbox rows, publishes them, and marks them sent |
| At-least-once | Every event is delivered one or more times; duplicates are possible, losses are not |
| **✓ Consistent / ✗ Lost or phantom** | Database and broker agree, or not |

## MongoDB: change streams as the relay

MongoDB's multi-document transactions are local to one replica set (or cluster). For "write and publish", a **change stream** reads the oplog: every committed change, in order, with a **resume token** to continue after a restart.

## Choosing

| Need | Choose |
|---|---|
| Publish events for a database change | Outbox table + relay, or CDC (change streams, PostgreSQL logical decoding with Debezium, MySQL binlog readers) |
| Update two databases you own, atomically | Avoid it: one owner per piece of data; otherwise a saga (steps with compensating actions) |
| A legacy XA-capable stack (JTA + two databases) | 2PC can work; monitor `pg_prepared_xacts` / `XA RECOVER` and alert on old entries |
| Consumers | Always idempotent by event id: every option above is at least once |

<Pitfall>
The outbox only moves the problem if the relay is careless: marking rows sent **before** publishing turns at-least-once into at-most-once (lost events on a crash), and publishing from inside a long-open transaction holds row locks and the cleanup horizon (Concepts 1–2). Publish, then mark, in short transactions, and delete or archive sent rows in batches (Concept 3).
</Pitfall>

## Real-world scenario: the missing invoices

An order service inserts orders and then calls the billing service over HTTP. Each month a few dozen paid orders have no invoice; they all coincide with deploys and pod restarts.

| Step | Change |
|---|---|
| 1 | Write `OrderPaid` to an outbox table in the order's transaction |
| 2 | A relay (or Debezium on the WAL) publishes to the queue billing consumes |
| 3 | Billing stores processed event ids under a unique key (Session 7) and ignores duplicates |
| 4 | Alert on the age of the oldest unsent outbox row |

## Key takeaways

1. A local transaction cannot include a broker or another service; dual writes lost 62 or invented 52 events per 1,000 with a 5% crash rate.
2. Two-phase commit is disabled by default in PostgreSQL; in MySQL an in-doubt XA branch outlived its client and kept its lock until resolved by hand.
3. The outbox writes the event in the same transaction as the change; a relay delivers it at least once: 0 lost, 377 duplicates with injected crashes.
4. Change data capture (MongoDB change streams, logical decoding, binlog readers) uses the database log as the outbox; resume tokens gave 1,000 of 1,000 events in order.
5. At-least-once delivery requires idempotent consumers keyed by event id.
