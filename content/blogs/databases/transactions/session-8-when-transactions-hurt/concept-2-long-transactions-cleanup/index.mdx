<Tldr>
MVCC (Session 4) keeps the old version of a row as long as **any** transaction might still need to read it. One long transaction therefore stops cleanup for everybody. In the lab, an open REPEATABLE READ snapshot in PostgreSQL made `VACUUM` report **"50000 are dead but not yet removable"**; repeated over four update cycles the table grew from **439 to 1,545 pages** (3.5×) and its index from 77 to 242, while the same workload without the old snapshot stayed at **439** pages. A subtle case: an idle **READ COMMITTED** transaction that had only read held nothing back, but one that had **written one row** kept **49,995** dead tuples alive. In MySQL an open read view stopped purge: the **history list** grew to **5,020** undo logs instead of ≈ 200, and the old reader's `SUM` went from **5.6 to 32 ms** because it had to rebuild old versions from undo. In MongoDB an open snapshot transaction pinned **50,019** transaction IDs in WiredTiger, released the moment it ended; MongoDB also refuses snapshots older than 300 s (**SnapshotTooOld**) and transactions older than 60 s.
</Tldr>

[Session 4, Concept 4](/blogs/databases/transactions/session-4-mvcc-internals/concept-4-long-transactions) explains how each engine stores and finds old versions and why the oldest snapshot sets the cleanup horizon. This concept is the operational side: what one long transaction costs on a busy table, which kinds of transaction hold cleanup back, and how to find the one that does.

## Who holds the horizon back

| Engine | Old versions live in | Cleaned by | Held back by |
|---|---|---|---|
| PostgreSQL | The table itself (dead tuples) and its indexes | HOT pruning, VACUUM / autovacuum | The oldest `backend_xmin` (snapshot) **or** `backend_xid` (running writer) in the database; also replication slots and prepared transactions |
| MySQL | Undo logs (history list) | Purge threads | The oldest active **read view**, server-wide |
| MongoDB | WiredTiger update chains in cache, then the history store | Eviction and checkpoints | The oldest open snapshot (transactions, snapshot reads), capped at `minSnapshotHistoryWindowInSeconds` (300 s) |

| Term | Meaning |
|---|---|
| Horizon / removable cutoff | The oldest transaction id whose snapshot might still need old versions; versions dead before it can be removed |
| Dead but not yet removable | A dead tuple newer than the horizon: VACUUM must keep it |
| History list length | Number of committed transactions' undo logs that purge has not processed yet (InnoDB) |
| Pinned range | WiredTiger: how many transaction IDs separate the oldest pinned snapshot from the newest |
| **✓ Cleaned / ✗ Kept** | Old versions removed and space reused, or kept for a reader |

## Finding the transaction that holds the horizon

| Engine | Query |
|---|---|
| PostgreSQL | `SELECT pid, state, backend_xid, backend_xmin, now() - xact_start AS age, left(query, 60) FROM pg_stat_activity WHERE backend_xid IS NOT NULL OR backend_xmin IS NOT NULL ORDER BY age(backend_xmin) DESC NULLS LAST;` also `pg_replication_slots` (`xmin`, `catalog_xmin`) and `pg_prepared_xacts` |
| PostgreSQL | `SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;` and `VACUUM (VERBOSE)` ("dead but not yet removable", "removable cutoff … XIDs old") |
| MySQL | `SELECT count FROM information_schema.innodb_metrics WHERE name = 'trx_rseg_history_len';` and the oldest `trx_started` in `information_schema.innodb_trx` |
| MongoDB | `transaction range of IDs currently pinned` and `$currentOp` with `idleSessions: true` for open transactions |

<Pitfall>
The long transaction is often not in the application at all. In PostgreSQL: a forgotten replication slot (its `xmin`), a prepared transaction nobody committed, a read replica with `hot_standby_feedback = on` running a 3-hour report, or `pg_dump` (which runs one long REPEATABLE READ transaction for the whole dump). In MySQL: a backup tool that holds a consistent snapshot, or an analyst's SQL client in manual-commit mode. All of them hold cleanup back for every table in the database (PostgreSQL) or the whole server (MySQL).
</Pitfall>

## Real-world scenario: the queue table that grew to 40 GB

A `jobs` table holds about 10,000 rows at any time; rows are inserted, updated twice and deleted within minutes. It is 40 GB on disk and every claim is slow. `n_dead_tup` is in the hundreds of millions; autovacuum runs constantly and removes nothing.

| Finding | Cause | Fix |
|---|---|---|
| `VACUUM VERBOSE`: "dead but not yet removable" in the millions | A nightly reporting transaction on the same database runs 6 hours at REPEATABLE READ | Run reports on a replica without `hot_standby_feedback`, or with `transaction_timeout` |
| Space not returned after the report ends | VACUUM frees space for reuse; it does not shrink the file | `pg_repack` (online) or `VACUUM FULL` in a maintenance window |
| It will happen again | No alert | Alert on the age of the oldest `backend_xmin` and on `n_dead_tup` growth |

## Key takeaways

1. Old versions are kept while any transaction might read them: one snapshot stops cleanup for the whole database (PostgreSQL) or server (MySQL).
2. PostgreSQL: 50,000 dead tuples "not yet removable", table 439 → 1,545 pages over four cycles; an idle READ COMMITTED transaction that wrote one row did the same.
3. MySQL: the history list grew to 5,020 instead of ≈ 200, and the old reader slowed down 5.7× rebuilding versions from undo.
4. MongoDB pinned 50,019 transaction IDs during an open snapshot transaction, but bounds the damage: 60 s transactions, 300 s snapshot history.
5. Find the holder by its snapshot/xid age (`pg_stat_activity`, `innodb_trx`, `$currentOp`), including non-application sources like replication slots, replicas and dumps.
