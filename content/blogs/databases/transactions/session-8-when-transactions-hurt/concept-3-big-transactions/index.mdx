<Tldr>
A bulk change ("set every job's `locked_by`", "recalculate all prices") is tempting as one statement in one transaction. In the lab, updating **100,000 jobs** took 0.2–0.4 s in each engine, but while the transaction stayed open a **single-row update of job 50 waited the whole time** (1.5–1.7 s: as long as we kept it open). In PostgreSQL the statement produced **37.6 MB of WAL** (309,262 records) at once, which a replica must receive and replay before it catches up. Rolling back differs sharply: PostgreSQL's `ROLLBACK` took **3 ms** (the new versions are simply never visible), InnoDB's took **184 ms** for one pass and **347 ms** for four, because it applies the undo log row by row. MongoDB committed 100,000 documents in one transaction, writing **one oplog entry** of 100,000 operations; with 200 bytes more per document it needed **two** entries of 15.9 and 15.4 MB (the 16 MB document limit). The default for bulk work is **batches** of a few thousand rows, each its own transaction: 20 batches of 5,000 took 0.27–0.57 s, and each held its locks for milliseconds.
</Tldr>

## What one big transaction costs

| Cost | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Locks | Every updated row locked until COMMIT | Every updated row: 100,465 rows locked in 466 lock structures | Every modified document |
| A writer that needs one of those rows | Waits for the whole transaction (1,508 ms) | Waits (1,686 ms), or 1205 after `innodb_lock_wait_timeout` | A plain write waits (1,600 ms) |
| Log | WAL written as it goes: 37.6 MB, 1,480 full-page images | Redo as it goes; the **binlog** is written at commit, in one piece | One oplog entry per 16 MB, all at commit |
| Rollback | **3 ms**: the aborted xid is marked, versions stay invisible and are vacuumed later | **184 ms** (1 pass), **347 ms** (4 passes): undo applied row by row | Aborted in memory |
| Cleanup | Old versions kept until the transaction ends (Concept 2) | Undo kept until purge | Pinned history |
| Replicas | Receive WAL continuously; replay can lag behind a burst | Receive the whole binlog event group at commit: a 10-minute transaction can arrive as a 10-minute replay | Receive the oplog entries at commit |

Not measured in the lab: replica lag (single-node containers). The rows about replicas describe each engine's documented replication design.

| Term | Meaning |
|---|---|
| Batch | A slice of the bulk change (e.g. 5,000 rows by primary-key range), committed as its own transaction |
| Full-page image (FPI) | PostgreSQL writes a whole 8 kB page to the WAL the first time it is modified after a checkpoint |
| Undo | InnoDB's record of how to reverse each change; used for rollback and for old versions |
| `partialTxn` | MongoDB oplog flag on all but the last entry of a transaction split into several entries |
| **✓ Short locks / ✗ Long locks** | Other writers wait milliseconds, or the length of the whole bulk job |

## Writing a good batch job

| Rule | Why |
|---|---|
| Slice by an indexed key range (`id BETWEEN …`), not `LIMIT` + `OFFSET` | Each batch is an index range scan; OFFSET re-reads everything before it (Indexing Session 10) |
| Commit each batch | Locks, undo and snapshots held for milliseconds |
| Make batches idempotent (`WHERE … AND NOT migrated`) | A rerun after a failure skips finished work |
| Pause between batches if replicas lag | Lets replication and VACUUM/purge keep up |
| Size by time, not rows (≈ 100–500 ms per batch) | Rows differ in cost; time is what blocks others |
| Do not wrap the loop in an outer transaction | ORMs and migration tools sometimes do; it turns batches back into one big transaction |

<Pitfall>
"All or nothing" is a real requirement only sometimes. A price recalculation that must switch atomically is better done by writing the new values to a new column or table in batches, then switching with one small transaction (rename, flag, or pointer update). That gives atomic visibility without holding 100,000 row locks for the whole computation.
</Pitfall>

## Real-world scenario: the nightly cleanup that stalled checkouts

`DELETE FROM sessions WHERE expires_at < now()` runs every night and removes ≈ 5 million rows in one statement. For 15 minutes logins are slow, replicas fall behind and the next morning the table is still bloated.

| Problem | Fix |
|---|---|
| 5M rows locked for 15 minutes | Delete in batches of 5,000 by primary key, committing each |
| Replica lag after the burst | Batches with a short pause; monitor lag between batches |
| Bloat afterwards | Batches let autovacuum keep up; or partition by day and drop old partitions (Indexing Session 7) |

## Key takeaways

1. A big transaction locks every row it touches until the end: a single-row update waited 1.5–1.7 s in each engine.
2. PostgreSQL wrote 37.6 MB of WAL for one 100,000-row UPDATE; replicas get it as a burst.
3. Rollback is cheap in PostgreSQL (3 ms, the cost moves to VACUUM) and proportional to the work in InnoDB (184–347 ms here, hours for hour-long transactions).
4. MongoDB writes a transaction to the oplog at commit, split into ≈ 16 MB entries; most bulk changes need no transaction there.
5. Batch bulk changes by key range, commit each batch, make them idempotent, and switch atomically at the end if needed.
