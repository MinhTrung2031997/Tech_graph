<Tldr>
Networks time out after the server has done the work, so clients **retry**; queues deliver **at least once**; users **double-click**. A handler that is not idempotent charges twice. The fix: the client sends an **idempotency key**, and the server records it under a **unique constraint in the same transaction as the effect**. In the lab, 200 payment requests each arrived **4 times concurrently**. Check-then-insert ("have I seen this key?") charged **696** times in PostgreSQL and **800** in MySQL; with a unique key and `ON CONFLICT DO NOTHING` / `INSERT IGNORE` / a unique index, exactly **200** charges and the balance was right in all three engines. Some critical sections have **no row to lock** ("next invoice number = max + 1"): 8 workers × 50 produced only **54** distinct numbers in PostgreSQL, **61** in MySQL and **120** in MongoDB. A transaction-level **advisory lock** (`pg_advisory_xact_lock`), MySQL's **`GET_LOCK`**, or MongoDB's **atomic counter** gave 400 distinct numbers.
</Tldr>

## Idempotency: the same request, once

| Term | Meaning |
|---|---|
| Idempotent operation | Running it twice has the same effect as running it once |
| Idempotency key | A unique id the client generates per logical request (a UUID) and resends unchanged on every retry |
| Check-then-insert | `SELECT` the key; if absent, `INSERT` it and do the work. Two concurrent copies both see "absent" |
| Unique-key claim | `INSERT` the key under a unique constraint; only one copy can succeed, the others get a conflict |
| Advisory lock | A lock on an application-chosen number or name, not on any row; the database only enforces mutual exclusion |
| **✓ Once / ✗ Repeated** | The effect happened once per key, or once per delivery |

### The measurements

200 requests to withdraw 1.00 from account 2, each delivered by 4 concurrent workers (a client retry storm). Correct result: 200 payments, balance 800.00.

| Variant | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| ✗ Check-then-insert, then debit, in one transaction | **696** payments, balance 304.00 | **800** payments, balance 200.00 | 200 payments, 800.00, 48–64 transaction retries (see below) |
| ✗ Check-then-insert, no shared write | | | **457** payments |
| ✓ Unique key claim, then debit if inserted | 200, 800.00 (`ON CONFLICT DO NOTHING RETURNING`) | 200, 800.00 (`INSERT IGNORE`) | 200, 800.00 (unique index; 600 duplicate-key errors) |

MySQL charged **every** copy: under REPEATABLE READ each transaction's check is a consistent read of its own snapshot, and none of the snapshots contained the others' inserts. MongoDB's first variant came out right only by accident: the four copies also updated the **same account document**, so three of them hit a write conflict, were retried, and on retry saw the payment. Without that shared write (second row), 257 duplicates appeared.

## Advisory locks: when there is no row to lock

"Invoice number = highest existing number + 1" has nothing to lock: the row does not exist yet, and `max()` reads many rows. 8 workers × 50 invoices:

| Variant | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| ✗ `max(number) + 1`, no lock | 400 invoices, **54** distinct numbers | 400 invoices, **61** distinct | 400 invoices, **120** distinct |
| ✓ Serialised | `pg_advisory_xact_lock(42)` first: 400 distinct, ≈ 0.47 s (vs 0.12 s) | `GET_LOCK('invoice', 10)` … `RELEASE_LOCK`: 400 distinct, ≈ 1.2 s (vs 0.2 s) | Counter document, `findOneAndUpdate` + `$inc`: 400 distinct, ≈ 0.34 s |

| Lock | Scope (measured) | Released |
|---|---|---|
| `pg_advisory_lock(42)` | Session: after A's `COMMIT`, B's `pg_try_advisory_lock(42)` still returned false; pg_locks showed `advisory`, ExclusiveLock, granted | `pg_advisory_unlock` or disconnect |
| `pg_advisory_xact_lock(43)` | Transaction: B got false during A's transaction, true right after A's `COMMIT` | End of transaction, automatically |
| MySQL `GET_LOCK('nightly-report', 0)` | Session: survived C's `COMMIT` (D got 0); D got 1 as soon as C disconnected | `RELEASE_LOCK` or disconnect |
| MongoDB | No advisory locks | Use a lock document with a unique `_id` and an expiry (a lease), or an atomic counter |

Advisory locks only work if **every** code path takes them; the database does not connect lock 42 with the invoices table. For numbering, a sequence or a counter row plus a unique constraint on `number` is usually the better design; advisory locks suit "only one instance may run this job" and "serialise work on customer 1234" (`pg_advisory_xact_lock(1234)`).

<Pitfall>
Session-level advisory locks (`pg_advisory_lock`, `GET_LOCK`) and connection poolers do not mix. With PgBouncer in transaction mode or any pool that hands a connection to another request after `COMMIT`, the lock stays on the pooled connection: the next request that happens to get it already "holds" the lock, and the request that took it cannot release it. Use the transaction-level form (`pg_advisory_xact_lock`) in pooled applications; MySQL has no transaction-level `GET_LOCK`, so release it in a `finally` on the same connection.
</Pitfall>

## Real-world scenario: the payment API behind a mobile app

Mobile clients time out after 10 s and retry; the payment provider sometimes answers in 12 s. Support sees customers charged twice.

| Step | Design |
|---|---|
| Client | Generates `Idempotency-Key: <uuid>` per checkout and resends it on retries |
| Server, transaction 1 | `INSERT INTO idempotency (key, request_hash, status) VALUES (…, 'started') ON CONFLICT DO NOTHING`; 0 rows → return the stored response (or "in progress") |
| Provider call | Outside the database transaction, passing the same key to the provider (most payment APIs accept one) |
| Server, transaction 2 | Store the provider result and the response body under the key |
| Retention | Keep keys for at least the client's retry window (24 h is common); delete older ones in batches |

## Key takeaways

1. Retries and redeliveries are normal; without idempotency 200 requests became 696–800 charges.
2. Check-then-insert does not work under concurrency, and in MySQL REPEATABLE READ it never sees concurrent inserts.
3. Insert the idempotency key under a unique constraint in the same transaction as the effect; the row count (or E11000) tells you whether to act.
4. MongoDB's check-then-insert looked correct only because of an unrelated hot document; use a unique index.
5. Advisory locks serialise work with no row to lock; prefer the transaction-level form, especially behind a connection pool.
