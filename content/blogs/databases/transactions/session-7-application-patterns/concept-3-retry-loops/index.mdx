<Tldr>
Stronger isolation and concurrent transactions mean some attempts will be **refused**: PostgreSQL `40001` (serialization failure) and `40P01` (deadlock), MySQL `1213` (deadlock), MongoDB errors labelled `TransientTransactionError`. In each case the database has **rolled back the whole transaction**, and the right reaction is to run it again from the start. In the lab, 8 workers × 100 transfers between 20 accounts needed **562–602 retries** under PostgreSQL SERIALIZABLE, **53–71** deadlock retries under MySQL SERIALIZABLE and **188–230** in MongoDB; with a retry loop every run ended with the money conserved (20,000.00). Two traps: PostgreSQL detects a deadlock only after **`deadlock_timeout` (1 s)**, so 3–6 deadlocks made the run **10–20× slower** than locking rows in a consistent order; and MySQL's **lock wait timeout (1205) rolls back only the statement**: in the lab the transaction carried on and committed **half a transfer**.
</Tldr>

## Which errors to retry

| Engine | Error | Meaning | Rolled back | Retry |
|---|---|---|---|---|
| PostgreSQL | `40001` serialization_failure: "could not serialize access due to read/write dependencies among transactions" (SERIALIZABLE) or "… due to concurrent update" (REPEATABLE READ) | Your transaction could not be ordered with a concurrent one | Whole transaction | ✓ whole transaction |
| PostgreSQL | `40P01` deadlock_detected | You were chosen as the victim of a lock cycle | Whole transaction | ✓ whole transaction |
| MySQL | `1213` ER_LOCK_DEADLOCK (SQLSTATE 40001): "Deadlock found when trying to get lock; try restarting transaction" | Deadlock victim | Whole transaction | ✓ whole transaction |
| MySQL | `1205` ER_LOCK_WAIT_TIMEOUT: "Lock wait timeout exceeded; try restarting transaction" | Waited `innodb_lock_wait_timeout` | **Only the statement** (default) | ⚠ roll back yourself, then retry |
| MongoDB | label `TransientTransactionError` (e.g. 112 WriteConflict) | Conflict or transient failure inside a transaction | Whole transaction | ✓ whole transaction |
| MongoDB | label `UnknownTransactionCommitResult` | The commit may or may not have applied | Unknown | ✓ retry **commit** only (it is idempotent) |

| Term | Meaning |
|---|---|
| Retryable error | The database refused this attempt for a concurrency reason; the same transaction may succeed if run again |
| Retry loop | Run the whole transaction (reads included) again, with a cap and a backoff |
| Backoff with jitter | Wait a short, random, growing time before retrying, so the same transactions do not collide again in lockstep |
| `deadlock_timeout` | PostgreSQL waits this long (1 s default) before checking for a deadlock |
| **✓ Commit / ✗ Retryable / ✗ Fatal** | The attempt committed; refused, run again; or a real error, give up |

## The measurements

8 workers × 100 transfers of 1.00 between random pairs of the first 20 accounts. Every run ended with the 20 balances summing to 20,000.00. Two runs each.

| Variant | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| READ COMMITTED (MySQL: RR), update `from` then `to` | 3–6 × `40P01`, ≈ 3.5–5.4 s | 5–6 × `1213`, ≈ 0.7–0.8 s | 220–230 transient retries, ≈ 0.5 s |
| Same, rows updated in id order | 0 errors, ≈ 0.26–0.30 s | 0 errors, ≈ 0.7 s | 188–195 transient retries, ≈ 0.4–0.5 s |
| SERIALIZABLE, read balance, check, update both | **562–602 × `40001`** + 4–6 × `40P01`, ≈ 4.5–6.5 s | **53–71 × `1213`**, ≈ 0.7–0.9 s | (transactions are snapshot isolation) |

Why the differences:

- **PostgreSQL deadlocks are slow.** A waiting transaction checks for a cycle only after `deadlock_timeout` (1 s): the captured deadlock took **1,000 ms** to report. 3–6 of them cost 3–5 s of an otherwise 0.3 s run. MySQL detected its deadlock after **1 ms**.
- **MySQL SERIALIZABLE turns plain SELECTs into shared locks.** Two transfers read (S lock) the same account, then both try to update it (X lock): a deadlock, 53–71 of them.
- **MongoDB conflicts are not deadlocks.** A transactional write to a document another open transaction modified fails at once with `WriteConflict` (≈ 4 ms), whatever the order. Ordering the writes did not reduce them (188–195 vs 220–230).

## A correct retry loop

```js
// Retry the whole transaction on retryable errors, with a cap and jittered backoff.
async function inTransaction(work, { maxAttempts = 10 } = {}) {
  for (let attempt = 1; ; attempt++) {
    const client = await pool.connect();
    try {
      await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE');
      const result = await work(client);          // all reads and writes happen in here
      await client.query('COMMIT');
      return result;
    } catch (e) {
      await client.query('ROLLBACK').catch(() => {});
      const retryable = e.code === '40001' || e.code === '40P01';   // MySQL: errno 1213 (and 1205 after ROLLBACK)
      if (!retryable || attempt >= maxAttempts) throw e;
      await sleep(Math.random() * 5 * attempt);   // jittered backoff
    } finally {
      client.release();
    }
  }
}
```

| Rule | Why |
|---|---|
| Retry the **whole** transaction, reads included | The decision was based on data that changed |
| No side effects inside the retried function | An email or HTTP call would be repeated on every attempt (outbox, Session 8) |
| Cap attempts, add jittered backoff | Unbounded retries amplify overload; lockstep retries collide again |
| Always `ROLLBACK` on error, explicitly | MySQL 1205 leaves the transaction open |
| Log the retry count | A rising count is the first sign of a hot row or a missing index (Session 5) |

<Pitfall>
Many frameworks retry nothing by default. Ecto's `Repo.transaction`, Spring's `@Transactional` and ActiveRecord's `transaction` all raise the 40001/1213 error to your code. And many HTTP clients will happily retry the **whole request** at a higher level, which re-runs non-idempotent work outside any transaction: make the endpoint idempotent first (Concept 5).
</Pitfall>

## Real-world scenario: moving to SERIALIZABLE

A team switches a PostgreSQL service to SERIALIZABLE to fix a write-skew bug (Session 2). Within an hour the error rate rises: `could not serialize access` on 5% of checkout requests during peak.

| Step | Action |
|---|---|
| 1 | Wrap each transaction in a retry helper like the one above; errors drop to ≈ 0 |
| 2 | Watch the retry count per endpoint: hot rows show up as high counts |
| 3 | Keep transactions short and read only what the decision needs (fewer dependencies) |
| 4 | Declare read-only transactions `READ ONLY`; SSI tracks them more cheaply |
| 5 | Where the conflict is a single row, use an atomic statement (Concept 1) instead |

## Key takeaways

1. `40001`, `40P01`, `1213` and `TransientTransactionError` mean "run the whole transaction again"; they are normal under concurrency.
2. With a retry loop, 800 transfers stayed correct even with 562–602 serialization failures.
3. PostgreSQL deadlocks cost `deadlock_timeout` (1 s) each; prevent them with a consistent lock order rather than retrying them.
4. MySQL `1205` undoes only the statement: always `ROLLBACK` before retrying, or you may commit half a transaction.
5. In MongoDB use `withTransaction`; keep the callback side-effect free, and retry only the commit on `UnknownTransactionCommitResult`.
