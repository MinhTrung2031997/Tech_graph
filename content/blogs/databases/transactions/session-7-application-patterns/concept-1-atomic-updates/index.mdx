<Tldr>
Application code loves the shape **read → compute → write**: load the account, subtract in the application, save the new balance. Under concurrency it silently loses work: two workers read 1000.00, both write 999.00, one withdrawal disappears. In the lab, **8 workers × 50 withdrawals** of 1.00 from one account ended at **947.00** in PostgreSQL (347 of 400 withdrawals lost), **950.00** in MySQL (350 lost) and **914.00** in MongoDB (314 lost), with no error anywhere. The fix needs no locks in application code: put the arithmetic **inside one statement** (`SET balance = balance - 1`, `$inc`). Each engine then applies it to the **latest** committed version of the row: all three ended at exactly **600.00**. Add the business rule to the same statement (`WHERE balance >= 1`) and the row count tells you whether the withdrawal happened.
</Tldr>

## The experiment

Account 1 starts at 1000.00. 8 workers each make 50 withdrawals of 1.00, so the correct final balance is **600.00**. Each statement is its own transaction (autocommit), as in most ORM code paths.

| Pattern | Statements per withdrawal | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|---|
| ✗ Read-then-write | `SELECT balance` → compute → `UPDATE … SET balance = :new` | 947.00–949.00: **347–349 lost** | 950.00: **350 lost** | 914.00–926.00: **314–326 lost** |
| ✓ Atomic | `UPDATE … SET balance = balance - 1 WHERE … AND balance >= 1` / `$inc` | 600.00, ≈ 0.24–0.27 s | 600.00, ≈ 0.6–1.0 s | 600.00, ≈ 0.12 s |

Two runs each; timings are approximate (other experiments shared the machine). The read-then-write runs were not slower: they were **fast and wrong**, and nothing in any log said so.

| Term | Meaning |
|---|---|
| Lost update | Two transactions read the same value, both write a value computed from it; the second write erases the first |
| Read-then-write | Read a value in one statement, compute in the application, write the result in another |
| Atomic update | The read, the computation and the write happen in one statement on one row or document |
| Conditional update | An atomic update whose `WHERE` (or filter) also checks the business rule (`balance >= 1`); the affected-row count says whether it applied |
| **✓ Correct / ✗ Lost** | Final balance 600.00, or higher because withdrawals vanished |

## MySQL

InnoDB has a twist: a plain `SELECT` is a **consistent read** from the transaction's snapshot, but `UPDATE` is a **locking read** that always works on the latest committed version. That is why the atomic form works even under REPEATABLE READ.

## MongoDB

A single-document update is atomic in MongoDB: the filter is matched and the update applied to one version of the document. Two concurrent updates of the same document cause a write conflict inside the storage engine, which the server retries automatically for single-document writes outside a transaction.

## The guard belongs in the statement

| Need | ✗ Read-then-write | ✓ Atomic, guarded |
|---|---|---|
| Withdraw if enough money | `SELECT balance`, `if balance >= amount`, `UPDATE … SET balance = :new` | `UPDATE accounts SET balance = balance - :amt WHERE id = :id AND balance >= :amt` → 1 row = done, 0 = refused |
| Sell one unit if in stock | `SELECT stock`, `if stock > 0`, `UPDATE … SET stock = :new` | `UPDATE inventory SET stock = stock - 1 WHERE sku = :sku AND stock > 0` |
| Count a page view | `views = views + 1` in the ORM entity | `UPDATE … SET views = views + 1` / `$inc` |
| Several fields from one decision | Read-then-write in a transaction, plus a lock or a version check | Concept 2 |

The `CHECK (balance >= 0)` constraint in the lab schema is a second line of defence: a buggy update that would go negative fails instead of silently corrupting data. It does not catch lost updates: 947.00 is a perfectly valid balance.

<Pitfall>
ORMs make read-then-write the default. `account = Repo.get(Account, 1)`, `account.balance - 1`, `Repo.update(changeset)` (Ecto), `account.balance -= 1; account.save` (ActiveRecord) or `entity.setBalance(…)` (JPA) all send `SET balance = <constant>`. Wrapping it in a transaction does not help under READ COMMITTED (PostgreSQL's default): the read still takes no lock. Use the ORM's atomic form (`Repo.update_all(… inc: [balance: -1])`, `update_counters`, `UPDATE … SET x = x - 1`), a version column, or a row lock (Concept 2).
</Pitfall>

## Real-world scenario: the flash sale

A shop sells 100 units of a product at 10:00. The checkout service reads `stock`, checks `stock > 0`, and writes `stock - 1`. With hundreds of concurrent checkouts, many read the same stock value: the shop sells far more than 100 units, and stock still looks positive.

| Fix | Effect |
|---|---|
| `UPDATE inventory SET stock = stock - 1 WHERE sku = ? AND stock > 0` | Exactly 100 succeed; the rest get 0 rows and see "sold out" |
| `CHECK (stock >= 0)` | Any other code path that would oversell fails loudly |
| One hot row for a very popular SKU | Every checkout queues on its row lock (Session 5); split stock into a few bucket rows if throughput matters |

## Key takeaways

1. Read → compute in the application → write loses updates under concurrency: 314–350 of 400 withdrawals in the lab, with no error.
2. Arithmetic inside one statement (`balance = balance - 1`, `$inc`) is applied to the latest version by all three engines: exactly 600.00.
3. Put the business rule in the same statement (`WHERE balance >= 1`) and use the affected-row count as the answer.
4. InnoDB's UPDATE is a locking read of the latest version, unlike its plain SELECT; PostgreSQL re-checks the WHERE clause on the new version (EvalPlanQual).
5. ORMs default to read-then-write; look for their atomic update form.
