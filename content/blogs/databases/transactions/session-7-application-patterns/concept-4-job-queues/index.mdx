<Tldr>
A `jobs` table with `status = 'queued'` is a fine queue, if workers claim jobs correctly. In the lab, 8 workers drained **2,000** jobs, each needing 2 ms of work. **No lock** (SELECT, then UPDATE): every job ran **3–5 times** (10,588 runs in PostgreSQL). **`FOR UPDATE`**: correct, but every worker waited for the same first row, so the work was serialised: **≈ 8–10 s** in PostgreSQL. **`FOR UPDATE SKIP LOCKED`**: each worker skipped rows locked by others and took the next one: **≈ 2 s**, every job exactly once. MySQL added a twist: under its default REPEATABLE READ the same SKIP LOCKED queue hit **2,594–3,017 deadlocks** (gap locks on the `(status, id)` index), and **0** under READ COMMITTED (≈ 1.6 s). MongoDB has no SKIP LOCKED and does not need it: `findOneAndUpdate` claims one queued job atomically (≈ 2.5 s, 0 duplicates). First of all, the claim needs an **index on the queued jobs**: without one every claim walked 90,000 finished jobs.
</Tldr>

## The claim query needs an index

The queue table keeps 90,000 `done` jobs and 10,000 `queued` ones. "Oldest queued job" without an index on the status:

| Engine | Without index | Index | With index |
|---|---|---|---|
| PostgreSQL | Index Scan on `jobs_pkey`, Rows Removed by Filter 90,000, 1,177 buffers, 7.6 ms | `CREATE INDEX jobs_queued_idx ON jobs (id) WHERE status = 'queued'` (partial) | 5 buffers, 0.06 ms |
| MySQL | Index scan on PRIMARY, 90,001 rows, 9.4 ms | `ALTER TABLE jobs ADD INDEX jobs_status_id (status, id)` | Covering index lookup, 0.1 ms |
| MongoDB | 90,001 keys and documents examined, 44 ms | `createIndex({ status: 1, _id: 1 })` | 1 key, 1 document |

Every claim runs this query, so at 8 workers the unindexed version is the bottleneck before any locking question arises (Indexing Session 5 covers partial indexes).

## The measurements

8 workers, 2,000 jobs, 2 ms of work per job done while the claim is held. "Runs" counts how many times any worker processed a job.

| Variant | PostgreSQL | MySQL (REPEATABLE READ) | MySQL (READ COMMITTED) | MongoDB |
|---|---|---|---|---|
| ✗ No lock: SELECT, then UPDATE | 10,588 runs (8,588 duplicates), ≈ 6.8 s | 8,975–9,445 runs, ≈ 10.5–13.5 s | | findOne + updateOne: 5,151 runs (3,151 duplicates), ≈ 3.9 s |
| ✗ `FOR UPDATE` | 2,000 runs, ≈ 7.8–10.1 s | 2,000 runs, **14,875 deadlocks**, ≈ 12.2 s | 2,000 runs, 0 deadlocks, ≈ 11.7 s | |
| ✓ `FOR UPDATE SKIP LOCKED` | 2,000 runs, ≈ 1.9–2.1 s | 2,000 runs, **2,594–3,017 deadlocks**, ≈ 3.9–6.9 s | 2,000 runs, **0 deadlocks, ≈ 1.6 s** | |
| ✓ `findOneAndUpdate` claim | | | | 2,000 runs, ≈ 2.5 s |

| Term | Meaning |
|---|---|
| Claim | Pick one queued job and make sure no other worker picks it |
| `SKIP LOCKED` | A locking read that silently skips rows other transactions have locked, instead of waiting |
| `NOWAIT` | A locking read that fails immediately if a row is locked |
| Empty claim | SKIP LOCKED returned nothing although queued jobs remained (all were locked by others at that moment): 8–40 per run |
| Lease | A claimed job records who took it and when, so a crashed worker's jobs can be re-queued later |
| **✓ Once / ✗ Duplicate / ✗ Waiting** | The job ran once; ran more than once; or the worker sat in a lock queue |

## MySQL: SKIP LOCKED plus gap locks

MySQL 8.0+ supports `SKIP LOCKED` too, but under the default REPEATABLE READ the claim's index scan also takes **gap locks** on `jobs_status_id`. The `UPDATE … SET status = 'done'` moves the job's entry from the `queued` part of the index to the `done` part, which needs an **insert intention** lock in a gap another worker has locked.

## MongoDB: claim atomically

MongoDB has no locking reads. It does not need them for a queue: `findOneAndUpdate` finds the first matching document **and** updates it as one atomic operation, so two workers can never get the same queued job.

## Two ways to hold a claim

| Style | How | Crash of a worker | Fits |
|---|---|---|---|
| Lock while working | `BEGIN; … FOR UPDATE SKIP LOCKED; work; UPDATE … 'done'; COMMIT` (measured above) | Rollback releases the job automatically | Short jobs (milliseconds to seconds) |
| Claim, commit, work | `UPDATE … SET status = 'running', locked_at = now() … RETURNING id` in a short transaction; work; mark done | Job stays `running`: a sweeper re-queues jobs with an old `locked_at` | Long jobs (do not hold a transaction for minutes, Session 8) |

<Pitfall>
"Queue empty" is a dangerous conclusion with SKIP LOCKED: the query returns no row when every remaining job is locked by another worker. The lab saw 8–40 such empty claims per run while jobs remained. Workers should sleep and poll again, not exit, and monitoring should count queued rows, not empty claims.
</Pitfall>

## Real-world scenario: the email queue that sent everything twice

A notifications service runs 4 workers on `SELECT … WHERE status = 'pending' LIMIT 50`, sends the emails, then marks them sent. Customers receive duplicates during busy periods, and the duplicates increase when workers are added.

| Fix | Effect |
|---|---|
| `… LIMIT 50 FOR UPDATE SKIP LOCKED` inside a transaction | Each batch claimed by one worker |
| Partial index `WHERE status = 'pending'` | The claim reads a few pages, not the sent history |
| MySQL workers at READ COMMITTED | No gap-lock deadlocks between batches |
| Claim-commit-work with `locked_at` for slow SMTP | No long transactions; crashed batches re-queued |
| Idempotency key per email (Concept 5) | A rare double run sends nothing twice |

## Key takeaways

1. Claiming with a plain SELECT runs jobs many times: 8,588 duplicate runs for 2,000 jobs in PostgreSQL.
2. `FOR UPDATE` is correct but serialises the workers; `FOR UPDATE SKIP LOCKED` runs them in parallel: ≈ 2 s vs ≈ 8–10 s.
3. Index the queued jobs (partial index in PostgreSQL): otherwise every claim scans the finished history.
4. MySQL queue workers should use READ COMMITTED: under REPEATABLE READ, gap locks caused thousands of deadlocks.
5. MongoDB claims with one atomic `findOneAndUpdate`; record who claimed and when, to recover from crashes.
