<Tldr>
Some changes need a decision in the application between the read and the write (check a limit, call a pricing rule, update several fields). Two ways keep that safe. **Pessimistic:** `SELECT … FOR UPDATE` locks the row before reading, so other writers **wait**. **Optimistic:** read freely, then `UPDATE … SET version = version + 1 WHERE id = ? AND version = :seen`; 0 rows means someone else won, so **retry**. Both ended at the correct balance in every run. The difference is contention: 8 workers × 100 withdrawals on **one** row cost the optimistic version **2,790–3,875 retries** in PostgreSQL and **5,095–5,190** in MySQL (2–3× slower than locking); spread over **1,000** rows it needed **0–5 retries** and was as fast or faster. MongoDB has no `FOR UPDATE`: a transaction that writes a document first is still **optimistic underneath**, aborting with `WriteConflict` (325–396 retries on the hot row) instead of waiting.
</Tldr>

## Two ways to protect a decision

| | Pessimistic | Optimistic |
|---|---|---|
| Idea | Lock first, then read and write | Read, then write only if nothing changed |
| SQL | `BEGIN; SELECT … FOR UPDATE; UPDATE …; COMMIT` | `UPDATE … SET …, version = version + 1 WHERE id = ? AND version = ?` |
| MongoDB | No row locks to request; a transaction that writes first aborts conflicting writers | `updateOne({ _id, version }, { $set: …, $inc: { version: 1 } })` |
| On conflict | The second writer **waits** | The second writer gets **0 rows** and retries |
| Holds | A row lock for the whole transaction | Nothing between read and write |
| Good for | Hot rows, expensive work that must not be repeated | Low contention, long "think time" (a form open for minutes) |

| Term | Meaning |
|---|---|
| `SELECT … FOR UPDATE` | A locking read: takes an exclusive row lock until the transaction ends |
| Version column | An integer incremented on every write; the write checks it still has the value that was read |
| Compare-and-set (CAS) | Write only if the current value equals the expected one |
| Contention | How often concurrent transactions touch the same row |
| **✓ Committed / ✗ Version mismatch** | The write applied, or found a newer version and must retry |

## The measurements

8 workers, each making withdrawals of 1.00. Every run ended at the correct total.

**One hot row** (8 × 50 withdrawals from account 1, two runs):

| Engine | Pessimistic | Optimistic | Optimistic retries |
|---|---|---|---|
| PostgreSQL | ≈ 0.44–0.45 s | ≈ 1.25–1.36 s | 1,379–1,422 |
| MySQL | ≈ 0.68–1.05 s | ≈ 0.72–1.07 s | 2,522–2,672 |
| MongoDB | ≈ 0.53–0.63 s (transaction) | ≈ 0.45–0.68 s | 996–1,389 |

**Contention falling** (8 × 100 withdrawals from a random account among the first K, two runs):

| K accounts | PostgreSQL pess / opt (retries) | MySQL pess / opt (retries) | MongoDB txn / opt (retries) |
|---|---|---|---|
| 1 | 0.9–1.3 s / 3.7–4.0 s (2,790–3,875) | 1.4–1.5 s / 2.3–2.8 s (5,095–5,190) | 1.4 s (325–396) / 1.1 s (2,030–2,977) |
| 10 | 0.24–0.34 s / 0.58–1.13 s (409–519) | 0.55 s / 0.34–0.56 s (406–482) | 0.27–0.42 s (115–118) / 0.24–0.38 s (162–169) |
| 1,000 | 0.20–0.31 s / 0.16–0.29 s (4–5) | 0.32–0.38 s / 0.26–0.39 s (0–2) | 0.23–0.32 s (3) / 0.20–0.29 s (1) |

Timings are approximate (other experiments shared the machine); the retry counts are the stable signal. On one row, optimistic workers mostly re-read and lose again: each success cost ≈ 3.5–6.5 attempts.

## Choosing

| Situation | Choose | Why |
|---|---|---|
| One counter or balance everyone updates | Atomic statement (Concept 1); if impossible, pessimistic | Optimistic retries explode: 2,790–5,190 per 800 writes |
| Rows rarely touched by two writers at once | Optimistic | No locks held, 0–5 retries, no lock waits to tune |
| A user edits a record in a form for minutes | Optimistic (version in the form) | Never hold a database lock across user think time |
| Expensive or external work between read and write (a payment API call) | Pessimistic, or restructure (Concept 5) | A retry would repeat the expensive work |
| MongoDB | Version field, or an atomic `findOneAndUpdate` | Transactions abort on conflict; they do not queue |

<Pitfall>
An optimistic retry loop that re-reads **inside the same REPEATABLE READ transaction** never sees the new version: in InnoDB the plain SELECT keeps returning the snapshot, so the version check fails forever (in PostgreSQL REPEATABLE READ the UPDATE raises 40001 instead). Start a new transaction for each attempt, and cap the number of attempts.
</Pitfall>

## Real-world scenario: the order editing screen

Two support agents open the same order, change the address and the discount, and press Save a minute apart. With plain `UPDATE orders SET … WHERE id = ?`, the second save silently overwrites the first agent's changes. Holding `FOR UPDATE` while the form is open would lock the row for minutes.

| Step | Implementation |
|---|---|
| Load | Return the order with its `version` (hidden form field or ETag) |
| Save | `UPDATE orders SET …, version = version + 1 WHERE id = ? AND version = ?` |
| 0 rows | Show "this order was changed by someone else", reload, let the agent re-apply |
| HTTP | `If-Match: "<version>"` → `412 Precondition Failed` on mismatch |

## Why this matters for application patterns

| Later concept | Why this concept matters |
|---|---|
| Concept 3: retry loops | Optimistic locking only works with a correct retry loop |
| Concept 4: job queues | Claiming jobs with `FOR UPDATE` is pessimistic locking with a twist (SKIP LOCKED) |
| Session 6 (deadlocks) | Pessimistic locks on several rows can deadlock; optimistic ones cannot |

## Key takeaways

1. Pessimistic (`FOR UPDATE`) makes conflicting writers wait; optimistic (version check) makes them retry.
2. Both were correct in every run; contention decides the cost: thousands of retries on one row, 0–5 over 1,000 rows.
3. A locking read or an UPDATE always sees the latest version in InnoDB, so version checks work there; re-reading with a plain SELECT in the same RR transaction does not.
4. MongoDB transactions behave optimistically: a conflicting write aborts with `WriteConflict` (TransientTransactionError), it does not wait.
5. Never hold a database lock across user think time; use a version for long edits.
