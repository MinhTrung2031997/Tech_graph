<Tldr>
Under **REPEATABLE READ**, an InnoDB locking read or write locks the index records it scans **and the gaps before them** (a **next-key lock**), so nobody can insert a row that would appear in a second run of the same query (a phantom). The side effects are large: `SELECT … WHERE id = 10005 FOR UPDATE` on a **missing** id beyond the last row locked the `supremum` and blocked **every** new account (ids 10003 and 20000 both timed out). `WHERE branch = 'B03' FOR UPDATE` on a secondary index took **1,001 next-key locks + 1 gap lock + 1,000 primary-key locks** and blocked an insert into **branch B02**, because the gap before the first B03 entry belongs to B02's last entry. Under **READ COMMITTED** the same statements took only record locks (6 for the range, 1,000 + 1,000 for B03) and the inserts went through. **PostgreSQL** and **MongoDB** have no gap locks: snapshots hide phantoms, and PostgreSQL's SERIALIZABLE tracks reads with non-blocking `SIReadLock`s (2 index pages + 1 relation lock here).
</Tldr>

## Records and gaps

An index is a sorted list of entries. Between two neighbouring entries there is a **gap**, and after the last entry of each page there is a pseudo-record called **supremum** (the gap "to infinity").

| Lock | `LOCK_MODE` in `data_locks` | Locks | Blocks |
|---|---|---|---|
| Record lock | `X,REC_NOT_GAP` | One index entry | Writes and locking reads of that entry |
| Gap lock | `X,GAP` | Only the gap before the entry | **Inserts** into that gap (never other gap locks) |
| Next-key lock | `X` | The entry **and** the gap before it | Both |
| Insert intention | `X,INSERT_INTENTION` | A point in a gap, requested by INSERT | Waits for any gap/next-key lock on that gap |
| **✓ Free / ✗ Locked** | | Can another session insert there now? | |

Gap locks exist only to stop **inserts**: two sessions can hold gap locks on the same gap at once (that matters for deadlocks, [Session 6](/blogs/databases/transactions/session-6-deadlocks/concept-3-hidden-deadlocks)).

Measured lock counts (`SELECT INDEX_NAME, LOCK_MODE, COUNT(*) FROM performance_schema.data_locks … GROUP BY 1, 2`):

| Statement | REPEATABLE READ | READ COMMITTED |
|---|---|---|
| `id = 500 FOR UPDATE` | 1 × `X,REC_NOT_GAP` | same |
| `id = 10005 FOR UPDATE` (missing) | 1 × `X` on supremum (blocks all higher inserts) | none |
| `id BETWEEN 100 AND 105 FOR UPDATE` | 1 × `X,REC_NOT_GAP` + 5 × `X` | 6 × `X,REC_NOT_GAP` |
| `branch = 'B03' FOR UPDATE` | 1,001 × `X` + 1 × `X,GAP` (secondary), 1,000 × `X,REC_NOT_GAP` (PRIMARY) | 1,000 + 1,000 × `X,REC_NOT_GAP` |

## Comparison

| | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| Phantoms in REPEATABLE READ / snapshot reads | Hidden by the snapshot | Hidden for plain reads (snapshot); prevented for locking reads by next-key locks | Hidden by the snapshot |
| Gap locks | None | Yes, in RR (and SERIALIZABLE); none in RC except FK and duplicate checks | None |
| SERIALIZABLE | SSI: `SIReadLock`, never blocks, may abort with 40001 | RR plus every plain SELECT becomes `FOR SHARE` (blocking) | Not offered |
| Cost of "check then insert" | No extra locking | Gap lock can block every insert in the gap | No extra locking, but no protection either |

<Pitfall>
"Lock the row if it exists, otherwise insert it" (`SELECT … FOR UPDATE` on a missing key, then INSERT) is the classic gap-lock trap in InnoDB: the check takes a gap lock, two sessions can both hold it, and both inserts then wait for each other: a deadlock ([Session 6](/blogs/databases/transactions/session-6-deadlocks/concept-3-hidden-deadlocks) reproduces it). Use `INSERT … ON DUPLICATE KEY UPDATE`, or rely on the unique constraint and handle the duplicate error.
</Pitfall>

## Real-world scenario: signups stall during a report

A nightly job runs `SELECT … FROM accounts WHERE created_at >= '2025-06-01' FOR UPDATE` over an index on `created_at`, under the default REPEATABLE READ, to "freeze" new accounts while it computes bonuses. During the job, every signup hangs: new rows go into the last gap of that index, which the job holds with a next-key lock on the supremum.

| Option | Effect |
|---|---|
| Drop `FOR UPDATE`; the job only needs a consistent snapshot | No locks; signups continue |
| Run the job under READ COMMITTED | Record locks only on existing rows |
| Lock only the rows it will update, by primary key, in small batches | Short lock windows |

## Key takeaways

1. InnoDB REPEATABLE READ locks scanned index records **and the gaps before them** (next-key locks) for locking reads and writes.
2. A locking read of a **missing** key locks the gap where it would be; at the end of the index that blocks every new row.
3. On a non-unique secondary index, the locked stretch includes the gap before the first match, which can block inserts of **neighbouring** values (B02 for a B03 query).
4. READ COMMITTED turns gap locking off for ordinary statements: record locks only.
5. PostgreSQL and MongoDB never lock gaps: snapshots hide phantoms; PostgreSQL SERIALIZABLE detects conflicts with non-blocking `SIReadLock`s.
