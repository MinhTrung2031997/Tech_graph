<Tldr>
A worker claiming jobs with `SELECT … FOR UPDATE` waits behind every other worker. **`SKIP LOCKED`** skips rows someone else holds: with T1 holding jobs 90001–90003, T2 got **90004–90006** at once in both PostgreSQL and MySQL. **`NOWAIT`** fails immediately instead (`55P03` / `ERROR 3572`). But the scan still matters: MySQL with no index on `status` put **90,420 next-key locks** on the 90,000 finished jobs it scanned past (Concept 3), so an update of an old job timed out; with an index on `(status, id)` it locked **3 + 3** records. For waits you cannot avoid, set a timeout, and know what it rolls back: PostgreSQL's `lock_timeout` **aborts the whole transaction**; MySQL's `innodb_lock_wait_timeout` rolls back **only the statement**, and a following COMMIT saved the transaction's other updates. **MongoDB** has no `SKIP LOCKED`: `findOneAndUpdate` claims one job atomically (4 workers × 50 claims → 200 distinct jobs), and transactions never wait on documents (write conflicts, Concept 1).
</Tldr>

## Waiting policies

| Policy | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| Wait (default) | Forever (`lock_timeout = 0`) | 50 s (`innodb_lock_wait_timeout`) | Transactions: no document waits; intent locks up to `maxTransactionLockRequestTimeoutMillis` (5 ms) |
| Fail at once | `FOR UPDATE NOWAIT` → `55P03` | `FOR UPDATE NOWAIT` → `ERROR 3572` | Default for transactions (`WriteConflict`) |
| Skip locked rows | `FOR UPDATE SKIP LOCKED` | `FOR UPDATE SKIP LOCKED` | Not available; use an atomic `findOneAndUpdate` |
| Timeout | `SET lock_timeout = '…'` | `SET SESSION innodb_lock_wait_timeout = …` (seconds) | `maxTimeMS` per operation |
| **✓ Claimed / ✗ Blocked** | The worker got rows, or it waited or failed | | |

## Comparison

| | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| Queue claim | `FOR UPDATE SKIP LOCKED` | `FOR UPDATE SKIP LOCKED` (+ index, or RC) | `findOneAndUpdate` |
| Locks on scanned, non-matching rows | None | Yes in RR (90,420 here) | None |
| Fail-fast error | `55P03` | `3572` | `WriteConflict` (transactions) |
| Timeout rolls back | The whole transaction (unless a savepoint) | Only the statement (`innodb_rollback_on_timeout = OFF`) | The operation (`maxTimeMS`) |
| Default wait | Forever | 50 s | Plain writes retry until done or `maxTimeMS` |

<Pitfall>
MySQL error **1205 does not end the transaction**. If your code catches it, logs, and continues to `COMMIT`, you commit everything except the statement that timed out: in the lab, two of three updates of a transfer. On 1205, roll back explicitly (or set `innodb_rollback_on_timeout = ON` server-wide). Deadlock error 1213 is different: it always rolls back the whole transaction (Session 6).
</Pitfall>

## Real-world scenario: a worker pool on MySQL

Ten workers poll `SELECT … WHERE status = 'queued' ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED` every second. Throughput is fine, but the admin page that re-runs a failed job (`UPDATE jobs SET status = 'queued' WHERE id = ?` on an old job) times out several times a minute.

| Check | Finding |
|---|---|
| `EXPLAIN` of the claim | `type: index` on PRIMARY, scanning all finished jobs |
| `data_locks` during a claim | Tens of thousands of `X` locks on old jobs |
| Fix | `CREATE INDEX jobs_status ON jobs (status, id)`; optionally move finished jobs to an archive table |

## Key takeaways

1. `SKIP LOCKED` lets workers take different rows without waiting; `NOWAIT` fails fast.
2. In InnoDB REPEATABLE READ the queue query still locks every record it scans: index the queue condition (`(status, id)`).
3. PostgreSQL `lock_timeout` aborts the whole transaction; MySQL `innodb_lock_wait_timeout` rolls back only the statement.
4. MongoDB has no `SKIP LOCKED`; `findOneAndUpdate` claims one document atomically, and it needs an index on the queue condition too.
5. Prefer short timeouts plus retries over long waits: a waiting session holds its own locks while it waits.
