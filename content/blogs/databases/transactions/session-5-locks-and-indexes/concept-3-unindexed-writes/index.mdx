<Tldr>
"A locking read, an UPDATE or a DELETE generally sets record locks on **every index record that is scanned**", whether or not it matches (MySQL manual). With no index on `shelf`, `UPDATE inventory SET stock = stock - 1 WHERE shelf = 7` scans the whole clustered index: under REPEATABLE READ it held **5,013 next-key locks** (5,000 rows + 13 page supremums) to change **100 rows**, so an update of an item on shelf 8 and an insert both timed out. `WHERE stock < 0`, matching **nothing**, locked the same 5,013. Under **READ COMMITTED** InnoDB releases non-matching rows after checking them: 100 locks, other shelves free. With an **index on `shelf`**: 101 next-key + 1 gap lock on the index and 100 on PRIMARY; shelf 8 was free, only an insert into shelf 7 waited. **PostgreSQL** and **MongoDB** lock only the rows they change (100), whatever they scan; the missing index costs them a full scan (5,000 documents examined), not extra blocking.
</Tldr>

## The setup

`inventory` has 5,000 SKUs on 50 shelves (100 each). `shelf` is deliberately **not indexed**. T1 takes one item from every SKU on shelf 7 and keeps the transaction open; T2 then touches other rows.

| Term | Meaning |
|---|---|
| Scanned record | An index entry the statement reads to evaluate its WHERE clause |
| Matched row | A scanned row that satisfies the WHERE clause and gets changed |
| Semi-consistent read | InnoDB under READ COMMITTED: a locked, non-matching row is checked against its last committed version and skipped without waiting |
| `trx_rows_locked` | Approximate number of rows a transaction has locked (`information_schema.innodb_trx`) |
| **✓ Free / ✗ Locked** | Can T2 change or insert that row now? |

## Comparison

| | PostgreSQL | InnoDB RR | InnoDB RC | MongoDB |
|---|---|---|---|---|
| Rows locked by `WHERE shelf = 7`, no index | 100 | 5,013 (all) | 100 | 100 (conflict set) |
| Effect of the missing index | Full scan (CPU, I/O) | Full scan **and** table-wide blocking | Full scan, brief locks while checking | Full scan |
| Effect of adding the index | Faster | Faster and 25× fewer locks | Faster | Faster |

<Pitfall>
In InnoDB, an index is a **concurrency** decision, not only a speed decision. An UPDATE or DELETE whose WHERE clause cannot use an index locks the whole table under the default REPEATABLE READ, even if it matches nothing. A periodic cleanup like `DELETE FROM jobs WHERE status = 'done' AND created_at < …` without a usable index blocks every worker for its whole duration. `EXPLAIN` the write: `type: ALL` means every row will be locked.
</Pitfall>

## Real-world scenario: the "harmless" stock reset

A back-office button runs `UPDATE inventory SET stock = 0 WHERE discontinued = 1` (no index on `discontinued`, 3 matching rows). Every time someone clicks it during a sale, checkout stalls for seconds: checkouts update other SKUs, and they all wait for the button's transaction, which holds next-key locks on every SKU until it commits (and the button's transaction also writes an audit log over HTTP before committing).

| Fix | Locks held |
|---|---|
| Index on `discontinued` | 3 rows + gaps |
| Select the SKUs first (plain read), then `UPDATE … WHERE sku IN (…)` by primary key | 3 rows |
| Run the session in READ COMMITTED | 3 rows (after a brief lock per scanned row) |
| Commit before the HTTP call | Shorter lock window, whatever is locked |

## Key takeaways

1. InnoDB locks every index record a locking statement **scans**, not only the rows it changes.
2. Without a usable index under REPEATABLE READ, an UPDATE or DELETE locks the whole table (5,013 locks for 100 changes), even with zero matches.
3. Lock memory stays tiny (bitmaps per page), so nothing warns you; `trx_rows_locked` and `data_locks` show it.
4. READ COMMITTED releases non-matching rows; an index limits the scan itself. Both cut the locks to the matches.
5. PostgreSQL and MongoDB lock or conflict only on rows they change; the missing index costs them a full scan, not blocking.
