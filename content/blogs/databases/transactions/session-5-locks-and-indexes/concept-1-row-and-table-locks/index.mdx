<Tldr>
Every UPDATE locks the rows it changes until the transaction ends, and a second writer of the same row **waits**. But the engines keep the lock in different places and report it differently. **PostgreSQL** writes the row lock **into the row** (its `xmax`), so `pg_locks` shows only a table-level `RowExclusiveLock`; a waiter shows up as waiting for a `ShareLock` on the holder's **transaction id**. It has four row-lock strengths, and `FOR KEY SHARE` (what foreign-key checks take) does not block an UPDATE of non-key columns. **InnoDB** keeps locks in a lock table: an `IX` intention lock on the table plus an `X,REC_NOT_GAP` lock on the **index record** (`performance_schema.data_locks`). **MongoDB** takes only intent locks (`w`) on the database and collection; documents are protected by WiredTiger's optimistic concurrency, so a second **transaction** that touches the same document fails at once with `WriteConflict` (8 ms in the lab), while a plain write **retries in a loop** (215 write conflicts over 3 s) until the transaction commits.
</Tldr>

## The question

Two sessions both update account 1. One must wait or fail, otherwise the second would overwrite a change it never saw (the lost update of [Session 2](/blogs/databases/transactions/session-2-anomalies/lab)). How does each engine record "this row is taken", and how can you see it?

| Term | Meaning |
|---|---|
| Row lock | Exclusive right to change (or protect) one row until commit or rollback |
| Table lock / intention lock | A lock on the whole table. `IX` (InnoDB) and `RowExclusiveLock` (PostgreSQL) only say "I am changing some rows in here" and do not conflict with each other |
| Lock wait | A session blocked until the holder commits, rolls back, or a timeout fires |
| Write conflict (MongoDB) | A write to a document already changed by an uncommitted transaction; it is not queued |
| **✓ Granted / ✗ Waits** | The lock is given at once, or the requester blocks |

Measured conflict matrix (T2's request while T1 holds a lock on account 2, `lock_timeout = 1s`):

| T1 holds ↓ / T2 asks → | `FOR KEY SHARE` | `FOR SHARE` | `UPDATE balance` | `UPDATE id` |
|---|---|---|---|---|
| `FOR KEY SHARE` | ✓ 1.6 ms | ✓ 1.2 ms | ✓ 0.65 ms | ✗ timeout |
| `FOR SHARE` | ✓ | ✓ | ✗ timeout | ✗ timeout |
| `FOR NO KEY UPDATE` (plain UPDATE) | ✓ 2.4 ms | ✗ timeout | ✗ timeout | ✗ timeout |
| `FOR UPDATE` (or DELETE, key UPDATE) | ✗ timeout | ✗ timeout | ✗ timeout | ✗ timeout |

Because row locks live in the rows, PostgreSQL can lock millions of rows without a lock table filling up; the price is a write to each locked row (Session 4 explains `xmax` and hint bits).

## Comparison

| | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| Where the row lock lives | In the row (`xmax`, infomask) | Lock table, one bitmap per page of index records | No row lock; uncommitted version in the WiredTiger update chain |
| Table-level marker | `RowExclusiveLock` | `IX` intention lock | Intent `w` on database and collection |
| Second writer | Waits on the holder's transaction id | Waits on the record | Transaction: `WriteConflict` at once. Plain write: retries until commit |
| Row-lock strengths | 4 (`KEY SHARE`, `SHARE`, `NO KEY UPDATE`, `UPDATE`) | 2 (`S`, `X`) | n/a |
| Where to look | `pg_locks`, `pg_stat_activity`, `pgrowlocks` | `performance_schema.data_locks`, `data_lock_waits`, `sys.innodb_lock_waits` | `$currentOp`, `serverStatus().transactions` |

<Pitfall>
`pg_locks` does not list row locks that nobody is waiting for: looking for "rows locked by T1" there finds nothing. Use `pgrowlocks` (it reads the table) or look for waiters (`pg_blocking_pids`). In MySQL the opposite trap: `sys.innodb_lock_waits.blocking_query` shows what the blocker is running **now**, not the statement that took the lock.
</Pitfall>

## Real-world scenario: "the UPDATE hangs"

An order service sometimes hangs for 50 s on `UPDATE accounts SET balance = …` and then fails with `Lock wait timeout exceeded`.

| Engine | First query | What it showed |
|---|---|---|
| MySQL | `SELECT * FROM sys.innodb_lock_waits` | `blocking_query` = NULL: the blocker is idle inside a transaction (it locked the row, then the app waited on an HTTP call) |
| PostgreSQL | `pg_stat_activity` + `pg_blocking_pids(pid)` | Blocker in state `idle in transaction` |
| MongoDB | `$currentOp` with `idleSessions: true` | An "inactive transaction" with `timeOpenMicros` growing |

Fix: never keep a transaction open across a network call; Session 8 covers `idle_in_transaction_session_timeout` and friends.

## Key takeaways

1. A write locks what it changes until the transaction ends; a second writer waits (PostgreSQL, InnoDB) or conflicts (MongoDB).
2. PostgreSQL stores row locks in the row; `pg_locks` shows only table locks and transaction-id waits. `pgrowlocks` shows row locks.
3. PostgreSQL has four row-lock strengths; `FOR KEY SHARE` (foreign-key checks) does not block updates of non-key columns.
4. InnoDB locks index records in a lock table: `IX` on the table plus `X,REC_NOT_GAP` on the record; `data_locks` shows them.
5. MongoDB transactions do not queue on documents: the second transaction gets `WriteConflict` at once; a plain write retries until the transaction finishes.
