<Tldr>
The victim policies differ. In the lab, a **big** transaction (50 rows updated, then account 1, then account 2) deadlocked with a **small** one (account 2, then account 1). **InnoDB** rolled back the **small** one (1 undo entry, 2 row locks) even though the big one closed the cycle: it picks the transaction with the least to undo. **PostgreSQL** aborted the **big** one, losing all 50 updates, because the victim is simply the session whose `deadlock_timeout` check finds the cycle. For diagnosis, PostgreSQL writes both statements to the **server log** (the client only gets "See server log for query details"); `log_lock_waits` also logs every wait longer than `deadlock_timeout`. InnoDB keeps only the **latest** deadlock in `SHOW ENGINE INNODB STATUS` (any newer deadlock, from any schema, overwrites it); `innodb_print_all_deadlocks` sends all of them to the error log. MongoDB has no deadlock report: count aborted transactions and write conflicts in `serverStatus()`.
</Tldr>

## The experiment

| t | T1 "big" | T2 "small" |
|---|---|---|
| 0.0 s | UPDATE 50 accounts (100–149), then account 1 | |
| 0.5 s | | UPDATE account 2, then account 1 → waits for T1 |
| 2.0 s | UPDATE account 2 → waits for T2: **cycle closed by T1** | |

| Term | Meaning |
|---|---|
| Victim weight (InnoDB) | Roughly the number of rows changed and locked; the lighter transaction is rolled back |
| `deadlock_timeout` check (PostgreSQL) | The waiter whose timer fires runs the search and, on finding a cycle, aborts itself |
| `log_lock_waits` | PostgreSQL logs a message when a wait exceeds `deadlock_timeout` |
| `LATEST DETECTED DEADLOCK` | Section of `SHOW ENGINE INNODB STATUS`; holds one deadlock only |
| **✓ Survivor / ✗ Victim** | |

## Comparison

| | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| Victim | The waiter whose check finds the cycle | The transaction cheapest to roll back | The transaction that hits the conflict |
| Lab: big (51 rows) vs small (1 row) | Big aborted, 50 updates lost | Small rolled back | n/a |
| Report with statements | Server log (every deadlock) | `SHOW ENGINE INNODB STATUS` (latest only); error log with `innodb_print_all_deadlocks` | None |
| Counters | `pg_stat_database.deadlocks` | `INNODB_METRICS.lock_deadlocks` | `serverStatus().transactions.totalAborted`, `metrics.operation.writeConflicts` |
| Long waits | `log_lock_waits` | `sys.innodb_lock_waits` (live) | `$currentOp` (live) |

<Pitfall>
Both SQL reports show the statements that were **waiting** when the cycle closed, not the statements that **took** the locks earlier in each transaction. "UPDATE … WHERE id = 2 deadlocked with UPDATE … WHERE id = 1" does not tell you why each transaction already held the other row: find that in the application code (or statement history) before "fixing" the queries in the report.
</Pitfall>

## Real-world scenario: deadlocks you cannot see

A team on MySQL sees `1213` in application logs a few times an hour, but `SHOW ENGINE INNODB STATUS` always shows a deadlock from a different service's tables.

| Step | Action |
|---|---|
| 1 | `SET PERSIST innodb_print_all_deadlocks = ON` (a server-wide change, by the DBA) |
| 2 | Group error-log entries by table and statement pair |
| 3 | The pair `UPDATE wallets … id = ?` / `UPDATE wallets … id = ?` dominates: opposite-order transfers |
| 4 | Fix with ordering (Concept 4); watch `lock_deadlocks` deltas drop |

## Key takeaways

1. InnoDB rolls back the transaction with the least to undo; in the lab, the 1-row one, not the one that closed the cycle.
2. PostgreSQL aborts the session whose deadlock check finds the cycle, regardless of its size; a big batch can lose all its work.
3. PostgreSQL logs every deadlock with both statements in the server log; enable `log_lock_waits` to see long waits too.
4. InnoDB keeps only the latest deadlock in `SHOW ENGINE INNODB STATUS`; use `innodb_print_all_deadlocks` and `lock_deadlocks` deltas.
5. MongoDB has no deadlock report; track abort and write-conflict rates from `serverStatus()`.
