<Tldr>
The standard cure for opposite-order deadlocks is to **lock rows in one global order** (lowest account id first). Measured with 8 clients doing random transfers between 10 hot accounts: **PostgreSQL** went from **27 to 2,689 transactions/s** (4.1% deadlocks → 0). The deadlocks themselves were few; the damage came from `deadlock_timeout`: each one held two of the 10 hot rows for a full second while everyone else queued (latency 285 ms vs 3 ms). Lowering `deadlock_timeout` to 100 ms gave 169/s; retries hid the errors but not the cost (25/s). **MySQL**, which detects deadlocks instantly, ran 791–1,112/s with 211–438 deadlocks per run and 949–1,293/s with none: ordering removes the errors, throughput barely moves. **MongoDB** ran ≈ 1,050–1,100/s **either way**, with about one retry per two commits: transactions conflict instead of waiting, so ordering cannot help; less contention does. Whatever you do, keep a **retry loop**: some deadlocks (Concept 3) cannot be ordered away.
</Tldr>

## The workload

```sql
-- One transfer: debit a, credit b (a ≠ b), both among accounts 1–10.
BEGIN;
UPDATE accounts SET balance = balance - 1 WHERE id = :a;
UPDATE accounts SET balance = balance + 1 WHERE id = :b;
COMMIT;
-- Ordered version: update least(a, b) first, then greatest(a, b), with the right sign.
```

| Term | Meaning |
|---|---|
| Hot rows | Few rows that many transactions update (10 accounts, 8 clients) |
| Lock ordering | Every transaction acquires locks in the same global order (ascending id), so no cycle can form |
| Retry loop | On `40P01` / `1213` / `TransientTransactionError`, run the whole transaction again |
| **✓ Throughput / ✗ Stalls** | |

Every run kept the total of the 10 balances at 10,000.00: no money was lost by the victims.

## Measured summary

| Engine | Random order | Id order | What ordering changes |
|---|---|---|---|
| PostgreSQL | 27 txn/s, 4.1% deadlocks, 285 ms | 2,689 txn/s, 0, 3.0 ms | Everything: removes 1 s stalls on hot rows |
| PostgreSQL, `deadlock_timeout = 100ms` | 169 txn/s, 6.6% deadlocks | | Shorter stalls, more victims |
| MySQL | 791–1,112 txn/s, 211–438 deadlocks per run | 949–1,293 txn/s, 0 | Removes errors; throughput similar |
| MongoDB | 1,052 commits/s, 0.51 retries per commit | 1,105 commits/s, 0.49 | Nothing; contention is the issue |

## Other prevention tools

| Technique | Prevents | Cost |
|---|---|---|
| Lock in a global order (sort ids; `SELECT … WHERE id IN (…) ORDER BY id FOR UPDATE` first) | Opposite-order cycles | Code discipline; you must know all rows up front |
| Lock the parent first (Concept 3) | FK / upgrade cycles | One more statement |
| Upserts instead of check-then-insert (Concept 3) | Gap-lock insert cycles | None |
| Shorter transactions (no network calls inside) | Fewer overlapping lock windows | Restructure code |
| Single-statement updates (`UPDATE … SET balance = balance - 1 WHERE id = ? AND balance >= 1`) | Read-then-write races, fewer locks held | Only for simple cases (Session 7) |
| Fewer hot rows (shard a counter into N rows) | Contention itself (helps MongoDB too) | More complex reads |
| Retry loop | Turns any remaining deadlock or conflict into a delay | Must be idempotent; keep a retry cap |

<Pitfall>
Sorting the statements is not enough if the **engine** decides the lock order. `UPDATE accounts SET … WHERE id IN (7, 3)` locks rows in the order the plan visits them, which is usually index order but can be physical order (a sequential or bitmap scan). If two statements can each lock several rows, lock explicitly first: `SELECT id FROM accounts WHERE id IN (3, 7) ORDER BY id FOR UPDATE`.
</Pitfall>

## Real-world scenario: the payout batch

A nightly payout updates 50,000 merchant balances in one transaction, while daytime-style traffic (refunds) continues. On PostgreSQL the batch fails with a deadlock after 40 minutes, every few nights, and restarts from zero (Concept 2: PostgreSQL does not spare the bigger transaction).

| Change | Effect |
|---|---|
| Process merchants in id order, the same order refunds use | No cycles between batch and refunds |
| Commit every 500 merchants (idempotent: mark each payout row as paid) | A failure loses one chunk, not the night |
| Retry a failed chunk | Remaining deadlocks become delays |

## Key takeaways

1. Locking rows in one global order makes opposite-order deadlocks impossible.
2. In PostgreSQL each deadlock stalls its rows for `deadlock_timeout`; with hot rows that cut throughput from 2,689 to 27 transactions/s.
3. In MySQL deadlocks are detected instantly and are cheap; ordering removes the errors more than it adds speed.
4. MongoDB transactions conflict instead of waiting, so ordering does not help; reducing contention does.
5. Keep a retry loop anyway: some deadlocks (gap locks, FK upgrades) are not about statement order.
