<Tldr>
A **deadlock** is a cycle of waits: T1 holds account 1 and waits for account 2, T2 holds account 2 and waits for account 1. Neither can finish, so the database must kill one. **PostgreSQL** does not look for cycles until a session has waited `deadlock_timeout` (1 s): T1's second UPDATE returned `ERROR: deadlock detected` after **1,001 ms**, and T2's waiting UPDATE went through 647 ms later. **MySQL** checks the moment a lock request would wait: T2 got `ERROR 1213 (40001) Deadlock found` **immediately** and its whole transaction was rolled back; T1 committed. **MongoDB** transactions never wait for documents, so no cycle can form: T1's second write failed at once with `WriteConflict` (`TransientTransactionError`) and T2 committed. In every engine the result is the same: one transfer applied, one must be **retried by the application**.
</Tldr>

## The cycle

Transfer A moves 100 from account 1 to account 2; transfer B moves 50 from account 2 to account 1. Each updates its source first.

| t | T1 (A: 1 → 2) | T2 (B: 2 → 1) |
|---|---|---|
| 0.0 s | UPDATE account 1 ✓ (locks 1) | |
| 0.3 s | | UPDATE account 2 ✓ (locks 2) |
| 1.0 s | UPDATE account 2 → waits for T2 | |
| 1.3 s | | UPDATE account 1 → waits for T1: **cycle** |

| Term | Meaning |
|---|---|
| Wait-for graph | Who waits for whom; a cycle in it is a deadlock |
| Deadlock detection | Searching the graph for a cycle; PostgreSQL after `deadlock_timeout`, InnoDB on every wait (`innodb_deadlock_detect = ON`) |
| Victim | The transaction the engine aborts to break the cycle |
| **✓ Committed / ✗ Victim** | Outcome per transaction |

## Comparison

| | PostgreSQL | MySQL InnoDB | MongoDB |
|---|---|---|---|
| When the cycle is found | After a waiter waits `deadlock_timeout` (1 s) | When the wait would start | Never forms |
| Error | `40P01 deadlock detected` | `1213 (40001) Deadlock found` | `112 WriteConflict` (`TransientTransactionError`) |
| What is rolled back | The victim's whole transaction | The victim's whole transaction | The conflicting transaction |
| Cost while it lasts | Both hold their locks for ≥ 1 s; others queue behind them | Microseconds | None (but retries) |
| Application must | Retry | Retry | Retry (`withTransaction` does it) |

<Pitfall>
A deadlock is not a bug in the database, and it does not corrupt data: the engine always picks a victim and the other transaction completes. The bug is an application that does not **retry** the victim. Every code path that writes more than one row in a transaction needs a retry loop for `40P01`, `1213` and `TransientTransactionError` (Session 7).
</Pitfall>

## Real-world scenario: two users pay each other

Users A and B send money to each other within the same second. The payment service runs "debit sender, credit receiver" in one transaction. Logs show occasional "deadlock detected" and failed payments.

| Engine | What users see without retries | With a retry loop |
|---|---|---|
| PostgreSQL | One payment fails after a 1 s stall | One payment takes ≈ 1 s longer |
| MySQL | One payment fails at once | One payment retries in milliseconds |
| MongoDB | One payment fails at once | `withTransaction` retries it |

Concept 4 shows how to remove the cycle entirely (lock both accounts in id order).

## Key takeaways

1. A deadlock is a cycle of lock waits; the engine must abort one transaction to break it.
2. PostgreSQL detects it only after `deadlock_timeout` (1 s); MySQL detects it the moment the cycle closes.
3. The victim's whole transaction is rolled back in both SQL engines (error `40P01` / `1213`).
4. MongoDB transactions do not wait on documents, so they cannot deadlock; they fail with `WriteConflict` instead.
5. In every engine the fix on the application side is the same: retry the failed transaction.
