<Tldr>
Some deadlocks happen even when both transactions touch rows "in the same order", because InnoDB takes **shared** or **gap** locks you did not write. **Check-then-insert**: two sessions `SELECT … FOR UPDATE` two *different* missing ids above the last row; both get the same supremum next-key lock (gap locks are compatible), then each INSERT's insert-intention lock waits for the other's gap lock: `1213`. **Duplicate insert**: T1 inserts id 20005; T2 and T3 insert the same id and wait with **S** locks; T1 rolls back, both S locks are granted, both want **X** to insert: `1213` for T3, T2 inserts. **Child then parent**: two transactions insert a `ledger` row for account 5 (the foreign-key check takes **S** on `accounts` row 5) and then update account 5 (needs **X**): `1213`. In **PostgreSQL** the same three sequences gave: both inserts succeed; T2 inserts and T3 gets a duplicate-key error; both transactions commit (the FK's `FOR KEY SHARE` does not conflict with a balance update). **MongoDB**: no gap or FK locks; a duplicate insert inside a transaction fails at once with `WriteConflict`.
</Tldr>

## Locks you did not ask for

| Statement | InnoDB takes | PostgreSQL takes |
|---|---|---|
| `SELECT … FOR UPDATE` on a missing key | Gap / next-key lock (compatible with other gap locks) | Nothing |
| `INSERT` | Insert-intention lock in the gap, then `X` on the new record | Row is new; unique check waits for the in-progress inserter |
| `INSERT` hitting a duplicate in progress | `S` lock on the existing record, waiting | Waits for the other transaction to end |
| `INSERT` child with a foreign key | `S` lock on the parent record | `FOR KEY SHARE` on the parent row |
| **✓ Commits / ✗ 1213** | | |

## Comparison

| Sequence | InnoDB (REPEATABLE READ) | PostgreSQL | MongoDB |
|---|---|---|---|
| Check missing key, then insert | ✗ 1213 | ✓ both | ✓ both (no read locks) |
| 3 × insert same key, first rolls back | ✗ 1213 for one waiter | ✓ one, duplicate-key error for the other | `WriteConflict` (txn) / retry (plain) |
| Insert child, then update parent | ✗ 1213 | ✓ both (`KEY SHARE` vs `NO KEY UPDATE`) | No FKs |

<Pitfall>
"Check whether it exists, then insert" is the most common source of InnoDB deadlocks in application code (`get_or_create`, `find_or_create_by`, idempotency checks). The check is not a lock you can rely on, and in InnoDB it is a gap lock that sets up the deadlock. Let the unique index decide: `INSERT … ON DUPLICATE KEY UPDATE` (MySQL), `INSERT … ON CONFLICT` (PostgreSQL), `updateOne(…, { upsert: true })` with a unique index (MongoDB), and handle the duplicate-key result.
</Pitfall>

## Real-world scenario: order items and order totals

An order service inserts `order_items` (FK to `orders`) and then updates `orders.total` in the same transaction. Two items added to the same order at once (double click, two tabs) deadlock on MySQL a few times a day; the same code on PostgreSQL never does.

| Fix | Why it works |
|---|---|
| Lock the parent first: `SELECT … FROM orders WHERE id = ? FOR UPDATE`, then insert items, then update the total | Both transactions queue on the parent's `X` lock before taking any `S` |
| Update the total first, then insert the item | The `X` lock is taken first; the FK check's `S` is then compatible with your own `X` |
| Compute totals on read (or asynchronously) | No parent update in the write path |

## Key takeaways

1. InnoDB adds locks you did not write: gap locks for locking reads of missing keys, `S` locks for duplicate checks and foreign-key checks.
2. Shared and gap locks are compatible with each other, so two transactions can both hold one and then both need to upgrade: a deadlock.
3. Check-then-insert, concurrent duplicate inserts and "insert child, update parent" all deadlocked in InnoDB and none did in PostgreSQL.
4. Prefer atomic upserts and unique constraints over check-then-insert.
5. When a parent row will be updated, lock it first (`FOR UPDATE`) so every transaction queues on the same lock.
