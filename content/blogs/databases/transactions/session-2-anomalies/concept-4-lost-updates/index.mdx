<Tldr>
A **lost update** happens when two transactions read the same value, each computes a new one in the application, and the second write overwrites the first. In the lab, T1 read balance 1,000 and wrote 1,100; T2 read 1,000 as well and wrote 950. Final: **950**, the +100 gone, in **PostgreSQL READ COMMITTED**, **MySQL REPEATABLE READ** (its default, with no error) and **MongoDB without a transaction**. **PostgreSQL REPEATABLE READ** rejected T2 ("could not serialize access due to concurrent update") and a **MongoDB transaction** failed T2 with `WriteConflict`: correct, but the application must retry. Two fixes worked everywhere: **lock the row while reading** (`SELECT … FOR UPDATE`: T2 waited and read 1,100) or **let the database do the arithmetic** (`balance = balance - 50`, `$inc`). Both gave **1,050**.
</Tldr>

## The pattern that loses updates

```
T1: read balance (1,000)          T2: read balance (1,000)
T1: write 1,000 + 100 = 1,100     
T1: commit                        T2: write 1,000 − 50 = 950
                                  T2: commit                → 950, not 1,050
```

| Term | Meaning |
|---|---|
| Read-modify-write | Read a value, compute in the application, write the result back |
| Atomic update | The database reads and writes in one statement: `SET balance = balance - 50` |
| Locking read | `SELECT … FOR UPDATE`: reads the latest value and locks the row until commit |
| **✓ 1,050** | Both changes applied |
| **✗ 950** | T1's +100 was overwritten |

<Pitfall>
MySQL's default level does not protect read-modify-write code, and ORMs write exactly that code: `account = find(20); account.balance += 100; save(account)` sends `UPDATE … SET balance = 1100`. Use an atomic update, a locking read, or optimistic locking with a version column ([Session 7](/blogs/databases/transactions/session-7-application-patterns/lab)).
</Pitfall>

## Real-world scenario: stock that never runs out

Two checkouts buy the last unit of a SKU at the same moment. Each reads `stock = 1`, checks `> 0`, and writes `stock = 0`. Both succeed; one item is sold twice.

| Fix | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| Atomic conditional update | `UPDATE inventory SET stock = stock - 1 WHERE sku = $1 AND stock > 0` (check the row count) | Same | `updateOne({ _id: sku, stock: { $gt: 0 } }, { $inc: { stock: -1 } })` (check `modifiedCount`) |
| Locking read | `SELECT stock … FOR UPDATE` | Same | Transaction (fails fast with WriteConflict) |
| Optimistic | `UPDATE … SET stock = 0, version = version + 1 WHERE sku = $1 AND version = $v` | Same | Filter on `version` |

## Key takeaways

1. Read-modify-write in application code loses updates unless something serializes the cycles.
2. Lost: PostgreSQL READ COMMITTED, MySQL REPEATABLE READ (silently), MongoDB without a transaction (950 each).
3. Detected: PostgreSQL REPEATABLE READ (error 40001) and MongoDB transactions (WriteConflict); the application must retry.
4. Prevented: `SELECT … FOR UPDATE` (T2 waited and read 1,100) and atomic updates (`balance = balance - 50`, `$inc`): 1,050.
5. MongoDB transactions fail fast on conflicts; non-transactional writes wait for the transaction.
