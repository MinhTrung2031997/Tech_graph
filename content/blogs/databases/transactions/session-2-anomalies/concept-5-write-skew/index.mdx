<Tldr>
**Write skew** is the anomaly snapshots cannot catch. Accounts 30 and 31 belong to one family, with a rule that their combined balance must stay at least 1,000 (both start at 1,000). T1 checks the total (2,000), withdraws 900 from account 30; T2 checks the total (2,000), withdraws 900 from account 31. They write **different rows**, so no write conflict exists, and both commit: total **200**. That happened at PostgreSQL and MySQL **REPEATABLE READ** and in **MongoDB transactions**. **PostgreSQL SERIALIZABLE** aborted T2 ("could not serialize access due to read/write dependencies", 40001), **MySQL SERIALIZABLE** turned the reads into shared locks and T2 died in a **deadlock**, and locking both rows with `FOR UPDATE` made T2 wait, see 1,100 and refuse. MongoDB has no SERIALIZABLE level: a write to a shared **guard document** forced a WriteConflict.
</Tldr>

## Why snapshots miss it

| Step | T1 | T2 |
|---|---|---|
| Read the rule's input | total of 30 + 31 = 2,000 | total of 30 + 31 = 2,000 |
| Decide | 2,000 − 900 ≥ 1,000 ✓ | 2,000 − 900 ≥ 1,000 ✓ |
| Write | account 30: 1,000 → 100 | account 31: 1,000 → 100 |
| Conflict check (snapshot isolation) | No other transaction wrote **row 30** | No other transaction wrote **row 31** |
| Result | Commit | Commit → total 200 ✗ |

Each transaction's decision depended on a row the **other** one changed. Snapshot isolation only compares write sets, so it sees nothing wrong.

| Term | Meaning |
|---|---|
| Write skew | Two transactions read overlapping data, write disjoint data, and together break a rule each one checked |
| SERIALIZABLE | The result must equal some one-at-a-time order of the transactions |
| SSI | Serializable Snapshot Isolation: PostgreSQL's SERIALIZABLE, which tracks read/write dependencies |
| **✓ Rule kept** | Total of accounts 30 and 31 ≥ 1,000 (it ended at 1,100) |
| **✗ Rule broken** | Total 200 |

<Pitfall>
Write skew hides behind code that looks correct: "check, then act" on rows that other transactions also check. Typical cases: at least one doctor on call, no double booking of a room (two inserts into an empty range), spending limits across several cards, unique usernames enforced by a SELECT instead of a UNIQUE index. Prefer a constraint the database can enforce (UNIQUE, exclusion constraint); otherwise use SERIALIZABLE with retries, or lock what the decision depends on.
</Pitfall>

## Real-world scenario: double booking

A booking service checks `SELECT count(*) FROM bookings WHERE room = 12 AND tsrange overlaps …` and inserts if zero. Under load, two bookings for the same slot appear every week. It is write skew with **inserts**: both transactions read an empty range and insert different rows.

| Fix | Engine |
|---|---|
| Exclusion constraint `EXCLUDE USING gist (room WITH =, during WITH &&)` | PostgreSQL ([Indexing Session 7](/blogs/databases/indexing/session-7-specialist-indexes/concept-4-gist-trigram)) |
| SERIALIZABLE + retry | PostgreSQL; MySQL (locks, deadlocks) |
| Lock a parent row (`SELECT … FROM rooms WHERE id = 12 FOR UPDATE`) first | PostgreSQL, MySQL |
| One document per room-day with an array of slots, updated with a condition | MongoDB |

## Key takeaways

1. Write skew: two transactions check a shared rule, write different rows, and break the rule together (total 200).
2. Snapshot isolation (PostgreSQL and MySQL REPEATABLE READ, MongoDB transactions) does not detect it.
3. PostgreSQL SERIALIZABLE aborted T2 with 40001; MySQL SERIALIZABLE produced a deadlock that rolled back T2.
4. Locking every row the decision reads (`FOR UPDATE` on both) or writing a shared guard document also prevents it.
5. Best of all: express the rule as a constraint the database enforces.
