<Tldr>
A **phantom** is a row that matches a query's condition but was not there the first time the query ran, because another transaction inserted (or updated a row into) the range. In the lab, T1 counted the 10,000 `queued` jobs, T2 inserted job 100,001 as `queued`, and T1 counted again: **10,001** at READ COMMITTED in PostgreSQL and MySQL. At PostgreSQL REPEATABLE READ and in a MongoDB transaction, both the count and T1's `UPDATE … WHERE status = 'queued'` saw **10,000**. MySQL REPEATABLE READ is different: the reads stayed at 10,000, but the `UPDATE` changed **10,001** rows (writes read the latest data), and afterwards T1's own count jumped to **10,001**.
</Tldr>

## Phantoms vs non-repeatable reads

| | Non-repeatable read (Concept 2) | Phantom |
|---|---|---|
| What changes | An existing row's values | The **set** of rows matching a condition |
| Caused by | UPDATE of a row T1 read | INSERT (or an UPDATE/DELETE that moves rows into or out of the condition) |
| Locks that could prevent it | Lock on the rows read | A lock on the **range** (rows that do not exist yet) |

| Term | Meaning |
|---|---|
| Consistent read | A plain SELECT that reads from the snapshot |
| Current read (MySQL) | `UPDATE`, `DELETE`, `SELECT … FOR UPDATE`: reads the latest committed version and locks it |
| **✓ Stable set** | T1's queries and writes all saw the same 10,000 jobs |
| **✗ Phantom** | Job 100,001 appeared in T1's results or was changed by T1 |

If T1 starts with a **locking** read instead, InnoDB places **next-key locks** (a row plus the gap before it) on everything it scans, and inserts into those gaps wait. In a second run, T1's `SELECT count(*) … WHERE status = 'queued' FOR UPDATE` returned 10,000 and held **100,466 locks** in `performance_schema.data_locks`: `status` has no index, so InnoDB scanned and locked all 100,000 rows. T2's insert waited **1.3 s**, until T1 committed. That is how InnoDB prevents phantoms for current reads, and why it needs an index to do so cheaply ([Session 5](/blogs/databases/transactions/session-5-locks-and-indexes/lab)).

<Pitfall>
"The count matched, so my UPDATE touched those rows" is not safe in MySQL REPEATABLE READ: reads come from the snapshot, writes from the latest data. Code that counts, then updates "the same" rows, can act on rows it never saw. Use a locking read for the first step, or make the write's own result (`ROW_COUNT()`, `RETURNING` in PostgreSQL) the source of truth.
</Pitfall>

## Real-world scenario: the batch that paid one invoice twice

A payout job in MySQL counts approved invoices, computes the total to transfer, then marks them `paid` with `UPDATE … WHERE status = 'approved'`. An invoice approved between the count and the update is marked paid but was not in the transfer total; next month's reconciliation finds it.

| Fix | Effect |
|---|---|
| `SELECT … FOR UPDATE` for the first read (MySQL) | Locks the matching rows and the gaps; new approvals wait |
| Select the ids once, then `UPDATE … WHERE id IN (…)` | The write acts exactly on what was read |
| PostgreSQL REPEATABLE READ or a MongoDB transaction | Writes ignore rows outside the snapshot |

## Key takeaways

1. A phantom is a new row matching a condition that a transaction already evaluated.
2. READ COMMITTED shows phantoms in both SQL engines (10,000 → 10,001).
3. PostgreSQL REPEATABLE READ and MongoDB transactions hide them from reads and writes alike.
4. MySQL REPEATABLE READ hides them from plain reads only: the UPDATE changed 10,001 rows and the next count said 10,001.
5. Locking reads in InnoDB prevent phantoms with next-key locks, at the cost of blocking inserts.
