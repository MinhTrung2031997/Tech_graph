<Tldr>
Session 1 made one transaction all-or-nothing. This session asks what happens when **two** run at once. An **anomaly** is a result that no one-at-a-time order of the transactions could have produced. The mildest is the **dirty read**: seeing another transaction's change **before it commits**, then watching it disappear in a rollback. In the lab, T1 set account 10 to 0 and rolled back two seconds later; meanwhile T2 under MySQL `READ UNCOMMITTED` read **0.00**, a balance that never existed. Under MySQL `READ COMMITTED`, under every PostgreSQL level (PostgreSQL treats `READ UNCOMMITTED` as `READ COMMITTED`) and in MongoDB, T2 read **1,000.00**.
</Tldr>

## The anomalies in this session

| Anomaly | What goes wrong | Concept |
|---|---|---|
| Dirty read | Read a change that is later rolled back | This one |
| Non-repeatable read / read skew | The same read, or two related reads, give inconsistent answers within one transaction | [Concept 2](/blogs/databases/transactions/session-2-anomalies/concept-2-non-repeatable-reads-and-read-skew) |
| Phantom | A repeated query returns new rows that match its condition | [Concept 3](/blogs/databases/transactions/session-2-anomalies/concept-3-phantoms) |
| Lost update | Two read-modify-write cycles overwrite each other | [Concept 4](/blogs/databases/transactions/session-2-anomalies/concept-4-lost-updates) |
| Write skew | Two transactions check a rule across rows and each changes a different row, breaking it together | [Concept 5](/blogs/databases/transactions/session-2-anomalies/concept-5-write-skew) |

Isolation levels decide which of these each engine allows; [Session 3](/blogs/databases/transactions/session-3-isolation-levels/lab) explains the mechanisms. Default levels: PostgreSQL **READ COMMITTED**, MySQL **REPEATABLE READ**, MongoDB **snapshot** inside a transaction (outside one, each read sees committed data at its own moment).

| Term | Meaning |
|---|---|
| T1, T2 | Two sessions, started in this order; the steps below are in time order |
| Uncommitted change | Written by a transaction that has not committed yet |
| **✓ Committed value** | T2 read 1,000.00, the last committed balance |
| **✗ Dirty value** | T2 read 0.00, a value T1 later rolled back |

<Pitfall>
`READ UNCOMMITTED` is sometimes used in MySQL (or `WITH (NOLOCK)` in SQL Server) to "avoid locks" in reports. InnoDB reads at READ COMMITTED and REPEATABLE READ do not take locks either; they read old versions from the undo log. Dirty reads buy almost nothing in InnoDB and can return totals that never existed.
</Pitfall>

## Real-world scenario: the report that showed a negative stock

A dashboard query in MySQL runs at `READ UNCOMMITTED` "for speed". During a bulk import that later fails and rolls back, it shows 3,000 SKUs at zero stock; the purchasing team reorders. Nothing in the database ever committed those zeros.

| Fix | Effect |
|---|---|
| Use the default level (REPEATABLE READ) or READ COMMITTED | Consistent reads from undo, still without locks |
| Point reports at a replica | Removes load from the primary without dirty data |

## Key takeaways

1. A dirty read sees a change before its transaction commits; if it rolls back, the reader saw a value that never existed.
2. Only MySQL `READ UNCOMMITTED` showed it in the lab (0.00).
3. PostgreSQL accepts `READ UNCOMMITTED` but runs it as `READ COMMITTED` (1,000.00).
4. MongoDB transaction writes are invisible until commit, even to read concern `available`.
5. InnoDB consistent reads take no locks, so `READ UNCOMMITTED` is rarely worth it.
