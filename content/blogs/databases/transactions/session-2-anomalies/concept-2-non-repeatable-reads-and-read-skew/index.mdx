<Tldr>
At **READ COMMITTED** each statement takes a fresh snapshot of committed data, so two reads in one transaction can disagree. Reading account 11 twice while T2 committed a new balance returned **1,000.00 then 500.00** in PostgreSQL and MySQL at READ COMMITTED and in MongoDB outside a transaction: a **non-repeatable read**. Its multi-row cousin is **read skew**: T1 read account 40 (1,000.00), T2 moved 100 from 40 to 41 and committed, T1 read account 41 (1,100.00) and saw a total of **2,100** that never existed. One snapshot for the whole transaction (PostgreSQL and MySQL **REPEATABLE READ**, a MongoDB **transaction**) returned 1,000.00 twice and a total of 2,000.
</Tldr>

## Statement snapshot vs transaction snapshot

| Level | Snapshot taken | Two reads of the same row |
|---|---|---|
| READ COMMITTED (PostgreSQL default) | At the start of **each statement** | Can differ |
| REPEATABLE READ (MySQL default) | At the **first read** of the transaction | Always equal |
| MongoDB outside a transaction | Per operation | Can differ |
| MongoDB transaction (`snapshot`) | At the first operation of the transaction | Always equal |

| Term | Meaning |
|---|---|
| Non-repeatable read | The same row, read twice in one transaction, has changed |
| Read skew | Two different rows read at different moments, so together they reflect no single committed state |
| **✓ Consistent** | Every read in T1 reflects the same committed state |
| **✗ Inconsistent** | T1's reads mix states from before and after T2's commit |

MySQL's REPEATABLE READ has a catch for **writes**: an `UPDATE` or a locking read (`SELECT … FOR UPDATE`) inside the transaction reads the **latest committed** row, not the snapshot. [Concept 3](/blogs/databases/transactions/session-2-anomalies/concept-3-phantoms) shows the consequence.

<Pitfall>
READ COMMITTED is the PostgreSQL default, and most ORMs run each request in it. Any code that reads related rows in **separate** statements and combines them (a balance sheet, "total of the order and its items", a consistency check) can see read skew. Use one statement, or REPEATABLE READ for that transaction.
</Pitfall>

## Real-world scenario: the audit that found missing money

A nightly audit job in PostgreSQL sums balances branch by branch with ten separate queries, at the default READ COMMITTED, while transfers between branches keep running. Some nights the grand total is off by a few thousand. Nothing is wrong with the data: each branch was summed at a different moment.

| Fix | Effect |
|---|---|
| `BEGIN ISOLATION LEVEL REPEATABLE READ` around the ten queries | All ten see one snapshot |
| One `SELECT branch, sum(balance) … GROUP BY branch` | One statement, one snapshot, even at READ COMMITTED |
| MongoDB: run the reads in one transaction, or one aggregation | Same snapshot for all |

## Key takeaways

1. READ COMMITTED takes a new snapshot per statement: two reads of one row returned 1,000.00 then 500.00.
2. Read skew mixes two moments across rows: a total of 2,100 that never existed.
3. REPEATABLE READ (PostgreSQL, MySQL) and MongoDB transactions keep one snapshot: 1,000.00 twice, total 2,000.
4. MongoDB reads outside a transaction behave like READ COMMITTED.
5. A single statement is always consistent with itself, even at READ COMMITTED.
