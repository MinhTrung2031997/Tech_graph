<Tldr>
WiredTiger stores each document's committed versions as an **update chain** hanging off the on-disk value in cache, newest first, each update stamped with a **commit timestamp**. A reader with a snapshot timestamp walks the chain until it finds a version committed at or before its timestamp; versions evicted from cache go to the **history store** (`WiredTigerHS.wt`). After a bulk write of **30,000** updates to account 1 (481 ms), a transaction that had started before them still read version **1**: 100 reads took **84 ms** instead of 30 ms, while a fresh reader took 27 ms; the history store received **0** inserts, so the whole chain was still in memory. Instead of letting old snapshots grow history without bound, MongoDB limits it in time: a read with `atClusterTime` 290 s in the past returned the old version, 400 s back failed with **SnapshotTooOld** (`minSnapshotHistoryWindowInSeconds` = 300), and a transaction left open for 130 s was aborted by the `abortExpiredTransactions` job (`transactionLifetimeLimitSeconds` = 60; one open for 70 s still committed).
</Tldr>

## Versions in memory, stamped with time

| Term | Meaning |
|---|---|
| Update chain | List of updates to one key, newest first, attached to the page in cache |
| Commit timestamp | Cluster time at which an update committed (the same timeline as the oplog) |
| Read timestamp | The point in time a snapshot reads at; versions committed later are skipped |
| History store | WiredTiger table holding older versions when a page is evicted or written by a checkpoint |
| `minSnapshotHistoryWindowInSeconds` | How much history (in seconds) the server keeps for snapshot reads; default 300 |
| `transactionLifetimeLimitSeconds` | Transactions older than this are aborted; default 60 |
| **✓ Version found** | A version committed at or before the read timestamp |
| **✗ Refused** | SnapshotTooOld or NoSuchTransaction |

| | PostgreSQL | InnoDB | WiredTiger |
|---|---|---|---|
| Visibility by | Transaction ids (xmin / xmax) | Transaction ids (read view) | Timestamps (plus transaction ids inside the server) |
| Old versions | In the table | Undo log | Update chain → history store |
| Bound on history | None (VACUUM waits) | None (purge waits) | Time: 300 s window, 60 s transactions |

<Pitfall>
MongoDB protects itself from long transactions by **killing them**, not by slowing everyone down. A batch job that does a lot of work inside one transaction can run fine in testing and start failing with `NoSuchTransaction` once production data makes it take longer than about a minute. Split long work into many short transactions, and do not raise `transactionLifetimeLimitSeconds` to hide the problem: that brings back the cache pressure the limit exists to prevent.
</Pitfall>

## Real-world scenario: the nightly reconciliation

A reconciliation job reads 2 million orders and their payments in one transaction so the totals are consistent.

| Approach | Result |
|---|---|
| One transaction for everything | Aborted with NoSuchTransaction once it outlives the limit (the lab's transaction survived 70 s, not 130 s) |
| Many short transactions | Each one consistent, but the totals may mix moments |
| One `atClusterTime` shared by many short reads (each a snapshot read at the same timestamp, outside a transaction) | Consistent totals, as long as the whole job finishes within the 300 s window |
| Read from a hidden secondary or a backup snapshot | No pressure on the primary; consistent to that point in time |

## Key takeaways

1. WiredTiger keeps a document's recent versions as an update chain in cache, each with a commit timestamp; older ones move to the history store.
2. A snapshot reads at a timestamp and walks back to the newest version committed before it: 2.8× the read cost after 30,000 updates, all in memory.
3. History is bounded in time: `minSnapshotHistoryWindowInSeconds` (300 s) for snapshot reads, SnapshotTooOld beyond it.
4. Transactions older than `transactionLifetimeLimitSeconds` (60 s) are aborted by a periodic job (70 s survived, 130 s did not).
5. Long work belongs in many short transactions or in timestamped snapshot reads, not in one big transaction.
