<Tldr>
Every engine can only throw away an old version once **no open snapshot** could still read it, so the **oldest** transaction decides what cleanup may do for the whole database (PostgreSQL) or server (InnoDB). In PostgreSQL, one session left **idle in transaction** while 10,000 accounts were updated three times: `VACUUM` reported **30,000 dead tuples "not yet removable"** and the table grew from **74 to 295 pages**; after the session committed, `VACUUM` removed all 30,000 and three more rounds of updates fit in the same 295 pages. In InnoDB, one open read view let the **history list** reach **30,007** (Concept 2). MongoDB caps the damage by **aborting** transactions older than 60 s (Concept 3). PostgreSQL can end such sessions itself (`idle_in_transaction_session_timeout`, `transaction_timeout`: both killed the lab session after 2 s); MySQL has no idle-transaction timeout, only `wait_timeout` for idle connections (default 8 hours), which closed a 2 s test session and rolled its update back.
</Tldr>

## The horizon

| Engine | What the oldest transaction holds back | Where it shows | Built-in limit |
|---|---|---|---|
| PostgreSQL | VACUUM and page pruning of dead tuples newer than its snapshot xmin (in that database) | `pg_stat_activity.backend_xmin`, `VACUUM VERBOSE` "dead but not yet removable" | `idle_in_transaction_session_timeout`, `transaction_timeout` (17+), `statement_timeout` (default 0 = off) |
| InnoDB | Purge of undo logs (server-wide) | `trx_rseg_history_len`, `information_schema.innodb_trx.trx_started` | None for idle transactions; `wait_timeout` closes idle connections (28,800 s by default) |
| MongoDB | Update chains and history store entries newer than its read timestamp | `$currentOp` `transaction.timeOpenMicros` | `transactionLifetimeLimitSeconds` (60 s) aborts it |

| Term | Meaning |
|---|---|
| Cleanup horizon | The oldest snapshot still open; versions replaced before it are removable, versions replaced after it are not |
| Idle in transaction | A session that ran `BEGIN` and some statements and is now waiting for the client, holding its snapshot |
| **✓ Space reused** | Cleanup removed the old versions; new versions fill the freed space |
| **✗ Not removable** | Old versions must stay because a snapshot might read them |

<Pitfall>
The classic culprit is not a long query but an **idle** transaction: an application that opens a transaction, then waits for a user, a queue message or an HTTP call, or a connection pool that returns a connection with a transaction still open. It uses no CPU and holds no obvious locks, yet in PostgreSQL and InnoDB it stops cleanup for everyone. Alert on transaction age, not just query time.
</Pitfall>

## Real-world scenario: the growing table nobody writes more to

A PostgreSQL `orders` table receives a steady update rate, but its size doubles in a week and queries slow down. Autovacuum runs every few minutes and logs that it removed almost nothing.

| Step | Query | Finding |
|---|---|---|
| Who holds the horizon | `SELECT pid, state, now() - xact_start, backend_xmin FROM pg_stat_activity ORDER BY xact_start LIMIT 5;` | A worker "idle in transaction" for 6 days |
| Confirm | `VACUUM (VERBOSE) orders;` | "N are dead but not yet removable", removable cutoff equal to that backend_xmin |
| Fix now | `SELECT pg_terminate_backend(pid);` then let autovacuum run | Dead tuples removed; size stops growing |
| Prevent | `ALTER ROLE app SET idle_in_transaction_session_timeout = '60s';` and fix the code path | Idle transactions cannot outlive a minute |

Other horizon holders to check in PostgreSQL: prepared transactions (`pg_prepared_xacts`), replication slots (`pg_replication_slots.xmin`) and standbys with `hot_standby_feedback` on.

## Key takeaways

1. The oldest open snapshot sets the cleanup horizon: nothing replaced after it can be removed.
2. PostgreSQL: one idle transaction kept 30,000 dead tuples; the table grew from 74 to 295 pages and stayed that size after cleanup.
3. InnoDB: an open read view let the history list reach 30,007; purge cleared it within 5 s of the commit.
4. MongoDB aborts transactions past their lifetime instead of keeping history for them.
5. Use timeouts (`idle_in_transaction_session_timeout`, `transaction_timeout`, `wait_timeout`) and alert on transaction age.
