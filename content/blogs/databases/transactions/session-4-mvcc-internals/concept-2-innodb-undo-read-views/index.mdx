<Tldr>
InnoDB keeps **one** version of each row in the clustered index: the newest. Every change also writes an **undo record** describing how to go back, and the row's hidden **DB_ROLL_PTR** points to it. A **read view** (taken at the first consistent read, Session 3) lists which transactions it may see; when a row was changed by a transaction the read view cannot see, InnoDB applies undo records until it reaches a visible version. In the lab, account 1 was updated **30,000** times (one commit each) while T1 kept an older read view: T1's read of that row went from **0.088 ms** to **14.8 ms**, a fresh reader still took **0.14 ms**. Undo can only be purged behind the **oldest** read view: the history list length went from **22** to **30,007** while T1 was open and fell to **0** within 5 s after it committed.
</Tldr>

## Rows in place, history aside

| Term | Meaning |
|---|---|
| `DB_TRX_ID` | Hidden 6-byte column: id of the last transaction that modified the row |
| `DB_ROLL_PTR` | Hidden 7-byte column: pointer to the undo record holding the previous version |
| Undo record | Enough information to rebuild the previous version (old column values, previous roll pointer) |
| Undo chain | Newest row → undo record → older undo record → … |
| Read view | Snapshot of active transaction ids at creation: ids below its low limit are visible, ids at or above its high limit and ids in its active list are not |
| History list | Committed transactions whose update undo is not yet purged (`trx_rseg_history_len`) |
| Purge | Background threads that delete undo (and delete-marked records) no read view can need |
| **✓ Version found** | A visible version was returned |

Unlike PostgreSQL (Concept 1), an UPDATE does not create a second row: the table and its indexes stay the same size, and the cost of history moves to the undo tablespaces and to readers of old versions.

<Pitfall>
In InnoDB, **rollback is expensive** and **commit is cheap**, the opposite of PostgreSQL. Updating all 100,000 rows of `jobs` took 339 ms; `COMMIT` then took 20 ms, but `ROLLBACK` took **139 ms**, because it applies the undo record of every changed row. In PostgreSQL the same `ROLLBACK` took **0.9 ms** (mark the xid aborted, Concept 1). Killing a transaction that updated millions of rows does not free the server immediately: it starts a rollback proportional to the work done.
</Pitfall>

## Real-world scenario: the slow replica report

A reporting job on a MySQL server opens a transaction at 08:00 for an export and is still open at 11:00. Meanwhile a hot table receives 2,000 updates per second.

| Symptom | Cause |
|---|---|
| History list length in the millions, undo tablespaces growing | Purge cannot pass the 08:00 read view |
| Queries on hot rows get slower over the morning for some sessions | Readers with old read views walk long undo chains (14.8 ms for 30,000 versions in the lab) |
| Everything recovers minutes after the job is killed | Purge catches up (0 within 5 s for 30,000 in the lab) |

Find it: `SELECT trx_id, trx_started, trx_mysql_thread_id FROM information_schema.innodb_trx ORDER BY trx_started LIMIT 5;` and watch `trx_rseg_history_len` (Concept 4).

## Key takeaways

1. InnoDB stores the newest row in place and older versions in the undo log, linked by DB_ROLL_PTR.
2. A read view decides visibility by transaction id; an invisible row is rebuilt by applying undo records.
3. Old read views pay for every newer version: 0.088 ms → 14.8 ms after 30,000 updates; fresh readers do not.
4. Purge frees undo only behind the oldest read view: history list 30,007 while T1 was open, 0 after.
5. Read-only transactions get no real transaction id; rollback applies undo (139 ms for 100,000 rows vs 0.9 ms in PostgreSQL).
