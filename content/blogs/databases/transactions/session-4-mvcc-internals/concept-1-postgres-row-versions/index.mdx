<Tldr>
Every PostgreSQL tuple carries **xmin** (the transaction that created it) and **xmax** (the one that deleted or replaced it). An UPDATE by transaction 2343343 set the old version's xmax to 2343343 and wrote a new version with xmin 2343343 on another page; both stayed in the table. A reader's **snapshot**, printed as `2343357:2343365:2343357,2343362`, lists the oldest running transaction, the next transaction id, and the transactions still running; a version is visible if its xmin committed **before** the snapshot and its xmax did not. After a **rollback** nothing is undone: the new version just becomes dead. Readers record what they learn from the commit log as **hint bits** (infomask 0x0802 → 0x0902 after the first `SELECT`), and **VACUUM FREEZE** marks old tuples as visible to everyone (0x0B02) so that 32-bit transaction ids can wrap around safely.
</Tldr>

[Session 3](/blogs/databases/transactions/session-3-isolation-levels/concept-1-when-the-snapshot-starts) used snapshots as a black box. This session opens them, one engine per concept. The index-side cost of PostgreSQL's design (new index entries for non-HOT updates) is covered in [Indexing Session 6](/blogs/databases/indexing/session-6-engine-differences/concept-1-postgres-mvcc).

## The tuple header

| Field | Meaning |
|---|---|
| `xmin` | Transaction id (xid) that inserted this version |
| `xmax` | xid that deleted it, replaced it (UPDATE) or locked it; 0 if none |
| `t_ctid` | Pointer to itself, or to the newer version after an UPDATE |
| `t_infomask` | Flags, including hint bits: `0x0100` xmin committed, `0x0200` xmin aborted (both = frozen), `0x0400` xmax committed, `0x0800` xmax invalid/aborted, `0x2000` this version was produced by an UPDATE |
| Snapshot `xmin:xmax:xip` | Oldest xid still running; first xid not yet assigned; list of xids running when the snapshot was taken |
| `pg_xact` | The commit log: 2 bits per xid (in progress, committed, aborted) |

Seen from SQL, `xmin`, `xmax` and `ctid` are hidden columns: `SELECT xmin, xmax, ctid, balance FROM accounts WHERE id = 1` returned `2343333 | 0 | (0,1) | 1000.00`. `pageinspect` shows every version on a page, including the ones no snapshot can see.

<Pitfall>
Transaction-id wraparound is the one MVCC problem that stops a PostgreSQL database. If freezing falls behind (autovacuum blocked by a long transaction, disabled, or too slow), `age(datfrozenxid)` keeps climbing, PostgreSQL first warns and finally refuses new transactions until a VACUUM catches up. Watch `SELECT datname, age(datfrozenxid) FROM pg_database` and alert well before 200 million.
</Pitfall>

## Real-world scenario: the read that writes

After a nightly bulk load of 50 million rows, the first morning report is slow and the server writes heavily although the report only reads.

| Cause | Evidence | Fix |
|---|---|---|
| The report is the first reader: it sets hint bits on every page and dirties them | Pages change infomask 0x0802 → 0x0902; checkpoints write the whole table again | `VACUUM (FREEZE, ANALYZE)` right after the load, or load with `COPY … FREEZE` into a table created in the same transaction |
| Later, autovacuum freezes the same pages again | Write spikes when tables reach the freeze age | Freezing right after the load does both jobs at once |

## Comparison with the other engines

| | PostgreSQL | InnoDB ([Concept 2](/blogs/databases/transactions/session-4-mvcc-internals/concept-2-innodb-undo-read-views)) | WiredTiger ([Concept 3](/blogs/databases/transactions/session-4-mvcc-internals/concept-3-wiredtiger-history)) |
|---|---|---|---|
| Where old versions live | In the table, next to new ones | Undo log | Update chain in memory, then history store |
| What the newest-version reader does | Follows t_ctid forward | Reads the row in place | Reads the newest entry of the chain |
| What an old snapshot does | Skips invisible tuples | Rebuilds the old version from undo | Walks the chain back |
| Rollback | Mark xid aborted (instant) | Apply undo (work proportional to changes) | Discard uncommitted updates |
| Cleanup | VACUUM / pruning | Purge thread | Eviction, history store cleanup |

## Key takeaways

1. Each tuple records its creator (xmin) and deleter (xmax); an UPDATE writes a new tuple and sets xmax on the old one.
2. A snapshot is `xmin:xmax:running-list`; a version is visible if its creator committed before the snapshot and its deleter did not.
3. Rollback is instant: the aborted versions become dead tuples for VACUUM.
4. Hint bits cache commit-log answers in the tuple, so the first read of new data writes pages.
5. Freezing retires old xids; falling behind leads to wraparound protection shutting writes down.
