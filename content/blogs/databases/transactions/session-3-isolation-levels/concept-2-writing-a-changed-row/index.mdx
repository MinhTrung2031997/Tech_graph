<Tldr>
T1 reads balance **1000**, T2 commits −100 (**900**), then T1 writes. What happens depends on engine and level. **PostgreSQL READ COMMITTED**: a relative `UPDATE … balance − 50` works on the newest row (**850**, correct), but writing a value computed from the stale read (`SET balance = 950`) loses T2's update (**950**). A blocked `UPDATE` re-checks its `WHERE` against the new row and can end up updating **0 rows**. **PostgreSQL REPEATABLE READ** refuses: `ERROR: could not serialize access due to concurrent update`. **MySQL REPEATABLE READ** does not refuse: the `UPDATE` writes on the newest row (850, or 950 with an absolute value), and an `UPDATE` of branch B01 touched **1,001** rows although the snapshot showed 1,000. A **MongoDB transaction** fails with `WriteConflict` (labelled `TransientTransactionError`) after **7 ms**, without waiting.
</Tldr>

## The question each engine answers

A write cannot go to an old version: it must change the **newest** version of the row. When the transaction's snapshot is older than that version, the engine has three choices:

| Choice | Who does it | Consequence |
|---|---|---|
| Write on the newest version | PostgreSQL READ COMMITTED, MySQL READ COMMITTED **and REPEATABLE READ** | No error; relative updates stay correct; values computed from the stale read overwrite the other commit (lost update) |
| Abort the transaction | PostgreSQL REPEATABLE READ and SERIALIZABLE ("first updater wins"), MongoDB transactions | The application must retry the whole transaction |
| Make the other transaction wait earlier | MySQL SERIALIZABLE (shared locks on reads, Concept 3) | Deadlocks instead of silent overwrites |

| Term | Meaning |
|---|---|
| Relative update | `SET balance = balance - 50`: the arithmetic runs on whatever version the UPDATE finds |
| Absolute update | `SET balance = 950`, where 950 was computed by the application from an earlier read |
| Re-check (EvalPlanQual) | PostgreSQL READ COMMITTED: after waiting for a row lock, re-evaluate the `WHERE` on the newest version |
| First updater wins | If a row was changed by a transaction that committed after my snapshot, my write fails |
| **✓ Correct balance** | 850: both changes applied |
| **✗ Error** | The engine aborts the write (40001 / WriteConflict) |
| **✗ Lost update** | 950: T2's −100 disappeared |

The test: accounts id 1 starts at 1000. T1 begins, reads it, sleeps 2 s, writes. T2 starts at 1 s and commits `balance − 100`.

## Summary of the same test

| T1 reads 1000, T2 commits 900, T1 writes | PG RC | PG RR | MySQL RR | MongoDB transaction |
|---|---|---|---|---|
| `balance − 50` | ✓ 850 | ✗ 40001 | ✓ 850 | ✗ WriteConflict |
| `SET balance = 950` (computed in app) | ✗ 950, lost update | ✗ 40001 | ✗ 950, lost update | ✗ WriteConflict |
| `… WHERE balance = 1000` | ✓ 0 rows | ✗ 40001 | ✓ 0 rows | ✗ WriteConflict |

<Pitfall>
"We run REPEATABLE READ, so lost updates cannot happen" is true in PostgreSQL and false in MySQL. The same read-then-write code that fails safely with 40001 in PostgreSQL silently overwrites in InnoDB. In MySQL, protect read-modify-write with `SELECT … FOR UPDATE`, a compare-and-set `WHERE`, or a relative `UPDATE`.
</Pitfall>

## Real-world scenario: the stock reservation

A checkout service reads `stock`, checks `stock >= qty` in code, then writes `stock = stock_read - qty`. In production two checkouts of the last item both succeed and stock ends at 0 instead of −1 being rejected.

| Engine / level | What happens (same mechanism as the balance test above) | Fix |
|---|---|---|
| PostgreSQL RC, MySQL RC / RR | Both read 1, both wrote 0: one sale is not reflected (lost update) | One statement: `UPDATE inventory SET stock = stock - 1 WHERE sku = ? AND stock >= 1`, check the row count |
| PostgreSQL RR | The second checkout got 40001 | Retry the transaction (Concept 5) |
| MongoDB | The second transaction got WriteConflict | `withTransaction()` retries; or a single `updateOne` with `stock: { $gte: 1 }` in the filter |

## Why this matters for transactions

| Later topic | Why this concept matters |
|---|---|
| Concept 3: write skew | Conflicts on the **same** row are caught; conflicts across different rows are not |
| Concept 4: locking reads | `FOR UPDATE` makes T2 wait instead of conflicting later |
| Concept 5: cost under contention | Every 40001 or WriteConflict is a retry |
| Session 7: application patterns | Relative updates, compare-and-set and version columns |

## Key takeaways

1. A write always targets the newest version; the engines differ in what they do when the snapshot is older.
2. PostgreSQL READ COMMITTED writes on the newest row and re-checks `WHERE` after waiting; REPEATABLE READ aborts with 40001.
3. MySQL REPEATABLE READ never aborts for this: relative updates stay correct, absolute ones lose updates, and UPDATE can touch rows the snapshot did not show.
4. MongoDB transactions abort with WriteConflict (TransientTransactionError) within milliseconds; single writes wait and retry internally.
5. Relative updates and compare-and-set conditions are correct at every level.
