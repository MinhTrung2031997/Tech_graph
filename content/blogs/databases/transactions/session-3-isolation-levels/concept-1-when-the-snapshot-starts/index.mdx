<Tldr>
All three engines use MVCC, so an isolation level is mostly a rule about **which snapshot a read uses**. In **READ COMMITTED** every statement takes a fresh snapshot: T1 read balance 1000, T2 committed −100, T1's next read returned **900**. In **REPEATABLE READ** (PostgreSQL, MySQL) and in a **MongoDB transaction**, the whole transaction reads one snapshot: the second read returned **1000** again, and a new row inserted by T2 stayed invisible (count 1000, not 1001). The snapshot starts at the transaction's **first read**, not at `BEGIN`: a transaction that waited 2 s before its first `SELECT` saw T2's change (900) in all three engines, unless MySQL is told `START TRANSACTION WITH CONSISTENT SNAPSHOT` (1000).
</Tldr>

[Session 2](/blogs/databases/transactions/session-2-anomalies/concept-1-dirty-reads) reproduced the anomalies. This session asks which **level** prevents each one, engine by engine. The first rule to learn is when the snapshot is taken.

## The levels each engine really has

| Level (SQL standard name) | PostgreSQL 17 | MySQL 8.4 InnoDB | MongoDB 8.0 |
|---|---|---|---|
| READ UNCOMMITTED | Accepted, behaves as READ COMMITTED | Reads the newest version, even uncommitted | No equivalent |
| READ COMMITTED | **Default.** New snapshot per statement | New snapshot per consistent read | Single operations outside a transaction (`readConcern: "local"` / `"majority"`) |
| REPEATABLE READ | Snapshot isolation: one snapshot per transaction | **Default.** One snapshot for plain `SELECT`s; locking reads and writes see the newest committed row (Concept 4) | Every multi-document transaction: snapshot isolation |
| SERIALIZABLE | Snapshot isolation + conflict detection (SSI, Concept 3) | REPEATABLE READ + every plain `SELECT` becomes `FOR SHARE` (Concept 3) | No equivalent |

| Term | Meaning |
|---|---|
| Snapshot | The set of transactions whose changes a read can see: everything committed before the snapshot was taken, plus the transaction's own changes |
| Statement-level snapshot | READ COMMITTED: each statement takes a new snapshot, so two reads in one transaction can disagree |
| Transaction-level snapshot | REPEATABLE READ / snapshot isolation: the first read takes the snapshot and every later read reuses it |
| Consistent read | MySQL's name for a plain `SELECT` that reads from a snapshot (no locks) |
| **✓ Stable read** | The second read returns what the first returned |
| **✗ Value changed** | The second read sees another transaction's commit (non-repeatable read or phantom) |

The test in every engine: T1 reads account 1 (balance 1000), sleeps 2 s and reads again; T2 starts 1 s later and commits `balance − 100`.

## What each level prevents (measured)

| Anomaly ([Session 2](/blogs/databases/transactions/session-2-anomalies/concept-1-dirty-reads)) | PG RC | PG RR | PG SERIALIZABLE | MySQL RC | MySQL RR | MySQL SERIALIZABLE | MongoDB transaction |
|---|---|---|---|---|---|---|---|
| Dirty read | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Non-repeatable read | ✗ (900) | ✓ (1000) | ✓ | ✗ (900) | ✓ for plain reads (1000); ✗ for locking reads (900) | ✓ | ✓ (1000) |
| Phantom | ✗ (1001) | ✓ (1000) | ✓ | ✗ | ✓ for plain reads; ✗ for UPDATE (1,001 rows updated, Concept 2) | ✓ | ✓ |
| Lost update (read, then write) | ✗ | ✓ error 40001 (Concept 2) | ✓ | ✗ | ✗ applied to the newer row (Concept 2) | ✓ deadlock (Concept 3) | ✓ WriteConflict (Concept 2) |
| Write skew | ✗ | ✗ (sum 200) | ✓ error 40001 (Concept 3) | ✗ | ✗ (sum 200) | ✓ deadlock 1213 | ✗ (sum 200) |

✓ = prevented, ✗ = allowed. Only the two SERIALIZABLE levels stopped write skew; every "prevented" in the bottom two rows works by **aborting** a transaction, which the application must retry (Concept 5).

<Pitfall>
`BEGIN` does not freeze the data. In all three engines the snapshot is taken by the first read, so code that opens a transaction, calls another service, and only then reads, sees the database as it was **after** the call. If several reads must reflect one moment, issue them all inside the transaction and, in MySQL, use `START TRANSACTION WITH CONSISTENT SNAPSHOT` when the read view must exist from the start.
</Pitfall>

## Real-world scenario: the monthly statement

A report job builds a customer statement with three queries: opening balance, list of movements, closing balance. Under READ COMMITTED a transfer committed between the queries makes the statement not add up (opening + movements ≠ closing).

| Option | Effect |
|---|---|
| Run the three queries in one REPEATABLE READ transaction (PostgreSQL, MySQL) | All three see one snapshot; the statement is consistent |
| `START TRANSACTION WITH CONSISTENT SNAPSHOT` (MySQL) | Same, with the snapshot fixed at the start |
| MongoDB: one transaction with `readConcern: "snapshot"` (60 s limit, Session 8) or one aggregation | One snapshot; very long reports belong on a secondary or in a nightly export |
| `READ ONLY` transaction (PostgreSQL `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`) | Documents intent; a read-only transaction can never fail with a serialization error at this level |

## Key takeaways

1. READ COMMITTED: a new snapshot per statement (PostgreSQL default). REPEATABLE READ / snapshot isolation: one snapshot per transaction (MySQL default, every MongoDB transaction).
2. In the lab: RC read 1000 then 900; RR and MongoDB transactions read 1000 twice and did not see a newly inserted row.
3. The snapshot starts at the first read, not at `BEGIN`; MySQL's `WITH CONSISTENT SNAPSHOT` is the exception.
4. Snapshot isolation prevents non-repeatable reads and phantoms for plain reads, but not write skew.
5. Outside a transaction, every MongoDB operation reads on its own; read concern is about durability, not repeatability.
