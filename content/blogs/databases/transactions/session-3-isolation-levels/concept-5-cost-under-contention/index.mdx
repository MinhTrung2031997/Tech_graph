<Tldr>
The same transfer (read one balance, move 1.00 between two accounts in one `UPDATE`) was run by **8 concurrent clients** at each level. On **10 hot accounts**, PostgreSQL READ COMMITTED committed every transaction (**0** failures): conflicting transactions simply **waited** for row locks. REPEATABLE READ and SERIALIZABLE **aborted** about **70%** of attempts with 40001, and even with up to 10 tries per transaction **3.8–5.7%** still failed and ≈ 60% needed at least one retry. MySQL READ COMMITTED and REPEATABLE READ: **0** failures; SERIALIZABLE: **2,302 of 8,000** transfers deadlocked. MongoDB transactions: **3,743 of 8,000** hit WriteConflict; with `withTransaction()` all 8,000 committed after **12,194** attempts, in about twice the time. Spread over **10,000** accounts the same workload had **0.2–0.3%** failures in PostgreSQL, **0** deadlocks in MySQL and **7** conflicts in MongoDB. Contention, not the level alone, sets the price.
</Tldr>

## Waiting vs aborting

| Level | When two transactions touch the same row | Application must |
|---|---|---|
| PostgreSQL READ COMMITTED, MySQL READ COMMITTED / REPEATABLE READ | The second waits for the row lock, then continues on the newest version | Nothing (but beware lost updates, Concept 2) |
| PostgreSQL REPEATABLE READ / SERIALIZABLE | The second waits, then **aborts** with 40001 if the first committed | Retry the whole transaction |
| MySQL SERIALIZABLE | Shared locks from reads make writers wait on each other: deadlock | Retry on 1213 |
| MongoDB transaction | The second **aborts at once** with WriteConflict | Retry (`withTransaction()` does it) |

| Term | Meaning |
|---|---|
| Hot rows | A few rows that most transactions touch (popular product, central account, counter) |
| Failure rate | Aborted attempts / all attempts, with no retries |
| `--max-tries` | pgbench option: retry a transaction up to N times on serialization failures and deadlocks |
| **✓ Committed** | The transfer was applied |
| **✗ Aborted** | 40001, deadlock 1213 or WriteConflict |

The workload ([lab](/blogs/databases/transactions/session-3-isolation-levels/lab) has the scripts): pick account `a` at random and a different account `b`, then `BEGIN; SELECT balance … WHERE id = a; UPDATE … WHERE id IN (a, b); COMMIT`. A single `UPDATE` touches both rows in primary-key order, so transfers never deadlock each other by lock order: every failure below is caused by the isolation level. The total balance stayed exactly 10,000.00 after every run. Timings are from a laptop shared with other workloads: compare the failure counts, not the throughput.

## All results

| Engine, level | Hot (10 accounts): committed / failed, no retry | Spread (10,000 accounts) |
|---|---|---|
| PostgreSQL READ COMMITTED | all / 0 | all / 0 |
| PostgreSQL REPEATABLE READ | 30.6% / **69.4%** (40001); with 10 tries 3.8% still fail | 0.23% fail |
| PostgreSQL SERIALIZABLE | 29.9% / **70.1%** (40001); with 10 tries 5.7% still fail | 0.26% fail |
| MySQL READ COMMITTED | 8,000 / 0 | – |
| MySQL REPEATABLE READ | 8,000 / 0 | 8,000 / 0 |
| MySQL SERIALIZABLE | 5,698 / **2,302** (deadlock) | 8,000 / 0 |
| MongoDB transaction | 4,257 / **3,743** (WriteConflict); `withTransaction`: 8,000 after 12,194 attempts | 7,993 / 7 |

<Pitfall>
Moving a hot workload from READ COMMITTED to REPEATABLE READ or SERIALIZABLE "for safety" without retry code turns waits into errors: in this test, 7 of 10 transfers started failing. Raise the level where a rule needs it (Concept 3), keep hot-row updates short and relative, and put a bounded retry loop with backoff around every transaction that can get 40001, 1213 or TransientTransactionError.
</Pitfall>

## Real-world scenario: the flash sale

A flash sale sends thousands of orders at one product row.

| Choice | Effect at the hot row |
|---|---|
| `UPDATE inventory SET stock = stock - 1 WHERE sku = ? AND stock > 0` in READ COMMITTED | Orders queue on the row lock and each re-checks `stock > 0` (Concept 2): correct, no retries |
| Same at REPEATABLE READ / SERIALIZABLE (PostgreSQL) or in a MongoDB transaction | Most attempts abort and retry; retries add load exactly when the row is hottest |
| Split the counter (e.g. 10 stock buckets per SKU) | Fewer conflicts per row; reads sum the buckets |

## Key takeaways

1. Under contention, READ COMMITTED waits; snapshot-based levels and MongoDB abort.
2. On 10 hot rows: PostgreSQL RR/SERIALIZABLE ≈ 70% aborts, MySQL SERIALIZABLE 29% deadlocks, MongoDB 47% WriteConflicts; READ COMMITTED and MySQL RR: 0.
3. Retries recover most failures but multiply work (MongoDB: 12,194 attempts for 8,000 transfers), and some still fail after 10 tries.
4. Spread over 10,000 rows, the same levels failed on under 0.3% of transactions.
5. Choose the level per transaction: the strongest level only where a multi-row rule needs it.
