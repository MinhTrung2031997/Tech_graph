<Tldr>
Rule: accounts 1 and 2 are a joint pair whose **combined balance must stay ≥ 1000**. T1 and T2 both read the sum (**2000**), each decides a 900 withdrawal is fine, and each withdraws from a **different** account. No row is written twice, so snapshot isolation sees no conflict: in PostgreSQL REPEATABLE READ, MySQL REPEATABLE READ and MongoDB transactions both committed and the sum ended at **200**. **PostgreSQL SERIALIZABLE** aborted T1 at commit (`could not serialize access due to read/write dependencies among transactions`, sum **1100**). It tracks reads with **SIRead locks** (tuples, index pages, or the whole table after a sequential scan), and coarse locks produce **false positives**: two transactions reading disjoint id ranges failed once three of their rows shared a heap page. **MySQL SERIALIZABLE** makes every `SELECT` in a transaction a shared lock, so the two withdrawals **deadlocked** (error 1213) instead. **MongoDB** has no serializable level: making each transaction also write the document it read turned the skew into a WriteConflict.
</Tldr>

## Why snapshot isolation misses it

| Term | Meaning |
|---|---|
| Write skew | Two transactions read overlapping data, then write **different** rows; each write is valid alone, together they break a rule |
| Serializable | The result equals some order of running the transactions one after another |
| SSI | Serializable Snapshot Isolation (PostgreSQL): snapshot isolation plus tracking of read/write dependencies; aborts a transaction that could make the order impossible |
| SIRead lock | PostgreSQL's record of "this transaction read here"; never blocks anyone, only used to detect conflicts |
| Pivot | A transaction with a dependency in and out (T_in → pivot → T_out); SSI aborts one transaction of such a pattern |
| Materialize the conflict | Make the transactions write a common row/document, so ordinary write-conflict detection catches them |
| **✓ Rule holds** | Combined balance ≥ 1000 (one withdrawal rejected) |
| **✗ Rule broken** | Combined balance 200 |

Neither transaction overwrote the other's row, so "first updater wins" (Concept 2) has nothing to catch. In any serial order the second transaction would have seen 1100 and refused, so the concurrent result (200) matches no serial order.

Granularity of SIRead locks, measured:

| Read | SIRead locks held |
|---|---|
| `WHERE id IN (1, 2)` via primary key | 1 index page + 2 tuples |
| `WHERE id BETWEEN 5001 AND 5050` (50 rows, three on a shared page) | 3 heap pages |
| `WHERE branch = 'B01'` (sequential scan, 1,000 of 10,000 rows) | the whole relation |

Indexes matter for SERIALIZABLE: the narrower the read, the fewer false aborts.

<Pitfall>
SERIALIZABLE in PostgreSQL never blocks, but it **aborts**, and not only for real conflicts: sequential scans lock whole tables and more than two reads on one page lock the page. Every transaction at this level needs a retry loop, and the abort can arrive at `COMMIT`, after all the work is done. MySQL's SERIALIZABLE trades those aborts for lock waits and deadlocks.
</Pitfall>

## Real-world scenario: on-call doctors

A hospital rule says at least one doctor must stay on call per shift. Two doctors, both on call, each open the app and go off call at the same moment. Each transaction checks "count on call ≥ 2", sees 2, and updates **its own** row.

| Engine | Fix |
|---|---|
| PostgreSQL | Run the transaction at SERIALIZABLE and retry on 40001; or lock the shift's rows with `SELECT … FOR UPDATE` |
| MySQL | `SELECT … FOR UPDATE` on the shift's doctor rows (writers queue instead of deadlocking); SERIALIZABLE works but deadlocks |
| MongoDB | Update a shift document (e.g. `onCallCount` with `$inc` and a `$gte` filter) in the same transaction, so both transactions write it |

## Key takeaways

1. Write skew breaks a rule spread over several rows; snapshot isolation does not detect it (sum 200 in all three engines).
2. PostgreSQL SERIALIZABLE tracks reads with SIRead locks and aborts with 40001, possibly at commit.
3. SIRead locks are tuples, index pages, heap pages or whole tables; coarse locks cause false aborts, so good indexes help.
4. MySQL SERIALIZABLE converts in-transaction SELECTs to shared locks; write skew becomes a deadlock (1213).
5. MongoDB has no serializable level; make the transactions write a common document.
