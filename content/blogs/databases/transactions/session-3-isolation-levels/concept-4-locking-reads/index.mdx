<Tldr>
A **locking read** (`SELECT … FOR UPDATE` / `FOR SHARE`) does two things a plain `SELECT` does not: it reads the **newest committed** version, and it **locks** that row until the transaction ends. In one MySQL REPEATABLE READ transaction, a plain read returned **1000**, `FOR UPDATE` returned **900** (T2's commit) and the next plain read **1000** again. Used for read-modify-write, it makes the second transaction **wait** instead of overwriting: with application-computed values, T2 waited (≈ 1 s in MySQL), read **950**, wrote 850, and the final balance was **850** in both PostgreSQL and MySQL. Under PostgreSQL REPEATABLE READ, `FOR UPDATE` on a row changed after the snapshot raises **40001** instead. `NOWAIT` fails at once (`could not obtain lock on row`, MySQL error **3572**) and `SKIP LOCKED` returns only unlocked rows. MongoDB has no locking read: writing first (`findOneAndUpdate` with `$inc: { version: 1 }`) made the second transaction retry **14** times in 1.2 s and also ended at **850**.
</Tldr>

## Plain read vs locking read

| | Plain `SELECT` | `SELECT … FOR UPDATE` |
|---|---|---|
| Which version | The transaction's snapshot (Concept 1) | The newest committed version |
| Locks | None | Row lock until COMMIT/ROLLBACK |
| Other writers | Not affected | Wait (or fail with NOWAIT) |
| Other plain readers | Not affected | Not affected (MVCC) |

| Lock clause | PostgreSQL | MySQL | Blocks |
|---|---|---|---|
| `FOR UPDATE` | ✓ | ✓ | Every other locking read and every write of the row |
| `FOR NO KEY UPDATE` | ✓ (taken by ordinary UPDATEs: `pgrowlocks` showed `No Key Update` during `UPDATE … SET balance`) | – | Like FOR UPDATE, but lets `FOR KEY SHARE` through (foreign-key checks) |
| `FOR SHARE` | ✓ | ✓ (`LOCK IN SHARE MODE` is the old name) | Writes and FOR UPDATE; other FOR SHARE readers allowed |
| `FOR KEY SHARE` | ✓ (taken by foreign-key checks) | – | Only changes to the key |
| `NOWAIT` / `SKIP LOCKED` | ✓ | ✓ (8.0+) | Fail at once / skip locked rows |

| Term | Meaning |
|---|---|
| Read-modify-write | Read a value, compute in the application, write the result |
| **✓ Correct balance** | 850 after T1 (−50) and T2 (−100) |
| **✗ Error / skipped** | The locking read failed (40001, NOWAIT) or skipped the row |

<Pitfall>
A locking read only helps if **every** writer takes it. If one code path updates the row without `FOR UPDATE` and computes from a plain read, it can still overwrite. And `SKIP LOCKED` hides rows by design: using it in a report or a balance check silently returns partial results.
</Pitfall>

## Real-world scenario: seat booking

A booking service reads seat 14C, checks it is free, then marks it taken.

| Engine | Pattern | Behaviour under two concurrent bookings |
|---|---|---|
| PostgreSQL / MySQL | `SELECT … FROM seats WHERE id = ? FOR UPDATE`, check, `UPDATE` | Second booking waits, then sees "taken" and refuses |
| PostgreSQL / MySQL, many seats | `… FOR UPDATE SKIP LOCKED LIMIT 1` over free seats | Each booking gets a different free seat without waiting |
| PostgreSQL / MySQL, kiosk UI | `… FOR UPDATE NOWAIT` | Second user is told "being booked" at once |
| MongoDB | `findOneAndUpdate({ _id, status: 'free' }, { $set: { status: 'held' } })` | One request matches; the other gets null, no transaction needed |

## Key takeaways

1. A locking read returns the newest committed version and locks it; a plain read returns the snapshot.
2. In MySQL REPEATABLE READ, plain and locking reads in one transaction can disagree (1000 / 900 / 1000).
3. With FOR UPDATE on both sides, read-modify-write gave 850 in PostgreSQL and MySQL: the second transaction waited.
4. PostgreSQL REPEATABLE READ refuses to lock a row changed after the snapshot (40001); locking first narrows the window but does not close it, so keep a retry.
5. NOWAIT fails immediately; SKIP LOCKED skips locked rows; MongoDB gets the same effect with an early write and retries.
