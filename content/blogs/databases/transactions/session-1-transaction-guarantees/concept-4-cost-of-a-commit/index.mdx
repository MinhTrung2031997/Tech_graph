<Tldr>
The flush at each commit (Concept 3) is a fixed cost of roughly a millisecond, paid **per transaction**, not per row. 5,000 one-row updates as **5,000 transactions** took **3.5–4.6 s** in PostgreSQL, **5.3–7.1 s** in MySQL and **9–14 s** in MongoDB; as **one transaction** they took **0.13–0.15 s**, **0.10–0.12 s** and **0.50–0.52 s**. Concurrent clients share flushes (**group commit**): PostgreSQL went from 1,274 commits/s with 1 client to 12,027 with 16, MySQL from 352 to 4,066. The opposite extreme also hurts: a huge transaction holds locks and keeps old row versions alive until it ends, so batches of hundreds to a few thousand rows are the usual sweet spot.
</Tldr>

## Per-transaction vs per-row cost

| Work | Paid | Lab order of magnitude |
|---|---|---|
| Find and change the row, write its log records | Per row | ≈ 0.02–0.03 ms in PostgreSQL (warm cache) |
| Flush the log at commit | **Per transaction** | ≈ 0.6–1.4 ms on the lab disk |
| Round trip client ↔ server | Per statement | ≈ 0.02–0.1 ms through `docker exec` |

| Term | Meaning |
|---|---|
| Batching | Putting many changes in one transaction so they share one commit |
| Group commit | Concurrent transactions committing at the same moment share one fsync |
| **✓ Shared flush** | Many rows or transactions per fsync |
| **✗ Flush per row** | One fsync for every row changed |

## How big should a transaction be?

| Too small (one row each) | Too big (millions of rows) |
|---|---|
| One flush per row: 23–36× slower in PostgreSQL, 43–68× in MySQL | Row locks held until the end block other writers ([Session 5](/blogs/databases/transactions/session-5-locks-and-indexes/lab)) |
| Partial results visible while the job runs | Old row versions kept for the whole time: VACUUM / purge cannot clean ([Session 4](/blogs/databases/transactions/session-4-mvcc-internals/lab)) |
| | A failure throws away all the work; replicas apply it in one burst ([Session 8](/blogs/databases/transactions/session-8-when-transactions-hurt/lab)) |
| | MongoDB: a transaction is aborted after 60 s by default (`transactionLifetimeLimitSeconds`) |

A practical default for bulk jobs: commit every few hundred to a few thousand rows, and make each batch safe to retry.

<Pitfall>
Batching changes **when** the work becomes visible and **what** a failure undoes. A job that commits every 1,000 rows and crashes at row 5,500 has committed 5,000 rows: it must be able to resume (for example by processing rows in key order and remembering the last committed key), or be idempotent.
</Pitfall>

## Real-world scenario: the nightly price update

A job updates the price of 200,000 SKUs, one `UPDATE` per SKU in autocommit, and takes 4 minutes on a fast disk, longer on a cloud volume with 2 ms fsyncs.

| Version | Commits | Expected |
|---|---|---|
| Autocommit | 200,000 | ≈ 200,000 × flush cost |
| Batches of 1,000 | 200 | Seconds; each batch atomic and retryable |
| One transaction | 1 | Fastest, but every price row stays locked until the end |

## Key takeaways

1. A durable commit costs one log flush, about a millisecond on the lab disk, whatever the number of rows.
2. 5,000 one-row updates: 3.5–4.6 s vs 0.13–0.15 s (PostgreSQL), 5.3–7.1 s vs 0.10–0.12 s (MySQL), 9–14 s vs 0.5 s (MongoDB transaction).
3. Group commit shares flushes between concurrent clients: 1,274 → 12,027 commits/s from 1 to 16 clients in PostgreSQL.
4. MongoDB `bulkWrite` saves round trips but is not atomic; a transaction is.
5. Batch in moderate sizes and make each batch retryable; huge transactions bring locking and cleanup problems.
