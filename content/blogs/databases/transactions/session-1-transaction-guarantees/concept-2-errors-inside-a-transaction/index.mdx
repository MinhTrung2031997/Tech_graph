<Tldr>
A transaction is all-or-nothing only if the failure **ends** it. The engines disagree on what a failed statement does to the transaction around it. **PostgreSQL** puts the transaction into an aborted state: every later command fails with "current transaction is aborted", and `COMMIT` replies `ROLLBACK`. **MySQL** undoes only the failing statement and keeps the transaction open, so a `COMMIT` after the error **committed the credit**: the total became 10,001,500, exactly as without a transaction. **MongoDB** aborts the transaction on the server; the next operation and the commit fail with `NoSuchTransaction`. **Savepoints** give PostgreSQL and MySQL partial rollback on purpose; psql's `ON_ERROR_ROLLBACK` uses them automatically and reproduced MySQL's behaviour, including the created money.
</Tldr>

## Three reactions to one error

| Engine | After the failed statement | What `COMMIT` does | Total after `COMMIT` |
|---|---|---|---|
| PostgreSQL | Transaction **aborted**: every command fails until `ROLLBACK` | Replies `ROLLBACK` | 10,000,000.00 |
| MySQL | Only the **statement** is undone; the transaction continues | Commits what succeeded | **10,001,500.00** |
| MongoDB | Transaction **aborted on the server** | Fails: `NoSuchTransaction` | 10,000,000.00 |

| Term | Meaning |
|---|---|
| Statement-level rollback | The failed statement's own changes are undone; earlier statements stay |
| Transaction-level abort | All changes since `BEGIN` are discarded |
| Savepoint | A named point inside a transaction to roll back to without ending the transaction |
| **✓ Safe** | The end state is all-or-nothing |
| **✗ Partial** | Some statements of the transaction were committed |

<Pitfall>
A MySQL client that runs a script and ignores errors (`mysql --force`, many migration tools, a `try/except: pass` in application code) followed by `COMMIT` commits whatever succeeded. The lab did exactly that and created 1,500. In MySQL the safety of a transaction depends on the code that handles errors, not on the database.
</Pitfall>

## Real-world scenario: the batch import that "mostly" worked

A nightly job imports 10,000 payments in one transaction per file, in MySQL, with a loop that logs and skips failed rows before a final `COMMIT`. A malformed file produces 300 errors; the commit makes the other 9,700 permanent and the reconciliation report is off by 300 payments. Moving the same job to PostgreSQL makes the first error abort the file.

| Goal | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| All or nothing per file | Default | `ROLLBACK` on the first error | Default |
| Skip bad rows, keep the rest | `SAVEPOINT` per row (or validate first) | Default, but log the skipped rows | One transaction per row, or validate first |

## Key takeaways

1. PostgreSQL aborts the transaction on any error; `COMMIT` then answers `ROLLBACK`.
2. MySQL undoes only the failed statement; a later `COMMIT` commits the rest (10,001,500 in the lab).
3. MongoDB aborts the transaction on the server; later operations fail with `NoSuchTransaction`.
4. Savepoints allow deliberate partial rollback in PostgreSQL and MySQL; MongoDB has none.
5. psql `ON_ERROR_ROLLBACK` and similar driver options silently give PostgreSQL MySQL-style behaviour.
