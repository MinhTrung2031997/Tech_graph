<Tldr>
Data pages are written to disk lazily; what makes a commit **durable** is a small **log record** forced to disk (`fsync`) before `COMMIT` returns. After a crash the engine replays the log. Every engine lets you skip or delay that flush for speed, at the price of losing the last commits in a crash (never of corrupting data). In the lab, one client updating one row per transaction managed **1,564 commits/s** in PostgreSQL with `synchronous_commit = on` and **36,110/s** with `off`. MySQL defaults to two flushes per commit (redo log and binary log); 5,000 autocommitted updates caused about **5,300 redo-log fsyncs**. In MongoDB, 5,000 updates took **9.0–14.2 s** with the default write concern `w: "majority"` and **0.56–0.70 s** with `w: 1, j: false`.
</Tldr>

## Where a commit goes

| Engine | The log that makes a commit durable | Flushed at commit by default | Relaxed by |
|---|---|---|---|
| PostgreSQL | WAL (write-ahead log) | Yes (`synchronous_commit = on`) | `synchronous_commit = off` (per transaction, session, role or database) |
| MySQL InnoDB | Redo log, plus the binary log when enabled (default in 8.x) | Yes (`innodb_flush_log_at_trx_commit = 1`, `sync_binlog = 1`) | `innodb_flush_log_at_trx_commit = 2` or `0`, `sync_binlog = 0` or N (server-wide only) |
| MongoDB | Journal (WiredTiger log) and, on a replica set, the oplog on a majority of members | Default write concern `w: "majority"` waits for a majority, journaled | Write concern per operation: `w: 1`, `j: false`, `w: 0` |

| Term | Meaning |
|---|---|
| fsync | System call that returns only when the data is on stable storage; ≈ 0.5–3 ms on the lab's Docker disk |
| Group commit | Several transactions waiting to commit share one fsync |
| Crash window | Commits acknowledged to the client but lost if the server crashes now |
| **✓ Durable** | The commit survives a crash of the database server |
| **✗ At risk** | The client was told "committed", but a crash can lose it |

<Pitfall>
Relaxed durability is invisible in testing: nothing is lost until a crash. Decide per kind of data. Payments, orders and anything a customer was told "done" need the default flush; metrics, sessions and caches can usually afford `synchronous_commit = off` or `w: 1`. Never turn off `fsync` itself (PostgreSQL `fsync = off`): that risks corruption, not just lost commits.
</Pitfall>

## Real-world scenario: the slow event log

An event-tracking service writes 3,000 one-row inserts per second into PostgreSQL and its latency doubles at peaks; disk graphs show fsync-bound WAL writes. The same database also stores orders.

| Option | Effect | Risk |
|---|---|---|
| `ALTER ROLE events_writer SET synchronous_commit = off` | Event inserts stop waiting for fsync (23× in the lab) | Last ≈ 0.6 s of events lost on a crash |
| Batch events (Concept 4) | One commit per 100–1,000 events | A failed batch must be retried |
| Keep orders on the default | Orders stay durable | None |

## Key takeaways

1. A commit is durable when its log record is on disk; data pages follow later.
2. PostgreSQL `synchronous_commit = off` (per session or transaction) gave 36,110 vs 1,564 commits/s, at the price of losing the last ≈ 0.6 s on a crash.
3. MySQL flushes the redo log and the binary log at each commit by default; relaxing them is server-wide.
4. MongoDB's default write concern is `w: "majority"`; `w: 1, j: false` was 13–25× faster in the lab but can lose ≈ 100 ms of writes.
5. Relaxed durability loses recent commits but does not corrupt data; `fsync = off` does.
