<Tldr>
A **transaction** groups statements so that they take effect **all together or not at all**. Without one, every statement is its own transaction (**autocommit**), and a failure in the middle leaves the work half done. In the lab, a transfer of 1,500 from account 1 (balance 1,000) to account 2 ran as two statements: the credit committed, the debit failed the `balance >= 0` rule, and the bank's total grew from **10,000,000 to 10,001,500** in PostgreSQL, MySQL and MongoDB alike. Inside a transaction the same failure left the total at **10,000,000**. ACID names four promises; this session covers **A**tomicity and **D**urability, Sessions 2 and 3 cover **I**solation.
</Tldr>

## The four promises

| Letter | Promise | What breaks without it | Where in this course |
|---|---|---|---|
| **A**tomicity | All statements of a transaction take effect, or none do | Half-finished transfers, orders without their items | This concept and Concept 2 |
| **C**onsistency | Every commit leaves the data valid under the declared rules (CHECK, UNIQUE, foreign keys) | Negative balances, orphan rows | The CHECK constraint in this lab |
| **I**solation | Concurrent transactions do not see each other's partial work | Anomalies: lost updates, write skew | [Session 2](/blogs/databases/transactions/session-2-anomalies/concept-1-dirty-reads), Session 3 |
| **D**urability | Once `COMMIT` returns, a crash does not undo it | Confirmed payments that vanish after a power cut | Concepts 3 and 4 |

Consistency is partly the application's job: the database only enforces the rules you declare. The lab's `accounts` table declares `CHECK (balance >= 0)`; MongoDB gets the same rule from a collection validator.

## Autocommit: every statement is a transaction

| Engine | Default | How to group statements |
|---|---|---|
| PostgreSQL | Each statement commits on its own (psql and drivers send no `BEGIN`) | `BEGIN … COMMIT` |
| MySQL | `autocommit = 1`: each statement commits on its own | `START TRANSACTION … COMMIT`, or `SET autocommit = 0` |
| MongoDB | Each **single-document** write is atomic on its own; nothing groups documents | `session.startTransaction()` … `commitTransaction()` (replica set or sharded cluster only) |

| Term | Meaning |
|---|---|
| Transfer | Credit account 2 with 1,500, debit account 1 by 1,500; both start at 1,000 |
| Total | `sum(balance)` over the 10,000 accounts: 10,000,000.00 before every run |
| **✓ Committed** | The change is permanent and visible to others |
| **✗ Rejected** | The statement failed the `balance >= 0` rule and changed nothing |

<Pitfall>
"Each statement is atomic" is not the same as "my operation is atomic". An ORM call such as `account.save()` followed by `other.save()` is two transactions unless the code opens one around them. The lab total grew by 1,500 in every engine, with no error that the second call could not have reported anyway.
</Pitfall>

## Real-world scenario: the order without items

A checkout inserts an `orders` row, then its `order_items`, then decrements stock, each through a separate repository call with autocommit. A timeout on the third call leaves a paid order with items but untouched stock; a crash after the first leaves an order with no items at all. Support finds them weeks later.

| Fix | Effect |
|---|---|
| One transaction around the three writes | All or nothing |
| Constraints for the invariants (`stock >= 0`, foreign keys) | The database rejects invalid states, even from buggy code |
| Idempotent retry of the whole transaction | Safe to repeat after a timeout ([Session 7](/blogs/databases/transactions/session-7-application-patterns/lab)) |

## Key takeaways

1. A transaction makes a group of statements all-or-nothing; without one, each statement commits by itself.
2. PostgreSQL and MySQL default to autocommit; MongoDB writes are atomic per document only.
3. A transfer split into two autocommitted statements created 1,500 out of nothing in all three engines.
4. Declared rules (CHECK, validators) give the C in ACID; the database enforces only what you declare.
5. MongoDB multi-document transactions need a replica set or sharded cluster.
