<ArticleStack>

A **race condition** is a type of bug that happens when **two or more operations run at the same time**, and the **final result depends on the order** in which they finish. Because the order is unpredictable, you can get **wrong, inconsistent, or unexpected results**.

<Divided>

## Database Locking

(Pessimistic Locking)

Also known as:

- SQL row-level locks
- `SELECT ... FOR UPDATE`
- Document-level lock (like in MongoDB transactions)

**How it works**

When a transaction reads a row, it **locks that row** so no other transaction can modify it until the lock is released.

Example (SQL):

```sql
BEGIN;
SELECT * FROM tickets WHERE id = 1 FOR UPDATE;
UPDATE tickets SET status = 'BOOKED';
COMMIT;
```

Only **one** transaction can lock the row.

<SplitPair>
  <SplitCol title="Pros">

- **Absolute correctness** → no overselling, no inconsistent writes.
- **Easy to implement** inside a monolithic or single-database system.
- Works well when data is stored in a **relational DB**.
- The database guarantees strong consistency.

</SplitCol>
  <SplitCol title="Cons">

- Risk of:
  - Deadlocks
  - Long waiting times
  - Performance bottlenecks under high load
- Not ideal for **high concurrency** (thousands of requests per second).

</SplitCol>
</SplitPair>

## Optimistic Locking

(+ Versioning)

Used widely in:

- JPA/Hibernate (`@Version`)
- MongoDB with version fields
- REST APIs with `etag`

**How it works**

Instead of locking, each row/document has a **version number**.

**Flow:**

1. Read record → version = 5
2. Modify data
3. Write with condition: version must still be 5
4. If another request wrote first → version changed → your update fails → retry

**Example**

```sql
UPDATE tickets
SET reserved_by = 'userA', version = version + 1
WHERE id = 1 AND version = 5;
```

If affected rows = **0**, another process won → retry.

<SplitPair>
  <SplitCol title="Pros">

- **High performance**: no locking, no blocking.
- Works very well for:
  - Microservices
  - Distributed systems
- Prevents lost updates clearly.
- Good for use cases where *conflicts are rare*.

</SplitCol>
  <SplitCol title="Cons">

- If the conflict rate is high → many retries → waste of resources.
- More complex with large transactions.
- Requires retry logic.

</SplitCol>
</SplitPair>

## Atomic Operations

(Database or Redis)

**How it works**

You let the database or Redis perform the entire operation in **one atomic instruction** so no two processes can break it.

**Examples:**

**SQL Atomic Update:**

```sql
UPDATE inventory SET stock = stock - 1 WHERE id = 1 AND stock > 0;
```

**Redis Atomic Increment:**

```text
INCR counter
```

<SplitPair>
  <SplitCol title="Pros">

- Extremely fast (especially Redis)
- No locks needed
- Perfect for counters, stock decrement, rate limiters

</SplitCol>
  <SplitCol title="Cons">

- Limited: only works for condition updates
- Not suitable for complex transactions
- Redis requires consistent distributed architecture (Redis cluster)

</SplitCol>
</SplitPair>

## Distributed Lock

(Redis, ZooKeeper, Consul)

**How it works**

Processes acquire a **distributed mutex** before updating shared data.

Example with Redis Redlock:

```javascript
LOCK_KEY(product:1)
do work
UNLOCK
```

Multiple servers share the lock.

<SplitPair>
  <SplitCol title="Pros">

Works across multiple servers, microservices, containers.

</SplitCol>
  <SplitCol title="Cons">

- Hard to implement correctly (especially Redis Redlock reliability debates).
- If lock server goes down → risk of stale locks.
- Slower than DB locks.

</SplitCol>
</SplitPair>

## Message Queue

(Serializing Requests)

**Examples:**

- Kafka
- RabbitMQ
- SQS

**How it works**

Instead of handling concurrent writes directly, you **put all requests into a queue**.

A worker processes them **one by one**, guaranteeing correct order.

**Example flow:**

1. API receives “book ticket”
2. Pushes message to queue
3. Worker processes strictly in order:
   - Check availability
   - Decrease stock
   - Confirm booking

<SplitPair>
  <SplitCol title="Pros">

- Zero race conditions (only one consumer)
- Highly scalable
- Very reliable for high-volume systems
- Decouples front-end API and backend worker

</SplitCol>
  <SplitCol title="Cons">

- Adds architectural complexity
- Requires async architecture
- User may not get instant confirmation (unless using callback or polling)
- Harder to debug

</SplitCol>
</SplitPair>

## Unique Constraints

(Database-level Check)

**Example:**

```sql
CREATE UNIQUE INDEX unique_seat ON bookings(seat_id);
```

If two users try to book the **same seat**, the database rejects one automatically.

<SplitPair>
  <SplitCol title="Pros">

- Very simple & extremely reliable
- Zero race condition for uniqueness constraints
- Database ensures correctness

</SplitCol>
  <SplitCol title="Cons">

- Only solves **duplicate insert** race conditions
- Does not prevent race conditions that modify existing rows

</SplitCol>
</SplitPair>

## Recommended Solution

### Strict correctness

**If you need strict correctness (tickets, money, stock):**

**Use atomic update or pessimistic locking**

This is the most reliable and simplest.

**Why?**

- Always accurate
- Database guarantees consistency
- Easy to reason about

### High concurrency

**For high concurrency systems (1000s RPS):**

**Atomic Update + Message Queue**

Best combination for scaling.

### Microservices

**For microservices architecture:**

**Optimistic Locking (versioning)**

Because:

- No blocking
- Very high performance
- Ideal for distributed architecture

### Shared resources

**For distributed shared resources:**

**Distributed locks (Redis/ZooKeeper)**

### Summary

| Use Case | Best Solution |
| --- | --- |
| Ticket booking | Pessimistic lock OR atomic update |
| High concurrency flash sale | Queue + Atomic update |
| Money transfer | Pessimistic lock + Transactions |
| Microservices writing same data | Optimistic locking |
| Distributed workers | Redis/Zookeeper locks |
| Prevent duplication | Unique constraint |
| Simple counter (likes/views) | Redis atomic ops |
