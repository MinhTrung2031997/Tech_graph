## Event Loop — interview answer

"JavaScript executes code on a single thread, meaning there is only one Call Stack and it can run one thing at a time. If we waited for every network request or timer to finish, the whole application would freeze. The Event Loop is the mechanism that solves this.

When code runs, synchronous functions are pushed onto the Call Stack and popped off when they finish, in LIFO order. When we hit an asynchronous operation, like setTimeout, an HTTP request or reading a file, JavaScript doesn't wait. It hands that work to the runtime: Web APIs in the browser, or libuv in Node.js. Then it keeps executing the next line.

When the async work completes, its callback isn't executed immediately. It is placed into a queue. Promise callbacks are queued as soon as the Promise settles. There are two types of queue:

</Divided>
  <SplitPair>
    <SplitCol title="Microtask Queue">

the Microtask Queue: Promise .then/.catch/.finally, await continuations, queueMicrotask; in Node.js also process.nextTick, which has its own queue with even higher priority.

</SplitCol>
    <SplitCol title="Macrotask Queue">

the Macrotask Queue, also called the Task Queue: setTimeout, setInterval, I/O callbacks, UI events, and setImmediate in Node.js.

</SplitCol>
  </SplitPair>
  <Divided>

The rule is: wait until the Call Stack is empty, run all microtasks, then run one macrotask, then all microtasks again, and repeat. Microtasks always cut in line, so a resolved Promise runs before a setTimeout of zero scheduled at the same time. For example: log 'A', set a timeout logging 'B', resolve a Promise logging 'C', log 'D'. The output is A, D, C, B.

In Node.js, macrotasks are not one single queue. libuv runs them in six phases, and each phase has its own queue:

1. Timers: runs setTimeout and setInterval callbacks whose delay has expired. The delay is a minimum, not an exact time.
2. Pending callbacks: a few system-level callbacks deferred from the previous loop, like certain TCP errors.
3. Idle / prepare: internal to Node, not something we use.
4. Poll: the most important one. It runs I/O callbacks such as file reads, network responses and database results. If there's nothing to do, it waits here for new I/O, but only until the next timer is due. If setImmediate callbacks are waiting, it stops waiting and moves on.
5. Check: runs setImmediate callbacks, right after poll.
6. Close callbacks: cleanup events like socket.on('close').

</Divided>
