The SOLID principles are a set of five design principles for writing maintainable and scalable software.

<Divided>

## 1. Single Responsibility Principle (SRP):

- A class should have only one reason to change, meaning it should have only one responsibility.
- Key Benefits:
  - Improves code readability and reusability.
  - Reduces the risk of unintended side effects during modifications.
  - Simplifies debugging and testing.

```typescript
class UserService {
  // Handle user-related operations
  createUser(user: User) {
    // Implementation for creating a user
  }

  updateUser(user: User) {
    // Implementation for updating a user
  }

  deleteUser(userId: string) {
    // Implementation for deleting a user
  }
}

class EmailService {
  // Handle email-related operations
  sendEmail(user: User, message: string) {
    // Implementation for sending an email
  }
}
```

## 2. Open/Closed Principle (OCP):

- A class, module, or function should be **opened for extension** but **closed for modification**.
- Key Benefits
  - Reduces the need to alter existing, stable code.
  - Makes the system easier to extend and maintain.
  - Encourages the use of abstractions (e.g., interfaces, inheritance, or composition).

```typescript
class Shape {
  getArea(): number {
    throw new Error("Method not implemented.");
  }
}

class Circle extends Shape {
  radius: number;

  constructor(radius: number) {
    super();
    this.radius = radius;
  }

  getArea(): number {
    return Math.PI * this.radius ** 2;
  }
}

class Rectangle extends Shape {
  width: number;
  height: number;

  constructor(width: number, height: number) {
    super();
    this.width = width;
    this.height = height;
  }

  getArea(): number {
    return this.width * this.height;
  }
}
```

## 3. Liskov Substitution Principle (LSP):

- Objects of a superclass should be replaceable  /rɪˈpleɪ.sə.bəl/ with objects of a subclass without affecting the correctness of the program
- Key Benefits:
  - Ensures that the inheritance hierarchy is logical and reliable.
  - Prevents unintended behavior when using subclasses in place of base classes.
  - Promotes consistency and reliability in code, especially in polymorphic scenarios.

```typescript
class Bird {
  fly(): void {
    // Implementation for flying
  }
}

class Sparrow extends Bird {
  // Specific implementation for Sparrow
}

class Penguin extends Bird {
  // Specific implementation for Penguin
  fly(): void {
    throw new Error("Penguins cannot fly.");
  }
}
```

## 4. Interface Segregation Principle (ISP):

- A client should not be forced to depend on interfaces it does not use. In other words, it's better to have multiple, specific interfaces rather than a single, general-purpose one.
- Key Benefits:
  - Reduces the complexity of interfaces by keeping them focused on specific client needs.
  - Makes the code more flexible and easier to refactor.
  - Avoids unnecessary dependencies and promotes better separation of concerns.

```typescript
interface CanFly {
  fly(): void;
}

interface CanSwim {
  swim(): void;
}

class Bird implements CanFly {
  fly(): void {
    // Implementation for flying
  }
}

class Fish implements CanSwim {
  swim(): void {
    // Implementation for swimming
  }
}
```

## 5. Dependency Inversion Principle (DIP):

- High-level modules should not depend on low-level modules. Both should depend on abstractions. Additionally, abstractions should not depend on details; details should depend on abstractions.
- Key Benefits:
  - Reduces tight coupling between components, making the system easier to maintain and extend.
  - Increases flexibility by allowing easier swapping of implementations.
  - Encourages the use of dependency injection, which improves testability and modularity.

```typescript
// Abstraction (Interface)
interface Logger {
  log(message: string): void;
}

// Low-level module
  class ConsoleLogger implements Logger {
  log(message: string): void {
    console.log(`[Console] ${message}`);
  }
}

// Another low-level module class FileLogger implements Logger {
  log(message: string): void {
    // Logic to log to a file
    console.log(`[File] ${message}`);
  }
}

// High-level module depending on abstraction
class MessageProcessor {
  private logger: Logger;

  constructor(logger: Logger) {
    this.logger = logger;
  }

  processMessage(message: string): void {
    // Some processing logic

    // Logging using the injected logger
    this.logger.log(message);
  }
}

// Example usage
const consoleLogger = new ConsoleLogger();
const fileLogger = new FileLogger();

const messageProcessorWithConsoleLogger = new MessageProcessor(consoleLogger);
messageProcessorWithConsoleLogger.processMessage("Message with console logger");

const messageProcessorWithFileLogger = new MessageProcessor(fileLogger);
messageProcessorWithFileLogger.processMessage("Message with file logger");
```

In this example:

- **`Logger`** is the abstraction (interface) that both **`ConsoleLogger`** and **`FileLogger`** implement.
- **`MessageProcessor`** is a high-level module that depends on the **`Logger`** abstraction.
- Instead of directly depending on specific implementations (**`ConsoleLogger`** or **`FileLogger`**), **`MessageProcessor`** receives a **`Logger`** through its constructor. This allows you to easily switch between different logger implementations without modifying the **`MessageProcessor`** class.
- This approach adheres to the Dependency Inversion Principle by ensuring that high-level modules depend on abstractions (interfaces) rather than concrete low-level implementations.
