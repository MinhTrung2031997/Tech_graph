## Foundation

What is SQL isolation?

- In relational databases, multiple transactions often run at the same time (concurrency). Isolation ensures that each transaction behaves as if it’s running alone, even though in reality the DB is multitasking.
- Isolation prevents incorrect reads, race conditions, phantom rows, dirty data, and ensures correctness.

## Why

Why is isolation needed?

✔ Many users

✔ Many writes

✔ Many reads

✔ High concurrency

✔ Different transactions touching the same rows

→ Without isolation, anomalies occur.

## Anomalies

Concurrency problems (anomalies).

### Dirty read

Transaction A reads data that Transaction B has written but not committed.

**Example:**

```text
T1: UPDATE accounts SET balance = 0 WHERE id = 1;   -- not committed
T2: SELECT balance FROM accounts WHERE id = 1;      -- sees 0 (dirty)
T1: ROLLBACK;
```

T2 reads data that never became real.

► Dangerous when reading money, inventory, scores, status flags.

### Non-repeatable read

A transaction reads the same row twice but gets different values because another transaction modified it.

```text
T1: SELECT balance FROM accounts WHERE id = 1;    -- balance = 200
T2: UPDATE accounts SET balance = 100 WHERE id=1; -- commit
T1: SELECT balance FROM accounts WHERE id = 1;    -- balance = 100
```

► The row changed inside a transaction → broken read stability.

### Lost update

Two writes overwrite each other.

```text
T1: SELECT balance = 200
T2: SELECT balance = 200

T1: UPDATE balance = 150
T2: UPDATE balance = 100  <-- overwrites T1
```

► Happens in wallet, inventory, bank, booking systems.

### Phantom read

A transaction queries a range twice, but new rows appear.

```text
T1: SELECT * FROM orders WHERE amount > 100  -- gets 5 rows
T2: INSERT INTO orders(amount) VALUES (200)
T1: SELECT * FROM orders WHERE amount > 100  -- now 6 rows
```

► Affects analytics, pagination, counting, searching tables.

## Isolation levels

SQL standard isolation levels.

### Read uncommitted

- **Description**: The lowest isolation level. Transactions can read uncommitted changes made by other transactions.
- **Prevents**: None (dirty reads, non-repeatable reads, and phantom reads can all occur).
- **Use Case**: Rarely used; suitable only for scenarios where performance is more critical than accuracy /ˈæk.jɚ.ə.si/, such as logging or reporting on volatile /ˈvɒl.ə.taɪl/ data.

### Read committed

Postgres default.

- **Description**: A transaction can only read data that has been committed. Uncommitted changes are not visible.
- **Prevents**: Dirty reads.
- **Allows**: Non-repeatable reads and phantom reads.
- **Use Case**: Most common default isolation level (e.g., in PostgreSQL and SQL Server). Suitable for applications where avoiding dirty reads is sufficient.

### Repeatable read

MySQL default.

- **Description**: Ensures that if a transaction reads a record, no other transaction can modify that record until the first transaction completes.
- **Prevents**: Dirty reads and non-repeatable reads.
- **Allows**: Phantom reads.
- **Use Case**: Scenarios requiring consistent reads of the same data, such as financial calculations.

### Serializable

- **Description**: The highest isolation level. Transactions are executed in a way that they appear to run sequentially (one after another), even if they are executed concurrently.
- **Prevents**: Dirty reads, non-repeatable reads, and phantom reads.
- **Use Case**: Scenarios requiring the highest level of consistency, such as critical financial operations. It may reduce performance due to increased locking and contention.

## Implementation

How databases implement isolation (internal techniques).

There are two big families:

</SplitLead>
<SplitCol title="Lock-based">

**Lock-based concurrency control**

- **shared Lock**: Allows multiple transactions to read a resource but prevents writes.
- **Exclusive Lock**: Prevents other transactions from reading or writing a resource.
- Range locks for preventing phantom reads

**Used by:** SQL Server, MySQL (InnoDB uses combination of locks + MVCC)

Pros: strong consistency

Cons: deadlocks, blocking

</SplitCol>
<SplitCol title="MVCC">

**MVCC (Multi-Version Concurrency Control)**

Most modern databases use this.

- Writers **do not block** readers
- Readers **read snapshots** in the past
- When updating, new row versions are created

**Used by:** PostgreSQL, MySQL InnoDB (partial), Oracle

Pros:

✔ high performance

✔ avoid read locks

✔ consistent snapshots

Cons:

✘ vacuuming / old versions overhead

✘ serializable isolation requires more computation
